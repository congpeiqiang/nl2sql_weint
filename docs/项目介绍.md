# NL2SQL 智能问数系统 — 项目介绍

---

## 一、项目概述

**NL2SQL 智能问数系统**：用户以自然语言提问，系统自动完成「Schema 理解 → SQL 生成 → 只读执行 → 结果/图表/报告输出」的全链路数据分析智能体产品，并对每一次查询做全链路可观测（Langfuse）、五维自动评估与 BadCase 迭代闭环。

一句话概括架构：

> **1 主 Agent（意图路由 + 异步委派）＋ 1 子 Agent（NL2SQL 数据执行）＋ 14 个 Skill（Wren 语义层 SOP 六步单循环）＋ WrenAI 语义层 / 直连双通道 ＋ Langfuse 监控评估迭代闭环。**

参考论文：*SQL-of-Thought: Multi-agentic Text-to-SQL with Guided Error Correction* (Chaturvedi et al., 2025)。系统初版按该论文实现阶段化流水线（已归档 `shared/skills_bak/`），后演进为以 **WrenAI 官方 SOP** 为骨架的六步单循环编排，论文的**错误分类法引导纠错**思想在现行纠错环中保留。

### 解决的核心问题

Text-to-SQL 落地产品的三大难点及本项目的应对：

1. **准确率** — Schema 幻觉、业务口径歧义、复杂 SQL 一次生成正确率低 → 六步 SOP 单循环 + 具名指标 Cube 硬车道 + 错误分类法引导纠错
2. **安全性** — LLM 生成 SQL 存在写库/DDL/全表拖取风险 → SQL 只读硬拦截 + 文件沙箱 + 执行护栏三层防护
3. **可迭代性** — 效果难以量化、Prompt 改动缺乏回归保障 → 五维评分 + BadCase 数据集 + 离线/在线双门禁的灰度发布体系

## 三、架构设计

### 3.1 总体架构

```
前端 (Next.js, SSE 流式 + 轮询)
   │  POST /threads/{id}/runs/stream
   ▼
LangGraph API Server (:2026)
   ├─ graph.json 注册 2 个 graph
   ├─ LANGGRAPH_HTTP → custom_app.py（90+ 自定义路由与原生路由同进程同端口）
   ├─ checkpointer → AsyncPostgres / AsyncSqlite（按 thread_id 隔离会话）
   │
   ├── chat_agent（主 Agent）
   │     意图路由 → start_async_task 异步委派 → check_async_task 结果汇总
   │     → generate_echarts（图表）→ build_report（报告）
   │     12 个中间件 · CompositeBackend VFS · 声明式文件权限
   │
   └── nl2sql_agent（NL2SQL 子 Agent，独立 thread/run）
         Wren SOP 六步单循环：四路取料 → 澄清 → 判路由(Cube/混合/手写)
         → dry_run 修正 → 性能优化 → run_sql（失败纠错 ≤3 轮）
         双通道路由 · SQL 只读硬拦截 · 8 个 wren-* Skill 按需加载
              │                │
              ▼                ▼
      WrenAI MCP 语义层     DB MCP Server（自建 FastMCP，stdio 子进程）
      wrenai_<库>_* 工具链   dbmcp_run_sql / dbmcp_get_db_info
              │                │
              └───────┬────────┘
                      ▼
        目标数据库：MySQL / PostgreSQL / ClickHouse / SQLite

支撑系统（横切）：
├─ Langfuse：trace / 五维评分 / prompt 版本 / Dataset:badcase —— 监控评估迭代闭环
├─ WorkspaceManager + AGENT_DATA_ROOT：工作区数据外置、多用户隔离
├─ 本地事件日志 traces.sqlite：实时事件/谱系/统计 API 数据源
```

### 3.2 多智能体架构（双 Graph + 异步委派）

- **主 Agent（chat_agent）**：负责意图识别（一般对话/数据查询/图表/报告）、子 Agent 委派与结果汇总。意图路由不是硬编码分支，而是 **system prompt 意图表 + 关键词中间件注入**，前端关键词与后端触发规则零漂移。
- **子 Agent（nl2sql_agent）**：独立注册为另一个 graph，通过 deepagents 异步子 Agent 机制（`start_async_task`）在**独立 thread + 独立 run** 中执行长流水线，主 Agent 本轮立即返回，不阻塞用户交互。
- **自动续跑链**：同步 watcher（守护线程）每 0.5s 读取子 run 状态，经 LangGraph SDK `threads.update_state` 写回主线程 state（`async_tasks`/`query_headers`/`active_queries`），前端轮询到终态后发起 auto-continue run，主 Agent 调 `check_async_task` 取结果并生成图表/报告。
- **并发多查询**：state 字段用 `Annotated[..., _merge_dict_by_key]` reducer 按 task_id 键控合并，多个子任务并行写回互不覆盖；进度按查询分组展示步骤与耗时。

### 3.3 NL2SQL 推理流水线（Wren 语义层 SOP 六步单循环）

Skill = `SKILL.md`（frontmatter 触发条件）+ `references/`（判据表/输出契约）+ `scripts/`，位于 `/shared/skills/nl2sql/` 的 **`wren-*` 系列 8 个技能**（编排器 + 6 个循环内能力技能 + 1 个循环外回写规范），由 `SkillsMiddleware` 注入、每步执行前按需加载。**流水线逻辑由 prompt + skill 驱动，而非手写 StateGraph 节点**——这是本项目与典型 LangGraph 教程项目的重要架构差异。

编排哲学：**单 Agent、工具优先、循环式**（WrenAI 官方 `wren_workflow` 落地，扩展「用户澄清」与「SQL 性能优化」两步）：

```
问句
 └─(1) wren-retrieve：四路并行取料一次取齐——结构(get_context) / 范例(recall_queries)
        / 规则(get_instructions) / 知识(list_knowledge)，四工具全程各至多一次
 └─(2) wren-clarify：依取料包裁决清晰度；不清晰 → [需要澄清] 停止本轮（追问上限 1 次）
 └─(3) 判路由（零工具调用，按「具名指标三条件」三分流）：
        三条件全满足        → 纯 Cube 车道（wren-metric-query → query_cube）
        ①②满足、③维度缺    → Cube 出主体 + 手写包外层（混合）
        measure 匹配不上 / cube 表达不了 → 手写 SQL（wren-sql-author，须写明为何不走 cube）
 └─(4) dry_run 验证 → 失败即改（回对应能力技能修正，≤3 次）
 └─(5) wren-perf-optimize：规则集检测 + 语义不变优化；改过必重 dry_run
 └─(6) wren-execution：run_sql(sql, limit=N) → 输出答案
        （执行失败 → 九大类错误分类法纠错环 ≤3 轮）
```

**具名指标三条件**（路由判据）：① 问题含聚合意图（总额/数量/平均/占比/去重计数/TopN）；② 能锁定某 cube 的某 measure——匹配只看 measure 的 `expression`（永不读 `type`，wren_core 编译忽略它）与 glossary/metrics 术语映射；③ 过滤/分组维度都在该 cube 的 dimensions/time_dimensions 内。三条件全满足**必须**走 Cube 车道，手写出等价 SQL 也算违规（无一致性校验兜底）；多时间轴场景用多次 `query_cube` 并列而非手写豁免。

设计原则（均经实践验证）：

1. **口径只认 Cube/知识料**——Cube 已声明口径禁止手写重算，聚合语义只认 `expression`；「口径硬车道」是数字一致性的机制保障
2. **dry_run 门 + 最终复验**——未 dry_run 通过禁止执行；SQL 在执行前被改动必须用最终 SQL 重跑 dry_run，杜绝"干跑 A 执行 B"
3. **行数契约**——SQL 正文不写 LIMIT，top-N 用 ORDER BY，行数上限由 `run_sql(sql, limit=N)` 服务端控制（避免双重 LIMIT 语法冲突）
4. **分类法引导纠错**——syntax/schema_link/join/filter/aggregation/value/subquery/set_ops/other 九大类 + 精简错误编码（如 `join_missing`）做 CoT 诊断；相同编码连续 2 次判"卡住"即终止，每次纠错从零开始不携带前次闲聊历史
5. **禁止会话内回写**——`store_query` 移出循环：LLM 自评"答对"无外部真值，错误范例一旦写入记忆库会被 `recall_queries` 召回当样板复利污染；回写唯一路径是 FeedbackStore 桥接任务（用户👍=L1 / 人工金标=L2）循环外异步执行
6. **复杂问题临时拆分**——不预设固定子问题分解阶段，多业务问题临时拆 2~3 个子问题各跑 (3)~(6) 再合并作答

步骤间数据传递：上下文注入优先，仅 >15KB 或技能明确要求时落盘 `/workspace/nl2sql_process_data/{thread_id}/skill_sop/`；大结果在工具边界自动落盘瘦身（消息内只留 20 行样例 + `row_count` + 全量文件路径），最终回复遵循"结论 + 样例表 + 全量文件"契约。

### 3.4 双通道路由与多库语义层

- **语义层通道**：每个已建模数据库独立启动一个 WrenAI MCP server，工具命名空间按库隔离（`wrenai_imdb_run_sql`、`wrenai_wit_get_context` 等），提供 MDL 转换、语义检索（get_context）、相似 NL→SQL 示例召回（recall_queries）、Cube 指标查询（query_cube）。
- **直连通道**：自建 FastMCP 服务（stdio 子进程），`dbmcp_run_sql`/`dbmcp_get_db_info` 两个工具，服务端强制默认 LIMIT，引擎注册表实际路由 MySQL/ClickHouse/PostgreSQL/SQLite，另备 6 种 runner。
- **实时路由判定**：子 Agent 每次模型调用前，`dynamic_prompt` 中间件用 `SemanticDbDetector` 判断当前库是否建模，注入对应工具链指引；未建模库附带警示防止误用语义层陷入纠错循环。
- **切库零改动**：前端选库 → `configurable.db_name` → 异步 run 透传 patch → 主/子 dynamic_prompt + ToolFilter + CurrentDbContext 四层联动，支持 10 种数据库引擎热接入。
- **Wren fast-path**：`WREN_MEMORY_BACKEND=grep` 时检索工具在主进程直调 Wren Python API，绕过 MCP 子进程与 420MB 嵌入模型加载，消除超时风险。

### 3.5 中间件体系（横切关注点）

基于 `AgentMiddleware`（`wrap_model_call` / `wrap_tool_call`）开发 18 个横切中间件，列表顺序即包裹顺序（第 0 项最外层），将安全、可观测、上下文管理等非功能关注点与业务逻辑彻底解耦：

| 类别 | 中间件 | 职责 |
|---|---|---|
| 容错 | QuotaError / ModelRequired / ModelTimeout | LLM 额度耗尽/未配模型/超时 → 友好提示 + **机器可读失败戳**（禁止文本匹配判据） |
| 安全 | SqlReadOnly / ExecuteGuard | run_sql 写/DDL 硬拦截（不执行不审批）；shell 破坏性命令与工作区外路径拦截 |
| 质量 | CaliberGate | 终稿缺「业务口径」块或无知识证据 → `jump_to="model"` 自动打回重写 |
| 上下文 | MessageSlimmer | 工具结果入 checkpoint 前瘦身：超大落盘截断留预览 + 重复去重，防 O(n²) token 膨胀 |
| 路由 | ToolFilter / dynamic_prompt / DynamicMcpTools | 按当前库过滤工具、注入双通道指引 |
| 模型 | ThinkingToggle | 按请求 configurable 运行时重建模型（思考开关/模型切换，进程级缓存） |
| 观测 | LangfuseSpan / TraceRecorder / TokenMeter | skill 级 span + 确定性评分 + LLM-judge 采样调度；本地事件日志；token 累积统计 |
| 交互 | ProgressTracker / WriteTodosProtocol / QueryKeywords | 子 Agent 步骤进度提取；todo 分级协议；前端关键词注入 |
| 路径 | VfsPathResolver | 模型输出的 `/workspace/…` 虚拟路径改写为真实磁盘路径 |

### 3.6 可观测性（一次查询 = 一条 trace）

- **入口注入**：ASGI 中间件拦截 run 创建请求，把 `langfuse_session_id=thread_id`、`trace_name=chat-turn`、db/workspace/prompt_label/release 写入 `config.metadata`。
- **trace 嵌套**：monkey-patch LangChain `on_chain_start`，子 Agent 根链构造 OTel `NonRecordingSpan`（必须 `trace_flags=SAMPLED`）挂入主 trace；auto-continue 续跑不新开 trace；连问场景按 task_id 路由回原 trace。
- **skill 级结构化层**：按工具名后缀分类创建 `skill:<skill>:<tool>` span，span 结束时写确定性评分（sql_valid / sql_exec_success / schema_match）并按 30% 采样调度 LLM-judge。
- **本地事件日志**：与 Langfuse 并行、不依赖外部系统的 traces.sqlite 事件库，支撑实时事件流、调用谱系树、统计 API。

### 3.7 评估与迭代闭环

「采集 → 复审 → 修复 → 回归 → 灰度 → 放量」六步闭环，Prompt/Skill 变更全程有闸门：

| 环节 | 实现 |
|---|---|
| 在线五维评分 | 确定性维零成本同步打分；LLM-as-Judge 维（业务正确性/报告表格/分析报告）daemon 线程采样评估 |
| BadCase 采集 | 每日 cron 按 4 类命中（系统异常/五维<0.6/差评/执行失败）自动入 Langfuse Dataset，stamp 去重 |
| 状态机 | badcase `pending→reviewed→fixed/invalid`，回归集 = 未闭环集合 |
| 离线 A/B 门禁 | `run_experiment` 按 prompt label 起 worker 子进程多跑 Dataset，核心三维低于参照 − 阈值即拦截发版 |
| 在线反馈门禁 | `feedback_gate` 比较 candidate/reference 的真实用户好评率，放量后持续守护 |
| 灰度发布 | Langfuse prompt 标签（latest/production/staging）+ canary 比例掷骰 + 五级回滚手段 |

**三道安全/质量闸门**：① 运行时 SQL 只读硬拦截 → ② 发版前离线回归门禁 → ③ 放量后在线真实反馈门禁。

### 3.8 安全与多用户隔离

| 层 | 机制 |
|---|---|
| SQL | `classify_sql` 前导词识别写/DDL 直接拒绝；SELECT 无 WHERE/LIMIT/聚合标记 full_dump（放行但评分打 0.4） |
| 文件 | CompositeBackend 最长前缀匹配 VFS（shared/ 只读、workspace/ 可写）+ 声明式 FILE_PERMISSIONS（先 allow 后 deny 兜底）+ 代码根退出 VFS |
| 执行 | ExecuteGuard 拦截 rm/下载等破坏性命令与工作区外路径（预留 OpenSandbox 彻底隔离后端） |
| 数据 | thread 所有权账本、报告归属校验、会话级文件沙箱（路径按 thread_id 钉死）、langgraph_sdk Auth 登录鉴权 |
| 配置 | 模型/数据库凭据 AES-256-GCM 加密存储，前端唯一配置来源，后端仅承接与安全校验 |
| API | 路径穿越防护、租户校验、白名单网关（cube/实验端点默认 403） |

### 3.9 持久化与部署

- **Checkpointer**：实现 LangGraph `BaseCheckpointSaver` 异步接口，生产 AsyncPostgresSaver（自动建表）、开发 AsyncSqliteSaver；全局共享不随工作区切换。关键约束：checkpointer 只能在 API 层（graph.json）配置，graph 定义内传参会被 langgraph dev 校验拒绝。
- **运行时状态库**：一库一目录（`<DATA_ROOT>/{eval_queue,trace_bind,pending_terminal}/<name>.sqlite`），升级首启自动接管旧文件。
- **部署形态**：Docker 多阶段构建（uv 依赖层缓存、国内镜像加速、裁剪 wrenai memory extra 省 1.3GB）；Compose 编排 nginx:80 → frontend:3000 + langgraph-api:2026；卷持久化 AGENT_DATA_ROOT。
- **发布运维**：蓝绿发布 + 零停机摘流（读取 langgraph 活跃 worker 指标平滑 drain）、启动就绪门控（MCP 工具为空拒绝启动、Langfuse 不可达仅告警）、每日 cron 自动化评估流水线。

## 四、关键难点与解决方案

1. **静默失败污染答案**：LLM 超时/额度耗尽被 SDK 吞成"友好的普通回复"，图正常 END、报 success，但这轮什么都没执行。→ 在失败消息 `additional_kwargs` 打机器可读失败戳，下游（口径门控/进度 watcher/任务终态/前端重试）以戳为唯一判据，配负对照验收脚本锁定行为。
2. **切库后仍查旧库**：db_name 经前端 → configurable → 异步 run 透传 patch → dynamic_prompt 前置注入 → 工具层强制覆盖，四层链路任一缺失都会漂移。→ 统一 `langgraph.config.get_config()` 读取规范（`request.runtime.config` 恒空是已踩过的坑），库名前置注入覆盖历史消息中的陈旧值。
3. **长流水线上下文爆炸**：多轮工具结果使 checkpoint 呈 O(n²) token 增长。→ MessageSlimmer 在入 checkpoint 前将超大结果落盘替换为 head+tail 预览、重复内容占位化，全程 fail-open。
4. **子 Agent 可观测断链**：跨 thread/run 后 trace 分裂、续跑新开 trace、连问归属错乱。→ OTel NonRecordingSpan 嵌套（trace_flags 必须 0x01 否则整棵子树不导出）+ 三张进程级映射表（root obs / thread→trace / task→trace）实现"一次查询=一条 chat-turn"。
5. **自托管 Langfuse v4 读接口 404**：legacy API 不兼容 events_only 模式。→ 封装 v4 reads 适配层（session→trace 定位、filter 分页取分数、撤销哨兵分 -1.0）。
6. **Prompt/Skill 迭代回归风险**：改一句话可能让全库查询质量漂移。→ 离线回归门禁 + 在线反馈门禁 + canary 灰度 + 五级回滚。

## 五、项目规模
