# 多用户并发能力评估

> 日期：2026-09-01
> 问题：很多个用户同时基于前端界面提问，nl2sql 项目能支持吗？
> 结论：**能支持「较多用户同时提问」，但有 3 个硬边界**——单进程模型、工作区全局化、LLM 限流。

---

## 一、架构现状（已逐项核实）

| 项 | 现状 | 并发影响 |
|---|---|---|
| 进程模型 | **单进程单 worker**（`python start_server.py` → `uvicorn.run` 无 `workers=`，默认 1，见 [start_server.py:170](../../start_server.py#L170)） | 异步事件循环，I/O 型并发 OK；CPU 密集段会互相争抢 |
| 会话状态 | 生产 **Postgres checkpointer**（`CHECKPOINT_DB_URI=postgresql://nl2sql:nl2sql_secret@postgres:5432/nl2sql_checkpoint`，[checkpointer_factory.py:57](../../src/agent/checkpoint/checkpointer_factory.py#L57)，事务 + 多实例安全） | ✅ 多用户状态可靠，支持多 worker 扩展 |
| 请求隔离 | thread_id / session / db_name / metadata 均请求级（configurable 注入）；进程级注册表（`_ROOT_OBS_MAP` / `_THREAD_TRACE_MAP` / `_TASK_TRACE_MAP` 等）有 FIFO 上限 + 锁 | ✅ 并发用户互不串扰 |
| 工作区 | **进程级全局**（注册表 active + `_LOCK` + 缓存快照，无请求级 ContextVar，见 [manager.py:166](../../src/agent/workspace_manager/manager.py#L166)） | ⚠️ 所有用户共享一个 active workspace |
| LLM | 每查询串行多次调用（knowledge→schema→subproblem→query-plan→sql-gen→执行→报告，约 7 次），timeout 60s×4 重试 | ⚠️ N 用户 ≈ N×7 并发 LLM 请求 → 限流/超时风险 |
| 后台同步 | 静默失败检测 + 自动续跑（方案1 sync watcher）是**单个后台循环** | ⚠️ 并发 run 多时可能延迟（30s 空闲窗口）或漏检 |
| 开发环境 | 无 `CHECKPOINT_DB_URI` → SQLite 单文件 checkpointer | 本地并发写有锁竞争；生产 Postgres 无此问题 |
| 前端 | 每会话 2s/1s 活跃轮询 | 用户数 × 频率的 HTTP 负载，量大需确认反向代理连接数 |

## 二、三个关键边界

### ① 工作区是全局的（多工作区并存的硬伤）

所有用户的 skill 中间结果、报告、checkpoint 语义都落在**同一个 active workspace**。前端工作区下拉切换的是**全局状态**——用户 A 切到 workspace1，用户 B 的所有新请求也一起去 workspace1。**现状只支持「全体用户共用一个工作区」**。

缓解：请求进入时对 workspace 路径拍快照（`config.metadata.workspace.path`，见 [langfuse_span.py:903](../../src/agent/middlewares/langfuse_span.py#L903)），已开始的请求中途不被切换影响。

改造方向（若需多工作区并存）：请求级隔离 —— ContextVar + configurable 透传，与「多问题隔离」是同一个方向的改造。

### ② 单进程 = 发版/崩溃会中断所有进行中的提问

run 队列、异步任务状态都在**进程内存**。进程重启（发版重建容器、OOM、崩溃）→ 正在提问的用户全部中断，无持久化恢复。

历史教训：
- [inmem 僵尸 runs 卡死队列]：`.langgraph_ops.pckl` 持久化 499 中断的 run 恒 running，新 run 不调度
- [async_tasks 写入丢失竞态]：子任务完成时主线程 in-flight run 拒绝 update_state 且无重试

**Postgres checkpointer 已支持多实例** → 加 worker 可行，但需先验证进程级全局对象在多 worker 下各自独立后的行为（见第四节）。

### ③ LLM 限流是实际吞吐上限

每个查询串行多次 LLM 调用（约 7 次）。N 人同时提问 ≈ N×7 并发 LLM 请求。超限即 429/超时，60s×4 重试会进一步放大压力。**要估容量，先测模型 API 的 QPS 上限**。

## 三、次要注意点

- **CPU 密集段**：大结果集处理、报告 Markdown/图表装配在同一事件循环，几十并发时延迟明显上升
- **开发环境 SQLite**：单文件锁竞争，仅限本地开发
- **前端轮询**：活跃轮询 2s/1s，空闲 10s，用户量上来了确认 Nginx 连接数

## 四、规模化建议路径

1. **先定目标**：多少并发用户？是否多工作区并存？这两点决定改造成本
2. **多 worker**：uvicorn `workers=2~4`，回归验证以下进程级全局状态在多 worker 下的正确性：
   - Langfuse 注入：`last_trace_id` 竞态、`_ROOT_OBS_MAP` / `_TASK_TRACE_MAP`（单进程共享 → 多 worker 各自独立，归属/续跑路由要重验）
   - 后台 sync watcher：单后台循环 → 每 worker 跑一份 or 抽独立服务
   - workspace 全局切换、消息注入中间件：每 worker 各自一份
3. **工作区请求级隔离**：不同部门/用户需要不同工作区时必改
4. **加保护**：进程优雅退出/重启时对 in-flight run 持久化恢复（或至少前端友好提示）

## 五、核实证据

- `start_server.py`：`uvicorn.run("langgraph_api.server:app", port=2026, reload=False)` 无 workers 参数
- 生产容器：`docker inspect` → `CMD: ["python","start_server.py"]`；`env` → `CHECKPOINT_DB_URI=postgresql://...@postgres:5432/nl2sql_checkpoint`、`DEPLOY_ENV=prod`、`AGENT_DATA_ROOT=/app/data`
- [checkpointer_factory.py](../../src/agent/checkpoint/checkpointer_factory.py)：`_PG_URI.startswith("postgresql://")` → AsyncPostgresSaver（生产），否则 AsyncSqliteSaver（开发）
- [workspace_manager/manager.py:166](../../src/agent/workspace_manager/manager.py#L166)：`_resolve_active_path` 读注册表 `active` + `WORKSPACE_PATH` + 默认，全程 `_LOCK` 全局缓存，无 ContextVar
- [langfuse_span.py:903](../../src/agent/middlewares/langfuse_span.py#L903)：`_active_workspace_path` 优先读 `config.metadata.workspace.path`（请求级快照）
