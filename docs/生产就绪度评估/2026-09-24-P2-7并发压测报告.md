# P2-7 真实并发压测报告（生产 25.64，2026-09-24）

> 目的：给 P3-1（提高 `N_JOBS_PER_WORKER`）/ P3-2（多进程多副本）提供决策依据，并校验 `concurrency-ceiling-10-run-slots` 里「10 个 run 槽 ⇒ 约 3~4 并发用户」的推导。
> 结论先行：**加槽位/加副本不是当前的收益点** —— 打满 10 槽时服务端一切健康，失败全部来自**出站模型调用连接错误**。

## 一、一句话结论

并发问数 **1 / 2 / 4 全部成功**且延迟平稳（p50 6~8s）；到 **6 并发问数**时 10 个 run 槽被打满（余槽 0.0），12 个问数**失败 4 个（33%）**。但这 4 个失败的**直接原因不是槽位排队、也不是 checkpointer / MCP / 内存 / 事件循环**，而是 `openai.APIConnectionError`（模型调用连接失败，SDK 重试耗尽，3 例）与 1 例「主 run 成功后 `next` 悬挂不推进」。
> ⚠️ **2026-09-24 复核**：那 1 例是**测试端口径误判**（把 `update_state` 的幽灵 `next` 当成「不收敛」），**不是丢步** —— 见 §四 第五条与清单 P2-12。即真实失败是 **3/12**（25%），全部为模型调用连接错误。

## 二、口径（怎么跑的，以及哪些没测）

- **环境**：生产 192.168.25.64，`docker exec` 进 `nl2sql-app_langgraph-api_1`，直连 `http://localhost:2026`
  - ⚠️ **绕过了 nginx 与鉴权中间件**（容器内回环不受 auth 影响）。用户真实路径另做验证，见 §六
- **库**：`witops`；问题集固定 4 条（应报工池在职人数 / 有多少个部门 / 有多少张表 / 人数最多的前 10 个部门）
- **档位**：1 → 2 → 4 → 6 **并发问数**，每档 2 轮，共 26 个问数
- **账号**：生产**只有 2 个账号**（admin / Z0051）⇒ 并发轴是「并发问数」而**不是**「并发用户」，账号轮转使用
- **安全栏**：`lag-abort=5.0s`（**未触发**，全程 lag ≤ 0.017s）、`budget=60` 问数、`max-seconds=5400`
- **采样**：每 2s 打一次 `/metrics` + `/ok` 队列视图

**未测**：真实登录态浏览器的并发；多库并测；长会话（>10 轮）；报告/图表类请求。

## 四、失败归因（逐条，这是本次最有价值的部分）

全库只在 5 个问数上出现异常，**时间线**：

| 时刻(UTC) | 档位 | run_id | 结果 | 说明 |
|---|---|---|---|---|
| 07:23:04 | 4 | `01a0d24b-b218…` | **恢复** | 自动续跑那一步的模型调用连接失败，图内重试后成功 ⇒ 该问数 turn 从 8s 被拉到 **50.78s**（这就是档位 4 的 p95/max 长尾） |
| 07:24:15 | 6 | `01a0d24c-e47b…` | **失败** | `turn_failed`，main run 6.09s `error` |
| 07:28:25 | 6 | `01a0d250-ab53…` | **失败** | `turn_failed`，main run 10.09s `error` |
| 07:28:26 | 6 | `01a0d250-ace4…` | **失败** | `turn_failed`，main run 8.12s `error` |
| 07:24:08→07:28:16 | 6 | `01a0d24c-de03…` | **卡死 248.77s** | 见下「第五条」 |

**前 4 条是同一条错**：

```
langgraph_api.worker - ERROR - {'run_id': …,
  'event': "Run encountered an error in graph:
            <class 'openai.APIConnectionError'>(Connection error.)"}
栈底：openai/_base_client.py:1683  raise APIConnectionError(request=request) from err
```

即 **openai SDK 已重试耗尽**（每个 run 打 4 行同日志 = 1 + 3 次重试）。

### 为什么**不能**归因给「网络」或「DeepSeek 限流」

| 检查 | 结果 | 排除 |
|---|---|---|
| 出站通道容量 | 容器内并发打 `https://api.deepseek.com/v1/models`：**2/6/12/20 并发全部成功**，延迟 0.08~0.23s，**零异常** | 「并发连接数不够」——20 并发下通道健康 |
| 是否配额限流 | 限流应由 SDK 抛 `RateLimitError`（429），**不是** `APIConnectionError` | 「DeepSeek 在限流」 |
| 本服务侧同时刻 | 排队 0 / `status 500` **0 次** / `the connection is closed` **0 次** / 自愈 WARNING **0 次** / RSS 平稳 912MB / 事件循环 lag ≤ 17ms / MCP 注册表无失败 | checkpointer、内存、事件循环阻塞、MCP |

**暂时归因**：高并发下**长连接 / 流式请求级**的失败（不是短连接容量问题），或与「10 个 run 共用一个事件循环，多个模型调用互相挤压」有关。
**无法进一步定位**，因为 `APIConnectionError` 的**底层 httpx 原因（`__cause__`）没有进日志** —— langgraph 只记录它看到的异常文本 `Connection error.`。⇒ 必须补日志，见 §九 P2-11。

**第五条：`settle_timeout` 248.77s（档位 6，1/12）** —— ⚠️ **2026-09-24 复核：这是测试端口径误判，不是主 run 丢失下一步。**

- `main_run` **8.06s `success`**、`last_message_is_final=True`，但结算检查持续看到
  `next=['PatchToolCallsMiddleware.before_agent']`，永不收敛，直到测试端 240s 放弃（`ans_len=0`）。
- **误判之处**：当时结算判据写的是「无活跃 run + **无待执行节点** + 最后一条是终稿」，比生产端点 `run-status` 的判据**多要了一条 `next` 为空**。而 `next` 非空正是 sync 的
  `update_state(as_node="__start__")` 状态补丁的**固有副作用**（它把 `next` 写成本图的入口节点；LangGraph 的 update_state 硬闸又保证这种补丁只可能落在主 run 终态之后）—— 端点判据 4「最后一条是终稿」本来就把它判成**不算未完成**（生产 trace 01a09ed5 同形态）。
- ⇒ **答复已就绪、图头那个节点没人推进也无害**（全 `src/` 只有 `run-status` 一个 `state.next` 读者）。测到的「卡死 248.77s」是**测试端空等**，`ans_len=0` 是**测试端没走到记录答案那一步**（不是答案为空）。机制复现与判据回归见 `scripts/verify_phantom_next.py`（23/23），清单项 P2-12 已按此结案。
- 已修：`scripts/load_test_concurrency.py` 改用端点自己的结论字段（`turn_settled`，**不再要求 `next` 为空**）并新增 `phantom_next` 计数 ⇒ **本次报告表格里档位 6 的「8/12 成功 / p95 248.8s」应以修正后的口径重读**（那一条不会再把这一档的长尾拉高）。
- 1/12，只在 6 并发档出现（并发相关性见 P2-12：由 409 硬闸 + `_SYNC_WRITE_LOCK` 争用推出的机制解释，**未经实测的并发-发生率曲线**）。

## 五、对 P3-1 / P3-2 / P3-4 的决策输入

- **10 个槽的实测位置**：**6 并发问数 = 峰值在跑 10.0、余槽 0.0（恰好打满）**；1~4 档余槽 ≥ 4。
- **每个问数吃几个 run**：主线程实测 `main_thread_runs=1`（偶发 2 = 自动续跑）；采样点的并发 run 数 ÷ 并发问数 = 3.0 / 1.0 / 1.5 / 1.67（档位 1/2/4/6）。综合上界仍是 **2~3 个 run / 问数**（与 P2-10 的差分测量一致）。
- ⇒ **10 槽支撑约 3~6 个并发问数** ⇒ `concurrency-ceiling-10-run-slots` 的「3~4 并发用户」推导**成立**（一个用户同时挂 1~2 句）。
- ⇒ **P3-1（提高 `N_JOBS_PER_WORKER`）不是当前收益点**：打满 10 槽时服务端零排队、零超时、内存与事件循环健康，失败**全部来自模型调用连接**。盲目加槽只会让**更多并发模型调用**去踩同一个坑。
- ⇒ **P3-2（多副本）同样不急**：单副本 6 并发问数下 RSS 仅 +170MB、lag 17ms。
- ⇒ **应该先做 P3-4（LLM 侧并发闸 + 队列 + 退避 + 按用户配额）**，并把 P2-11（补 `__cause__` 日志）一起做掉，否则下一次还是只能看到「Connection error.」。

## 六、用户真实路径（nginx + 鉴权）连带发现

压测脚本直连 `localhost:2026`，**绕过了 nginx 与鉴权中间件**；而 2026-09-24 事故里用户看到的正是 nginx 那条路径。所以补做了浏览器路径验证：

- 容器内用 admin Cookie 打 `http://nginx`：`/threads/search`、`/assistants/search`、`/assistants/count`、`/api/model-configs`、`/api/auth/me` **全部 200**；**无 Cookie 一律 401** ⇒ 「无 Cookie 即被认成 internal」那扇旁路门仍关着。
- **由此发现一个与压测无关但更紧急的生产问题**：前端「设置 → 部署 URL」被配成 `http://192.168.25.64:2026`，而 `:2026` 只发布在**回环**上（09-23 关旁路门时改的）⇒ 浏览器连不上 ⇒ `Failed to fetch`，UI 报「尚未配置模型 / 加载对话列表失败」。修法 = 改填 nginx 入口 `http://192.168.25.64:8080`（详见记忆 `frontend-deployment-url-must-be-nginx-entry`）。

## 七、口径 caveat（如实记，避免以后误用这些数）

1. **采样 2s ⇒ 峰值低估**：`peak_running`/`peak_pending` 都是采样点上的瞬时值，4~8s 的 turn 可能整段落在两次采样之间。档位 1/2 的 `samples` 只有 **7/6** 个 ⇒ **档位 1/2 的峰值基本不可信**；档位 4/6 有 31/130 个，相对可信。
2. **`nl2sql_process_children` 测不出 MCP 真实子进程数**：它是 `/proc` 里 `PPid==本进程` 的计数，由 P2-3 的采样循环**每 10s** 更新一次，而 stdio MCP 子进程随调用生灭 ⇒ 档位 4 偶然采到 5、档位 6 采到 0。**「MCP 子进程峰值」这一项目前测不出来**，需在 P3-6 里单独量。
3. **`peak_pending` 全程 0 ≠「从不排队」**：本次从未超过 10 个并发 run（恰好打满），根本没触发排队；2s 采样也看不见短排队。
4. **JSON 里 `round` 字段是 `None`**（工具缺陷）⇒ 分轮只能用 `t_submit` 时间戳人工切。
5. **并发轴 ≠ 用户轴**：生产只有 2 个账号，本次是「2 个账号并发发问」。
6. 压测线程由脚本自行删除（`threads_deleted=26`）；**子 agent 线程的清理仍需核对**。
