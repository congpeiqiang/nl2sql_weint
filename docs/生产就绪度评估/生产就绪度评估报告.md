### C2. SQL 注入风险 — 任意 SQL 执行无校验

**严重程度**: 致命  
**影响**: 生产数据库可能被 LLM 生成的恶意 SQL 破坏

所有数据库引擎的 `sql_runner.py` 都直接执行原始 SQL，无任何安全校验：

| 引擎 | 文件 | 行号 | 代码 |
|------|------|------|------|
| MySQL | `engine/mysql/sql_runner.py` | 81 | `cursor.execute(args.sql)` |
| SQLite | `engine/sqlite/sql_runner.py` | 41 | `cursor.execute(args.sql)` |
| PostgreSQL | `engine/postgres/sql_runner.py` | 90 | `cursor.execute(args.sql)` |
| Snowflake | `engine/snowflake/sql_runner.py` | 140 | `cursor.execute(args.sql)` |
| ClickHouse | `engine/clickhouse/sql_runner.py` | 75 | `client.query(args.sql)` |
| Presto | `engine/presto/sql_runner.py` | 99 | `cursor.execute(sql)` |
| Oracle | `engine/oracle/sql_runner.py` | 63 | `cursor.execute(sql)` |
| MSSQL | `engine/mssql/sql_runner.py` | 63 | `pd.read_sql_query(self.sa.text(args.sql), conn)` |

特别危险：
- Snowflake runner 使用 f-string 拼接 SQL（行 129, 133, 137）：`f"USE ROLE {self.role}"`
- `run_sql` MCP 工具支持分号分隔的多语句执行
- 无 SQL 关键字白名单（DROP / DELETE / TRUNCATE 全部允许）
- 无查询长度限制
- 无只读模式

**修复方案**:
1. 数据库连接使用只读账户
2. SQL 解析 + 关键字黑名单（拦截 DROP / DELETE / ALTER / TRUNCATE / INSERT / UPDATE）
3. 查询超时限制
4. 语句数量限制

### C3. 零自动化测试

**严重程度**: 致命  
**影响**: 无法保证功能正确性，每次变更都是盲改

- 项目中无任何 `test_*.py` 文件（仅 `.venv` 中的第三方包测试）
- 无 `tests/` 目录
- 无 pytest / unittest 配置
- 无 CI 测试流水线

**修复方案**:
1. 建立 `tests/` 目录，添加核心流水线测试
2. 至少覆盖：SQL 生成流水线、MCP 工具调用、错误处理路径
3. 集成到 CI/CD

### C4. MCP 服务器无认证暴露网络

**严重程度**: 致命  
**影响**: 任何人可远程执行任意 SQL

MCP 服务器配置：
- 绑定 `0.0.0.0:8000`（所有网卡接口）—— 见 `.env:47` `NL2SQL_MCP_HOST=0.0.0.0`
- **无任何认证**：无 JWT、无 API Key、无 Bearer Token、无中间件
- `db_server.py:58-61` 硬编码假用户 `user_001`
- 暴露 `run_sql`（任意 SQL 执行）和 `get_db_info`（泄露配置信息）给任何能访问 8000 端口的人
- 无 CORS 配置，任何网页可跨域调用

**修复方案**:
1. MCP 绑定改为 `127.0.0.1`
2. 添加认证中间件
3. 添加 CORS 限制
4. 添加 TLS

### H3. 无数据库连接池

**严重程度**: 高  
**影响**: 并发请求耗尽 `max_connections`

`MySQLRunner`（`sql_runner.py:65-96`）每次查询新建连接，无连接池：

```python
conn = self.pymysql.connect(...)  # 每次新建
try:
    ...
finally:
    conn.close()
```

**修复方案**: 使用 `DBUtils.PooledDB` 或 SQLAlchemy 连接池

---

### H4. 无超时控制

**严重程度**: 高  
**影响**: 拒绝服务风险

| 组件 | 超时配置 | 文件 |
|------|---------|------|
| LLM 调用（ChatDeepSeek） | **无** | `model.py:20` |
| 数据库查询 | **无** | `sql_runner.py:81` |
| MCP 工具运行时调用 | **无** | `path_resolver.py` |

**修复方案**:
- LLM: 添加 `request_timeout`
- DB: 添加 `connect_timeout` + `execute timeout`
- MCP: 工具调用包裹 `asyncio.wait_for`

### H6. 无优雅降级

**严重程度**: 高

- MCP 全部失败 → agent 以空工具列表启动，但仍接受请求
- LLM API 不可用 → `create_deepseek_model()` 返回 `None`，直接传给 `create_deep_agent()` 导致崩溃
- 数据库不可达 → 每次查询抛出未处理异常

无熔断器、无降级策略、无就绪门控。

**修复方案**:
- 工具全部加载失败时拒绝启动（readiness gate）
- 添加健康检查端点验证 MCP/LLM/DB 连通性

---

### H7. SQLite Checkpointer 不支持并发

**严重程度**: 高  
**影响**: 多用户并发写入失败

`AsyncSqliteSaver` 是单文件锁，多用户并发写入会 `database is locked`，不适合多节点部署。

**修复方案**: 生产环境切换为 `AsyncPostgresSaver`

## 🟡 中等问题（5 项，生产后尽快解决）

### M1. 依赖版本松散

`pyproject.toml` 全部使用 `>=` 无上界：

```toml
"deepagents>=0.6.12",
"fastmcp>=3.4.4",
"langchain-openai>=1.3.5",
```

Major 升级可能引入破坏性变更。

**修复方案**: 锁定上界 `>=0.6.12,<1.0`，生成 lock 文件

---

### M2. 并发安全

- 全局可变状态无锁（`_tools`/`_tools_loaded`、`_runner_cache`）
- 进度文件并发写入无文件锁
- 无 `asyncio.Lock` 使用
- `_tools_loaded` 的 check-then-set 是经典 TOCTOU 竞态

**修复方案**: 添加 `asyncio.Lock` 保护共享状态

---

### M3. 无取消机制

长时间运行的操作一旦启动无法中断：
- SQL 查询（可能数分钟）
- LLM API 调用
- 沙箱命令（1 小时超时）

`recursion_limit: 500` 只限制步数，不取消进行中的操作。

**修复方案**: 添加 `asyncio.CancelledError` 处理和取消传播

---

### M4. 无健康检查

只有框架自带的 `/ok`，不检查依赖服务状态。服务降级时无法被监控系统发现。

**修复方案**: 自定义健康检查端点，验证 MCP/LLM/DB 连通性

---

### M5. 日志质量差

- `print()` 与 `logging` 混用（`mcp_tool.py` 和 `start_server.py` 大量使用 emoji `print`）
- WARNING 级别打印工具调用结果前 200 字符（可能泄露数据）
- `get_safe_config()` 已实现但从未被调用
- SQL 明文写入日志（`sql_runner.py:80`: `logger.info(f"执行sql: {args.sql}")`）
- 事件循环泄漏风险：`mcp_tool.py:61-62` 在模块加载时创建新事件循环

**修复方案**: 统一使用结构化日志，敏感信息脱敏
