## 一、结论

**当前架构无法支撑「多用户并发请求」，瓶颈不是容量而是形态。** 三个硬边界：

| # | 边界 | 一句话 |
|---|---|---|
| 1 | **单进程 × 10 个 job 共用 1 个事件循环** | 任一请求里的阻塞调用会拖慢**其他所有用户**，而非只是自己慢 |
| 2 | **无法水平扩展** | 固定端口 + inmem 运行时 + stdio 子进程 + 本地 SQLite + 本地报告卷，四处都挡住第二副本 |
| 3 | **并发正确性有缺陷** | 至少 6 处进程级共享状态会在并发下静默串数据（把 A 的活记到 B 名下） |

**能力定级（实测 + 推算，非压测）**

**关键等式**：`N_JOBS_PER_WORKER=10` 是**全局**并发槽位（含所有会话的所有 run），而**一次问数 = 约 3 个 run**：1 个主 run + 1 个 nl2sql 子 run（deepagents 异步子 agent 是**独立的后台 run**）+ 子任务成功后自动续跑的 1 个主 run。全部抢同一个池（证据见 §3.2）。

| 场景 | run 占用 | 结论 |
|---|---|---|
| 单人、单问数 | **≈3** | ✅ 可用，占 3 个槽 |
| **单人开 5 个并发问数**（前端 `HARD_CAP=5`） | **最坏 ≈15** | ⚠️ **单个人就能打满 10 个槽** |
| **3 人各 1 活跃问数** | **≈9** | ⚠️ 逼近上限 |
| **4 人各 1 活跃问数** | **≈12 > 10** | ❌ **开始排队**：多出的 run 停在 `pending`，前端表现是「卡住/无响应」而非报错 |
| 10 人并发 | ≫10 | ❌ 队列堆积，且全在同一个事件循环上互相阻塞 |
| 200 人（文档预期） | — | ❌ 差得远。文档自己也只写「先观测」（`docs/agent优化记录/多用户登录与用户隔离方案.md:403`） |

> 这是**代码推导**而非压测实测（推导链见 §3.2，压测列为 P2-7）。结论：**并发用户是个位数——约 3~4 人；且无法靠「限制每人 1 个问题」规避，因为单会话就允许 5 个并发问数。**

**同时存在一处必须先处理的安全洞**：生产 LangGraph API 的认证**可被一个可省略的请求头绕过**，且绕过后的身份能读写删**所有用户**的会话。这是「多用户」需求下最该先堵的一项（详见 §4.1）。

**可立即使用的最大杠杆**：`BG_JOB_ISOLATED_LOOPS=true` —— 一个环境变量，把 10 个 job 从「共用 1 个事件循环」改成「各自独立事件循环」，直接缓解边界 1。详见 §6 P0-1。

## 二、生产实际形态（本次实测，非文档推断）

**⚠️ 首要前提：仓库里的 `docker-compose.yml` 与生产实际使用的那份是两份不同的文件。**

- 仓库版 `docker-compose.yml`（`agent_data:/app/data` + `deploy.resources.limits.memory: 1200m`）**不是线上在跑的那份**。
- 线上那份由服务器手工维护，本地镜像在 `D:\code_work_space\llm\deepseek-workspace\nl2sql-app\docker-compose.yml`（`docs/agent优化记录/多用户登录与用户隔离方案.md:407` 明说 compose 与 nginx.conf「不随发版脚本传播」）。
- 两者实质差异：线上用 `workspace:/app/src/agent/workspace` 卷（即 **AGENT_DATA_ROOT 走代码内回退目录**）、nginx 暴露 **8080**（非 80）、frontend 不发布宿主端口、postgres 绑 `127.0.0.1:5435`、**且线上那份完全没有 `deploy.resources` —— 没有任何 CPU/内存上限**。

> 教训：任何基于仓库 compose 得出的容量/限额结论对线上都不成立。改端口、加 limit、加卷都必须登服务器手工改。

**实测数据（2026-09-23）**

| 项 | 实测值 | 来源 |
|---|---|---|
| 宿主机 | **8 核 / 31GB**，Ubuntu 24.04 | `ssh 25.64 'nproc; free -g'` |
| 同机容器 | **40+ 个**（ragflow、milvus、langfuse×4、metabase、xinference、one-api…） | `docker ps` |
| nl2sql-api 限额 | **`Mem=0`、`NanoCpus=0`（无任何上限）** | `docker inspect` |
| nl2sql-api 进程 | 单进程 `python start_server.py` | `docker inspect` `Cmd` |
| nl2sql-api 空载内存 | 681 MB | `docker stats --no-stream` |
| 重启策略 | `unless-stopped` | `docker inspect` |
| 端口暴露 | `2026` 绑 **0.0.0.0**（可绕过 nginx 直连） | `docker inspect` `PortBindings` |
| 模型服务 | 公网 `https://api.deepseek.com/v1`，模型 `deepseek-v4-flash` | `.env.prod` |
| checkpoint | Postgres 14（compose 内服务，`@postgres:5432`） | 线上 compose + `checkpointer_factory.py:57` |

**无 cgroup 兜底 + 40 个邻居 = 单点 OOM 会波及全家。** 当前 `langgraph-api` 无内存上限，而并发用户数会线性放大子 agent 与 MCP 子进程的内存占用（每个 wrenai 库一个 `wren serve mcp` 子进程、每个 dbmcp 一个 Python 子进程）。一旦打爆，宿主 31GB 被一个容器吃掉，ragflow/milvus/langfuse 一起遭殃。

## 三、并发天花板与单请求成本（边界 1 的展开）

§1 的边界 1「单进程 × 10 个 job 共用 1 个事件循环」是本次评估的核心，这里逐层拆开：**槽位怎么被吃**（3.2）→ **为什么会互相拖死**（3.3）→ **单请求有多贵**（3.4）→ **外部依赖的天花板**（3.5）→ **为什么加不了机器**（3.6）。

### 3.1 【核心】10 个 job 共用 1 个事件循环

这是整个评估最重要的一条，已从「应用配置」与「运行时源码」两侧确认：

```
start_server.py:70        N_JOBS_PER_WORKER = "10"
start_server.py:212-217   uvicorn.run("langgraph_api.server:app", host="0.0.0.0", port=2026, reload=False)
                          ↑ 没有 workers= 参数 → 单进程
start_server.py:65        LANGGRAPH_ALLOW_BLOCKING = "true"
```

运行时侧（`.venv/Lib/site-packages/langgraph_runtime_inmem/queue.py`）：

```python
concurrency = config.N_JOBS_PER_WORKER          # :91  → 10
runners = AsyncQueue[BgLoopRunner](concurrency) # :92  → 恰好 10 个 runner
if config.BG_JOB_ISOLATED_LOOPS:                # :120
    ...  10 个各自独立的 event loop（ThreadPoolExecutor + BgLoopRunner(idx)）
else:
    await logger.ainfo("Starting queue with shared loop")   # :126 ← 实际走这条
    for _ in range(concurrency):
        runners.put_nowait(cast(BgLoopRunner, object()))
```

而 `BG_JOB_ISOLATED_LOOPS` 默认 **False**（`langgraph_api/config/__init__.py:337`），`start_server.py` 也没设它。

**后果**：10 个并发 job 全部跑在**同一个事件循环**上。

**雪上加霜**：`LANGGRAPH_ALLOW_BLOCKING=true` 关掉了运行时的阻塞检测护栏（`queue.py:104` 的 `_enable_blockbuster()` 分支不生效）。运行时自己的告警原文是：

> *"Be aware that blocking code in one run may tie up the shared event loop and slow down ALL other server operations."*

而本项目的阻塞调用是**已知存在且遍布 async 路径**的（清单见 §3.3）。

**所以并发下不是「各自慢」，是「互相拖死」。** 一个用户触发了慢 SQL 或卡住的 MCP 子进程，其他 9 个用户的请求一起卡住。

### 3.2 这 10 个槽位怎么被吃掉：一次问数 ≈ 3 个 run

子 agent **不是进程内子图，而是同一个 LangGraph 服务上的另一个后台 run**：

```python
# 派发：.venv/.../deepagents/middleware/async_subagents.py:338-360
client.threads.create()  →  client.runs.create(thread_id=..., assistant_id=spec["graph_id"], ...)
# 成功后自动续跑（出图/出报告）：src/agent/subagents/sync_subagent_todos.py:1666
client.runs.create(thread_id=main_thread_id, assistant_id="chat_agent", ...)
```

| 事实 | 位置 |
|---|---|
| 子 agent 是**独立 run**，因此**吃同一个 10 槽池** | `async_subagents.py:338-360`；`sync_subagent_todos.py:412` 注释自陈 |
| 每个子任务**成功后**再触发一次主 run；**失败**路径也再来一次（`:1761`） | `sync_subagent_todos.py:1648-1682, 1761` |
| **后端无任何扇出闸门**（无信号量、无每用户配额） | `async_subagents.py` 的 prompt 只说 "Multiple async subagents can run concurrently" |
| 唯一的上限在**前端**：单会话最多 5 个并发问数 | `harness-deep-agents-ui/src/app/components/ChatInterface.tsx:746-747` `HARD_CAP = 5` |
| 所有子任务的 state 写回**全局串行**在一把锁上 | `sync_subagent_todos.py:35` `_SYNC_WRITE_LOCK`（`:211`） |

**⇒ 一次问数 ≈ 3 个 run**（主 + 子 + 续跑主），**单会话最坏 ≈15 个 run** —— **一个人就能打满全局 10 个槽位。**

**槽位被占的时长也不短**：

| 阶段 | 时长 | 依据 |
|---|---|---|
| 典型单次问数 | **1~3 分钟** | trace 实测 67s / 150s（其中 LLM 42.7~59.7s）；MCP 子进程冷启动 2-4s × 5~12 次 |
| 正常收尾上限 | ~10 分钟 | `STALE_RUN_TIMEOUT = 600` 强制 `runs.cancel`（`sync_subagent_todos.py:541-560`） |
| 最坏（回退守卫） | ~15 分钟 | `REGRESSION_GUARD_MAX_SECONDS = 900` |
| **卡在审批态** | **最长 2 小时** | `_AWAIT_APPROVAL_TIMEOUT = 7200`（`:81`）——**期间 2 Hz 轮询不停**，且这一个 run 一直占着 1/10 的全局槽位 |

而 run 级兜底是 `BG_JOB_TIMEOUT_SECS` 默认 **86400s（24 小时）**，等于不拦。**一个卡住的 run 可以让全站 10% 的并发能力消失两小时。**

### 3.3 async 路径里直接做的同步阻塞调用（这就是 §3.1 会「互相拖死」的原因）

`LANGGRAPH_ALLOW_BLOCKING=true` 关掉了检测，所以下面每一处都**静默发生**。按阻塞时长排序：

| 类别 | 位置 | 阻塞上限 |
|---|---|---|
| **wren CLI 子进程** | `wren_semantic.py:1005` context build / `:1008` **memory index** / `:1026` validate | 180s / **600s** / 180s |
| **git 子进程** | `wren_semantic.py:1563,1569,1577-1580,1601,1608-1621`（push 300s、tag 120s）+ `:1597` 自动建仓（含 `requests.post` 30s） | 30~300s |
| **同步 DB 内省** | `wren_semantic.py:1162,1242,1746` → `db_introspect.py:115,127`（ClickHouse `requests.get timeout=30`），MySQL/PG 走同步驱动 | 30s × N |
| **人工标注 SQL 预览 = 真查询** | `feedback_annotation.py:251` `df = await runner.run_sql(...)` —— **名为 async，实现里没有一个 `to_thread`**（`mcp_server/db_mcp_server/db/engine/*/sql_runner.py`：mysql `pymysql.connect`、postgres `psycopg.connect`…） | 无 statement timeout |
| 连接探活 | `db_config.py:271 test_config` → `pymysql.connect` + `SELECT 1` | — |
| **会话全文检索（含全量重建索引）** | `thread_search.py:296-321` → `_refresh_index`（`:169-210`）同步 sqlite 全量拉取写 FTS | — |
| trace 查询 | `trace_routes.py:94,147,158,173` → 同步 sqlite | — |
| 反馈读写 | `feedback_annotation.py` 20+ 处、`message_feedback.py:500-531` 同步 sqlite + `commit()`（**同一文件里另一半却走了线程，做法不一致**） | — |
| 工作区操作 | `workspace.py:77`（含目录拷贝）、`:118` `delete_workspace`（可能 `shutil.rmtree` 整棵） | — |
| **每个请求都走的中间件** | `auth_middleware.py:138` `verify_token`（同步）+ `:156` `register_user`（**SQLite 写 + commit**）；`langfuse_metadata.py:182` `claim_thread`、`:205` `record_thread_db`（**再两次 SQLite 写**） | 每请求 2~3 次同步写 |
| 同步 HTTP | `model_config.py:70,156,187` `urllib.request.urlopen`（模型探活每个模型一次） | — |
| **共享 loop 上的 CPU 重活** | `check_progress.py:1316-1360` `_check_async`（async）内部**同步**调 `:1158 plan_run_sql`（wren 引擎构建）；`wren_plan.py:222-241` 引擎构建**在锁内 ~0.9s**，缓存 `_CACHE_MAX=4` → **并发访问 >4 个库时反复重建** | 0.9s × N |

**对照（已经做对的，可作为整改模板）**：`mcp_tool.py:571` 注释要求「起 MCP 子进程必须放线程」→ `db_config.py:222,251` 用了 `asyncio.to_thread`；`sync_subagent_todos.py` 多处 `to_thread(_sync_update_state, ...)`；`report_builder.py:316` `to_thread(model.invoke, ...)`；deepagents 的 shell 执行默认走线程（`backends/protocol.py:845-857`）。

> **整改口径**：上表每一处都应包 `asyncio.to_thread`（与 P0-1 的 loop 隔离是**互补而非替代** —— 隔离只保证「各自有 loop」，同步阻塞仍会饿死自己那个 loop 上的 SSE 与子任务）。

### 3.4 单请求的资源放大（决定内存与子进程数的量级）

| 放大项 | 事实 | 位置 |
|---|---|---|
| **MCP 子进程无池** | **每次工具调用都新建 session = 新建子进程，用完即销毁**；wren 冷启动 2-4s；单请求 5~12 次调用 → **10~48s 纯进程开销**，峰值可达**数十个并发子进程** | `langchain_mcp_adapters/tools.py:460-471`、`sessions.py:213-273`、`mcp/client/stdio/__init__.py:203-209,262-278`（2s 宽限后强杀进程树） |
| **目标库连接无池** | 每次 `run_sql` 新建连接 + `finally: close()`；**无 statement timeout**；`fetchall()` **全量进内存，无行数上限** | `sql_runner.py`（mysql `:65,95-96`、postgres `:82-84,114-116`；仅 mssql 用 SQLAlchemy 池） |
| **进程内 dump 无界** | 每个工具调用写一份 ≤**8MB** 的 process_data JSON（默认开启）→ 单请求可写几十个文件 | `langfuse_span.py:100` `_DUMP_MAX_BYTES`、`:1047-1091` |
| **轮询线程** | 每个活跃子任务 1 条 daemon 线程、2 Hz、**每轮 ~5 次 HTTP → 约 10 req/s/task**，全部回环打到本机 2026 的同一个 loop | `sync_subagent_todos.py:135-150,366`；`_get_run_status`/`_read_task_status`/`_read_current_main_todos` 等 5 处 |
| 长结果进上下文 | `LARGE_RESULT_TRUNCATE_CHARS` 实际取 **16000**（`.env:113`/`.env.prod:55`，非默认 8000）；图表豁免 60000 | `message_slimmer.py:59-61,81-83` |
| 请求体全量缓冲 | 中间件把**整个请求体读进内存重新编码**再转发 → 长会话历史在并发下成倍占内存 | `langfuse_metadata.py:83-84,249-267` |
| 无 body 上限 | 原生路由有 300MB/413 保护，**自定义 `/api/*` 没有**（只有 nginx 50m 兜底） | `langgraph_api/config/__init__.py:188-189` vs `src/api/_common.py:19-28` |

**⚠️ 线上没有 1200m 上限**（§2），所以这些放大项不会撞到 limit，而是**撞宿主机的 31GB —— 连同机上 40 个邻居一起 OOM**。

### 3.5 LLM 是公网 API，且系统侧没有任何并发闸

| 事实 | 位置 |
|---|---|
| 走公网 `https://api.deepseek.com/v1`，单 key 共享 | `.env.prod` |
| 单次模型调用 `timeout=60, max_retries=3` → **最坏 240s** | `src/agent/llms/model.py:396-403` |
| 一次问数串行多次模型调用（knowledge→schema→…→sql-gen→报告） | 流程结构，见 `src/agent/graphs/nl2sql_agent.py` |
| **全仓无 LLM 并发上限 / 无限流 / 无队列长度控制 / 无按用户配额** | grep `Semaphore` 仅 `thread_search.py:189` 一处（限的是索引重建的自身 fan-out，与 LLM 无关） |
| 超时被转成一条友好中文消息而非报错 | `src/agent/middlewares/model_timeout.py` |

**吞吐上限由 DeepSeek 的公网配额决定，系统侧没有任何削峰手段。** N 个用户 ≈ N × 多次并发模型请求，超限即 429/超时；而超时导致的失败对用户表现为「模型说抱歉」，不是显式错误——**并发压力会被伪装成质量问题**，这是运维排查时最容易误判的一点。

### 3.6 无法水平扩展：四处硬阻断

| 阻断点 | 证据 |
|---|---|
| 固定宿主端口 `2026:2026` | 线上 compose；同机第二副本必然端口冲突 |
| inmem 运行时 + run/线程注册表落本地 `.langgraph_api` | `start_server.py:57-64`（`DATABASE_URI=":memory:"` / `REDIS_URI="fake"` / `LANGGRAPH_RUNTIME_EDITION="inmem"`）；线上 compose 用 `nl2sql_api_meta` 卷保 threads 元数据，**该文件属单个容器** |
| MCP 是 **stdio 子进程**（每库一个 `wren serve mcp`、dbmcp 一个 Python 进程），且**每次工具调用新建 session = 新建子进程、用完即销毁、无进程池** | `src/agent/tools/mcp_tool.py`（`transport: "stdio"`）；改 HTTP/SSE 才能多副本复用（P3-2） |
| 本地 SQLite 全集 + 本地报告卷 + nginx 从该卷静态直出 | 见 §4.5；线上 nginx `/report/` → `alias /workspace/report/` |

另有一条运维陷阱：langgraph_api 会**跨请求复用 PG 连接**，所以**单独重启 postgres 容器会导致全员报 `the connection is closed`，必须再重启 langgraph-api**（`src/agent/checkpoint/checkpointer_factory.py:65-70`）。

**唯一已具备扩展条件的只有 checkpoint 表（Postgres）**，其余全部要改。

## 四、并发正确性缺陷（会静默串数据）

这一节的问题比「慢」更危险：**不报错、不崩溃，只是把 A 的数据记到 B 名下**。按危害排序。

### 4.1 【严重】认证可被一个可省略的请求头绕过，且绕过身份拥有全部会话权限

三件事叠加成一个完整的利用链：

**① 两处 bypass 的判据都是「客户端可省略的东西」**

| 位置 | 判据 | 绕过方式 |
|---|---|---|
| `src/api/auth_middleware.py:41-47,106` | 来源 IP 属 `172.`/`10.`/`127.0.0.1`/`::1` **且不带 Cookie** | nginx 转发来的请求源 IP 正好是 `172.x`，**不发 Cookie 即可** |
| `src/agent/auth/backend.py:40-45`（09-22 提交 `cd666df`） | **无 token 且无 `X-Forwarded-For`** | 直连 `0.0.0.0:2026` 的攻击者本来就不发 XFF |

代码注释自陈了第一条的前提（`auth_middleware.py:92-94`：「nginx 转发的用户请求也来自 Docker 网络（172.x）」），而 `start_server.py` 未传 `proxy_headers`/`forwarded_allow_ips`，uvicorn 不会用 XFF 重写 client。

**③ 绕过后的 `internal` 身份在归属校验里被短路**

`src/agent/auth/backend.py` 的三个资源级授权 handler（`:110` `auth.on.threads.create`、`:130` `search`、`:141` `threads`）**全部对 `internal` 直接放行**：

**这不仅是「免登录」，而是「拿到所有人的会话」。** 这是「多用户并发」需求下必须先处理的一项。

> 缓解（按成本排序）：
> 1. **收回 2026 端口**（改为仅 `127.0.0.1:2026` 或走 compose 内网），让它不可被局域网直连——立即消除第二条 bypass 的可达性。
> 2. 把 bypass 判据换成**不可由客户端伪造**的东西（容器内网共享密钥头、Unix socket，或干脆给内部调用签发短期 token 而不是放宽认证）。
> 3. `internal` 身份不应短路归属校验；应给它一个明确的、受限的授权集。

### 4.3 【高】trace 中间件把 per-request 状态存在进程级单例上

`TraceRecorderMiddleware` 是模块级单例（`src/agent/main_agent.py:237`，`src/agent/graphs/nl2sql_agent.py:225`），而它把当前请求的 thread_id 存在**实例属性**上：

```python
trace_recorder.py:50    self._cached_thread_id = None
trace_recorder.py:124   self._cached_thread_id = thread_id    # wrap_model_call   写
trace_recorder.py:161   self._cached_thread_id = thread_id    # awrap_model_call  写
trace_recorder.py:200   thread_id = self._cached_thread_id or ""   # wrap_tool_call   读
trace_recorder.py:261   thread_id = self._cached_thread_id or ""   # awrap_tool_call  读
```

**写入（模型调用）到读取（工具调用）之间的窗口 = 整个 LLM 推理时长（秒级）**。任何其他请求在这期间发起模型调用就会覆盖它。所以并发下这**不是罕见竞态，而是近乎必然的系统性错记**：A 的工具执行事件会被写进 B 的 thread。

对比：同一文件 `:72-85` 的 `_get_parent_thread_id()` 用 `langgraph.config.get_config()` 读取，是正确做法。`_cached_thread_id` 应改为同样的请求级读取（contextvar / `request.runtime.execution_info`）。

### 4.7 【中高】本地持久化：锁都是进程内的，跨进程零互斥

**共性缺口（逐处 grep 得出）**：

1. **全仓 SQLite 无一处设置 `PRAGMA busy_timeout`**，也无一处显式 `BEGIN IMMEDIATE`。

| 文件日志 | `/app/logs/agent-server.log`，`TimedRotatingFileHandler` 每日轮转保 7 份（`start_server.py:232-241`）——**但线上 compose 没有挂 `/app/logs` 卷** → **每次发版重启即丢历史日志** |
| 健康检查 | 只有 `/ok`（LangGraph 内置）+ `/healthz`（`db_config.py:275`）+ `/api/mcp/status`；**无聚合就绪检查、无依赖连通性检查** |
| 追踪 | Langfuse（同机 `:3010`）+ LangSmith **双报**；`thread_id`/`run_id`/`trace_id` 贯穿 |

多用户场景下最缺的正是「谁在什么时候发了哪个 run、慢在哪」的入口。Langfuse 是**旁路**（注入失败只 debug 日志、不影响主流程，这是对的），但也意味着**追踪缺失是静默的**；且 Langfuse 与本服务同机，高并发写 trace 会反过来争资源。

### 5.4 容量基线：不存在

- **无任何压测/QPS/SLA 数据**；文档里唯一的规模预期是 **200 人**，且原文只写「`N_JOBS_PER_WORKER=10` 与 `LANGGRAPH_RUNTIME_EDITION=inmem` 在 200 人下的排队行为要先观测」（`docs/agent优化记录/多用户登录与用户隔离方案.md:403`）。

- **所以「能撑多少人」目前无法从仓库回答**，只能现场观测（§1 的 3~4 人是代码推导值，压测列为 P2-7）。
