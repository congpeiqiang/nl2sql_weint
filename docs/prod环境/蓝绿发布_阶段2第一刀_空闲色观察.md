# 蓝绿阶段 2 第一刀：起第二个色（空闲形态）做一次观察

> **这不是发版，也不切任何流量。** 目的是把三件**单色时永远测不到**的事变成实测结论 ——
> 而这三件事，阶段 2 真上线那天必须在**发版过程中**才撞上，那就太晚了。
>
> 最便宜的形态：起一个**不接流量、不领 run、指向 scratch 空库**的临时容器，静置几分钟，然后删掉。
> 回滚 = 一条 `stop && rm`。
>
> 依据：`蓝绿发布_阶段0实测.md`（运行时/启动顺序/自动迁移）、`蓝绿发布_阶段1切库手册.md`（切库与事故复盘）。
> 配置：仓内 `docker/compose.colorB.yml`（**只新增服务**的 overlay，静态闸 `scripts/verify_color_b_idle.py` 29/29）。

## 为什么是这一道（三件从未被测过的事）

| # | 从未测过 | 不测的后果 |
|---|---|---|
| 1 | **两色共享 `agent_data` 的多进程 SQLite**（grants / fts / traces / eval_queue / `pending_terminal` 都是 SQLite，仓库那把锁是**进程内**的） | 阶段 2 上线当天在**发版中**才发现 `database is locked` |
| 2 | **空闲色真的不漏活**（`N_JOBS_PER_WORKER=0` 是否真挡住「从共享队列领 run」） | 未验证的新代码在正式发版**之前**就已在处理真实用户问题 |
| 3 | **开机自动迁移**（官方 runtime 启动即跑 `/storage/migrations`）打的是**哪个库** | 新色一开机就改共享库 schema 而旧色还在跑 ⇒ expand-contract 无从设计 |

外加两个阶段 0 留下的未决项，同一次观察顺手收掉：**在跑计数是不是 per-process**（决定 promote/demote
能不能用）、**SIGTERM 会不会传到 Go core 子进程**。

**为什么指向 scratch 库**：第 3 条要「让迁移真跑」、第 1 条要「让补写器真跑」，这两件事在生产库上跑
就是**生产写**。把第二色的 `DATABASE_URI` 与 `CHECKPOINT_DB_URI` **都**指到新建的两个 scratch 空库，
迁移与补写器的**效果**全落在 scratch，生产库一个字节不动；而日志签名、启动行为与生产完全同型。
这能隔离得住，是因为补写器的写是**走 HTTP 到本色自己的 `LANGGRAPH_API_URL`**
（`src/agent/subagents/pending_terminal.py:418` + `:526`），不是直写共享文件。

> **无开关的那两处**（先说清，别事后才发现）：`api/custom_app.py:134-146` 的三个启动副作用里
> `NL2SQL_RETENTION_ENABLED`（有开关，本步已关）、`pending_terminal` 补写器（**没开关**）
> 与 `feedback`/`traces` 的 import 期建表迁移（**没开关**，但代码上已证是幂等 no-op：
> 全仓自建表都带 `IF NOT EXISTS`，`feedback/store.py` 的列迁移是逐列 try + `count>0` 早退）。
> 补写器一启动就**立即一轮**、之后每 60s 一轮。

### ⚠️ 开工前读到的三条，把观察①的预期改了

1. **`pending_terminal` 表当前是空的（0 行，2026-10-08 实测）**，且补写器**没有任何按 `attempts`
   升级成 `abandoned`/丢行**的路径（`attempts` 只 `+1`；唯一的放弃判据是 `created_at` 超
   `NL2SQL_PENDING_TERMINAL_MAX_AGE_SECS`（默认 6h））。⇒ 它**不可能**误丢、误弃生产的待补行；
   工作路径也对不上（B 的 API 在 scratch 库里查不到线程 ⇒ 只会 `bump_attempt` 后 `busy` 退出）。
   **代价是：它也不产生写**，所以**静置观察不到多进程写竞争**。
2. 同理，全站在**空闲**时几乎没有自然写流量（`traces`/`auth`/`fts`/`eval_queue` 都只在有 run /
   有登录 / 有搜索 / 有评测时才写）。⇒ **观察①本次只能证「两色并存不炸」，证不了「并发写不炸」。**
   真正的并发写竞争要等**两色同时有流量**的 promote/demote 演练（或下面那条受控探针）。
3. **`.env.prod` 里有 `CHECKPOINT_DB_URI`**（指向生产正文库）⇒ overlay 的那条覆盖是**承重的**，
   不是可选的。部署前必须用 `docker-compose config` 看到 B 的合并结果确实是 scratch
   （步骤 2 里那行 `config` 就是干这个的）。

### 3.5 受控并发写探针（**2026-10-08 已单独授权并执行**）

上面的静置观察**证不了**「两色同时写同一份 SQLite 会不会 `database is locked`」（空闲时没有自然写流量）。
要证它只能**造**并发写。探针写的是**共享生产卷**上一个**新建的、一次性的**文件（不碰任何应用数据、
用完即删），所以**单独拿了一次点名授权**，没有顺手带在观察里。

**第一版（两写者各 200 行短事务）—— 结果干净，但探针本身没被验证：**

```
busy_timeout=15000，两写者各 200 次 INSERT+commit：
  A: n=200 errors=0   B: n=200 errors=0   总行数 400   journal_mode=wal
负对照 busy_timeout=0，各 50 次：A0: n=50 errors=0  B0: n=50 errors=0  总行数 100
```

⚠️ **负对照没有出现竞争**（期望 `< 100` 行）⇒ 这一版**没有证明探针能检出竞争**，那 400/400 干净
也就**说明不了什么**（可能只是两个短事务恰好没重叠）。WAL + 微秒级短事务的自然重叠概率太低。

**第二版（造真竞争：写者 HOLD 显式持写锁 5s，1s 后另一写者尝试）—— 这一版才有判别力：**

```bash
# HOLD：BEGIN IMMEDIATE + INSERT + sleep 5 + COMMIT（isolation_level=None 手动管事务）
# TRY ：同一文件，HOLD 持锁 1s 后发起
# 用 A 容器当 HOLD、一次性容器（同一 agent_data 卷）当 TRY，两种 busy_timeout 各跑一次
```

| 用例 | TRY 的结果 | HOLD |
|---|---|---|
| `busy_timeout=0` | ❌ `OperationalError: database is locked`（**0.00s 就放弃**） | OK 持锁 5.0s |
| `busy_timeout=15000` | ✅ **等待 3.93s 后成功** | OK 持锁 5.0s |

⇒ **探针有判别力（能造出并检出竞争），且 `busy_timeout` 正是把它吸收掉的那个参数。**

**回到仓库：共享卷上的 SQLite 全部已是这个形态**（逐个读码核对，非推理）：

| 库 | 位置 | `journal_mode=WAL` | `busy_timeout` |
|---|---|---|---|
| grants / 归属账本 | `src/agent/auth/grants.py:93-99` | ✅（+`synchronous=NORMAL`） | **15000** |
| FTS `thread_text` | `src/api/thread_search.py:131-134` | ✅ | **15000** |
| feedback | `src/agent/feedback/store.py:233-238` | ✅ | **15000** |
| eval_queue | `src/agent/eval/eval_queue.py:109-115` | ✅ | **15000** |
| pending_terminal | `src/agent/subagents/pending_terminal.py:145-149` | ✅ | **15000** |
| trace_bind | `src/agent/trace/trace_bind_store.py:98-104` | ✅ | **15000** |
| traces 事件库 | `src/agent/trace/event_store.py:94-99` | ✅ | **15000** |
| retention（读/删上面这几个库） | `src/agent/utils/retention.py:196-198`（另 :230/:260/:627 同款） | —（WAL 是**库文件持久属性**，开过一次即长期有效，故无需重设） | **15000** |

也就是说：**「两色并发写」的防线是「WAL + 统一 15s busy_timeout」，这条防线已实测有效、
且全仓共享库无一处漏设。** 观察①至此**从「未知」降级为「机制已证 + 生产库形态已核对一致」**。

**仍未覆盖的**（若日后要钉死）：探针是**合成负载**（单行短事务 + 一个刻意长事务），
不是生产形态（真实写是批量 upsert + 更大的事务）；`journal_mode=WAL` 是**按库文件**生效的，
若某个库文件从没被任何进程在 WAL 下设过就地会退回 rollback journal —— 本次抽查的 8 个库都已 WAL。

### 三条修正与新增发现

1. **`_read_workers` 的「无效计数」分支在空闲色上并不触发**（我读 `drain.py:126` 的
   `if "active" not in workers` 时以为会）。实测空闲色 B 的 `metrics['workers']` **有** `active: 0`
   ⇒ `_read_workers()` 会返回 `(0, "postgres", **True**, …)` = **可信的 0**。这比预期好：
   空闲色能被断言成「真的没在跑」，promote/demote 流程可以放心用它。
2. **`/metrics` 经 nginx 是 404** —— P2-3 的指标端点在 `:8080/metrics` 这个路径上够不着
   （要么路径不对，要么没被 proxy）。本步改走容器内直读绕过，但**它本身是个待查项**。
3. **B 的启动日志里有 `chinook_semantic ... target/mdl.json missing`** —— 与本次无关的既有告警
   （A 的启动日志里同样有 2 条），因为两色都在启动时预检 workspace 里的项目。别把它算到蓝绿头上。

### 本次**没有**证实的那件事（已从「未知」收窄为「机制已证、合成负载」）

观察① 原本只证明了「两色**并存、空闲**时不出事」。**并发写那半，已由 §3.5 的探针补上**：
探针有判别力（能造出竞争也能检出竞争），`busy_timeout` 被证明正是吸收它的参数，且全仓 8 个共享库
的连法**逐个核对一致**（WAL + 15000）。所以结论从「未知」升为**「机制已证」**。

**仍未覆盖的**（诚实边界）：探针是**合成负载**（单行短事务 + 一个刻意 5s 的长事务），
不是生产形态（真实写多为批量 upsert、事务更长）；因此它证的是**「这类库在这个参数下能扛住跨进程写」**，
不是**「生产全部写路径在峰值下都扛得住」**。要钉死后者，仍只有阶段 2 真做 promote/demote 演练、
让两色**都有真实流量**时再抓一遍。
