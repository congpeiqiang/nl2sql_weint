## 本次改了什么（四个面）

| 面 | 改动 | 为什么 |
|---|---|---|
| 平台存储 | `LANGGRAPH_RUNTIME_EDITION=postgres` + `DATABASE_URI=…/nl2sql_platform` | inmem 是**每容器一份 pckl**、last-writer-wins ⇒ 两色并存必互相抹数据，蓝绿无从谈起 |
| 新库 | `CREATE DATABASE nl2sql_platform`（与 `nl2sql_checkpoint` 分库） | 平台元数据与会话正文分开，正文库 11 天历史不受影响 |
| 新服务 | `redis:7`（内网、不发布端口、无 requirepass） | 跨实例订阅**在跑的 run**（切流后浏览器在新色上仍收得到旧色那条流的 token） |
| 新运行时 | 镜像里补 `core-api-grpc` + `langgraph_runtime_postgres` + `/storage/migrations` | PyPI 上没有这个包（阶段 0 实测：simple 页 0 文件）⇒ 只能从官方镜像抽 |

**不动**：前端（本次零前端改动，不用 rebuild）、nginx、`nl2sql_checkpoint` 库、
`nl2sql_api_meta` 卷（**保留不删** —— 回滚要用）。

## 已知窗口（先把预期说清）

1. **≈30s 全量 502**：`stop -t 240` 排空 + 冷启（postgres 版型 16~26s）。与今天的发版同量级。
2. **数十秒的「空侧边栏」**：新容器起来时平台库还没有 threads，迁移脚本 POST 完才好。

4. 时间戳靠迁移脚本第 ⑤ 段直写回填（`ThreadCreate` 没有时间戳字段，不补就全挤到迁移那一刻）。

```bash

docker run --rm -v nl2sql-app_nl2sql_api_meta:/v alpine \

# ── 1. 平台库（POSTGRES_DB 只建了 checkpoint 库，第二个库必须手工建一次）──

  -c 'CREATE DATABASE nl2sql_platform'
docker exec nl2sql-app_postgres_1 psql -U nl2sql -l | grep -E 'nl2sql_(checkpoint|platform)'

# ── 2. 换线上 compose（就地覆盖，同 inode）────────────────
#    用仓库 docker/compose.prod.yml 的内容替换线上那份（保留原有 PG_PASSWORD 插值写法）
#    校验：docker-compose config -q          # 期望无输出

# ── 3. redis（新服务，不影响在跑容器）──────────────────────
#    ⚠️ 必须**在换完 compose 之后**再起：覆盖前线上 compose 里还没有 redis 这个服务，
#       先跑只会得到 `No such service: redis`（2026-10-05 实测踩到，步骤次序反了）。
docker-compose up -d redis
docker exec nl2sql-app_redis_1 redis-cli ping        # 期望 PONG

# ⚠️⚠️ 从这里开始，**任何** docker-compose 命令都不许用裸 `up -d <svc>`：
#    它会顺带收敛 depends_on 的依赖，而「重建」路径在本机（compose v1.29.2 + docker 29）
#    必炸 `KeyError: 'ContainerConfig'` —— 见文末「事故」。规则只有两条：
#    · 动本服务 → `up -d --no-deps langgraph-api`
#    · 动依赖   → 只在**确实不存在**时 `up -d`；已存在一律 `--no-recreate`
```

## 2026-10-05 实测记录与事故复盘

**实际结果**：`thread` 表 **264** 条（262 条带 owner，262/262 全是真实 `user_id`，0 条
`unknown`），新建失败 0、owner 丢失 0、`schema_migrations` = 61、FTS 185 行未动、
grants 账本 `backfill_thread_owner.py` 对账 **0 条待补**（本来已一致）。

### 事故：一次 `up -d` 把 postgres 打死（停摆 55 分钟）

第一遍执行时，我**没有**按上面步骤 2/3 的次序走，直接在旧版型上做了「起 postgres 版型」，
用的正是官方脚本那一行 `docker-compose up -d langgraph-api`（**没带 `--no-deps`**）。

- **机理**：compose v1 的 `up -d <svc>` 会把 `depends_on` 的依赖**一起纳入收敛计划**。
  langgraph-api 的依赖里有 postgres；compose 认为 postgres 需要 **recreate** ⇒ 走上重建
  路径 ⇒ 撞 docker 29 不支持的老接口：`compose/service.py:1579 get_container_data_volumes`
  里 `KeyError: 'ContainerConfig'`（重建要 inspect 旧镜像，而 docker 29 的镜像 inspect
  已没有这个键）。compose 把 postgres **停掉之后**才抛异常 ⇒ 停在一个「容器已删/已停、
  新的没起来」的状态。
- **为什么是这次才炸**：对比过 config-hash —— postgres 的 hash 在新旧 compose 文件里
  **完全一致**（`4e826ca1…`），而运行中的 postgres 容器携带的是更老的 `0356dc4b…`。
  也就是说 **postgres 容器与 compose 文件早就不同步**（远早于本次改动），compose 一直想
  recreate 它，只是以前没走到那条路径上。⇒ **这颗雷与阶段 1 的改动无关，是既有隐患**。
- **修复**：`docs/prod环境/release-backend.ps1` 第 5 步改成 `up -d --no-deps langgraph-api`，
  并就地写下事故注释。手册步骤 3 后面也加了同样的铁律。
- **恢复**：postgres 容器改名回滚 + 启动 ⇒ 零数据丢失；随后 `up -d --no-deps` 起
  langgraph-api，服务健康、`/ok` 立刻 200。
- **副作用（不是回归）**：恢复后一批用户报 401。逐条排掉后确认与切库无关 —— 签名密钥
  mtime 稳定在 09-21、`NL2SQL_AUTH_SECRET` 未设、`auth.sqlite` 最后写于 05:30 UTC、
  日志里**没有** `verify_token` 的吊销/删号告警，即走的是「根本没有 token」那条分支：
  **24h cookie 在 55 分钟停摆期间到期**。⇒ 教训是「停机时长会吃 cookie 寿命」，
  以及一个前端缺口：`/state` 轮询在 401 时**不会跳登录页**，用户看到的是转圈而不是登录框。

### 归属对账：三层来源 + 「跳过而不是回落 legacy」

`migrate_platform_store.py` 判一个孤儿线程归谁，按这个次序：

1. **pckl `metadata.owner`**（旧版型里带 owner 的那批）；
2. **grants 账本** `auth.sqlite.thread_owner` —— 注意列名是 **`user_id`**，不是 `owner`；
3. FTS `thread_text` —— ⚠️ **它根本没有 owner 列**（`thread_text(thread_id, title,
   updated_at, content)`），所以这一层现在取不到东西，留着只为将来 schema 变化。

三层都取不到 ⇒ **跳过，不建**（本次 205 条）。**绝不能回落 `owner="legacy"`**：
`legacy` 是**公共哨兵**，`owner_filter(identity)` 是
`{"$or": [{owner: identity}, {owner: "legacy"}]}` ⇒ 任何登录用户都能看见所有 legacy 线程，
把归属不明的孤儿塞进去 = **把别人的会话泄露给每个用户**。跳过则维持它们「本来就看不见」
的现状，是安全的那一侧。

### 迁移脚本的两处真实形态（合成夹具曾把它们掩盖掉）

- pckl 的 `threads` 是 **list**（元素是 dict，`thread_id` 是 **UUID 对象**、不是 str），
  不是 dict；`collect_threads` 原来按 dict 处理 ⇒ 生产 dry-run 读出 `threads = 0`。
  现在 list/dict 两态都认，且统一 `str()`（UUID 直接喂 `POST /threads` 序列化不了）。
- `collect_threads` 改成**白名单输出**（只搬 `thread_id/metadata/created_at/updated_at/
  state_updated_at`），其余键一律不搬 —— 免得把 `values`/`config` 这些整份搬进平台库。

## 阶段 2 必须接着做的两件事（本次不做，记在这里）

1. **把开机自动迁移改成受控步骤**：官方 runtime 启动即跑 `/storage/migrations`
   （阶段 0 实测 61 条）。单色时没问题；**两色并存时新色一开机就改共享库 schema**，
   而旧色还在跑 ⇒ 用 `DB_MIGRATION_BY_CORE_API` 这个杠杆（默认 `false`，语义需在阶段 2
   实测确认后再定怎么用），配合 expand-contract。
2. **两色共享 `agent_data` 的多进程 SQLite**：grants / fts / traces / eval_queue 都是
   SQLite。同进程内是「共享连接 + 一把进程内锁」，**两色 = 两个进程**，走的是 SQLite
   自己的文件锁 —— 需要复核 `busy_timeout` 与 WAL 在真并发下够不够（阶段 2 的 E2E 里带上）。
