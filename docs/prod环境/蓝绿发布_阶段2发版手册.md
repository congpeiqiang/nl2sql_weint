# 蓝绿发布 · 阶段 2 发版手册（后端链路 · 真零中断）

> 适用对象：`192.168.25.64`（64 生产）上的 nl2sql 后端。
> 一键入口：`docs/prod环境/release-backend-bluegreen.ps1`。本手册是它的**说明书 + 验收清单 + 出事了怎么办**。
> 前序：阶段 0（postgres 版运行时可行）→ 阶段 1（平台存储切 postgres）已完成，见
> `蓝绿发布_阶段0实测.md`、`蓝绿发布_阶段1切库手册.md`。

---

## 0. 一句话说清它解决什么

今天发一次后端 = `stop` 旧容器 + 冷启新容器，两段**串行** ⇒ **2026-10-05 实测 ≈29 秒全量 502**
（436 个请求里 11 个 502）；若发版时正好有 run 在跑，窗口还要先叠加排空（最长 240s）。

蓝绿把这件事换成：**起一个不接流量的新色 B → 探测 → 提升 → 改 nginx 一行 + reload → 排空并停旧色 A
→ 用新镜像把 A 起回来 → 再改一行 + reload 切回 A → 排空并停 B**。
用户侧的目标是 **0 个 5xx**（注意：是 5xx，不只是 502 —— 见下面「为什么切流必须在排空之前」）。

第一次切流让用户离开「跑旧代码的 A」，第二次切流把用户带回「跑新代码的 A」。
中间 A 被停掉重建、B 被停掉删除，这两件事**都发生在它们已经收不到用户请求之后**，
所以冷启（~26s）与排空（最长 240s）全都不可见 —— 这就是 0 个 5xx 的来源。

### 为什么切流必须在排空之前（这是整套设计里最关键的一条）

现有脚本是「**先排空再停**」。排空期间新提交的查询会被 `DrainGateMiddleware` 明确拒掉
（**503** + Retry-After）。503 也是 5xx，用户照样看得见。所以旧顺序只是**把 502 换成了 503**。

蓝绿必须**先切流、再排空**：切流之后旧色再也收不到用户请求，它的排空（以及排空期的 503）
**没有任何人看得见** ⇒ 这才是「零 5xx」。

### 本轮边界（诚实声明）

* 零中断**只覆盖后端/API 链路**。
* **前端发版仍是 `stop/rm/up frontend`**，`location /` 会有几秒 502。前端是无状态静态服务，
  套同一套 overlay 形态即可覆盖，**本轮不做**。
* 稳态**内存不变**：平时只跑 1 个色，第二色只在发版窗口里存在，收尾时被删掉。

## 1. 前置条件（每次发版前只读核对）

| # | 检查 | 命令 / 判据 |
|---|---|---|
| 1 | 平台存储是 postgres 版型（不是 inmem pckl） | `.env.prod` 无 `LANGGRAPH_RUNTIME_EDITION=inmem`；线上 `docker-compose.yml` 有 `DATABASE_URI` |
| 2 | nginx 上游是**请求期解析** | 线上 `docker/nginx.conf` 里有 `resolver 127.0.0.11 valid=10s ipv6=off;` 且 `proxy_pass http://$backend_up;` |
| 3 | 线上 nginx.conf 与**仓库模板**一致 | 脚本第 0 步自动比对（遮掉 `$backend_up` 那一行）。不一致会**中止**并打印 diff，确认无误才加 `-Force` |
| 4 | 磁盘有余量（新镜像 + 第二色的 `.langgraph_api` 卷） | `df -h` 剩余 ≥ 10G |
| 5 | postgres / redis 在跑 | `docker ps` 里有 `nl2sql-app_postgres_1`、`nl2sql-app_redis_1` |
| 6 | 上一次的残留第二色不存在 | `docker ps -a \| grep langgraph-api-b` 应为空（脚本会自己重建，但残留说明上次没走收尾） |
| 7 | **迁移必须是 add-only** | 见第 6 节 |

脚本第 0 步（`preflight`）会把这些打出来，包括当前线上镜像 ID —— **回退要用它，请抄下来**。

## 2. 发版时序（脚本 `release-backend-bluegreen.ps1` 逐步做什么）

> 以下「步骤号」与脚本里的 `== N/12 ==` 对齐。服务器侧的每一步都抽在
> `/tmp/nl2sql_bg_steps.sh` 里（脚本上传，可单独调用做手工排查）。

**稳态契约：`A`（`langgraph-api`）是常驻色，`B`（`langgraph-api-b`）只在发版窗口里存在。**
发版以「A 跑旧代码」开始、以「A 跑新代码」结束 —— 中途借 B 顶一下流量，收尾把 B 删掉。

| 步 | 动作 | 关键理由 |
|---|---|---|
| 0 | 预检（只读）：镜像 ID、nginx 防呆比对、**当前流量在哪一色**、**有没有残留 B**、`docker ps`、磁盘 | 有一样不对就**在动手之前**停。两条稳态前置不满足时**直接拒绝发版**（见 §2.1） |
| 1 | 本地打包（排除 `.env.dev` / `docker/` / `model_config.json` …） | 与 `release-backend.ps1` 逐字相同 |
| 2 | 分片上传（0.5MB/片，每片重试 8 次） | VPN 链路单连接寿命短，整包必断 |
| 3 | 服务器拼接 + `rm -rf backend/src` + 解压 + `docker-compose build langgraph-api` | 解压**不删**「仓库里已删」的文件，先清后解 |
| 4 | 上传 overlay（`IMAGE_ID_PLACEHOLDER` → 实测 image ID）、`bg_steps.sh`；`docker cp` 新的 `ops_drain.py` 进 A 容器 | `docker/` 不进发版包，必须单独传；旧镜像里的 `ops_drain.py` 是**旧逻辑** |
| 5 | `COLOR_B_JOBS=0` **先 `stop && rm -f` 再** `up -d --no-deps langgraph-api-b`，探测 B，并**与 A 对照预检结论** | 先起**空闲色**：新代码就绪但绝不先领真实用户的 run（`N_JOBS_PER_WORKER` 只在 import 期读一次，没有运行期开关）。先清再起＝铁律③（残留 B 会让 `up -d` 走 recreate 路径 ⇒ `KeyError:'ContainerConfig'`）；预检判据见 §2.2 |
| 6 | 提升 B：`stop && rm -f && COLOR_B_JOBS=10 up -d --no-deps` | 提升只能靠**重建**（同上）。此刻 B 还没接流，重建免费 |
| 7 | **切流到 B**：起 1s `/ok` 轮询 → 渲染 nginx.conf（只改 `set $backend_up` 一行）→ 备份 → `cat >` 就地写 → `nginx -t` → `nginx -s reload` | reload 是**优雅**的：旧 worker 会服完已建立的连接才退，在跑的 SSE 不被掐。`nginx -t` 失败会自动就地回滚，绝不留下坏配置 |
| 8 | **排空 A** → 连续 3 次 idle 确认 → 同一 ssh 会话内 `docker stop -t 240` + `rm -f` | A 已收不到用户请求，它的排空对任何人不可见 |
| 9 | **用新镜像把 A 起回来**（`start_a_new`：base compose、`--no-deps --no-build`、`N_JOBS_PER_WORKER=10`）→ 探测 `/ok` | B 在接流，A 的冷启对用户不可见。A 起来就领 run 是**安全**的：它跑的镜像与正在接流的 B **逐字节相同**（B 已把这份代码验证过）；与「起空闲色 B」不同，B 承载的是未经验证的新代码 |
| 10 | **切流回 A**（同一套就地覆盖 + `nginx -t` + reload） | 稳态契约恢复：流量回到常驻色 |
| 11 | **先 `docker cp` 新 `ops_drain.py` 进 B**，再 **排空并停临时色 B**（`cutover`，同一 ssh 会话内） | `docker cp` 是 **per-container**，第 4 步只给 A 就位过 ⇒ 不给 B 就位的话，B 那侧的排空判据根本跑不起来（2026-10-08 E2E 实撞，见 §2.3）。B 与 A 是同一份镜像，就算它在切流那一瞬又领到 run 也无害；`cutover` 仍会先排空再停 |
| 12 | 停轮询、断言 0 个非 200、打印窗口、两色日志查 `database is locked`、写状态文件 | 「零中断」这个结论必须由采样数据支撑 |

### 2.1 为什么结尾要绕回 A（而不是让 B 常驻）

留 B 常驻能少一次切换，但代价是：**下一次发版就没有空闲的第二色可用了**（B 自己就是活色），
脚本第二次会走到第 4 步 `cp_drain $ACt` 才失败 —— 那时 A 的容器已经不存在了。
而且 `release-backend.ps1`、日志 grep、运维习惯、监控全都认 `nl2sql-app_langgraph-api_1` 这个名字。

所以第 0 步有两条**拒绝发版**的前置检查（不满足时脚本直接停，不往前走）：

1. **当前流量必须在 A**（从线上 `docker/nginx.conf` 的 `set $backend_up` 读出）。
   不满足 ⇒ 上一次发版/回退没走完 ⇒ 先 `-Rollback` 或 `rm_b`，别硬来。
2. **不能有残留的 B 容器**。有 ⇒ 先 `bash /tmp/nl2sql_bg_steps.sh rm_b`。

> 这两条把「脚本跑第二遍」这种输入变成**响亮的拒绝**，而不是让它走到一半才炸。
> 硬来（`-Force`）能做，但要知道自己在破坏哪条假设。

### 2.2 第 5 步的预检判据：**B 不比 A 差**（不是「B 有没有预检失败」）

`start_server.py` 的启动预检是**两档**的：

- **致命档**：关键 server（`wrenai_*` / `dbmcp`）缺失 ⇒ `sys.exit(1)`，**进程直接退出**
  ⇒ `/ok` 永远不会 200。这一档由脚本里的 `wait_ok` 覆盖，**不需要额外判据**。
- **降级档**：`MCP_ALLOW_DEGRADED=1` 时打一行 `⚠️ 预检失败(降级启动): 非关键 server 缺失（…）`
  然后**照常启动**。

⚠️ **本机（64）长期处于降级档**：`.env.prod:71` 设了 `MCP_ALLOW_DEGRADED=1`，而
`wrenai_chinook` 这个 **`[CRITICAL]`** 语义库连不上（`[sub] wrenai_chinook: FAILED`），
所以 **A 自己的启动日志里就有「❌❌❌ MCP 启动预检失败」+「降级启动」**（A 已这样健康跑了数小时）。

⇒ 拿「日志里有没有『预检失败』」当判据是**错的**：那等于把 **A 的常态**判成 B 的失败，
这台机器**永远发不了版**（2026-10-08 首次 E2E 就是这么被拦下的 —— 尽管当时 B 健康、`/ok`=200）。

脚本用的判据是**与正在接流的 A 对照**：

1. B 有「预检失败」而 **A 没有** ⇒ 新镜像带来回归 ⇒ **拒绝切流**。
2. 两者都有 ⇒ 各自取出缺失 server 集合，**B 新增了 A 没有的**才拒流（子集判断）。
3. 两色缺失集合相同（本机常态：都是 `wrenai_chinook`）⇒ 记一行 info，继续。

> 语义是「**新镜像不许比正在跑的那版更差**」—— 这正是蓝绿发版该问的问题。
> 子集判断用的是 `comm -13`，两边都先 `sort -u`（`comm` 对未排序输入会静默给错结果）。

### 2.3 排空探针必须**跑得起来**，否则拒绝停容器（fail-closed）

`ops_drain.py` 是**仓库里**那份、在发版时 `docker cp` 进容器 `/tmp/nl2sql_ops_drain.py`
（容器镜像里那份是旧逻辑 ⇒ 判据不会跟着发版更新）。而 `docker cp` 是 **per-container** 的：

* 第 4 步只给 **A** 就位；
* **B 是另起的一个容器** ⇒ 第 11 步必须**再给 B 就位一次**。

2026-10-08 的生产 E2E 就撞在这上面：第 11 步的 B 里没有这份脚本，`docker exec python
/tmp/nl2sql_ops_drain.py` 报 `can't open file`，**整段排空被静默跳过** —— 只因为当时系统空闲
（零 run）才没出事。

⇒ 所以 `cutover` 里加了一道**硬闸**：

```bash
docker exec "$ct" test -s /tmp/nl2sql_ops_drain.py \
  || die "$ct 存在但里面没有 /tmp/nl2sql_ops_drain.py —— 先跑 bash $0 cp_drain $ct；拒绝在无法判定排空时停容器"
```

**「不知道有没有在跑的 run」绝不允许被当成「已排空」** —— 那正是这套设计要根除的 fail-open
（同一个病还有第二处：`ops_drain.py` 的就绪判据原本只看 `remaining == 0`，而服务端读不到计数时
会兜底返回 0；已改成必须 `remaining == 0 and counter_trusted`）。

另外两条同类硬化：

* `cutover` / `cp_drain` 对**不存在**的色**空转**（打 `DRAIN_READY=n/a` 后 `exit 0`）——
  回退路径上临时色往往已被删掉，不空转的话 `-Rollback` 会死在 `docker cp` 上。
* `DRAIN_READY` 不是 `yes` 时**响亮地警告**（仍然停，靠 `docker stop -t 240` 与应用自身的
  SIGTERM 协作式排空兜底），绝不安静地过去。

### 2.4 预检字段的解析：`docker inspect` 对不存在的对象会吐一个**空行**

本机 docker 对**不存在**的容器，`docker inspect -f '{{.Id}}' <名字>` 会先往 **stdout 打一个空行**
再以非 0 退出。所以

```bash
echo "B_EXISTS=$(docker inspect -f '{{.Id}}' "$B_CT" 2>/dev/null || echo no)"   # ✗ 错
```

拿到的是 **两行**（`""` + `"no"`）—— PowerShell 侧 `B_EXISTS=(\S+)` 匹配不到，`$bExists` 变成**空串**，
于是稳态（没有残留 B）下**每一次发版都被守卫拦死**。2026-10-08 回退演练实撞（正向那次只因有残留 B
+ 带 `-Force` 才走了 warn 分支，稳态分支从来没被跑过）。

定式：**先剥空白再给默认值**，或干脆只看退出码。

```bash
b_id=$(docker inspect -f '{{.Id}}' "$B_CT" 2>/dev/null | tr -d '[:space:]')
echo "B_EXISTS=${b_id:-no}"                                                     # ✓ 恰好一行
```

PowerShell 侧另有兜底：**取不到 `B_EXISTS` 就响亮地拒绝发版**，绝不把空串当成「没有残留 B」。

### 为什么第 8 步要「同一 ssh 会话内」做完

`N_JOBS_PER_WORKER` 是进程 import 期常量，**旧色一旦起来就会持续从共享队列领 run，直到被停**。
切流之后 A 仍持有 10 个 run 槽，仍可能领到刚提交给 B 的 run。本机无法消除这个竞态（见第 5 节），
只能把「确认它空闲」与「真的停掉它」压进**一次 ssh 往返**里，窗口缩到毫秒。
所以第 8 步的判定与 `docker stop` 在**同一个** `bg_steps.sh cutover` 子命令内。

## 3. 验收断言（发完必须逐条核）

| # | 断言 | 怎么核 |
|---|---|---|
| 1 | **1s 轮询 `/ok` 全程 0 个非 200**（覆盖**两次**切换 + A 的重建 + 两次排空） | 脚本结尾直接打印 `非 200 **0** 个`；原始采样在 `/tmp/nl2sql_bg_poll.log` |
| 2 | 切流到 B 后**停掉 A 不产生 502** | 同上（这正是「切流真的生效了」的证据——若 nginx 没切过去，停 A 必出 502） |
| 3 | 两色日志 `database is locked` 各 0 条 | 脚本第 12 步打印；A/B 的日志在停容器前已另存 `/tmp/nl2sql_last_langgraph-api*.log`（`rm` 会把日志一起带走） |
| 4 | `thread` / `schema_migrations` 计数不变 | 见下面的 SQL（平台库 `nl2sql_platform`） |
| 5 | 新色真的在领 run | `bash /tmp/nl2sql_bg_steps.sh final_checks`；或看 A/B 日志里不再是 `Skipping queue` |
| 6 | **稳态恢复**：只剩 A 一个 langgraph-api 容器、`set $backend_up` 是 `langgraph-api:2026` | 脚本第 12 步的 `final_checks`；再 `docker volume rm nl2sql-app_nl2sql_api_meta_b` 收尾 |
| 7 | 回退闸（做了演练的话）两个方向都 200 | `/tmp/nl2sql_bg_poll.log` 里两个方向切换点的前后都是 200 |

```bash
# 平台库计数（容器名按线上实际）
docker exec nl2sql-app_postgres_1 psql -U nl2sql -d nl2sql_platform -c \
  "select (select count(*) from thread) as thread, (select count(*) from schema_migrations) as migrations;"
```

### 残余竞态怎么量

第 8 步（停旧色 A）与第 11 步（停临时色 B）都会打印 `DRAIN_READY=yes|stale|no`：

* `yes` = 排空清零**且计数可信**，且随后 3×2s 里它一直空闲 ⇒ 在采样精度内没有领到新 run；
* `stale` = 3 次确认期间它**又变忙了** —— 这就是残余竞态被观测到的那一次（见第 5 节）。

> **只看第 8 步的那个值。** 第 11 步停 B 时 A/B 已是同一份镜像，B 领到 run 也无害
> （两色跑的是同一份代码）；有害的只有第 8 步：A 跑的是**旧代码**，被它领走的 run 会用旧逻辑跑完。

## 4. 回退

### 4.1 切流之前出问题（B 起不来 / 探测不过 / `nginx -t` 失败）

**线上零影响**：B 没接流，nginx 也没切。脚本会在这些点直接抛错退出，A 照常服务。
处理：`bash /tmp/nl2sql_bg_steps.sh rm_b` 清掉 B（这个子命令**脚本里真有**，只碰 B 那一个容器），
排查后重跑。

> `nginx_apply` 若 `nginx -t` 失败，**已经就地回滚**到备份，且**没有 reload** ——
> 线上仍是旧配置，流量未变。

### 4.2 要回退（发完发现新版有问题）

```powershell
.\release-backend-bluegreen.ps1 -Rollback                 # 旧镜像 ID 从 /tmp/nl2sql_bluegreen.state 读
.\release-backend-bluegreen.ps1 -Rollback -OldImageId sha256:xxxx…   # 显式给（推荐：不依赖临时文件）
```

**回退本身也走蓝绿**：用**旧镜像**起临时色 B（`N_JOBS_PER_WORKER=0`）→ 提升 → **切流到 B**
→ 排空并停 A（此刻它跑的是要退掉的那版）→ `docker tag` 旧 ID 把 A 换回旧镜像起回来
（`--no-build` 是硬保证，不会悄悄构建别的东西）→ **切流回 A** → 排空并停 B。

> **为什么回退不能直接重启 A 换镜像。** 回退最常见的场景恰好是「发完发现新版有问题」，
> 而那时**窗口已经关了**（B 已删、流量在 A）。若此时 `stop/rm/up` 把 A 换成旧镜像，
> 就是拿真用户等 ≈26s 冷启 —— 与「零中断」自相矛盾。所以回退用**同一套 A→B→A 形态**，
> 只是镜像角色对调。**要害只有一条：切流到 B 必须早于「把 A 换回旧镜像」**
> （`verify_blue_green.py` 把这条连同负对照做成了断言）。

**回退的终点与发版的终点是同一个稳态**（A 常驻、B 已删），所以回退之后可以立刻再次发版；
`-Rollback` 连跑两次就是「退回去、再退回来」，状态文件会正确地翻两次，最终回到原样。

⚠️ 回退**要有旧镜像 ID**。它来自发版脚本第 0 步打印的 `OLD_IMAGE_ID`，也写在
`/tmp/nl2sql_bluegreen.state`。若容器被 `docker image prune` 清过，旧镜像就真没了 ——
那时只能回到「用当前仓库重新构建」这条老路。

⚠️ 回退之后 A 跑的是**上一版代码**，而平台库可能已经被新版的迁移改过（迁移 add-only，
所以旧代码一般仍能跑，但要留意；见第 6 节）。

## 5. 残余风险

### 5.1 不可消除的那一条：切流后旧色仍可能领到一个 run

`N_JOBS_PER_WORKER` 是 import 期常量（`langgraph_api/config/__init__.py:380`，
`start_server.py:97` 只是 `setdefault`），**没有运行期开关**；平台队列也不归我们管。
所以夹在「nginx 已切到 B」与「A 被停掉」之间的那几毫秒里，A 若刚好从共享队列领到一个
新 run，那个 run 会跑在**旧代码**上。

* 缓解：第 8 步的「连续 3 次 idle 判定 → 立刻 stop」压到**同一次 ssh 会话**内。
* 观测：第 8 步的 `DRAIN_READY=stale` 就是被观测到的一次。
* 影响面：那一个 run 用旧代码跑完（不是崩溃、不是丢数据），用户拿到的是旧版行为的结果。
* ⚠️ **第 11 步停 B 时没有这个问题**：那时 A 与 B 是**同一份镜像**，B 领到的 run 也在
  为同一版代码干活。整轮发版**只有第 8 步那一个窗口**是有害的。

### 5.2 第二色是「原样复制」的隐式契约

overlay 里所有 `environment` 都必须与 base **逐字相同**（只有 `N_JOBS_PER_WORKER` 是变量）。
**以后往 base 加了新环境变量，必须同步加到 overlay** —— 忘了的话新色会用不同的配置接流量，
而且症状会很怪（一半请求正常、一半不正常）。`scripts/verify_blue_green.py` 把「两条 URI 与
base 逐字相同」做成了断言，但新增变量这一条只能靠人。

### 5.3 其它已知但不在本轮范围的

* 前端不零中断（第 0 节边界）。
* 单例后台任务（补写器 / 保留策略 / metrics 采样）在窗口里会有**短暂双跑**：已核实这些动作
  幂等或无害（补写器的写是 HTTP 到自己色、行级唯一索引兜底；保留策略按 M2 口径只清机器产物）。
  `eval_queue` 的重复打分风险已用租约消除（见 `src/agent/eval/eval_queue.py`）。
  真正的单例闸门（`pg_try_advisory_lock`）是后续项。

## 6. expand-contract 约束（加了迁移就要看这一节）

第二色开机时会跑 `/storage/migrations`（**在 `DATABASE_URI` 指定的库上**）——
也就是说，**新镜像带的迁移会在「起空闲色」那一刻就打到共享生产库**，而旧色还在跑。

⇒ 强制约束：**langgraph 官方迁移与本仓自建表迁移都只能 add-only**
（新表 / 新列 / 新索引，不删不改不重命名）。本仓自建表的惯例（`IF NOT EXISTS` + 逐列 `try`）
已满足；**发版前请核一遍本次 diff 里有没有 DDL 是破坏性的**。

真要做破坏性变更（删列/改类型），只能走「停机窗口」这条老路 —— 那时用
`release-backend.ps1`（老脚本仍在，见 `发布脚本.md`）。

## 7. 收尾清理

发版成功后临时色 B 会在**第 11 步**被排空并删掉，稳态只剩常驻色 A。若中途失败留下残留：

```bash
bash /tmp/nl2sql_bg_steps.sh rm_b                       # 删 B 容器（脚本里真有其人，见 §4.1）
docker volume rm nl2sql-app_nl2sql_api_meta_b           # 删 B 的独占卷（确认 B 不在跑）
docker exec nl2sql-app_nginx_1 grep -n 'backend_up' /etc/nginx/nginx.conf   # 确认现在切在哪一色
```

第 12 步结尾脚本会**打印**这条 `docker volume rm` 提示（卷留着不影响服务，下次发版会重建它）。

`docker/compose.colorB.yml` **保留**（下次发版还要用）。

> **第 9 步会看到一行 `Found orphan containers (nl2sql-app_langgraph-api-b_1)` —— 这是预期的。**
> `start_a_new` 故意**不带 overlay**（A 的 compose config-hash 必须回到 base 原样，见 §2.1），
> 而此刻 B 还在跑 ⇒ compose 只认得 base 里的服务，自然把 B 报成 orphan。它**不会**动 B。

## 8. 与旧脚本的关系

| 场景 | 用哪个 |
|---|---|
| 常规后端发版 | `release-backend-bluegreen.ps1` |
| 破坏性迁移 / 需要停机窗口 / 蓝绿本身出问题要回到简单路径 | `release-backend.ps1`（**仍在，且仍可用**） |
| 前端发版 | `release-frontend.ps1`（本轮无改动） |

两个脚本共用同一套打包/上传/解压逻辑，互不依赖。
