# 蓝绿阶段 1 切库：浏览器验收清单（三条）

> **谁执行**：需要同时具备 ① 一个浏览器 ② 一个**非 admin** 账号 ③ 64 的 SSH。
> **对应**：`蓝绿发布_阶段1切库手册.md`「验收」第 3、4 条 —— 那两条是**只能靠浏览器**的部分，
> 其余（条数、schema_migrations、计数来源、日志）已在 2026-10-05 切库当天从数据层核过。
>
> **前置**：阶段 1 已切库（2026-10-05），后端跑 postgres 版型，`thread` 表 264 行。

## 为什么是这三条

数据层核对验的是「**我用一套读法**打开这些库看到的东西」；这三条验的是「**应用用另一套读法**读得回来」。
两套读法不一致时，前者**看不见** —— 本仓已经被同类坑咬过两次（真 pckl 的 `threads` 是 list 而我按 dict 读；
`thread_text` 的 owner 列的存在性假设）。三条各锁一个面，且**每一条的失败都是静默的**：

| # | 面 | 失败形态 |
|---|---|---|
| 1 | 授权过滤（平台库 `metadata.owner`） | owner 丢了 ⇒ 全员侧边栏**空**；或回落 `legacy` ⇒ **跨用户泄露** |
| 2 | 检索（`fts.sqlite` 的 owner 列） | 非 admin **搜什么都搜不到**，admin 一切正常 |
| 3 | 续跑（平台库 `thread_id` ↔ checkpoint 键） | 点开老会话是**空的/新会话** —— 侧边栏看着完全正常，用户以为历史没了 |

⚠️ **1 和 2 都必须用非 admin 账号**：过滤是二选一的（[thread_search.py](../../src/api/thread_search.py)
`if is_admin: owner_clause = ""`），**admin 不过滤 ⇒ 用 admin 测会把三类问题全部掩盖**。

## 1. 非 admin 只看自己的（授权过滤面）

**做什么**
1. 浏览器开 `http://192.168.25.64:8080`，**用非 admin 账号登录**（清掉旧 cookie，别复用 admin 的会话）。
2. 看侧边栏：把分组展开，数一遍总条数。
3. 在侧边栏翻找 0.1 里那个**靶子会话的标题/首句**。

**通过的样子**
- 侧边栏总数 = 0.1 ① 里该 owner 的 N（±1，迁后新建的会话会加）。
- 靶子会话**找不到**（标题、首句都搜不到）。
- 控制台/网络面板里 `threads/search` 之类的请求是 200，**不是 401/403**（403 说明是登录态问题，不是过滤问题）。

**不通过 → 意味着什么**
| 现象 | 含义 |
|---|---|
| 侧边栏**空**，但 SQL 显示该 owner 有 N 条 | `metadata.owner` 在迁移中丢了或写成了别的值 ⇒ fail-closed，**所有人侧边栏都空** |
| 能看到**别人的**靶子会话 | owner 被回落成了 `legacy`（公共哨兵，所有登录用户都放行）⇒ **跨用户泄露，最高优先级** |
| 只看得到自己的、但**总数对不上** | 有一条路径（分页/分组/搜索）没走同一个过滤器 |

## 2. FTS 点搜（检索面）

### 2.0 先探一个未决点：线上这版到底有没有 owner 过滤

`thread_text` 的 owner 列是**懒加**的（没有就 `ALTER`，**旧行留空**），而查询侧非 admin 是
`AND t.owner IN (?, ?)` —— **空 owner 一律不放行**。2026-10-08 直接读生产 `fts.sqlite`：
**没有 owner 列**（185 行）。

**已判死，不是缺陷**：`owner_clause` 与这段懒 `ALTER` 是 2026-09-28 `c33e4ec` 引入的，
是 `ee8c194`（v13.0.1）的**祖先** ⇒ 10-05 重建的生产容器**必然带**它。缺列只说明
**那次重建之后还没人用过搜索框**（185 行正是切库前的索引口径）。自愈路径在代码里：
`_connect()` 的 `ALTER` 与 `_search` 的过滤查询在**同一把锁内、ALTER 在前**（不会 500），
而刷新 `_refresh_if_stale` 排在 `_search` **之前**（`thread_search.py:442` → `:447`），
`to_rebuild` 的三元组比对**含 owner**，会把刚被 ALTER 写成空 owner 的历史行全量重拉补上归属
（其 docstring 明写「owner 为空的那一批……必须重拉一次把归属补齐」）。

⇒ **这一步探的是「自愈有没有真的发生」**，期望：搜一次之后 owner 列出现，且 t1 自己的会话
`owner='t1'`（不是空）。

```bash
# 先看「搜之前」的状态（2026-10-08 实测：无 owner 列、185 行）
docker exec -i nl2sql-app_langgraph-api_1 python - <<'PY'
import sqlite3
c = sqlite3.connect('file:/app/data/shared/checkpoint/fts.sqlite?mode=ro', uri=True)
cols = [r[1] for r in c.execute('PRAGMA table_info(thread_text)')]
n = c.execute("SELECT count(*) FROM thread_text").fetchone()[0]
print('列:', cols, '| 总行数:', n)
if 'owner' in cols:
    e = c.execute("SELECT count(*) FROM thread_text WHERE coalesce(owner,'')=''").fetchone()[0]
    print('owner 为空:', e, '行')
PY
```

然后走完 §2.1 的搜索，**再跑一次同一段**：期望 owner 列**已出现**、总行数涨到平台库的量级、
且 `owner` 为空的行只占少数（拉取失败的那几条）。**空 owner 的行永远搜不出来**，
它的主人也搜不到自己那条 —— 这是本步真正要抓的东西（见 2.4）。

### 2.1 用非 admin 账号搜

1. 仍以**非 admin** 账号，用搜索框搜 0.1 靶子会话里的一个**特征词**（3 字以上中文，或英文/数字）。
2. 再搜一个**自己会话里**的特征词。
3. 再搜一个**肯定不存在**的词。

**通过的样子**
- 搜自己会话的特征词 → **有命中**（这条是基线，空说明搜索整体坏了，与 owner 无关）。
- 搜别人的特征词 → **0 命中**。
- 搜不存在的词 → 0 命中，且**不报错**。

**不通过 → 意味着什么**
| 现象 | 含义 |
|---|---|
| 搜**自己的**也 0 命中 | 检索整体断了：FTS 索引里的 `thread_id` 与平台库对不上（表征不一致），或索引没重建 |
| 搜**别人的**有命中 | owner 过滤没生效 ⇒ **跨用户泄露**（对照 2.0：若没有 owner 列，基本可以坐实是这版代码的问题） |
| 短词（≤2 字）搜不到 | **不是故障**：trigram 下限 3，中文两字词恒不命中，会回退 LIKE —— 换 3 字以上的词再测 |

### 2.4 真正的残留风险：自愈是「逐会话 best-effort」的

刷新对每个待重建会话调一次 `GET /threads/{tid}/state`，**非 200 直接 `return`、
异常只 `warning` 不复位 owner**（`_fetch_one`）⇒ 那一条会**永久停在 `owner=''`**，
它的主人从此搜不到自己的这条会话，而**别人也搜不到**（不泄露，但静默丢一条）。

所以 §2.1 里「搜**自己的**也 0 命中」这一格，指的就是这个 —— 对照搜后探针里
**空 owner 的行数**：只有几条 = 这几条拉取失败，按会话删索引重建即可；**整批都空**
= 刷新整体没跑起来（看 `docker logs … | grep thread_search`）。

**别在这份清单里就地改代码。** 判线上跑什么只有 `docker exec md5sum <文件> | tr -d '\r'` 说了算。

## 3. 老会话续问（续跑面）

**做什么**
1. 以非 admin 账号，点开 **0.1 里排最前面的那条老会话**（切库前就存在的）。
2. 确认**历史消息全在**（用户问句 + 助手回答 + 图表/报告如果当时有）。
3. 在输入框里**接着问一句**（越省越好，例如「总结一下我们上面聊了什么」），等它答完。

**通过的样子**
- 历史消息完整，**不是**一个空会话。
- 接着问的回答**接得上上面的内容**（不是答非所问、不是把它当成新会话）。
- 回答过程里前端正常出流式。

**不通过 → 意味着什么**
| 现象 | 含义 |
|---|---|
| 点开是**空会话** / 只有一条新消息 | 平台库的 `thread_id` 与 `nl2sql_checkpoint` 里的 checkpoint 键**不是同一个表征** ⇒ 正文找不回来（**看起来就是历史丢了**） |
| 历史在、但**续问接不上** | 同上，只是断在 checkpoint 读取那一刻 |
| 点开**报错** | 看 `docker logs nl2sql-app_langgraph-api_1` 的同期报错，别猜 |

> **已知降级，别误判为失败**：**历史 run 没有迁移**，所以老会话里**看不到历史 run 卡片**，
> 前端会退化成「轮询 state + 继续按钮」。**会话消息、图表、报告全在**（正文在 `nl2sql_checkpoint`，
> 本次没动过）。判定标准是**消息内容**，不是 run 卡片。
