# 生产发版命令手册（192.168.25.64）

> 本文**只列命令**。设计原理、逐条验收理由、残余风险见 [蓝绿发布_阶段2发版手册.md](蓝绿发布_阶段2发版手册.md)。
> dev 环境（25.34）的脚本在 `docs/dev环境/`，**两者不要混用**。账号地址见 [账号密码汇总.md](账号密码汇总.md)。

| 脚本（都在本目录） | 作用 |
|---|---|
| [release-backend-bluegreen.ps1](release-backend-bluegreen.ps1) | **后端发版（蓝绿，首选）** —— 用户侧 0 个 5xx |
| [release-backend.ps1](release-backend.ps1) | 后端发版（老路）—— 破坏性迁移 / 停机窗口的退路，≈29s 全量 502 |
| [release-frontend.ps1](release-frontend.ps1) | 前端发版 —— **不是蓝绿**，`location /` 有几秒 502 |

## 1. 后端发版（蓝绿 · 首选）

```powershell
cd D:\code_work_space\llm\nl2sql\docs\prod环境
.\release-backend-bluegreen.ps1
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `-DrainBudget` | `180` | 排空预算（秒），须 < compose `stop_grace_period=240s` |
| `-ChunkMB` / `-MaxRetry` | `0.5` / `8` | 分片大小 / 每片重试；VPN 链路差时把 `-ChunkMB` 调更小 |
| `-Force` | — | 线上 nginx 与仓库模板不一致 / 流量不在 A / 有残留 B 时，允许继续（**知道自己破坏哪条假设再用**） |
| `-Rollback` / `-OldImageId` | — | 见 §4 |

**发版前只读核对**（脚本第 0 步会自己打一遍，不满足会**在动手前停**）：

```bash
ssh weint@192.168.25.64 'docker ps -a | grep langgraph-api; \
  docker exec nl2sql-app_nginx_1 grep -n backend_up /etc/nginx/nginx.conf'
```
期望：只有 `nl2sql-app_langgraph-api_1` 一个容器（无残留 B），且 `set $backend_up  "langgraph-api:2026"`。

**结束时看这几行**（脚本尾部的「本次发版结论」）：

```
POLL_TOTAL=131   POLL_NON200=0        ← 1s 轮询 /ok 全程非 200 计数
OLD_IMAGE_ID=sha256:…                 ← 抄下来，回退要用
排空确认：A=yes  B=yes                 ← A=stale 见 §5
RELEASE_EXIT=0
```

> ⚠️ 第 9 步会打一行 `Found orphan containers (nl2sql-app_langgraph-api-b_1)`，**这是预期的**（起 A 时故意不带 overlay）。

## 2. 后端发版（老路 · 只在三种情况用）

```powershell
cd D:\code_work_space\llm\nl2sql\docs\prod环境
.\release-backend.ps1
```

只在 ① **破坏性迁移**（删列 / 改类型，蓝绿的 expand-contract 不允许）、② 明确要一个**停机窗口**、
③ 蓝绿脚本本身出问题时用。代价：**≈29s 全量 502**（有 run 在跑时 = 排空最长 240s + 冷启）。

## 3. 前端发版

```powershell
cd D:\code_work_space\llm\nl2sql\docs\prod环境
.\release-frontend.ps1              # 本地构建 → 打包 → 分片上传 → 只重启 frontend → 验 BUILD_ID
.\release-frontend.ps1 -SkipBuild   # 跳过本地构建（.next 须已是最新）
```

* 构建**必须在本地**：前端源码含 DLP 密文，只有本机的 DLP agent 解得了，服务器上 build 不出来。
* 只对 `frontend` 做 `stop/rm/up`，**不碰 nginx**（新前端 IP 由 nginx 请求期解析 ≤10s 自愈）。
* **不是蓝绿**：`location /` 有几秒 502。

## 4. 回滚

### 后端（蓝绿，零中断）

```powershell
cd D:\code_work_space\llm\nl2sql\docs\prod环境
.\release-backend-bluegreen.ps1 -Rollback -OldImageId sha256:xxxx…
.\release-backend-bluegreen.ps1 -Rollback          # 不给 ID 则读 /tmp/nl2sql_bluegreen.state
```

* 旧镜像 ID 来自上次发版第 0 步的 `OLD_IMAGE_ID`。**被 `docker image prune` 清过就真没了** ——
  那时只能回当前仓库重新构建发一版。
* 回退的终点 = 发版的终点（A 常驻、B 已删），所以回退完可以**立刻再次发版**；`-Rollback` 连跑两次 = 退回去再退回来。
* 回退后 A 跑的是上一版代码，而平台库可能已被新版迁移改过（迁移是 add-only，一般仍能跑）。

### 切流之前就出问题（B 起不来 / 探测不过 / `nginx -t` 失败）

**线上零影响**（B 未接流、nginx 未切），清掉 B 重跑即可：

```bash
ssh weint@192.168.25.64 'bash /tmp/nl2sql_bg_steps.sh rm_b'
```

> `nginx_apply` 若 `nginx -t` 失败会**就地回滚到备份且不 reload**，线上仍是旧配置。

### 前端

切回上一版前端代码，重跑 `.\release-frontend.ps1`。生产每次覆盖 `:latest`，**没有 tag 回滚机制**；
要留旧版就在发布前手动 `docker tag nl2sql-app_frontend:latest nl2sql-app_frontend:rollback-<ts>`。

## 5. Prompt 同步

> ⚠️ **`--env` 必填**（2026-10-19 起）：不传直接失败，脚本不做默认猜测。
> 环境文件：**每个环境只读自己那一份，都不加载 `.env` 基线**——
> `--env dev` → `.env.dev`，`--env prod` → `.env.prod`。解析出的 `LANGFUSE_BASE_URL`
> 主机还必须与所选环境一致（`dev`→`192.168.25.34`，`prod`→`192.168.25.64`），
> 否则同样失败——防止「以为推 dev、实际推生产」。

### 同步主/子系统 prompt

```powershell
# 同步所有默认 prompt（main_system_prompt + nl2sql_system_prompt）
D:\code_work_space\llm\nl2sql\.venv\Scripts\python.exe -m agent.prompt.sync_prompts --env dev  --all
D:\code_work_space\llm\nl2sql\.venv\Scripts\python.exe -m agent.prompt.sync_prompts --env prod --all

# 容器内（env_file 已注入目标环境凭据，同样必须带 --env）
# dev 34：docker exec nl2sql-app-langgraph-api-1 env PYTHONPATH=/app/src python /app/src/agent/prompt/sync_prompts.py --env dev --all
# prod 64：在 64 的 langgraph-api 容器内执行同一命令，--env prod

# 只同步某一个
D:\code_work_space\llm\nl2sql\.venv\Scripts\python.exe -m agent.prompt.sync_prompts --env dev --name main_system_prompt --file src/agent/prompt/MAIN_AGENT_PROMPT.md

D:\code_work_space\llm\nl2sql\.venv\Scripts\python.exe -m agent.prompt.sync_prompts --env prod --name nl2sql_system_prompt --file src/agent/prompt/NL2SQL_SYSTEM_PROMPT.md
```

### 同步全部 skill 到 Langfuse

```powershell
D:\code_work_space\llm\nl2sql\.venv\Scripts\python.exe -m agent.prompt.sync_prompts --env dev  --skills
D:\code_work_space\llm\nl2sql\.venv\Scripts\python.exe -m agent.prompt.sync_prompts --env prod --skills
```

把 `shared_skills_dir` 下每个 SKILL.md 同步为 Langfuse prompt `skill/{group}/{name}`。新增 skill 后跑一次，消除 `Prompt not found during refresh` 警告。

> skill 的**运行时内容仍从磁盘读**（`<AGENT_DATA_ROOT>/shared/skills`），Langfuse 那份只用于
> trace `metadata.skills` 的版本标注（`source=langfuse|local`）——推失败不影响功能，只影响版本回溯。
>
> ⚠️ `.env.dev` 里 `AGENT_DATA_ROOT=/app/data`（容器路径）。在 Windows 本机跑 `--env dev --skills`
> 会扫不到技能（报「未扫描到 SKILL.md」）；本机推 skill 需先在 shell 里覆盖
> `AGENT_DATA_ROOT=D:\nl2sql_data`，或在 dev 34 容器内执行。

## 6. 验证

### ① 发版脚本自带的采样断言（看结尾那几行）

| 看什么 | 期望 |
|---|---|
| `POLL_NON200` | `0`（覆盖两次切流 + A 的重建 + 两次排空；原始采样 `/tmp/nl2sql_bg_poll.log`） |
| `排空确认：A=` | `yes`。出现 **`stale`** = 切流之后旧色 A 又领到 run（残余竞态被观测到），查 A 的日志定位是哪一条 |
| 两色日志 | `database is locked` 各 0 条（日志另存在 `/tmp/nl2sql_last_langgraph-api*.log`） |

> 只看**第 8 步**的 A。第 11 步停 B 时两色已是同一份镜像，B 领到 run 也无害。

### ② 手工冒烟（服务器上跑）

```bash
# 后端直连 + 经 nginx（200 与 401 都算「通」：401=需登录，说明请求到得了应用；502=上游没解析到，404=路由没挂）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:2026/ok        # 200
for p in / /ok /api/db-configs /api/mcp/status; do \
  printf "%-18s -> " "$p"; curl -s -o /dev/null -w "%{http_code}\n" "http://127.0.0.1:8080$p"; done

# 稳态：只剩 A 一个色、流量在 A
docker ps -a | grep langgraph-api
docker exec nl2sql-app_nginx_1 grep -n backend_up /etc/nginx/nginx.conf

# 平台库计数（发版前后应一致）
docker exec nl2sql-app_postgres_1 psql -U nl2sql -d nl2sql_platform -c \
  "select (select count(*) from thread) as thread, (select count(*) from schema_migrations) as migrations;"

# 预检结论与工具数（改了 MCP / 语义库时必看）
docker logs nl2sql-app_langgraph-api_1 2>&1 | grep -E "预检通过|预检失败" | tail -4
```

> 64 长期处于**降级档**（`MCP_ALLOW_DEGRADED=1` + `wrenai_chinook` 连不上）：A 自己的日志里
> 本来就常驻「预检失败 / 降级启动」。**别拿它当回归判据** —— 判据是「B 不比 A 差」。

## 7. 改了 `docker/nginx.conf` 怎么上

```bash
bash docs/prod环境/apply-nginx-request-id-patch.sh
```

* `docker/nginx.conf` **不在发版包里**（tar 排除 `docker/`），改了必须手工跑这一条；发版不会带过去。
* 它做的是「md5 判差异 → 备份 → 就地写**同一 inode** → `nginx -t`（失败自动回滚）→ reload」，
  同步的是**整份文件**（名字里的 "request-id" 是历史）。
* 换个容器**不需要**这条（上游是请求期解析，≤10s 自愈）；只有**配置本身变了**才用。
* ⚠️ 变量形式的 `proxy_pass` 不做启动期解析 ⇒ **上游主机名写错 `nginx -t` 也照样通过**，必须真打一次请求。
