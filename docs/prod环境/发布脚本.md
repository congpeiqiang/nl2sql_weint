**脚本统一放在本目录**（2026-09-22 合并 `scripts/` 与 `docs/prod环境/` 两份，与 `docs/dev环境/` 对称）：

| 文件 | 作用 | 用法 |
|------|------|------|
| [release-backend.ps1](release-backend.ps1) | 后端改代码发布 | `.\release-backend.ps1` |
| [release-frontend.ps1](release-frontend.ps1) | 前端改动发布 | `.\release-frontend.ps1 [-SkipBuild]` |
| [apply-nginx-request-id-patch.sh](apply-nginx-request-id-patch.sh) | **把仓库的 `docker/nginx.conf` 整份同步到线上** | `bash docs/prod环境/apply-nginx-request-id-patch.sh` |

> ⚠️ **`docker/nginx.conf` 不在发布包里**（发布 tar 排除 `docker/`）—— 改了它**必须**用上面第三个脚本手工应用，发版不会带过去。它是 `md5 判差异 → 备份 → 就地写同一 inode → nginx -t（失败自动回滚）→ reload`；名字里的 "request-id" 是历史（P2-2 是它最早服务的补丁），**别当成只打那几行**。

## 0. 总览：两种场景

| 场景 | 何时用 | 代价 | 脚本 |
|------|--------|------|------|
| **A. 只改后端代码** | 日常 90%（改 prompt / 中间件 / API / 工具） | **蓝绿：用户侧 0 个 5xx** | [release-backend-bluegreen.ps1](release-backend-bluegreen.ps1) → §2 |
| **A'. 同一件事的老路** | 破坏性迁移 / 需要停机窗口 / 蓝绿本身出问题 | ≈29s 全量 502（有 run 时更长） | [release-backend.ps1](release-backend.ps1) → §2 |
| **B. 改前端** | UI 有改动 | 本机构建 + 分片上传 + 重建镜像 + 只重启 frontend（**不碰 nginx**） | §3 |
| **C. 改边缘配置** | 改 `docker/nginx.conf` | 手工同步 + reload（**不中断**，不动任何容器） | §5「上游解析」 |

**发版会中断多少（已量化，别再靠想象）**：老路（`release-backend.ps1`）2026-10-05 实测一次后端发版
造成 **≈29 秒全量 502**。那 29 秒的构成很关键 —— `stop_grace_period=240s` 的**排空**与 ~26s 的
**冷启是串行的**，当时没有在跑的 run 才这么快；**有 run 时窗口 = 排空（最多 240s）+ 冷启**。

2026-10-08 起，后端发版走**蓝绿**（阶段 2，已具备）：起空闲第二色 → 提升 → **切 nginx 一行 + reload**
→ 排空并停旧色。用户侧 **0 个 5xx**（含 503）。设计要点与验收清单见
**[蓝绿发布_阶段2发版手册.md](蓝绿发布_阶段2发版手册.md)**。

> ⚠️ **关键时序**：蓝绿是「**先切流、再排空**」，与老脚本相反。原因是老顺序的排空期新提交拿到
> **503** —— 503 也是 5xx，用户照样看得见；先切流之后旧色的排空对任何人不可见。

> ⚠️ **本轮边界**：零中断**只覆盖后端/API 链路**；前端发版仍是 `stop/rm/up frontend`，
> `location /` 有几秒 502。

**与 dev 的核心差异**（先看懂再动手）：

1. **生产没有 bind 挂载 src/**：后端代码烤进 Docker 镜像，每次发布都要 `docker-compose build` 重建镜像（dev 只需重启容器）。
2. **VPN 链路不稳**：上传走分片 + 重试（0.5MB/片 × N 片，每片独立重试 8 次），不是一次性 scp 整包。
3. **docker-compose v1 两条**：重建容器需 stop/rm/up 三步（v1 的 `up -d` 改配置会报 `ContainerConfig KeyError`）；且 **`up -d` 必须带 `--no-deps`**，否则会连带收敛 `depends_on` 的依赖（详见 §7 坑 2）。
4. **tar 解压前必须先清旧代码**：tar 不会删除仓库里已删/已改名的文件，旧文件会一直躺在容器里烤进镜像。2026-09-20 事故正是这个原因。

## 2. 场景 A：后端代码发布

> **首选**：**[release-backend-bluegreen.ps1](release-backend-bluegreen.ps1)**（蓝绿 / 真零中断）——
> 用法与验收见 **[蓝绿发布_阶段2发版手册.md](蓝绿发布_阶段2发版手册.md)**。本节描述的是**老路**，
> 它**仍然可用**（破坏性迁移、需要停机窗口、或蓝绿本身出问题时的退路），下面保留原文。

> 脚本文件：**[release-backend.ps1](release-backend.ps1)**

五步流程：

| 步 | 动作 | 要点 |
|---|------|------|
| 1 | 本地打包（gzip 压缩） | 排除清单见下 |
| 2 | 分片上传到服务器 | 0.5MB/片 × N 片，每片独立重试 8 次 |
| 3 | 服务器拼接 + 解压 + 重建镜像 | **先清旧 src/ 再解压**（防 2026-09-20 事故重演） |
| 4 | **先协作式排空**，再三步重启 | 容器内 `scripts/ops_drain.py` → `docker-compose stop && rm -f && up -d --no-deps`（v1 必需三步，`--no-deps` 见坑 2） |
| 5 | **经 nginx 轮询** `/ok` 到 200 + 量窗口 | 探 `http://127.0.0.1:8080/ok`（不是直连 2026 再盲等 75s）+ 预检日志 |

> **为什么第 4 步先排空再 `stop`**：`stop` 会**先关监听**，那一刻新请求是 `connection refused`（nginx 报 502），之后才轮到信号式排空。反过来先排空，进程还在正常接连接 —— 新 run 能被**明确拒绝**（503 + `Retry-After: 30`，前端文案「服务正在停机排空（发版中）…」），在跑的 run 也能收尾。⇒ **长时间中断由 502 变 503**，硬中断只剩冷启。
> 排空是 **best-effort**：旧镜像没这脚本 / 端点不可达 / 预算（`--budget 180` < compose `stop_grace_period=240s`）用尽，都**只告警不拦发版**（`stop` 的信号式排空兜底）。
> **第 5 步探的是「经 nginx」而不是直连 2026**：一次探针同时证明「冷启完成」和「nginx 已解析到**新容器**」—— 后者正是变量 `proxy_pass` 的端到端验收（见 §5「上游解析」）。

| ~~`src/agent/workspace_manager/workspaces.json`~~ | ~~运行时注册表~~ —— **2026-09-25 注册表机制已删除**，文件与排除项一起作废 |

### 第 3 步的旧代码清理（2026-09-20 事故教训）

脚本在解压前执行：
```bash
rm -rf /tmp/nl2sql_ws_keep && mkdir -p /tmp/nl2sql_ws_keep
if [ -d backend/src/agent/workspace ]; then mv backend/src/agent/workspace /tmp/nl2sql_ws_keep/ ; fi
rm -rf backend/src
tar -xzf backend_release.tar.gz -C backend
if [ -d /tmp/nl2sql_ws_keep/workspace ]; then mv /tmp/nl2sql_ws_keep/workspace backend/src/agent/workspace ; fi
rm -rf /tmp/nl2sql_ws_keep
```

逻辑：先移出 `workspace`（运行时数据） → 清空整个 `src/` → 解压新代码 → 放回 `workspace`。两点边界：
- `scripts/` 不动：服务器上可能有仓库里没有的运维脚本（如 cron 调用的）。
- `workspace` 是 AGENT_DATA_ROOT 未配置时的回退目录（默认工作区 + db_config.json + feedback SQLite），tar 本来就排除它。

### 分片上传

VPN 链路不稳，整包 scp 容易中途断开且无重试。分片策略：
- 0.5MB/片（可用 `-ChunkMB` 调，下限 0.0625）
- 两位补零命名（`part00`、`part01`…），`cat part*` 字典序 = 数字序
- 每片独立重试 8 次（`-MaxRetry`），失败时提示调小 ChunkMB

## 3. 场景 B：前端发布

> 脚本文件：**[release-frontend.ps1](release-frontend.ps1)**

六步流程：

| 步 | 动作 | 要点 |
|---|------|------|
| 1 | 本地 Docker 构建 | **必须在本地**：UI 源码的 DLP 密文只有这台机器解得了 |
| 2 | 提取并验证 BUILD_ID | 后续与服务器对比确保一致 |
| 3 | 打包产物（tar） | `.next` + `public` + `Dockerfile` + `next.config.ts` |
| 4 | 分片上传到服务器 | 1MB/片（前端产物比后端大） |
| 5 | 拼接 + 解压 + 重建镜像 + **只重启 frontend** | `docker-compose build frontend`；`stop/rm/up` **只对 frontend** —— **不碰 nginx**；打印产物 `BUILD_ID` |
| 6 | 验证 | 轮询经 nginx 的 `/` 到 200；再打 `/ok`（期望 200）与 `/api/deployment-info`（期望 200/401）证明后端链路照旧 |

> **第 5 步为什么不再 `up -d frontend nginx`**：nginx 已经不在启动期缓存上游 IP 了，新前端容器的 IP 它自己在 ≤10s 内发现，**不需要 reload 或重建**。旧写法在配置没变时 compose 只打 `up-to-date`、看似无害，但**一旦真被重建就是白白多引入一次 nginx 停机**。
> **第 6 步为什么要两发探针**：本次 nginx 改动**两个 location 都动了** —— `/ok` 命中的是 `location ~ ^/(threads|runs|…)`，覆盖不到 `location /api/`，所以补一发 `/api/deployment-info`（它 `require_user`，无 cookie 必然 **401**，与 200 一样都算「经 nginx 到得了应用」；502=上游没解析到、404=路由没挂）。

### DLP 加密与本地构建

前端源码含 DLP 加密文件（`config.ts` / `types.ts` / `useChat.ts` / `modelConfigs.ts` 等），只有本机的 DLP agent 能解密。构建命令：

```powershell
cd D:\code_work_space\llm\huice\008\harness-deep-agents-ui
docker build -t nl2sql-app_frontend:latest -f Dockerfile .
```

构建失败时 `yarn.lock` 可能被 DLP 解密过程修改，脚本会自动 `git checkout -- yarn.lock` 还原。

### 明文 next.config.ts

UI 源码里的 `next.config.ts` 是 DLP 密文，不能直接用于构建。生产服务器上需要一份**明文**版本（只含构建期设置），脚本会一起传上去。

### BUILD_ID 验证

构建产物里有 `.next/BUILD_ID`，是 Next.js 每次构建的唯一标识。脚本在服务器重启后提取容器的 BUILD_ID 并与本地对比，不一致说明镜像没替换或旧容器未清理。

### 上游解析：换容器为什么不需要 reload（2026-10-05 起）

`docker/nginx.conf` 里**没有 `upstream` 块了** —— 上游是 `resolver 127.0.0.11 valid=10s ipv6=off`
+ **变量形式** `proxy_pass http://$backend_up;`（`set` 在 `server` 块）。差别：

| | 旧（`upstream { server langgraph-api:2026; }`） | 新（`resolver` + 变量 `proxy_pass`） |
|---|---|---|
| 解析时机 | **启动期一次**，IP 永久缓存 | **请求期**，`valid=10s` 到期重查 |
| 容器换 IP | 一直打旧 IP ⇒ **永久 502 直到 reload** | ≤10s 自愈 |
| 后端不在时 | `host not found in upstream` ⇒ **nginx 起不来** | nginx 照常启动 |
| `nginx -t` 能查出主机名写错吗 | 能 | **不能**（见下） |

**改过 `docker/nginx.conf` 后的验收（必须真打请求，别只看 `nginx -t`）**：

```bash
# 1) 应用（md5 判差异 → 备份 → 就地写同一 inode → nginx -t → reload；reload 不打断已建连接）
bash docs/prod环境/apply-nginx-request-id-patch.sh
# 2) 生效的不是"文件"，是**请求期解析**：重建一个下游容器，看 IP 变了没有 + 有没有自己恢复
#    （以下 4 条在服务器上跑：ssh weint@192.168.25.64）
cd /home/weint/apps/nl2sql/nl2sql-app
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' nl2sql-app_frontend_1   # 记下 IP
docker inspect -f '{{.State.StartedAt}}' nl2sql-app_nginx_1                                            # 记下 nginx 启动时刻
docker-compose stop frontend && docker-compose rm -f frontend && docker-compose up -d --no-deps frontend
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' nl2sql-app_frontend_1    # IP 应已变（没变= Docker 复用了同一 IP，这步证明不了什么，再来一次）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/                                        # 应 200，且**全程没跑过 nginx -s reload**
docker inspect -f '{{.State.StartedAt}}' nl2sql-app_nginx_1                                            # 应与上面一致 ⇒ nginx 没被重启过
# 3) 负对照（一次就够，证明"代价"真的存在）：把上游改成不存在的名字，nginx -t **照样通过**，
#    请求期才 502 + error_log 里 "could not be resolved"。改完立刻还原。
```

> ⚠️ **变量形式 `proxy_pass` 不做启动期解析** ⇒ 主机名/端口写错时 `nginx -t` **也通过**，只有请求期 502 + error_log 会暴露。**改完必须打一次真请求**（上面 2）/ 3)）。
> ⚠️ 本次**没有**加 `upstream { keepalive N; }`：连接池要挂在 `upstream` 块上，而变量形式正是为了躲开块级缓存；每请求新解析最简单，对本仓的流量级别没有代价。
> ⚠️ `resolver` 的正面缓存是**每 worker 一份**；**失败查找不做负缓存**（NXDOMAIN 会删名字节点）⇒ 新容器一注册即可用，残余窗口只有那 ≤10s（且仅在重启间隔短于 10s 时可能被看见）。

**真问答冒烟**（改模型配置、评估链路、子 agent 后建议跑）：

```bash
API=http://127.0.0.1:2026
TID=$(curl -s -X POST $API/threads -H 'Content-Type: application/json' -d '{}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["thread_id"])')
curl -s -X POST "$API/threads/$TID/runs" -H 'Content-Type: application/json' \
  -d '{"assistant_id":"nl2sql_agent","input":{"messages":[{"role":"user","content":"Chinook 库里一共有多少位客户？"}]},"config":{"configurable":{"db_name":"Chinook_AutoIncrement"}}}'
# 然后轮询 run 状态，最后看 GET /threads/$TID/state
```

## 6. 红线与坑（都是踩过的）

### 通用

1. **tar 解压不删已删文件** → 替换代码前必须先清空目标目录（2026-09-20 事故根因：仓库里删了一个文件，但服务器 tar 解压后旧文件仍在，导致 import 指向已删文件，白排查一轮）。脚本已处理。
2. **docker-compose v1 重建容器需三步**：`stop → rm -f → up -d --no-deps`。直接 `up -d` 改配置会报 `ContainerConfig KeyError`；**漏 `--no-deps` 更阴**——它会把 `depends_on` 的依赖一并收敛，撞同一个 KeyError 的却是**依赖**（2026-10-05：裸 `up -d langgraph-api` 把 postgres 打死、停摆 55 分钟）。依赖的 config-hash 与 compose 文件不一致（历史遗留带出来的）就会触发，**与你这次改没改它无关**。
3. **模型是导入时解析的**：模型库为空时启动，子 agent 会落到框架默认的 Anthropic 模型，run 会以「error 字段为空」的方式失败。**先配模型、再重启后端**。判断依据是启动日志里有没有 `[model] provider=... model=...`。
4. **前端源码含 DLP 加密**：只能在本机解密 + 构建，再传产物到服务器。服务器上不能直接 build。
5. ~~**nginx 缓存上游 IP** → 容器重建后 502 就 `docker-compose restart nginx`~~ —— **2026-10-05 起作废**。上游已改成 `resolver` + **变量** `proxy_pass`（请求期解析），换容器后 ≤10s 自愈，**不需要 reload、更不需要重建 nginx**（发版脚本已明确不碰它）。原文说的正是旧的启动期解析 —— 那才是「永久 502 直到 reload」的来源。见 §5「上游解析」。
6. ~~**报告目录由 nginx 静态服务**（`/report/`）~~ —— **该 location 已删除（P0-3）**：它 `alias` 到 `workspace/report/` 并 `autoindex on`，**绕过后端认证** —— 未登录即可列出/下载全站报告；前端也从未用过它。报告预览/下载走 `GET /api/reports/{name}`（前端把 `/workspace/report/xxx.md` 映射到该 API）。**别再把 `location /report/` 加回来。**

### VPN 链路

7. **分片上传**：VPN 不稳，整包 scp 容易中途断。脚本走分片 + 重试，链路特别差时把 `-ChunkMB` 调更小。
8. **ssh keepalive**：脚本里所有 ssh/scp 都带 `-o ServerAliveInterval=20 -o ServerAliveCountMax=6`，防止链路空闲被判死。

## 7. `.ps1` 文件必须带 UTF-8 BOM

Windows PowerShell 5.1 对没有 BOM 的 `.ps1` 按 GBK 解码：中文注释的字节会被"吃掉"后面一个字符，**连行尾换行都可能被吞**，于是下一行代码变成注释的一部分 —— 症状是某个变量莫名是空值。

检查：`head -c 3 文件 | od -An -tx1` 应为 `ef bb bf`。

加 BOM 最快的一条命令：
```bash
printf '\xef\xbb\xbf' > f2 && cat f >> f2 && mv f2 f
```

这条规则对临时小工具一样成立：代码是纯 ASCII，但字符串里带着中文目录名，没 BOM → 中文路径被 GBK 解码后吃掉后面的引号 → 静默失败。

### 改完 `.ps1` 必须过解析闸（比 BOM 更容易踩）

PS 双引号串里 `"` 的转义符是**反引号**；写成 `\"` 会**提前闭合字符串**。2026-09-26 这条坑让 `release-backend.ps1` 第 5 步**整段没跑过**，而脚本照样打印「发布完成」—— 因为它把后半段当成了字符串的一部分，语法坏掉的那一段永远执行不到。**语法错误只有解析器看得见**，所以改完必跑：

```bash
cd docs/prod环境 && powershell.exe -NoProfile -Command \
  '$e=$null; [void][System.Management.Automation.Language.Parser]::ParseFile((Resolve-Path ".\release-backend.ps1").Path,[ref]$null,[ref]$e); if($e){$e|%{$_.Message}} else {"PARSE_OK"}'
```

本目录的这两个动作（解析闸 + BOM）连同本次上游解析/排空的静态断言，已固化成离线套件：

```bash
PYTHONIOENCODING=utf-8 uv run --no-sync python scripts/verify_release_zero_downtime.py
```

它验五段：① `nginx.conf` 上游是请求期解析（无 `upstream` 块、`resolver` 在 `http`、三个 `proxy_pass` 全是变量形式、`proxy_redirect off`；附负对照）② 后端脚本「排空在 `stop` 之前」+ 经 nginx 探针 + 不碰 nginx + 三步重启带 `--no-deps` ③ 前端脚本「只 `up -d --no-deps frontend`」+ 两发经 nginx 探针 ④ 两个 `.ps1` 过解析闸 ⑤ 两个 `.ps1` 带 BOM（共 43 项）。**改脚本/改 nginx.conf 后先跑它。**
