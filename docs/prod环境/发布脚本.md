# 生产环境（192.168.25.64）— 发布脚本与更新手册

> 适用：生产环境 192.168.25.64 | 建立 2026-09-21
> dev 发布脚本在同仓 `docs/dev环境/`（面向 25.34），**两者不要混用**。
> 账号地址见同目录 [账号密码汇总.md](账号密码汇总.md)。

**可直接运行的脚本已落在同目录**：

| 文件 | 作用 | 用法 |
|------|------|------|
| [prod-release-backend.ps1](prod-release-backend.ps1) | 后端改代码发布 | `.\prod-release-backend.ps1` |
| [prod-release-frontend.ps1](prod-release-frontend.ps1) | 前端改动发布 | `.\prod-release-frontend.ps1` |

## 0. 总览：两种场景

| 场景 | 何时用 | 代价 | 脚本 |
|------|--------|------|------|
| **A. 只改后端代码** | 日常 90%（改 prompt / 中间件 / API / 工具） | 分片上传 + 重建镜像 + 三步重启 | §2 |
| **B. 改前端** | UI 有改动 | 本机构建 + 分片上传 + 重建镜像 + 三步重启 | §3 |

**与 dev 的核心差异**（先看懂再动手）：

1. **生产没有 bind 挂载 src/**：后端代码烤进 Docker 镜像，每次发布都要 `docker-compose build` 重建镜像（dev 只需重启容器）。
2. **VPN 链路不稳**：上传走分片 + 重试（0.5MB/片 × N 片，每片独立重试 8 次），不是一次性 scp 整包。
3. **docker-compose v1**：重建容器需 stop/rm/up 三步（v1 的 `up -d` 改配置会报 `ContainerConfig KeyError`）。
4. **tar 解压前必须先清旧代码**：tar 不会删除仓库里已删/已改名的文件，旧文件会一直躺在容器里烤进镜像。2026-09-20 事故正是这个原因。

## 1. 前置：SSH 免密

本机 `~/.ssh/id_ed25519` 已配好到 64 的免密（实测三把私钥里只有这把能登 64，别删）。脚本里所有 ssh/scp 都带 keepalive 和 ConnectTimeout，不需要额外配置。

> ⚠️ **提示符里没有环境名**，而且 dev 与生产**端口号完全相同**（8080 / 2026 / 3010）。跑命令前先 `hostname` 或 `ip a` 确认落在哪台机器上。

## 2. 场景 A：后端代码发布

> 脚本文件：**[prod-release-backend.ps1](prod-release-backend.ps1)**

五步流程：

| 步 | 动作 | 要点 |
|---|------|------|
| 1 | 本地打包（gzip 压缩） | 排除清单见下 |
| 2 | 分片上传到服务器 | 0.5MB/片 × N 片，每片独立重试 8 次 |
| 3 | 服务器拼接 + 解压 + 重建镜像 | **先清旧 src/ 再解压**（防 2026-09-20 事故重演） |
| 4 | 三步重启 | `docker-compose stop && rm -f && up -d`（v1 必需） |
| 5 | 等待 75s + 验证 | `/ok` + 预检日志 |

### 排除清单

| 排除项 | 原因 |
|--------|------|
| `.venv` / `node_modules` | 依赖在服务器镜像内，不传 |
| `.env` / `.env.prod` | 生产环境变量只在服务器，不传本地副本 |
| `src/agent/workspace` | 运行时数据目录（AGENT_DATA_ROOT 回退） |
| `src/agent/workspace-temp` | 运行时临时数据（db_config.json / eval / process_data / 临时查询结果） |
| `src/agent/workspace_manager/workspaces.json` | 运行时注册表（dev 机条目会覆盖生产） |
| `src/agent/shared/model_config.json` | 运行时模型配置（容器读 AGENT_DATA_ROOT 那份） |
| `__pycache__` / `*.pyc` | 编译缓存，推上去没意义 |

### 第 3 步的旧代码清理（2026-09-20 事故教训）

脚本在解压前执行：
```bash
rm -rf /tmp/nl2sql_ws_keep && mkdir -p /tmp/nl2sql_ws_keep
if [ -d backend/src/agent/workspace ]; then mv backend/src/agent/workspace /tmp/nl2sql_ws_keep/ ; fi
rm -rf backend/src
tar -xzf backend_release.tar.gz -C backend
if [ -d /tmp/nl2sql_ws_keep/workspace ]; then mv /tmp/nl2sql_ws_keep/workspace backend/src/agent/workspace ; fi
rm -rf /tmp/nl2sql_ws_keep
```

逻辑：先移出 `workspace`（运行时数据） → 清空整个 `src/` → 解压新代码 → 放回 `workspace`。两点边界：
- `scripts/` 不动：服务器上可能有仓库里没有的运维脚本（如 cron 调用的）。
- `workspace` 是 AGENT_DATA_ROOT 未配置时的回退目录（默认工作区 + db_config.json + feedback SQLite），tar 本来就排除它。

### 分片上传

VPN 链路不稳，整包 scp 容易中途断开且无重试。分片策略：
- 0.5MB/片（可用 `-ChunkMB` 调，下限 0.0625）
- 两位补零命名（`part00`、`part01`…），`cat part*` 字典序 = 数字序
- 每片独立重试 8 次（`-MaxRetry`），失败时提示调小 ChunkMB

## 3. 场景 B：前端发布

> 脚本文件：**[prod-release-frontend.ps1](prod-release-frontend.ps1)**

六步流程：

| 步 | 动作 | 要点 |
|---|------|------|
| 1 | 本地 Docker 构建 | **必须在本地**：UI 源码的 DLP 密文只有这台机器解得了 |
| 2 | 提取并验证 BUILD_ID | 后续与服务器对比确保一致 |
| 3 | 打包产物（tar） | `.next` + `public` + `Dockerfile` + `next.config.ts` |
| 4 | 分片上传到服务器 | 1MB/片（前端产物比后端大） |
| 5 | 服务器拼接 + 解压 + 重建镜像 | `docker-compose build frontend` |
| 6 | 三步重启 + 验证 BUILD_ID | 对比本地与服务器 BUILD_ID 一致 |

### DLP 加密与本地构建

前端源码含 DLP 加密文件（`config.ts` / `types.ts` / `useChat.ts` / `modelConfigs.ts` 等），只有本机的 DLP agent 能解密。构建命令：

```powershell
cd D:\code_work_space\llm\huice\008\harness-deep-agents-ui
docker build -t nl2sql-app_frontend:latest -f Dockerfile .
```

构建失败时 `yarn.lock` 可能被 DLP 解密过程修改，脚本会自动 `git checkout -- yarn.lock` 还原。

### 明文 next.config.ts

UI 源码里的 `next.config.ts` 是 DLP 密文，不能直接用于构建。生产服务器上需要一份**明文**版本（只含构建期设置），脚本会一起传上去。

### BUILD_ID 验证

构建产物里有 `.next/BUILD_ID`，是 Next.js 每次构建的唯一标识。脚本在服务器重启后提取容器的 BUILD_ID 并与本地对比，不一致说明镜像没替换或旧容器未清理。

## 6. 红线与坑（都是踩过的）

### 通用

1. **tar 解压不删已删文件** → 替换代码前必须先清空目标目录（2026-09-20 事故根因：仓库里删了一个文件，但服务器 tar 解压后旧文件仍在，导致 import 指向已删文件，白排查一轮）。脚本已处理。
2. **docker-compose v1 重建容器需三步**：`stop → rm -f → up -d`。直接 `up -d` 改配置会报 `ContainerConfig KeyError`。
3. **模型是导入时解析的**：模型库为空时启动，子 agent 会落到框架默认的 Anthropic 模型，run 会以「error 字段为空」的方式失败。**先配模型、再重启后端**。判断依据是启动日志里有没有 `[model] provider=... model=...`。
4. **前端源码含 DLP 加密**：只能在本机解密 + 构建，再传产物到服务器。服务器上不能直接 build。
5. **nginx 缓存上游 IP** → 后端/前端容器重建后如果 502，需 `docker-compose restart nginx`。
6. **报告目录**：`http://192.168.25.64:8080/report/` 由 nginx 直接静态服务。聊天里 agent 回显的路径是 `D:/workspace1/report/xxx.html`（开发机路径），替换为 `http://192.168.25.64:8080/report/` 即可访问。

### VPN 链路

7. **分片上传**：VPN 不稳，整包 scp 容易中途断。脚本走分片 + 重试，链路特别差时把 `-ChunkMB` 调更小。
8. **ssh keepalive**：脚本里所有 ssh/scp 都带 `-o ServerAliveInterval=20 -o ServerAliveCountMax=6`，防止链路空闲被判死。

### 数据安全

9. **排除 model_config.json**：运行时模型配置在容器里读 AGENT_DATA_ROOT 那份，不传本地副本。
10. **排除 workspaces.json**：运行时工作区注册表，传上去会覆盖服务器上的注册表。
11. **排除 .env / .env.prod**：生产环境变量只在服务器，不传本地副本。

### 与 dev 隔离

12. **生产脚本面向 64，dev 脚本面向 34**，不要混用。端口号相同（8080/2026/3010），SSH 时先确认机器。
13. **生产用 `docker-compose` v1，dev 用 `docker compose` v2**，语法不同。

## 7. `.ps1` 文件必须带 UTF-8 BOM

Windows PowerShell 5.1 对没有 BOM 的 `.ps1` 按 GBK 解码：中文注释的字节会被"吃掉"后面一个字符，**连行尾换行都可能被吞**，于是下一行代码变成注释的一部分 —— 症状是某个变量莫名是空值。

检查：`head -c 3 文件 | od -An -tx1` 应为 `ef bb bf`。

加 BOM 最快的一条命令：
```bash
printf '\xef\xbb\xbf' > f2 && cat f >> f2 && mv f2 f
```

这条规则对临时小工具一样成立：代码是纯 ASCII，但字符串里带着中文目录名，没 BOM → 中文路径被 GBK 解码后吃掉后面的引号 → 静默失败。
