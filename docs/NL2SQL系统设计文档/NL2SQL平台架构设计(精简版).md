# DataAgent 智能数据查询平台 — 架构设计文档

> **版本**: v13 | **日期**: 2026-10

---

## 1. 产品概述

DataAgent 是一个**基于 SQL-of-Thought 的多智能体自然语言转 SQL 平台**，面向企业数据分析场景。

用户以自然语言提问，系统自动完成：**语义理解 → SQL 生成 → 查询执行 → 可视化图表 → 分析报告**的全链路。

### 核心理念

**SQL-of-Thought**: 将 SQL 生成拆解为多个认知步骤（知识加载 → 模式链接 → 子问题分解 → 查询规划 → SQL 生成 → 性能优化 → 纠错），每一步由专门的 Prompt 驱动，通过中间件链串联为完整流水线。

### 技术栈总览

| 层次 | 技术选型 |
|------|---------|
| 前端 | Next.js (SSR), ECharts |
| 反向代理 | Nginx（支持蓝绿部署） |
| API 框架 | LangGraph API + 自定义路由层 |
| Agent 框架 | deepagents（基于 LangGraph） |
| 语义层 | WrenAI（语义模型 + MCP 工具服务） |
| 大模型 | 支持多种 LLM（DeepSeek、Qwen 等） |
| 混合检索 | LanceDB（向量 + 全文检索）, bge-m3 嵌入 |
| 工具协议 | MCP (Model Context Protocol) |
| 数据库 | MySQL / PostgreSQL / ClickHouse / SQLite |
| 可观测性 | Langfuse + LangSmith |
| 部署 | Docker Compose, 蓝绿部署 |

## 2. 整体架构

### 2.1 架构分层

```
┌─────────────────────────────────────────────────────────────┐
│                     前端层 (Next.js)                          │
│   会话管理 │ 图表渲染 │ 语义库管理 │ 标注/评估 │ 模型配置    │
├─────────────────────────────────────────────────────────────┤
│                  反向代理层 (Nginx)                            │
│   蓝绿切流 │ SSE 长连接 │ 请求 ID 传播 │ 缓存策略           │
├─────────────────────────────────────────────────────────────┤
│              API 网关层 (LangGraph API)                       │
│   路由模块 │ 中间件栈 │ 认证/授权 │ 优雅停机                │
├─────────────────────────────────────────────────────────────┤
│                     Agent 编排层                              │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐   │
│  │  主 Agent     │───▶│ NL2SQL 子Agent│───▶│ MCP 工具集群  │   │
│  │  编排 + 聚合  │    │ SQL 生成      │    │ 语义/直连/图表│   │
│  └──────────────┘    └──────────────┘    └──────────────┘   │
├─────────────────────────────────────────────────────────────┤
│                     数据与存储层                               │
│  PostgreSQL (会话) │ Redis (消息) │ SQLite (授权) │ LanceDB  │
│  业务数据库 (MySQL / PostgreSQL / ClickHouse)                 │
├─────────────────────────────────────────────────────────────┤
│                     可观测性层                                 │
│  Langfuse (trace/eval) │ LangSmith │ 请求日志 │ Prometheus   │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 请求数据流

```
用户提问 → Nginx → API 网关 → 主 Agent (意图识别)
    → NL2SQL 子 Agent (上下文检索 → SQL 生成 → 执行)
    → 主 Agent (结果聚合 → 图表/报告)
    → SSE 流式推送 → 用户
```

## 3. Agent 系统

### 3.1 双 Agent 架构

系统采用**主 Agent + 子 Agent** 的分层架构：

```
┌─────────────────────────────────┐
│          主 Agent                │
│  职责: 编排、聚合、图表、报告     │
│  能力: 意图识别、子任务派发、     │
│       结果汇总、可视化生成        │
│  中间件: 18 层                   │
└──────────────┬──────────────────┘
               │ 异步派发
               ▼
┌─────────────────────────────────┐
│       NL2SQL 子 Agent            │
│  职责: SQL 生成与执行             │
│  能力: 知识检索、语义理解、       │
│       SQL 编写、性能优化、纠错    │
│  中间件: 22 层                   │
│  双通道: 语义层 / 直连           │
└─────────────────────────────────┘
```

### 3.2 主 Agent

- **意图识别**: 判断用户提问类型（数据查询、闲聊、操作指令）
- **子 Agent 派发**: 异步派发 NL2SQL 任务，透传数据库名、用户身份
- **结果聚合**: 汇总子 Agent 输出，生成最终回答
- **图表生成**: 调用 ECharts MCP 工具生成可视化图表
- **报告导出**: 生成结构化 Markdown 分析报告
- **归因分析**: 支持贡献度分解（"为什么涨了/跌了"）

### 3.3 NL2SQL 子 Agent

采用**双通道路由**策略：

| 通道 | 适用场景 | 流程 |
|------|---------|------|
| **语义通道** | 已建模数据库 | 语义模型 → dry_plan → 物理 SQL |
| **直连通道** | 未建模数据库 | 直接 SQL 生成 → 执行 |

**7 个 SOP Skills 驱动 SQL 生成流水线**:

| 阶段 | 职责 |
|------|------|
| 编排器 | SQL 生成全流程编排 |
| 知识检索 | 业务术语、指标定义加载 |
| 歧义澄清 | 不明确时向用户确认 |
| 指标查询 | 预定义指标专用查询 |
| SQL 编写 | 核心 SQL 生成 |
| 性能优化 | SQL 执行计划优化 |
| 记忆回写 | 新知识回写到语义库 |

## 4. 语义层 (WrenAI)

### 4.1 架构

每个已建模的数据库对应一个独立的 WrenAI 语义服务进程：

```
语义项目结构:
├── models/        数据模型（表、字段、关系）
├── cubes/         多维分析模型
├── views/         视图定义
├── knowledge/     业务知识
│   ├── glossary/    术语表
│   ├── metrics/     指标定义
│   ├── rules/       业务规则
│   ├── sql_patterns/ SQL 模式
│   └── caveats/     注意事项
└── target/mdl.json  构建产物（语义模型）
```

### 4.2 核心能力

- **语义到 SQL 翻译**: 业务术语自动映射到物理表和字段
- **知识加载**: 从 knowledge 目录加载业务规则、指标口径
- **Cube 多维分析**: 预定义的聚合分析模型，加速常见查询
- **热加载**: 新增/修改语义库无需重启服务

## 5. 混合检索层

### 5.1 架构

```
┌──────────────────────────────────────────────┐
│               混合检索层                       │
│                                               │
│  Embedder (bge-m3, 1024d)                     │
│      ↓                                        │
│  Indexer (mdl.json + knowledge/)              │
│      ↓                                        │
│  ┌────────────┐    ┌────────────────────┐     │
│  │  LanceDB   │    │  JSONL (fallback)   │     │
│  │  向量 + FTS │    │  IDF n-gram 检索    │     │
│  └─────┬──────┘    └─────────┬──────────┘     │
│        └──────────┬──────────┘                │
│                   ↓                           │
│        RRF 融合 (k=60)                        │
│        score = Σ 1/(k + rank)                 │
└──────────────────────────────────────────────┘
```

### 5.2 三种模式

| 模式 | 行为 |
|------|------|
| 关闭 | 不使用检索增强 |
| 全文 | 仅全文词汇匹配 |
| 混合 | 全文 + 向量，RRF 融合排序；嵌入超时自动降级为全文 |

### 5.3 高可用设计

- **后台预热**: 定期对嵌入服务发送心跳，避免 GPU 冷启动超时
- **自动降级**: 向量服务不可用时自动降级为全文检索
- **断路器**: 连续失败后进入冷却期，防止雪崩

## 6. MCP 工具体系

### 6.1 运行时注册表

所有工具基于 MCP 协议，支持运行时动态注册：

| 工具类别 | 说明 |
|---------|------|
| 语义层工具 | 每个语义库一组（SQL 执行、知识加载等） |
| 数据库直连工具 | 直接 SQL 查询执行 |
| 图表工具 | ECharts 可视化生成 |
| 报告工具 | Markdown 报告组装 |
| 归因分析工具 | 贡献度分解 |

### 6.2 热加载机制

- **指纹检测**: 基于工具列表哈希判断变更
- **后台重载**: 检测到变更后自动重载，无需重启
- **优雅降级**: 单个工具服务故障不影响其他工具

## 7. 中间件体系

### 7.1 三层防御模型

```
Layer 1: Prompt 引导         → 提示词层面约束模型行为
Layer 2: Soft Gates 软闸口    → 可降级的检查（检索、压缩）
Layer 3: Hard Circuit Breakers → 不可绕过的硬闸（安全、熔断）
```

### 7.2 中间件分类 (26+)

| 类别 | 代表中间件 | 职责 |
|------|-----------|------|
| **模型门控** | 配额检查、超时熔断 | 控制 LLM 调用成本与可用性 |
| **工具管理** | 动态注册、工具过滤 | 运行时工具生命周期管理 |
| **查询守卫** | 只读校验、失败熔断 | SQL 安全 + 连续失败保护 |
| **消息处理** | 结果压缩、大结果落盘 | 控制 context window 使用 |
| **上下文注入** | 关键词标记、数据库上下文 | 为模型提供当前环境信息 |
| **追踪计量** | Token 计量、Trace 记录 | 可观测性数据采集 |
| **安全** | 文件权限、产物归属 | 多用户隔离保障 |

### 7.3 关键机制

**失败熔断**: 连续工具调用失败达到阈值时自动熔断，防止无效循环消耗 Token 配额。

**查询守卫**: 强制只读查询（仅 SELECT），禁止数据变更操作。

**口径治理**: 业务指标口径必须有知识库原文佐证，防止 LLM 幻觉。

## 8. 认证与权限隔离

### 8.1 认证

- **Token 认证**: 基于 HMAC-SHA256 签名的令牌机制
- **密码存储**: PBKDF2 密钥派生，高迭代次数
- **令牌撤销**: 支持密码变更后的令牌批量失效

### 8.2 四层权限模型

```
Layer 1: 身份认证 → 令牌验证，确认用户身份
Layer 2: 数据库授权 → 用户 × 数据库 白名单
Layer 3: 会话隔离 → 用户只能访问自己创建的会话
Layer 4: 产物归属 → 报告/图表归属到创建者
```

### 8.3 安全原则

| 场景 | 策略 | 理由 |
|------|------|------|
| 写操作权限 | fail-closed | 安全底线，异常时拒绝 |
| 会话所有权 | fail-closed | 隔离是安全底线 |
| 读操作权限 | fail-open | 读异常不阻断正常业务 |
| 检索/嵌入 | fail-open | 降级不应阻断查询 |
| 可观测性 | fail-open | 追踪故障不影响业务 |

## 9. 部署架构

### 9.1 容器编排

系统通过 Docker Compose 编排以下服务：

| 服务 | 职责 |
|------|------|
| 后端 API | LangGraph 运行时 + 自定义路由 |
| PostgreSQL | 会话状态 + 平台数据（双库分离） |
| Redis | 跨实例消息发布/订阅 |
| 前端 | Next.js SSR |
| Nginx | 反向代理 + 蓝绿切流 |

### 9.2 蓝绿部署

实现**零停机发版**的蓝绿部署方案：

```
设计原则:
  1. 先切流，再排空（保证请求不丢失）
  2. A 色常驻，B 色只在切换窗口存活
  3. Nginx 请求期 DNS 解析（无需 reload 即可切流）

切流机制:
  Nginx 使用变量式 proxy_pass + Docker DNS
  → 每次请求重新解析目标容器地址
  → 发版脚本修改切换点后，新请求自动路由到新色
  → 旧色排空活跃请求后安全停机
```

### 9.3 优雅停机

- **排空机制**: 停机前先拒绝新请求，等待活跃请求完成
- **长连接保护**: SSE 超时 ≥ Nginx worker 关闭超时
- **有序停机**: 按依赖逆序关闭内部服务

## 10. 可观测性

### 10.1 全链路追踪

- **Langfuse 集成**: 每轮 LLM 调用自动生成 trace/span
- **Token 计量**: 实时统计每个会话的 Token 消耗
- **请求日志**: Nginx + 应用层双重日志，含请求 ID 关联

### 10.2 评估体系

```
反馈采集 → 自动评估 → 人工标注 → 模型优化
   ↑                                    │
   └──────────── 闭环 ─────────────────┘
```

- **用户反馈**: 点赞/点踩 → 自动收录为评估样本
- **LLM Judge**: 自动化质量评估（采样评估，节省成本）
- **标注平台**: 人工标注 + 数据集管理
- **离线实验**: 支持 A/B 测试（不同模型/语义版本对比）

## 11. 关键设计决策

### 11.1 为什么用双 Agent 而非单 Agent?

| 考量 | 说明 |
|------|------|
| 职责分离 | 编排与执行解耦，降低单次 LLM 调用的复杂度 |
| 上下文管理 | 子 Agent 独立 context，避免主 Agent 上下文膨胀 |
| 可复用性 | 子 Agent 可被多个入口复用 |
| 中间件隔离 | 不同 Agent 可配置不同的中间件链 |

### 11.2 为什么是双通道而非统一语义层?

```
语义通道:
  ✅ 业务语义理解 (术语、指标、规则)
  ✅ Cube 多维分析加速
  ❌ 需要预先建模

直连通道:
  ✅ 即开即用，零配置
  ✅ 低延迟
  ❌ 无业务语义辅助

路由策略: 有语义模型 → 语义通道; 无 → 直连通道
```

### 11.3 为什么中间件这么多层?

```
三层防御:
  Prompt 引导      → 最低成本，覆盖常见场景
  软闸口           → 可降级的增强检查
  硬熔断           → 不可绕过的安全底线

排序原则:
  成本控制 (模型门控) → 最先执行，省钱
  安全检查 (查询守卫) → 在 SQL 执行前
  消息处理 (压缩裁剪) → 在模型看到消息前
  追踪计量          → 跨全链路
```
