# 语义库表/字段级权限方案

> 状态：**方案（未实施）** —— 本文只定设计，不动代码。
> 日期：2026-10-09
> 前置：[多用户登录与用户隔离方案](多用户登录与用户隔离方案.md)（P0/P1 已发版）。
> 本方案是它的**纵向加深**：库级授权之上再收一层"库内哪些表、哪些列"。
> 硬约束不变（用户原话）：**"后端存在一份数据库和语义库，后台更新一次语义库，所有需要访问对应语义库的人都能访问最新的"**
> —— 所以语义库**永远只有一份**，本方案做的是它的**按人投影**，不是复制。

---

## 0. 结论速览

**一句话**：语义库与 MDL 仍然只有一份；每个用户看到的是它按 `field_grants` 投影出来的**可见视图**，
投影在三个地方同时生效 —— **模型可见（看不见）→ 执行侧闸（拦得住）→ 产出与旁路**。

四条要点：

1. **授权模型**：在既有库级 `grants` 旁边加一张 `field_grants`（主体 × 库 × 表 × 列 × 效果），
   **默认拒绝**（白名单语义）。库级授权仍是第一道，字段级只在**已授权库内部**再收窄。
2. **判定入口唯一**：`visible_schema(user, db_name) -> {表: {列}} | None`（`None` = 该用户该库未启用字段级，
   等价于今天行为）。所有执行点都调它，不在各处重写一遍 SQL。
3. **执行侧不手搓 SQL 解析器**：用过滤后的 MDL 在**进程内**建一个引擎跑 `dry_plan`，
   让**引擎自己**报"未知 model/column"。拒绝理由与线上同源，天然 fail-closed。
   同一套 API 本仓已在 `wren_plan.py` 用于报告的物理 SQL 复算（已与 wren CLI 逐字节对拍）。
4. **真正的防线是执行侧**：工具返回文本的裁剪（面 A）永远不可能穷尽 —— 模型可以从知识料、
   报告、历史会话里推断出隐藏对象。**"看不见"是体验与降噪，"拦得住"才是权限。**

### 1.3 MDL 与语义库的物理形态

- 语义库 = 磁盘上一个 Wren 项目目录，`db_config.json` 的 `wren_project` 指过来（一份，管理员维护）。
- `target/mdl.json` = `wren context build` 产物（`wren/context.py:816` `build_json` → `save_target`），**引擎与全部 schema 工具都读它**。
- 顶层键：`catalog / schema / models / relationships / views / cubes / dataSource / layoutVersion`。
- **今天唯一被引擎认的隐藏键是列级 `is_hidden`**（`models/<表>/metadata.yml` 的列块）→ 由 camelCase 映射表
  （`wren/context.py:121` 的 `"isHidden": "is_hidden"`）→ mdl.json 的 `isHidden`
  → `wren/mdl/cte_rewriter.py:144,196` 丢弃该列：`SELECT *` 不展开它，显式 select 它编译不过（`No field named …`）。
  `hidden:` 是**死键**（不在 camelCase 映射表里，被原样搬进 mdl.json，无人读）。
- **它是全局的**：对所有用户同时生效，不能表达"甲能看、乙不能看"。

> **这个机制正是本方案执行侧的模板**：`is_hidden` 做的是"**构建期、对所有人**"的列裁剪；
> 本方案做的是"**运行期、按人**"的同一件事（投影 MDL → 引擎自己拒绝）。所以不是另起一套，是同一个原理换个维度。

**两条既有的、但不是按用户的邻近机制**（读源码确认，写在这里免得重复造）：

- **RLAC / CLAC**：`wren/context.py:117-118` 有 `rowLevelAccessControls` / `columnLevelAccessControl` 的 snake↔camel
  映射，`wren/mdl/cte_rewriter.py:337,375,854` 把 `SELECT *` 原样透传给 **wren-core（Rust）** 去应用。
  **Python 侧没有任何执行**，Rust 侧是否真的生效**未验证**（见 §5 第 8 条）。
- **`strict_mode` SQL 策略**（`wren/policy.py:173 validate_sql_policy`）：拦数据读取型 TVF（`:387`）与
  **非 MDL 表**（`:221 _check_tables`）。**是表级、但全局、不看身份** —— 与本方案正交，且它保证
  "只能引用 MDL 里的对象"，正好是本方案执行侧投影法的前提。

## 2. 目标模型

### 2.1 授权只到（库，表，列）

```sql
-- <AGENT_DATA_ROOT>/auth/auth.sqlite，与 grants 同库同文件
field_grants(
    subject_type TEXT,     -- 'user' | 'group'（group 预留，与 grants 一致）
    subject_id   TEXT,
    db_name      TEXT,
    table_name   TEXT,     -- 支持 '*' 通配（"该库所有表"）
    column_name  TEXT,     -- 支持 '*' 通配（"该表所有列"）；整表授权写 '*'
    effect       TEXT,     -- 'allow' | 'deny'
    PRIMARY KEY (subject_type, subject_id, db_name, table_name, column_name)
)
```

**判定语义**（唯一一份，写死在 `field_grants.py`）：

1. **deny 优先**：命中任一条 `effect='deny'` ⇒ 不可见（哪怕另有 allow 覆盖）。
2. 否则看是否被某条 `effect='allow'` 覆盖：`table_name` 逐字或 `*` 命中 **且** `column_name` 逐字或 `*` 命中。
3. **未被任何 allow 覆盖 = 不可见**（白名单，fail-closed）。
4. **`level='admin'` 的库**（管理员）⇒ 不看 `field_grants`，全表全列可见。

**迁移期语义（关键，决定存量不炸）**：`visible_schema(user, db)` 返回 `None` 当且仅当
**该 (用户, 库) 没有任何一条 field_grants 行** ⇒ 完全等价于今天的库级行为（全表全列）。
一旦管理员为某人某库写了第一条字段规则，该 (人, 库) 立刻切进白名单模式 —— **灰度由管理员逐人控制**，
不是全局开关，也不用一次性给所有人补清单。

> 这条不是 fail-open 漏洞：库级授权仍然在前面拦着；它只是"还没开始按字段管"的默认。

### 2.2 可见视图：唯一判定入口

```python

def visible_schema(user: dict, db_name: str) -> dict[str, frozenset[str]] | None:
    """该用户在该库的可见 schema。None = 未启用字段级（等价今天：全量可见）。"""

def can_read(user, db_name, table, column=None) -> bool: ...
def allowed_tables(user, db_name) -> set[str] | None: ...
def deny_hint(user, db_name, table, column) -> str:      # 给模型的拒绝文案（附可用清单）
def set_field_grants(...) / list_field_grants(...) / revoke_field_grants(...)   # 管理写路径
```

**数据来源**：MDL 的**权威抽取器**，不自己遍历 `mdl.json`：

```python

```

`extract_schema_items(manifest)`（`wren/memory/schema_indexer.py:220`）是语料权威源，与全量注入路径同源；
本仓 `src/agent/retrieval/indexer.py:143-171` 已有复用它建索引的先例，键约定（`relationship` 取左表名、
`cube` 取 `baseObject`、`view` 为空串）也已在 `indexer.py:85` 钉死 —— **同一份映射，不抄第二份**。

**缓存**：`(项目路径, mdl 指纹, 策略版本号)` → 可见视图。策略版本号在每次 `field_grants` 写入时 +1

### 2.3 面 A：模型可见（看不见）

**A-1 · 提示词注入**（`nl2sql_agent.py:dynamic_prompt`）
已建模分支：把今天注入的 Cube 清单扩成**过滤后的可见 schema 摘要**（表名 + 可见列名，来自 `visible_schema`）。
这一步决定模型"知道有什么"，是降低"幻觉出不存在的表"的第一手段（与已发版的失败熔断是同一目标）。

**A-2 · 取料快路径**（`path_resolver._wren_fast_path` + `retrieval/adapters.py`）
- `context_artifact`：命中片段按 `meta.model` 过滤（隐藏表/列既不出现在片段里，也不出现在 `_schema_skeleton` 的名字清单里）。
- `describe_schema` 的 full 回落分支：**先投影 manifest 再渲染**（`describe_schema(projected_manifest)`）。
- `matches_artifact`（`recall_queries`）：Demo SQL 逐字含表名列名 ⇒ 按 `model_name` 过滤，命中隐藏对象的范例对整条丢弃。

**A-3 · 结果后处理**（`path_resolver._wrap_tool` 的 `wrapped_run` / `wrapped_arun`）
对**走 MCP 子进程**的那几类（`get_mdl` / `describe_model` / `list_models` / `list_cubes` / `describe_cube` /
`get_instructions` / `list_knowledge` / `get_all_knowledge` / `list_stored_queries`）：
在结果返回模型前做一次**确定性裁剪** ——
① JSON 结构里按 `name`/`model`/`columns[].name` 字段删隐藏项；
② 纯文本按**逐字命中的隐藏表名/列名**删除所在行。
**并且必须让模型知道"被裁剪过"**：追加一行 `（部分对象因权限未展示；如需请向管理员申请）` ——
否则模型会以为表不存在而来回试（已发版的失败熔断会因此误伤）。

> ⚠️ A-3 是**降噪与体验**，不是防线。文本裁剪不可能穷尽（换行、别名、中文描述里的同义词都会漏）。
> 写进代码注释与运维手册，防止后人把它当权限。

### 2.4 面 B：执行侧（拦得住）

**落点**：`QueryGateMiddleware._gate`（`query_gate.py:369`）中**规则零之后**插入"规则零之二"：

```python
denied = self._db_authorized(request, name)      # 规则零（库级，已有）
if denied is not None: return denied
denied = self._field_authorized(request, name)   # 规则零之二（字段级，本方案）
if denied is not None: return denied
```

覆盖 `_is_query_tool(name)` 的**全部** `wrenai_*` / `dbmcp_*`（含 Schema/知识读工具 —— 它们同样按库返回业务元数据，
统一判权省掉一份"哪些工具算查询"的清单要跟上游同步，这条理由在 `_is_query_tool` 的注释里已经写过）。

**判定机制（核心，不手搓 SQL 解析器）**：

1. 取 `visible_schema(user, db)`；为 `None` ⇒ 放行（未启用字段级）。
2. 把该项目的 MDL **投影**成一份过滤后的 MDL JSON：
   - 表：整表不可见 ⇒ 从 `models` / `views` / `cubes` / `relationships` 里**整条删掉**；
   - 列：不可见 ⇒ 从该 model 的 `columns` 里删掉（而不是标 `is_hidden` —— 投影产物是临时的，不必也不该走全局语义）。
   - **Cube 的可见性判据 = 它的 `base_object`**：一个 Cube 只绑**唯一**一个 base object（`wren/context.py:1200-1216` 校验它必须引用已定义的 model/view；
     `describe_cube` 就回这个 `base_object`，`wren/mcp_server.py:263`），**没有 Cube 级隐藏键**（唯一被引擎认的隐藏键只有列级 `isHidden`）。
     所以 `base_object` 的表不可见 ⇒ 该 Cube 整条删；表可见但某些 measure/dimension 引用的列隐藏 ⇒ 把那些 measure/dimension 删掉。
     引用隐藏列的 Cube 若整体保留会同时踩**取料面**（`describe_cube` 逐字回 measures/dimensions 名）与**执行面**（`query_cube` 走 `cube_query_to_sql` 照样出隐藏列）。
3. 用**过滤后的 MDL** 在进程内建引擎跑 `dry_plan`：
   - `run_sql` / `dry_run` / `dry_plan`：对模型写的那条**语义层 SQL** 跑 `engine.dry_plan(sql)`；
   - `query_cube`：对 `_build_cube_query(...)` → `cube_query_to_sql(...)` 的产物跑 `dry_plan`。
   - 直接复用 `src/agent/utils/wren_plan.py` 的既有能力：`probe_wren_api()`（`:83`，私有 API 能力探测，不通过则本规则**降级为只按 A-2 裁剪 + 记 WARNING**）、
     `_build_engine_for(mdl_path, conn)`（`:226`，`conn_required=False` ⇒ **不开数据库连接**）、`_engine_for` 的 LRU（`:239`）。
4. **编译成功 ⇒ 放行；引擎报"未知 model/column"或任何异常 ⇒ 拒绝**（返回 `status="error"` 的 `ToolMessage` + `deny_hint`）。
   拒绝理由由**引擎**给出，与线上同源；且是 **fail-closed**（有疑即拒），与报告那条 fail-open 路径取向相反 —— 因为这条属于"越权阻止"，不是"能力降级"。

**`SELECT *` 的处理（必须显式说清）**：过滤后的 MDL 上 `*` 只展开可见列，
但**线上执行走的是未过滤的 MCP 引擎** ⇒ `*` 会把隐藏列也捞回来。所以：

- `run_sql` / `dry_plan` / `dry_run`：**拒绝裸 `SELECT *`**（`COUNT(*)`、`COUNT(* ) OVER()` 之类放行），
  拒绝文案要求显式列出列名。提示词本来就要求显式列名，这条只是把它变成硬约束。
- `query_cube`：**不需要 `*` 规则** —— cube 的度量/维度是定义里写死的，按 cube 与所列 measures/dimensions 的可见性判定即可。

**缓存**：投影后的 MDL + 引擎按 `(项目, mdl 指纹, 策略版本)` 缓存（复用 `_ENGINE_CACHE` 的 LRU 形态），
上限用 `WREN_SCOPE_CACHE_MAX` 覆盖（键数 ≈ 库数 × 活跃策略数，默认给足）。

| 对象 | 现状 | 本方案 |
|---|---|---|
| **报告** | `report_owner` 按库可见（`grants.can_read_report` :357-368，**无记录 ⇒ allow**） | 报告正文含**执行 SQL**（`wren_plan` 复算的物理 SQL，逐字带物理表名列名）⇒ 产出时记 `referenced_objects`（表/列）；读取时要求 `referenced_objects ⊆ 读者的 visible_schema`，否则 **404**。老报告无该字段 ⇒ 退回今天的库级可见（迁移语义，同 §2.1） |
| **会话 / FTS** | 已按 `thread_owner` 只搜自己的 | 不变 |
| **trace / 反馈** | 已带 `db_name`，按 `thread_owner` 过滤 | 不变（标注队列/导出照旧限管理员） |
| **知识料 `knowledge/`** | 语料层一份，逐字写着取数口径 | 面 A-3 覆盖读取；**不做**自动删改（会破坏语料）。管理端新增一条**非阻断提示**："本文件提到 N 个受限对象" |

### 2.6 与既有机制的关系（叠加，不替代）

- **库级 `grants` 仍是第一道**：字段级只在已授权库内部再收窄。执行顺序 = 库级 → 字段级。
- **`ToolFilterMiddleware`**（出站裁剪，`tool_filter.py:67-90`）继续按库裁；字段级**不改工具名**（工具还是那 18+2 个），
  所以与它正交，不需要新的过滤清单。
- **`is_hidden`**（MDL 里的全局列隐藏）：本方案**不动它**。两者叠加 = 全局隐藏 ∪ 用户级隐藏。
  管理员用 `is_hidden` 表达"这列谁都不该看"，用 `field_grants` 表达"这列只有某几个人能看"。

## 3. 分期与验收（都可离线复现）

| 期 | 内容 | 验收 |
|---|---|---|
| **P1 地基 + 执行侧** | `field_grants` 表 + `visible_schema` 判定 + 管理 API + 「规则零之二」（`_field_authorized`） | 未授权列 `select 工号, 薪资 from 员工` ⇒ **拒绝且未执行**（日志无 MCP 调用）；`select * from 员工` ⇒ 拒绝 + 提示显式列；授权后同一条 SQL 通过；`visible_schema` 为 `None` 时逐字等价今天行为（负对照） |
| **P2 模型可见** | `dynamic_prompt` 注入 + 取料快路径/检索过滤 + `_wrap_tool` 后处理 | 隐藏表名**不出现**在任何工具返回与注入提示词里（逐字节断言，含 `_schema_skeleton` 的名字清单与知识料片段）；被裁剪时提示行在位 |
| **P3 产出** | 报告 `referenced_objects` + 知识料非阻断提示 | 拿 B 的 cookie 读 A 的报告（引用了 B 不可见的列） ⇒ 404；无 `referenced_objects` 的老报告仍按库可见（负对照） |

P1 单独就能交付一个**可用的功能**（拦得住）；P2/P3 是体验与旁路收口。

## 4. 验证（离线为主）

**离线**（新房风：UTF-8 头 + 中文长 docstring + `check/section` + ANSI OK/NG + 负对照 + `n/t 通过` + `sys.exit(main())`）：

1. `scripts/verify_field_grants.py` —— 判定语义四律（deny 优先 / allow 覆盖 / 白名单兜底 / admin 豁免）+ 迁移语义
   （无行 ⇒ `None`）+ 通配匹配边界（`*` 只在整段位置，不做前缀匹配 —— 负对照：`emp_*` 不得命中 `emp_salary`）。
2. `scripts/verify_query_gate_field.py` —— 「规则零之二」的**执行侧**断言：拒绝时**handler 未被调用**、库级规则顺序在前、
   `visible_schema` 为 `None` 时恒放行、`SELECT *` 拒绝但 `COUNT(*)` 放行、`query_cube` 走 cube 可见性分支、
   引擎能力探测失败时降级为放行 + WARNING（fail-open 的**唯一**例外，必须显式断言并在注释里写为什么）。
3. 投影函数单测：MDL 投影后 `describe_schema(projected)` 的文本里**不含**隐藏表名/列名（逐字节，含负对照 —— 投影前的文本必须**含**）。
4. **全量 sweep**：`scripts/verify_*.py` 全绿（本仓既有 49+ 套；改 `query_gate` 必跑 `verify_query_gate*`）。

**E2E（需点名授权，另行发起）**：两个账号（一个白名单、一个全量）对同一库同一问题各跑一次，
断言白名单账号的**会话消息里**不含隐藏列名、结果表头不含隐藏列、`run_sql` 越权调用被拒且未执行。

## 5. 边界与先决条件（必须先接受 / 必须先堵）

| # | 事项 | 处置 |
|---|---|---|
| 1 | **文本裁剪不可能穷尽** | 真正的防线是面 B 的执行侧闸。这条写进运维手册，防止后人把面 A 当权限 |
| 2 | **`dbmcp_*` 直连通道没有 MDL** ⇒ 字段级无从判定 | 启用字段级时，**整体禁用直连通道**（与"已建模库禁直连"同款硬闸，`query_gate._channel_deny` 已有先例）。要字段级的库**必须先建模** |
| 3 | 一条共享数据库连接 ⇒ **不能**靠数据库自身权限做列级 | 只能由平台保证"下发的 SQL 不含隐藏列、返回的结果不含隐藏列" |
| 4 | SQL 里跨库引用 `别的库.表`、或引用 MDL 里不存在的对象 | 投影后的 MDL 编译不过 ⇒ 天然拒绝（fail-closed 的好副作用） |
| 5 | **性能** | 每次执行多一次进程内 `dry_plan`（本地小库 1~3ms；冷建引擎 ~0.9s，有 LRU）。与既有 `wren_plan` 同量级；`WREN_SCOPE_CACHE_MAX` 控制内存 |
| 6 | 依赖 wren 私有 API（`wren.cli._build_engine` / `wren_core.cube_query_to_sql`） | 已有 `probe_wren_api()` 能力探测。探测不过 ⇒ 本规则降级（记 WARNING），面 A 仍在；**这一降级必须显式记录**，不能静默 |
| 7 | 行级数据权限（RLS，如"只看本部门"） | **不做** —— 语义层表达不了，用户也未提。若将来要做，落点是 MDL 里注入行过滤条件（另一条链） |
| 8 | **实施前必须先查清 RLAC / CLAC**（`rowLevelAccessControls` / `columnLevelAccessControl`） | `wren/context.py:117-118` 有映射、`wren/mdl/cte_rewriter.py:337,375,854` 把 `SELECT *` 透传给 **wren-core（Rust）**。**Python 侧不执行、Rust 侧是否生效未验证**。若上游已支持按 MDL 里的这些键做行/列级管控，本方案的执行侧可以改成"**按用户投影出 RLAC/CLAC 声明**"而不是整份 MDL 投影 —— **先验证再定实现**，但**设计结论不变**（都是一份 MDL + 运行期按人投影） |

## 6. 明确不做

- **不给每个人/每个项目复制语义库目录**（违背硬约束；本方案的投影是**运行期视图**，不落盘、不进语料层）。
- **不改 MDL 的全局 `is_hidden` 语义**（它是"所有人都别看"，与 per-user 正交）。
- **不 fork / 不改 wren 上游**，不动 `wren serve mcp` 的参数面。
- **不做行级权限**。
- **不做前端字段勾选 UI**：P1 只给管理 API（`/api/auth/field-grants`），前端另立一轮
  （前端那套"设置页"有过 readOnly / 只能读一次的历史包袱，入口单独设计比顺手加稳妥）。
