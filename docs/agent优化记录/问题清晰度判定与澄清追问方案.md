# 问题清晰度判定与澄清追问方案（A+B 组合）

> 2026-08-14 · 状态：设计已确认，待实施（用户已要求暂不实施）

## 背景与需求

前端提问时，系统应判断问题是否清晰；不清晰时大模型需要进一步询问用户。覆盖四类不清晰：

1. **缺查询条件** — 如「查询销售数据」没给时间范围/区域/维度
2. **业务术语歧义** — 如「查一下活跃用户」，库里可能有多个口径（月活/日活/留存），必须对照 Schema/指标定义才能判
3. **笼统/太泛** — 如「分析一下数据」，不是明确的数据查询
4. **多义/二选一** — 如「各类型的销售额」，「类型」对应多个可选维度列

**核心洞察**：四类问题需要不同深度的上下文——
- 「笼统/太泛」→ 主 agent 意图分类层就能挡（不需要 Schema）
- 「缺条件/术语歧义/多义」→ 必须能查 Schema 和业务指标定义，只有 nl2sql 子智能体（有 WrenAI 工具）能判准

单一层覆盖不了四类，故采用分层组合。

## 总体架构（分层判定，各管一类）

```
前端提问
  │
  ▼
主 agent 意图层（B，纯提示词，零成本）
  │   ├─ 意图完全无法归类（"分析一下数据""随便看看"）→ 直接追问用户，不委派
  │   └─ 归为数据查询 → 委派 nl2sql
  ▼
nl2sql 子 agent 澄清门 Step 0（A，Schema 感知）
  │   ├─ clear=true  → 继续 sql-of-thought 策略决策（A/B/C）
  │   └─ clear=false → 停止流水线，返回澄清问题 → 主 agent 转述给用户
  ▼
用户回答 → 主 agent 把「原问题 + 回答」合并 → 重新委派 → 澄清门复核 → 流水线执行
```

**职责边界**：B 只挡"连任务类别都分不清"的泛问（不需要 Schema）；A 挡"缺条件 / 术语歧义 / 多义"（必须看 Schema + 知识库）。A 是价值核心，B 是廉价前置过滤器。

**架构前提**：澄清门必须放在 nl2sql 子 agent 内，因为主 agent 没有 WrenAI Schema 工具（get_context / get_instructions / list_knowledge 只对子 agent 可用）。

## 方案对比（为何选 A+B）

| 方案 | 位置 | 优点 | 缺点 |
|------|------|------|------|
| A. 子 agent 澄清门 | nl2sql 子 agent，sql-of-thought Step 0 | 判定准（有 Schema 上下文）、可控制（结构化输出+独立技能） | 每次查询多一次 LLM 调用 + Schema 工具开销；有过问风险需护栏 |
| B. 主 agent 意图层 | MAIN_AGENT_PROMPT.md 意图识别规则 | 零基础设施 | 无 Schema 判不了术语歧义/多义；纯提示词可靠性不稳 |
| C. 前端预检 | 前端提交前轻量判定 | 省后端 token、响应快 | 无 Schema 判不了业务歧义；新建端点维护成本高 |
| **A+B（选定）** | 主 agent 轻挡 + 子 agent 精确判 | 四类全覆盖、判定准、前端零改动 | 比单独 B 多一个子 agent 层 |

C 放弃：收益低、和主 agent/nl2sql 知识口径易脱节。

## B 层：主 agent 意图层轻挡（纯提示词）

在 `src/agent/prompt/MAIN_AGENT_PROMPT.md` 的「意图识别规则」最顶部新增一类：

**「意图不清 / 信息不足 → 澄清」**，触发：
- 无明确任务类别：`分析一下数据`、`随便看看`、`有什么好问题`、`帮我查查`（没说查什么）
- 明显超出能力：`预测明年股价`、`对比整个行业`（无表可查）
- 指代不明：`对比一下他们`（"他们"指谁无从判断）

**行为**：主 agent 直接向用户追问 1 个问题（**不调任何工具、不委派**），只问最关键的一点：
> "您想分析哪方面数据？比如销售趋势、用户增长，或具体某张表？"

**防误伤规则**：
- 能归为数据查询的 → **一律交给子 agent**，B 不拦（子 agent 有 Schema，判得更准）
- B 只在"连类别都无法确定"时才开口
- 追问限 1 轮：用户回答后若仍无法归类 → 按最可能的类别继续，不再追问

## A 层：nl2sql 子 agent 澄清门

### 新增技能 `nl2sql-clarification`

放在 `src/agent/skills/nl2sql/` 下，与现有 7 个技能同级。由 `sql-of-thought` 作为 **Step 0** 在策略决策前加载。

改动点：
- `src/agent/skills/nl2sql/sql-of-thought/SKILL.md`：新增「Step 0: 澄清检查」章节
- `src/agent/prompt/NL2SQL_SYSTEM_PROMPT.md`：技能清单加 `nl2sql-clarification`

### 判定流程（Schema 感知，只调 2 个工具）

```
1. get_context(question)     → 语义检索相关 Schema 片段（哪个模型/列命中）
2. get_instructions() + list_knowledge()  → 业务规则 + 指标/术语定义
3. 对照产出结构化裁决
4. 将检索结果写入 /workspace/nl2sql_process_data/{thread_id}/clarification/context.json
   → 后续 schema-linking 步骤直接复用，不重复调用（省一次工具往返）
```

**不用** describe_schema 全量拉取（token 贵）；`get_context` 的语义命中本身就是"哪个模型最相关"的信号。

### 结构化裁决输出

SKILL.md 强制子 agent 输出固定 JSON（写盘 + 作为最终回复核心）：

```json
{
  "clear": false,
  "reason": "TERM_AMBIGUOUS",
  "issues": [
    {
      "type": "missing_condition",
      "field": "时间范围",
      "question": "请提供查询的时间范围，如：2024年全年、最近30天"
    },
    {
      "type": "term_ambiguity",
      "term": "活跃用户",
      "definitions": ["月活", "日活"],
      "question": "「活跃用户」指哪种口径？（月活 / 日活）"
    },
    {
      "type": "multi_choice",
      "field": "类型",
      "candidates": ["电影类型", "用户类型"],
      "question": "您说的「类型」指哪一种？"
    }
  ]
}
```

- `clear=true` 时也输出一个 `assumption` 字段（如"按2024年全年、取月活口径"），随结果一起展示——**透明性**。
- 清晰问题直接过，**零额外成本**（只多一次 get_context，且可被 schema-linking 复用）。

### 四类判据

| reason | 判定信号 | 触发条件 |
|--------|---------|---------|
| `VAGUE` | get_context 无任何模型命中 / 语义相似度极低 | 笼统、非查询 |
| `MISSING_CONDITION` | 命中模型/列，但关键过滤字段（时间、实体名）问题里没给 | 缺条件 |
| `TERM_AMBIGUOUS` | 知识库/指标定义里同一术语有多个口径 | 业务术语歧义 |
| `MULTI_CHOICE` | get_context 命中多个互斥的维度列/模型，各自都"像" | 二选一 |
| `OK` | 单一模型+列明确映射 | 清晰，直接过 |

### 防过度追问护栏

- **能猜就猜**：单一解释明显占优（>~7 成把握）→ 不追问，走 assumption。
- **只问 1~3 个最关键缺口**，一个问题最多 3 个选项，紧凑呈现。
- **一轮上限**：每次委派最多澄清 1 轮；用户回答后仍不清 → 带 assumption 继续执行，不再追问。
- **故障回退**：`get_context`/`get_instructions` 调用失败（库离线）→ 视为 clear，直接进流水线，**不因基础设施故障阻塞查询**。

### 结果回流与多轮衔接

当前异步链路：主 agent `start_async_task` → 子 agent 后台跑 → 完成时主 agent 收到 `[系统自动通知]`。

澄清时：
```
1. 子 agent Step 0 发现不清晰 → 流水线停止，返回带标记的回复：
   [需要澄清] 问题:「查询销售数据」
   请补充：① 时间范围？② 按地区还是按产品？
   （JSON 裁决同时写盘留痕）
2. 子 agent 很快完成 → 主 agent 收到自动通知 → 读到 [需要澄清] 标记
   → 把问题原样转述给用户（不当作查询结果呈现）
3. 用户回答「2024年，按地区」
4. 主 agent 识别这是对上一轮澄清的回复 → 重新委派，
   prompt = 【原始问题】查询销售数据 2024年按地区 + 用户补充信息
5. 子 agent 复核 Step 0 → 现在 clear → 进流水线执行
```

**主 agent 侧改动**（`MAIN_AGENT_PROMPT.md`）：
- 识别子 agent 返回的 `[需要澄清]` 标记 → 转述，不呈现为结果、不触发"推荐图表→报告"链路
- 新增规则："若上一轮已向用户提出澄清问题，用户本轮回答视为对澄清的回答，合并原问题重新委派"

## 多轮衔接风险分析（2026-08-14 补充）

多轮衔接（子 agent 返回 `[需要澄清]` → 主 agent 转述 → 用户回答 → 合并重新委派）是整套设计中风险最集中的环节。逐条风险按严重度排序，并给出减风险设计调整。

### R1【高】澄清可能不主动弹出，用户只看到"查询已提交"

- **现状**：委派规则是"`start_async_task` 后只回复『查询已提交』，**等用户下一次发言再处理结果**"。澄清依赖的自动续跑路径（`[系统自动通知]` → 主 agent 恢复转述）正是 `sync_subagent_todos.py` 记录的有竞态的那条——主线程空闲时 `update_state` 可能被 LangGraph 以 "has in-flight runs" 拒绝，终止态写不进 async_tasks，前端自动续跑丢失。
- **后果**：用户提交后看到"查询已提交"再无下文，直到再发一条消息才触发 `check_async_task` 把澄清问题顶出来。在"缺条件"高频场景下被反复放大。
- **缓解**：见调整 ③。

### R2【高】澄清状态无显式记录，跨轮衔接靠主 agent"猜"

- **现状**：没有任何 `pending_clarification` 状态。主 agent 判断"用户这轮回答是对澄清的回应、合并原问题重新委派"全靠从对话历史回忆。对话长/被压缩后可能不记得提过澄清 → 把回答当独立新查询委派；或合并时原问题转述走样。
- **缓解**：见调整 ①。

### R3【中-高】结构化信息在转述中丢失

- **现状**：子 agent 裁决是 JSON（含 `candidates`/`definitions`），回流给主 agent 的通道是文本。主 agent 转述可能改写、丢选项；写盘的裁决 JSON 主 agent 不读。
- **缓解**：见调整 ②。

### R4【中】并发查询下回答绑错任务

- **现状**：系统支持并发多查询（`active_queries` 按 task_id 键控）。两个查询同时在跑、其中一个要澄清时，用户回答可能被合并进错误的 task_id。
- **缓解**：澄清内容按 task_id 落盘；重新委派时按 task_id 关联（沿用现有键控模式）。

### R5【中】`[需要澄清]` 文本标记不可靠

- **现状**：主 agent 靠返回文本里的固定标记区分"澄清"vs"查询结果"。子 agent 没按技能输出标记 → 主 agent 把澄清问题当查询结果展示，还错误触发"推荐图表→报告"链路。
- **缓解**：见调整 ④。

### R6【低-中】多轮成本 + "随便"回答

- **现状**：每轮澄清 = 重新委派 + 子 agent 完整跑一遍。护栏（最多 1 轮、仍不清带假设执行）防死循环；但用户回"都行/随便"时系统带假设继续，必须把假设明确展示，否则用户不知道模型猜了什么。

## 减风险设计调整（纳入正式设计，非可选）

1. **① 用显式状态替代"靠历史猜"（解 R2）**
   子 agent 裁决时把澄清内容写到固定路径 `/workspace/nl2sql_process_data/{thread_id}/clarification/verdict.json`。主 agent 重新委派时**确定性读此文件**合并，不靠对话历史回忆。加 `pending_clarification` 标记进 async_tasks 状态。

2. **② 转述走结构化（解 R3）**
   主 agent 转述**原样转发**子 agent 的 JSON，前端据此渲染选择题；用户点选后前端把「原问题+所选」**已合并**发回——把"合并"从主 agent 提示词逻辑移到前端/状态层。**P3（前端 chips）由可选项升级为必要项。**

3. **③ 澄清门做"快查快回"（缓解 R1）**
   Step 0 只做 `get_context` + 裁决，几秒完成，不碰流水线。委派指令改分支逻辑："收到自动通知且是 `[需要澄清]` → 立即转述；运行中 → 回复已提交"。缩短自动续跑竞态的暴露窗口。

4. **④ 标记冗余校验（解 R5）**
   主 agent 识别 `[需要澄清]` 时**同时校验 verdict.json 存在**，两信号都齐才算澄清，否则按查询结果处理。

**底线判断**：R1、R2 是这套方案真正可能翻车之处，R1 还踩在已记录未修复的竞态上。①②③④纳入后，多轮衔接从"靠提示词碰运气"变为"有状态、有校验、结构化"，风险基本可控。代价是多一块状态管理 + 前端渲染，这正是 P3，绕不开。

## 验证记录（T5 实测，2026-08-14）

> 验证方式：通过 `/threads/{tid}/runs/stream` 起主 agent run，轮询 GET `/threads/{tid}/state` 的 `async_tasks` 至终止态，再发「查询进度」触发主 agent 读取转述。（注意：读 state 必须用 **GET**，POST 是更新端点，返回无 values——此前验证脚本 v2 的 bug。）

### 已验证 ✅

| 项 | 结果 |
|----|------|
| 澄清门加载与运行 | ✅ 每次查询进度条出现「澄清检查 ✅ 完成」，证明 Step 0 已进流水线 |
| verdict.json / context.json 落盘 | ✅ 每次查询后 `nl2sql_process_data/{thread_id}/clarification/` 下均有 verdict + context，且 assumption 基于真实 get_context/get_instructions 结果 |
| 清晰问题零变化 | ✅ 「查询 average_rating 最高的5部电影」等清晰问题直接出结果，不多问、不阻塞 |
| B 层缺实体拦截 | ✅ 「查询演员的作品列表」→ 主 agent 直接追问「请提供演员姓名」，未委派、未生成假数据 |
| 基础设施故障不阻塞 | ✅ get_context/get_instructions 失败 → clear 继续（代码路径已确认） |

### 关键发现：A 层「能猜就猜」护栏过松，自然问题几乎不触发

5 个自然语言不清晰候选，**全部被判定 clear=true**（默认映射到单一口径，写入 assumption）：

| 候选问题 | 判定 | 假设口径 |
|---------|------|---------|
| 查询电影的平均评分 | OK | 全库平均 6.23 |
| 查询评分高的电影 | OK | average_rating |
| 查询电影的评分情况 | OK | 评分分布 |
| 查询评分最高的电影 | OK | average_rating + num_votes>10000 |
| 哪个电影口碑最好 | OK | average_rating |
| 哪个导演人气最高 | OK | SUM(num_votes)（star_power 未采用） |

imdb 知识库定义 4 个评分指标（average_rating / Quality Score / Bayesian / Vote-Weighted）+ Star Power，但护栏「>7 成把握就猜」让模型每次都能选出一个默认口径，**从不输出 `[需要澄清]`**。

**后果**：A 层（Schema 感知澄清门）实际沦为"每次跑一遍但只写 verdict、从不追问"；真正的追问能力只剩 B 层缺实体拦截。Half 2（`[需要澄清]` → 主 agent 转述 → 用户回答 → 合并重委派）因 A 层从不触发，**未能在自然场景验证**。

### 决策（2026-08-14 用户拍板）

**保持现状，关闭 T5**。护栏保守是设计意图——imdb 上 average_rating 是强默认，不追问是对的；真实业务系统（无强默认）上 A 层才有用武之地，届时 Half 2 链路可按本方案既有实现验证。后续若出现「术语歧义需要追问」的真实场景，再考虑收紧 TERM_AMBIGUOUS 触发条件。
