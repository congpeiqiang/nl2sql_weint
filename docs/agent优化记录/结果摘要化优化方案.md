# 结果摘要化优化方案

> 基于 trace 01a022be 分析：`check_async_task` 返回的 SQL 查询结果未经处理直接塞给 LLM，导致 prompt 膨胀到 34k+ tokens，首轮 LLM 调用耗时 34.3s。

---

## 问题定位

### 数据流

```
子 agent 执行 SQL → run_sql 返回结果 → 子 agent 的 last message
  → _enhanced_build_check_result 取 last["content"] 作为 result["result"]
  → json.dumps(result) → ToolMessage content
  → 下一轮 LLM 调用时，该 ToolMessage 进入上下文 → prompt 34,565 tokens
```

### 关键代码路径

1. **`check_progress.py:108-112`**：`_enhanced_build_check_result` 在 `status=="success"` 时，把子线程最后一条消息的 `content` 完整放入 `result["result"]`：
   ```python
   if run["status"] == "success":
       if messages:
           last = messages[-1]
           result["result"] = (
               last.get("content", "") if isinstance(last, dict) else str(last)
           )
   ```

2. **`check_progress.py:139-165`**：`_enhanced_build_check_command` 把整个 `result` dict 做 `json.dumps` 塞进 ToolMessage：
   ```python
   return Command(
       update={
           "messages": [ToolMessage(
               json.dumps(result, ensure_ascii=False, indent=2),
               tool_call_id=tool_call_id,
           )],
           ...
       }
   )
   ```

3. **`message_slimmer.py`**：现有 `MessageSlimmerMiddleware` 在 `wrap_tool_call` 阶段截断，阈值 16,000 字符。但 SQL 查询结果可能 **不到 16,000 字符** 却包含大量结构化数据（如 50 行 × 10 列），在 JSON 序列化后 token 数远高于字符数。

### 根因

`result["result"]` 包含了子 agent 的完整最后一条消息（AI 消息），其中可能包含大量 SQL 查询结果、推理过程，但没有做任何摘要/截断。即使 `MessageSlimmerMiddleware` 的 16,000 字符阈值被触发，截断后的 JSON 截断可能破坏结构，LLM 仍然要处理大量数据。

---

## 方案设计

### 总思路：在 `check_async_task` 返回结果时做摘要，而非事后截断

事后截断（`MessageSlimmerMiddleware`）的问题是：
- 截断 JSON 字符串会破坏结构，LLM 可能读到不完整的 JSON
- 字符阈值对 SQL 结果不敏感（5KB 的 CSV 表格 ≈ 2,000 tokens，但 5KB 的 JSON 可能 ≈ 1,500 tokens）

**正确做法**：在 `_enhanced_build_check_result` 中，对 `result["result"]` 做结构化摘要——保留结构、截断数据。

### 方案 A：`check_async_task` 返回时智能摘要（推荐）

在 `check_progress.py` 的 `_enhanced_build_check_result` 中增加摘要逻辑。

#### 摘要策略

```
对 result["result"]（子 agent 最后一条消息内容）做分层处理：

1. 长度 ≤ 2000 字符 → 保留原文
2. 长度 > 2000 字符 → 智能摘要：
   a. 检测是否包含 SQL 查询结果（匹配 "|" 表格格式 / CSV / JSON 数组）
   b. 如果是 SQL 结果 → 保留列名 + 前 N 行 + 统计摘要（总行数、列数）
   c. 如果是 AI 推理文本 → 保留前 500 字符 +  "...(已截断，完整结果可通过 check_async_task 增量读取获取)"
   d. 同时保留原始消息的 metadata（行数、列数、数据大小）供 LLM 判断是否需要图表
```

#### 代码实现

```python
# check_progress.py 新增

_MAX_RESULT_CHARS = 2000      # 结果内容最大字符数
_MAX_RESULT_ROWS = 20         # SQL 结果最多保留行数

def _summarize_result(content: str) -> str:
    """智能摘要子 agent 返回的结果内容。
    
    保留结构信息（列名、行数），截断数据行，确保 LLM 能判断是否需要图表。
    """
    if len(content) <= _MAX_RESULT_CHARS:
        return content
    
    # ── 1. 检测 SQL 表格结果（Markdown 表格格式） ──
    lines = content.split("\n")
    table_lines = [l for l in lines if l.strip().startswith("|")]
    if len(table_lines) >= 3:  # 至少有 header + separator + 1 行数据
        # 保留 header + separator + 前 N 行数据 + 统计
        header = table_lines[0]
        sep = table_lines[1] if len(table_lines) > 1 else ""
        data_rows = table_lines[2:]
        kept = data_rows[:_MAX_RESULT_ROWS]
        summary = (
            f"{header}\n{sep}\n" + 
            "\n".join(kept) +
            f"\n\n*(共 {len(data_rows)} 行数据，以上展示前 {len(kept)} 行)*"
        )
        return summary
    
    # ── 2. 检测 JSON 数组结果 ──
    import json as _json
    try:
        data = _json.loads(content)
        if isinstance(data, list) and len(data) > 0:
            kept = data[:_MAX_RESULT_ROWS]
            summary = _json.dumps(kept, ensure_ascii=False, indent=2)
            summary += f"\n\n*(共 {len(data)} 条记录，以上展示前 {len(kept)} 条)*"
            return summary
    except (_json.JSONDecodeError, ValueError):
        pass
    
    # ── 3. 普通文本：保留头尾 ──
    head = content[:_MAX_RESULT_CHARS // 2]
    tail = content[-(_MAX_RESULT_CHARS // 2):]
    return f"{head}\n\n...(中间已省略，共 {len(content)} 字符)...\n\n{tail}"
```

#### 修改 `_enhanced_build_check_result`

```python
def _enhanced_build_check_result(run, thread_id, thread_values):
    result = {"status": run["status"], "thread_id": thread_id}
    messages = (
        thread_values.get("messages", [])
        if isinstance(thread_values, dict)
        else []
    )
    if run["status"] == "success":
        if messages:
            last = messages[-1]
            raw_content = (
                last.get("content", "") if isinstance(last, dict) else str(last)
            )
            # ★ 新增：智能摘要
            result["result"] = _summarize_result(raw_content)
            # 附加元数据供 LLM 判断是否需要图表
            result["result_size"] = {
                "chars": len(raw_content),
                "summarized": len(raw_content) > _MAX_RESULT_CHARS,
            }
        else:
            result["result"] = "(completed with no output messages)"
    # ... 其余逻辑不变 ...
```

### 方案 B：新增 `MessageSlimmerMiddleware` 行级截断能力（辅助）

在现有 `message_slimmer.py` 中增加对 SQL 结果的结构感知截断，与方案 A 互补——方案 A 处理 `check_async_task` 的结果摘要，方案 B 处理其他工具（如 `read_file`）返回的 SQL 结果。

#### 新增配置参数

```python
class MessageSlimmerMiddleware(AgentMiddleware):
    def __init__(
        self,
        *,
        backend: BackendProtocol | None = None,
        max_chars_before_truncate: int | None = _DEFAULT_MAX_CHARS_BEFORE_TRUNCATE,
        # ★ 新增
        max_rows_before_truncate: int | None = 50,  # SQL 结果行数阈值
        max_tool_result_chars: int | None = 8000,    # 通用工具结果字符阈值（降低）
    ) -> None:
        ...
```

#### 降低默认阈值

当前 `_DEFAULT_MAX_CHARS_BEFORE_TRUNCATE = 16_000`（16KB），对于 SQL 结果场景偏大。建议降低到 **8,000**，让更多结果触发截断：

```python
_DEFAULT_MAX_CHARS_BEFORE_TRUNCATE = 8_000  # 从 16,000 降到 8,000
```

#### 修改 `main_agent.py` 初始化参数

```python
# main_agent.py 中
message_slimmer = MessageSlimmerMiddleware(
    backend=composite_backend,
    max_chars_before_truncate=8_000,  # 降低阈值
)
```

### 方案 C：P1-7 增量读取推广（已有但未充分利用）

`check_progress.py` 已经实现了 `since` 游标增量读取（P1-7），但 LLM 可能不会主动使用。方案：

1. **在 prompt 中强化**：告诉 LLM 首次 `check_async_task` 不传 `since`，获取完整状态（含摘要后的结果）；如果需要详细数据，再传 `since` 做增量读取
2. **默认启用摘要**：首次 `check_async_task` 自动摘要（方案 A），LLM 评估后如需完整数据，再以 `since` 增量获取
