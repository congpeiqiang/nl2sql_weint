# 真正并发多查询实现方案

> 日期：2026-08-06
> 状态：已实施
> 涉及项目：nl2sql 后端 (`D:\code_work_space\llm\nl2sql`) + 前端 (`D:\code_work_space\llm\huice\008\harness-deep-agents-ui`)

## 1. 背景与问题

当前系统只能有效运行**一个**数据查询。主智能体通过 `start_async_task` 委派 nl2sql 子任务，
但进度字段（`query_header`、`subagent_steps`、`query_active`）是**单值**的：
每个 `start_async_task` 启动的独立 sync 线程都往主线程 state 写**同一字段** → **互相覆盖**。

实际测试（thread `019fd503`）确认：两个查询并发时进度只显示最新一个，auto-continue 误判。

## 2. 并发失败点

| # | 问题 | 位置 | 根因 |
|---|------|------|------|
| C1 | 单值字段互相覆盖 | `sync_subagent_todos.py` | 字段无 reducer，`update_state` 整值替换，多线程 last-write-wins |
| C2 | `async_tasks` 整字典读-改-写竞态 | `sync_subagent_todos.py` | 线程 A/B 都 get_state→改→写整字典，后写的用旧拷贝覆盖前者的 success |
| C3 | auto-continue 只看最新任务 | `useChat.ts` | `async_tasks` 累积历史，`max(created_at)` 误触发/漏触发 |
| C4 | 硬拦截第二个查询 | `ChatInterface.tsx` | `queryInProgress && isQueryMessage` → toast + return |
| C5 | 进度条假设单任务 | `ChatInterface.tsx` | `activeTask = first in_progress`，无多任务展示 |

## 3. UX 决策（用户确认）

1. **进度展示**：堆叠列表 + 最新置顶（所有并发查询进度同时可见，最新发起的在最上方）
2. **问题识别**：进度条要能识别**每个 nl2sql 查询任务对应的问题** + 该问题的进度，对用户友好
3. **结果呈现**：逐个完成自动呈现 + 可中断（每个完成的查询独立触发续跑；
   同时待续跑的任务数达到上限时暂缓，避免主智能体上下文爆炸）

## 4. 后端改动（D:\code_work_space\llm\nl2sql）

### 4.1 `src/agent/main_agent.py` — 新增 keyed 字段（reducer 合并安全）

`MainAgentState` 加 3 个按 task_id 键控的合并字段（复用 `_tasks_reducer` 的 merge 语义）：

```python
def _merge_dict_by_key(existing: dict | None, update: dict) -> dict:
    merged = dict(existing or {})
    merged.update(update)
    return merged

class MainAgentState(DeepAgentState):
    todos: NotRequired[list]
    query_headers:       Annotated[NotRequired[dict[str, dict]],  _merge_dict_by_key]  # task_id -> {id,content,status,task_id}
    subagent_steps_map:  Annotated[NotRequired[dict[str, list]],  _merge_dict_by_key]  # task_id -> [steps]
    active_queries:      Annotated[NotRequired[dict[str, bool]], _merge_dict_by_key]   # task_id -> True(运行)/False(完成)
    # 旧单值字段保留（供旧前端回退）
    query_header: NotRequired[dict]
    subagent_steps: NotRequired[list]
    query_active: NotRequired[bool]
```

**不重声明 `async_tasks`**：它已由 deepagents `AsyncSubAgentMiddleware` 注入 `_tasks_reducer`。

### 4.2 `src/agent/subagents/sync_subagent_todos.py` — 每任务写自己的 key

- `launch_sync(..., task: dict | None = None)`：接收 `sync_launcher` 传来的 `AsyncTask` 字典
- **标题按任务提取**：新增 `_extract_task_title()`，扫主线程消息找 `start_async_task` 工具调用、
  匹配其 ToolMessage 中的 task_id，返回该调用的 `args.description`（并发时不取错标题）；
  失败回退 `_extract_user_query`。**注意**：最终方案中前端也从消息做同样的提取
  （`polledTaskTitles`），后端 `query_headers` 只是补充，不依赖其完整性
- 各字段均写**单 key**（`values={"query_headers": {sub_thread_id: ...}}`）：
  - `query_headers[task_id]`
  - `active_queries[task_id]`（运行中 true，终止 false）
  - `subagent_steps_map[task_id]`（步骤 id 加 task 前缀 `__subagent_{task8}_{i}__` 防 React key 冲突）
- **async_tasks 竞态修复**：基于传入 task 字典 + run_status 直接写单 key，不再读-改-写整字典
- **退出条件**：不再等"主线程 todos 全 completed"，改为固定宽限计数（20×0.5s=10s）

> **已知限制**：`query_headers` / `subagent_steps_map` / `active_queries` 仍是并发 `update_state`
> 写入，存在**竞态导致部分任务字段丢失**（实测并发 4 任务时 1 个缺失）。因此最终方案中
> 前端**不依赖这些字段的完整性**，从消息 + 子线程自行提取（见 5.2）。`subagent_steps_map`
> 仍保留用于**耗时显示**（含 `(Xs)` 后缀），缺失时回退子线程 todos。

### 4.3 关键发现：`update_state` 必须加 `as_node="__start__"`

前置验证（对运行中 graph 实测）：
- `update_state(values={"query_headers": {taskA: ...}})` **不加 as_node** → 报
  `InvalidUpdateError: Ambiguous update, specify as_node`
- **加 `as_node="__start__"`** → reducer 合并生效，多个 key 都保留

因此 sync 线程所有 `update_state` 统一加 `as_node="__start__"`。
（`async_tasks` 之前能无 as_node 写入，但统一加更保险。）

### 4.4 `src/agent/subagents/sync_launcher.py`

`_maybe_launch_sync` 改为 `launch_sync(main_thread_id, sub_thread_id, agent_name, task_info)`，
把已有的 `AsyncTask` 字典传下去。

## 5. 前端改动（D:\code_work_space\llm\huice\008\harness-deep-agents-ui）

### 5.1 `src/app/types/types.ts`

- `TodoItem.status` 加 `"query"`（原本用 `as any` 伪造）
- 新增 `QueryTask`：
  ```ts
  interface QueryTask {
    task_id: string;
    agent_name?: string;
    title: string;            // 查询标题（去 📋 前缀）
    status: "running" | "success" | "error" | "cancelled" | "pending";
    created_at: string;       // 用于最新置顶排序
    steps: TodoItem[];
  }
  ```

### 5.2 `src/app/hooks/useChat.ts`

**核心设计（最终方案）**：前端**不强依赖后端 keyed 字段**（它们有并发写入竞态），而是：
- **标题**：从主线程消息提取（`start_async_task` 工具调用 → task_id → `【任务目标】`后的用户问题）
- **进度**：从子线程 state 的 todos 提取（按 task_id 隔离，不会识别错问题）
- keyed 字段（`query_headers` / `subagent_steps_map`）仅作**补充回退**，不依赖其完整性

具体实现：

- `StateType` 加 `query_headers?` / `subagent_steps_map?` / `active_queries?` / `async_tasks?`
- **Loop A（2s 轮询）**：
  - 读 keyed 字段 → `polledQueryHeaders` / `polledSubagentStepsMap` / `polledActiveQueries` /
    `polledAsyncTasks`（沿用缓存 ref 模式防 checkpoint 重载丢失）
  - **从消息提取 `polledTaskTitles`**：扫描 `start_async_task` 工具调用，匹配其 ToolMessage
    中的 task_id，从 `args.description` 提取 `【任务目标】` 后的简洁标题（task_id → 标题映射）
  - **从子线程读 `polledSubagentTodos`**：对每个活跃任务（最多 5 个），调
    `client.threads.getState(taskId)` 读其 `values.todos`（作为该任务进度，按 task_id 隔离）
- **派生 `queryTasks` memo**：join `async_tasks` × `taskTitles` × `subagentTodos` × keyed 字段，
  按 `created_at` 降序（最新置顶）：
  - **标题**：优先 `polledTaskTitles`（消息提取），其次 `query_headers`，最后 task_id 兜底
  - **进度（steps）**：优先 `subagent_steps_map`（**含耗时**，后端 sync 从进度文件计算），
    其次子线程 `todos`（无耗时，兜底），最后空
  - **状态**：`active_queries[id]===true` → running，否则 `async_tasks[id].status`
- **`runningQueryCount`** = running 的 queryTasks 数；`queryInProgress` = `runningQueryCount > 0`
- **Loop B（1s auto-continue）按任务 + 并发上限**：
  - refs：`continuedTaskIdsRef(Set)` / `processingRef` / `prevLoadingRef`
  - 每 1s：`processingRef` 且上次 run 结束 → 复位；否则挑**最旧**的终止任务
    （success/error，未 continue 过）：
    - **并发上限**：衡量「待续跑的已完成任务数」（`terminalTasks.length`），超过
      `AUTO_CONTINUE_CAP(3)` 才暂缓 —— **不是子查询 running 数**，否则并发查询多时
      第一个完成的会因其他查询仍在 running 而被无限暂缓
    - 否则：**先** `continuedTaskIdsRef.add(id)`，置 `processingRef`，
      `stream.submit` 单任务续跑消息（含 task_id + 标题，引导主智能体 `check_async_task(task_id)`）
  - 移除旧全局 `autoContinuedRef` 重置逻辑；保留 `hasPendingMainTasks` guard
- **返回值**：加 `queryTasks`、`runningQueryCount`

### 5.3 `src/app/components/ChatInterface.tsx`

- **堆叠渲染**：顶部折叠区加并发查询卡片（`queryTasks.map`），每任务：状态图标 + 标题 +
  状态标签 + 步骤列表；`steps` 空显示"🔄 初始化..."。`queryTasks` 已按 created_at 降序
  → 最新置顶
- **主 todos 与查询进度分离**：`allTodos` 不再注入 `queryHeader`/`subagentSteps`
- **`handleSubmit` 放开并发**：
  - `isLoading` 且是查询 → toast"主智能体正在处理"并 return
  - `runningQueryCount >= HARD_CAP(5)` → toast 阻止（保护上限）
  - `runningQueryCount > 0` 且查询 → **放行** + toast"已加入并发查询"
  - 否则正常发送

## 8. 风险 / 边界

- **标题映射**：前端 `polledTaskTitles` 依赖 tool_call→task_id 匹配，消息压缩可能失效
  → 回退 `query_headers` / task_id 兜底
- **进度竞态**：后端 keyed 字段（`query_headers` / `subagent_steps_map` / `active_queries`）
  有并发 `update_state` 竞态，部分任务字段丢失。最终方案前端**不依赖其完整性**，
  从消息 + 子线程 todos 自行提取；`subagent_steps_map` 仅用于耗时显示，缺失时回退
- **耗时显示**：`subagent_steps_map` 含耗时（`(Xs)`），但竞态可能缺失；缺失任务显示
  子线程 todos（无耗时）。若需保证所有任务耗时，需另修后端竞态（待定）
- **续跑竞态**：`processingRef` 在 submit 前同步置位；submit 抛错则从 `continuedTaskIdsRef`
  移除重试
- **结果关联**：续跑消息带 task_id，主智能体需对该任务调 `check_async_task`（prompt 已支持）
- **图表附随错位风险**：前端 `chartAttachmentHtml` 用**单值** `pendingChart` 追踪"最新生成的
  echarts iframe"，附到下一个"AI 无工具、有正文"的报告消息上（`ChatInterface.tsx` L470-498）。
  正常流程下 Loop B **串行**续跑每个任务（一个 run 处理一个任务的图表+报告），消息流是
  `[A图][A报告][B图][B报告]`，归属正确。但若状态**分批到达**（如 `[A图][B图][A报告]`），
  一次 useMemo 扫描会把 B 的图表错附到 A 的报告上；下次渲染（消息补全）会修正。风险点是
  **短暂错位/闪烁**。若需严格按任务归属，需将 pendingChart 改为按 task_id 键控（当前未做，可接受）。
