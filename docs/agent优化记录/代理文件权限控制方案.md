# 代理文件读写安全控制方案（deepagents FilesystemPermission）

> 日期：2026-08-12（2026-08-28 更新：权限收紧 + execute 护栏，见 §11）
> 状态：已实施并验证（规则模块 + 两处 agent 接线完成；单元断言/启动门槛直测/E2E 全部通过；2026-08-28 收紧版 26/26 + execute 护栏 22/22）
> 涉及项目：nl2sql 后端（`D:\code_work_space\llm\nl2sql`），主 agent（chat_agent）与子 agent（nl2sql_agent），前端不涉及
> 相关机制：deepagents 0.6.12 `FilesystemPermission`（VFS 声明式权限）+ ExecuteGuardMiddleware（execute 中间件护栏）

---

## 1. 背景与目标

主 agent 与子 agent 都由 `create_deep_agent` 构建，deepagents 自动注入 6 个文件工具
（`ls / read_file / write_file / edit_file / glob / grep`，主 agent 另有 `execute`），但此前**从未传过
`permissions` 参数——文件读写全放行**，agent 可随意改写 `src/agent` 下的提示词/技能/记忆等代码与配置。

**目标**：基于 deepagents 的 `FilesystemPermission` 声明式权限规则（虚拟文件系统），约束 agent：
- **只读**：`D:\code_work_space\llm\nl2sql`（agent 侧实际映射为 VFS 根 `src/agent`，见 §3）
- **可读写**：仅 `src/agent\workspace\{report,tmp,nl2sql_process_data}` 三个子目录

零新增依赖、不改 langgraph/deepagents 源码、不改前端。

## 2. 已确认的设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| VFS 根作用域 | **保持 `src/agent`**（不重设到项目根） | agent 可读面 = `src/agent` 全部（其实际需要的那部分）；根外（`.env` 含 DeepSeek 密钥、`docs`、`src/mcp_server`、`.venv`）由 `virtual_mode=True` 路径锚定天然不可达，更安全；三个可写目录与虚拟路径 1:1 映射，改动最小 |
| `execute` 绕过 | **2026-08-28 已用 ExecuteGuardMiddleware 补护栏**（见 §11）；不再是「完全不受控」，但仍是护栏非安全边界 | deepagents 框架仍不支持 execute 的权限控制；在中间件层补拦截（破坏性命令 + 工作区外路径引用），`EXECUTE_GUARD_STRICT=0` 可关路径规则 |

## 3. 需求路径 → VFS 映射

VFS 根 = `D:\code_work_space\llm\nl2sql\src\agent`（`FilesystemBackend(root_dir=src/agent, virtual_mode=True)`）：

| 真实路径 | 虚拟路径 | 权限 |
|---|---|---|
| `D:\code_work_space\llm\nl2sql\src\agent`（整棵，含 prompt/skills/memory/workspace） | `/` | 只读 |
| `...\src\agent\workspace\report` | `/workspace/report/**` | 可读写 |
| `...\src\agent\workspace\tmp` | `/workspace/tmp/**` | 可读写 |
| `...\src\agent\workspace\nl2sql_process_data` | `/workspace/nl2sql_process_data/**` | 可读写 |

## 4. 权限规则（核心实现）

`src/agent/settings/file_permissions.py`（单一事实来源，两处 agent 共用）：

```python
from deepagents import FilesystemPermission

FILE_PERMISSIONS: list[FilesystemPermission] = [
    # 1) 只读整个 VFS 根（显式声明；当前默认 allow 等价，防御默认值变化）
    FilesystemPermission(operations=["read"], paths=["/**"], mode="allow"),
    # 2) 仅这三个 workspace 子目录可写
    FilesystemPermission(operations=["write"], paths=[
        "/workspace/report/**",
        "/workspace/tmp/**",
        "/workspace/nl2sql_process_data/**",
    ], mode="allow"),
    # 3) 其余路径写操作一律拒绝（default allow → 必须显式 deny 兜底）
    FilesystemPermission(operations=["write"], paths=["/**"], mode="deny"),
]
```

**顺序敏感**：deepagents `_check_fs_permission` 按声明顺序首条命中即胜、无命中默认放行——
必须「先 allow 三个写目录、再 deny /** 兜底」，顺序颠倒会导致三个目录也写不了。

## 5. 接入点

- 主 agent：[`src/agent/main_agent.py`](../../src/agent/main_agent.py) 的 `create_deep_agent(...)` 加 `permissions=FILE_PERMISSIONS`
- 子 agent：[`src/agent/nl2sql_agent.py`](../../src/agent/nl2sql_agent.py) 的 `create_deep_agent(...)` 同样加（**独立 graph，不会自动继承**主 agent 权限，必须单独传）

## 6. 机制依据（deepagents 0.6.12，已探明）

- `FilesystemPermission` dataclass（`operations ∈ read|write`，`edit_file` 归 write、`ls/glob/grep` 归 read；`paths` 为 `/` 开头的 glob）：`.venv/Lib/site-packages/deepagents/middleware/filesystem.py:90`
- 解析：声明顺序、首条命中、无命中放行：`filesystem.py:127`
- 权限在**工具层**校验（read/write 各 sync+async 一处）：`filesystem.py:976/1015/1168/1195/1235/1274/1329/1371/1422/1518/1600/1643`
- 注入：`create_deep_agent(permissions=...)` → `FilesystemMiddleware(_permissions=...)`：`graph.py:269`
- **启动门槛**：对「支持执行的后端 + 权限」有 `NotImplementedError` 前置校验（`filesystem.py:863-875`）。主 agent 的 `CompositeBackend(routes={"/": file_backend})` 因所有规则路径以 `/` 开头通过 `_all_paths_scoped_to_routes`（`filesystem.py:158`）；子 agent 后端不支持执行，条件整体为 False——两者均不触发（已用真实配置直测通过）。

## 7. 已知局限（本次不解决，已记录）

- **`execute` 不受权限控制**：主 agent shell 沙箱在 `workspace` 下，可读写 workspace 内任意位置（memory/skills/checkpoint 等），绕过「仅 3 目录可写」。2026-08-28 起由 ExecuteGuardMiddleware 补护栏（§11），但护栏可被命令混淆绕过（`cmd /c del`、变量拼接、编码），**非安全边界**。
- **进程内直接写盘不走文件工具**：图表落盘（`src/agent/utils/path_resolver.py`）、skill_data（`src/agent/middlewares/skill_data.py`）、大结果落盘（`message_slimmer.py` → `/large_tool_results`）不经 `_check_fs_permission`。其中图表落盘与 skill_data 恰好落在允许的 report/nl2sql_process_data 内，无冲突；`large_tool_results` 属框架内部 offload，不拦也不破坏。
- **MCP 工具非文件工具**：`dbmcp_run_sql`（可执行任意 SQL）与图表 MCP 是独立写通道，不在文件权限模型内（如需控 DB 写需另行设计）。

## 11. 2026-08-28 权限收紧 + execute 护栏（方案 A）

> 日期：2026-08-28
> 状态：已实施并验证（权限规则 26/26、execute 护栏 22/22 断言通过；需重启后端生效）

### 11.1 背景

1. 用户要求把权限从「只读全根 + 三目录可写」进一步收紧为：**`/shared` 只读、前端动态选择的工作区可读写、代码根（src/agent/ 除 shared 外）禁止读写**。
2. 实测会话 `01a047bc`：agent 用 `execute("rm /tmp/xxx.txt")` 删除了工作区之外的文件——`FilesystemPermission` 只管文件工具（ls/read/write/edit/glob/grep），**管不住 execute**（`LocalShellBackend` 用 `subprocess.run(shell=True)` 直跑宿主 shell，无沙箱）。方案 B（OpenSandbox 沙箱接线）成本太大，用户明确搁置，选方案 A（中间件护栏）。

### 11.2 权限规则收紧（file_permissions.py）

最终规则（顺序敏感：先 allow、再 deny `/**` 兜底；首条命中即胜、无命中默认放行）：

```python
FILE_PERMISSIONS: list[FilesystemPermission] = [
    FilesystemPermission(operations=["read"],  paths=["/shared/**", "/workspace/**"], mode="allow"),  # 读：共享 + 工作区
    FilesystemPermission(operations=["read"],  paths=["/**"],                          mode="deny"),   # 其余读拒绝（代码根/未知路径）
    FilesystemPermission(operations=["write"], paths=["/workspace/**"],                 mode="allow"),  # 写：仅工作区
    FilesystemPermission(operations=["write"], paths=["/**"],                          mode="deny"),   # 其余写拒绝
]
```

**同步修改**：`src/agent/graphs/nl2sql_agent.py` 的 composite routes 补 `/workspace/` → workspace_data_backend。
原因：CompositeBackend 按最长前缀路由，`/` 路由（代码根，=默认工作区）会吃掉一切非更长前缀路径；
不补这条路由，非默认工作区（如 `D:\workspace1`）的写会落到代码根，与「前端动态选择的工作区可写」矛盾。
（隔离前：`/workspace/...` 走 `/` → shared_code_backend 根目录 src/agent/。）

### 11.3 execute 护栏（ExecuteGuardMiddleware，方案 A）

文件：`src/agent/middlewares/execute_guard.py`（新建）；接线：`src/agent/main_agent.py`（import + `execute_guard = ExecuteGuardMiddleware()`，
middleware 列表放 `QuotaErrorMiddleware()` 之后）。

**原理**：在 `wrap_tool_call` / `awrap_tool_call` 层拦截 `name=="execute"` 的工具调用（与 trace_recorder / message_slimmer 同机制）。
命中拦截规则 → 直接返回 `status="error"` 的中文 ToolMessage，不执行；未命中 → `handler(request)` 透传。

**两条拦截规则**：

| 规则 | 内容 | 开关 |
|---|---|---|
| ① 破坏性命令 | `rm/rmdir/del/erase/rd/deltree/unlink/remove-item/rmtree` + `format/fdisk/mkfs/shutdown/reboot/taskkill/pkill/kill`，词边界匹配（`\bdel\b` 不误伤 `delete`/`model`）。**工作区内 `rm report/old.md` 也拦**——删除一律走受控文件工具 | 常开，不可关 |
| ② 工作区外路径引用 | 命令里出现活跃工作区之外、且不属于 `/shared`、`/workspace` VFS 前缀的绝对路径（POSIX `/etc/passwd`、Windows `X:\xxx`、`../` 越界、`~/` 家目录） | `EXECUTE_GUARD_STRICT=0` 关闭（默认开） |

**放行**：`python save_chart.py`（相对路径）、`python /shared/skills/.../save_chart.py`、`mkdir -p /workspace/tmp /workspace/report`、
`ls -la`、`git status`、`python -m venv .venv`、工作区盘符路径（`D:\workspace1\...`）。

**动态工作区跟随**：`_resolve_roots()` 每次拦截时从 `WorkspaceManager.active_workspace` 重新解析——
前端切换工作区后，护栏的「工作区外」判定基准即时跟随，无需重启。

**验证**（`d:\tmp\test_execute_guard.py`，22/22 PASS）：拦截 `rm /tmp/xxx.txt`、`cat /etc/passwd`、`cd /tmp && rm x`、
`del /q C:\Windows\foo`、`python -c "shutil.rmtree('/tmp/x')"` 等；放行 save_chart / mkdir /workspace / git 等。

### 11.4 定位与边界

这是**护栏，不是安全边界**：
- 命令混淆可绕过（`cmd /c del ...`、变量拼接、`$IFS`、base64 编码）——只拦命令文本里显式出现的路径/动词；
- 拦不住「python 脚本内部读工作区外的文件」。
- 要彻底隔离需方案 B（OpenSandbox 沙箱），已搁置；方案 C（HITL 审批）未实施。
