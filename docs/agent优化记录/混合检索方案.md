# 混合检索实施方案（FTS + 向量 + RRF）

**日期**：2026-09-28
**状态**：**P1 第一段（检索薄层本体 + 验收）已实施**，代码在 `src/agent/retrieval/`（`schema` / `embedder` / `indexer` / `backends/{lance,jsonl}` / `search`），验收 `scripts/verify_retrieval.py` **184/184 通过（两个后端各跑一遍同一套语义断言 + ⓿ 镜像级惰性 import 闸门）**；**默认后端 = LanceDB**（`Dockerfile` 已按 `langchain-qwq` 先例加 `lancedb==0.37.1`），JSONL 为装不出来时的降级路径。**消费点接线与生产索引构建待做**（今天全仓无消费者 ⇒ 默认 off 下完全惰性）。**2026-09-28 生产只读探针核对完成**：语料量级、落点路径、运行环境按实测修正（§2、§3、§9、§12）。
**需求来源**：「目前 nl2sql 检索方式不是向量检索，希望用 lancedb + fts 混合检索」

**一句话方案**：在**工作区下的隐藏目录**挂一份 **per-库钉死的混合索引**（items = schema / cube / 关系 / 知识 / 示例 SQL），**FTS 腿是自写的 idf 加权字符 n-gram**（中文与 ASCII 同一套，二元起 + 子串兜底）、**向量腿走 `192.168.25.13:11435` 的 `bge-m3`（1024 维）**、融合用 **自写 RRF**；索引**只由注册表里的活库构建（单写者）**，问数链路只读；检索薄层落 `src/agent/retrieval/`，逐个接上现有 fast-path 消费点。

> **收益口径**：不在于「加了向量」，而在于把 **278KB 的 schema 全量注入** 与 **135KB 知识（19 文件）的全量读** 换成 top-k，以及**让 `knowledge/sql/` 里那 12 条示例 SQL 变得可被检索**（池子今天是静态的、无检索入口、也不会因反馈增长）。向量腿是可选增益，缺它系统仍可跑（见 §8.1 降级链）。

> **⚠️ 引擎当天翻转过两次，最终 = LanceDB（决策留痕见 §0）**：原定 LanceDB ⇒ 实施期发现语料只有几百条、装它「收益为 0」而改零依赖 ⇒ 当天再测**内存曲线**后翻回 LanceDB（用户拍板**接受改 Dockerfile + 重建镜像 + 停机**）。买它的不是 FTS 延迟（自写腿 18.4ms vs lance-icu 26.8ms，**自写反而更快**），而是 **on-disk mmap 的内存曲线**（自写方案 20k 条时 **776MB/进程**）。**默认 `lance`，装不出来自动退 `jsonl`**（`NL2SQL_RETRIEVAL_BACKEND` 可强制）。§4 / §4.4 / §5.1 / §6 / §9 的表述以 §0 为准。

实施第一段（写 `src/agent/retrieval/` + `scripts/verify_retrieval.py`）时，六条原本写在纸上的前提被实测顶翻。逐条留证：

| # | 原方案 | 实测 | 处置 |
|---|---|---|---|
| 1 | 引擎 **LanceDB**（代价：改 Dockerfile + 重建镜像） | 语料 = **233 条**（本机真项目）/ 生产约几百条 ⇒ Python 全量打分 **1.2~2.8ms/查**、构建 **44ms**、索引 **118KB** | ~~改零依赖~~ ⇒ **第 7 行翻回 LanceDB**：延迟数据成立，但那是「几百条」下的数据，**没算内存** |
| 2 | FTS 腿用引擎的 `ngram(3,3)` / FTS5 trigram，**短查询靠子串兜底** | 自己写打分器就不必受引擎的 3 字符下限：**n-gram 下限取 2** 后两字业务词照常进 idf 加权；只靠子串兜底时那是个**扁平**加分、不参与排序 | 自写打分器，`NGRAM = 2`（`NGRAM_MAX = 6`）。子串通道保留，负责一字词与整串命中。⚠️ **2026-09-28 复测更正**：用引擎也**不必**受 3 字符下限 —— LanceDB 的 3 只是 `ngram_min_length` 的**配置默认值**（调到 2 两字即命中，行 8），**FTS5 trigram 的 3 才是引擎硬下限**。自写打分器现在的理由是「**零依赖降级路径**」，不再是「引擎做不到」 |

| 4 | 索引落点 **`<wren_project>/.index/`**（项目内） | 语义库目录是 **git 版本化且会自动提交推送**；`wren_semantic._local_content_state` 判「有无自建内容」是「根目录除 `wren_project.yml` 外任何条目都算内容（未知文件也算）」 | 改 **`<AGENT_DATA_ROOT>/workspace/.retrieval/<项目目录名>/`**（工作区级、项目外、隐藏目录 ⇒ 不会被 `_scan_wren_projects` 认成语义库） |
| 5 | 语料抽取自己遍历 mdl.json | 真 mdl 的 `models[].properties` / `columns[].properties` **常常整个不存在**（元数据在 `cubes[].measures` / `relationships` 里）；**wren 自己就有** `wren.memory.schema_indexer.extract_schema_items`，八类全覆盖且与全量注入路径 `describe_schema` **同源** | 复用 `extract_schema_items`，只补它丢掉的两样：`displayName`/同义词，以及 **`tableReference` 物理表名**（wren 的 model 文本里没有） |

## 1. 目标与非目标

**目标**

1. schema / cube / 知识 / 示例 SQL 四类语料可**按问题检索**（FTS + 向量 + RRF）。
2. 注入模型的上下文从「全量」变「top-k」，且**开关关闭时与今天逐字一致**。
3. 示例 SQL 池有了产出（修写路径），`recall_queries` 有真实命中。

**非目标**

- 不替换 wren 的语义层与编译器，不改 `mdl.json` 的生成。
- **不把口径核验改成检索**（硬规则 R1）。
- 不在 app 容器（`langgraph-api`）里加载 `sentence-transformers` / torch。
- 本期不做 ANN 选型、不做重排模型（预留接口，见 §4.3）。

## 4. 选型

### 4.1 结论（**2026-09-28 已拍板**）

**LanceDB（自建薄层，不用 wren 的 `MemoryStore`）**，FTS 用 `ngram(3,3)` 起步。**接受代价：改 Dockerfile + 构建一次镜像**（具体动作见 §4.4）。

### 4.2 对比

| 维度 | **LanceDB**（选它） | sqlite-vec + FTS5(trigram)（备选） |
|---|---|---|
| 混合检索 | 原生：`create_fts_index` + `search(query_type="hybrid").rerank(RRFReranker())`；后续可换 `CrossEncoderReranker` | 需自写融合（RRF 约 60 行） |
| 中文 FTS | `ngram(3,3)`（零模型文件）或 `jieba/*`（需 `LANCE_LANGUAGE_MODEL_HOME` 语言模型文件） | FTS5 `tokenize=trigram`（本仓已跑通） |
| 依赖 | `lancedb` 已在 lock；**不拖 `sentence-transformers`/torch** | `sqlite-vec` 已在 lock（stdlib sqlite + 扩展） |
| 与本仓约定 | 新形态（非 sqlite）⇒ 备份/保留/metrics 要另做（R6） | 完全吻合「一库一目录 sqlite + 共享连接 + RLock + WAL」既有约定 |
| 写并发 | **无跨进程写锁保障**（架构文档已列为风险、目标态是 pgvector：`docs/agent优化记录/NL2SQL存储与部署架构方案.md:106`）⇒ 必须单写者 | 一把 RLock 解决 |
| **镜像成本** | **需改 Dockerfile + 构建镜像**（生产镜像里没有 `lancedb`/`lance`，见 §3.1）⇒ 一次新的发版形态 | **零镜像改动**：`sqlite_vec 0.1.9` 已在镜像内 |
| 主要成本 | 单写者纪律 + 每库路径钉死 + 一次并发写实测（R5） | 自己写融合（好处是可确定性测试） |

**选 LanceDB 的理由**：既然 **FTS 腿与 RRF 融合选谁都得自己写**（前提 #3），LanceDB 自带的混合检索与重排口子就是净省下来的代码；`ngram` 不需要额外模型文件。语料 10²~10³ 用不上 ANN 是「不必要」，不是「不合适」。

> **⚠️ 2026-09-28 实测改变了成本对比**：生产镜像里**没有 `lancedb`/`lance`**（当初为省 1.3GB 剥掉 `wrenai[memory]` extra，LanceDB 随之消失），而 `sqlite_vec` **已在镜像内**。于是 LanceDB 的代价多了「改 Dockerfile + 构建镜像」，sqlite-vec 一侧多了「零镜像改动 + 直接复用一库一目录/RLock/WAL 既有约定」。两者都仍需自写融合（LanceDB 换到的是 RRF 与重排器接口）。**已拍板：走 LanceDB**，接受一次镜像构建（§4.4）。

### 4.3 什么时候翻回 sqlite-vec

- 要求索引与其它运行时数据**同构**（同一套备份 / 保留 / metrics / 审计），或要求**零新形态**；
- 需要在同一进程里既写又读、不接受「单写者」约束；
- 压测发现 10⁴ 量级下 LanceDB 的打开/索引开销不可接受。

## 5. 目标架构

### 5.1 分层

```
语义库(wren project, git 版本化)
  ├─ models/*/metadata.yml, cubes/*/metadata.yml        → schema items
  ├─ knowledge/{rules,glossary,metrics,caveats,sql}/*.md → knowledge items / example_sql
  └─ target/mdl.json (278KB@48 models)                    → 索引构建的输入
                 │
        [索引构建]（写路径，单写者；输入只取注册表里的活库）
                 ▼
   <AGENT_DATA_ROOT>/workspace/.retrieval/<项目目录名>/   ← 索引目录（工作区级、**项目外**）
                                                          ← 项目路径取自 db_config.json 注册表
     ├─ items.jsonl        一行一条：id, kind, src_path, title, text, meta_json, rev
     ├─ vectors.bin        float32 顺序拼接（可稀疏）
     ├─ vectors.idx.json   哪些条目有向量（稀疏下标）
     ├─ index.json         元数据：rev / items / vectors / dim / model / kinds / built_at
     └─ rev = sha256(target/mdl.json)[:16]
        FTS 腿 = 自写字符 n-gram（无引擎、无 3 字符下限，见 §0 第 2 条）
                 │
        [检索薄层 src/agent/retrieval/]（问数链路只读）
          hybrid(q, k) = FTS top-k ∪ vector top-k → RRF → 过滤(db_name/kind)
                 │
      ┌──────────┼──────────────┬─────────────────┐
      ▼          ▼              ▼                 ▼
  get_context  recall_queries  search_knowledge  store_query(写)
  （schema）   （示例 SQL）     （口径/术语）      （唯一写入口）
```

### 5.2 设计点（每条对应一个已知事故形态）

1. **路径 per-库钉死**，不用 `~/.wren/memory/` 单槽（前提 #4）。本仓「拿磁盘目录当共享单槽」已出过三次事故（wren 活项目目录 / semantic_db 物化 / skills_versioning 物化）。
2. **单写者**：索引只由「语义库构建 / 更新」写；问数链路只读。理由是 LanceDB 跨进程写锁无保障（§4.2）。
3. **索引是派生物**：键 = `(db_name, mdl_hash | semantic_rev)`；**重建挂在语义库写入/更新路径上**，不要另造「切换」事件当失效入口（失效入口只有「切换」一个，机制一删就漏）。
4. **嵌入不在 app 容器里做**（§8）：检索薄层只做「取向量 → 查库」。
5. **降级链**：向量腿失败 ⇒ 自动降级纯 FTS（fail-open）。「检索变差」绝不允许变成「问数不可用」。
6. **并发写入**：索引目录同时只有一个写者，读侧多进程打开；实现前先做一次两进程同写的实测，确认失败形态与恢复手段（R5）。
7. **索引输入取自注册表，禁止扫目录**：权威源 = `<AGENT_DATA_ROOT>/workspace/db_config.json` 的 `databases[].wren_project`（生产只有一个：`name:"witops"` → `/app/data/workspace/witops_wrenai`）。扫目录会踩到 `witops_wrenai.备份-20260921-182109`（**151 models 的旧库**）与 `/app/data/` 下的 `shared.bak-*.tgz` / `skills.old-*` ⇒ 把备份当活库建索引（本仓同型坑已出过三次）。

### 5.3 索引内容（kind → 来源）

| kind | 来源 | 检索价值 |
|---|---|---|
| `schema_table` / `schema_column` | `<project>/models/*/metadata.yml`（或从 `mdl.json` 拆） | **最高**：现为 602KB 全量注入 |
| `cube` / `measure` / `dimension` | `<project>/cubes/*/metadata.yml` | 高（Cube 通道已在用） |
| `knowledge_rule` / `knowledge_glossary` / `knowledge_metric` / `knowledge_caveat` | `<project>/knowledge/*/*.md` | 高（现为全量读，20.9k 字符） |
| `example_sql` | `<project>/knowledge/sql/*.md`（+ 自动化回写） | 中：生产**已有 12 条**但无检索入口；P0 让它可检索、让它能长 |

## 8. 嵌入通道

**已定：`http://192.168.25.13:11435`（Ollama 专用 `bgem3` 容器）+ `bge-m3:latest`（1024 维）**，OpenAI 兼容面 `/v1/embeddings`。

| 项 | 值 |
|---|---|
| 模型 | `bge-m3:latest`（1.16GB，566M 参数，F16）——**已就位，无需 pull** |
| 维数 | **1024** |
| 延迟口径（热态） | 短文本 **61–85ms/条**；~100 字 chunk **60–120ms/条**；**4 条并发总 166ms**（`OLLAMA_NUM_PARALLEL=4`） |
| 冷启 | **16.8s**（GPU 加载，一次性）；该容器 `OLLAMA_KEEP_ALIVE` 永不驱逐 ⇒ 首调后摊销 |
| 资源占用 | 常驻 GPU0 ~1.1G（`offloaded 25/25 layers`）；GPU2/3 被 vLLM 占满（21.8G/23G）不受影响；该机 4×RTX 4090、内存 251G、磁盘可用 539G |
| 该机其它服务 | `:11434` = 另一个 Ollama 实例（Langfuse judge 用 `…/v1` 跑 `qwen3.8:27b`）；`:8100` = vLLM（只服务 27B，**无 `/v1/embeddings`**）；`:8000` GraphRAG；`:8200` mineru；另有 k8s 节点 |
| 白名单 | `192.168.25.13` 已在 Langfuse SSRF 白名单内；本仓 `net_guard` 的私网放行口径也覆盖它 |

**接线约束**

- **固定 `:11435`，不用 `:11434`**：后者 `OLLAMA_MAX_LOADED_MODELS=1` ⇒ bge-m3 与 judge 的模型**互驱**；索引期 bge-m3 常驻会把 27B 反复踢出，重载代价极高。`:11435` 是同镜像专用实例，代价仅首次冷启。
- **不要走 `:8100`**（实测 `/v1/embeddings` → 404）。
- 问数期每问 **1 次**嵌入调用；必须带超时；**不可用 ⇒ 降级纯 FTS**（fail-open）。
- 索引期批量嵌入：**限流 + 分批 + 单批超时**；该机是共享主机（k8s / mysql / kafka / GraphRAG / 另一个 vLLM），要能容忍对方重启。
- **不假设 GPU 必然可用**：这台机不是我们的，容量与占用会变 ⇒ 降级链是硬要求，不是优化项。

### 8.1 降级契约（嵌入不可用时会发生什么）

**底线：嵌入通道不是可用性依赖，只是质量增益。** 三级降级链，任何一级失败都往下掉，**绝不让问数失败**：

| 级别 | 触发条件 | 行为 | 代价 |
|---|---|---|---|
| **L0** | 一切正常 | FTS + 向量 + RRF | — |
| **L1** | **查询期**嵌入失败/超时（连接失败 / 冷启超时 / 模型缺失 / 维数不符） | **纯 FTS** + 短查询子串兜底（R7） | 语义改写的问法召回下降（问「人员效率」而库里只有「工时」）；**字面词命中不受影响** |
| **L2** | 索引缺失 / 损坏 / 从未构建 | **回落今天的全量注入** —— `get_context` 保持 `strategy:"full"`、`recall_queries` 返回 `[]` | ＝**今天的行为，逐字一致** |

**按阶段的容错要求**：

- **索引构建期**（一次性，10²~10³ 条 items）：嵌入不可用 ⇒ **允许建出「无向量」的 FTS-only 索引**（`vector` 列可空），向量稍后 backfill。**构建不许因嵌入挂了整体失败**。
- **增量写入期**（`store_query` / goodcase 回写）：同样先落 FTS 可检索的 items，向量缺省待补。
- **查询期**：嵌入调用**必须带硬超时**（建议 2~3s，远小于工具超时 300s）；超时即降 L1。**不许把 300s 花在等嵌入上。**

**三条必须实现的护栏**：

1. **维数 / 模型校验**：索引元数据记 `dim` 与 `model` 名；查询向量与之不符 ⇒ **拒绝向量腿只做 FTS**（换模型会让 1024 变别的维数，不校验则相似度**静默错乱**——不报错，只是排序变垃圾）。
2. **冷启预算**：`.13` 上 bge-m3 冷启实测 **16.8s**（容器重启后首调）⇒ 要么在服务启动/健康检查时**预热**一次，要么让首问走 L1。**16.8s 不能压在单次问数上**。
3. **DR：模型丢了我们修不回来**。`.13` **无外网**、registry 不可达 ⇒ **bge-m3 一旦从那台机消失，无法自行重拉**（该机还有别的团队的 vLLM/k8s/GraphRAG，改用途、占端口都可能）。两条保险：① 备份 `.13` 上 `/icp-data/sulin_data/ollama_bgem3/` 的 blob（~1.16GB）；② **64 有外网**，在 64 上起 Ollama 把 `bge-m3` pull 下来当**备用通道/镜像源**（base_url 一换即可，`/v1/embeddings` 形状不变）。

**最坏情况**：`.13` 彻底不可用 ⇒ 退化成 FTS + 子串匹配 —— 中文短词照样命中（本就走子串兜底），只是「换个说法问同一件事」的召回变差。**功能可用，质量下降**；不会变成「问数挂掉」。

**备选通道（按代价排序）**

| 选项 | 评价 |
|---|---|
| 64 上自建 Ollama | 备选。64 有外网可 pull，但占 64 的磁盘与运维面；有现成的 `.13` 时不用 |

## 9. 索引构建与失效

- **写入口唯一**：`retrieval/indexer.py`。调用方 = 语义库构建/更新路径 + `store_query`（示例 SQL 增量）。
- **索引键**：`rev = (db_name, mdl_hash | semantic git rev)`；rev 变化 ⇒ 整库重建（幂等）；示例 SQL 增量可只 append。
- **落点**：**`<AGENT_DATA_ROOT>/workspace/.retrieval/<项目目录名>/`**（生产 ≈ `/app/data/workspace/.retrieval/witops_wrenai/`）——**在工作区下、绝不在 wren 项目目录内**（理由见 §0 第 4 条：项目目录是 git 版本化且自动提交推送；`_local_content_state` 把「未知的新条目」算作自建内容）。⚠️ **不要按 db_name 拼目录名**——注册表 `name: "witops"` vs 目录 `witops_wrenai` **不同名**，项目路径一律从 `db_config.json` 的 `databases[].wren_project` 取。per-库钉死，禁用 `~/.wren/memory/` 单槽。
- **失效入口挂在写路径上**，不挂在「切换」等事件上（设计点 3）。
- **备份与保留**：索引目录进备份/保留策略（R6）；索引损坏 ⇒ 直接重建（派生物，绝不是唯一真相源；真相源永远是语义库）。
- **体积预算**：**实测 118KB / 233 条**（本机真项目）⇒ 生产几百条量级约 **数百 KB**，可忽略；零依赖 ⇒ **没有 lancedb 那 1~2GB**（§0 第 1 条）。

## 11. 硬规则

| # | 规则 |
|---|---|
| **R1** | **口径核验绝不能被检索窄化**。检索只服务「注入给模型的上下文」；`load_knowledge_corpus`（[caliber_evidence.py:339-387](../../src/agent/utils/caliber_evidence.py#L339-L387)）必须继续看**全量**语料，否则「证据不在库」会变成假判决（报告口径要逐字原文，此契约已被证伪过两次） |
| **R2** | **默认开关 = 旧行为逐字不变**（照 `scripts/verify_failure_signal.py` 范式：每段带**负对照**，锁住「无开关时与今天一致」） |
| **R3** | 不要只翻 `WREN_MEMORY_BACKEND`（§7 陷阱） |
| **R4** | 若最终选 sqlite 形态：新 store 要补 `sqlite_paths.STORE_NAMES` + `retention.py` 的 `/metrics` 字节数与按龄清理表两处硬编码 |
| **R5** | ~~LanceDB 并发写实测~~ → **随引擎变更失效**（零依赖形态下写入口只有一个进程内函数，无跨进程写问题）。若将来真换 LanceDB，这条**重新生效** |
| **R6** | 索引目录要进备份/保留策略；索引损坏 ⇒ 可重建（派生物） |
| **R7** | **中文短查询必须走子串兜底**：FTS5 trigram 与 LanceDB `ngram(3,3)` 都以 **3 字符**为最小单位 ⇒ **两字中文查询 MATCH 恒为空**（生产容器实测：`MATCH '工时'`→`[]`、`MATCH '部门'`→`[]`，而 `MATCH '本月工'`→命中）。而「工时 / 部门 / 项目」正是问数里最高频的词。⇒ **本层自写打分器后已从根上绕开**（n-gram 下限取 2，见 §0 第 2 条）；子串通道仍保留（管一字词与整串命中）。**若哪天换回引擎 FTS，本条重新生效** |
| **R8** | 索引构建的输入取**注册表活跃库**，禁止扫目录（设计点 7） |
| **R9** | **嵌入通道不得成为可用性依赖**：三级降级链（L0 混合 → L1 纯 FTS → L2 回落全量注入）任何一级失败都往下掉，**问数必须成功**；嵌入调用带硬超时（2~3s）；索引允许「无向量」存在且可 backfill；索引元数据记 `dim`/`model` 做校验（§8.1） |
| **R10** | **检索层不许在 import 期依赖任何第三方**：`lancedb` 是「将来才可能有」的包，**一切第三方 import 必须在函数内惰性进行**（`wren.memory.schema_indexer` 也已按此处理）⇒ 代码可以先于依赖发版，缺依赖只损失功能、不毁 agent |
| **R11** | **n-gram 下限 = 2，且 ASCII 标识符要按 `_` 切开**（§0 第 2、3 条）。这两条都是真语料上「静默返回空」的成因，改回去会让整个检索在中文两字词与带后缀表名上**看起来正常但零命中** |
| **R12** | **索引语料必须与全量注入同源**（`extract_schema_items` / `describe_schema`）——否则「检索没给」与「库里没有」会混淆，而这正是口径类事故的成因（R1 的同类）。补字段（业务名/物理表名）只许**加法** |

## 13. 风险与回退

| 风险 | 处置 |
|---|---|
| 选 LanceDB 需改镜像（**已接受**），构建受阻或拖入重依赖 | 只加 `lancedb==0.37.1`（闭包 +7、**不带** torch，§4.4）；构建不可行 ⇒ 翻 sqlite-vec（§4.3，零镜像改动） |
| 向量腿不可用（`.13` 停机 / 被他人改用途 / 网络抖动） | 降级纯 FTS，功能不降级；`:11434` 作为备选实例 |
| LanceDB 跨进程写冲突 | 单写者 + 写前实测（R5）；真冲突 ⇒ 翻回 sqlite-vec（§4.3） |
| 检索窄化导致口径假判决 | R1 + `verify_caliber_evidence` / `verify_report_caliber` 作为硬闸 |
| 索引与新语料不同步 | 重建挂在写路径上（设计点 3）；rev 不匹配即重建 |
| 检索质量不够（top-k 漏掉关键表） | P4 用 goodcase golden set 定量；兜底保留 `strategy:"full"` 开关 |
| app 容器内存增长 | 嵌入不进 app 容器（设计点 4）；索引按需 mmap |

**回退**：全部改动由一个显式开关控制（默认关 = 今天行为）；关闭后四个 fast-path 走原路径、`get_context` 恢复整份注入，索引目录可直接删除，语义库不受影响。
