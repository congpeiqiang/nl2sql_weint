# 新增语义库 — 实现方案

## 一、功能概述

在现有语义库管理模块（"从 Git 拉取" + "关联本地目录"）基础上，新增**"新增语义库"**能力，支持从零创建一个 Wren 语义库项目。

## 二、总体流程

```
Step 1         Step 2          Step 3          Step 4          Step 5
选择数据库  →  提取表结构  →  生成模型+模板  →  校验+构建  →  应用/上传Git
```

## 四、后端新增 API

在 `src/api/wren_semantic.py` 中新增以下路由：

| 路由 | 方法 | 说明 |
|------|------|------|
| `/api/wren-projects/create` | POST | 创建空项目骨架 |
| `/api/wren-projects/{name}/introspect` | POST | 连接数据库，提取表结构 |
| `/api/wren-projects/{name}/generate-models` | POST | 按选中表生成 models/relationships |
| `/api/wren-projects/{name}/knowledge/template` | GET | 获取所有业务知识模板内容 |
| `/api/wren-projects/{name}/knowledge/save` | POST | 保存业务知识 |
| `/api/wren-projects/{name}/open-directory` | POST | 在资源管理器中打开项目目录 |
| `/api/wren-projects/{name}/push` | POST | 推送至 Git 远程仓库 |

### 4.1 `POST /api/wren-projects/create`

```json
// Request
{
  "project_name": "my_project",
  "db_name": "clickhouse",
  "description": "可选描述"
}
// Response
{
  "ok": true,
  "project": { ... },
  "path": "D:/.../workspace/my_project"
}
```

后端逻辑：
1. 校验 `project_name` 不冲突
2. 在 `semantic_dir` 下创建目录
3. 生成 `wren_project.yml`（从目标库的 `db_type` 推导 `data_source`）
4. 生成 `config/connection_{db_type}.json`（从 `db_config_store` 解密连接信息）
5. 初始化空目录：`models/`, `knowledge/`（含 `glossary/`, `metrics/`, `rules/`, `sql/`, `caveats/`）, `views/`, `cubes/`, `target/`
6. 生成 `knowledge/knowledge.yml`（`schema_version: 1`）
7. 生成 `knowledge/rules/general.md`（模板占位）

### 4.2 `POST /api/wren-projects/{name}/introspect`

```json
// Request
{ "db_name": "clickhouse" }  // 可选，默认用创建时的关联库
// Response
{
  "ok": true,
  "tables": [
    {
      "name": "aix_crystal_comm_data",
      "comment": "通信数据表",
      "columns": [
        { "name": "id", "type": "VARCHAR", "wren_type": "VARCHAR", "nullable": true, "comment": "主键uuid" }
      ],
      "primary_key": null,
      "row_count": 123456
    }
  ],
  "foreign_keys": [
    { "source_table": "...", "source_column": "...", "target_table": "...", "target_column": "..." }
  ]
}
```

后端逻辑 — 新建 `src/agent/utils/db_introspect.py` 模块：

```python
# 核心抽象
def introspect_database(db_config: DBConfig) -> IntrospectResult:
    if db_config.db_type == "clickhouse":
        return _introspect_clickhouse(db_config)   # HTTP 查 system.tables/columns/foreign_keys
    elif db_config.db_type == "mysql":
        return _introspect_mysql(db_config)         # SQLAlchemy inspect + INFORMATION_SCHEMA
    elif db_config.db_type == "postgres":
        return _introspect_postgres(db_config)      # SQLAlchemy inspect + information_schema
```

- ClickHouse 策略直接复用 `gen_models.py` 中的 HTTP 查询逻辑（`system.tables`, `system.columns`, `system.foreign_keys`, `system.keys`）
- MySQL/PostgreSQL 策略复用 `gen_models_mysql_bak.py` 中的 SQLAlchemy inspect 逻辑
- 类型映射统一使用 `TYPE_MAP`（与 `gen_models.py` 一致）

### 4.3 `POST /api/wren-projects/{name}/generate-models`

```json
// Request
{
  "selected_tables": ["aix_crystal_comm_data", "aix_crystal_record_data"],
  "selected_columns": { "aix_crystal_comm_data": ["id", "name"] },
  "include_relationships": true,
  "patch_existing": false,
  "prune": false
}
// Response
{
  "ok": true,
  "generated": { "models": 2, "removed": 0, "relationships": 1 }
}
```

- 对每个选中表生成 `models/{table_name}/metadata.yml`
- `selected_columns` 缺省 ⇒ 该表全列可见（老行为，向后兼容）；给了 ⇒ 不在列表里的列写 `is_hidden: true`
- 如果 `include_relationships=true`，生成 `relationships.yml`
- `patch_existing=true` ⇒ 已存在的模型文件**原地改隐藏开关**，不重写（保住手改的描述）；`prune=true` 必须与它同时使用，删掉未选中的表目录
- 写入逻辑复用 `gen_models.py` 的 `write_model` 模式

详见第九节。

```json

```

后端执行 `os.startfile(str(project_path))`（Windows）或 `subprocess.run(["open", str(project_path)])`（macOS）。

### 4.7 `POST /api/wren-projects/{name}/push`

```json
// Request
{
  "remote_url": "https://github.com/org/repo.git",
  "branch": "main",
  "tag": "v1.0.0",
  "commit_message": "初始化语义库"
}
// Response
{ "ok": true, "message": "推送成功" }
```

后端逻辑：
1. 如果项目目录下无 `.git`，执行 `git init` → `git remote add origin` → `git add -A` → `git commit` → `git push --set-upstream`
2. 如果已有 `.git`，执行 `git add -A` → `git commit` → `git push`
3. 如果指定了 `tag`，额外执行 `git tag <tag>` → `git push origin <tag>`
4. 复用 `git_repo.py` 的 `_run` 和 `validate_repo_url`

## 八、关键设计决策

1. **"打开文件"**：通过 `os.startfile()` 打开系统资源管理器，用户可直接编辑文件后点"保存"按钮触发生效
2. **Git 上传**：复用 `git_repo.py` 的 `_run`（`subprocess` + `shell=False`），安全校验只允许 http(s) URL
3. **安全**：项目目录必须在 `semantic_dir` 内，连接信息从 `db_config_store` 解密后生成 `connection_*.json`
4. **兼容**：新增功能与现有"从 Git 拉取"、"关联本地目录"完全并列，互不影响
5. **重启提示**：同现有语义库操作，新增/修改后提示需重启后端（Wren MCP server 是进程级单例）

## 九、按表/字段构建（废弃表、废弃字段）

不止「选哪些表」，还要「选这些表的哪些字段」—— 有些列已经废弃，不该让模型看见。

### 9.1 字段隐藏用 `is_hidden`，不是 `hidden`

wren 只认 `is_hidden: true`：`metadata.yml` 里写它，`wren context build` 出来的 `target/mdl.json` 才是 `isHidden: true`，引擎才会真正把这一列从 `SELECT *`、从可引用列里剔除。

写 `hidden: true` **不起任何作用** —— 它不在 wren 的 YAML→JSON 键名映射表里，会被原样搬成一个没人读的 `hidden` 键。**这个坑值得记住：标了 `hidden` 的列，模型照样看得见。**

### 9.2 结构列必须保持可见（主键 / 表关联列）

`relationships.yml` 的 `condition` 是 `a.id = b.a_id` 这种**列名文本**，所以：

- **列不能删，只能隐藏**。删列会让 `wren context build` 直接报错。
- **被关系引用的列不能隐藏**。隐藏后 `wren context build` 照样成功，但之后**每次 JOIN** 都报 `Schema error: No field named a.id` —— 构建期看不出来，查询时才炸。所以界面上这类列连主键一起灰掉、不给勾。
- 一个连带效果：`SELECT <隐藏列>` 在 dry-plan 下**不报错**，会被编译成退化查询。**「dry-plan 没报错」不等于「列还在」**，验收要看 `SELECT *` 的输出和 mdl.json。

### 9.3 新建流程与已有库调整走两条路径

| | 新建（Step 2） | 已有库（卡片「⚙️ 调整模型」） |
|---|---|---|
| 已存在的模型文件 | 重写（`patch_existing=false`） | **原地打标**（`patch_existing=true`），只改隐藏开关这一行 |
| 未勾选的表 | 不生成 | 默认**不删**；显式勾「同时删除」才 `prune` |
| `relationships.yml` | 按外键重建 | 默认**不动**（按外键重建等于给已有库悄悄加进一批 join，要就显式勾） |
| 库的当前状态来源 | —— | `introspect` 响应新增的 `existing_models` 键 |

原地打标为什么不用 `yaml.safe_load` + `dump`：实测 48 个生产模型文件里有 12 个的长 `description` 会被 `dump` 按 80 列重排，改一个开关会捎带一堆无关 diff。改成在文本里定位 `- name: <列>` 块、插入/删除一行；**认不出来就报错，绝不猜**。

### 9.4 校验前置（fail-closed）

`_validate_column_selection` 在**动文件之前**跑，拒绝三种选择并返回哪张表哪一列为什么：不存在的列、被隐藏的主键、被本次会写出的关系引用的列。被拒绝时**一个字节都不落盘**。前端也做同一套判断（灰掉而不是等后端 400），后端文案原样透出让用户看到。

### 9.5 关系过滤判据的修正

选表时跳过关系的老判据是「**两端都没选中**才跳过」（`and`）。只取消勾选一侧时，`relationships.yml` 仍会写上这条关系，而它引用了不存在的模型 ⇒ `wren context build` 报 `references unknown model` 并中止。已改成「**任一端没选中就跳过**」（`or`），与写模型时的可写集合严格一致。

### 9.6 前端复用已导出的 API，不新增接口

读：`introspectTables()`（多出来的 `existing_models` 用类型收窄断言取，与既有的 `untracked_changes` 同一手法）。

写：`generateModels()`（payload 用 `as Parameters<typeof generateModels>[1]` 断言带上 `selected_columns` / `patch_existing` / `prune`，`JSON.stringify` 会原样透传）。

条状的列清单 UI（`TableSelectionList`）在新建流程与「调整模型」两处共用。
