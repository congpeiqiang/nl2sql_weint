# SQL 性能优化技能调研报告与设计方案

> 生成时间：2026-08-03
> 数据来源：sqlglot 30.12.0 / sqlfluff 4.2.2 实测 + nl2sql 子智能体架构分析

---

## 1. 概述

用户需求：在 nl2sql 过程编排流程（sql-of-thought 技能流）中，**新增一个 SQL 性能优化技能环节**，插入在 `nl2sql-correction` 环节之前。

本报告调研了通用 SQL 优化工具（sqlglot / sqlfluff，不依赖阿里云），并基于 nl2sql 子智能体的实际架构约束，给出技能设计方案。

## 2. 工具调研结果

### 2.1 sqlglot（30.12.0）— 已安装，被 wrenai 依赖

**核心能力（全部实测验证通过）：**

| 能力 | 说明 | 实测结果 |
|------|------|---------|
| 方言支持 | 32 种方言（MySQL/Postgres/ClickHouse/Snowflake 等） | ✅ |
| SQL 解析 | `parse_one` 返回 AST | ✅ |
| 方言转译 | MySQL→Postgres 等 | ✅ |
| 优化器 | `sqlglot.optimizer.optimize`（简化/消除子查询/谓词下推/列裁剪） | ✅ |
| 表达式分析 | 检测函数包裹列、CAST、OR 条件、LIKE 通配符、NOT 条件 | ✅ |

**性能检测能力（8 类规则全部实测通过）：**

| 检测规则 | 说明 | 实测 |
|---------|------|:---:|
| SELECT * | 应明确列出所需列 | ✅ |
| DELETE/UPDATE 无 WHERE | 危险操作 | ✅ |
| JOIN 无 ON 条件 | 笛卡尔积风险 | ✅ |
| 子查询 | 可改写为 JOIN | ✅ |
| SELECT 无 LIMIT | 可能返回大量数据 | ✅ |
| DISTINCT | 可优化 | ✅ |
| 函数包裹列 | 如 `YEAR(created_at)` 导致索引失效 | ✅ |
| NOT IN | 可改写为 NOT EXISTS | ✅ |

**优化器实测：**
- `simplify`：`WHERE 1=1 AND a=a` → `WHERE a=a`
- `eliminate_subquery`：`SELECT * FROM (SELECT * FROM users) t` → 消除冗余子查询
- `predicate_pushdown`：谓词下推到子查询内
- `column_pruning`：列裁剪

### 2.2 sqlfluff（4.2.2）— 已安装（官方源）

**核心能力（实测验证通过）：**

| 能力 | 说明 | 实测 |
|------|------|:---:|
| Linter | 输出规则违规（LT13/AM04/RF02/AL01/AM05 等） | ✅ |
| 方言支持 | 28 种方言（mysql/postgres/sqlite/ansi 等） | ✅ |
| 性能相关规则 | AM08（隐式交叉连接）、AM09（LIMIT 无 ORDER BY）、RF02（未限定 SELECT *）等 | ✅ |

**性能相关规则（实测）：**
- `AM08`：隐式交叉连接（笛卡尔积）
- `AM09`：LIMIT/OFFSET 无 ORDER BY（结果不确定）
- `RF02`：多表 SELECT 中未限定 `*`
- `AM05`：JOIN 子句未完全限定
- `AL05`：别名未使用

## 3. 关键架构约束（重要发现）

**nl2sql 子智能体无法运行 Python 脚本。**

通过分析 `nl2sql_agent.py` 和 deepagents 框架源码确认：

- nl2sql 子智能体使用 `FilesystemBackend`，它**只实现 `BackendProtocol`**（提供 `ls/read/write/edit/grep/glob` 文件工具）
- **不实现 `SandboxBackendProtocol`**，因此 `execute` 工具会返回错误
- 子智能体的工具集 = WrenAI MCP 工具（run_sql/dry_run/get_context 等）+ 文件工具
- **没有 execute / Python 工具**

**结论：sqlglot/sqlfluff 无法在 nl2sql 子智能体内部直接调用。**

## 4. 技能设计方案

### 4.1 方案对比

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. 纯 LLM 技能** | SKILL.md 指导 LLM 基于规则手动检查 SQL | 无需开发工具，立即可用 | 依赖 LLM 推理，不如程序化准确 |
| **B. 新增 MCP 工具** | 开发封装 sqlglot/sqlfluff 的 MCP 服务器 | 程序化、准确、可复用 | 需要开发 MCP 服务器 |
| **C. 混合方案（推荐）** | SKILL.md 指导 + 规则集参考 | 立即可用 + 规则完整 | 仍依赖 LLM 推理 |

### 4.2 推荐方案：C（混合方案）

设计 `nl2sql-performance-optimization` 技能，核心是 **SKILL.md 指导 LLM 基于完整规则集手动检查 SQL**，规则集来自已验证的 sqlglot/sqlfluff 检测能力。

### 4.3 技能结构

```
/workspace/skills/nl2sql/nl2sql-performance-optimization/
├── SKILL.md                    # 技能主文件（触发条件、流程、规则）
└── references/
    └── performance-rules.md    # 性能检测规则集（来自 sqlglot/sqlfluff 验证）
```

### 4.4 插入点

在 `nl2sql-sql-generation` 生成 SQL 并 `dry_run` 成功后、`run_sql` 执行前插入：

```
Step 5: nl2sql-sql-generation  → 合成可执行SQL + dry_run 验证
Step 5.5: nl2sql-performance-optimization  → 性能优化（新增）
Step 6: run_sql(sql)           → WrenAI 执行
Step 7: [可选] nl2sql-correction → 失败时纠错循环
```

**定位区分：**
- `nl2sql-correction`：SQL **执行失败**时纠错（正确性）
- `nl2sql-performance-optimization`：SQL **执行成功但可优化**时优化（性能）

### 4.5 性能检测规则集（核心内容）

基于 sqlglot/sqlfluff 验证的规则，设计 10 类检测规则：

| # | 规则 | 检测方式 | 优化建议 |
|---|------|---------|---------|
| 1 | SELECT * | AST 检测 `exp.Star` | 明确列出所需列 |
| 2 | SELECT 无 LIMIT | AST 检测无 `exp.Limit` | 添加 LIMIT |
| 3 | JOIN 无 ON 条件 | AST 检测 `exp.Join` 无 on | 添加 ON 条件 |
| 4 | 子查询 | AST 检测 `exp.Subquery` | 改写为 JOIN |
| 5 | 函数包裹列 | AST 检测 `exp.Func` 包裹 `exp.Column` | 避免索引失效 |
| 6 | NOT IN | AST 检测 `exp.In` + `exp.Not` | 改写为 NOT EXISTS |
| 7 | DISTINCT | AST 检测 `exp.Distinct` | 评估是否必要 |
| 8 | LIKE 前缀通配符 | AST 检测 `exp.Like` 以 `%`/`_` 开头 | 避免索引失效 |
| 9 | OR 条件 | AST 检测 `exp.Or` | 考虑 UNION ALL |
| 10 | LIMIT 无 ORDER BY | 检测 LIMIT 但无 ORDER BY | 添加 ORDER BY |

### 4.6 输出格式

技能输出优化建议列表（JSON 格式），供子智能体决定是否采纳：

```json
{
  "sql": "原始SQL",
  "optimized_sql": "优化后的SQL（如有）",
  "issues": [
    {
      "rule": "select_star",
      "severity": "high",
      "message": "SELECT * 应明确列出所需列",
      "suggestion": "SELECT id, name, age FROM users"
    }
  ],
  "summary": "共发现 2 个性能问题，1 个高风险"
}
```
