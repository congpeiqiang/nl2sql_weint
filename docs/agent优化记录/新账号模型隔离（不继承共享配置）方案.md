# 新账号模型隔离：不继承共享大模型，必须自己新增（含管理员账号）

**日期**：2026-09-28
**需求**：「新创建的账号，不需要继承原有的大模型，要求新增自己的大模型；新增的账号是管理员账号也要隔离大模型。」
**推翻的旧拍板**：2026-09-25「新用户与 admin 的模型一致 = 期望行为，保持现状」（见 memory `model-config-user-first-seed`，已同步改为新决定）。

---

## 1. 现象与根因

新建账号首次登录后，「设置 → 模型」里**直接显示 admin 的那几个 provider**（api_key 显示 `****` 但服务端能用）⇒ 该账号可以直接问数，**额度记在 admin 名下**。新建的**管理员**账号同样如此。

根因有**两层**，只修第一层需求只做到一半：

| # | 位置 | 行为 |
|---|---|---|
| ① 播种（表层） | `agent/settings/model_config_store.py::get_user_store` | 用户文件不存在/0 字节时，把**共享 `model_config.json` 整份拷贝**过去（日志「首次初始化：从共享配置拷贝 N 个 provider」）。这是"界面里出现别人的 provider"的唯一来源。 |
| ② 静默回落（深层） | `agent/llms/model.py::deepseek_model`（模块级，`create_model()` **不带 user_id** ⇒ 读全局/共享 store）+ `middlewares/thinking_toggle.py` 里 `if model is None: return request` | 删掉①之后，账号没配模型时 `create_model` 返回 `None`，中间件**保留图节点自带的那个共享模型** ⇒ 依然拿别人的 key 打模型，只是界面不再显示。前端空配置时**根本不发** `llm_route/llm_model`，走的正是这条链。 |

另有两个**绕开前端门禁**的入口会真打到后端（前端 `ChatInterface.tsx` 的 `modelConfigured` 拦不住它们），所以必须在**服务端** fail-closed：
- `useChat` 的「子任务完成自动续跑」（不带 configurable 里的模型参数）；
- `ExperimentForm`（后端实验端点全是 `require_admin`，本方案不动）。

---

## 2. 改动

### A. 删掉播种（`src/agent/settings/model_config_store.py`）

- `get_user_store()` 里「从共享整份拷贝」整段删除；用户文件不存在时拿到的就是**空 store**（`ModelConfigStore` 对不存在的路径即空配置，**不落盘空文件**）——语义等同"用户自己把 provider 删光"。
- `_shared_config_path()` 删除（唯一调用点就是那段播种）。
- 新增 `reset_user_stores()`：**仅供验收脚本**清进程级缓存用。
- ⚠️ **不回溯清理**已有账号的存量副本：那是历史播种出的快照，删掉会把"本来能用"的账号变成"没有模型"。

### B. 无模型时 fail-closed（`src/agent/middlewares/model_required.py`，新增）

照 `quota_error.py` 的成熟范式：**不抛异常**，直接返回一条带友好文案的 `ModelResponse`（不带 `tool_calls` ⇒ 模型节点后直接 END）⇒ agent 正常收尾、消息进 checkpoint、前端按普通 AI 回复渲染，界面不卡不空转。

- **判据只有一份**：`agent/llms/model.py::has_usable_model(user_id)`，内部就是 `_resolve_llm_config(None, None, user_id)` 的非空判断（与 `create_model` 同一条解析链）。**不要**在别处另写「provider 个数 > 0」——半个配置（填了 base_url 没填 api_key）在那条弱判据下会"通过"，然后 `create_model` 返回 `None` 再被上层回落成别人的模型。
- **挂载**：两个图各挂一次，都在**最外层**（命中时连模型实例都不构造）——`main_agent.py` 的 `middleware=[...]` 首元素、`nl2sql_agent.py` 的 `_middleware.insert(0, ...)`。
- **无 `user_id` 时不拦**（维持旧行为）：AUTH_DISABLED 本地开发、离线实验 / Langfuse evaluator 等无身份批处理面仍读全局 store。
- 身份来源：`configurable.user_id`（由 `api/langfuse_metadata.LangfuseMetadataMiddleware` 强制钳制成本人登录身份，伪造无效；**异步子 agent** `deepagents_async_config_patch` 与**同步续跑** `sync_subagent_todos` 都透传 ⇒ 子 agent 同样拦得住）。
- 同时给 `thinking_toggle.py` 的 `if model is None: return request` 加注释：该分支现在**只**服务"无登录身份"的路径。

### C. 两处按账号解析（后端）

| 位置 | 改动 | 缺模型时的降级（原有） |
|---|---|---|
| `api/auto_title.py` | `_get_title_model(user_id)`，单例改**有上限的 per-user 缓存**（64，超出整体清空）；handler 里 `require_user(request)["user_id"]` | 返回 `{"error": "模型不可用"}` ⇒ 前端用问题原文当标题 |
| `api/thread_compact.py` | `_generate_summary(messages, user_id)`；`compact_thread` 里 `require_thread()` 的返回值顺带取 `user_id` | `_fallback_summary` 截断摘要 |

报告侧（`tools/report_builder.py`）原本就已按账号传 `user_id`，未改。

### D. 前端文案（`harness-deep-agents-ui`，需单独 rebuild 发版）

- `ModelConfigDialog.tsx` 空态：删掉已过期的「.env 的默认模型会在后端首次启动时自动迁入」，改为「模型配置按账号独立，只对本账号生效，不会继承其他账号的配置」。
- `ChatInterface.tsx` 门禁提示追加「（模型配置按账号独立，不与其他账号共用）」。
- `UserManagementPanel.tsx` 新增用户弹窗加提示：新账号（含管理员）**不继承**现有账号的大模型，需自行新增，否则无法发送消息。

## 3. 判据链（改代码前先看这里）

```
前端 GET /api/model-configs  →  require_user → get_user_store(user_id)   （空的 ⇒ 禁发）
服务端 run                   →  ModelRequiredMiddleware.is_blocked()
                                → current_user_id()（configurable.user_id / langgraph_auth_user_id）
                                → has_usable_model(user_id)
                                → _resolve_llm_config(None, None, user_id)
                                → get_user_store(user_id).get_all_decrypted()
                                  ⇒ api_key && base_url && model 三者齐备才算"有模型"
```

`create_model`（由 `ThinkingToggleMiddleware` 每次调用时按 `configurable.llm_route/llm_model` 重建）走**同一条** `_resolve_llm_config`，所以"门禁放行"与"真能建出模型"不会脱节。

### 3.1 ⚠️ 踩坑：`dev` / `internal` 是**非空串**，判据不能写 `if not user_id`

计划里原本写的是"无 `user_id` 时不拦"，但**实测不成立**：`NL2SQL_AUTH_DISABLED=1` 时 AuthMiddleware 的 dev 旁路把 `scope["state"]["user"]["user_id"]` 写成 `"dev"`，`langfuse_metadata` 再**覆盖式**写进 `configurable.user_id` ⇒ 单机开发的身份是一个**非空哨兵**。若门禁与 store 只判 `if not user_id`，本地开发会变成：

- 前端 `/api/model-configs` 读 `users/dev/`（空）⇒ 界面「尚未配置模型」+ 禁止发送；
- 后端 `ModelRequiredMiddleware` 判 `has_usable_model("dev")` 为假 ⇒ **run 直接被拒**。

⇒ 统一改用 `agent.auth.ownership.is_real_owner(uid)`（`internal`/`dev`/`legacy` 都不是真实用户，与归属补打**同一份口径**，不要另写黑名单）：
`get_user_store` 命中非真实身份时回退全局 store（`get_store()`），`is_blocked_for` 直接放行。验收脚本第 ⑦ 组专测这一条（含"真实账号同样条件仍拦"的对照）。

## 4. 明确边界（不做的）

1. **不回溯清理**现有账号已播种的副本。
2. **不改** `db_config` 的「全局 + grants 过滤」范式（那是另一套账本）。
3. **不改**离线实验 / 评测的全局模型来源：`/api/experiment*` 全部端点 `require_admin`，且 `run_experiment` 的 configurable 不带 `user_id` ⇒ 属"管理员批处理面"，维持现状。
4. **不删**共享 `model_config.json` 与 `get_store()`（无登录身份路径的兜底）。
5. **不做**「管理员一键把模型复制给新账号」这类按钮（正是本次要取消的继承）。
6. **不改**用户创建链路（`api/auth_admin.py` 完全不碰模型配置）。

`scripts/verify_user_model_config.py`（改动前**零覆盖**，这是唯一的回归网）—— 七组共 **60 条**：

| 组 | 关键用例（含负对照） |
|---|---|
| ① 播种已移除 | 共享有 2 个 provider + 新账号无文件 ⇒ `list_configs()==[]` 且**不落文件**；**负对照 A** 老账号历史副本仍可用、**负对照 B** `get_store()` 仍读得到共享；源码断言无 `_shared_config_path` / 无 `write_text` |
| ② 判据一份 | **关键负对照**：共享有 provider + 本账号空 ⇒ `has_usable_model` **False**；缺 api_key / 缺 base_url / models 空 ⇒ False；`user_id=None` 读全局 |
| ③ 门禁中间件 | 无模型 ⇒ **handler 调用 0 次** + 文案一致（同步/异步）；有模型 / 无身份 ⇒ 放行；AST 断言两个图都挂且在最外层 |

## 6. 风险与回退

- **新账号在配模型前完全不能用** —— 这就是本次需求本身。靠三处让管理员预先知道：①前端空态/门禁文案 ②新增用户弹窗告警 ③本文档 + `docs/prod环境/账号密码汇总.md` §8。
- **key 的发放方式变了**：若公司网关的 key 原本是"全员共用"，改造后要么逐个发 key、要么新账号自己填同一个 key（那是**他自愿填的**，不是系统继承）。给新同事开账号时要一并给他 base_url + api_key。
- **老账号若从未加载过自己的 store**（改版前只登录过、没进过聊天页）⇒ 改造后也会变"无模型"。方向与需求一致，但发版前可用 `docker exec` 数一下 `users/*/model_config.json` 与账号数的差。
- **回退**：改动 = 「删一段播种 + 加一个中间件 + 两处传参 + 三处文案」，`git revert` 即净；已有账号文件不受影响，共享 store 与 `get_store()` 原样保留。

## 7. 生产 E2E（两个交付面分别发版）

1. 后端 `release-backend.ps1`（整包 src + 重启）；前端 `release-frontend.ps1`。

3. 无痕窗口用新账号登录 ⇒ 聊天页显示「尚未配置模型…」且发送被禁 ⇒「设置 → 模型」为空态新文案 ⇒ 新增接入点后能正常问数（且用的是**该账号自己**的 key）。
4. 回归确认**老账号**（含 admin）仍能正常问数。
