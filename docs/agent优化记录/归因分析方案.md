# 归因分析方案（维度贡献分解）

**日期**：2026-09-30　**状态**：方案定型 + 实施步骤已细化到文件与函数，未实施（代码一行未动）
**需求来源**：「如果用户查询完问题，想基于返回的答案做进一步归因分析或者直接做归因分析，有什么方案？」
**参考实现**：Datus-agent（开源，HEAD `f58c766`）的 `attribution_analyze`。本方案的算法与护栏**逐条移植**它已被生产验证的
`GenericAttributeAnalyzer`，证据见附录 A。

**一句话方案**：把归因当成**确定性计算问题**，不是模型能力问题 —— 移植 Datus 的归因内核（加法分解 + 11 项护栏），
**复用本仓已有的 wren 编译链**（`plan_cube_sql` 产出的就是归因要的 `GROUP BY` SQL），在**一次工具调用内**跑完 `2+2D` 条聚合，
模型只负责**选维度、选期间、写解读**。

> **收益口径**：不在于「模型会算贡献度」（它算不对），而在于把「哪个部门/项目贡献了这次变化」变成
> **可复算、可审计、能贴给业务**的一份产物 —— 且**每条结论能点到真实 SQL**。

## 一、方案定义

### 1.1 做什么、不做什么

| | 内容 | 判定 |
|---|---|---|
| **做 T1** | 维度贡献分解：ΔY = Σ_d ΔY_d（加法型，**可精确加总**） | ✅ 完全确定，逐值给 `delta` / `contribution_pct` |
| **做 T2** | 结构-强度分解：Δ(Y/X) = 结构效应 + 强度效应（比率型） | ✅ 确定（算法有标准解），逐值给 `mix_effect` / `rate_effect` |
| **不做 T3** | 因果归因：「到底为什么会降」 | ❌ 反事实推断**单靠数据不可确定** |

**T3 红线**：产品文案只能用「贡献度分解 / 归因分解」，**不许出现「原因」「导致」**。
理由是归因恰好是幻觉最容易被当成结论的地方（本仓已两次吃过同类亏：「78 个部门」幻觉、`_extract_last_sql` 取错 SQL）。
**这条写进工具 docstring 本身**（每次调用模型都读到），比写在文档里可靠。

**同样不做**：明细级归因（逐条比对，会撞行数上限且量级完全不同）；native 双路径（我们没有可下推的引擎，只有一条路）。

### 1.2 工具契约

新增**本地工具**（`StructuredTool`，注册范式同 `build_report`，**不走 MCP 循环**；**挂主 agent**，理由见 §4.4）：

```
attribution_analyze(
    db_name: str | None = None,                      # 哪个语义库；见下面的三级解析（**不许读裸 configurable**）
    cube: str | None = None,                         # ─┐
    measures: list[str] | None = None,               #  │ 指标标识（**列表**，load_cube_metadata 锁定）
    time_dimension: str | None = None,               #  │ 归因时间锚点
    baseline: [start, end] | None = None,            #  │ 半开区间 [start, end)，与 Datus 同契约
    current: [start, end] | None = None,             # ─┘ 这五个缺省 ⇒ 取「答案指纹」（§4.9）
    candidate_dimensions: list[str] | None = None,   # 缺省 = 自动取 cube dimensions
    filters: list[Filter] | None = None,             # 全局过滤；Filter = {dimension, operator, value}
    fingerprint: str | None = None,                  # 用哪条「答案指纹」（§4.9）；缺省 = 最近一条
    top_n_dimensions: int = 3, top_n_values: int = 10,
    max_values_per_dimension: int = 500,             # 硬顶 1000
) -> { measures, primary_measure, per_measure, warnings,
      comparison_metadata, queries_executed }
```

**`measures` 是列表**（2026-09-30 更正，原为单数 `measure`）—— 一份报告常常牵涉多个指标，
同 cube 的多个度量**一次调完**（成本仍 `2+2D`，§2.1）；**跨 cube 由模型分次调用**（编译契约一次只吃一个 cube）。
结果逐度量一份放在 `per_measure` 下：`per_measure.<measure>.{total_change, strategy, dimension_ranking,
selected_dimensions, top_dimension_values, per_dimension, warnings, comparison_metadata}` ——
**这些字段名逐字对齐 Datus，只是多了一层按度量分组的壳**（§4.3 记了为什么顶层不做镜像）。

⚠️ **`db_name` 的三级解析（S3 必须照此实现，不要图省事读 `configurable.db_name`）**：

1. 显式入参 `db_name`（用户说「对 XX 库的工时做归因」）；
2. 「答案指纹」里的 `db_name`（§4.9 字段清单里有它）；
3. **`_current_db_name()`**（[`report_builder.py:381`](../../src/agent/tools/report_builder.py#L381)）——
   `configurable.db_name` → **会话 `thread_db` 账本兜底**（只在**恰好记着一个库**时采用；多库＝拿不准）。

**为什么第 3 级必须带账本兜底、不能只读 `configurable`**：`_current_db_name` 的 docstring 记的就是
**2026-09-26 的生产实证**（trace `eaf1c8b2…`）—— 主 agent 的活**永远**由同步循环触发的**续跑 run**
接着干，而那条 run 的 `configurable` 是手拼的、只有 `user_id` ⇒ `db_name` 读成空。
归因工具挂在主 agent 上（§4.4），**踩的是同一条路**：续跑 run 里读裸 `configurable` 必然空。
（这正是 memory 里「db_name 会传染性丢空，64 填 13 空」那条的成因。）

**三级全空 ⇒ 回 `UNKNOWN_DB`，不许猜一个库** —— 拿错库的 cube 声明去解释另一个库的数字，
比拒答坏得多。同理第 3 级的「多库不采用」也是 fail-closed。

- **上面那五个参数可缺省**：用户说「就刚才那个数归因一下」时，指标（cube + measures）、时间锚点、两期区间
  **全部从「答案指纹」取**（§4.9），模型只需要补 `candidate_dimensions`（挑哪几个维度分解）。
  **取不到指纹就回 `NO_FINGERPRINT`，不允许从聊天史猜**（那正是幻觉的温床）。
  指纹里的 `final_cube_spec.measures` **本身就是列表**（`normalize_cube_spec` 保序去重）⇒
  「上一轮问了几个指标，这次就归因几个」是**直读**，不需要模型回忆。
  指纹里**没有**可用的两期区间时（§4.9 会说明为什么可能没有），`baseline` / `current` 必须由模型显式给 ——
  也**不许**把「上个月」这种相对说法自行折成绝对日期。
- **返回字段名逐字对齐 Datus**：`total_change.{baseline_value,current_value,delta,pct_change}`、
  `per_dimension.<dim>.values[].{delta, contribution_pct, segment_kind, drill_down}`、`warnings[].code`。
  理由：可对照参考实现、便于将来核对；**不自创词汇**。`strategy` 字段留位，M1 只产 `term_wise` / `unsupported`。
  这些键**逐字保留**，只是被按度量分到 `per_measure.<measure>` 下（多度量时**没有**「主度量」这回事，
  顶层镜像会让模型拿 A 的排名讲 B 的结论）。
- ⚠️ **`where` 不收字符串，收结构化 `filters`** —— 这是本方案**唯一一处刻意偏离参考实现**，因为本仓的编译链
  本来就只吃结构化过滤：`plan_cube_sql` 的 `args["filters"]` 是 `list[str]`、每条形如 `dim:op:value`
  （`.venv/.../wren/cube_cli.py:40-65` 的 `_parse_filter` ⇒ 解析成 `{dimension, operator, value}` 交给引擎）。
  ⇒ **本工具因此不存在「模型自由文本进物理 SQL」的口子**，注入面按构造关闭。
  `operator` 限枚举（`eq/ne/gt/gte/lt/lte/in/not_in/is_null/is_not_null`）、`dimension` 必须落在 cube 元信息里的
  dimensions 集合内（进程内 `load_cube_metadata`，**不调 `describe_cube`**，理由见 §4.4），任一不满足即拒（`INVALID_FILTER`）。
- **下钻回传的也是结构化 `drill_down.filters`**（工具生成，值取自查询结果本身）。同时给一个
  `drill_down.where_sql`：**只读展示用**（渲染给人看/进报告），**绝不被当作入参接收** ——
  保留它只为与参考实现对照，以及在报告中留一行可读的过滤条件。
- **参数透传记入 `comparison_metadata`**，以备审计。

**分工是这份方案的核心**：**代码**决定分解算法、生成 SQL、算贡献、排序、落盘可复算产物；
**模型**只负责**选维度、选期间、写解读** —— 且解读受第四章的提示词纪律约束。

## 二、内核：算法与护栏

### 2.1 算法（按**查询组**计价，每组 `2+2D` 条）

1. **两期窗口校验**：ISO 半开区间 `[start, end)`，天数 ≤ 0 直接报错。
2. **两期总量**：不带维度的聚合各一次 → `total_delta`。
   **本组全部度量在同一条查询里取回**（`SELECT SUM(a), SUM(b) …`），不是每个度量一条。
3. **逐候选维度**：`GROUP BY dim` 两期各一次，同一条查询把**本组全部度量**一起算出来
   （`SELECT dim, SUM(a), SUM(b) … GROUP BY 1`）⇒ 两期各 D 条 = `2D`。
   内核按参考实现把 `limit = max_values_per_dimension + 1` 传下来，语义是**判截断**（不靠 COUNT 预估）。
   ⚠️ 本仓这个 `limit` **进不了 SQL**（`plan_cube_sql` 固定 1001），判截断口径要改，见 §4.3 的方框。
4. **并集分解**：两期维度值取并集，逐值 `delta = current - baseline`、`contribution_pct = delta / total_delta × 100`。
   **每个度量各算一套**（结果按度量分开给，见 §4.4 的 `per_measure`），互不串味。
5. **维度打分**：`score = max|delta_i| / |total_delta|` → 排序取 top-N 维（默认 3）+ 每维 top-N 值（默认 10）。
   多度量时**逐度量各排一次**（不是把多个度量的 δ 混进一个分数里比）。

**成本公式：`查询数 = G × (2 + 2D)`** —— D = 候选维度数，G = 查询组数。
**一个「查询组」= (cube, time_dimension, baseline 窗口, current 窗口)**：这四样里任何一样不同就是两组，
因为编译出的 SQL 没法把它们拼进一张结果表。

⚠️ **度量个数 M 不进公式**（2026-09-30 更正）。同一组内 M 个度量**共用**这 `2+2D` 条查询 ——
`plan_cube_sql` 的 `measures` 本来就是**列表**（§4.3 的 4 键契约），引擎自己就会
`SELECT dim, SUM(a), SUM(b)`，M 只影响每行的列数。**不要按「一度量一查询」实现**：
那会把成本变成 `M × (2+2D)`，而参考实现的单度量形状并不是本仓的约束。

**G 在 v1 恒为 1**：`plan_cube_sql` 的 `args["cube"]` 是**单值**（不是列表），编译契约本身表达不了跨 cube；
`time_dimension` 也钉在一次调用上。⇒ **一次工具调用 = 一个 cube + 一个时间锚点**。
「一份报告牵涉多个指标」由**模型分次调用**解决：同一 cube 的多个度量**一次调完**（仍 `2+2D`）、
不同 cube / 不同锚点**各调一次**（各 `2+2D`、各过预算）。
C 个 cube 的问题最坏 `C × (2+2D)` —— 这是本工具成本唯一会上去的地方，playbook（§4.6）里点名。

**所有候选维度都会被查**，之后才排名筛 top-3。维度是模型给的（`candidate_dimensions`），
所以成本可控、可预算 —— 这直接决定第四章的 D 该定几个。

### 2.2 护栏（可靠性的全部来源）

| 护栏 | 行为 | 为什么必须有 |
|---|---|---|
| **可加性对账** | `Σ分组值` vs 期间总量，容差 `0.02`；不过的维度打 `non_additive_dimension` 警告并**踢出排名** | 不可加维度（去重计数、比率）的「贡献度」是假的；宁可不出，不可出错的 |
| **高基数截断** | `truncated` + 警告；测试钉住**按 \|delta\| 排序、主因不被截掉**（`max_values_per_dimension=1` 仍返回 −2900 那个收缩项） | 截断掉主因是最坏结果；排名必须按影响量而非取值名 |
| **取值进出** | `segment_kind ∈ {normal, entered, exited}` | 「新增/消失的部门」不是贡献度，是结构变化，必须区分 |
| **零变化省略** | Δ≈0（`< 1e-6`）时 `contribution_pct` **整个字段省略**（不是 `null` / `0` / `inf`） | 除以 0 会产出 `inf`，模型会把它当「无限大贡献」讲出来 |
| **零总变化但有分量变化** | `zero_total_delta_with_component_changes` → 提示「用绝对增量解读，不要用百分比」 | 分子分母同时消失时百分比无意义 |
| **两期不等长** | 只给 `unequal_windows` 警告，**不静默归一化** | 静默折算等于编数据 |
| **逐维故障隔离** | 单维失败 → `dimension_analysis_failed`，**继续跑其余维度** | 一个维度炸掉不该让整次归因没有输出 |
| **当期不完整** | `incomplete_current_period` 警告，**绝不按比例折算** | 按比例折算等于用半段数据外推，会凭空造出一个「下降」 |
| **NULL ≠ 字符串** | SQL NULL 与字面量 `'(null)'` 是**两个成员**，下钻分别走 `IS NULL` / `= '(null)'` | 合并两者会算错一整类数据 |
| **类型化错误码** | 列/窗口类：`MISSING_METRIC_COLUMN` / `MISSING_DIMENSION_COLUMN` / `DUPLICATE_DIMENSION_KEY`（提示「可能是隐式时间粒度」）/ `NON_NUMERIC_METRIC_VALUE` / `MULTI_ROW_TOTAL` / `INVALID_TIME_WINDOW`；**口径类**：`UNSUPPORTED_MEASURE`（`COUNT(DISTINCT)`）/ `NON_TERM_WISE_MEASURE`（比值 / `AVG`）/ `NO_FINGERPRINT` / `MISSING_MEASURE`（名字不在 cube 声明里）/ `MISSING_DIMENSION`（维度名不在 `dimensions` 里）/ `MISSING_TIME_DIMENSION`（锚点不在 `time_dimensions` 里 —— 与上一条**分开**：两个列表平级，处置不同）/ `UNKNOWN_CUBE` / `UNKNOWN_DB`（库名三级解析全空，§1.2）/ `DB_NOT_AUTHORIZED`（判权不通过，§4.5 闸②）/ `ATTRIBUTION_DISABLED`（总开关关着）；入参类：`INVALID_FILTER` / `INVALID_ARGUMENT` | 失败要能机读归因，不能只有一句自然语言错误。**「该补参数重试」与「重试也没用」必须分开**：`NO_FINGERPRINT` / `MISSING_*`（模型补齐入参即可，错误文本里带**可用名字清单**）vs `UNKNOWN_CUBE` / `UNKNOWN_DB`（语义层里就没有）vs `DB_NOT_AUTHORIZED`（**换库或找管理员，重试同一个库没有用**）vs `ATTRIBUTION_DISABLED`（**按设计拒绝，不许重试**，错误文本里明写「请直接用 `run_sql` 查两期数据对比」）—— 四条路的下一步动作不同，混成一个码模型只会瞎重试 |
| **不支持的度量要「明确拒」而不是「算着看」** | 命中 `unsupported` / `mix_shift` 的 measure ⇒ 回上面的口径类错误码，**`success == 1`**（是「按设计拒绝」，不是工具故障）。多度量时**一票否决**：请求里只要有一个不支持，整次调用不产出数字（§4.4），**不许静默少算一个** | 归因算出一个漂亮但无意义的贡献度，比拒答危险得多（§1.1 那条红线）；而**静默少算**更坏 —— 模型会把没算的那个当成「没有变化」讲出来 |
| **参数透传** | 入参完整记入 `comparison_metadata` | 出问题时能复算 |

### 2.3 策略由度量表达式的**形状**决定，不是声明、不是模型选

| 度量定义 | 表达式形状 | 分类 | 本库实测 |
|---|---|---|---|
| 加法型 | `SUM(x)` / `COUNT(*)` / `SUM(CASE …)` / `SUM(x) - SUM(y)` | `term_wise` | **57** |
| 比率型 | 比值 `SUM(A) / SUM(B)`（含除以 `COUNT(*)` / `COUNT(DISTINCT …)`） | `mix_shift` | **12** |
| 比率型 | `AVG(x)` | `mix_shift`（由 AVG 脱糖） | **10** |
| 乘积型 | `SUM(x) × SUM(y)` | `factor_shapley` | **0** |
| 不可加 | `COUNT(DISTINCT …)`（**且不含 `/`**） | `unsupported`（**不是工具失败**，`success == 1`） | **9** |

右列是**本库 88 个 measure 的实测分布**（2026-09-30 逐 `cubes/*/metadata.yml` 的 `expression` 分类 ——
判据是 `attribution_analyze.classify_measure_expression` 本体，不是另写一份正则：
`57 + 12 + 10 + 0 + 9 = 88` 闭合；逐 cube 见下）。

⚠️ **判定顺序：`/` 先于 `DISTINCT`**（实现里就是这么排的，`classify_measure_expression` 第 1 条）。
差值只有一个度量：`workhour_analysis.avg_hours_per_user` =
`SUM(work_hour) / NULLIF(COUNT(DISTINCT user_id), 0)` —— 它**同时**含 `/` 与 `DISTINCT`，
归**比值**（12）而不是「不可加」（9）。这一条 2026-09-30 更正过：原表把 12 个比值里的这一个数进了
`DISTINCT` 那一格（写成「比值 11 / 不可加 10」），与 §3.6 那张分类表**自己**把
`avg_hours_per_user` 归在「比值」相互矛盾。**两处现在是同一个判据**，`verify_attribution` 段⑭-⑥
把这两个数钉在真库上（跑 `classify_measure_expression` 复算，不是人眼看）。

| cube | measures | 其中加性 | `timeDimensions` |
|---|---|---|---|
| `bug_quality` | 21 | 13 | 5 |
| `iteration_burndown_cube` | 16 | 11 | 5 |
| `project_portfolio` | 4 | 2 | 1 |
| `story_delivery` | 23 | 17 | 7 |
| `task_timeliness` | 14 | 10 | 2 |
| `workhour_analysis` | 10 | **4** | **1** |
| **合计** | **88** | **57** | **21** |

⚠️ 比值与 `AVG` **不是同一类**：参考实现里 `AVG` 走脱糖路径，而比值是**两个可加度量之比** ——
本库 12 个比值里 **11 个以 `_rate` 结尾**（`finished_rate` / `done_rate` / `approve_rate` / `within_24h_rate` …），
第 12 个是 `avg_hours_per_user`（人均工时：分子 `SUM(work_hour)` 可加，**分母不可加**）。
⇒ **别拿名字当判据**（`_rate` 后缀会把第 12 个漏掉、也会把 `avg_*` 系列误当同类）：
判据**只有表达式的算子形状**，这也正是「语义库新增 measure 不必改代码」的原因（§4.4 的形状闸）。
M1 两类都不做，但**别把它们的分类混为一谈**（将来做 T2 时是两条不同的实现路径）。

⚠️ **`iteration_burndown_cube` 整块 11 个加性 measure 不进候选** —— 它是**快照表**，
`statistic_date` 自己的 description 就写着「查询时必须限定，否则跨天重复累加」⇒
`Σ分组值 vs 总量` 的对账**必炸**，会被 `_check_additivity` 全部踢出排名（不是 bug，是这张表不该做归因）。
⇒ 加性候选实际是 **46 个**（57 − 11），且 `workhour_analysis` 只有 **4** 个（§3.6 那张表）。

**验收判据是「能不能对上账」**，不是「故事讲得像不像」——参考实现的手算 oracle 全部用**精确相等**断言：
`term_wise` 的 `Σdelta == total delta`；`mix_shift` 的 `mix_effect + rate_effect == delta` 且 `factor_totals.residual ≈ 0`；
`factor_shapley` 的 `Σfactors[].effect == total delta`。

⚠️ **M1 只做 `term_wise`**：`mix_shift` / `factor_shapley` 的算法本体是私有包（不在本机、读不到），
只有从集成测试的手算 oracle 断言反推出的输入输出语义。**M4 若要做，需先拿到实现**。

## 三、落到本仓

### 3.1 复用 wren 编译链：归因要的 SQL 就是它

- 入口：[`wren_plan.py:353`](../../src/agent/utils/wren_plan.py#L353) `plan_cube_sql(project_path, conn, args)`
  → `{"cube_sql","dialect_sql","dialect","limit_appended","dup_limit"}`（fail-open 返回 `{}`）。
- 真身：`.venv/.../wren/cube_cli.py:297-300` `_build_cube_query(cube, measures, dimensions, time_dimension, filters, limit, offset)`
  + `cube_query_to_sql` ⇒ **产物天生就是 `SELECT dim…, SUM(m)… GROUP BY dim…`**。
- ⇒ **归因不需要自己拼 SQL、不需要新引擎**，只是把「维度集合」从 1 个换成 `2+2D` 次调用、把「期间」从 1 个换成 2 个。
- 另有 `query_cube(..., sql_only=True)` 只回 SQL 不执行（`.venv/.../wren/mcp_server.py:150-155`）
  ⇒ **可以先审 SQL 再执行**，天然适配本仓审计文化。
- ⚠️ **`plan_cube_sql` 只编译、不执行**：它不开连接（`_engine_for` 缓存 + `engine.dry_plan`，
  [`wren_plan.py:270-288`](../../src/agent/utils/wren_plan.py#L270)），返回的 `dialect_sql` 是**待执行**的物理 SQL。
  **执行是另一条通道**，见 §4.3 —— 这是本方案实施时最容易走偏的一步（以为拿了 `dialect_sql` 就完事了）。
- ⚠️ **分组查询的物理 `LIMIT` 固定为 1001，不由我们指定**：`_finish` 里 `limit=None` 写死 →
  `effective_probe_limit(None) = DEFAULT_ROW_LIMIT(1000) + 1`。后果有两条，实施时必须按这个事实设计：
  - `max_values_per_dimension` 只能是**逻辑上限**（超过就标 `truncated`），真正的物理截断点在 1001。
  - 分组 SQL **没有 `ORDER BY`** ⇒ 数据库返回顺序任意。所以「按 |delta| 排序取 top-N」是在
    **取回的 ≤1001 行样本内**排序，**不是全局 top-N**。只有当某维度取值数 ≤ 1001 时才保证是全局。
    ⇒ 高基数维度上 `truncated` / `high_cardinality_dimension` 两个警告的分量比参考实现更重，
    必须真的让模型照 playbook 换成更粗的维度，而不是当装饰。
  - 想要真正的全局 top-N，需要「先按 measure 降序取 top-N、再全量求和判截断」⇒ 成本从 `2+2D` 涨到 `3+3D`。
    **M1 不做**，列入 M2 的评测项（§六 L2 已有「高基数」一题）。
- ⚠️ cube 的 `hierarchies` 只是**可选**：wren 侧只被**渲染进 schema 描述**，没有引擎级「沿层级聚合」API
  ⇒ 层级链展开要我们自己多跑几次 `plan_cube_sql`，**不是一次调用**。下钻本身靠现场生成 `where`，不依赖层级声明。

### 3.2 执行路径（关键决策）

**一次工具调用内完成全部 `2+2D` 条聚合 SQL**：主进程常驻引擎编译（`_engine_for` 缓存，亚毫秒）→
现有物理库连接逐条执行 → `attribution_core` 内存分解 → 返回结构化 JSON。**中间查询对 LLM 完全透明。**

⚠️ **禁止走「MCP 循环调 `query_cube`」**：MCP 子进程单次调用实测 **2.5~4.2s**，
D 个维度需 `2+2D` 次子进程调用（5 维 ≈ **40s+**），**必须一次工具调用内完成**。

**「现有物理库连接」具体指哪条通道 —— 照抄 [`feedback_annotation.py:236-278`](../../src/api/feedback_annotation.py#L236)
的 `_run_preview`**，它已经是平台内「进程内执行物理 SQL」的**已审过**模板，逐字对应本方案需要的三件事：

| `_run_preview` 做的 | 归因为什么要同一份 |
|---|---|
| `classify_sql(sql)` → `verdict == "write"` 直接拒（`:255-257`） | 只读硬闸，见 §4.5 |
| `McpSqlConfig.from_env(db_name)` + `_load_runner_class(cfg.db_type)(**cfg.config)`（`:259-264`） | 复用 dbmcp 同一套 runner 与连接配置，**不自己拼连接** |
| `split_sql_statements` → 逐条 `await asyncio.to_thread(_run_engine_blocking, runner, RunSqlToolArgs(sql=stmt), context)` → 收 `list[(stmt, df)]`（`:267-274`） | **只借「每条单独跑」这一条**：`2+2D` 条每条都要结果，**不能用 `combine_multi_results`**（它按设计只留**最后一条**为主结果，`multi_sql.py:91-93`）。⚠️ **实现里没有 `split_sql_statements`，也没有 `_run_engine_blocking`**（2026-09-30 按实现更正）：前者是「一次收多语句」的批处理入口，而归因是**内核按需取数、一条一取**；后者在 `api/feedback_annotation` 里，`agent` 反向 import `api` 会造环 ⇒ `_dbmcp_execute` 重写了那两行（`_load_runner_class` + `_build_tool_context` + `asyncio.run(runner.run_sql(...))`），并如实记下为什么**不**再走 `_apply_default_limit` / `split_sql_statements`（§4.3） |

配套的三个解析入口（**编译侧与执行侧必须同源**，`mcp_tool.py:175-178` 明确要求）：

- 项目路径 + 连接字典：`resolve_wren_ctx_by_db(db_name)`（`wren_call_extract.py:278`）
  = `(project_path, conn)`，conn 与 `wren_conn_dict(db_name)`（`mcp_tool.py:172`）是同一份 —— 它同时喂给
  `plan_cube_sql`（定方言）与 `McpSqlConfig.from_env`（建连接），方言因此不会错位。
- 活跃库名：`_current_db_name()`（`report_builder.py:381`；configurable.db_name → 会话账本兜底）。
- cube 元信息：**不要直接调 `wren.context.load_cubes`** —— `_load_cubes_v2:680` 的
  `meta_file.read_text()` 不带 encoding，Windows 上中文 cube 定义会 `UnicodeDecodeError: 'gbk'`
  （`wren_plan.py:22-25` 记过这个坑）。走 `wren_call_extract.load_cube_metadata(project_path, cube_name)`
  （`:317`，utf-8，fail-open 返回 `{}`）。

### 3.4 必须守的五条约束

**① 绝不许按维度 fan-out 子任务。** run 槽全局 = **10**（`start_server.py:93`；真约束在 `.venv/.../langgraph_runtime_inmem/queue.py:91-95`），
**一次问数已吃掉约 3 个槽**（主 run + 子 run + 续跑主 run），**子任务消耗同一个池**。
5 个维度并行 = 5 槽 ⇒ **2 个并发用户就打满**。归因必须在**同一个 run 内顺序循环**，且最好一次工具调用内跑完 `2+2D` 条。

**② 归因结论必须带「业务口径」节，并过逐字核验。** 归因最容易出的错是**用不属于该口径的维度去分解** ——
例：口径写明「派遣工不计入在职」，却按「用工性质」分解在职人数；结论看着头头是道，口径上根本不成立。
复用现有机制：契约在子 agent 提示词末尾（[`NL2SQL_SYSTEM_PROMPT.md:269`](../../src/agent/prompt/NL2SQL_SYSTEM_PROMPT.md#L269)）、
抽取 `parse_caliber_block`、**逐字核验** `verify_caliber_entries`（[`caliber_evidence.py:391`](../../src/agent/utils/caliber_evidence.py#L391)）。

**③ 数字必须由代码算，模型不许自己加减。** 本仓两次同类教训（`_extract_last_sql` 取错 SQL、「78 个部门」双表计数错）。
参考实现更彻底：**指标/归因结果的唯一出口就是数值工具**，且下钻 `where` 由工具生成。

**④ 归因结果免截断，且不许被读成低分。**
`attribution_analyze` 必须进 slimmer 免截断名单（**数字本身就是交付物**，与图表同级）；
提示词必须写明**「掉出 `dimension_ranking` 的维度不是低分维度」**，否则静默降级会被模型转述成结论。
（本仓曾因 `MessageSlimmer` 按行截断弄丢 `</iframe>` —— 归因数字与图表同类。）

⚠️ **本仓没有 `SUMMARY_TOOLS_NO_CLIP`**（那是参考实现的常量名）。现有机制是
[`message_slimmer.py:122`](../../src/agent/middlewares/message_slimmer.py#L122) 的
`_KNOWLEDGE_EXEMPT_TOOL_SUFFIXES`（**tuple、后缀匹配**，兼容 `wrenai_<库名>_` 前缀）。
**归因不要塞进这个 tuple**：它的语义是「知识料取料」，`verify_slimmer_exempt.py` 的断言绑定了该语义，
塞进去既是语义污染、又会让既有断言漂移。要新增**独立常量 + 独立判据**（§4.6）。

**⑤ 降级路径必须闸住口径。** 语义层覆盖不到的目标（非 cube measure）只允许一条降级路：
**手写环比 SQL，并显式标注「口径不可比」**，且该结果**不得进入归因结论**。
理由：参考实现的归因面**没有裸 SQL 出口**（工具白名单里没有任何 db/sql 工具），
它宁可回答「没有合适指标」也不回落 SQL。我们允许降级是因为存量语义库覆盖不全，
但**降级产物与语义层产物混在一份结论里，就是 ② 那类错误的入口**。

### 3.5 开关（默认全关）

| 变量 | 默认 | 作用 |
|---|---|---|
| `NL2SQL_ATTRIBUTION_ENABLE` | `off` | 总开关；关闭时工具拒绝执行并回告未启用（**fail-closed**） |
| `NL2SQL_ATTRIBUTION_MAX_VALUES` | `500` | 每维取值的**告警阈值**（超过即打 `high_cardinality_dimension`，**不丢值、不截断**）；硬顶 **1000**（超过的入参直接拒）。语义与参考实现不同，见 §4.3 |
| `NL2SQL_ATTRIBUTION_TOP_DIMS` | `3` | 返回的 top 维度数 |
| `NL2SQL_ATTRIBUTION_TOP_VALUES` | `10` | 每维返回的 top 取值数 |
| `NL2SQL_ATTRIBUTION_QUERY_BUDGET` | `12` | `2+2D` 的预算上限（**按调用算**，不乘度量个数 M；§2.1）；超出直接拒绝并回告「候选维度太多」⇒ **延迟有上界** |

⚠️ **预算是「一次调用」的，不是「一个问题」的**：多 cube 的问题由模型分次调用（§2.1），
每次各自过这道闸 ⇒ 单次延迟有界（≤ 12 条顺序查询），而整场问题的最坏成本 = `C × 12`。
这是刻意的：把闸设成「全场累计」需要跨调用记账，而记账一旦跨请求就会引入状态与竞态；
**把上界放在单次调用上，代价是模型可能多调几次，收益是每次调用的延迟和成本都是确定值**。

### 3.6 指标**不预设、不白名单**：由「这次问的是哪些度量」决定（2026-09-30 更正）

⚠️ **本节的旧结论「第一版固定 `workhour_analysis.total_hours`」已被推翻**，理由是一条口径事实：
**一份报告 / 一个问题经常牵涉多个指标**（「工时和报工条数为什么都降了」「缺陷数和完成率」），
把它钉成单一 measure 会把这类问题排除在能力之外，而工具本身并没有「只支持一个指标」的约束 ——
`plan_cube_sql` 的 `measures` 本来就是列表（§2.1 的成本公式因此与度量个数 M 无关）。

**现在的口径（拍板）**：

| 项 | 做法 |
|---|---|
| 允许哪些 | **任意 cube 的任意 measure** —— 不建白名单、不预置「第一版目标指标」 |
| 一次调用几个 | 同一 cube 的**任意多个**（§2.1）；跨 cube 由模型分次调用 |
| 谁决定用哪个 | **模型**：从问题（或 §4.9 答案指纹里的 `final_cube_spec.measures`）里取，工具不猜 |
| 放行/拒的判据 | **运行时按算子形状判**（§2.3）：加法型 ⇒ `term_wise` 放行；比值 / `AVG` / `COUNT(DISTINCT)` ⇒ 明确拒（§2.2 口径类错误码）。判据是 `metadata.yml` 里的 `expression`，**不是 measure 名**，所以新 measure 不需要改代码 |
| 拒的粒度 | **调用级**：请求的度量里**只要有**一个命中了不支持的形状，整次调用回错误码并列出是哪几个（不悄悄少算一个 —— 那正是「算着看」） |

**为什么仍然把 `workhour_analysis` 这一族写下来** —— 它不是白名单，是**本库第一个能跑通的组合**，
S2 的实测与 S6 段⑩ 的真编译断言都建立在它上面（`time_dimensions` 只有 1 条 = 锚点无歧义，
所以它适合当**冒烟集**）。依据全部来自语义库内声明（`D:\code_work_space\llm\witops-wrenai`，
即生产活跃库的 git checkout，48 models 与生产一致）：

| 筛 | 内容 |
|---|---|
| ① 算子形状 | `total_hours` = `SUM(work_hour)` —— 纯加性、无 `CASE WHEN`、无 `DISTINCT`、无除法 ⇒ `term_wise`，内核能算 |
| ② 时间锚点唯一 | 本 cube 的 `time_dimensions` 只有 **1 条**（`work_date`，`type=date`，levels 到 day）；其余 cube 有 5~7 个日期字段，「用哪个」本身就是歧义源 |
| ③ 业务频次最高 | 12 份真实问数范例（`knowledge/sql/*.md`）里**工时为 5 份、居首**（缺陷 2 / 需求 2 / 项目 2 / 迭代 1） |
| ④ 维度即归因轴 | 13 个 dimension 全为 `type ∈ {string,int}`：**9 个分析轴** —— `department_full_name`（部门全路径）/ `dept_level1` / `project_name` / `product_name` / `project_module_name` / `role_name` / `if_approve`（0/1）/ `if_leave_form` / `project_category`；**3 个人名类** `user_name` / `job_number` / `approve_user_name`（**高基数，playbook 禁作候选维度**）；1 个 ID 类 `project_code`（归因轴里无意义） |

**声明原文**（`cubes/workhour_analysis/metadata.yml`）：
cube = `工时投入分析立方体 — 按人员/部门/项目/产品/月份维度下钻，衡量工时投入规模、分布与审核情况`；
measure `total_hours` = `SUM(work_hour)`、`DOUBLE`、`工时合计（小时）`；
base view `v_workhour`（`views/v_workhour/sql.yml`）⇒ **`FROM do_work_hour_detail_extend WHERE deleted = 0`**。

**⚠️ 两个陷阱（已核实；反直觉的写在前面）**

1. **cube 建在「明细宽表」上，不是报工主表。** `v_workhour` 的 `FROM` 是 `do_work_hour_detail_extend`，
   而仓内口径文档（`knowledge/caveats/常见陷阱.md:96-101`）写明该表是**统计首选**、
   **无未来数据**（实测最大 2026-09-11）⇒ 常说的「`do_work_hour` 含未来预填」陷阱**对本 cube 不适用**（那是主表的问题）。
   但反过来有一条更硬的：**两表口径不同值也不同**（2026-08：主表 8422 条/28732.7h vs 明细宽表 8720 条/29413.2h），
   文档明写「**同一次分析内不要混用两表**」⇒ 归因算出的 `total_hours` 与用户上一轮可能从主表查来的数
   **不会逐字相符**。⇒ 工具必须在 `comparison_metadata` 里带上**来源视图名**，解读文案不许把两者当同一个数。
2. **`work_hour` 存在 100 的异常录入值 —— 但那条证据指的不是本 cube 读的表。**
   原文（`knowledge/metrics/指标定义.md:465`）说的是 **`do_work_hour.work_hour`**（主表）；
   本 cube 读 `do_work_hour_detail_extend`，**同一异常是否存在于该表未经验证**（本地 checkout 无 DB 连接，查不了）。
   ⇒ **开工第一件事**：`SELECT MAX(work_hour) FROM do_work_hour_detail_extend`。若存在，100 这个量级会显著扰动
   `Σ分组 vs 总量` 的 **2% 对账容差**（§2.2），处置方式（是否加合理区间过滤 / 是否放宽容差）**必须先定，不许边跑边看**。

**同一 cube 其余 measure 的分类**（这是**冒烟集**，不是白名单；判定同 §2.3 的算子形状表）：

| measure | 表达式 | 分类 |
|---|---|---|
| `total_hours` | `SUM(work_hour)` | ✅ `term_wise` —— 冒烟首选 |
| `approved_hours` / `pending_hours` | `SUM(CASE WHEN if_approve = … THEN work_hour ELSE 0 END)` | ✅ `term_wise` |
| `record_count` | `COUNT(*)` | ✅ `term_wise`（整数计数，非连续量） |
| `avg_hours_per_record` | `AVG(work_hour)` | ❌ `mix_shift`，M1 不做 |
| `avg_hours_per_user` / `approve_rate` | 比值（`NULLIF(COUNT(DISTINCT …),0)` / `NULLIF(COUNT(*),0)`） | ❌ 比值，M1 不做 |
| `user_count` / `work_days` / `project_count` | `COUNT(DISTINCT …)` | ❌ `unsupported`，**按设计拒绝**（不是工具失败，回 `success` 载荷 + 错误码） |

⇒ 命中不支持的 measure 时**必须回明确错误码**（`UNSUPPORTED_MEASURE` / `NON_TERM_WISE_MEASURE`）并
**点名是哪几个度量**，**不许「先算着看」、也不许「悄悄只算支持的那个」** ——
两者都是 §1.1 那条红线要堵的东西（后者更坏：模型会把「少算的那个」当成「没有变化」讲出来）。

### 4.2 S1 内核：纯函数、零 IO

内核**不 import wren、不开连接、不读盘**。它与外界的唯一接口是两个方法：

```python
# src/agent/utils/attribution_core.py
class AttributionRunner(Protocol):
    def fetch_total(self, window: Window) -> list[dict]: ...                      # 不带维度的聚合
    def fetch_grouped(self, dim: str, window: Window, limit: int) -> list[dict]: ...  # GROUP BY dim

def attribute(runner: AttributionRunner, request: Request) -> dict: ...           # 主循环 2+2D
```

两个方法都返回**行 dict 列表**（列名 → 值），**列解析由内核自己做**—— 这样 S2 的真实实现与 S6 的桩实现
签名完全一致，单测就是「换一个实现」而已（参考实现的 `ScriptedAdapter` 正是这个形状，两个方法、约 20 行）。

模块骨架（左列是照搬清单里的符号，右列是本仓落点）：

| 符号 | 内容 |
|---|---|
| 常量 | `_ADDITIVITY_TOLERANCE = 0.02`、`_ZERO_DELTA_EPSILON = 1e-6`、`_MAX_DIMENSION_VALUES = 1000` |
| `TypedError(Exception)` | 带 `code` 字段；全部类型化错误码（§2.2 末行） |
| `Window` / `validate_window()` | ISO 半开区间；天数 ≤ 0 或反序 ⇒ `INVALID_TIME_WINDOW` |
| `_column_leaf(name)` / `_resolve_column(columns, want)` | `casefold` + `rsplit(".", 1)` / `rsplit("__", 1)` 取叶子名；`DUPLICATE_DIMENSION_KEY`（含「可能是隐式时间粒度」提示）在这里报 |
| `_parse_total(rows)` | 0 行 ⇒ `null_total_*`；>1 行 ⇒ `MULTI_ROW_TOTAL`；非数 ⇒ `NON_NUMERIC_METRIC_VALUE` |
| `_parse_grouped(rows, dim)` | → `dict[str \| None, float]`，**键 `None` 代表 SQL NULL**，与字面量 `'(null)'` 是两个成员 |
| `_check_additivity(grouped_sum, total)` | 容差 `0.02`；不过 ⇒ `non_additive_dimension` 且**踢出排名** |
| `_is_effectively_zero_delta` / `_has_material_component_change` | 零变化省略 `contribution_pct`；`zero_total_delta_with_component_changes` |
| `_build_contributions(...)` | `delta` / `contribution_pct` / `segment_kind ∈ {normal, entered, exited}` / `drill_down` |
| `_drill_down(dim, value, base_filters)` | 产出 `filters`（结构化）+ 只读 `where_sql`（渲染） |
| `attribute(runner, request)` | 主循环：2 条总量 + 逐维 2 条分组（`limit = max_values_per_dimension + 1`）+ 并集分解 + 维度打分 + 逐维故障隔离 |

**两个反直觉点，写进注释**：
① 内核把 `limit = max_values+1` 传给 `fetch_grouped`，语义是**判截断**而**不是分页**（多取的那一行不进结果）。
   参考实现里这个值直接进 SQL 的 `LIMIT`；**本仓进不去**（`plan_cube_sql` 写死 1001）⇒ 判截断的口径按 §4.3 那个方框改。
   **协议保留这个参数**是为了让内核与参考实现同构、单测断言可逐字对照，不代表 S2 必须兑现它。
② 零变化时 `contribution_pct` 是**整个键缺席**，不是 `None` / `0` / `inf`。除以 0 产出的 `inf`
会被模型原样讲成「无限大贡献」，所以这里必须是「没有这个字段」，让模型无法引用。

### 4.3 S2 取数通道

```python
# src/agent/utils/attribution_runner.py
class WrenCubeRunner:                      # 实现 AttributionRunner（**内核协议一行不改**）
    def __init__(self, project_path, conn, db_name, *,
                 cube, measures, time_dimension, filters): ...   # measures: list[str]
    def fetch_total(self, window) -> list[dict]: ...
    def fetch_grouped(self, dim, window, limit) -> list[dict]: ...

def get_runner(db_name, **kw) -> WrenCubeRunner | None: ...   # 解析失败 ⇒ None，由工具层回错误码

async def run_attribution(runner, request: Request | Sequence[Request]) -> dict:
    ...   # 一个 Request ⇒ 单度量；一串 ⇒ 多度量共用取数（同一趟 offload）
```

**多度量：一次取数喂多个度量**（2026-09-30 补充，实现已随 S2 落地）

内核是**单度量**的（`Request.measure`），S2 **不改内核**，而是：

1. runner 收 `measures=[…]`，`_compile` 把**整组度量**编译进**同一条 SQL**（`measures` 既然是列表，
   引擎自己就会 `SELECT d, SUM(a), SUM(b)`）；
2. `run_attribution` 对每个度量各跑一次 `attribute(runner, Request(measure=m, …))`；
   同一批行里其余度量的列被内核 `_resolve_column`（先整名匹配、再叶子名匹配，命中**恰一个**才采纳）**天然忽略** ——
   所以「内核不知道多度量」这件事是**结构上成立**的，不是靠约定；
3. 取数在**执行层**按**编译出的物理 SQL** 去重（`self._cache`，生命周期 = runner 实例 = 一次调用）：
   M 个度量 ⇒ 编译 M×(2+2D) 次（进程内、毫秒）、**执行仍只有 `2+2D` 条**。
   ⇒ `queries_executed` 数的是**真正发出去的 SQL**，恒 `2+2D`、**与 M 无关**。

⚠️ **不跨调用复用缓存**（不做进程级 memo）：同一条 SQL 在毫秒级窗口里跑两次本来就是重复劳动，
而跨请求缓存会引入「读到旧的数」这类静默错数 —— 这类账不值得省。

**返回形状恒定**（单度量与多度量**同一个形状**，调用方不必分情况写）：

```python
{
  "measures": ["total_hours", "record_count"],   # 去重保序 = 入参顺序
  "primary_measure": "total_hours",              # = measures[0]
  "per_measure": {m: <内核 attribute() 的返回，逐字>},   # 内含 total_change / strategy /
                                                        # dimension_ranking / per_dimension / warnings …
  "warnings": [ {**warning, "measure": "…"} ],   # 各度量的**并集**（按 code+message 去重）
  "comparison_metadata": {…, "measures": […], "queries_executed": N, "query_groups": G},
  "queries_executed": N,
}
```

三处刻意的取舍：

- **顶层不镜像主度量**：镜像会让 M=1 与 M>1 出现两套读法（模型得先判「这次看哪个」），且多度量时
  顶层必然与 `per_measure` 重复。代价是单度量多一层嵌套 —— 换「永远只有一个地方读数」。
- **顶层 `warnings` 逐条带 `measure`**：多度量时不知道警告属于哪条度量，模型会把 A 的
  `non_additive_dimension` 按到 B 头上（那正是要被踢出排名的维度）。
- **顶层 `queries_executed` 数「真正发出去的」、`per_measure.<m>.comparison_metadata` 里那份数「内核尝试了几次」**：
  内核在发起前就 `+1`（段⑨ 的 `2+1+2 = 5` 就是它），而编译失败的维度**根本没发查询**。
  审计取顶层 —— 「这次调用到底打了几条 SQL」才是它要回答的问题。两者都**不会**被 M 乘起来。

**`db_name → (project_path, conn)` 用现成解析器，不要按目录名拼路径**：
[`resolve_wren_ctx_by_db(db_name)`](../../src/agent/utils/wren_call_extract.py#L278) ——
它的 docstring 就是为**这个场景**写的：「`resolve_wren_ctx` 的**正向孪生**……
交互式场景手里只有 `db_name`，没有工具名可用」，**返回值正好是 `(项目路径, 连接字典)`**，一次调用两样都给全，
且：库名先过 `normalize_db_name` 归一（大小写 / 物理库名与配置名不同名）、
内部走 `discover()` + `project_path_for()`（后者已含 `WREN_SEMANTIC_OVERRIDE` 版本物化，`semantic_db.py:737`）、
**fail-open 回 `("", {})`** ⇒ 正好映射到本工具的「解析失败回错误码」。
既有同类调用方三处，全在只读分析类工具里：`report_builder.py:438`、`caliber_evidence.py:357`、`feedback_annotation.py:608`。

⚠️ **绝不许用目录名拼**：生产注册表里 `name` 是 `witops` 而工作区目录是 `witops_wrenai`
（同级还有 `*.备份-*`）⇒ 任何 `f"{db_name}_semantic"` 这类写法都会指到错的地方，且**不报错**。

**编译**：`args = {"cube":…, "measures":[…], "dimensions":[…], "filters":[…]}` ——
**键集恰为这四个**（形状照 [`check_progress.py:1393-1399`](../../src/agent/subagents/check_progress.py#L1393) 的 `_cube["args"]`；
`measures` 是**列表**，多度量 = 多几列，不是多次编译）
→ `plan_cube_sql_checked(project_path, conn, args)["dialect_sql"]`。三条实测约束：

- ⚠️ **两期窗口走 `filters`，不发 `time_dimension`**：wren 的 `time_dimension: "name:day:start,end"`
  会注入 `DATE(work_date) AS work_date__day` 并 `GROUP BY 1, 2 ORDER BY 1` ⇒ 同一个维度值**一天一行** ⇒
  内核 `DUPLICATE_DIMENSION_KEY` 直接拒。正确写法是把窗口渲染成 `["<时间维>:gte:<start>", "<时间维>:lt:<end>"]`
  拼进 `filters`（实测编译结果：`WHERE work_date >= 'X' AND work_date < 'Y' GROUP BY 1 LIMIT 1001`，
  半开区间、无 `ORDER BY`）。**不许改成 `lte end`** —— 那会把 end 当天算进来，两期边界重叠一天。
- ⚠️ **`time_dimension` 必须是 cube 的维度名**（`time_dimensions[].name`），**不是物理列名**：
  写成物理列名时报 `Error during planning: Unknown filter dimension '…' in cube '…'`（实测）。
  生产上两者多数同名，所以这条只在真出问题时才暴露 —— 白名单也按 §4.4 的 `time_dimensions` 键集取。
- **`limit` / `offset` 不要放进 args**：`_cube_sql_plan` 刻意传 `None` 给引擎（线上由 `sql_approval` 剥掉），
  `strip_cube_window` 会把它们摘出来只作为 `window_limit` 返给调用方（`wren_plan.py:311`）。

**取编译失败的原因用 `plan_cube_sql_checked`，不要用 fail-open 的 `plan_cube_sql`**：后者失败恒返回 `{}`，
「维度名/度量名写错」会退化成一句「编译不出 SQL」；`_checked` 抛 `CubePlanError`，引擎原话（`Unknown filter
dimension …`）进错误文本 —— 那正是 S3 的工具反馈给模型、让它自己改参数的唯一信号（实测在这上面耗掉一整个诊断脚本）。

**执行**：照 §3.2 的表格 —— `classify_sql`（闸①）→ `McpSqlConfig.from_env(db_name)` → 每条查询
`asyncio.run(runner.run_sql(RunSqlToolArgs(sql=sql), context))`。

⚠️ **不是「先把 `2+2D` 条都跑完、再按 label 取值」**（本条 2026-09-30 按实现更正）：
内核的协议是**按需取数**（`fetch_total(window)` / `fetch_grouped(dim, window, limit)`），
所以是「内核要一条、跑一条、把行 dict 交回去、内核自己按列名解析」。
label（`total@2026-08-01~2026-09-01` / `dim=dept_level1@…`）只进 `query_log` 做**取证**，
不参与取值 —— 取值靠列名的叶子归一（`_rows_from` 用**内核那一份** `column_leaf`，不复制第二份规则）。

- `_dbmcp_execute` **每条查询新建连接**（`MySQLRunner.__init__` 只存参数，`pymysql.connect` 在 `run_sql` 里），
  与 `api/feedback_annotation._run_preview` 同源：不持有跨请求的长连接，代价是 `2+2D` 次建连，换来**无连接态**。
- **不调 `_apply_default_limit` / 不 `split_sql_statements`**：发出去的已是编译产物（自带 `LIMIT 1001`、单语句），
  再改写一遍只会让 `query_log` 里那条 SQL **不再等于真正执行的语句**，而那条 SQL 是取证用的。
- `asyncio.run` 而不是 `await`：引擎的 `run_sql` 是 **async 外壳 + 同步实心**，`await` 只会把查询挂在循环上；
  而这段代码**本来就在工作线程里**（`run_attribution` 已把整趟 offload 出去），那条线程没有运行中的循环 ⇒ `asyncio.run` 合法。

> ⚠️ **`max_values_per_dimension` 在本仓换了含义，实现时必须按下面这套写，不要试图让 SQL 带上这个 limit**
> （§3.1 已查明 `plan_cube_sql` 的物理 `LIMIT` 写死 1001、不接受传参 —— **不要为了它去改 `plan_cube_sql`**）：
> - **判 `truncated` 用物理上限**：返回行数 ≥ 1001 才算真截断（此时同时打 `high_cardinality_dimension`）。
> - **`per_dimension.<dim>.values` 必须是本次取回的全部取值** —— 加法对账（§4.7 段②）断言的正是它，
>   少一个值就会让「Σ分组 ≠ 总量」凭空成立、把一个可加维度误判成不可加。**`top_n_values` 只裁
>   `top_dimension_values`**（跨维展示摘要），不裁 `values`。
> - **取值数落在 `max_values_per_dimension … 1001` 之间：不截断、不丢值**，只打 `high_cardinality_dimension`
>   提醒模型换更粗的维度（这正是 playbook 里那条纪律的触发点）。⇒ 这个参数的实际作用 = **触发警告的阈值** +
>   硬顶校验（`> _MAX_DIMENSION_VALUES(1000)` 直接拒，`INVALID_ARGUMENT`），**不再影响 SQL**。
>   参考实现里它同时是 SQL 的 `limit`，本仓没有这个自由度，所以**宁可改语义也不要留一个名不副实的参数**。

**循环必须顺序、不许并发**：`2+2D` 条走同一个 runner，且同一个库连接上并发会互踩（本仓 SQLite 的教训是
「共享连接 + 一把锁，读也要进锁」）。D ≤ 5 时 `2+2D = 12` 条顺序执行是秒级，不值得为它引并发。
**多度量也在同一趟里顺序跑**（不是每个度量一条线程）：整趟由 `run_attribution` **一次** `offload()`
搬进**同一条**工作线程，`attribute()` 在内核线程里逐度量同步跑完 —— 运行槽全局只有 10 个（§3.4①），
按度量或按维度 fan-out 就是拿并发去换一个本来只要几百毫秒的东西。

**列名归一**在这一层收口：把 `df` 的列统一成 `{leaf_name: value}`，叶名规则与内核 `_column_leaf` 同一份
（**引入内核里的那个函数，不要复制一份**），否则「编译出的别名带前缀」和「内核想要的裸名」两套规则会漂移。

### 4.4 S3 工具壳与注册

三件套照 [`report_builder.py`](../../src/agent/tools/report_builder.py)：
`AttributionAnalyzeSchema(BaseModel)`（:760 范式）→
`async def _attribution_analyze_coro(..., runtime: Annotated[ToolRuntime, InjectedToolArg()])`（:788 范式，
`runtime` 用于取 user / thread）→
`attribution_analyze_tool = StructuredTool.from_function(coroutine=…, name="attribution_analyze", description=…, args_schema=…)`（:1074 范式）。
**工具 docstring 里必须写 §1.1 的 T3 红线**（不用「原因/导致」，只说贡献度分解）—— 这是模型每次调用都会读到的地方。

入参缺省逻辑（§1.2 的五个可缺省参数）从 `runtime.state.get("answer_fingerprints")` 取最近一条，
**依赖 S8**（§4.9）—— S8 已落地，所以这条缺省分支是**活的**：`cube` / `measures` / `time_dimension` /
两期窗口一个不传也能算（工具直接读指纹），取不到才回 `NO_FINGERPRINT` 而不是猜。

**「最近一条」怎么定**（`_latest_task_id`）：优先按 `async_tasks` 里该 task 的
`last_updated_at` / `last_checked_at` / `created_at` 取最大；时间戳全缺（不同写者各写各的）时退回
**字典写入序的最后一条** —— `_merge_dict_by_key` 是 `dict(existing); update(new)` ⇒ 新写的键在末尾，
这是天然兜底。⚠️ 它只是启发式：并发多查询里**重查一个旧任务**也会把它挪到末尾，
所以模型随时可以用 `fingerprint` 显式指定是哪条（`NO_FINGERPRINT` 的文本里也提示了这条路）。

#### 入参：`measures` 是**列表**；形状闸在工具层、拒在**调用级**（2026-09-30 补充）

- **`measures: list[str]`**（原为单数 `measure`）：同 cube 的多个度量**一次调完** ⇒ 成本仍 `2+2D`（§2.1）。
  缺省时从指纹的 `final_cube_spec.measures` **原样取**（它本来就是列表）；再缺省 ⇒ `NO_FINGERPRINT`。
  **跨 cube 不在一次调用里**：`plan_cube_sql` 的 `args["cube"]` 是单值 ⇒ 模型按 cube 分次调用。
- **形状闸的位置**：用 `load_cube_metadata` 的 `measure_expressions` 判每个度量的算子形状（§2.3），
  **先于** `get_runner`（顺序见 §4.5：**闸② 判权更早** —— 越权时连 `project_path` 都不算；
  入参白名单要等元信息读出来才能判，所以排在它后面）。命中不支持形状 ⇒
  回 `UNSUPPORTED_MEASURE` / `NON_TERM_WISE_MEASURE`，**并把是哪几个度量点名**。
- **拒的粒度 = 调用级（一票否决）**：请求 3 个度量、其中 1 个是 `AVG` ⇒ **整次调用不产出任何数字**，
  而不是「算 2 个、静默丢掉 1 个」。理由：静默少算的那一个，模型会把它当成「没有变化」讲出来 ——
  比拒答坏得多（§1.1 那条红线）。工具在错误里给出可操作的话：「`avg_hours_per_record` 是 AVG（比值类），
  M1 不支持；去掉它后可重试」——模型自己改参数重试就完事了。
- **提示词必须点名「分次调用」**（§4.6 的 playbook）：模型天然倾向「一次调用把整份报告涉及的指标全覆盖」，
  而跨 cube 做不到；不说明白它会拿错 cube 硬塞，或干脆漏掉一部分指标不归因。

#### 注册到主 agent（2026-09-30 拍板）

**结论：工具挂主 agent，与 `build_report` 同层。** 三条理由，都不是「顺带」：

1. **指纹本来就在主 agent 的 state 里**（§4.9 写在 `MainAgentState`）。工具挂主 agent ⇒
   读指纹就是一次 `runtime.state` 取值，**没有跨图传值、没有新协议**。
   （早期草案把工具挂子 agent，那会构造出「指纹在主 state、工具在子 agent」的跨界读，
   一个本该是一次属性访问的动作变成一条必须设计的通路 —— 这个矛盾正是本轮审计抓出来的。）
2. **cube 元信息不需要 MCP 就能拿到**：`load_cube_metadata`（[`wren_call_extract.py:317`](../../src/agent/utils/wren_call_extract.py#L317)）
   是**进程内**读 `<project>/cubes/<cube>/metadata.yml`，不经过任何 MCP 循环。**先例就在主 agent 内**：
   `build_report` 用它取 cube 描述（[`report_builder.py:969`](../../src/agent/tools/report_builder.py#L969)）。
   所以「主 agent 拿不到 cube 元信息、无从选维度」**不成立** —— 那是只把 `describe_cube` 当唯一元信息源的结论。
3. **追问归因不必再起一次子 run**：用户问「刚才那个数为什么降了」时，主 agent 直接算。
   子 agent 的价值是「去查数据」，而这里的数据全部由本工具自己编译执行，**没有需要委派的部分**。

注册点（与 `build_report` 并列，**一行加法**）：

```python
# src/agent/main_agent.py:27
from agent.tools.attribution_analyze import attribution_analyze_tool

# src/agent/main_agent.py:270
tools=[*mcp_tools, build_report_tool, attribution_analyze_tool],
```

⚠️ **两处不要动**：
- **不改 `nl2sql.yaml` 的 `tools:`** —— 它只作用于 MCP 名字子串匹配与 `set_sub_tool_filter`
  （`nl2sql_agent.py:70-83`）；本地工具不经这条通道，加一个 `attribution_analyze` 模式只会留下无匹配的误导项。
- **不追加到 `nl2sql_agent.py:302` 的 `tools=[*resolved_tools, …]`** —— `resolved_tools` 只由 MCP `sub_tools`
  经 YAML 子串过滤而来，塞本地工具进去会污染子 agent 的工具面，而**子 agent 用不到它**（指纹不在子 state 里）。

#### 元信息读取：`load_cube_metadata` 要做一处**加法**扩展

现版只回 `{cube_description, measures: {name: desc}, dimensions: {name: desc}}` ——
**丢掉了 `expression` 与整个 `time_dimensions`**（`wren_call_extract.py:348-356` 只取 `name`/`description`），
而本工具两样都要：

| 要的字段 | 用途 | 现版有吗 |
|---|---|---|
| `measures[].expression` | 判算子形状 → `term_wise` / `AVG` / 比值 / `COUNT(DISTINCT)`（§2.3 / §3.6 的判定要**程序化**，不能靠 measure 名猜） | ❌ |
| `time_dimensions[].name` | `time_dimension` 入参的白名单（cube 级，**不在 `dimensions` 里**） | ❌ |

⚠️ **`load_cube_metadata` 返回的 `dimensions` 里没有时间维** —— 所以 §4.5③ 的「必须落在返回的集合内」这句话，
**对 `time_dimension` 而言前提不成立**，必须显式补上 `time_dimensions` 这一路，否则
`work_date` 会被判成非法维度（而它恰恰是工时库唯一的锚点 —— 归因必须有一个）。

处置：**给 `load_cube_metadata` 的返回纯新增平行键**（同一个文件已经读进来，不新写第二份 reader），
**既有三个键的形状一个字节都不动**：

```python
{
  "cube_description": str,                            # 原样
  "measures":   {name: description},                  # 原样，值仍是 str
  "dimensions": {name: description},                  # 原样，值仍是 str
  # ── 以下为新增（归因要的）──
  "measure_expressions":   {name: expression},        # 判算子形状（§3.6）
  "dimension_expressions": {name: expression},
  "time_dimensions":       {name: {"expression": str, "type": str, "levels": [str]}},
}
```

⚠️ **不要改成「把 `measures` 的值从 `str` 变成 `{"description":…, "expression":…}`」** ——
那是**破坏性改形状**，而 `report_builder:969` 拿 `measures[名]` 时预期的是字符串，
改完它的「业务口径」层会静默退化（渲染出 dict 或直接异常，而那是 fail-open 分支，**不会报错，只会变难看**）。
平行键虽然键名多了两个，但**同一次循环里一起填、不可能漂移**，而换形状是拿既有下游的稳定性去换省两个键名，不划算。
（这正是 §3.4 那条「补字段只许加法」的适用场合。）

**`time_dimension` 白名单 = `time_dimensions` 的键集**，与 `candidate_dimensions` 取 `dimensions` 的键集**分别校验** ——
两者在 yml 里是两个平级列表，混在一起校验会让 `work_date` 被误判非法（§4.5③ 已同步更正）。

#### 实施记录（2026-09-30 完成，`verify_attribution` 段⑭ 275/275）

`src/agent/tools/attribution_analyze.py`（新，工具壳 + 形状闸）、`main_agent.py` 两行注册、
`wren_call_extract.load_cube_metadata` 加法扩展 —— 三件都已落地。实施中查出的两条**方案没写、但不写就会踩**的事：

1. **`load_cube_metadata` 的两个既有键是 `dict`（`{名字: 描述}`），不是名字列表。**
   「缺省 `candidate_dimensions` = 该 cube 的全部维度」喂进去的是**键集**；只认 `list` 的归一化函数
   会把它静默读成**空集**，然后报「cube 没有可用维度（语义层声明为空）」——
   **把工具自己的类型疏忽说成语义层的问题**，模型拿到这句话只会去怀疑语义库。
   实测就是靠段⑭-⑨（端到端跑通、缺省维度）当场红的。（`_normalize_names` 现在也吃 dict 取键。）
2. **五样入参要「先判全、再读盘」。** `cube` 名是读 `load_cube_metadata` 的入参，所以直觉上要「先有 cube
   才能读元信息」；但**「缺哪几样」这一步一个字节都不用读盘** ⇒ 必须排在读盘**之前**，
   否则「没给 cube」先撞 `UNKNOWN_CUBE`、模型补上 cube 再来一次才被告知「还缺两期窗口」——
   **白烧一轮 LLM 往返**（而这个工具的调用方是 LLM，往返就是钱和延迟）。
   落地就是把五样抽成 `_resolve_required`（纯读指纹/入参），`_build_requests` 只收它的结果。
   ⚠️ 缺了给的是 `NO_FINGERPRINT` 而**不是** `UNKNOWN_CUBE`：前者「补参数即可」，后者「语义层里没有，重试无意义」——
   两条路的下一步动作不同（§2.2 那条码表已同步）。

**闸②（判权）与闸③（cube 目录名 / 维度名 / 时间锚点 / `filters` 白名单）见 §4.5**（2026-09-30 已落地，段⑮）。
⚠️ 但 `NL2SQL_ATTRIBUTION_ENABLE` **仍保持 `off`**（fail-closed，§4.8 的上线顺序）：S5 的**代码**（免截断）与
提示词**文件**都已落地，但提示词还没推到 Langfuse、代码也还没发版 ⇒ 线上模型既没被教过、也读不到 playbook，
现在开开关等于让一个没人教过的模型去调它。
在那之前工具**注册了但在工具面上是「明确拒」**，不是「静默算错」也不是「消失」
（消失会让模型以为工具不存在、转而去编）。

### 4.5 S4 三道闸（本工具不在任何现成中间件的名单里）

⚠️ **这是最容易被漏掉的一步**。现成的 SQL 护栏全部按**工具名后缀**匹配：
`_is_run_sql_tool`（`sql_approval.py:228`，`run_sql` 结尾）、`_is_cube_tool`（`sql_approval.py:128`，`query_cube` 结尾）、
`_is_query_tool`（`query_gate.py:206`，只认 `dbmcp_*` / `wrenai_*`）——
**`attribution_analyze` 一条都不命中 ⇒ 三个中间件一个都不会给它上闸**。闸必须建在工具内部：

1. **只读硬闸**：编译出的物理 SQL 过 `classify_sql`（`sql_approval.py:179`），`verdict == "write"` 直接拒 ——
   与 `_run_preview:255-257` 同法。这条是**纵深防御**（SQL 由我们编译，理论上必是 SELECT），
   代价只有一次正则，但它是「语义层被改坏/引擎行为变化」时的唯一兜底。
   位置在 `attribution_runner._compile_checked`（**取数通道里**，不是工具层）⇒ 任何调用方都绕不过。
2. **判权**：`grants.can_access_db(user, db_name)`（`grants.py:199`，调用范式 `feedback_annotation.py:605-607`）。
   ⚠️ `db_name` 用 **§1.2 三级解析后的值**（不是裸 `configurable`）；解析与判权**必须在建连接之前** ——
   越权时连 `project_path` 都不该算出来。
   工具是 agent 侧本地工具，**没有 REST 层替它做判权**，必须自己调。
   **身份解析照抄本仓既有约定**（`query_gate.py:359-365`、`tool_filter.py:78`）：
   `resolve_caller("attribution_analyze")` 回 `None` = 「**不启用**按用户判权」（内部调用 / dev 旁路 /
   读用户记录失败）⇒ **放行**；回 `dict` 才逐库判，不通过的拒。
   ⚠️ **本节原写的「从 `runtime` 取不到 user ⇒ fail-closed 拒绝」已作废**：那句话会把 dev34、离线套件、
   以及任何没有 config 上下文的调用整片拒掉，而真正的越权（身份真实、账号在、就是没授权）走的是
   `can_access_db` 的**正常 False** —— 该拒的照拒。工具内部自己发明 fail-closed 只会造出一个
   「别的工具能查、归因不能查」的孤岛，反而更难排查。两个被调函数各自已把读盘失败收敛掉
   （→ `None` / → `True`+warning），所以工具里**不需要也不该**再写 catch。
3. **输入校验**：四个名字各自对**正确的集合**校验（来源 = 进程内 `load_cube_metadata`，
   **不调 `describe_cube`**，见 §4.4），任一不命中就回带**名字**的错误码，**而不是把它拼进 SQL**：

   | 入参 | 校验集合 | 错误码 |
   |---|---|---|
   | `cube` | 项目下 `cubes/` 的**目录名集合**（先解析 `project_path`，见 §4.3） | `UNKNOWN_CUBE` |
   | `measures` | **逐个**都要在 `measures` 的键集内 **且** `measure_expressions[m]` 被算子形状判为 `term_wise`（§2.3）；**列表去重保序**，全空即在 `_resolve_required` 处拒 | `MISSING_MEASURE` / 形状类 |
   | `candidate_dimensions` | `dimensions` 的键集 | `MISSING_DIMENSION` |
   | `time_dimension` | **`time_dimensions` 的键集**（⚠️ 与 `dimensions` 是**两个平级列表**，不是子集关系 —— 混用会把 `work_date` 判成非法） | `MISSING_TIME_DIMENSION` |

   ⚠️ **`measures` 的校验是「全部通过才算过」**（一票否决，§4.4）：失败时错误文本要**点名**是哪一个度量、
   原因是什么（`avg_hours_per_record` 是 `AVG`）—— 模型据此删掉它重试即可。

   ⚠️ **`cube` 那一格顺带关掉了路径穿越**：cube 名会被拼进文件路径（`cubes/<cube>/metadata.yml`），
   `cube="../../x"` 能让它越出项目目录读另一份 yml。先判目录名成员，这条路径**按构造**就不存在
   （目录名里不含路径分隔符）；判成员必须**排在 `load_cube_metadata` 之前**。
   代价是「目录在、`metadata.yml` 读/解析失败」与「名字不在 `cubes/` 里」同码不同因 ⇒ 错误文本分开写。

   `filters` 的 `operator` 限 `FILTER_OPERATORS` 枚举、`dimension` 限
   **`dimensions ∪ time_dimensions`** 白名单、`value` 原样交给引擎（不经字符串拼接、**不自己转义** ——
   wren 侧 `'` → `''` 已实测，我们自己再转一遍只会把安全值转坏，见 `render_filter_spec` 的实测记录）。
   维白名单要并上时间维度：窗口下推本身就是同一形状的过滤（`work_date:gte:…`），把时间维度判成非法会让
   「只归因某一年」这类**合理**请求无法表达（`_compile_filters` 里那条 AND 叠加的日志正是为它写的）。
   ⚠️ `AttributionFilter.operator` 是 `str` + `json_schema_extra` 的 enum —— **pydantic 不校验它**
   （段⑮ 有一条断言专门证明 `operator="like"` 构造得出来）⇒ 这道闸是唯一拦它的地方。故意不用
   `Literal`：pydantic 校验失败会在工具里抛异常（错误形状与其它拒答不一致），而这里要的是同一套
   `to_payload()` 机读形状 + 允许集合清单。

**实施记录（2026-09-30，段⑮ 295/295）**：闸② 建在工具内、**排 `resolve_wren_ctx_by_db` 之前**
（源码顺序也被一条断言钉住）；闸③-a 是 `_list_cubes`（只列**有 `metadata.yml`** 的目录 —— 列进来却读不出来的
名字会让模型按提示改完还是被拒）。新增三个错误码进 §2.2 那张表：`DB_NOT_AUTHORIZED` / `MISSING_DIMENSION` /
`MISSING_TIME_DIMENSION`（不复用 `MISSING_DIMENSION_COLUMN` —— 那个是「结果集里缺列」，语义不同，
混用会让机读归因失去意义）。四条端到端负对照全部确认**零编译、零 project_path / 零建连接**。

**顺带一个结构性收益**：闸建在工具内以后，本工具对「模型能往物理 SQL 里送什么」的回答是
**「只有列名和值，且都在白名单内」** —— 比「事后 classify 拦截」强一个档位。
