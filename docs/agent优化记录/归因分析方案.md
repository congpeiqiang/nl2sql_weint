# 归因分析方案（维度贡献分解）

**日期**：2026-09-29　**状态**：方案定型，未实施（代码一行未动）
**需求来源**：「如果用户查询完问题，想基于返回的答案做进一步归因分析或者直接做归因分析，有什么方案？」
**参考实现**：Datus-agent（开源，HEAD `f58c766`）的 `attribution_analyze`。本方案的算法与护栏**逐条移植**它已被生产验证的
`GenericAttributeAnalyzer`，证据见附录 A。

**一句话方案**：把归因当成**确定性计算问题**，不是模型能力问题 —— 移植 Datus 的归因内核（加法分解 + 11 项护栏），
**复用本仓已有的 wren 编译链**（`plan_cube_sql` 产出的就是归因要的 `GROUP BY` SQL），在**一次工具调用内**跑完 `2+2D` 条聚合，
模型只负责**选维度、选期间、写解读**。

> **收益口径**：不在于「模型会算贡献度」（它算不对），而在于把「哪个部门/项目贡献了这次变化」变成
> **可复算、可审计、能贴给业务**的一份产物 —— 且**每条结论能点到真实 SQL**。

## 一、方案定义

### 1.1 做什么、不做什么

| | 内容 | 判定 |
|---|---|---|
| **做 T1** | 维度贡献分解：ΔY = Σ_d ΔY_d（加法型，**可精确加总**） | ✅ 完全确定，逐值给 `delta` / `contribution_pct` |
| **做 T2** | 结构-强度分解：Δ(Y/X) = 结构效应 + 强度效应（比率型） | ✅ 确定（算法有标准解），逐值给 `mix_effect` / `rate_effect` |
| **不做 T3** | 因果归因：「到底为什么会降」 | ❌ 反事实推断**单靠数据不可确定** |

**T3 红线**：产品文案只能用「贡献度分解 / 归因分解」，**不许出现「原因」「导致」**。
理由是归因恰好是幻觉最容易被当成结论的地方（本仓已两次吃过同类亏：「78 个部门」幻觉、`_extract_last_sql` 取错 SQL）。
**这条写进工具 docstring 本身**（每次调用模型都读到），比写在文档里可靠。

**同样不做**：明细级归因（逐条比对，会撞行数上限且量级完全不同）；native 双路径（我们没有可下推的引擎，只有一条路）。

### 1.2 工具契约

新增**本地工具**（与 `build_report` 同级注册，**不走 MCP 循环**）：

```
attribution_analyze(
    cube: str, measure: str,                        # 指标标识（describe_cube 锁定）
    baseline: [start, end], current: [start, end],   # 半开区间 [start, end)，与 Datus 同契约
    time_dimension: str,                             # 必填，归因时间锚点
    candidate_dimensions: list[str] | None = None,   # 缺省 = 自动取 cube dimensions
    where: str = None,                               # 全局过滤（下钻续查时传入）
    top_n_dimensions: int = 3, top_n_values: int = 10,
    max_values_per_dimension: int = 500,             # 硬顶 1000
) -> { total_change, strategy, dimension_ranking, selected_dimensions,
      top_dimension_values, per_dimension, warnings, comparison_metadata }
```

- **返回字段名逐字对齐 Datus**：`total_change.{baseline_value,current_value,delta,pct_change}`、
  `per_dimension.<dim>.values[].{delta, contribution_pct, segment_kind, drill_down.where_sql}`、`warnings[].code`。
  理由：可对照参考实现、便于将来核对；**不自创词汇**。`strategy` 字段留位，M1 只产 `term_wise` / `unsupported`。
- **`drill_down.where_sql` 由工具生成**（值做转义、NULL 走 `IS NULL`），不是 LLM 自由文本 ⇒ 堵死注入。
- **参数透传记入 `comparison_metadata`**，以备审计。

**分工是这份方案的核心**：**代码**决定分解算法、生成 SQL、算贡献、排序、落盘可复算产物；
**模型**只负责**选维度、选期间、写解读** —— 且解读受第四章的提示词纪律约束。

## 二、内核：算法与护栏

### 2.1 算法（`2+2D` 条查询）

1. **两期窗口校验**：ISO 半开区间 `[start, end)`，天数 ≤ 0 直接报错。
2. **两期总量**：不带维度的聚合各一次 → `total_delta`。
3. **逐候选维度**：`GROUP BY dim` 两期各一次，`limit = max_values_per_dimension + 1` ——
   **多取一行专门用于判截断**（不靠 COUNT 预估）。
4. **并集分解**：两期维度值取并集，逐值 `delta = current - baseline`、`contribution_pct = delta / total_delta × 100`。
5. **维度打分**：`score = max|delta_i| / |total_delta|` → 排序取 top-N 维（默认 3）+ 每维 top-N 值（默认 10）。

**成本公式：`查询数 = 2 + 2D`**（D = 候选维度数）。**所有候选维度都会被查**，之后才排名筛 top-3。
维度是模型给的（`candidate_dimensions`），所以成本可控、可预算 —— 这直接决定第四章的 D 该定几个。

### 2.2 护栏（可靠性的全部来源）

| 护栏 | 行为 | 为什么必须有 |
|---|---|---|
| **可加性对账** | `Σ分组值` vs 期间总量，容差 `0.02`；不过的维度打 `non_additive_dimension` 警告并**踢出排名** | 不可加维度（去重计数、比率）的「贡献度」是假的；宁可不出，不可出错的 |
| **高基数截断** | `truncated` + 警告；测试钉住**按 \|delta\| 排序、主因不被截掉**（`max_values_per_dimension=1` 仍返回 −2900 那个收缩项） | 截断掉主因是最坏结果；排名必须按影响量而非取值名 |
| **取值进出** | `segment_kind ∈ {normal, entered, exited}` | 「新增/消失的部门」不是贡献度，是结构变化，必须区分 |
| **零变化省略** | Δ≈0（`< 1e-6`）时 `contribution_pct` **整个字段省略**（不是 `null` / `0` / `inf`） | 除以 0 会产出 `inf`，模型会把它当「无限大贡献」讲出来 |
| **零总变化但有分量变化** | `zero_total_delta_with_component_changes` → 提示「用绝对增量解读，不要用百分比」 | 分子分母同时消失时百分比无意义 |
| **两期不等长** | 只给 `unequal_windows` 警告，**不静默归一化** | 静默折算等于编数据 |
| **逐维故障隔离** | 单维失败 → `dimension_analysis_failed`，**继续跑其余维度** | 一个维度炸掉不该让整次归因没有输出 |
| **当期不完整** | `incomplete_current_period` 警告，**绝不按比例折算** | 按比例折算等于用半段数据外推，会凭空造出一个「下降」 |
| **NULL ≠ 字符串** | SQL NULL 与字面量 `'(null)'` 是**两个成员**，下钻分别走 `IS NULL` / `= '(null)'` | 合并两者会算错一整类数据 |
| **类型化错误码** | `MISSING_METRIC_COLUMN` / `MISSING_DIMENSION_COLUMN` / `DUPLICATE_DIMENSION_KEY`（提示「可能是隐式时间粒度」）/ `NON_NUMERIC_METRIC_VALUE` / `MULTI_ROW_TOTAL` / `INVALID_TIME_WINDOW` | 失败要能机读归因，不能只有一句自然语言错误 |
| **参数透传** | 入参完整记入 `comparison_metadata` | 出问题时能复算 |

### 2.3 策略由度量表达式的**形状**决定，不是声明、不是模型选

| 度量定义 | 表达式形状 | 分类 |
|---|---|---|
| 加法型 | `SUM(x) ± SUM(y)` | `term_wise` |
| 比率型 | `AVG(x)` / 比值 | `mix_shift`（自动脱糖为结构效应 + 强度效应） |
| 乘积型 | `SUM(x) × SUM(y)` | `factor_shapley` |
| 不可加 | `COUNT(DISTINCT …)` | `unsupported`（**不是工具失败**，`success == 1`） |

**验收判据是「能不能对上账」**，不是「故事讲得像不像」——参考实现的手算 oracle 全部用**精确相等**断言：
`term_wise` 的 `Σdelta == total delta`；`mix_shift` 的 `mix_effect + rate_effect == delta` 且 `factor_totals.residual ≈ 0`；
`factor_shapley` 的 `Σfactors[].effect == total delta`。

⚠️ **M1 只做 `term_wise`**：`mix_shift` / `factor_shapley` 的算法本体是私有包（不在本机、读不到），
只有从集成测试的手算 oracle 断言反推出的输入输出语义。**M4 若要做，需先拿到实现**。

## 三、落到本仓

### 3.1 复用 wren 编译链：归因要的 SQL 就是它

- 入口：[`wren_plan.py:353`](../../src/agent/utils/wren_plan.py#L353) `plan_cube_sql(project_path, conn, args)`
  → `{"cube_sql","dialect_sql","dialect","limit_appended","dup_limit"}`（fail-open 返回 `{}`）。
- 真身：`.venv/.../wren/cube_cli.py:297-300` `_build_cube_query(cube, measures, dimensions, time_dimension, filters, limit, offset)`
  + `cube_query_to_sql` ⇒ **产物天生就是 `SELECT dim…, SUM(m)… GROUP BY dim…`**。
- ⇒ **归因不需要自己拼 SQL、不需要新引擎**，只是把「维度集合」从 1 个换成 `2+2D` 次调用、把「期间」从 1 个换成 2 个。
- 另有 `query_cube(..., sql_only=True)` 只回 SQL 不执行（`.venv/.../wren/mcp_server.py:150-155`）
  ⇒ **可以先审 SQL 再执行**，天然适配本仓审计文化。
- **分组结果的行数天然安全**：只有「维度取值数 × 2 期」，远低于 `DEFAULT_ROW_LIMIT=1000`。
- ⚠️ cube 的 `hierarchies` 只是**可选**：wren 侧只被**渲染进 schema 描述**，没有引擎级「沿层级聚合」API
  ⇒ 层级链展开要我们自己多跑几次 `plan_cube_sql`，**不是一次调用**。下钻本身靠现场生成 `where`，不依赖层级声明。

### 3.2 执行路径（关键决策）

**一次工具调用内完成全部 `2+2D` 条聚合 SQL**：主进程常驻引擎编译（`_engine_for` 缓存，亚毫秒）→
现有物理库连接逐条执行 → `attribution_core` 内存分解 → 返回结构化 JSON。**中间查询对 LLM 完全透明。**

⚠️ **禁止走「MCP 循环调 `query_cube`」**：MCP 子进程单次调用实测 **2.5~4.2s**，
D 个维度需 `2+2D` 次子进程调用（5 维 ≈ **40s+**），**必须一次工具调用内完成**。

### 3.4 必须守的五条约束

**① 绝不许按维度 fan-out 子任务。** run 槽全局 = **10**（`start_server.py:93`；真约束在 `.venv/.../langgraph_runtime_inmem/queue.py:91-95`），
**一次问数已吃掉约 3 个槽**（主 run + 子 run + 续跑主 run），**子任务消耗同一个池**。
5 个维度并行 = 5 槽 ⇒ **2 个并发用户就打满**。归因必须在**同一个 run 内顺序循环**，且最好一次工具调用内跑完 `2+2D` 条。

**② 归因结论必须带「业务口径」节，并过逐字核验。** 归因最容易出的错是**用不属于该口径的维度去分解** ——
例：口径写明「派遣工不计入在职」，却按「用工性质」分解在职人数；结论看着头头是道，口径上根本不成立。
复用现有机制：契约在子 agent 提示词末尾（[`NL2SQL_SYSTEM_PROMPT.md:269`](../../src/agent/prompt/NL2SQL_SYSTEM_PROMPT.md#L269)）、
抽取 `parse_caliber_block`、**逐字核验** `verify_caliber_entries`（[`caliber_evidence.py:391`](../../src/agent/utils/caliber_evidence.py#L391)）。

**③ 数字必须由代码算，模型不许自己加减。** 本仓两次同类教训（`_extract_last_sql` 取错 SQL、「78 个部门」双表计数错）。
参考实现更彻底：**指标/归因结果的唯一出口就是数值工具**，且下钻 `where` 由工具生成。

**④ 归因结果免截断，且不许被读成低分。**
`attribution_analyze` 必须进 slimmer 白名单（`SUMMARY_TOOLS_NO_CLIP`：**数字本身就是交付物**，与文件系统工具同级）；
提示词必须写明**「掉出 `dimension_ranking` 的维度不是低分维度」**，否则静默降级会被模型转述成结论。
（本仓曾因 `MessageSlimmer` 按行截断弄丢 `</iframe>` —— 归因数字与图表同类。）

**⑤ 降级路径必须闸住口径。** 语义层覆盖不到的目标（非 cube measure）只允许一条降级路：
**手写环比 SQL，并显式标注「口径不可比」**，且该结果**不得进入归因结论**。
理由：参考实现的归因面**没有裸 SQL 出口**（工具白名单里没有任何 db/sql 工具），
它宁可回答「没有合适指标」也不回落 SQL。我们允许降级是因为存量语义库覆盖不全，
但**降级产物与语义层产物混在一份结论里，就是 ② 那类错误的入口**。

## 四、提示词纪律

参考实现的归因纪律**只有 17 行**，没有归因专属 skill、没有专属提示词模板 ——
全部在 `ask_metrics_system_1.0.j2:58-74` 的 `## Attribution Playbook`，**逐字移植**：

```jinja
## Attribution Playbook
- Treat attribution as descriptive change decomposition; it does not establish causation.
- Use `get_dimensions` to choose 3-5 low-cardinality categorical candidates. Exclude time
  dimensions and numeric measures, IDs, or high-cardinality fields unless the user explicitly needs one.
- `attribution_analyze` uses the same OSI half-open `[start, end)` time-range contract as `query_metrics`.
- Use equal-length baseline and current windows. If the result contains `unequal_windows`,
  disclose that values were not normalized before comparing them.
- Read the observed change from `total_change`. If `strategy` is `unsupported`, disclose
  `unsupported_reason` and do not give a dimension-attribution conclusion.
- Read detailed contributions from `per_dimension.<dimension>.values`. Never compare or add
  contribution percentages across different dimensions. `top_dimension_values` is only a
  cross-dimension display summary.
- Do not interpret a dimension whose `non_additive` or `truncated` flag is true. A dimension
  omitted from `dimension_ranking` because it failed, was non-additive, or was truncated is
  not a low-scoring dimension.
- For `mix_shift`, distinguish `mix_effect` from `rate_effect`. For `factor_shapley`, use
  `factors` to explain factor effects before discussing dimension values.
- To drill into a top value, reuse its `drill_down.where_sql` as `where` and retain every
  parent filter from prior drill-down calls.
- Always disclose attribution `warnings`:
  - With `non_additive_dimension`, do not interpret that dimension's percentages as an additive decomposition.
  - With `no_data_*`, `null_total_*`, or `zero_or_no_data_*`, do not give an attribution
    conclusion; first confirm coverage with `query_metrics`.
  - With `zero_total_delta` or `zero_total_delta_with_component_changes`, explain structural
    movement using absolute component deltas, not contribution percentages.
  - With `high_cardinality_dimension`, attribute a coarser dimension first and use `where` to narrow.
  - With `dimension_analysis_failed`, disclose the affected dimension and continue with successful ones only.
```

**三条配套硬规则**（同文件）：

- `:26` **数值工具是唯一能产出指标/归因结果的入口**（不探索原始表、不写 SQL、不猜指标值；没有合适指标就直说，**不回落裸 SQL**）。
- `:15-18` **`get_dimensions` 必须早于** grouping / filtering / 归因 / 选时间粒度 —— 先看维度清单再选候选。
- **候选维度定死 3-5 个** ⇒ 成本即可预算为 **8~12 条聚合 SQL**（`2+2D`，D=3~5）。这个数字是延迟预算的前提。

▸ **不另立 skill 协议**：纪律就是这 17 行。省掉一整套 SKILL.md 的维护面。
