> 参考 DeepSeek Harness 的 7 层轨迹架构，针对 NL2SQL 多智能体场景设计
> 日期：2026-08-22（2026-08-23 更新）
> 状态：**Phase 1（后端事件日志 + 会话谱系 + trace API）已实施**；
> 前端轨迹可视化（原 Phase 3）**取消**，后期计划接入 **Langfuse** 作为外部追踪。

---

## 一、DeepSeek Harness 轨迹能力分析

DeepSeek Harness 的轨迹系统是一个 **7 层架构**：

| 层 | 名称 | 核心能力 |
|---|---|---|
| L1 | Session Event Log | 单调递增的 `seq` 事件日志，所有交互的规范数据源 |
| L2 | Session Persistence | JSONL/SQLite 持久化，支持压缩、批写、崩溃修复 |
| L3 | Session Telemetry | OTel 导出 + 脱敏瀑布流 + 三种模式 (FULL/FEEDBACK_ONLY/DISABLED) |
| L4 | Session Projection | 基于事件日志的 eager fold 计算视图（SessionStats, TokenUsage） |
| L5 | Session Query | 事件回溯（traceEvent）、会话谱系（traceSession）、全文搜索 |
| L6 | Session Log Export | 浏览器端 ZIP 下载（含后代会话和附件） |
| L7 | Feedback System | 用户反馈记录 + 反馈门控遥测导出 |

其中 **对 NL2SQL 最有价值** 的能力是：

1. **L5 会话谱系追踪** — `traceSession(id)` 能追踪所有祖先和后代会话，构建树形结构。这对 NL2SQL 的 **多智能体架构**（chat_agent → nl2sql_agent）至关重要
2. **L1 统一事件日志** — 将所有交互归一化为 `SessionEvent`，解决当前 NL2SQL 日志分散（LangSmith + 自定义中间件 + 临时文件）的问题
3. **L5 事件回溯** — `traceEvent(seq)` 返回替换链、源事件、派生事件，对调试 SQL 生成流程价值极高
4. **L4 计算投影** — 基于事件日志的统计视图，不受 compaction 影响，比当前 TokenMeter 的 state 内累积更可靠

## 二、NL2SQL 当前状态 vs 目标

### 已有能力（无需重建）

| 能力 | 实现 | 评价 |
|---|---|---|
| 外部追踪 | LangSmith (`LANGSMITH_TRACING=true`，可选） | 开发环境可用，**生产环境可能关闭**；不能作为唯一追踪通道 |
| Token 计量 | `TokenMeterMiddleware` → `state.token_stats` | 可被 TraceRecorder 替代（双写 EventStore + state） |
| 进度追踪 | `ProgressTrackerMiddleware` → 临时文件 | 可改造为事件日志的一部分 |
| 前端统计 | `StatsLine` 组件 | 已有，可增强 |
| 会话导出 | `GET /api/threads/{tid}/export` | 已有，需增强为包含完整事件日志 |
| 反馈存储 | `feedback/store.py` (SQLite) | 已有，可关联到事件 |

### 缺失能力（需要新建）

| 能力 | DeepSeek Harness 对应 | NL2SQL 多智能体场景的重要性 |
|---|---|---|
| **多智能体会话谱系** | L5 `traceSession` | ⭐⭐⭐ 核心：chat_agent 父子关系、并发多查询任务树 |
| **统一事件日志** | L1 Session Event Log | ⭐⭐⭐ 核心：当前日志分散，无法跨 agent 关联。生产环境无 LangSmith 时是**唯一全量日志** |
| **事件级查询** | L5 `traceEvent` / `searchEvents` | ⭐⭐⭐ 高：生产环境无 LangSmith 时，这是**唯一调试手段** |
| **计算投影** | L4 Session Projection | ⭐⭐⭐ 高：跨 agent 的 token 统计、耗时分析。生产环境无 LangSmith 时替代 LangSmith 的统计面板 |
| **OTel 导出** | L3 Session Telemetry | ⭐ 中：可选，本地 API 已覆盖核心调试需求 |
| **脱敏瀑布流** | L3 Redaction Waterfall | ⭐ 中：SQL 含敏感数据时需要 |

## 三、多智能体场景的特殊挑战

NL2SQL 的多智能体架构引入了 DeepSeek Harness 单智能体场景没有的复杂性：

```
chat_agent (thread_A)
  ├─ 思考 → 调用 start_async_task("nl2sql", "查询销售额")
  │   └─ nl2sql_agent (thread_B, task_id=xxx)
  │       ├─ Phase 0: WrenAI 语义预处理
  │       ├─ Phase 1: Schema 知识获取
  │       ├─ Phase 2: SQL 生成 (策略 A/B/C)
  │       └─ Phase 3: 纠错重试 (最多 3 次)
  ├─ sync_thread → 轮询 thread_B 状态 → 写回 thread_A state
  ├─ 前端 auto-continue → chat_agent 继续
  └─ chat_agent 渲染图表 + 生成报告
```

**关键挑战：**

1. **跨 thread 事件关联** — chat_agent 的 `start_async_task` 工具调用 与 nl2sql_agent 的完整执行过程 需要关联
2. **并发多查询** — 同一 chat_agent 可能同时有多个 nl2sql_agent 子任务（不同 task_id），事件需要按 task_id 分组
3. **sync 线程写入** — sync_subagent_todos 的 state 写入 不是标准的事件流，需要纳入事件日志
4. **auto-continue** — 前端的自动续跑 是会话谱系中的关键节点

### 4.2 事件模型设计

```python
# src/agent/trace/event_log.py

from dataclasses import dataclass, field
from enum import Enum
from typing import Optional
import time

class EventType(str, Enum):
    # 会话生命周期
    SESSION_CREATED = "session/created"

    # 用户交互
    USER_MESSAGE = "user/message"
    ASSISTANT_MESSAGE = "assistant/message"
    ASSISTANT_CHUNK = "assistant/chunk"      # 流式 delta

    # LLM 调用
    LLM_CALL_START = "llm/call_start"
    LLM_CALL_END = "llm/call_end"           # 含 usage_metadata

    # 工具调用
    TOOL_CALL_START = "tool/call_start"
    TOOL_CALL_END = "tool/call_end"          # 含 result

    # 多智能体
    SUBAGENT_SPAWN = "subagent/spawn"        # start_async_task
    SUBAGENT_COMPLETE = "subagent/complete"  # 子 agent 完成
    SUBAGENT_PROGRESS = "subagent/progress"  # sync 线程写入

    # 系统事件
    AUTO_CONTINUE = "system/auto_continue"   # 前端自动续跑
    STATE_UPDATE = "system/state_update"     # sync 线程 updateState
    ERROR = "system/error"

@dataclass
class TraceEvent:
    seq: int                          # 单调递增序号（per thread）
    thread_id: str                    # LangGraph thread_id
    agent_type: str                   # "chat_agent" | "nl2sql_agent"
    task_id: Optional[str] = None     # 子任务 ID（多查询场景）
    parent_thread_id: Optional[str] = None  # 父 thread_id（子 agent）
    event_type: EventType
    timestamp: float = field(default_factory=time.time)
    data: dict = field(default_factory=dict)  # 事件载荷
```

#### 4.4.1 TraceRecorderMiddleware（事件采集）

```python
# src/agent/middlewares/trace_recorder.py

class TraceRecorderMiddleware:
    """
    在 chat_agent 和 nl2sql_agent 的 middleware 链中安装。

    截获事件：
    - awrap_model_call: LLM 调用开始/结束 + Token 用量
    - awrap_tool_call: 工具调用开始/结束 + 结果
    - 特别处理 start_async_task → 记录 SUBAGENT_SPAWN + 建立 lineage
    """

    def __init__(self, db_path: str, agent_type: str):
        self.store = EventStore(db_path)
        self.agent_type = agent_type
        self._seq_counter: dict[str, int] = {}  # thread_id → seq

    async def awrap_model_call(self, request, handler):
        thread_id = get_thread_id()
        self._record(thread_id, EventType.LLM_CALL_START, {
            "model": request.model_name,
            "input_message_count": len(request.messages),
        })

        start = time.time()
        response = await handler(request)
        elapsed_ms = (time.time() - start) * 1000

        self._record(thread_id, EventType.LLM_CALL_END, {
            "elapsed_ms": elapsed_ms,
            "usage": _extract_usage(response),
        })
        return response

    async def awrap_tool_call(self, request, handler):
        thread_id = get_thread_id()
        tool_name = request.tool_call.get("name", "unknown")

        # 特殊处理：子 agent 启动
        is_subagent_spawn = (tool_name == "start_async_task"
                             and self.agent_type == "chat_agent")

        self._record(thread_id, EventType.TOOL_CALL_START, {
            "tool": tool_name,
            "args_summary": _summarize_args(request.tool_call),
        })

        result = await handler(request)

        if is_subagent_spawn:
            # 从 result 中提取 sub_thread_id
            sub_thread_id = _extract_sub_thread_id(result)
            task_id = _extract_task_id(request.tool_call)
            if sub_thread_id:
                self._record(thread_id, EventType.SUBAGENT_SPAWN, {
                    "sub_agent_type": "nl2sql",
                    "sub_thread_id": sub_thread_id,
                    "task_id": task_id,
                })
                # 建立 lineage
                self.store.upsert_lineage(
                    thread_id=sub_thread_id,
                    parent_thread_id=thread_id,
                    agent_type="nl2sql_agent",
                )

        self._record(thread_id, EventType.TOOL_CALL_END, {
            "tool": tool_name,
            "result_summary": _summarize_result(result),
        })
        return result
```

      ├─ nl2sql_agent (task_1: "查询销售额")

## 七、设计决策总结

| 决策 | 选择 | 原因 |
|---|---|---|
| 存储引擎 | SQLite（与 checkpoint/feedback 一致） | 不引入新依赖，已有 SQLite 基础设施 |
| 事件采集方式 | Middleware（非侵入式） | 不改动 agent 代码，通过 middleware 链安装 |
| Token 计量 | 保留 `TokenMeterMiddleware`，TraceRecorder 只记事件 | 双写同一字段会 reducer 累加重复（实测翻倍） |
| 前端轨迹可视化 | **取消**（原 Phase 3） | 后期接入 Langfuse 承担外部追踪/可视化 |
| 外部追踪 | LangSmith（可选）→ 后期 **Langfuse** | 生产环境可无 LangSmith；Langfuse 接入时 EventStore 仍是本地兜底 |
| 外部导出 | 暂不实现 OTel（Phase 4 可选） | Langfuse 后期接管，OTel 非紧急 |
| 前端轮询 | 复用现有 1s/10s 轮询 | 事件日志通过 API 按需查询，不增加轮询负担 |
| 工作区隔离 | 与 checkpoint/feedback 一致，per workspace | 保持架构一致性 |

## 八、Langfuse 接入计划（后期）

> 前端不实现轨迹可视化，后期接入 **Langfuse** 作为外部追踪/可视化。本方案为预留方向，
> 实施时间另行评估。接入时本地 EventStore（Phase 1）**保留不动**，作为
> 「无 Langfuse 环境」的本地兜底与数据源，不因接入 Langfuse 而移除。

### 8.1 为什么选 Langfuse

| 维度 | Langfuse | 本地 EventStore |
|---|---|---|
| 追踪可视化（trace timeline） | ✅ 现成 | ❌ 前端可视化已取消 |
| Token/成本统计面板 | ✅ 现成 | ⚠️ 需自建投影 |
| 多智能体 span 关联 | ✅ LangGraph callback 自动 span | ✅ 谱系树（手动实现） |
| 生产环境依赖 | 需部署/托管 | ✅ 零依赖，自包含 |
| 数据私有性 | 数据出本地（除非自托管） | ✅ 全在本地 SQLite |

### 8.2 推荐接入方式

Langfuse 官方提供 **LangGraph 回调集成**（`langfuse` SDK + `CallbackHandler` /
`LangfuseLanggraphHandler`），通过 LangGraph 的 `get_stream_writer` / callbacks 自动捕获
LLM 调用、工具调用、子 agent span，无需改 agent 代码。

```python
# 规划：langfuse_client 初始化（环境变量 LANGFUSE_PUBLIC_KEY / LANGFUSE_SECRET_KEY /
# LANGFUSE_HOST 可控开关，参照现有 LANGSMITH_TRACING 模式）
# from langfuse.callback import CallbackHandler
# handler = CallbackHandler(...)  # 通过 run_config/回调注入
```

对接要点：
1. **开关可控**：`LANGFUSE_ENABLED` 环境变量门控，默认关闭，生产可选开启
2. **与本地 EventStore 并存**：Langfuse 负责外部可视化/统计；EventStore 负责本地
   自包含回溯（无外部服务时仍可查 `/api/traces/...`）
3. **多智能体 span**：LangGraph callback 天然产出 chat_agent → nl2sql_agent 的嵌套 span，
   可替代本地谱系树的「可视化」职责；本地谱系仍保留用于 lineage 结构化查询
4. **隐私**：SQL 结果可能含业务数据，若需外接需评估脱敏（参照 MessageSlimmer 截断策略）
5. **迁移路径**：若后期决定 EventStore 不再需要，可移除 trace 中间件与 API；
   当前先保留，成本低、无外部依赖风险
