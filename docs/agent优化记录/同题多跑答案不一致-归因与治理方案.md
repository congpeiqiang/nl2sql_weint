## 1. 背景与一句话结论

同一问题、同一库、同一模型、同一 prompt、同一套技能集，三次运行（`8f8d…bb1` / `dbe6…90f` / `6a59…807`）给出三种结局：**18 人 / [需要澄清] / 12 人**。

> 结论：这不是配置差异，而是「应报工人员池」口径无权威定义 + 澄清门触发不稳定 + 跨线程/跨 run 上下文检索泄漏（含读到 eval 参考答案）+ 底层数据在评测窗口内漂移」四类因素叠加导致。模型采样只是放大器。

## 3. 事实核对：三次运行配置一致

已对三份 trace 的 metadata / observations 做全量比对，**非差异项**如下（采样噪声之外的自由度几乎为零）：

- 用户问题 `user_question` 完全一致：`上周有都有谁没有报工`；库 `db_name` 一致：WIT运营管理平台数据库
- 全部 GENERATION 观测 `model` = `deepseek-v4-flash`（ChatDeepSeek），无混模型
- prompt 一致：`prompt_label=production / version=1 / source=langfuse`
- 可用技能集与版本一致：15 个 skill，含 `nl2sql-clarification`/`sql-of-thought`/`knowledge-loader v0.2.0` 等，全部 `source=local`
- agent/graph 一致：`main_agent`（顶层）→ `nl2sql_agent`（委派子任务）
- metadata 差异项仅 `langgraph_step`、`checkpoint_ns`、`langgraph_parent_trace_id`、时间等固有字段；`metadata.skill` 字段（T1/T3=`nl2sql-sql-of-thought`，T2=`sql-of-thought`）为最后一次 span 归属名，非配置差异

> 因此三结果差异 = **非确定性/路径依赖**，而非实验配置（如模型、prompt、技能版本）差异。

## 4. 根因分析（每条附 trace 内证据）

### 4.1 应报工人员池口径无权威定义 —— 结构性根因

库/schema/knowledge 中**没有字面「报工」概念**，也没有业务口径规则。T2 检索后明确记录：schema 中"报工"无匹配（grep 为空）、`get_instructions()` 业务规则为空模板、`recall_queries()` 返回空（03:11 摘要）。于是"谁算应报工"只能靠模型猜，而候选口径人数差很大：

- `do_department_user_detail`（在职）：1139 行 / 307 个 user 的**宽表**，仅 `deleted='0'` 为当前在职 190 人（T1 口径 → 18）
- `do_table_user`（月度报工花名册）：按 `table_month_id` 分月，2026-08=`33` 共 **184** 人（T3 口径 → 12）
- "当周有出勤的人" 等其它口径

证据：T1 在过程摘要里自己也标注过 `do_table_user …是待验证的另一个"应报工人员池"候选口径`（02:53），说明它**知道有歧义但选择了猜**。这是任何 prompt/模型都消除不了的，除非有业务规则成为单一事实来源。

### 4.2 澄清门触发不稳定 —— T2 问，T1/T3 不问

- **T2**：无任何历史结论可依 → 判定"无字面报工映射 + ≥2 种合理口径 + 无默认规则" → 按 `nl2sql-clarification/SKILL.md`「无据不猜」要求以 `[需要澄清]` 停止（03:13:41），列出 A/B/C 三口径。行为上**最合规**。
- **T3**：靠表名启发（"报工报表花名册 `do_table_user` likely defines 应报工人员"）自认清晰 → 不问。
- **T1**：因检索到早前会话已把口径定过 → 自认清晰 → 不问。

> `nl2sql-clarification/SKILL.md` 已内置强纪律（"存在 ≥2 种合理解释 → 一律 `clear=false`"），但它是**文本纪律**，模型可借由表名或历史"合理"跳过——澄清决策本身成为一次自由发挥。

### 4.3 跨线程 / 跨 run 上下文泄漏 —— 不可复现 + 潜在 eval 泄题

T1 通过文件工具（`read_file` / `grep` / `ls`）读取了**其它会话 / 其它 run** 的产物（02:49~02:53）：

| T1 读取内容 | 路径 | 后果 |
|---|---|---|
| 早前同题整段对话 | `/workspace/conversation_history/01a06a46….md`（反复 grep `do_department_user_detail` / `190` / `Z0444` / `final SQL` / `21 人`） | 复制早前口径与 SQL 模式 |
| 早前 run 的报告 | `/workspace/report/上周未报工人员名单_2026-09-04_10-09-31.md`（**21 人**） | 口径被早前结论锚定 |
| **另一 run 的评测 subject** | `/workspace/nl2sql_process_data/01a06a23…/eval-subject/f7943e7a.json`（内嵌该 run 的 `final_answer=21 人`） | **在线 agent 读到 eval 参考答案** |
| 另一 run 的查询结果快照 | `…/01a06a23…/query_result/cc11a38c_result-2.md`（在职员工 60 行全表快照） | 数据版本混用 |

T1 最终口径（在职、排除 Z0444）与说明（"数据比早前会话略有更新""复用已验证 SQL 模式"）基本被早前结论牵着走。带来的三问题：

1. **可复现性差**：答案变成"之前哪次会话怎么答的"的函数，与当次数据无关；
2. **eval/答案泄漏**：在线 agent 能读到离线实验 run 的 `eval-subject`（内含最终答案/SQL），等于对着答案做题，同时污染后续离线评测公平性；
3. **错误传播**：早前 run 若口径选错，会被当"已验证知识"继续扩散。

代码侧成因：

- `src/agent/settings/file_permissions.py`：读权限整条 `allow /workspace/**`（`/workspace/` 下平铺所有 thread 的 `conversation_history/`、`report/`、`nl2sql_process_data/{thread}/…`）；
- `src/agent/eval/eval_subject.py`：subject 写入根 = `workspace/nl2sql_process_data/{session_thread}/eval-subject`，落在 agent 可达区；
- `knowledge-loader/SKILL.md` 本只应走 MCP（`get_instructions/recall_queries/get_all_knowledge`），但文件工具存在使模型可绕开 skill 漫游。

### 4.4 底层数据在评测窗口内漂移 —— 活库且含未来/计划数据

同一"上周"窗口 `do_work_hour` 报工人数随时间变化：早前(10:09) **169** → T1(10:49) **172** → T3(11:20) **173**；全量 `deleted` 行数也从 300,153 增至 300,198。库同时含未来日期行（`do_date_config` 最大 `2026-10-10`，`do_work_hour` 预填至 09-30）。

直接后果：**即使口径一致，不同时刻跑结果也不同**——T1 的 18 人名单正是从早前 21 人名单里"消失"了 Z0289/Z0316/Z0430（期间补录了报工）。把"数据变了"误判成"模型不稳定"会浪费排查。

### 4.5 采样噪声（放大器）

T2 与 T3 检索到的信息几乎等价（都只有 SKILL + schema，`recall_queries` 均空），一个选择问、一个按表名猜——纯采样放大上面的路径分叉。属次要，可被 §5 收敛，无需单独治理。

## 5. 治理方案（S1~S5，均未实施）

### S1 权威业务口径（根治"18 还是 12"）🟡 内容已产出待落库

- 每个库一份与语义库同 repo 的 `knowledge/` 词条（结构对齐 `src/test/wrenai_exec_Chinook/knowledge/{rules,metrics,glossary,caveats}`，已被 `get_instructions/get_all_knowledge` 读取），为 WIT 库补齐：
  - `报工/工时填报` ≡ `do_work_hour`（含 `deleted` 语义、`0`/`1` 编码、未来预填行说明）
  - `应报工人员池`：默认口径已拍板 = **在职员工**（`do_department_user_detail.deleted='0'` 约 190 人，非花名册 184），附入职/离职剔除规则
  - `上周/本周` 取数基准（库 `CURRENT_DATE` 而非墙钟）
  - 典型句式模板："谁没报工" = roster − reported 差集
- 随语义库一起走 git 版本化与 semantic_refs 拉取（机制已存在）。
- 效果：glossary 有「报工」定义后，"schema 无字面报工 → 必须问"（T2 触发条件）消失；口径不再靠猜。

**产出**：`docs/agent优化记录/WIT知识库词条-报工口径/{glossary/报工与工时.md, rules/报工口径规则.md}`，
待放入 WIT 语义库 git 仓库 `knowledge/` 后 commit + tag（见该目录 README）。

### S2 治理跨线程/跨 run 检索泄漏（可复现性 + 防泄题）✅ 已实施

只作用于 **nl2sql 子 agent 图**，两刀（第 3 刀 SKILL 纪律并入第 1 刀物理封堵）：

1. **收窄文件读权限（静态层）**：`file_permissions.py` 新增 `NL2SQL_FILE_PERMISSIONS`，
   `nl2sql_agent.py` 读范围由 `/workspace/**` 收窄为：
   - `allow /shared/**`（memory/skills）
   - `allow /workspace/large_tool_results/**`（大结果表落盘，工具调用 id 键控非会话目录）
   - `allow /workspace/nl2sql_process_data/**`（本次流水线中间产物）
   - `deny /**`（兜底 → conversation_history / report / tmp / 工作区根 / 未知路径一律不可读）
   - 写规则不变（`allow /workspace/**`，含 conversation_history 自动压缩 offload）。
2. **运行时线程护栏**：新增 `filesystem_thread_guard.py`（`FilesystemThreadGuardMiddleware`），
   在工具调用边界对 `read_file/ls/glob/grep` 做线程级裁决——`/workspace/nl2sql_process_data/{thread}/**`
   只放行 `{thread} == 当前会话线程 id`（会话 id 与 `langfuse_span._thread_id` 同源），
   其它线程目录（含 eval-subject / query_result / schema）一律拒绝。
3. **eval 产物移出 VFS**：`eval_subject.py` 的 `eval_root_dir` 由
   `nl2sql_process_data/{thread}/eval-subject` 迁到 `<data_root>/eval_runs/{thread}/eval-subject`
   （对应 VFS `/eval_runs/...`），`langfuse_span.py` 落盘根由 `_active_workspace_path()` 改为
   新增的 `_data_root_path()`；在线 agent 无论主/子图都读不到 subject/gold。

> 已拍板：`conversation_history` / 其它 thread `report` 不允许 nl2sql 子 agent 跨线程读取（业务口径只走 glossary）。main agent（主图）保持宽读不变（泄漏发生在子图内）。

**实施/验证**：静态层 42 项逻辑回归（权限规则 + 护栏纯逻辑 + 中间件端到端放行/拒绝两路径）全过；py_compile 通过。生产 E2E 需重启后端生效（未发版）。

### S3 澄清门确定性护栏（把 T2 的纪律变成代码）✅ 已实施

在模型裁决外增加两层代码护栏（均确定性、不加 LLM、未命中零干预）：

1. **词条覆盖预检（口径约束注入）**：新增 `caliber_spec.py` 口径规范（按库组织、大小写不敏感），
   `nl2sql_agent.py` 的 `dynamic_prompt` 在路由注入后追加：命中敏感术语且**有默认口径** → 注入
   「默认口径表 + 禁止表」约束（权威、勿猜）；命中但**无默认口径** → 注入「不得自行猜测、停下追问」。
2. **SQL 口径后置护栏（final SQL 校验）**：`check_progress._enhanced_build_check_result` 在
   `_extract_last_sql` 产出最终 SQL 后，命中 `forbidden_roster_tables` → 写 `result["caliber_warning"]`
   告警（软提醒，随 check 结果透传给主 agent）。只查最终产出 SQL，不查探索期探测 SQL。

> 目的：让「换个口径直接溜过」在代码上不可能；T3 用 `do_table_user`（184 口径 → 12 人）的场景会被后置护栏告警。

### S4 收敛可复现性 + 回归基线

- S1+S2 后同 config 仅剩纯采样自由度；"是否澄清/选口径"收敛到 S3 确定性组件。
- 将本问题固化为 offline experiment dataset item（gold 名单**待口径拍板后人工标注**，勿用早前模型输出当 gold），作为每次改动的回归锚点。
- 可选：同 config 连跑 N 次方差测试（weint 线上、清理跨线程文件后连问 3 次即可验证）。

### S5 数据漂移可观测化 ✅ 已实施（部分）

- **数据快照写 trace metadata**：`langfuse_metadata._inject` 新增 `data_snapshot = {ts, db_name}`，
  每次 run 启动即写入 trace metadata → 跨 run 可比对「是否同一数据窗口」（指纹/时点不同不当作模型差异比较）。
- **报告标注数据截至时点**：`report_builder` 报告头新增「数据截至：{时点}（活库数据，可能随时间变动）」。
- **指纹 SQL 规范**：`caliber_spec.py` 每库定义 `fingerprint_sql`（`do_work_hour` count/max(date)、
  `do_department_user_detail` count 等）；⚠ **确定性执行器未做**（需在 nl2sql 子 agent 启动时直接调 DB
  MCP 工具跑这些 SQL 并写回 metadata），当前仅快照时间戳+库名。离线评测按快照分组的消费端也待接。

> 效果：活库数据漂移从「被误判为模型不稳」变为「可观测、可分组」。

## 8. 验收建议

- **口径一致性**：定稿口径后，weint 线上清空跨线程文件，连问同题 3 次 → 名单/人数一致，且 trace 均未读其它 thread 目录。
- **泄题封堵**：agent 对其它 thread 的 `eval-subject`/`conversation_history` `ls/read_file` 被权限拒绝（trace 中体现 ERROR 或不可读）。
- **澄清正确性**：glossary 补「报工」词条后，该问不再因"无字面概念"误问；对 glossary 无定义的疑似术语仍稳定触发澄清。
- **口径护栏**：构造用非默认口径表做名单的 SQL → 被后置护栏拦截一次。
- **数据漂移**：两次 run 指纹不同时，trace metadata 可见，报告中体现数据截止时点。
