## 1. 背景与需求

**需求**：在前端界面配置要接入的数据库，支持 **mysql / clickhouse / postgresql / 数据仓（公司内部）**；
前端配置的数据库必须能传入后台服务，让子智能体真正查询用户选中的库。

**现状**：只支持 mysql 在 `.env` 中配置（`DB_1/2/3_*`），前端 `DatabaseSelector` 硬编码 2 个库
（aix_report、Chinook_AutoIncrement）。

## 2. 现状链路与三个断点

完整链路调研结论（均已实证定位）：

```
前端 DatabaseSelector ──db_name──▶ stream.submit config.configurable ──▶ 主 agent
   (硬编码2库)                      (useChat.ts:688-697)                  (get_config().configurable ✓)
                                                                               │
                                                                               ▼ 委派 AsyncSubAgent
                                                              deepagents: client.runs.create(thread_id, assistant_id, input)
                                                                   │  ✗ 不传 config → configurable 丢失
                                                                   ▼
                                                          nl2sql 子 agent ──▶ wrenai_run_sql ──▶ WrenAI 语义层
                                                          (get_config().configurable 为空)      (固定绑定 imdb 单一数据源)
```

| # | 断点 | 位置 | 后果 |
|---|------|------|------|
| **B1** | 异步子 agent 的 run **不接收 configurable** | `deepagents/middleware/async_subagents.py`：`start_async_task`/`astart_async_task`/`update_async_task`/`aupdate_async_task` 共 4 处 `client.runs.create(thread_id, assistant_id, input)` **无 `config` 参数** | 前端传的 db_name 到不了子 agent，`_inject_db_name` 读 `get_config().configurable.db_name` 恒为空 |
| **B2** | `_inject_db_name` 工具名匹配 bug | `src/agent/utils/path_resolver.py:539`：`if tool_name != "run_sql"` 精确匹配；但子 agent 工具实际名是 **`wrenai_run_sql`**（`mcp_tool.py:75` `tool_name_prefix=True`，前缀 `wrenai_`，见 `path_resolver.py:686` 超时表同名佐证） | 即使 configurable 到了，注入也不触发 |
| **B3** | WrenAI 语义层**绑定单一数据源** | `workspace/imdb_project/config/connection_mysql.json` 硬编码 `mysql-master:3306/imdb`；`_get_sub_server_config`（`mcp_tool.py:134-150`）只加载 wrenai 一个 MCP server | 子 agent 的 `wrenai_run_sql` 永远查 imdb，**db_name 选库对执行无影响**（现状选择器是摆设） |

另外两处现状约束：

- **C1**：`db_mcp_server`（直连 SQL 执行器，`src/mcp_server/db_mcp_server/`）**当前未被任何地方启动/加载**（全仓库 grep 无 `NL2SQLMcpSqlServer(` 调用点），`_RUNNER_REGISTRY` 只注册 mysql/sqlite（`db_server.py:34-37`）。clickhouse/postgres/mssql/presto/bigquery/snowflake/oracle/duckdb 的 runner 文件都在，但**未注册 + 导入路径错误**（`from db.sql_runner import ...` 是顶层包路径，与现有 `mcp_server.db_mcp_server.db.sql_runner` 布局不符）。
- **C2**：驱动情况 —— `clickhouse_connect`、`psycopg2`、`pymysql` 已装；`clickhouse_driver`、`asyncpg` 未装（部分 runner 可能用到）。

> **结论**：现有「前端选库」功能在**查询执行路径上实际未生效**（B1+B2+B3 叠加）。本方案要打通的不只是「配置能传进去」，还有「配置真能决定查询打到哪个库」。

## 3. 总体架构与决策点

### 决策点 D1：配置存储位置（推荐方案 1）

| | 方案 1：后端集中存储（推荐） | 方案 2：前端全量传递 |
|---|------|------|
| 做法 | 后端维护 `db_config.json`（连接信息）+ 管理 API（增删改查）。前端只保存「库名/别名」，聊天时只传 **db_name 引用** | 前端把 host/port/user/password/db_type 全量放 `configurable` 每次随请求传 |
| 安全 | ✅ 密码只落后端文件，不进浏览器/聊天请求/checkpoint | ❌ 密码暴露在前端 localStorage 与每次请求，还会进 LangGraph run config 与 checkpoint，泄露面大 |
| 子 agent | 只需一个名字，LLM 无负担 | configurable 体积大，且每类库字段不一致，LLM 易困惑 |
| 实现 | 需一个管理 API（见 §5.2） | 免管理 API |

**推荐方案 1**：前端配置 → 后端存储 → 聊天只传 `db_name`。符合「数据仓(公司内部)」这类含敏感连接信息的场景。

### 决策点 D2：查询执行通道 —— ✅ 已确认：先 A（db_mcp_server 直连）后 C（混合）

WrenAI 语义层**绑定单一数据源**（B3），前端新配的任意库无法直接走 WrenAI。三条路：

| | A. db_mcp_server 直连（MVP 主通道） | B. WrenAI 多数据源建模 | C. 混合（最终态） |
|---|------|------|------|
| 机制 | 激活 db_mcp_server，注册 clickhouse/postgres 等 runner；`run_sql` 按 `db_name` 路由到对应 runner **直连查 SQL** | 每个库在 Wren 项目里建 datasource + models + 语义别名，`db_name` → 模型集 | 已建模主库走 WrenAI 语义层；前端新配的任意库走 db_mcp_server 直连，按 db_name 是否建模路由 |
| 优点 | 任意 DB 即配即查，**无需建模**；与「前端任意配库」场景匹配 | 保留语义层（业务词表/MDL/dry_run/查询优化） | 兼得语义层体验与任意库即配即查 |
| 缺点 | 失去 WrenAI 语义层能力；需修 runner 导入/注册 | 每个新库都要建 MDL，重；不适合前端任意配库 | 两条通道并存，需维护路由逻辑 |
| 工作量 | 小 | 大 | 中 |

**确认路线：先落 A 打通「前端配库 → 直连执行」闭环（MVP），后按 C 把已建模主库保留在 WrenAI 语义层。B 留作远期选项。**

#### D2 详解

**现状（全走 WrenAI）**：前端选 db_name → 子 agent → `wrenai_run_sql` → WrenAI(imdb_project) → 固定 mysql:imdb。WrenAI 是语义层：有 MDL 业务词表（get_mdl/list_models）、dry_run 预演、Cube 预聚合加速；但**绑定一个建模项目**，接任意新库需逐库建模，成本高。

**方案 A（直连）**：子 agent → `dbmcp_run_sql` → db_mcp_server → 按 db_name 选 runner（mysql/clickhouse/postgres）直连该库。runner 文件全部已存在，只差注册 + 修导入 + 启动接入。**无需建模**，符合「前端任意配库」形态。代价：无语义层，子 agent 需自行发现表结构（扩展 `get_db_info` 返回表清单），适合 schema 明确、口径简单的库。

**方案 C（混合）—— 语义层为硬需求**：子 agent 工具表同时有 `wrenai_run_sql` 与 `dbmcp_run_sql`；路由判定——
- `db_name` ∈ 已建模库（Wren 项目里建模过，当前 imdb）→ `wrenai_run_sql`（语义层体验）；
- `db_name` ∈ 前端新配库（未建模）→ `dbmcp_run_sql`（直连）。
路由实现两种：**提示词引导**（configurable 注入 db_name + db_type，系统提示词告诉子 agent 选哪个工具），或**确定性路由**（升级 `_inject_db_name` 为"路由注入"，拦截 run_sql 按 db_name 是否建模转发到对应 MCP）。

> **需求确认（2026-08-11）**：用户后续会**新增 wren 语义库**，要求这些库走语义层（不是直连）。因此：
> 1. 混合路由是**需求约束**，不是可选最终态 —— WrenAI 语义层通道必须保留且**可动态扩展**。
> 2. 「已建模库集合」**不能硬编码 imdb**，需**动态发现**：从 Wren 项目模型（models 的 dataSource 字段 / list_models 返回）构建 `db_name → 已建模` 映射，新增 wren 语义库即自动进入语义层通道（见 §5.4 `SemanticDbDetector`）。
> 3. 实现待确认：新增 wren 语义库的形态 —— 推荐 **单 Wren 项目多数据源**（Wren 原生支持，一个 `wren serve mcp` 实例内含多 datasource + models，模型带 dataSource 标识）；若为多项目多实例，则 `_get_sub_server_config` 需支持多个 wren MCP server（复杂度高，不推荐）。

**连带变化**：子 agent 硬编码「默认 imdb」（`nl2sql_agent.py:81`）改为从 configurable 动态注入「当前数据库 X（类型 Y）」+ 工具选择指引（依赖 §4.1/B1 透传修复）。

### 决策点 D3：数据仓（公司内部） —— ✅ 已确认：暂不实现

第一阶段不接入数据仓，范围仅 **mysql / clickhouse / postgresql**。`db_mcp_server` 现有 runner 覆盖 mysql/clickhouse/postgres/…，后续接入数据仓时再按引擎类型注册对应 runner（若为 Doris/StarRocks 可复用 mysql runner）。

## 4. 打通链路的必修修复（无论选哪条通道）

以下 3 项是「前端配置能传到子 agent 并影响查询」的**前置条件**，与通道选择无关。

### 4.1 修复 B1：async subagent 透传 configurable

deepagents（pip 包，`.venv/Lib/site-packages/deepagents/middleware/async_subagents.py`）4 处 `client.runs.create` 均未传 config。LangGraph SDK 的 `runs.create` **原生支持 `config` 参数**（`_sync/runs.py:359-370`，payload `"config": config`）。

**做法**（推荐：项目内 patch 层，不改 site-packages）：
新建 `src/agent/middlewares/deepagents_async_config_patch.py`，在 agent 启动时 monkeypatch 这 4 个函数，给 `client.runs.create(..., config=...)` 传 **只含 configurable 的配置**：

```python
config={"configurable": runtime.config.get("configurable", {})}
```

> 注意：**只透传 `configurable`，不透传整个 runtime.config** —— 后者含主线程 `thread_id`/`checkpoint_id` 等，直接转发会导致子 run 状态冲突。

patch 目标（4 处）：
- `start_async_task`（sync）— L298-302
- `astart_async_task`（async）— L338-340
- `update_async_task`（sync）— L529-533
- `aupdate_async_task`（async）— L568-572

`runtime.config` 在 deepagents 中间件里就是当前 run 的 config（`query_keywords` 中间件已在主 agent 用同一来源读 `configurable`，见 `src/agent/middlewares/query_keywords.py:44-47`），因此该 patch 可行。

### 4.2 修复 B2：`_inject_db_name` 工具名匹配

`src/agent/utils/path_resolver.py:539`：

```python
# 改前
if tool_name != "run_sql":
    return args, kwargs
# 改后（同时覆盖 run_sql / wrenai_run_sql 及未来 dbmcp_run_sql）
if "run_sql" not in tool_name:
    return args, kwargs
```

### 4.3 修复 B3：让「选库」真正决定查询目标

见 §6 路由设计（依赖 D2 通道决策）。

## 5. 后端改动（方案 1 + 通道 A 为主，C 为最终态）

### 5.1 配置存储层 — 运行时 `db_config.json`

新建 `src/mcp_server/db_mcp_server/db/core/db_config_store.py`：

- 数据模型：每个库一条
  ```json
  {
    "name": "生产MySQL",
    "db_type": "mysql",
    "host": "mysql-master",
    "port": 3306,
    "database": "aix_report",
    "user": "aoi-dev",
    "password": "***（加密）",
    "extra_config": {},          // DB_EXTRA_CONFIG 等价物
    "created_at": "...", "updated_at": "..."
  }
  ```
- 文件位置：后端数据目录（如 `src/agent/workspace/db_config.json`，gitignore）。
- **密码加密**：用 `.env` 里的密钥（新增 `DB_CONFIG_SECRET`）做 AES 加密落盘，明文不落文件。
- 兼容：启动时把 `.env` 的 `DB_N_*` 导入 store（迁移一次），后续统一由 store 管理。
- `McpSqlConfig.from_env` → 增加 `from_store(db_name)`；`Settings.get_databases()` 增加 store 读取路径（保留 .env 兜底）。

### 5.2 配置管理 API

提供 CRUD（增删改查）数据库配置，供前端「数据库管理」面板调用。挂在既有 langgraph dev server 或新增轻量 FastAPI 上：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/db-configs` | 列表（**密码脱敏**，仅返回是否已配置） |
| GET | `/api/db-configs/<name>` | 单条（脱敏） |
| POST | `/api/db-configs` | 新增/更新（name/db_type/host/port/database/user/password） |
| POST | `/api/db-configs/<name>/test` | **连通性测试**（前端保存前校验） |
| DELETE | `/api/db-configs/<name>` | 删除 |
| GET | `/api/db-configs/<name>/schemas` | （可选）拉库内表清单，供建 Wren 模型/提示词用 |

> 安全：密码只进后端 store；API 列表永远脱敏；`test` 接口只回连不通/连通，不回明文。

### 5.3 runner 激活（通道 A 必需；首阶段范围 mysql/clickhouse/postgres，数据仓除外）

1. **修导入路径**：各 runner 文件 `from db.sql_runner import ...` → 改为相对 `mcp_server.db_mcp_server.db.sql_runner` 布局的导入。
2. **注册**：`db_server.py:34-37` `_RUNNER_REGISTRY` 补 `clickhouse` / `postgres`。
3. **db_type 按库取值**：`McpSqlConfig.from_env` 现在用**全局单值** `settings.DB_TYPE`（`config.py:48`），需改为按库存 `db_type` 取值（`_get_runner` 的 `_load_runner_class(cfg.db_type)` 才能路由到不同引擎）。
4. **get_db_info 扩展**：直连通道无语义层，子 agent 需自行发现表结构 —— 把 `get_db_info`（`db_server.py:113`）扩展为返回该库的表清单/字段（或新增 `list_tables` 工具），供子 agent 写 SQL 前了解 schema。
5. **启动**：`db_mcp_server` 以 http 传输启动（`NL2SQL_MCP_PORT`），在 `mcp_tool.py` 加第二个子 agent server 配置（`_get_sub_server_config` 返回 wrenai + dbmcp 两个 server）。

### 5.4 查询路由（D2）

以 C（混合）为最终态（**语义层为硬需求**，见 §3 D2）：子 agent 的 `run_sql` 调用按 `db_name` 判断——

```
db_name ∈ 已建模库（Wren 项目建模过，动态发现）  →  wrenai_run_sql（WrenAI 语义层）
db_name ∈ 前端新配库（未建模）                    →  dbmcp_run_sql（db_mcp_server 直连）
```

- **已建模库集合动态发现**：新建 `SemanticDbDetector` —— 启动时/定期扫描 Wren 项目（`models/*/metadata.yml` 的 dataSource 字段，或运行时 `list_models` 返回），产出 `{db_name: 是否已建模}`。新增 wren 语义库后**自动感知、无需改代码**，并同步给前端下拉徽标（`db-configs` 列表每库返回 `semantic: boolean`）。
- MVP 先落 A：新配库全走 dbmcp；既有 imdb 主路径保持 wrenai。
- 路由实现建议在 `wrap_tool`（`path_resolver.py:720`）里根据 db_name 选 MCP 客户端，或直接给两个 server 同名工具按 config 分派。
