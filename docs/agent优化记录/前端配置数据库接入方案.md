## 1. 背景与需求

**需求**：在前端界面配置要接入的数据库，支持 **mysql / clickhouse / postgresql / 数据仓（公司内部）**；
前端配置的数据库必须能传入后台服务，让子智能体真正查询用户选中的库。

**现状**：只支持 mysql 在 `.env` 中配置（`DB_1/2/3_*`），前端 `DatabaseSelector` 硬编码 2 个库
（aix_report、Chinook_AutoIncrement）。

## 3. 总体架构与决策点

### 决策点 D1：配置存储位置 —— ✅ 已确认并落地：后端集中存储（方案 1）

| | 方案 1：后端集中存储（已实施） | 方案 2：前端全量传递 |
|---|------|------|
| 做法 | 后端维护 `db_config.json`（连接信息）+ 管理 API（增删改查）。前端只保存「库名/别名」，聊天时只传 **db_name 引用** | 前端把 host/port/user/password/db_type 全量放 `configurable` 每次随请求传 |
| 安全 | ✅ 密码只落后端文件，不进浏览器/聊天请求/checkpoint | ❌ 密码暴露在前端 localStorage 与每次请求，还会进 LangGraph run config 与 checkpoint，泄露面大 |
| 子 agent | 只需一个名字，LLM 无负担 | configurable 体积大，且每类库字段不一致，LLM 易困惑 |

**已实施**：`db_config_store.py`（AES 加密落盘）+ 管理 API（**合并进 langgraph API，端口 2026**，CRUD + 连通测试 + 密码脱敏 + semantic 标记）。

### 决策点 D2：查询执行通道 —— ✅ 已确认并落地：先 A（db_mcp_server 直连）后 C（混合）

| | A. db_mcp_server 直连 | B. WrenAI 多数据源建模 | C. 混合（最终态，已实施） |
|---|------|------|------|
| 机制 | `dbmcp_run_sql` 按 `db_name` 路由到对应 runner **直连查 SQL** | 每个库在 Wren 项目里建 datasource + models | 已建模主库走 WrenAI 语义层（`wrenai_run_sql`）；前端新配的任意库走 dbmcp 直连，按 db_name 是否建模路由 |
| 优点 | 任意 DB 即配即查，无需建模 | 保留语义层能力 | 兼得语义层体验与任意库即配即查 |
| 缺点 | 失去语义层能力 | 每库建 MDL，重 | 两通道并存，需维护路由 |

**落地形态（C 混合）**：子 agent 工具表同时含 `wrenai_*` 与 `dbmcp_*`；路由由 `SemanticDbDetector` 动态判断——
- `db_name` ∈ 已建模库（Wren 项目建模过，当前仅 imdb）→ `wrenai_run_sql`（语义层）；
- `db_name` ∈ 前端新配库（未建模）→ `dbmcp_run_sql`（直连）。

路由实现在 `nl2sql_agent.py` 的 `dynamic_prompt`：从 configurable 读 db_name → `SemanticDbDetector.is_modeled()` → 动态注入「当前数据库 X（已建模/未建模）+ 通道指引」。新增 wren 语义库自动进入语义层通道（`SemanticDbDetector` 实时扫描 Wren 项目）。

### 决策点 D3：数据仓（公司内部） —— ✅ 已确认：暂不实现

首阶段不接入数据仓，范围仅 **mysql / clickhouse / postgresql**。`_RUNNER_REGISTRY` 已注册 mysql/clickhouse/postgres/sqlite。

## 4. 打通链路的必修修复（已全部实施）

### 4.1 修复 B1：async subagent 透传 configurable —— ✅ 已实施

新建 `src/agent/middlewares/deepagents_async_config_patch.py`，monkey-patch deepagents `_ClientCache.get_sync/get_async`，包装 `client.runs.create`：

```python
# 读当前主 run 的 configurable，过滤运行时内部键后注入子 run config
def _current_configurable() -> dict:
    cfg = get_config()
    configurable = cfg.get("configurable", {}) or {}
    return {k: v for k, v in configurable.items() if not _is_internal_key(k)}
```

**实施中的关键坑（已修复）**：langgraph 运行时会在 `get_config().configurable` 混入大量 `__pregel_*` 内部键
（`__pregel_node_finished`=function、`__pregel_runtime/read/call`=Runtime/partial 等），全部不可 JSON 序列化，
原样转发会报 `Type is not JSON serializable: function`。`_is_internal_key()` 过滤 `__` 前缀与 `langgraph_` 前缀的键，
只透传用户自定义键（db_name / query_keywords / run_id / graph_id / assistant_id / user_id / checkpoint_map）。

### 4.2 修复 B2：`_inject_db_name` 工具名匹配 —— ✅ 已实施

`path_resolver.py`：`if "run_sql" not in tool_name` 子串匹配，覆盖 `wrenai_run_sql` / `dbmcp_run_sql` 及未来变体。
参数已有 db_name 时不覆盖；从 `get_config().configurable.db_name` 注入。

### 4.3 修复 B3：让「选库」真正决定查询目标 —— ✅ 已实施（D2-C 混合路由）

见 §5.4。**补充修复**：`wrap_tool` 的 `_pack_chart_props` 原对所有工具无条件注入 `outputType="option"`（CHART_ENGINE=echarts），
导致所有 DB 工具参数被 args_schema（extra=forbid）拒绝，报 `Unexpected keyword argument: outputType='option'`。
已改为 `if is_chart:` 保护（同步 `_run` + 异步 `_arun` 两处）——只给图表工具注入图表参数。

### 4.4 补充修复：主 agent 感知 configurable.db_name —— ✅ 已实施

**问题**：主 agent 的 system prompt 是静态文件（MAIN_AGENT_PROMPT.md），middleware 不注入 db_name →
主 agent LLM 读不到 `configurable.db_name`，切库后委派子 agent 时【数据库名称】写错（默认 imdb）。

**修复**：`main_agent.py` 加 `@dynamic_prompt`，每次模型调用前从 `get_config().configurable.db_name` 读当前库并注入提示词：
「当前用户选中的数据库是 `{db_name}`，委派时【数据库名称】必须写 `{db_name}`，禁止写 imdb」。

**实施中的坑**：主 agent 的 `request.system_message.content` 是 **str**（子 agent 才是 block 列表），
取文本必须用 `.text` 属性，`content[-1]["text"]` 会 `TypeError: string indices must be integers`。

## 12. 修复记录：切库后仍连旧库（clickhouse→imdb 回归，2026-08-11）

**用户报告**：前端切库 clickhouse 后问「有多少表」，实际仍连 imdb。

### 12.1 根因：上下文污染（context contamination）

分层取证（LangSmith + LangGraph run）：
1. 前端 `configurable.db_name=clickhouse` 传对了；
2. `dynamic_prompt` 的 system prompt 注入也生效（LangSmith 显示「当前用户选中的数据库是 clickhouse」）；
3. **但主 agent LLM 采信对话历史/总结里自己上轮说过的「当前应用数据库是 imdb」**，而非系统提示词中刚注入的 clickhouse；
4. 于是 `start_async_task` 的 description【数据库名称】写成了 imdb。

结论：模型对「自己历史陈述」的信任度高于「本轮 system prompt 注入」，把 db_name 注入进 system prompt 末尾不够——必须把当前库名做成**当轮用户侧最高优先级信号**。

### 12.2 修复（4 处）

| # | 文件 | 改动 |
|---|------|------|
| 1 | `src/agent/main_agent.py` `dynamic_prompt` | 从「追加末尾」改为**前置到提示词最顶部** + 权威化措辞：`## 当前数据库（configurable 动态注入）— 最高优先级`，「无论历史或总结如何描述一律以本段为准，历史库名已过时，禁止写 imdb」 |
| 2 | `src/agent/middlewares/current_db_context.py` 新增 `CurrentDbContextMiddleware`（`main_agent.py` 注册） | 每次模型调用前把 `【当前数据库：{db_name}】` 前缀注入**最新一条用户消息**（HumanMessage），作为当轮用户侧最高优先级信号；工具回环/无 db_name 时不注入，幂等 |
| 3 | `src/agent/nl2sql_agent.py` | **移除** system_prompt 里硬编码的「默认 imdb」兜底，改为以 dynamic_prompt 注入的「查询通道路由」段为准 |
| 4 | `src/agent/utils/path_resolver.py` `_inject_db_name` | 匹配范围从 `run_sql` 扩展到 `run_sql` / `get_db_info`（子 agent 首次 schema 发现也注入 db_name） |

### 12.3 关键新发现：`ModelRequest.runtime.config` 恒为空 dict

调试中发现 `CurrentDbContextMiddleware` 最初按 `request.runtime.config.configurable` 读 db_name，**从不生效**（日志 db_name=''）。查 langchain 源码：

> langchain 官方文档：**`Runtime` does not include `config`**。读取 `RunnableConfig` 的推荐方式是 `langgraph.config.get_config()`。

即模型调用中间件里 `request.runtime.config` 永远是 `{}`。**读 configurable 必须用 `langgraph.config.get_config()`**（`dynamic_prompt` 一直用这条路径所以一直有效）。

连带发现并修复同源 bug：
- `CurrentDbContextMiddleware._resolve_db_name`：改为 `get_config()` 优先，`runtime.config` 兜底；
- **`QueryKeywordsMiddleware._resolve_keywords`**：同样读 `request.runtime.config.configurable` → **前端查询关键词设置从未真正生效**（一直注入默认词）。已改 `get_config()`，E2E 实证读到了传入的 `票房、排行`。详见《前后端关键词一致性方案》§8。

### 12.4 E2E 验证（2026-08-11，后端已重启加载新代码）

1. **委派正确**：`start_async_task`【数据库名称】= `clickhouse`（修复前 imdb）；
2. **消息级注入生效**：后端日志 `[dbctx] 注入当前库名到最新用户消息: db_name=clickhouse prefix='【当前数据库：clickhouse】'`；
3. **子 agent 直连命中**：`dbmcp_get_db_info(db_name=clickhouse)` → `dbmcp_run_sql(sql=SELECT name FROM system.tables..., db_name=clickhouse)`，全程无 imdb / 无 wrenai 语义层弯路；
4. **关键词值读取生效**：显式传 `query_keywords=["票房","排行"]` → 日志 `[QueryKeywords] 注入查询关键词: 票房、排行`；回归：不传时回退默认词；
5. **回归**：imdb 主查询路径不受影响。

### 12.5 维护提示

- 以后在模型调用中间件里读 configurable（db_name / query_keywords / 其他前端设置），**一律用 `langgraph.config.get_config()`**，不要用 `request.runtime.config`（恒空）。
- `CurrentDbContextMiddleware` 只在最新消息是 HumanMessage 时注入；工具回环/auto-continue 阶段不注入（避免把前缀拼进 tool-result 轮次）。

## 13. 管理 API 合并进 langgraph API（单 REST 服务，2026-08-11）

### 13.1 背景

原 db-config 管理 API 独立跑在 **8008** 端口，前端分别直连两个端口（chat→2026、db-config→8008）。
本次利用 langgraph 官方 **`LANGGRAPH_HTTP.app` 自定义 app 钩子**，把 db-config 路由挂进 langgraph
同一进程/同一端口（**2026**），**不改 langgraph-api 源码**；并以「组合根 + 每 API 一模块」结构落地在
`src/api/`，为后期新增自定义 API 预留扩展点。

### 13.2 方案要点

- **钩子机制**：`.env` 里 `LANGGRAPH_HTTP={"app": "src/api/custom_app.py:app"}` → `HttpConfig.app`
  指向用户 Starlette 实例；`langgraph_api/server.py` 把该 app 路由 + langgraph 原生路由合并进同一 app
  （合并 lifespan 与 exception handlers）。`start_server.py` 与 `langgraph dev` 两条启动路径都会加载 .env，均生效。
- **组合根**：`src/api/custom_app.py` 聚合各 API 模块的 `routes`（当前仅 `api.db_config`）。
  **新增自定义 API = 在 `src/api/` 建模块暴露 `routes` + 在 `ROUTES` 展开一行**。
- **消除全局中间件**：原独立服务用 `_JSONBodyMiddleware`（BaseHTTPMiddleware）吞全 app 的 JSON body，
  对 langgraph SSE 流式路由有风险 → 直接删除，handler 内 `await request.json()`（`api/_common.parse_body`）。
- **路径锚点修正**：`_scan_wren_projects` 由 `parents[3]` 改为 `parents[2]`（`src/api/` 比旧位置浅一层）。
- **语义标记新鲜度**：`upsert_config` / `delete_config` 后仍调 `get_detector().invalidate()`。
- **前端**：`harness-deep-agents-ui/src/lib/dbConfig.ts` 的 `apiBase()` 改为复用配置 `deploymentUrl`
  （与聊天同源同端口，默认 `http://localhost:2026`），去掉 8008 硬编码。
- **回滚**：删 `.env` 的 `LANGGRAPH_HTTP` + 前端 `apiBase()` 还原 → 8008 shim 独立启动即可。

### 13.3 验证（真实 2026 端口，非仅 TestClient）
