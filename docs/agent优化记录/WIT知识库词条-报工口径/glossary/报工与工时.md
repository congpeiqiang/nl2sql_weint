# 报工 / 工时填报 术语表

> 本文件对齐 Wren 语义库 `knowledge/glossary/`，由 `get_all_knowledge()` 读取。
> 落库前请随语义库 git 提交并打 tag（semantic_refs 机制按 ref 物化）。
> 「是否报工」的判定规则见 `rules/报工口径规则.md`（R3/R5），本表为术语与字段说明。

## 报工（工时填报）
- **定义**：员工在某一天填报工时/工作记录的行为。**「是否报工」以员工本人提交的报工单 `do_work_hour_examine` 判定**（见 R3），**不是** `do_work_hour`。
- **报工单主表 `do_work_hour_examine`**：`user_id`（人）、`date`（DATE，填报日期）、`work_hour`（DOUBLE，工时）、`status`（INTEGER，`1`=待审核；只要提交了即算报工，审核是否通过不影响「是否报工」）、`create_user_id`（提交人，实证 100% = `user_id`，即员工本人）、`deleted`（VARCHAR，`'0'`=有效 / `'1'`=软删）。
- **工时明细表 `do_work_hour`**（⚠ 仅作工时数值展示，**勿用于「是否报工」判定**）：`user_id`、`date`、`work_hour`、`type`、`deleted`、`create_user_id`。含**系统自动/补录行**（`create_user_id` 为空，如 08-24~28 李威 `type=8` 行）与未来预填行，会误判报工与否。
- **明细宽表 `do_work_hour_detail_extend`**（含 `user_name` / `job_number` / `department_full_name` / `if_approve` / `approve_user_name`）：需要直接带出姓名时用它 join 展示，但**判定**仍基于 `do_work_hour_examine`。

## 应报工人员池
- **默认口径（权威）**：**在职员工** = `do_department_user_detail` 中 `deleted='0'` 的记录（与 user 1:1，约 190 人）。
- **坑**：`do_department_user_detail` 是宽表（全量 1139 行 / 307 个 DISTINCT user，含历史快照与已离职）。只有 `deleted='0'`（190 行）才是「当前在职」。**切勿**用 `DISTINCT user_id`（307）或全量行数（1139）当在职人数。
- **其它候选口径（非默认，仅当用户明确要求时才用）**：
  - 月度报工花名册 `do_table_user`（按 `table_month_id` 分月，如 2026-08 对应 `table_month_id=33` 共 184 人）——用于「某月应报工名单」场景，**不是**「当前在职」。

## 上周
- **定义**：以**数据库当前日期**（`CURRENT_DATE`，数据库时区，非墙钟）的上一自然周（周一 ~ 周日）。
- **取数**（见 R4）：
  - 上周一 = `DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 7 DAY)`
  - 上周日 = `DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 1 DAY)`

## 谁没报工（未报工名单）
- **公式**：应报工人员池（R1+R2） − 上周有报工记录的人（R3：`do_work_hour_examine`，`date` BETWEEN 上周窗口且 `deleted='0'`，含 status=1 待审核）= 差集。
- **实现**：见 R5 NOT EXISTS 模板 SQL。
- **口径演进**：曾误用 `do_work_hour` 判「是否报工」——该表系统补录行会误判已报工、examine 待审核行未写入会误判未报工。2026-09-04 拍板改以 `do_work_hour_examine` 为准（同题 13 vs 17 差集根因，judge 证 13 正确）。
