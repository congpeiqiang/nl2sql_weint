# 报工 / 工时 业务规则

> 本文件对齐 Wren 语义库 `knowledge/rules/`，由 `get_instructions()` 读取（返回 rules/*.md 全量）。

## R1 应报工人员池 = 在职员工（默认口径）
`do_department_user_detail` 中 `deleted='0'` 即为应报工人员池（约 190 人，与 user 1:1）。

- **切勿**用 `do_table_user`（月度花名册）替代，除非用户明确要求「某月花名册」口径。
- **切勿**用 `DISTINCT user_id`（307）或全量行数（1139）当在职人数。

## R2 在职池按统计窗口剔除两类人
对 `deleted='0'` 的应报工池，还需按统计窗口剔除：

1. **已离职**：`leave_date IS NOT NULL AND leave_date < 统计周起始`（上周开始前已离职）；
2. **尚未入职**：`entry_date IS NOT NULL AND entry_date > 统计周末`（上周之后才入职，如 09-03 入职者不应计入 08-24~30 那周）。

等价过滤：

```sql
deleted='0'
AND (leave_date IS NULL OR leave_date >= <周起始>)
AND (entry_date IS NULL OR entry_date <= <周末>)
```

## R3 报工记录的有效判定源 = `do_work_hour_examine`（报工单表）
「某人上周是否报工」一律以 `do_work_hour_examine` 判定（`deleted='0'` 且 `date` 落在窗口内）。

- **依据（2026-09-04 trace 实证）**：`do_work_hour_examine` 的记录 **100% 由员工本人创建**（`create_user_id = user_id`，2033/2033 验证），即员工报工提交动作本身落此表。
- **`do_work_hour_examine.status`**：`status=1`（待审核）也算已报工——只要员工**提交了报工单**就算，审核是否通过不影响「是否报工」判定。
- **切勿**用 `do_work_hour`（工时表）作为「是否报工」的判定源：该表含**系统自动/补录行**（`create_user_id` 为空，如 2026-08-24~28 李威的 `type=8` 行），会把人误判成已报工；同时 `do_work_hour_examine` 待审核（status=1）记录尚未写入 `do_work_hour`，只用 `do_work_hour` 又会把人误判成未报工。两向都会错。
- 若需带出姓名/工号/部门，可用 `do_work_hour_detail_extend`（宽表，含 `if_approve`）join 取展示列，但**判定**仍在 `do_work_hour_examine` 上做。

## R4 上周 = 库当前日期的上一自然周（周一 ~ 周日）
用 `CURRENT_DATE`（数据库时区），不是墙钟：

- 周起始（上周一）= `DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 7 DAY)`
- 周末（上周日）= `DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 1 DAY)`

（`CURRENT_DATE` 即本周一所属自然周的当周；`WEEKDAY()` 周一=0…周日=6。）

## R5 未报工名单 = 差集
应报工池（R1+R2 过滤后）对 `do_work_hour_examine`（`date` BETWEEN 上周窗口且 `deleted='0'`）做 NOT EXISTS，无匹配者即未报工：

```sql
SELECT d.user_id, d.name AS user_name, d.job_number
FROM do_department_user_detail d
WHERE d.deleted = '0'
  AND (d.leave_date IS NULL OR d.leave_date >= DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 7 DAY))
  AND (d.entry_date IS NULL OR d.entry_date <= DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 1 DAY))
  AND NOT EXISTS (
    SELECT 1
    FROM do_work_hour_examine x
    WHERE x.user_id = d.user_id
      AND x.deleted = '0'
      AND x.date >= DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 7 DAY)
      AND x.date <= DATE_SUB(DATE_SUB(CURRENT_DATE, INTERVAL WEEKDAY(CURRENT_DATE) DAY), INTERVAL 1 DAY)
  )
ORDER BY d.user_id
```

## R6 数据漂移与未来预填行（务必注意）
- `do_work_hour` 含**未来预填**数据（预填至 09-30）、`do_date_config` 含未来日期（至 10-10）。必须按 `date BETWEEN 上周窗口` 精确过滤，**切勿**用「最近 N 天」或「截至当前」代替。
- 活库：同一周报工人数会随补录实时变化。同一口径不同时刻跑结果可不同，属正常数据漂移，不是模型不稳。

## R7 典型句式模板
- 「上周谁没报工」 = 应报工池（R1+R2） − 上周有报工者（R3：`do_work_hour_examine`，`date` BETWEEN R4 窗口，含 status=1 待审核）。
- 结果输出：只列未报工者姓名/工号；结果为 0 人时如实报告「未查询到数据/无未报工人员」。

## R8 判定历史（为什么定 R3）
- **2026-09-04 拍板**（用户）：报工判定源 = `do_work_hour_examine`，含 status=1 待审核；不用 `do_work_hour` 判定。
- 反例教训：同题两次 run，一次用 `do_work_hour_examine`（判定 13 人未报工，judge 0.9）、一次用 `do_work_hour`（判定 17 人未报工，judge 0.0）。差集恰为 5 个「待审核已提交」被误判未报工 + 1 个「系统补录」被误判已报工。详见 `glossary/报工与工时.md`。
