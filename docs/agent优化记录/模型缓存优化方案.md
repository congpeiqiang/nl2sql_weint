# 模型缓存优化方案

> 实施状态：✅ 已完成（2026-08-18）

---

## 问题背景

基于 benchmark 实证：`ChatDeepSeek` 构造函数耗时 ~8.2s，`create_model()` 每次调用 ~9.2-9.5s。优化前 `ThinkingToggleMiddleware._maybe_swap()` 每次 LLM 调用都重建模型，4 轮浪费 ~36s。

## 最终架构：三层模型复用策略

```
┌────────────────────────────────────────────────────────────────┐
│  第 1 层：模块级单例（进程启动时）                               │
│  deepseek_model = create_model()  ← 导入时执行一次              │
│  → 作为 main_agent / nl2sql_agent 的占位模型                    │
├────────────────────────────────────────────────────────────────┤
│  第 2 层：ThinkingToggleMiddleware 进程级缓存（热路径）           │
│  _model_cache: dict[(enable, route, model_name), model]         │
│  → 用户对话中的每次 LLM 调用，命中缓存 ~0s                       │
│  → 最多 8 条，FIFO 淘汰，model_config.json 变更时自动失效        │
├────────────────────────────────────────────────────────────────┤
│  第 3 层：独立路径懒加载单例（冷路径）                            │
│  auto_title.py: _title_model = None → _get_title_model() 懒加载  │
│  thread_compact.py: 直接 create_model()（低频手动触发，无需缓存） │
└────────────────────────────────────────────────────────────────┘
```

## 第 2 层：ThinkingToggleMiddleware 进程级缓存（核心）

### 位置

[src/agent/middlewares/thinking_toggle.py:30-75](src/agent/middlewares/thinking_toggle.py#L30-L75)

### 缓存数据结构

```python
class ThinkingToggleMiddleware(AgentMiddleware):
    _model_cache: dict[tuple, Any] = {}      # (enable, route, model_name) → model 实例
    _model_cache_mtime: float = 0.0          # model_config.json 最后修改时间
    _MAX_CACHE_SIZE = 8                      # 最大缓存条目（防内存泄漏）
```

### 调用流程

```
wrap_model_call / awrap_model_call
  → _maybe_swap(request)
    → _resolve_overrides(request) → (enable, route, model_name)
    → 三个都为 None → return request（短路径，0 开销）
    → _cache_get(key)
      → 检查 model_config.json mtime，变更则清空缓存
      → 命中 → 直接 return request.override(model=cached)  ← ~0s
      → 未命中 ↓
    → create_model(enable_thinking=enable, route=route, model_name=model_name)
    → _cache_set(key, model)
    → return request.override(model=model)
```

### 缓存 key 设计

```python
def _cache_key(self, enable, route, model_name):
    return (enable, route or "", model_name or "")
```

三元组 `(enable_thinking, llm_route, llm_model)` 区分不同模型实例。不同 provider（DeepSeek / Qwen / GLM / Kimi）独立缓存，互不干扰。

### 缓存失效机制

```python
def _cache_get(self, key):
    mtime = self._model_config_mtime()
    if mtime != self._model_cache_mtime:
        self._model_cache.clear()       # 全量清空
        self._model_cache_mtime = mtime
        return None
    return self._model_cache.get(key)

@staticmethod
def _model_config_mtime():
    path = get_workspace_manager().model_config_path
    return path.stat().st_mtime if path.exists() else 0.0
```

- **被动失效**：每次查缓存时比对 `model_config.json` 的 `st_mtime`
- **开销可忽略**：`os.stat` 调用 ~0.0001s，远小于模型重建的 8.2s
- **无需 TTL**：模型配置不频繁变更，mtime 检测已足够

### FIFO 淘汰策略

```python
def _cache_set(self, key, model):
    if len(self._model_cache) >= self._MAX_CACHE_SIZE:
        oldest = next(iter(self._model_cache))  # Python 3.7+ dict 保持插入顺序
        del self._model_cache[oldest]
    self._model_cache[key] = model
```

最多 8 条缓存条目，覆盖所有合理组合（2 种 enable_thinking × 2 个 provider × 2 个 model_name）。

### 线程安全

- `_model_cache` 是类级别属性，所有实例共享
- 在 asyncio 事件循环中，同一时刻只有一个协程执行（Python GIL），`dict` 的 get/set 是原子的
- 当前无需 `threading.Lock`，若未来引入多线程并发可加锁

### 收益

| 场景 | 优化前 | 优化后 | 节省 |
|:---|:---:|:---:|:---:|
| 第 1 次 LLM 调用 | 9.3s | 9.3s（冷启动） | 0s |
| 第 2 次 LLM 调用 | 9.3s | **~0s** | 9.3s |
| 第 3 次 LLM 调用 | 9.3s | **~0s** | 9.3s |
| 第 4 次 LLM 调用 | 9.3s | **~0s** | 9.3s |
| **4 轮合计** | **~37s** | **~9.3s** | **~28s (75%)** |

## 设计决策记录

### 为什么选方案 A（中间件缓存）而非方案 B（模块级缓存）

| 维度 | 方案 A（中间件缓存）✅ | 方案 B（模块级缓存） |
|:---|:---|:---|
| 改动范围 | 仅 `thinking_toggle.py` | `model.py` + `thinking_toggle.py` |
| 受益范围 | 热路径（用户对话 LLM 调用） | 所有 `create_model()` 调用方 |
| 缓存粒度 | 与中间件 override 逻辑耦合 | 通用，独立于中间件 |
| 风险 | 低（只影响思考开关路径） | 中（影响所有模型创建） |

方案 A 已覆盖最大的性能瓶颈（用户对话热路径），冷路径（auto_title 有懒加载、thread_compact 低频）无需额外优化。

### 为什么模型实例可以安全复用

`ChatDeepSeek` / `ChatOpenAI` 等实例是**无状态的配置载体**（api_key、base_url、model、temperature 等），所有运行时状态在 `langchain_core.language_models.BaseChatModel` 层管理。`request.override(model=...)` 只替换调用链中的模型引用，不修改模型实例内部状态。

### 为什么 `enable_thinking=None` 不走缓存

`None` 时 `_resolve_overrides` 返回 `(None, None, None)`，三个值都为 `None` 时直接走短路径 `return request`，不进入缓存逻辑。这意味着前端未传思考开关时，使用 import 时的默认模型（思考默认开），零额外开销。
