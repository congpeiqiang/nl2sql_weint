## 1. 一句话结论

口径库从「几个词条」到「规模化业务知识库」，核心矛盾只有一个：**口径要成为单一事实来源，但 `get_instructions()`/`get_all_knowledge()` 目前是「全量读取 + LLM 关键词过滤」，条目多了会塞爆上下文、漏命中，又退回到「模型靠猜」的老问题。**

解决思路分三层：**组织规范**（一术语一文件 + 结构化 frontmatter）→ **检索分层**（小规模全量读，规模化切确定性查表）→ **澄清门兜底**（口径缺失只会多问不会答错，天然可增量）。

---

## 2. 组织规范（一库一 knowledge/、一术语一文件、结构化 frontmatter）

规模上来后，**一个文件堆所有口径 = 灾难**（diff 不可读、检索靠全文模糊、改一个撞一堆）。改成：

```
knowledge/
  knowledge.yml          # 总索引（术语清单 + 变更记录）
  glossary/               # 名词定义 → get_all_knowledge 读
    报工.md
    应报工人员池.md
    上周.md
    ...
  rules/                  # 业务规则 → get_instructions 读
    报工口径规则.md
    ...
  metrics/ caveats/ sql/
```

### 词条 frontmatter 模板（程序化检索/过滤的唯一入口）

每个词条顶部加 YAML frontmatter，让 knowledge-loader 的「关键词过滤」从「正文模糊匹配」升级为「frontmatter `keywords`/`aliases` 精确匹配 + 正文兜底」：

```markdown
---
term: 报工
aliases: [工时填报, 填工时, 打卡工时]
tables: [do_work_hour, do_work_hour_detail_extend]
related_terms: [应报工人员池, 上周]
keywords: [报工, 未报工, 谁没报工]
owner: 财务部
updated: 2026-09-04
---
## 定义
……
```

字段约定：

| 字段 | 必填 | 说明 |
|---|---|---|
| `term` | ✅ | 术语唯一主键（= 文件名），同库内不可重复 |
| `aliases` | ✅ | 口语别名，命中扩展（如「工时填报」「填工时」） |
| `keywords` | ✅ | 用户问题触发词，供检索过滤 |
| `tables` | ✅ | 关联物理表，供 schema-linking 校验口径表 |
| `related_terms` | — | 关联词条（差集/组合口径） |
| `owner` | ✅ | 业务归属（口径是权威事实，须有负责人） |
| `updated` | ✅ | 最近更新日期，审计用 |

### 总索引 `knowledge.yml` 模板

```yaml
schema_version: 1
terms:
  - term: 报工
    file: glossary/报工.md
    owner: 财务部
    updated: 2026-09-04
  - term: 应报工人员池
    file: glossary/应报工人员池.md
    owner: 财务部
    updated: 2026-09-04
```

一眼看出有哪些口径、谁维护、何时更新。

## 3. 检索分层演进（关键）

| 规模 | 现状 | 做法 |
|---|---|---|
| 小（< 十几 KB） | 全量读 + LLM 关键词过滤 | 现在够用 |
| 中（十几 KB ~ 几百条） | 全量读开始爆 | 靠 frontmatter 过滤收紧注入；`knowledge-loader` 只注入命中的词条而非全量 |
| 大（几百~上千条） | 全量读不可行 | **确定性查表**：口径不进 prompt，在 schema-linking/clarification 阶段按问题抽术语 → 精确 lookup 命中才注入对应条目。注入量与查询相关、与库规模无关 |

> 判据其实已在代码里：`knowledge-loader` 有「数据 >15KB 落盘 `knowledge.json`」的 fallback 阈值——系统本身就把 ~15KB 当成上下文压力线。全量 knowledge 接近这条线时，就该从「全量读」切到「分层/查表」。

---

## 4. 澄清门兜底：维护天然可增量（好维护的根因）

`nl2sql-clarification` 纪律「**无权威口径 → 必须问**」决定了：

- 口径库里没有的词，**只会多问一次，不会答错**；
- 补上一条，对应场景自动不再问。

所以口径库可**渐进式补全**：从高频问题开始（如「报工」），缺的让澄清门兜底，并**把「被澄清门拦下的未知术语」登记进待补清单**（反馈闭环/badcase 机制已有雏形），人工补齐。形成「越用越准」的闭环。

---

## 5. 变更与审计

- **git 版本化 + tag**：每次改口径打 tag（`v7`/`v8`），semantic_refs 按 ref 物化 → 每次实验/查询都能回溯「当时用了哪版口径」。治原 bug 的「错误口径被当已验证知识传播」。
- **口径变更走 review**：口径是权威事实，改错会传播。commit message 规范化：`glossary: 新增「应报工人员池」口径=在职`。
- 变更记录进 `knowledge.yml` 或 CHANGELOG。

---

## 6. 落地建议（待评审）

1. **给已产出的 2 个词条补 frontmatter + 建 `knowledge.yml` 总索引**，作为后续追加的模板。（低成本、立刻可用）
2. **（可选，代码改动）把 `knowledge-loader` 过滤升级为「frontmatter 优先」**，让「追加口径」和「命中口径」解耦。改动小、收益大，需重启后端。
3. 规模触发「查表」后，再议 `nl2sql-clarification`/`schema-linking` 阶段的口径确定性预检（与 S3 词条预检同构，可合并）。
