## 1. 背景与问题

### 1.1 前后端关键词不一致

| 位置 | 关键词来源 |
|------|-----------|
| 后端 LLM 判断委派 | `MAIN_AGENT_PROMPT.md` 中"数据查询触发关键词"硬编码 |
| 前端判断 | `ChatInterface.tsx` 中 `isQueryMessage` 硬编码数组 |

两套关键词人工维护，容易漂移——前端可能漏判/误判，与 LLM 实际委派行为不一致。

---

## 2. 方案设计

### 2.1 总体架构

采用 **前端配置关键词 + 动态提示词注入**。

```
前端 localStorage（queryKeywords）
  │
  └─ stream.submit(configurable.query_keywords) ──► 后端 QueryKeywordsMiddleware
                                                      │ 注入 LLM 系统提示词"触发关键词"行
                                                      ▼
                                                  LLM 判断是否委派 nl2sql
```

**核心思想**：关键词只在前端 localStorage 一份（改词不用动后端），
通过 context（`configurable`）传给后端中间件注入 LLM prompt，
使 **LLM 委派判断与前端判断使用同一份关键词**，零漂移。

## 3. 改动清单

### 3.1 后端

#### 3.1.1 新增 `src/agent/middlewares/query_keywords.py`

`QueryKeywordsMiddleware` —— 在每次模型调用前，从 `request.runtime.config.configurable.query_keywords`
读取前端传入的关键词，动态替换系统提示词中 `**触发关键词**:` 行。

```python
class QueryKeywordsMiddleware(AgentMiddleware):
    _DEFAULT_KEYWORDS = "查询、统计、分析、多少、列表、汇总、排名、占比、趋势"

    def wrap_model_call(self, request, handler):
        modified = self._inject_keywords(request)
        return handler(modified)

    async def awrap_model_call(self, request, handler):
        modified = self._inject_keywords(request)
        result = handler(modified)
        return await result if hasattr(result, "__await__") else result
```

- `_resolve_keywords()`：从 `request.runtime.config.configurable.query_keywords` 读取，
  支持 list/tuple/str，缺失回退默认
- `_inject_keywords()`：定位 `**触发关键词**:` 行并**替换**（只保留一行新关键词），
  无标记行时兜底追加

#### 3.1.2 `src/agent/main_agent.py`

- 注册中间件：`middleware=[skills_middleware, query_keywords_middleware]`

查询关键词的 UI 配置入口——放置在**会话页输入框**旁（齿轮按钮 ⚙️），
而非 ConfigDialog（部署配置弹窗），避免语义混淆（部署 URL / 助手 ID 是连接配置，
关键词是查询行为规则）。

```tsx

  <Settings className="size-4" />
</button>

// 弹窗：关键词编辑 + 保存
```

- 弹窗显示当前关键词（逗号分隔），支持逗号/顿号/换行分隔解析

- 保存后立即生效：前端 `isQueryMessage` 与后端中间件（经 configurable）都用新词

## 4. 关键词一致性（三处对齐）

| 位置 | 关键词 |
|------|--------|
| ① 后端 prompt `MAIN_AGENT_PROMPT.md:52` | 查询、统计、分析、多少、列表、汇总、排名、占比、趋势 |
| ② 后端中间件 `_DEFAULT_KEYWORDS` | 查询、统计、分析、多少、列表、汇总、排名、占比、趋势 |
| ③ 前端 `DEFAULT_QUERY_KEYWORDS` | 查询、统计、分析、多少、列表、汇总、排名、占比、趋势 |

前端配置 `queryKeywords` 优先级最高：配置了用配置值，未配置用默认值（= 后端一致）。

## 5. 关键技术点

### 5.1 为什么不用 `@dynamic_prompt` + `context_schema`

对比分析：

| 维度 | QueryKeywordsMiddleware（选用） | `@dynamic_prompt` + context |
|------|------|------|
| 数据来源 | `configurable`（前端可传）✅ | `runtime.context`（仅 Python 端可传）❌ |
| 前端调用 | `stream.submit(config.configurable)` | 前端 SDK **不支持**传 context |
| 代码量 | ~80 行 | ~15 行 |
| 类型安全 | 弱（裸 dict） | 强（dataclass） |

**结论**：关键词来自前端 localStorage，必须经 `configurable` 传递（前端能传的唯一通道），
因此选用 QueryKeywordsMiddleware。若未来关键词改放后端静态配置，可切换 `@dynamic_prompt`。
