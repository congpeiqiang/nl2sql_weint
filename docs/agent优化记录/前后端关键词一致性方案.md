## 1. 背景与问题

### 1.1 前后端关键词不一致

| 位置 | 关键词来源 |
|------|-----------|
| 后端 LLM 判断委派 | `MAIN_AGENT_PROMPT.md` 中"数据查询触发关键词"硬编码 |
| 前端判断 | `ChatInterface.tsx` 中 `isQueryMessage` 硬编码数组 |

两套关键词人工维护，容易漂移——前端可能漏判/误判，与 LLM 实际委派行为不一致。

---

## 2. 方案设计

### 2.1 总体架构

采用 **前端配置关键词 + 动态提示词注入**。

```
前端 localStorage（queryKeywords）
  │
  └─ stream.submit(configurable.query_keywords) ──► 后端 QueryKeywordsMiddleware
                                                      │ 注入 LLM 系统提示词"触发关键词"行
                                                      ▼
                                                  LLM 判断是否委派 nl2sql
```

**核心思想**：关键词只在前端 localStorage 一份（改词不用动后端），
通过 context（`configurable`）传给后端中间件注入 LLM prompt，
使 **LLM 委派判断与前端判断使用同一份关键词**，零漂移。

## 3. 改动清单

### 3.1 后端

#### 3.1.1 新增 `src/agent/middlewares/query_keywords.py`

`QueryKeywordsMiddleware` —— 在每次模型调用前，从 `request.runtime.config.configurable.query_keywords`
读取前端传入的关键词，动态替换系统提示词中**数据查询段**的 `**触发关键词**【数据查询】:` 行。

```python
class QueryKeywordsMiddleware(AgentMiddleware):
    _DEFAULT_KEYWORDS = "查询、统计、分析、多少、列表、汇总、排名、占比、趋势"

    def wrap_model_call(self, request, handler):
        modified = self._inject_keywords(request)
        return handler(modified)

    async def awrap_model_call(self, request, handler):
        modified = self._inject_keywords(request)
        result = handler(modified)
        return await result if hasattr(result, "__await__") else result
```

- `_resolve_keywords()`：从 `request.runtime.config.configurable.query_keywords` 读取，
  支持 list/tuple/str，缺失回退默认
- `_inject_keywords()`：定位 `**触发关键词**【数据查询】:` 行并**替换**（只保留一行新关键词），
  无标记行时兜底追加
  - **注意（2026-08-11 修复）**：marker 必须带 `【数据查询】` 限定。曾用宽泛 `**触发关键词**:`
    会同时替换 L77 文档处理 / L85 报告生成 / L108 图表可视化三段的触发词，破坏意图识别（见 §8）

#### 3.1.2 `src/agent/main_agent.py`

- 注册中间件：`middleware=[skills_middleware, query_keywords_middleware]`

## 4. 关键词一致性（三处对齐）

| 位置 | 关键词 |
|------|--------|
| ① 后端 prompt `MAIN_AGENT_PROMPT.md:52`（数据查询段，marker `**触发关键词**【数据查询】:`） | 查询、统计、分析、多少、列表、汇总、排名、占比、趋势 |
| ② 后端中间件 `_DEFAULT_KEYWORDS` | 查询、统计、分析、多少、列表、汇总、排名、占比、趋势 |
| ③ 前端 `DEFAULT_QUERY_KEYWORDS` | 查询、统计、分析、多少、列表、汇总、排名、占比、趋势 |

前端配置 `queryKeywords` 优先级最高：配置了用配置值，未配置用默认值（= 后端一致）。

## 5. 关键技术点

### 5.1 为什么不用 `@dynamic_prompt` + `context_schema`

对比分析：

| 维度 | QueryKeywordsMiddleware（选用） | `@dynamic_prompt` + context |
|------|------|------|
| 数据来源 | `configurable`（前端可传）✅ | `runtime.context`（仅 Python 端可传）❌ |
| 前端调用 | `stream.submit(config.configurable)` | 前端 SDK **不支持**传 context |
| 代码量 | ~80 行 | ~15 行 |
| 类型安全 | 弱（裸 dict） | 强（dataclass） |

**结论**：关键词来自前端 localStorage，必须经 `configurable` 传递（前端能传的唯一通道），
因此选用 QueryKeywordsMiddleware。若未来关键词改放后端静态配置，可切换 `@dynamic_prompt`。

## 8. 实施后修复记录（2026-08-11）—— 关键词替换范围收窄为「仅数据查询段」

### 8.1 发现的问题

`QueryKeywordsMiddleware._inject_keywords()` 原用宽泛 marker `**触发关键词**:` 定位并替换，
但 `MAIN_AGENT_PROMPT.md` 中该文本出现在 **4 处**：

| 行 | 意图类别 | 被覆盖后果 |
|----|---------|-----------|
| L52 | 数据查询类（本意） | ✅ 应被替换 |
| L77 | 文档处理类 | ❌ "读取、写入、保存、查看、编辑、创建文件" 被覆盖成查询关键词 |
| L85 | 报告生成类 | ❌ "下载报告、导出为 Markdown、生成分析报告…" 被覆盖 |
| L108 | 图表可视化类 | ❌ "图表、可视化、画图、柱状图、折线图、饼图" 被覆盖 |

即：用户在前端设置查询关键词后，**文档处理/报告生成/图表可视化三类的触发词全部被查询关键词覆盖**，
LLM 意图识别词表被破坏（示例仍在可部分兜底，但触发词指引错乱）。

### 8.2 修复

将 marker 限定为只匹配数据查询段：

- `src/agent/middlewares/query_keywords.py`：`_KEYWORDS_MARKER = "**触发关键词**【数据查询】:"`
- `src/agent/prompt/MAIN_AGENT_PROMPT.md` L52：`**触发关键词**【数据查询】: 查询、统计、…`
- 其他三段的 `**触发关键词**:`（无限定）保持不变，不被替换

同时优化前端 `KeywordSettingsDialog.tsx` 的描述文本，明确关键词作用：
「命中关键词 → 识别为数据查询，自动委派 NL2SQL 子智能体查询；未命中 → 走普通对话；查询进行中再次输入同类查询 → 拦截提示」。

### 8.3 验证

probe（真实调用 `_inject_keywords`，mock ModelRequest，自定义关键词含 "top"）：
- 仅 L52 发生变化（追加自定义词），断言 `changed == [52]` 通过；
- L34/L44（中文冒号变体）、L77/L85/L92/L108 均保持原触发词；
- 文档处理/报告生成/图表可视化三类原关键词字符串完整保留。

### 8.4 维护注意事项

若未来在提示词中新增「数据查询类」以外的触发词段，**不得**使用 `**触发关键词**【数据查询】:`
作为行前缀——该 marker 已专用于数据查询段替换定位。新增意图类别的触发词用普通 `**触发关键词**:`
（或中文冒号变体）即可，不会被关键词设置覆盖。

### 8.5 后续发现（2026-08-11，同日）：前端关键词**从未真正生效** —— 值读取路径 bug

§8.2/8.3 修复的是「替换范围」（marker 宽泛导致覆盖 4 段），但**值读取路径本身也是坏的**：

**问题**：`QueryKeywordsMiddleware._resolve_keywords()` 从 `request.runtime.config.configurable` 读取前端关键词。
但 langchain 官方明确 **`Runtime` 不含 `config`** —— 模型调用中间件里 `request.runtime.config` 恒为**空 dict**，
因此**无论前端传什么关键词，`_resolve_keywords` 永远回退默认 9 词**。§8.3 的 probe 只 mock 了 ModelRequest
（未走真实 runtime），没暴露这条路径；而此前对「设置生效」的结论是基于 probe 的误判。

**实证（真实 E2E，2026-08-11）**：run 的 configurable 显式传 `query_keywords=["票房","排行"]`，
后端日志 `[QueryKeywords] 注入查询关键词: 查询、统计、分析、…（默认词）` —— 传了但没读进去。

**修复**：`_resolve_keywords` 改为 `langgraph.config.get_config()` 优先读取（与 `main_agent.dynamic_prompt`
同路径），`runtime.config` 兜底。

**验证**：同样传 `["票房","排行"]` → 日志 `[QueryKeywords] 注入查询关键词: 票房、排行`；不传 → 回退默认词（回归通过）。

**教训（通用）**：模型调用中间件里读 configurable（db_name / query_keywords / 前端设置），**一律用
`langgraph.config.get_config()`**，不要用 `request.runtime.config`（恒空）。同源问题见
《前端配置数据库接入方案》§12.3（`CurrentDbContextMiddleware` 同因失效）。
