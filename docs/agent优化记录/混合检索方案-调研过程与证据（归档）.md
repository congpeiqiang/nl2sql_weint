# 混合检索方案（LanceDB + FTS）：评估与实施设计

**日期**：2026-09-28
**状态**：**评估稿，未实施**（代码一行未动）
**需求来源**：「目前 nl2sql 检索方式不是向量检索，希望用 lancedb + fts 混合检索」
**结论摘要**：**推荐 LanceDB**（自建薄层，不用 wren 的 `MemoryStore`）＋ **FTS 用 `ngram(3,3)` 起步** ＋ **远端/独立服务嵌入（不要在 app 容器里加载 `sentence-transformers`）** ＋ **单写者**。真正的瓶颈不是「没有向量」，而是①示例 SQL 的**写路径从未接线**（池子是空的）、②**schema 与知识目前是全量注入**（WIT `mdl.json` 602KB / `get_instructions` 实测 20.9k 字符）。

- **三台主机网络口径一览（2026-09-28 实测，别互相套用）**：**64（weint，部署服务器）有外网** · **34（dev 测试）无外网、DNS 不可用** · **13（ai-gpu，GPU/嵌入主机）无外网**（huggingface 与 registry.ollama.ai 均不可达）。

### 2.2 内存：**待确认，且限制可能从未生效**

- `docker-compose.yml` 写的是 `deploy.resources.limits.memory: 1200m`，注释口径为「服务器 3.4GB，Langfuse 已占 ~2GB」。
- 但部署用的是 **`docker-compose` v1**（[NL2SQL-部署与更新手册.md:26](../../docs/weint环境/NL2SQL-部署与更新手册.md#L26) 的「v1 铁律」），且该文件**没有 `version:` 头** ⇒ compose v1 在 v1 格式下**忽略 `deploy` 键**（典型表现是一句 `WARNING: Some services use the 'deploy' key, which will be ignored`）。**即 1200m 很可能从未生效。**
- 用户口径：服务器**还有 20G 空闲内存**。
- **判定命令（只读）**：`docker inspect langgraph-api --format '{{.HostConfig.Memory}}'` → `0` = 无限制。
- 若要真正设限：compose v1 只认 `mem_limit:` / `memswap_limit:`（或跑 `docker-compose --compatibility`）；`docker-compose.yml` **不在发版 tar 里，必须在服务器侧打补丁**；重建走三步 `stop → rm -f → up -d`。
- 附注：**加内存不会提高问数并发**——天花板是全局 10 个 run 槽（一次问数约 3 个 run），P2-7 实测 6 并发的失败是 `openai.APIConnectionError` 而非排队。

### 2.3 教训（写给未来）

**判「某环境能不能联网 / 能不能加依赖 / 有多大内存」，只看运行期配置与实测**（`model_config.json` 的 base_url、`docker inspect`、`docker exec` 探针），**不要引用文档里的资源与网络断言**——本仓已有两处台账因这类断言写错（本文 §2.1 与 2.2）。写方案时把「离线」「内存不足」当**待验证假设**列出，而不是当已知约束。

## 3. 选型

### 3.1 两引擎对比

| 维度 | **LanceDB**（推荐） | sqlite-vec + FTS5(trigram)（备选） |
|---|---|---|
| 混合检索 | 原生：`create_fts_index` + `search(query_type="hybrid").rerank(RRFReranker())`，后续可换 `CrossEncoderReranker` | 需自写融合（RRF 约 60 行） |
| 中文 FTS | `ngram(3,3)`（零模型文件）或 `jieba/default`（需语言模型文件） | FTS5 `tokenize=trigram`（**本仓已跑通**） |
| 依赖 | `lancedb` 已在 lock；**不要拖 `sentence-transformers`/torch** | `sqlite-vec` 已在 lock（stdlib sqlite + 扩展） |
| 与本仓约定 | 新形态（非 sqlite）⇒ 备份/审计/metrics 要另做 | 完全吻合「一库一目录 sqlite + 共享连接 + RLock + WAL」既有约定 |
| 写并发 | **无跨进程写锁保障**（本仓架构文档已把此列为风险、并把 pgvector 当目标态：`docs/agent优化记录/NL2SQL存储与部署架构方案.md:106`）⇒ 必须单写者 | 一把 RLock 解决 |
| 规模适配 | 10³~10⁴ 用不上 ANN，但不妨碍 | 暴力扫 10ms 级，够用 |
| 主要成本 | 单写者纪律 + 每库路径钉死 + 一次并发写实测 | 自己写融合（可确定性测试） |

### 3.2 为什么推荐 LanceDB

原来的推荐是 sqlite-vec，撑它的三根支柱是「① 离线烘不了权重 ② 内存放不下 ③ wren 不给混合检索」。**①② 已分别被 §2.1 / §2.2 拆掉**，只剩 ③——而 ③ 同时是 LanceDB 的理由：既然 **FTS 腿与 RRF 融合选谁都得自己写**（事实 #3：wren 0.13.0 没有 `create_fts_index`/`query_type`/`rerank`），那 LanceDB 自带的混合检索就是**净省下来的代码**，还白送后续换 CrossEncoder 重排的口子。语料 10³~10⁴ 用不上 ANN 是「不必要」，不是「不合适」。

### 3.3 什么情况下翻回 sqlite-vec

- 要求索引与其它运行时数据**同构**（同一套备份/保留/metrics/审计），或要求**零新形态**；
- 需要在同一进程里既写又读、且不想受「单写者」约束；
- 压测发现在 10⁴ 量级 LanceDB 的打开/索引开销不可接受。

## 4. 目标架构

### 4.1 分层

```
语义库(wren project, git 版本化)
  ├─ models/*/metadata.yml, cubes/*/metadata.yml   → schema items
  ├─ knowledge/{rules,glossary,metrics,caveats,sql}/*.md → knowledge items / example_sql
  └─ target/mdl.json (602KB@151表)                  → 索引构建的输入
                 │
        [索引构建]（离线/写路径，单写者）
                 ▼
   <AGENT_DATA_ROOT>/<db>_semantic/.index/           ← LanceDB（per-库钉死路径！）
     ├─ items 表：id, kind, src_path, title, text, meta_json, rev, vector
     ├─ FTS index on text（ngram(3,3) → 后续 jieba/default）
     └─ rev = (mdl_hash | semantic git rev)
                 │
        [检索薄层 src/agent/retrieval/]（问数链路只读）
          hybrid(q, k) = FTS top-k ∪ vector top-k → RRF → 过滤(db_name/kind)
                 │
      ┌──────────┼──────────────┬─────────────────┐
      ▼          ▼              ▼                 ▼
  get_context  recall_queries  search_knowledge  store_query(写)
  （schema）   （示例 SQL）     （口径/术语）      （唯一写入口）
```

### 4.2 关键设计点（每条都对应一个已知事故形态）

1. **路径 per-库钉死**，不要 `~/.wren/memory/` 单槽（事实 #4）。本仓「共享单槽」出过三次事故（wren 活项目目录 / semantic_db 物化 / skills_versioning 物化）。
2. **单写者**：索引只由「语义库构建/更新」这条写路径写；问数链路只读。原因是 LanceDB 跨进程写锁无保障（3.1 表）。
3. **索引是派生物**：键 = `(db_name, mdl_hash | semantic_rev)`；**重建挂在语义库写入/更新路径上**，不要再造「切换」事件当失效入口（`workspace-switch-cache-reset` 的血案：失效入口只有「切换」一个，机制删了就漏）。
4. **嵌入不在 app 容器里做**（见 §5），检索薄层只负责「取向量 → 查库」，向量由远端/独立服务提供。
5. **降级链**：向量腿失败 ⇒ 自动降级纯 FTS（fail-open），保证「检索变差」永远不会变成「问数不可用」。

### 4.3 索引内容（kind → 来源）

| kind | 来源 | 检索价值 |
|---|---|---|
| `schema_table` / `schema_column` | `<project>/models/*/metadata.yml`（或从 `mdl.json` 拆） | **最高**：现在是 602KB 全量注入 |
| `cube` / `measure` / `dimension` | `<project>/cubes/*/metadata.yml` | 高（Cube 通道已在用） |
| `knowledge_rule` / `knowledge_glossary` / `knowledge_metric` / `knowledge_caveat` | `<project>/knowledge/*/*.md` | 高（现为全量读，实测 20.9k 字符） |
| `example_sql` | `<project>/knowledge/sql/*.md`（+ 将来的自动化回写） | 中（**前提是把池子填起来**，见 §6 分期 P0） |

| 但 Ollama 自己的调度器 | 启动时**认得出** CUDA：`sched.go:620 gpu memory id=0 library=CUDA available="21.2 GiB"`、WARN 里 `gpus=1` ⇒ 出现「调度器以为在 GPU、runner 实际在 CPU」的错位，日志因此极难看懂 |
| 排除镜像/宿主问题 | 同一镜像现起 `docker run --rm --gpus '"device=0"'` → `nvidia-smi -L` **正常列出 RTX 4090（rc=0）** ⇒ 镜像与宿主的透传都好，**坏的是这两个已 Up 3 周的长命容器**（设备节点与驱动库其实都在：`/dev/nvidia2`、`/usr/lib/x86_64-linux-gnu/libcuda.so.1`、ldconfig 有缓存，`CUDA_VISIBLE_DEVICES` 未设，但进程就是开不了卡） |

⇒ **实测的修复配方 = compose 重建，连语法都不用改**：这两个容器由 **docker compose v2** 管（project `ollama_sl`，文件 `/icp-data/sulin_data/ollama_sl/docker-compose.yml`，服务 `ollama-bgem3`/`ollama-qwen38`，`network_mode: host`）。我用**现有写法**（`deploy.resources.reservations.devices`，生成的 `DeviceRequests.Driver="nvidia"`）现起临时容器实测：`nvidia-smi -L` 正常、bge-m3 真上卡 ⇒ **坏的只是 09-05 创建的那两个长命容器**（Docker/工具链升级后其设备访问失效），**不是写法问题**（CDI 写法 `devices: [nvidia.com/gpu=0]` 同样可用，属可选）。动作：备份 compose → 把 `ollama-bgem3` 的 `device_ids: ["2"]`/`NVIDIA_VISIBLE_DEVICES=2` 改成 `["0"]`/`0`（GPU2/3 已被 vLLM 占 21.8G/23G，bge-m3 挤不下；GPU0/1 全空）→ `docker compose up -d --force-recreate ollama-bgem3`（**别用 `down`**，会连带删另一个服务）。**三条验证判据**：`docker exec bgem3 nvidia-smi -L` 列出 GPU、日志有 `CUDA0 model buffer`、`/api/ps` 的 `size_vram > 0`。
> 另注：**这台机不是我们的**（同机有别的团队的 vLLM/k8s/GraphRAG），所以方案设计仍**不假设** GPU 必然可用 —— 嵌入不可用要能降级纯 FTS。

⇒ 连带影响（机理同源，待重建验证）：`qwen38` 与 `bgem3` 是同一 compose 同一秒创建、同一套注入路径 ⇒ 里面的 `qwen3.8:27b`（Langfuse judge 用）**也在 CPU 上跑**（`system_info: n_threads = 56 / 112` 是 CPU 口径的痕迹）。重建应同样修好，那才是数量级的收益；重建前先确认谁在依赖 `:11434`。

**选它的三条理由**：① 零部署、零镜像增长、零 app 容器内存（嵌入不进 `langgraph-api`）；② **数据不出内网**（`bge-m3` 在私网、判断力实测正常）；③ 不与他人争 GPU（修复后只占 GPU0 的 ~1.1G；GPU2/3 的 vLLM 完全不受影响）。

**修复后的延迟口径（2026-09-28 实测，替代此前"CPU 55ms/条"）**：热态短文本 **61–85ms**、~100 字 chunk **60–120ms**、**4 条并发总耗时 166ms**（`OLLAMA_NUM_PARALLEL=4` 有效）。两个反直觉点记下来：① **GPU 冷启 16.8s > CPU 冷启 4.9s**；② 首次长输入出现过 **10.9s**（一次性，host-mapped 那半权重首次入页缓存），复测即回落 —— 所以单次慢请求不要急着判故障，先复测。另：**`nvidia-smi` 采样到 util 0% 不等于没上卡**（请求只有几十毫秒，0.7s 采样基本抓不到），判据要用 `offloaded N/N layers` + `CUDA0 model buffer`。

**接线注意（写进实现）**：
- **主选 `:11435`（专用 `bgem3` 容器）**：`:11434` 的 `OLLAMA_MAX_LOADED_MODELS=1` ⇒ bge-m3 与 judge 的模型**互驱**（实测：bge-m3 载入后 `/api/ps` 只剩它一个）。索引期 bge-m3 常驻会把 27B judge 反复踢出去，而 27B 重载代价极高（重建前是 CPU 重载 17G；重建后即便在 GPU 上也仍是一次昂贵冷启）。`:11435` 是同镜像的专用实例，代价是冷启一次（该容器 `OLLAMA_KEEP_ALIVE` 已是永不驱逐，首调后摊销）。
- `:11434` 降为**备选**（若 `:11435` 被他人占用/改用途）。
- 索引期批量嵌入要**限流 + 分批 + 单批超时**；该机是共享主机（k8s + mysql/kafka + GraphRAG + 另一个 vLLM），要能容忍对方重启。
- **不要走 `:8100`**（那是另一个 vLLM 容器，实测 `/v1/embeddings` → 404）。
- 硬约束不变：问数期每问 1 次嵌入调用；**嵌入不可用 ⇒ 降级纯 FTS**（fail-open），且必须有超时。

**其它通道（备选，按代价）**：

| 选项 | 评价 |
|---|---|
| 64 上自建 Ollama 服务 | 备选。有外网可 pull，但要占 64 的磁盘与运维面；放着现成的 `.13` 不用没道理 |
| 百炼 compatible-mode `/embeddings`（`text-embedding-v4`） | 备选。零部署，但业务知识全文发公网 + 公网抖动 |
| 容器内本地模型（ONNX 优先，**别用 torch**） | 兜底。镜像 +150~200MB、首调加载；只在 `.13` 不可用时考虑 |
| dev34 内网 Ollama（`192.168.25.34:11434`） | 仅用于 34 上的功能回归（34 无外网；本机 curl `/api/tags` 不通，有哪些模型未确认） |

| 期 | 内容 | 验收 |
|---|---|---|
| **P0** | 修**写路径**：goodcase/点赞 → `knowledge/sql/*.md`（今天完全没接）+ 同步写 items | 示例池 0 → N；`recall_queries` 有真实命中 |

## 8. 风险与硬规则

| # | 规则 |
|---|---|
| **R1** | **口径核验绝不能被检索窄化**。检索只服务「注入给模型的上下文」；`load_knowledge_corpus`（[caliber_evidence.py:339-387](../../src/agent/utils/caliber_evidence.py#L339-L387)）必须继续看**全量**语料，否则「证据不在库」会变成假判决（报告口径要有逐字原文，这条已被证伪过两次） |
| **R2** | **默认开关 = 旧行为逐字不变**（照 `scripts/verify_failure_signal.py` 的范式：每段带**负对照**，锁住「无开关时与今天一致」） |
| **R3** | 不要只翻 `WREN_MEMORY_BACKEND`（§5 陷阱） |
| **R4** | 若最终选 sqlite 形态：新 store 要补 `sqlite_paths.STORE_NAMES` + `retention.py` 的 `/metrics` 字节数与按龄清理表两处硬编码 |
| **R5** | LanceDB 必须先做一次**并发写实测**（两进程同时写同一库目录），确认失败形态与恢复手段，再决定单写者的强制方式 |
| **R6** | 索引目录要进备份/保留策略；索引损坏 ⇒ 可重建（派生物，不许成为唯一真相源） |
