## 0. 结论速览

**隔离的原子是"库"（`db_name`），不是"人"，也不是"目录"。**

| 层 | 内容 | 位置 | 谁维护 | 份数 |
|---|---|---|---|---|
| **语料层** | `db_config.json`（库连接 + `wren_project` 绑定）、wren 语义库目录（MDL + 知识库）、`skills/`、`model_config.json` | `<AGENT_DATA_ROOT>/workspace/`（工作区，2026-09-25 起路径钉死）+ `<AGENT_DATA_ROOT>/shared/` | 管理员 | **全公司 1 份** |
| **授权层** | `人/组 → db_name` 授权、`thread → 归属人`、`报告 → 产出的库` | `<AGENT_DATA_ROOT>/auth/auth.sqlite` | 管理员 + 系统自动写 | 1 份 |

四句话：
1. **语料层一份不动**——库配置与语义库目录物理上永远只有一份，管理员更新一次全公司生效（语义库**内容**更新本来就不需要重启后端）。授权只是"看得见哪些库"的**视图**，不复制任何目录。这直接满足硬约束。
2. **后端不做登录、不存账号**：前端登录后给 token，后端**只校验 token** 并映射成本地 `user_id`（§4）。
3. **执行点只有四处**：库清单 API 过滤 → 语义库 API 过滤 → 运行期工具裁剪（`wrenai_<库>`/`dbmcp_<库>`）→ 库名入参校验（前端传来的 `db_name` 是不可信输入）。
4. **库级授权必须兼任"数据可见性"维度**（§3.4），并且**必须先关掉 nginx 的 `/report/` 静态目录**（§7 第 1 条，现存洞）——否则隔离会被这两条路绕过。

## 3. 目标模型

### 3.1 授权只到库

```sql
users(user_id PK, display_name, source, status, last_seen_at)   -- 由 token 首次出现时自动登记，管理员只补授权
groups(group_id PK, name, external_id)                          -- external_id = 网关/AD 组标识（可选）
user_groups(user_id, group_id)
grants(subject_type, subject_id, db_name, level)                -- level: query | admin
thread_owner(thread_id PK, user_id, created_at)                 -- 会话可见性 = 仅本人
thread_db(thread_id, db_name, first_seen, last_seen)            -- 该会话用过哪些库（供 trace/报告的库维度判定）
```

- **可见库集** = 直接授权给他的 `db_name` ∪ 所在组的 `db_name`，与 `corpus/db_config.json` 里实际存在的库取交集。
- `level=admin` 的库可看配置与语义库管理入口；普通 `query` 只能看见"有这个库"并发起查询。
- 语义库与库的对应关系**现成存在**：`db_config.json` 每条记录的 `wren_project` 指向该库的语义库目录（`db_config_store.py:45-57`），`wrenai_<库名>` MCP server 一一对应（`mcp_tool.py:196-203`）。所以按 `db_name` 授权自动覆盖"对应的语义库"，不需要第二张表。
- **若 token 里带 AD/网关组信息，grants 直接映射组** → 管理员不用维护人员名单（§4.4 会问对方要字段）。

### 3.2 硬约束如何被满足

| 动作 | 结果 |
|---|---|
| 管理员更新语义库内容（git pull + wren build） | 全公司下一个查询即读到新 MDL，**不需要重启**（MCP 每次工具调用新起子进程读 `target/mdl.json`） |
| 管理员改授权（把库 A 给项目组 B） | 立即生效，**不需要重启**（库与语义库都没变，只是可见性变化） |
| 管理员**新增/删除**一个库或语义库 | **不需要重启**（2026-09-19 已把当初的重启门槛消除：运行期工具注册表 `_sub_entries` + `DynamicMCPToolsMiddleware`，写接口同步装/卸该库工具；`POST /api/mcp/reload` 可手动全量对账）。与登录隔离正交，但**它正是"授权变化立即生效"的前提**——否则新库的工具要重启才能出现 |

> 注：本方案初稿（2026-09-19 早）把"新增/删除库需重启"记为**既有约束**并声明不在方案内消除；当天稍后已作为独立改动落地（见 §5.4 末尾与 `docs/agent优化记录/wren语义库管理.md`）。
### 3.3 判定入口（全后端唯一）

```python
# src/agent/auth/grants.py
def visible_dbs(user) -> set[str]              # 该用户可见的库名集合（含组授权）
def can_access_db(user, db_name) -> bool        # 单库判定；管理员恒 True
def require_db(user, db_name) -> None           # 不通过 → 403
def owned_thread(user, thread_id) -> bool       # 会话可见性 = 仅本人（管理员例外）
```

**所有地方都走这几个函数**，不要在各 handler 里各写一遍 SQL——散落的判定必然漏。

### 3.4 【关键】库级授权必须兼任"数据可见性"维度

库级授权只管"能不能对某个库发查询"。如果不管产出，隔离会被现成的路绕过：

- `GET /api/threads/fts?q=`（`thread_search.py:146-166`）——**主动枚举全库所有会话**建索引，B 搜一个关键词就读到 A 的 WIT 会话内容，并顺带泄漏 thread_id。
- `GET /api/reports/{filename}`（`report_file.py:38-53`）——报告目录全局共享、文件名可枚举。
- **（更严重，且已在生产开着）nginx 的 `/report/` 静态路由 + autoindex**：服务器上 `nginx` 把 workspace 卷只读挂进容器，`location /report/` alias 到 `/workspace/report/` 且 **autoindex on**（`docs/weint环境/nl2sql-部署信息.md:16-24`，访问入口 `http://192.168.25.64:8080/report/` 可目录浏览）。**它完全绕过后端**——后端加多少校验都没用。**必须先关掉**（§7 第 1 条）。

**处置**：

- **会话**：`thread_owner(thread_id → user_id)`，可见性 = 仅本人（管理员可跨用户，走显式开关 + 审计）。**已确定，不做"同库互看"**。
- **报告**：记录产出时的 `db_name` 与作者 → 可见性 = 我对该库有授权（默认**同库可见**，因为报告是交付物且同项目的人本该互看；要收成仅本人只是一处判定）。实现用 `report/.index.json`（`{filename: {db_name, user_id, created_at}}`，写入加锁），**索引里没有的记录 → 只有作者/管理员可读**（fail-closed）。
- **trace / 反馈 / 标注条目**：三者都已带 `db_name`（`feedback/store.py:70-93` 有 `db_name` 列；`langfuse_metadata.py:172` 把 `db_name` 写进 trace metadata）→ 按同一判定过滤。

**为什么报告按库而非按人**：同项目的人本来就该互看报告（否则同组要互相传文件），跨项目天然隔离；而且 `report/` 不用分目录——**分子目录会改 `/api/reports/{filename}` 的 URL 形状**，踩到前端那份很脆的报告链接正则契约（锚点必须 `/report/` 段、文件名允许空格与中文标点，有事故史）。索引方案对前端零影响。

## 4. 后端鉴权层（token 校验，不做登录）

### 4.1 两个挂载点（都必须，缺一个就有洞）

| 要保护的 | 机制 | 依据 |
|---|---|---|
| `/api/*`（63 个端点）+ 全局校验 | `src/api/custom_app.py` 加 `TokenAuthMiddleware`（写 `scope["state"]["user"]` / `request.state.user`） | `server.py:194` 把 custom middleware 提升为全局 |
| langgraph 原生 `/threads`、`/runs/*`（401 + 图内身份） | `LANGGRAPH_AUTH` → `src/agent/auth/backend.py:auth`（`langgraph_sdk.Auth()` + `@auth.authenticate`） | `auth/custom.py`；`models/run.py:241-247` 注入 `configurable` |

两处调**同一个** `verify_token()`（`src/agent/auth/token.py`），逻辑不重复。

**两个必须知道的坑**：

1. **`middleware_order: "auth_first"` 修不好这个问题**——读了 `server.py:151-201`，它只调换 `protected_mount` 内 auth 与 custom 的先后次序，自定义路由的 bundle（`user_app`）**始终不带 auth 中间件**。要覆盖 `/api/*` 只能自己写中间件。
2. **鉴权中间件只读 header/cookie，绝不读/重放 body**（SSE 会被破坏，本仓有教训）。

**`LANGGRAPH_AUTH` 的落法**：`start_server.py` 读 `graph.json` 时**不吃 `auth` 键**（只吃 graphs/checkpointer/store，见 `:42-70`）。任选其一：

```python
# 方案 A（推荐，与 checkpointer/store 同款写法）
auth_config = config.get("auth")
if auth_config:
    env_updates["LANGGRAPH_AUTH"] = json.dumps(auth_config)
```

或方案 B：写进 `.env` / `.env.prod`（compose `env_file` 注入进程环境）。**注意 `os.environ.setdefault` 在 `load_dotenv` 之前执行**，env 文件不会被 graph.json 的默认值顶掉。

**一条生产护栏**：**绝不能设 `LANGSMITH_LANGGRAPH_API_VARIANT=local_dev`** —— 该变体下 `auth/custom.py` 会挂 `StudioNoopAuthBackend`，任何带 `x-auth-scheme: langsmith` 的请求**免登录**。当前 compose 与 `start_server.py` 都没设（安全），要把"别设"写进部署手册。

### 4.2 token 校验适配器（本方案唯一需要外部对接的代码）

`verify_token(token) -> User | None`，按 token 类型二选一：

| token 类型 | 校验方式 | 成本 |
|---|---|---|
| **签名 JWT**（推荐，网关/SSO 常见） | 用公钥/JWKS **本地验签**，读 `sub`/`preferred_username`/`groups` | 无网络往返，最优 |
| **不透明 token**（opaque） | **服务端到服务端**调网关 introspection/userinfo 校验 | 有往返 → **必须本地缓存**（TTL 60~300s，按 token 哈希），否则 200 人每请求一次会把网关打爆 |

产出统一的内部 `user`：`{user_id, display_name, groups[]}`。**`user_id` 一旦选定就不再变**（建议用网关的 `sub` 或工号；不要用显示名）。

**必须有的两个开关**（否则开发/离线测试全挂）：

- `NL2SQL_AUTH_DISABLED=1`：**仅 dev**，跳过校验并把身份固定成配置的开发用户。生产由 compose 硬编码 `"0"`（防 `.env` 覆盖——本仓在 `ALLOW_PREVIEW_OPT_IN` 上已经栽过一次：本该生效的错值突然生效，见部署手册 §9.4）。
- `NL2SQL_AUTH_DEV_TOKEN=<token>`：给离线测试/脚本用，等价于一个固定 token。生产不设。

### 4.3 必须放行的白名单

`/ok`（**compose healthcheck 用**：`curl -sf http://localhost:2026/ok`，拦了容器会反复重启）、`/_next/*`（Next 静态资源）、`/ui*`（langgraph Studio 资源路径，官方中间件本身就绕过它）、静态登录页本身。

**建议同时关掉**：`/docs`、`/openapi.json`（`LANGGRAPH_HTTP.disable_meta`）——否则整套 API 结构对未登录者可见。**注意 `/ui`（LangGraph Studio）在启用鉴权后要不要留，需要明确**：它是个可读写全部 thread 的调试 UI。

### 4.4 与前端/网关团队的接口契约（唯一接缝）

**后端提供**：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | **（P0 临时端点，SSO 接入后下线）** 校验用户名密码 → `Set-Cookie: nl2sql_token=<token>` → `200 {"user_id","display_name","is_admin"}` / `401` |
| POST | `/api/auth/logout` | 清除 cookie → `204` |
| GET | `/api/auth/me` | 带 cookie 调用 → `200 {"user_id","display_name","is_admin","dbs":[...]}` / `401`。前端用它渲染当前用户与"我能看哪些库" |
| — | 其余全部端点 | 一律要求凭据 |

**凭据传递（已确认选 Cookie）**：

**Cookie `nl2sql_token=<token>`**（`SameSite=Lax, Path=/`）：页面与后端同域（生产走 nginx `:8080` 统一入口），浏览器 `fetch` 默认 `credentials: "same-origin"` → **前端不需要给 langgraph SDK 设 `defaultHeaders`，登录页种好 cookie 即可**。不改 DLP 密文文件（`ClientProvider.tsx`、`useChat.ts`、`config.ts`）。同时兼容 `Authorization: Bearer <token>` header（为后续 SSO/网关场景预留）。

**约定**：

1. **401 与 403 语义分开**：`401`（无/过期/无效 token）→ 前端跳登录或刷新 token；`403`（已认证但无权访问该库/该会话）→ 显示"无权访问"，**不要跳登录**（跳了会让用户以为要重新登录，反复刷新 token）。
2. **前端不要自己裁剪库列表**：下拉框数据源就是 `GET /api/db-configs`，后端已按授权过滤。前端只需处理"列表为空"→ 提示"你的账号尚未被授权任何数据库，请联系管理员"。
3. **不要相信前端传来的 `db_name`**：后端会交叉校验（§5.5），越权返回 `403` 而**不是静默换库**（静默换库会让用户以为查的是自己的库，是更坏的 bug）。
4. **token 过期与刷新**：由前端负责（登录侧的事）。后端只做无状态校验；**不做 token 续期**。
5. **需要对方提供的信息**（拿到这些才能写完 `verify_token`）：
   - token 是签名 JWT 还是不透明串？若是 JWT：算法 + **验签公钥或 JWKS 地址**；
   - 若是不透明串：**校验接口 URL + 调用鉴权方式**（是否需要 client_id/secret）；
   - token 里代表**用户唯一标识**的字段名（`sub`/工号/域账号）；
   - **是否带 AD/网关组信息**（字段名）——带的话，库授权可以直接映射组，管理员不用维护人员名单；
   - token 有效期/刷新机制；
   - **登录是否一定要经过本系统的域名**（若前端已处理，后端不关心）。

**网关/SSO 场景的推荐流程**（供前端参考）：用户访问系统 → 无 token → 跳公司登录 → 登录成功后前端拿到 token 并种 cookie（或直接调 `/api/auth/me` 验证）→ 之后所有请求带该 cookie/header。

### 5.4 面 C：运行期工具裁剪（唯一能真正阻止"对无权库发查询"的地方）

`src/agent/middlewares/tool_filter.py` 已有同构先例（按 `configurable.db_name` 只保留 `wrenai_<当前库>_*`，并可选移除 `dbmcp_*`）。**扩一处**：

```
规则：当前用户未授权的库，其 wrenai_<库>_* / dbmcp_<库>_* 工具一律摘除
```

- 库名解析沿用既有路径（`_resolve_db_name()` 用 `langgraph.config.get_config()`，**不能用 `request.runtime.config`**，后者恒为空——本仓踩过）。
- 库名 → 工具前缀沿用 `semantic_db.wrenai_server_name()`（**唯一净化源**，别二次实现，库名含中文时前缀会漂移）。
- 用户身份同样从 `get_config()["configurable"]` 读（`langgraph_auth_user_id`），与 `db_name` 同源。
- **fail-closed**：身份缺失或授权查询失败 → 只保留非 wrenai/dbmcp 工具（图表等），**不放行**。注意这与既有 `NL2SQL_SEMANTIC_EXCLUSIVE_TOOLS` 的 fail-open 取向相反，原因是那条规则属于"能力降级"，这条属于"越权阻止"。

效果：**只有被授权的库的工具会出现在模型面前**，模型连"看到别的库"的机会都没有。

**⚠️ 与 2026-09-19 新增的动态工具通道的交互（实施面 C 时必须一并处理）**：
`DynamicMCPToolsMiddleware` 已抢先挂在 `_middleware` 最外层（`nl2sql_agent.py:221`），
它会把**运行期注册表里的全部子工具**并入 `request.tools`。两条硬要求：

1. **顺序**：授权过滤必须跑在它**内层**（即保留它继续当第 0 项）。合并 → 再按授权裁，
   顺序反了授权过滤会被重新加回来的工具绕过。`ToolFilterMiddleware` 现在就在内层，
   所以按库过滤（面 C 的邻居）天然成立。
2. **执行侧也要判**：`DynamicMCPToolsMiddleware.wrap_tool_call` 会按名字把调用**改道**到
   注册表里的当前实例并执行 —— 它不看授权。所以面 C 不能只做"出站清单裁剪"：历史消息里的
   存量 tool_call、模型幻觉出的库名，都会走到这里。**授权判定必须同样加在工具执行路径上**
   （最小改法：在这条 wrap_tool_call 链上加一道 `can_access_db` 检查，未授权同样返回
   `status="error"` 的 ToolMessage）。这跟 QueryGate 的"看不见 + 拦得住是纵深"是同一条道理。

## 8. 容量与运维

- **容量已解除阻塞**：服务器可扩容 → 内存不再是前提条件。但 `N_JOBS_PER_WORKER=10` 与 `LANGGRAPH_RUNTIME_EDITION=inmem` 在 200 人下的排队行为要先观测。

- **端口暴露（与鉴权相关，不只是运维）**：生产后端 `langgraph-api` **宿主直连可达（`:2026`）**。由于本方案的 token 校验在**后端**（不在 nginx），直连不构成绕过；但若将来把校验挪到 nginx，`:2026` 就必须收回（只留 compose 内网）。**结论：校验必须留在后端**，这条写进设计约束。
- **备份**：`auth.sqlite`（授权与归属）**必须备份且加密**；`corpus/`（语义库 + 知识库）已在 git 上。
- **配置不同步陷阱**（本仓已有前科）：`docker-compose.yml` 与 `docker/nginx.conf` **不随发版脚本传播**，服务器那份是手工维护的。§7.1 的 nginx 改动手工同步，且要写进部署手册。

### A.1 后端改动清单

#### 新建 `src/agent/auth/` 模块（4 个文件）

| 文件 | 职责 |
|------|------|
| `__init__.py` | 空 |
| `token.py` | `sign_token(user_id, display_name, is_admin, token_version=0) -> str`：HMAC-SHA256 签发，payload=`base64({user_id, display_name, is_admin, exp, pv})` + `.` + `hex(sig)`；24h 过期。`verify_token(token) -> User \| None`：验签 + 过期 + **吊销**（P1-12：`pv` ≠ 账号当前 `token_version`／账号已删 → 无效；`display_name`/`is_admin` 改为**以记录为准**，降权立即生效）。`NL2SQL_AUTH_DISABLED=1` 时跳过校验返回固定 dev 用户。密钥来源：`NL2SQL_AUTH_SECRET` 环境变量，未设则自动生成并存 `AGENT_DATA_ROOT/auth_secret`。 |
| `backend.py` | langgraph 官方 auth 适配：`auth = Auth()` + `@auth.authenticate` 从 Cookie `nl2sql_token` 或 `Authorization: Bearer` 提取 token → 调 `verify_token` → 返回 `{display_name, is_staff}` 或抛 `AuthenticationError`。 |
| `users.py` | 临时用户管理：读 `AGENT_DATA_ROOT/auth_users.json`（`[{user_id, password_hash, display_name, is_admin, token_version, must_change_password}]`）；`verify_password(username, password) -> User \| None`。**P1-12（2026-09-23）**：密码哈希由单轮无盐 SHA-256 改为 **PBKDF2-HMAC-SHA256（26 万次迭代 + 每用户随机盐）**，旧哈希在登录成功时就地升级（不强制重置密码）；`token_version` 作吊销计数器（改密/`revoke_tokens` +1，登录不动 → 多设备并存）；`must_change_password` 标记首登应改密（默认只标记不拦截）。首次启动无文件 → 自动创建默认管理员 `admin/admin123`（带改密标记）。SSO 接入后此文件整体替换。 |

#### 新建 `src/api/auth_routes.py` — 4 个端点

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/auth/login` | 读 JSON body `{username, password}` → `verify_password`（**放线程**跑，PBKDF2 是同步 CPU 活） → `sign_token` → `Set-Cookie: nl2sql_token=<token>; Path=/; SameSite=Lax; Max-Age=86400`（**P1-12：走 HTTPS 时才加 `Secure`**，`NL2SQL_COOKIE_SECURE` 可覆盖）→ `200 {user_id, display_name, is_admin, must_change_password}` / `401 {error}` |

#### ③ Sub-agent trace 的 user_id 透传

**现状**：`_build_langfuse_metadata()` 只设 `langfuse_session_id`、`langfuse_trace_name`、`langfuse_tags`，**不设 `langfuse_user_id`**。子 agent 的 trace 因此不带 user_id。

```python
def _build_langfuse_metadata(parent_tid, config):

    meta = {
        "langfuse_session_id": parent_tid,
        "langfuse_trace_name": "nl2sql-agent",
```

### B.4 user_id 在各 Langfuse 维度的最终效果

| 维度 | user_id 来源 | 效果 |
|---|---|---|
| **Trace** | `langfuse_metadata.py` 自动（P0 贯通） | Langfuse UI Sessions 页可按 User 过滤 |
| **Session** | 不变（仍 = thread_id） | session 与 thread 一一对应 |
| **Score** | `create_score()` metadata 增加 `user_id` | 可追溯"谁给的反馈"、"哪个用户的查询得了这个分" |
| **Dataset item** | metadata 增加 `annotator_id` / `collected_by` | 可追溯"谁标注的 badcase/goodcase" |
| **Sub-agent trace** | `deepagents_async_config_patch.py` 透传 | 子 agent trace 也归属到同一用户 |
| **Span** | `langfuse_span.py` OTel `user.id` 属性 | skill 级 span 可关联用户 |
| **Experiment** | worker config 透传 `initiator_user_id` | 实验 trace 归属发起人 |

### B.5 实施优先级

| 优先级 | 改动 | 原因 |
|---|---|---|
| **P0 同步** | ③ sub-agent 透传 + ④ span user.id | 与 P0 鉴权同步落地，零额外成本；不补则子 agent trace 仍匿名 |
| **P0 同步** | ① score metadata + ⑥ feedback store user_id 列 | 用户反馈是核心质量信号，必须从第一条反馈开始就有 user_id |
| **P1 联动** | ② dataset item annotator_id | 与 P1 库级授权联动（标注员可见性按 user_id 过滤） |
| **P1 联动** | ⑤ experiment user_id | 与 P1 实验权限联动（谁能发起实验） |
