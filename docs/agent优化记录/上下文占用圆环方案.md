# 上下文占用圆环方案（已实施）

NL2SQL 前端「上下文占用圆环」方案（2026-08-21 **已实施**）。对标 Claude Code 的上下文圆环，显示当前会话的上下文占用比例，并在接近上限时提醒用户手动压缩。

**目标**：圆环上显示上下文占比进度，鼠标悬停显示使用详情；位于界面中模型下拉框与发送按钮之间。

---

## 核心设计

### 分子：当前上下文占用

取 `tokenStats.steps` 末步的 `total_input_tokens`。原因：

在 LangGraph agent 循环中，每次 LLM 调用都把**完整的消息历史**作为输入（不是增量），所以末步的 `input_tokens` 就是当前上下文的总 token 数。

```
LLM 调用 1: input = [system, human_msg1]                           → 5000 tokens
LLM 调用 2: input = [system, human_msg1, AIMsg, ToolMsg]           → 8000 tokens  （含调用1全部）
LLM 调用 3: input = [system, human_msg1, AIMsg, ToolMsg, AIMsg, ToolMsg] → 12000 tokens （含调用1+2全部）
```

末步的 12000 就是完整上下文占用。这是 Claude Code 同款设计——Claude Code 也是取最近一次 API 调用的 `usage.input_tokens` 作为当前上下文占用。

**不能用累积的 `total_input_tokens`**——那是跨多轮累加值，每轮都重复计算了历史消息，会一直涨到远超窗口值。

### 分母：上下文窗口

三层优先级：

1. 用户在模型配置中显式设置的 `context_window`（`model_config.json` → API → 前端 `ModelInfo.context_window`）
2. `model.py` 的 `KNOWN_MODEL_CONTEXT_WINDOWS` 精确匹配（如 `deepseek-chat` → 128000）
3. `_FUZZY_WINDOW_PATTERNS` 模糊匹配（模型 ID 包含关键词，如含 `deepseek` → 128000）
4. 默认 `120000`（兜底）

后端 `create_model()` 中 `resolve_context_window()` 按同样优先级解析，设置 `ModelProfile(max_input_tokens=context_window)`，供 SummarizationMiddleware 计算压缩阈值。前端 `ContextRing` 通过 `/api/model-configs` 获取自动填充后的 `context_window`，与后端一致。

### 配色阈值

- <50%：蓝绿（安全）
- 50–80%：琥珀（警告）
- >80%：红色（危险）

### 子智能体 token 不纳入

圆环只监控**主智能体**的上下文占用。NL2SQL 子智能体是独立的 graph（`create_deep_agent` 单独创建），有自己独立的 state 和 messages，不会撑爆主智能体的上下文窗口。子智能体返回的结果（SQL 结果、分析文本）作为消息写回主智能体 state，这部分 token 已体现在主智能体下次 LLM 调用的输入中。圆环看主智能体就够了。

### 对标 Claude Code

| 方面 | Claude Code | NL2SQL |
|---|---|---|
| 分子 | 最近一次 API 调用的 `usage.input_tokens` | `steps` 末步的 `total_input_tokens` |
| 分母 | 模型上下文窗口 | 模型配置 → 已知模型表 → 120000 兜底 |
| 刷新时机 | 每次 API 调用完成后 | 每次 LLM 调用完成后（同为 agent 循环） |
| 压缩 | 无内置压缩（仅指示器） | v2 手动压缩 + v3 自动压缩 |
| 子 agent | 不适用（单 agent） | 子智能体不纳入（独立 graph） |

## v1 上下文圆环

纯 SVG 圆环，对标 Claude Code 的上下文圆环：

- 分子：`tokenStats.steps` 末步的 `total_input_tokens`
- 分母：通过 `/api/model-configs` 获取当前选中模型的 `context_window`（后端自动填充真实值），兜底默认 120000
- 配色：<50% 蓝绿 / 50-80% 琥珀 / >80% 红
- 悬停 tooltip 显示：百分比、token 数、步数、压缩提示
- 点击触发 v2 手动压缩（低于 50% 时 disabled）
- 压缩中显示 spinner 动画，完成后显示结果提示（3 秒自动消失）
- 仅统计主智能体 token，子智能体不纳入

## v2 手动压缩

用户点击圆环 → 前端 `POST /api/threads/{thread_id}/compact` → 后端自调用 langgraph API → LLM 生成摘要 → `RemoveMessage` 裁剪 state → 圆环刷新。

**后端** `src/api/thread_compact.py`：

- 自调用 `GET /threads/{tid}/state` 取 `values.messages`
- 按 keep 策略分割消息（保留最近 ~10% 上下文窗口，约 12000 tokens）
- 调用 LLM 生成摘要（`create_model(enable_thinking=False)` 节省成本）
- 写入 `RemoveMessage(REMOVE_ALL_MESSAGES)` + 摘要 + 保留消息
- fail-safe：任意步骤失败返回 502，不修改原始 state
- 少于 20 条消息自动跳过（无需压缩）

**前端** `ContextRing.tsx` 点击处理：

- 低于 50% 时点击无效果（tooltip 提示"上下文充足，无需压缩"）
- 压缩中显示 spinner 动画
- 压缩完成后圆环数值自然下降（旧消息被 RemoveMessage 裁剪 + 摘要替换）

## v3 自动压缩

`create_deep_agent`（deepagents v0.6.11）自动注入 `SummarizationMiddleware`，**无需代码改动**：

- 触发条件：`("fraction", 0.85)` — token 占用达到上下文窗口的 85% 时自动触发
- 保留策略：`("fraction", 0.10)` — 保留最近 10% 上下文窗口的消息
- 非侵入式：通过 `_summarization_event` 私有字段追踪，不修改 `state.messages`
- `ContextOverflowError` 兜底：自动 fallback 到 summarization 路径
- 运行时日志确认 `SummarizationMiddleware.awrap_model_call` 已激活

### v2 与 v3 的关系

互补而非互斥：

- **v3 自动**：在 85% 阈值自动触发，覆盖"用户没注意"的场景
- **v2 手动**：用户点击圆环主动触发，覆盖"用户想提前清理"的场景
- 两者可共存：手动压缩作为独立 API 端点，不依赖 SummarizationMiddleware；自动压缩作为中间件静默运行

## FAQ：悬停数值分子有时变大、有时变小（2026-08-26）

**问题**：前端圆环悬停显示的上下文占用，分子（`tokenStats.steps` 末步的 `total_input_tokens`）有时变大、有时变小，是 bug 吗？值还准吗？

**解答**：正常，不是 bug。分子是「主 agent 最近一次已完成的 LLM 调用实际发送的 input tokens」的**按步采样值**，模型真正看到的上下文是**可以变小**的。变大（历史累积）是常态；变小只发生在以下三个机制触发的时刻。

### 变小机制 1：MessageSlimmer 大结果落盘占位（最常见）

[message_slimmer.py](../src/agent/middlewares/message_slimmer.py) 把超过阈值（默认 8000 字符，环境变量 `LARGE_RESULT_TRUNCATE_CHARS` 可调；与 [langfuse_span.py](../src/agent/middlewares/langfuse_span.py) 的 span output 截断同源对齐）的工具结果替换为 head+tail 预览占位符（`/workspace/large_tool_results/...`）写回消息历史。因此：

- 拿到大结果的那一步：历史含完整结果 → input 大（如 60k）；
- 下一步：历史里该消息已是占位符 → input 变小（如 40k）。

这个变小是「忠实」的——下一条给模型的消息确实只有占位符，模型真的少看了那些内容。另附工具消息去重（`_dedup`）也会让历史变短。

### 变小机制 2：手动压缩

用户点击圆环 → [thread_compact.py](../src/api/thread_compact.py) 用 `RemoveMessage(REMOVE_ALL_MESSAGES)` + 摘要消息重写 `state.messages`，下一条 LLM 调用 input 骤降。这是设计意图，是压缩成功的直观证据。

### 变小机制 3：deepagents 85% 自动压缩（最大变小时刻）

`create_deep_agent` **默认注入** `SummarizationMiddleware`（`main_agent.py` 即使显式传 `middleware=[...]`，`create_deep_agent` 内部也会 `extend(create_summarization_middleware(...))`），消息计数达到模型 `max_input_tokens` 的 85% 时自动触发：

- 旧消息摘要化，落盘到 `conversation_history/{thread_id}.md`；
- **关键**：它直接改模型请求 `request.override(messages=摘要 + 保留尾部)`，**不重写 `state.messages`**（通过 `_summarization_event` 私有字段追踪，见 deepagents `SummarizationMiddleware.wrap_model_call`）；
- 因此下一条 LLM 调用的 input_tokens 降到约保留比例（~10% 窗口 + 尾部），但 state 里的完整消息日志仍保留（Langfuse trace / 前端消息记录不受影响）。

同阈值下还包含旧消息工具参数截断（`truncate_args_settings`：write_file/edit_file 的大参数被裁剪），进一步减小输入。

### 存储位置（2026-08-26 统一到前端选择的工作区）

两类压缩产物都落在**前端界面选择的工作区**（`_wm.active_workspace`，切换工作区即时生效）：

| 产物 | 落盘位置 | 机制 |
|---|---|---|
| 大工具结果全文 | `{active_workspace}/large_tool_results/{tool_call_id}` | MessageSlimmer 截断落盘（前缀 `/workspace/large_tool_results` 命中 CompositeBackend `/workspace/` 路由 → workspace_data_backend）；SummarizationMiddleware 溢出裁剪（`_clip_overflow_tail`）同路径 |
| 自动压缩被替换的旧消息 | `{active_workspace}/conversation_history/{thread_id}.md` | SummarizationMiddleware 通过 `CompositeBackend(artifacts_root="/workspace/")` 推导 `_history_path_prefix`（默认 `/` 会落到 `src/agent/`，故显式设 `artifacts_root="/workspace/"`） |
| 摘要本身 + cutoff | state 私有字段 `_summarization_event`（不入 `state.messages`） | 自动压缩 |
| 手动压缩摘要 | `state.messages` 内 HumanMessage（`lc_source="summarization"`）；旧消息不落盘，仅留 Langfuse trace 历史 | 手动压缩 |

改动文件：`main_agent.py` / `nl2sql_agent.py`（CompositeBackend 加 `artifacts_root="/workspace/"`）、`message_slimmer.py`（前缀改 `/workspace/large_tool_results` + 阈值读环境变量）、`langfuse_span.py`（阈值同源 + vfs 指针改 `/workspace/large_tool_results/...`）。

### 精度说明

- 分子是**按步采样**而非连续计量器：同一轮内主 agent 多次调模型时，随中间工具结果逐步变大；跨轮若无占位/压缩则持续变大。
- 「变小」只出现在占位 / 手动压缩 / 自动压缩 / 去重这几个时点，且变小量等于模型**真实少看到的量**——所以数值始终准确反映「下一条真正会发送的内容量」，用它判断「何时该手动压缩」是可靠的。
- 排查方法：在变小前后各查一次 `GET /threads/{tid}/state` 的 `values.token_stats.steps` 尾部两条，对比 `total_input_tokens` 与前后消息——通常能看到中间夹着被 `vfs://large_tool_results/` 占位的大工具消息，或触发自动压缩后紧跟的摘要消息。
