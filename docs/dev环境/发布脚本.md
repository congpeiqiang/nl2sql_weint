# dev 环境（192.168.25.34）— 发布脚本与更新手册

> 适用：dev 环境 192.168.25.34 ｜ 建立 2026-09-21
> 生产发布脚本是仓库根的 `scripts/release-backend.ps1` / `scripts/release-frontend.ps1`（面向 25.64），**两者不要混用**。
> 账号地址见同目录 [账号密码汇总.md](账号密码汇总.md)。

**可直接运行的脚本已落在同目录**。下表这些 `.ps1`/`.sh` 文件是**唯一权威实现**，本手册只讲原理、红线与坑，不再复制一份代码 —— 之前手册里贴的那份副本很快就和脚本不一致了（还留着一段会把 dev 的 `src/` 删半截的 `find -delete`），属于自找麻烦。

| 文件 | 作用 | 用法 |
|------|------|------|
| [dev-setup-ssh.ps1](dev-setup-ssh.ps1) | **一次性**：把本机 SSH key 装到 34，之后全程不问口令 | `.\dev-setup-ssh.ps1`（只问一次 34 口令） |
| [dev-release-backend.ps1](dev-release-backend.ps1) | §2 后端改代码 | `.\dev-release-backend.ps1` |
| [dev-release-frontend.ps1](dev-release-frontend.ps1) | §3 前端改动 | `.\dev-release-frontend.ps1` |
| [dev-swap-src.sh](dev-swap-src.sh) | 服务端助手：备份/换装/回滚 `src`（后端脚本每次自动送上去） | 不用手动跑；回滚时按 §6 用 |

**口令策略：每一处都最多问一次**（第一版是"每一步弹一次口令"，一次发布 30+ 次，已改掉）：

| 链路 | 认证方式 |
|------|----------|
| 本机 → 34 | SSH key（先跑一次 `dev-setup-ssh.ps1`）。脚本里所有 ssh/scp 都带 `-o BatchMode=yes`：**没配好 key 就立刻报错退出**，不会退回到弹口令 |
| 本机 → 64 | **本来就免密**（生产发版脚本也要求这个）。实测本机三把私钥里只有 `~/.ssh/id_ed25519` 能登 64（`id_rsa`、`id_rsa_nl2sql` 都不行，也登不上 34），别删它 |
| 34 → 64 | 只有前端脚本第 5 步（搬镜像）需要。脚本**先试 `BatchMode` 免密**，通了就完全不用口令；不通才用本机缓存的口令：首次问一次，之后不再问，缓存在 `$WorkDir\.pw64.cache`（不进仓库），`-ForgetPassword` 清除 |

## 0. 总览：四种场景

| 场景 | 何时用 | 代价 | 脚本 |
|------|--------|------|------|
| **A. 只改后端 Python 代码** | 日常 99%（改 prompt / 中间件 / API） | **秒级**，无镜像构建 | §2 |
| **B. 只改前端** | UI 有改动 | 本机构建 + 64 上建镜像 + 搬运 | §3 |
| **C. 后端依赖变了** | 改了 `pyproject.toml` / `uv.lock` | 同 B，且属**未验证路径** | §4 |
| **D. 让 dev 追平生产版本** | 想把生产那版原样搬到 dev 验证 | 纯搬运，不构建 | §5 |

**为什么和生产的脚本长得不一样**（三条硬约束，先看懂再动手）：

1. **dev 的 `/mydata/nl2sql/src` 是 bind 挂载到容器 `/app/src` 的** → 后端改代码**不需要重建镜像**，这也是 dev 存在的意义（改一行、重启 20 秒见效）。
2. **34 不能出外网** → 任何 `docker build`（要拉基础镜像 / `uv sync` / `yarn install`）在 34 上都跑不起来，镜像只能在别处造好再搬进来。
3. **本机（Windows）没有 docker** → 前端镜像本机也造不了；前端构建产物又依赖本机 DLP 解密，所以是「**本机 build 产物 → 64 上 build 镜像 → 搬进 34**」这条组合路径。

## 1. 一次性准备：到 34 的 SSH 免密

```powershell
cd D:\code_work_space\llm\nl2sql\docs\dev环境
.\dev-setup-ssh.ps1          # 只在这一步输一次 34 的口令
```

它做三件事：① 复用（没有才生成）`~/.ssh/id_ed25519`；② 把公钥**去重后**追加到 34 的 `~/.ssh/authorized_keys`；③ 用 `-o BatchMode=yes` 验证免密真的生效 —— 验证不过会明确报错，不会让你带着隐患往下走。幂等，重复跑没事。

**为什么非配不可**：一次后端发布有 30+ 次远程调用（打包/上传/换装/重启/轮询/查日志），没有 key 时**每一次都会单独弹一次口令**。轮询那 30 次就够受的了。

> **别指望连接复用（ControlMaster）**：本机 Git Bash 的 ssh 实测不支持 —— 主连接建不起来（`mm_send_fd: sendmsg(2): Broken pipe`、`mux_client_request_session: send fds failed`），复用更是无从谈起（scp 同样失败）。所以只有"装 key"这条路。
>
> 同一个 `id_ed25519` 也是本机唯一能登 64 的 key（见上表），一把钥匙两处用，别删、别重新生成。

> ⚠️ **提示符里没有环境名**，而且 dev 与生产**端口号完全相同**（8080 / 2026 / 3010）。跑命令前先 `hostname` 或 `ip a` 确认落在哪台机器上，别在生产上跑 dev 脚本。

## 2. 场景 A：只改后端代码（日常）

> 脚本文件：**[dev-release-backend.ps1](dev-release-backend.ps1)**（不传参直接跑；自带备份、包校验、失败回滚提示）

原理：本机 `src/` 打包 → 传到 34 → **在一次性 root 容器里**备份、校验、清空挂载目录并解包 → 重启容器。

五步各做了什么：

| 步 | 动作 | 要点 |
|---|------|------|
| 1 | 打包本机 `src/` | 排除清单见下 |
| 2 | 上传到 `${DevDir}/.tmp/` | 上传前先探连通性；`BatchMode`，失败立刻退出、不弹口令 |
| 3 | 备份 → 校验 → 清空 → 换装 | 交给服务端助手 `dev-swap-src.sh`，**在 root 容器里做**（原因见下） |
| 4 | `docker compose restart langgraph-api` | 不重建镜像（`src` 是 bind 挂载） |
| 5 | 轮询 `/ok`（最长 120s） | **一次 ssh、在服务端循环**，不是每 5 秒一次 ssh |

### 为什么第 3 步要绕一个容器（2026-09-21 的实际事故）

容器以 root 运行，会在挂载目录里写出 **root 属主的 `__pycache__/*.pyc`**；`weint` 删不掉这些文件。于是宿主机上那条 `find src -mindepth 1 -delete` 必然**中途**以 `Permission denied` 退出 —— 而它退出时 `src` 已经被删掉一半。实际后果：**278 个 `.py` 全没了**，只剩 123 个 root 属主的 `__pycache__` 目录，靠第 3 步的备份才恢复。

现在的做法：用**应用镜像起一次性 root 容器**做文件操作（不需要 sudo、不需要口令；注意应用镜像里**只有 `tar` 没有 `find`**），并且**先解到暂存区、校验哨兵文件通过，再清空真目录** —— 解包失败时线上 `src` 原封不动，不会再重演"半残"。

助手 `dev-swap-src.sh` 的四个模式（后端脚本每次会自动把它送到 `${DevDir}/.tmp/dev_swap_src.sh`）：

```bash
bash .tmp/dev_swap_src.sh check              # 只报告现状：.py 数 / 非 weint 属主文件数 / 容器内有无 tar
bash .tmp/dev_swap_src.sh backup <stamp>     # 备份到 .tmp/src-prev-<stamp>.tgz
bash .tmp/dev_swap_src.sh swap   <tar>       # 校验 → 清空 → 解包（tar 顶层必须含 src/）
bash .tmp/dev_swap_src.sh restore <备份tgz>  # 从备份恢复（回滚用，见 §6）
```

### 排除清单为什么是这些

- `__pycache__` / `*.pyc`：编译缓存。本地推上去没意义 —— 而且**服务器上那份是容器以 root 生成的**，正是上面事故的元凶。
- `agent/workspace` / `agent/workspace-temp`：仓库里的运行时残留（容器里 `AGENT_DATA_ROOT=/app/data`，不读这份）。
- `workspace_manager/workspaces.json`：**运行时工作区注册表**，跟着推上去会覆盖服务器上的注册表（09-08 事故）。
- `.tmp`：服务器临时目录。

（`tar` 同时写 `*/x` 和 `x` 两种形式，兼容不同 `tar` 的 glob 语义。）

> **注意**：`docker compose restart` 只重启容器、不换镜像 → 若你改的代码依赖新装的 Python 包，这条会静默失败（`ImportError` 写进日志）。这时走 §4。

> **它推的是本机工作树（含未提交改动）**：这正是 dev 的用途，但跑之前 `git status` 看一眼推的是什么（脚本也会打印 `未提交改动 N 项` 提醒）。

## 3. 场景 B：只改前端

> 脚本文件：**[dev-release-frontend.ps1](dev-release-frontend.ps1)**（`-SkipBuild` 复用现有 `.next`；`-SkipTransport` 用于镜像已在 34 上、只想换 tag 重启）

链路：**本机构建产物 → 传到 64 的独立构建目录 → 64 上 build 镜像 → 搬进 34 → 换 tag → 重启 frontend + nginx**。

七步：

| 步 | 动作 | 要点 |
|---|------|------|
| 1 | 本机 `yarn build` | **必须在本地**：UI 源码的 DLP 密文只有这台机器解得了 |
| 2 | 打包 `.next` `public` `package.json` `yarn.lock` | 不含 `node_modules`（`--exclude=.next/cache`） |
| 3 | 传到 64 的 `/home/weint/apps/nl2sql/dev-build/frontend/` | 先把该目录 `rm -rf` 重建；另传生产那份**明文** `next.config.ts` 与 `Dockerfile`（UI 源码里那两份是 DLP 密文，不能用于构建） |
| 4 | 64 上 `docker build -t nl2sql-dev-frontend:<ts>` | 输出重定向到 `/tmp/dev_fe_build.log` 再取退出码 —— `docker build \| tail` 之后 `$?` 恒为 `tail` 的 0，会掩盖失败（09-10 生产事故就这么报过"成功"） |
| 5 | 34 侧 `ssh 64 'docker save <img>' \| docker load` | 口令策略见下 |
| 6 | 存 rollback tag → 顶到 `:latest` → 重建 frontend → **重启 nginx** | ① 回滚只需一条 `docker tag`；② dev 的 compose 固定引用 `:latest`；③ nginx 启动时把上游主机名解析成 IP 并缓存，前端容器重建后 IP 变了，不重启 nginx 就是 502 |
| 7 | 等 12s → 验 `:8080`=200 → 比镜像 ID → 比 `BUILD_ID` | 镜像 ID 用 `docker inspect`：**容器看 `.Image`、镜像看 `.Id`**（都是完整 `sha256:`）。`docker images -q` 给的是短 ID，和 `.Image` 直接比会永远不等（假失败） |

### 第 5 步的口令：先试免密

```powershell
# 脚本内部逻辑（示意，实际以脚本为准）
$hopKey = ssh 34 "ssh -o BatchMode=yes weint@192.168.25.64 'echo HOP_OK'" -match HOP_OK
if ($hopKey) {  # 34→64 已有 key：直接 BatchMode 搬，连 askpass 都不建
} else {        # 否则：本机缓存的口令 → 写成 34 上的临时 askpass 助手（chmod 700，用完即删）
}
```

没有缓存时才交互式问一次，输入的口令会缓存在本机 `$WorkDir\.pw64.cache`（`icacls` 收紧到仅当前用户可读，**不进仓库、不进 transcript**），`-ForgetPassword` 清除。走口令分支时，口令写成 34 上的临时文件、由 `SSH_ASKPASS` 读，**不拼进任何 shell 引号里**（避免口令含 `$` `'` `"` 时的转义问题）；`chmod` 必须 700（600 会让 ssh 报 `askpass: exec(...): Permission denied`）。

> 想让这条路也零口令，就得给 34 装一把能登 64 的 key（即把 34 的公钥加进 64 的 `authorized_keys`）—— 那是在**生产 64** 上动 `~/.ssh`，超出"只写 `/home/weint/apps/nl2sql/`"的红线，别自作主张，先跟负责人确认。

另外两条红线：在 64 上**只写** `/home/weint/apps/nl2sql/dev-build/`，**只用** `nl2sql-dev-frontend:*` 这个 tag —— 打上 `nl2sql-app_frontend:latest` 会动到生产镜像、影响生产回滚。

## 4. 场景 C：后端依赖变了（改了 pyproject.toml / uv.lock）

> ⚠️ **这条路我还没跑过**（本次部署只搬了生产现成镜像）。首次使用请盯住构建日志，失败就按下面「兜底」退回。

原理与场景 B 同构，把「前端产物」换成「整个后端仓库」：

```powershell
# 步骤概览（按需要拼成脚本，与 §3 完全同构）
# 1) 本机打包后端（沿用生产脚本的排除清单，但**不要**排除 src，dev 也要它进镜像）：
#    tar -czf dev_backend.tar.gz --exclude=.venv --exclude=.git --exclude=logs `
#        --exclude=.langgraph_api --exclude=__pycache__ --exclude=docs `
#        --exclude=.env --exclude=.env.prod --exclude=src/agent/workspace `
#        --exclude=src/agent/workspace_manager/workspaces.json -C D:\code_work_space\llm\nl2sql .
# 2) 传 64 的独立目录 /home/weint/apps/nl2sql/dev-build/backend/（不碰生产的 backend/）
# 3) 64 上构建： docker build -t nl2sql-dev-backend:<ts> .      # 同样只用自己的 tag
# 4) 34 侧搬运： ssh 64 'docker save nl2sql-dev-backend:<ts>' | docker load
#    （34→64 的认证同 §3 第 5 步：先试 BatchMode 免密，不通再用本机缓存的口令）
# 5) 34 上换 tag 重建：
#    docker tag nl2sql-app_langgraph-api:latest nl2sql-app_langgraph-api:rollback-<ts>
#    docker tag nl2sql-dev-backend:<ts> nl2sql-app_langgraph-api:latest
#    cd /mydata/nl2sql/nl2sql-app && docker compose up -d --force-recreate langgraph-api
#    docker compose restart nginx          # 后端容器 IP 变了，nginx 必须重启
# 6) 验证同 §2 第 5 步
```

**兜底**：若 `docker build` 在 64 上失败（比如 Dockerfile 里引用了只有生产 compose 才提供的构建参数），退而求其次——**在 64 上把生产那版后端镜像搬过来**（场景 D），dev 与生产同版本；依赖差异带来的问题就不在 dev 复现了。

## 5. 场景 D：让 dev 追平生产版本（不构建，最稳）

用途：dev 想验证的正是生产那版行为；或者场景 B/C 构建失败时的兜底。**首次部署 dev 就是这么做的**（9 个镜像全部搬过来，已验证 `fail=0`）。

```powershell
# 从 34 上执行：逐个把 64 的镜像 save | load。64 上零落盘（docker save 走 stdout）。
# 34 需要一个临时 askpass（64 的密码），用完即删。
$IMGS = @(
  "docker.m.daocloud.io/nginx:alpine",
  "docker.m.daocloud.io/postgres:14",
  "docker.m.daocloud.io/redis:7",
  "docker.m.daocloud.io/minio/minio:RELEASE.2025-07-23T15-54-02Z",
  "clickhouse/clickhouse-server:25.12",
  "langfuse/langfuse:4",
  "langfuse/langfuse-worker:4",
  "nl2sql-app_langgraph-api:latest",   # 后端
  "nl2sql-app_frontend:latest"         # 前端
)
# 提示：日常追平版本通常只搬最后两个（应用镜像），中间件不需要动。
```

搬运脚本本体（在 34 上跑，`/mydata/nl2sql/.tmp` 里执行即可）：

```bash
#!/bin/bash
# 34 上：从 64 搬镜像。用法：bash pull_from_64.sh [镜像名...]
# ⚠️ 先替换下面 <64密码> 占位符为真实口令（生产中 weint 的登录口令）。
set -u
BASE=/mydata/nl2sql
printf '#!/bin/sh\necho "<64密码>"\n' > "$BASE/.tmp/.ask64.sh"; chmod 700 "$BASE/.tmp/.ask64.sh"
export SSH_ASKPASS="$BASE/.tmp/.ask64.sh" SSH_ASKPASS_REQUIRE=force
SSHOPTS="-o StrictHostKeyChecking=no -o NumberOfPasswordPrompts=1 -o PreferredAuthentications=password -o ConnectTimeout=10 -o ServerAliveInterval=20"

IMGS=("$@")
[ ${#IMGS[@]} -eq 0 ] && IMGS=("nl2sql-app_langgraph-api:latest" "nl2sql-app_frontend:latest")

fail=0
for img in "${IMGS[@]}"; do
  echo "[$(date +%H:%M:%S)] START $img"
  if ssh $SSHOPTS weint@192.168.25.64 "docker save '$img'" | docker load; then
    echo "[$(date +%H:%M:%S)] OK    $img"
  else
    echo "[$(date +%H:%M:%S)] FAIL  $img"; fail=1
  fi
done
rm -f "$BASE/.tmp/.ask64.sh"
echo "ALL_DONE fail=$fail"
```

搬完**必须重启对应容器**（镜像换了 tag 指向同一 `:latest` 时，容器不会自动换）：

```bash
cd /mydata/nl2sql/nl2sql-app
# 后端
docker compose up -d --force-recreate langgraph-api && docker compose restart nginx
# 前端
docker compose up -d --force-recreate frontend   && docker compose restart nginx
```

> 参照速度：首次搬 9 个镜像共 10.2GB，约 9 分钟（≈21MB/s）。

> 上面的 `SSH_ASKPASS` 那几行是**没有免密时**的写法。若 34→64 已经配了 key（前端脚本第 5 步会替你探一次），删掉 `printf`/`export` 两行、把 `ssh $SSHOPTS` 换成 `ssh -o BatchMode=yes …` 即可，全程零口令。
> 注意这段脚本要在 **34 上**创建并执行（`/mydata/nl2sql/.tmp/`），`<64密码>` 占位符**必须**替换成真实口令 —— 这里没有缓存机制兜着。
> 一次性搬十几个 GB 会占满一条局域网链路，别在生产高峰做。

## 6. 回滚

| 对象 | 回滚方式 |
|------|----------|
| 后端 src（场景 A） | 脚本第 3 步已把旧 src 备份成 `.tmp/src-prev-<时间戳>.tgz`，**脚本结尾也会原样打印这条命令**：<br>`ssh weint@192.168.25.34 "cd /mydata/nl2sql && bash .tmp/dev_swap_src.sh restore .tmp/src-prev-<时间戳>.tgz && cd nl2sql-app && docker compose restart langgraph-api"` |
| 前端镜像（场景 B） | `docker tag nl2sql-app_frontend:rollback-<ts> nl2sql-app_frontend:latest && docker compose up -d --force-recreate frontend && docker compose restart nginx` |
| 后端镜像（场景 C/D） | `docker tag nl2sql-app_langgraph-api:rollback-<ts> nl2sql-app_langgraph-api:latest && docker compose up -d --force-recreate langgraph-api && docker compose restart nginx` |

> ⚠️ 回滚后端 src **不要**图省事写 `find src -mindepth 1 -delete && tar -xzf ...`：容器写出的 `__pycache__/*.pyc` 是 root 属主，`weint` 删不掉，`find` 会在删到一半时以 `Permission denied` 退出，把线上 `src` 弄成半残（09-21 事故就是这么发生的）。`dev_swap_src.sh restore` 走的是同一条 root 容器路径，能删干净。
>
> 备份是**只增不删**的，攒多了自己清：`ls -lt /mydata/nl2sql/.tmp/src-prev-*.tgz`。

看现有可回滚的 tag：`docker images | grep -E "nl2sql-app_|nl2sql-dev-"`

> 注意：直接 `docker load` 生产镜像（场景 D）会**顶掉** `:latest`，旧的会变成 `<none>` 悬空镜像 —— 所以场景 D 之前也建议先 `docker tag ... rollback-<ts>` 留个名字。

## 7. 发布后验证清单

```bash
# ① 后端活着
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:2026/ok                 # 200
# ② 预检通过 + 工具数（改动涉及 MCP/语义库时必看）
cd /mydata/nl2sql/nl2sql-app && docker compose logs --tail=200 langgraph-api | grep -E "预检通过|预检失败"
# ③ MCP 注册表逐项 ok
curl -s http://127.0.0.1:2026/api/mcp/status | python3 -m json.tool | grep -E '"status"|"server"' 
# ④ 对外链路（经 nginx）
```

## 8. 红线与坑（都是踩过的）

**在 64 上**
1. 只做两件事：**只读盘点** + `docker save`（走 stdout，零落盘）。不改文件、不重启/不删容器、不动镜像。
2. 构建 dev 镜像时**必须用独立 tag**（`nl2sql-dev-*`）和**独立目录**（`/home/weint/apps/nl2sql/dev-build/`）。打上 `nl2sql-app_frontend:latest` 会动到生产镜像、影响生产回滚。
3. 需要新建文件时优先放 `/home/weint/apps/nl2sql/` 树内（`dev-build/`），不要往别处写。

**在 34 上**
4. 只写 `/mydata/nl2sql`；不删任何文件/镜像/容器；不碰别人的 k8s / Harbor / fastpg / mysql。
5. `/mydata/nl2sql/src` 是 bind 挂载点 → **只能清内容，不能删目录**。而且**别在宿主机上删**：容器以 root 运行，会往里面写 root 属主的 `__pycache__/*.pyc`，`weint` 删不掉 → `find src -mindepth 1 -delete` 会在删到一半时 `Permission denied` 退出（09-21 事故：278 个 `.py` 全没）。文件操作一律走 `dev-swap-src.sh`（一次性 root 容器）。
6. 34 无外网 → 一切需要联网的构建都跑不了，镜像只能搬进来。

**通用**
7. **tar 解压不删已删文件** → 替换代码前必须先清空目标目录（09-20 生产事故根因）。
8. **nginx 缓存上游 IP** → 后端/前端容器重建后必须 `docker compose restart nginx`，否则 502。
9. **模型是导入时解析的**：模型库为空时启动，子 agent 会落到框架默认的 Anthropic 模型，run 会以「error 字段为空」的方式失败。**先配模型、再重启后端**，然后才跑第一次问答。判断依据是启动日志里有没有 `[model] provider=... model=...`。
10. `docker compose`（v2 插件）唯一可用；`docker-compose` v1 在 docker 29 下会崩（`KeyError: 'ContainerConfig'`）。
11. dev 推的是**本机工作树（含未提交改动）** —— 这是 dev 的意义（先验证再发版），但要清楚每次推上去的是哪份代码：脚本会打印 `git: <分支> ｜ 未提交改动 N 项`，N>0 时另起一行提醒，跑之前扫一眼。
12. 生产与 dev 端口号相同（8080/2026/3010），**SSH 时先确认机器**。
13. **凡是 `.ps1`，只要内容里出现中文（含路径），就必须有 UTF-8 BOM**。Windows PowerShell 5.1 对没有 BOM 的 `.ps1` 按 GBK 解码：中文注释的字节会被"吃掉"后面一个字符，**连行尾换行都可能被吞**，于是下一行代码变成注释的一部分 —— 症状是某个变量莫名是空值（今天就踩了：`$DevDir` 赋值整行消失，拼出来的远端命令变成 `cd ;`）。仓库里生产的 `scripts/release-*.ps1` 也是带 BOM 的，保持一致。检查：`head -c 3 文件 | od -An -tx1` 应为 `ef bb bf`。
    这条**对临时小工具一样成立**：本次排查时我写的 AST 抽取脚本代码是纯 ASCII，但字符串里带着中文目录名（`docs\dev环境\...`），没 BOM → 中文路径被 GBK 解码后吃掉了后面的引号 → 文件数组字符串化 → 脚本"抽取出 0 条命令"，不报错、静默失败，白查两轮。给这类脚本加 BOM 最快的一条命令：`printf '\xef\xbb\xbf' > f2 && cat f >> f2 && mv f2 f`。
14. **不要在发布脚本上"为了让它跑起来"去掉 `-o BatchMode=yes`**。它存在的意义就是：没配好免密时**立刻报错**，而不是退回到每一步弹一次口令（一次发布 30+ 次）。看到这样的报错，正确反应是去跑 `dev-setup-ssh.ps1`，不是改脚本：
    ```
    连不上 weint@192.168.25.34（或 /mydata/nl2sql/src 不存在）。先跑一次 .\dev-setup-ssh.ps1 配好免密（只需一次口令）。
    ```
    唯一**必须**用口令交互的地方是 34→64 那一跳（`SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force`）—— 那里绝不能加 `BatchMode`，加了 askpass 就失效了。
15. **别用 ControlMaster 连接复用来省口令**：本机 Git Bash 的 ssh 实测不支持（`mm_send_fd: sendmsg(2): Broken pipe`、`mux_client_request_session: send fds failed`），主连接建不起来，后面的连接全部失败，包括 scp。只有装在 34 上的 key 这条路走得通。
