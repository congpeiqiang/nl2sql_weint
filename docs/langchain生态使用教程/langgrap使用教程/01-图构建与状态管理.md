## 1. 包结构与公共面

### 1.1 `langgraph/graph/__init__.py`

```python
from langgraph.constants import END, START
from langgraph.graph.message import MessageGraph, MessagesState, add_messages
from langgraph.graph.state import StateGraph

__all__ = (
    "END", "START", "StateGraph",
    "add_messages", "MessagesState", "MessageGraph",
)
```

`langgraph.graph` 包的公共面刻意收得很窄，只有 6 个符号：

| 符号 | 作用 |
|---|---|
| `StateGraph` | 图构建器（builder），一切图的入口 |
| `START` / `END` | 虚拟入口/终止节点常量 |
| `add_messages` | 消息列表 reducer |
| `MessagesState` | 预置的 `{"messages": ...}` 状态 Schema |
| `MessageGraph` | 已废弃（见第 4 章） |

注意 `BranchSpec`（`_branch.py`）、`StateNodeSpec`（`_node.py`）都带下划线前缀模块名——它们是**内部实现**，
不承诺 API 稳定性，但理解它们对读懂编译过程至关重要（第 6、7 章）。

### 1.2 `langgraph/constants.py`：START / END 的真身

```python
TAG_NOSTREAM = sys.intern("nostream")          # 给聊天模型打此 tag 可禁用流式
TAG_HIDDEN   = sys.intern("langsmith:hidden")  # 对 tracing/streaming 隐藏节点或边
END   = sys.intern("__end__")    # "The last (maybe virtual) node in graph-style Pregel."
START = sys.intern("__start__")  # "The first (maybe virtual) node in graph-style Pregel."
```

三个要点：

1. **`START` 就是字符串 `"__start__"`，`END` 就是 `"__end__"`**。它们用 `sys.intern` 驻留，全进程唯一。
   这解释了很多"魔法"：`add_edge(START, "a")` 本质是往 `edges` 集合里塞 `("__start__", "a")`；
   你在 trace 里看到 `as_node="__start__"` 也是在用同一个字符串（本仓库踩过的
   `update_state(as_node="__start__")` 幽灵 next 问题，根源就是它被当作真实节点名参与调度）。
2. **"maybe virtual"**：`START` 在编译后确实会物化成一个 `PregelNode`（负责把 invoke 输入分发进各 state
   通道，见 §7.3）；`END` 则**永远不是真节点**——它只是一个特殊通道名，写入它代表"该分支结束"。
3. 该模块还实现了 `__getattr__` 兜底：从 `langgraph.constants` 导入 `Send`/`Interrupt` 会收到弃用警告
   （1.0 起移到 `langgraph.types`），导入其它私有常量同样警告。**新代码一律
   `from langgraph.types import Send, Command, interrupt, RetryPolicy, CachePolicy`。**

## 2. StateGraph 核心 API 全景

`StateGraph`（`graph/state.py:130`）是一个**构建器（builder）**，本身不可执行；
`compile()` 之后得到 `CompiledStateGraph`（`Pregel` 的子类，即一个标准 `Runnable`）才能
`invoke / stream / batch / ainvoke`。

### 2.1 构造函数与内部数据结构

```python
class StateGraph(Generic[StateT, ContextT, InputT, OutputT]):
    edges: set[tuple[str, str]]                              # 普通有向边 (start, end)
    nodes: dict[str, StateNodeSpec[Any, ContextT]]           # 节点名 -> 节点规格
    branches: defaultdict[str, dict[str, BranchSpec]]        # 源节点 -> {分支名 -> 分支规格}
    channels: dict[str, BaseChannel]                         # state key -> 通道
    managed: dict[str, ManagedValueSpec]                     # 托管值（不进 checkpoint）
    schemas: dict[type[Any], dict[str, BaseChannel | ManagedValueSpec]]
    waiting_edges: set[tuple[tuple[str, ...], str]]            # 多起点 join 边
    compiled: bool

    def __init__(
        self,
        state_schema: type[StateT],                 # 必填：状态 Schema
        context_schema: type[ContextT] | None = None,  # 运行期只读上下文 Schema
        *,
        input_schema: type[InputT] | None = None,   # 缺省 = state_schema
        output_schema: type[OutputT] | None = None, # 缺省 = state_schema
        **kwargs,
    ) -> None:
```

源码解析：

- **四个 Schema 各司其职**：`state_schema` 定义节点间通信的完整状态；`input_schema` /
  `output_schema` 可以裁剪出对外暴露的输入/输出子集（例如内部状态有 10 个 key，
  对外只接受 `messages`、只输出 `answer`）；`context_schema` 描述 `Runtime.context`
  里**不可变的运行期依赖**（user_id、db_conn 等），通过 `invoke(..., context=...)` 传入。
- **`config_schema` 已废弃**（v0.6.0 起，构造函数里收到该 kwarg 会发
  `LangGraphDeprecatedSinceV10` 警告并转写为 `context_schema`）；`input=` / `output=`
  这两个旧参数名同理映射到 `input_schema` / `output_schema`。
- 构造函数末尾立刻执行三次 `_add_schema`：

```python
self._add_schema(self.state_schema)
self._add_schema(self.input_schema, allow_managed=False)
self._add_schema(self.output_schema, allow_managed=False)
```

  `allow_managed=False` 表示 **Input/Output Schema 里不允许出现托管值（ManagedValue）**，
  否则抛 `ValueError("Invalid managed channels detected in ...")`。

- **`set_node_defaults(...)`**（1.x 新增）：给全图节点设置默认 `retry_policy` /
  `cache_policy` / `error_handler` / `timeout`，在 `compile()` 时落地，
  **per-node 显式传入的值永远优先，且默认值不会被子图继承**。其中两条安全规则值得记住：
  错误处理器节点不享受 cache 默认值（缓存失败态结果不安全），也不会被挂上错误处理器
  （handler 不能捕获自己）。

### 2.2 Schema → 通道：`_add_schema` / `_get_channels` / `_get_channel`

StateGraph 的每个 state key 在编译期都会变成一个 **channel（通道）**。推断规则全在
`_get_channel`（`state.py:1836`）：

```python
def _get_channel(name, annotation, *, allow_managed=True):
    # ① 剥掉 Required / NotRequired 包装
    if hasattr(annotation, "__origin__") and annotation.__origin__ in (Required, NotRequired):
        annotation = annotation.__args__[0]
    # ② Annotated 元数据里是托管值？
    if manager := _is_field_managed_value(name, annotation): ...
    # ③ Annotated 元数据里直接是 BaseChannel 实例/子类？（如 EphemeralValue、DeltaChannel）
    elif channel := _is_field_channel(annotation): channel.key = name; return channel
    # ④ Annotated 元数据末尾是"恰好两个位置参数"的 callable？→ reducer
    elif channel := _is_field_binop(annotation): channel.key = name; return channel
    # ⑤ 兜底：LastValue（同 key 后写覆盖，一步只许一个写入者）
    fallback: LastValue = LastValue(annotation); fallback.key = name; return fallback
```

优先级：**托管值 > 显式 Channel 注解 > 二元 reducer 注解 > `LastValue` 兜底**。

`_is_field_binop` 对 reducer 的签名校验很严格：

```python
if sum(p.kind in (p.POSITIONAL_ONLY, p.POSITIONAL_OR_KEYWORD) for p in params) == 2:
    return BinaryOperatorAggregate(typ, meta[-1])
else:
    raise ValueError(f"Invalid reducer signature. Expected (a, b) -> c. Got {sig}")
```

即 **reducer 必须是 `(旧值, 新值) -> 合并值` 的两个位置参数函数**，多一个少一个都在建图时直接报错。

`_get_channels` 还处理一种退化情形：Schema 没有 `__annotations__`（比如直接传
`Annotated[list, add_messages]` 或一个裸类型），整个状态坍缩成单通道 `"__root__"`——
这就是 `MessageGraph` 的实现基础（§4），也是编译产物里 `output_channels == "__root__"`
特殊分支的来源。

**通道重名规则**（`_add_schema`）：同一 key 在多个 Schema 中出现时，若两边推断出的
channel 不相等——`LastValue` 静默让位（pass），其它情况抛
`ValueError("Channel '{key}' already exists with a different type")`。
典型触发方式：同一个 key 在父图和节点 `input_schema` 里一个带 reducer、一个不带。

### 2.3 `add_node`：四种重载与完整校验链

`add_node` 有 4 个 `@overload`（是否显式命名 × 是否显式 `input_schema`），实际实现一份
（`state.py:662`）。关键参数：

```python
def add_node(
    self,
    node: str | StateNode,          # 节点名，或直接传函数/Runnable（名字自动推断）
    action: StateNode | None = None,
    *,
    defer: bool = False,            # 延迟到本轮 run 即将结束时才执行
    metadata: dict | None = None,   # 节点元数据（进 trace / checkpoint）
    input_schema: type | None = None,  # 节点自己的输入 Schema（缺省用图 state_schema）
    retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
    cache_policy: CachePolicy | None = None,
    error_handler: StateNode | None = None,   # 节点级错误处理器
    destinations: dict[str, str] | tuple[str, ...] | None = None,  # 仅用于渲染
    timeout: float | timedelta | TimeoutPolicy | None = None,      # 仅 async 节点可真正取消
    **kwargs,
) -> Self:
```

实现里的完整校验链（按源码顺序）：

1. **名字推断**：不传字符串时，`Runnable` 取 `get_name()`，函数取 `__name__`，
   否则取类名；拿不到名字抛 `ValueError("Node name must be provided...")`。
2. **编译后追加只打日志警告**：`"Adding a node to a graph that has already been compiled.
   This will not be reflected in the compiled graph."` —— builder 和 compiled 是两份对象，
   compile 之后再改 builder 对已编译图**完全无效**（静默陷阱）。
3. **重名**：`ValueError("Node 'x' already present.")`。
4. **保留名**：`node == START or node == END` 抛 `ValueError("Node 'x' is reserved.")`。
5. **保留字符**：节点名不得含 `NS_SEP`（`"|"`）与 `NS_END`（`":"`）——这两个字符是
   checkpoint 命名空间/task 路径的分隔符（§9.4）。
6. **输入 Schema 推断**：若 action 是函数/方法，取其**第一个形参的类型注解**；
   注解是一个"有 type hints 的类型"时作为 `inferred_input_schema`。
   优先级：`input_schema 显式传入 > 首参注解推断 > 图的 state_schema`。
   ⚠️ 整段推断包在 `except (NameError, TypeError, StopIteration): pass` 里——
   **推断失败是静默的**。这与本仓库 memory 里"工具别加 `from __future__ import annotations`"
   是同一类坑：字符串化注解在这里可能解析失败，节点会静默退回整图 state_schema。
7. **`Command` 返回注解 → `ends`**：如果函数返回注解是 `Command[Literal["a", "b"]]`
   （或 Union 中含它），会把 `("a", "b")` 记为该节点的 `ends`。**这只影响图渲染与
   静态分支登记，不影响执行**——`destinations=` 参数同理（文档字符串里明确
   "only used for graph rendering"）。
8. **`error_handler`**：自动生成一个名为 `__error_handler__{node}` 的隐藏节点
   （`is_error_handler=True`），原节点失败时改跑它。

最终每个节点存成一个 `StateNodeSpec`（`graph/_node.py:84`）：

```python
@dataclass(slots=True)
class StateNodeSpec(Generic[NodeInputT, ContextT]):
    runnable: StateNode[NodeInputT, ContextT]   # coerce_to_runnable 包装后的可执行体
    metadata: dict[str, Any] | None
    input_schema: type[NodeInputT]
    retry_policy: RetryPolicy | Sequence[RetryPolicy] | None
    cache_policy: CachePolicy | None
    is_error_handler: bool = False
    error_handler_node: str | None = None
    ends: tuple[str, ...] | dict[str, str] | None = EMPTY_SEQ
    defer: bool = False
    timeout: TimeoutPolicy | None = None
```

`action` 会先经 `coerce_to_runnable(action, name=node, trace=False)` 包成
`RunnableCallable`——正是这个包装层在运行时**按函数签名的形参名**决定注入
`config` / `writer` / `store` / `runtime`（§5.1）。

### 2.4 `add_edge` / `add_sequence` / 三个便捷入口

```python
def add_edge(self, start_key: str | list[str], end_key: str) -> Self:
```

- **单起点**（`str`）：校验 `END` 不能当起点、`START` 不能当终点，然后
  `self.edges.add((start_key, end_key))`。普通边编译后的语义是
  "start 节点**每次**完成都触发 end 节点"。
- **多起点**（`list[str]`）：所有起点必须已 `add_node`，存进
  `self.waiting_edges.add((tuple(start_key), end_key))`。编译后生成
  `NamedBarrierValue` **join 通道**——`end_key` 要等列表里**所有**节点在本超步内都完成
  才触发（§7.3）。
- `add_sequence([a, b, c])`：语法糖，按顺序 `add_node` + `add_edge` 串起来；
  支持 `(name, node)` 元组显式命名（lambda 必须用元组，否则重名/无名）。
- `set_entry_point(key)` ≡ `add_edge(START, key)`；
  `set_finish_point(key)` ≡ `add_edge(key, END)`；
  `set_conditional_entry_point(path, path_map)` ≡ `add_conditional_edges(START, ...)`。

### 2.5 `add_conditional_edges`

```python
def add_conditional_edges(
    self,
    source: str,                       # 源节点：它每次执行完都会调用 path
    path: Callable | Runnable,         # 路由函数：返回目标节点名 / 名字序列 / Send
    path_map: dict[Hashable, str] | list[str] | None = None,
) -> Self:
    path = coerce_to_runnable(path, name=None, trace=True)
    name = path.name or "condition"
    if name in self.branches[source]:
        raise ValueError(f"Branch with name `{path.name}` already exists for node `{source}`")
    self.branches[source][name] = BranchSpec.from_path(path, path_map, True)
```

- 路由函数会被包成 Runnable 并**开启 trace**（`trace=True`，与节点的 `trace=False` 相反，
  所以条件函数在 LangSmith/Langfuse 里是一个独立可见的 span）。
- 同一源节点上分支按名字去重：具名函数重名会抛错；两个匿名 lambda 都叫
  `"condition"` 也会撞名——这就是有时要给路由函数起名字的原因。
- `path_map` 的三种形态与 `BranchSpec.from_path` 的推断逻辑见第 6 章。

### 2.6 `validate()`：编译前的静态检查

```python
def validate(self, interrupt=None) -> Self:
    # ① 所有边的 source 必须是已知节点或 START
    # ② 必须有入口：
    if START not in all_sources:
        raise ValueError("Graph must have an entrypoint: add at least one edge from START ...")
    # ③ 所有 target 必须是已知节点或 END；
    #    branch 没有 ends（path_map=None 且无 Literal 注解）时，
    #    保守地把「除 source 外的所有节点 + END」都算作可能 target
    # ④ interrupt_before/after 点名的节点必须存在
    self.compiled = True
```

两个易踩的点：

- **"Graph must have an entrypoint"** 是新手最常见报错——只 `add_node` 忘了
  `add_edge(START, ...)`。
- 分支没有 `ends` 时校验会放行一切目标，**代价是图渲染（`get_graph().draw_mermaid()`）
  会画出 source 到所有节点的边**。想要干净的渲染，给路由函数加
  `-> Literal["a", "b"]` 返回注解或传 `path_map`。

## 3. 状态定义的三种方式

### 3.1 方式一：TypedDict + Annotated + reducer（最常用）

```python
import operator
from typing import Annotated
from typing_extensions import TypedDict, NotRequired

class State(TypedDict):
    question: str                              # 无注解 → LastValue：后写覆盖
    steps: Annotated[list[str], operator.add]  # reducer → BinaryOperatorAggregate：追加合并
    retry_count: NotRequired[int]              # NotRequired 会被 _get_channel 剥掉再推断
```

- **不带 `Annotated` 的 key 是 `LastValue` 通道**：一个超步内只接受一次写入，
  多个并行节点同时写会抛 `InvalidUpdateError`。
- **带 reducer 的 key 是 `BinaryOperatorAggregate` 通道**：同一超步内多个写入按
  `reducer(reducer(旧值, 写入1), 写入2)` 依次折叠，天然支持并行扇入。
- reducer 必须是两个位置参数的 callable（§2.2 的签名校验）。
- 本项目 `MainAgentState` 的 `_merge_dict_by_key` 就是自定义 reducer 的生产级例子（§10.1）。

### 3.2 方式二：Pydantic BaseModel（或 dataclass）

```python
from pydantic import BaseModel

class State(BaseModel):
    x: int = 0
    history: Annotated[list[str], operator.add] = []
```

编译期 `_pick_mapper`（`state.py:1718`）决定了它与 TypedDict 的差别：

```python
def _pick_mapper(state_keys, schema):
    if state_keys == ["__root__"]:
        return None
    if isclass(schema) and (issubclass(schema, BaseModel) or is_dataclass(schema)):
        return partial(_coerce_state, schema)   # 节点收到的是模型实例
    return None                                  # TypedDict：节点收到普通 dict

def _coerce_state(schema, input: dict): return schema(**input)
```

即：**Pydantic/dataclass Schema 下，节点函数收到的第一个参数是被构造好的模型实例**
（内部通道存的仍是逐 key 的值，进节点前 `schema(**input)` 组装，节点返回的 dict 再逐 key
写回通道）。好处是字段校验和 IDE 补全；代价是每步多一次模型构造，且**返回更新时仍要返回
dict（或模型实例，`_get_updates` 里 `get_cached_annotated_keys` 分支也能处理）**，
不能返回 `State(x=...)` 期望"整体替换"——更新永远按 key 走通道。

`input_schema` / `output_schema` 是 Pydantic 模型时，`get_input_jsonschema()` /
`get_output_jsonschema()` 直接吐 `model_json_schema()`，这对 LangGraph Server 的
OpenAPI 面板很有用。

### 3.3 方式三：MessagesState + add_messages（对话图标配）

```python
from langgraph.graph import MessagesState, StateGraph, START, END

class State(MessagesState):        # 继承即可扩展
    db_name: str

builder = StateGraph(State)
```

`MessagesState` 本体只有两行（`graph/message.py:372`）：

```python
class MessagesState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```

`add_messages` 这个 reducer 的合并语义（`message.py:61`，逐条对应源码）：

1. **归一化**：左右两边都 `convert_to_messages`（接受 `"文本"`、`("assistant", "文本")`
   元组、dict、`BaseMessage`），`BaseMessageChunk` 转成正式 `BaseMessage`。
2. **补 ID**：没有 `id` 的消息补 `uuid4` —— 这是"同 ID 替换"语义的基础。
3. **同 ID 替换**：`right` 里的消息若与 `left` 中某条同 ID，**原位替换**而非追加。
4. **`RemoveMessage(id=...)`**：删除对应 ID 的消息；删不存在的 ID 抛 `ValueError`。
5. **`REMOVE_ALL_MESSAGES`**（`RemoveMessage(id="__remove_all__")`）：清空历史，
   只保留该标记**之后**的新消息（`return right[remove_all_idx + 1:]`）——上下文压缩就靠它。
6. **默认 append-only**：其余情况追加到尾部。
7. **可参数化**：`add_messages` 被 `_add_messages_wrapper` 包过——同时传 `left/right`
   是普通 reducer 调用；**都不传时返回 `partial`**，所以可以写
   `Annotated[list, add_messages(format="langchain-openai")]`，让合并结果自动格式化成
   OpenAI 消息形状（text/image_url block、ToolMessage 独立）。

另有实验性的 `_messages_delta_reducer`：配合 `DeltaChannel` 的批量 reducer，
一次处理整个 writes 列表（满足批次不变性 `reducer(reducer(s,xs),ys)==reducer(s,xs+ys)`），
用于增量快照场景，一般业务用不到。

### 3.4 三种方式对比

| 维度 | TypedDict + Annotated | Pydantic BaseModel | MessagesState |
|---|---|---|---|
| 节点收到的 state | 普通 `dict` | **模型实例**（`_coerce_state`） | 普通 `dict` |
| 类型校验 | 无（运行期不检查） | 构造时校验 | 无 |
| 扩展性 | 任意 key + 任意 reducer | 同左 | 本质就是预置了 `messages` key 的 TypedDict |
| JSON Schema | `TypeAdapter` 生成 | `model_json_schema()` 原生 | 同 TypedDict |
| 典型场景 | 工作流/流水线 | 强 Schema 校验、对外 API | 聊天/Agent 图 |
| 性能 | 最好 | 每步多一次模型构造 | 好（`add_messages` 线性合并） |

三者不互斥：实践中最常见的是 **继承 `MessagesState` 再补 TypedDict 字段**（本项目
`MainAgentState` 继承 deepagents 的 `DeepAgentState`，后者正是这种形态）。

## 4. MessageGraph：已废弃的历史与替代方案

`graph/message.py:312`：

```python
@deprecated("MessageGraph is deprecated in langgraph 1.0.0, to be removed in 2.0.0. "
            "Please use StateGraph with a `messages` key instead.", category=None)
class MessageGraph(StateGraph):
    def __init__(self) -> None:
        warnings.warn(...)   # LangGraphDeprecatedSinceV10
        super().__init__(Annotated[list[AnyMessage], add_messages])
```

**它的全部实现就一行**：把 `Annotated[list[AnyMessage], add_messages]` 当作
`state_schema` 传给 `StateGraph`。由于这个 Schema 没有 `__annotations__`，
`_get_channels` 走 `__root__` 分支——**整个图的状态就是一个消息列表**：

- 节点输入 = 完整消息列表；节点返回 = 若干消息（自动经 `add_messages` 并入）；
- `invoke([...])` 的返回值也是消息列表本身（`output_channels == "__root__"`）。

**适用场景**（历史上）：纯聊天链、无需在消息之外携带任何结构化状态的小图。
**为什么不推荐**：真实系统几乎总需要消息之外的 key（当前库名、todos、中间结果……），
`__root__` 形态没有扩展余地；1.0 起实例化即发弃用警告，2.0 将移除。
**替代方案**就是 §3.3 的 `MessagesState`——多打一个 `state["messages"]`，换来无限扩展性。

## 5. 节点函数签名与返回值形态

### 5.1 九种入参形态（`graph/_node.py`）

`_node.py` 用一组 `Protocol` 穷举了合法签名，并合成 `StateNode` 类型别名：

```python
class _Node(Protocol):            def __call__(self, state): ...
class _NodeWithConfig(Protocol):  def __call__(self, state, config: RunnableConfig): ...
class _NodeWithWriter(Protocol):  def __call__(self, state, *, writer: StreamWriter): ...
class _NodeWithStore(Protocol):   def __call__(self, state, *, store: BaseStore): ...
class _NodeWithConfigWriterStore(Protocol):
    def __call__(self, state, *, config, writer, store): ...
class _NodeWithRuntime(Protocol):
    def __call__(self, state, *, runtime: Runtime[ContextT]): ...

StateNode: TypeAlias = ( _Node | _NodeWithConfig | _NodeWithWriter | _NodeWithStore
    | _NodeWithWriterStore | _NodeWithConfigWriter | _NodeWithConfigStore
    | _NodeWithConfigWriterStore | _NodeWithRuntime | Runnable )
```

规律：

- **第一个位置参数永远是 state**（类型注解还参与 `input_schema` 推断，§2.3）。
- 其余依赖**按参数名注入**：`config`（RunnableConfig）、`writer`（自定义流写入器）、
  `store`（跨线程长期存储）、`runtime`（`Runtime` 对象，v0.6+ 推荐的统一入口）。
  注入由 `coerce_to_runnable` 产出的 `RunnableCallable` 在运行期做签名嗅探完成。
- 直接传一个 **`Runnable`**（包括编译好的子图、LCEL 链）也合法。
- 源码注释明说 `config`/`store` 形态未来可能被 `runtime` 收敛取代——**新代码优先
  `(state, *, runtime: Runtime[Ctx])` 签名**。
- ⚠️ 注入依赖真实的函数签名内省。本仓库 memory 记录过同类教训
  （`from __future__ import annotations` 会让 `ToolRuntime` 注入静默失效，判据
  `'runtime' in tool._injected_args_keys`）——节点侧同理，**别用 `**kwargs` 吞参数、
  别指望字符串化注解参与推断**。

### 5.2 返回值：dict / Command / Send / 列表

节点返回值如何变成状态写入，核心在 `attach_node` 内部的 `_get_updates`

四种合法返回形态总结：

| 返回 | 语义 |
|---|---|
| `None` | 不更新状态（但仍会走静态出边） |
| `dict`（部分 state） | 按 key 写入对应通道；**带 reducer 的 key 走合并，LastValue key 走覆盖**；schema 之外的 key 被静默过滤 |
| `Command(update=..., goto=...)` | 更新 + **动态跳转**（绕过静态边）；`goto` 可以是节点名、名字列表、`Send` 或 `Send` 列表；`graph=Command.PARENT` 时写给父图 |
| `Send(node, arg)` | 把 `arg`（**任意形状，不必是本图 state**）作为输入去派发 `node` 的一次执行——map-reduce 扇出的基础 |

返回其它类型（如裸字符串）会得到 `InvalidUpdateError`，错误码
`INVALID_GRAPH_NODE_RETURN_VALUE`。

`Command` 的字段（`langgraph/types.py:759`）：

```python
class Command(Generic[N]):
    graph: str | None = None   # None=当前图；Command.PARENT=最近的父图
    update: Any | None = None  # 状态更新（dict 等）
    resume: ... = None         # 配合 interrupt() 恢复执行的值
    goto: Send | Sequence[Send | N] | N = ()  # 下一跳
```

`Send` 的字段（`types.py:664`）：`node`（目标节点名）、`arg`（发给它的输入）、
`timeout`（本次派发的独立超时策略）。

### 5.3 `Runtime` 对象（`runtime.py`）


- `merge()`：父/子 runtime 合并，`other` 里非空的字段优先；`stream_writer`/`heartbeat`
  以"不是 no-op 默认值"为准。
- 全局取用：`get_runtime(context_schema)` = `get_config()[CONF][CONFIG_KEY_RUNTIME]`。

## 6. 条件边与路由：_branch.py 源码解析

### 6.1 `BranchSpec`

```python
class BranchSpec(NamedTuple):
    path: Runnable[Any, Hashable | list[Hashable]]   # 路由函数（已包装）
    ends: dict[Hashable, str] | None                 # 路由结果 → 节点名 的映射（可无）
    input_schema: type[Any] | None = None            # 路由函数首参注解推断出的 Schema
```

### 6.2 `from_path`：path_map 的三种来源

```python
@classmethod
def from_path(cls, path, path_map, infer_schema=False):
    path_map_ = None
    if isinstance(path_map, dict):      path_map_ = path_map.copy()      # ① 显式 dict
    elif isinstance(path_map, list):    path_map_ = {n: n for n in path_map}  # ② 显式 list（恒等映射）
    else:
        # ③ 推断：路由函数返回注解是 Literal["a","b"] → {"a":"a","b":"b"}
        func = path.func or path.afunc ...
        if rtn_type := get_type_hints(func).get("return"):
            if get_origin(rtn_type) is Literal:
                path_map_ = {name: name for name in get_args(rtn_type)}
    input_schema = _get_branch_path_input_schema(path) if infer_schema else None
    return cls(path=path, ends=path_map_, input_schema=input_schema)
```

- **`ends` 有值**：路由函数的返回值先查表映射成节点名，查不到直接 `KeyError`；
  渲染时只画这些边。`ends` 的值可以是 `END`（`"__end__"`），即"路由到结束"。
- **`ends` 为 None**：返回值被直接当节点名用（灵活但渲染退化为全连接，§2.6）。
- `_get_branch_path_input_schema` 与 `add_node` 同款逻辑：取路由函数**首参类型注解**
  作为分支自己的 input_schema（`add_conditional_edges` 传 `infer_schema=True`），
  这样路由函数可以只声明它关心的 state 子集。

### 6.3 `run()` 与 `attach_branch`：编译期接线

`BranchSpec.run(writer, reader)` 返回一个不追踪的 `RunnableCallable`
（`func=self._route, afunc=self._aroute`，闭包携带 `writer`/`reader`），并通过
`ChannelWrite.register_writer` 把 `ends` 的**静态写入项**（带 label）登记上去——供图渲染。

`CompiledStateGraph.attach_branch`（`state.py:1563`）在编译期做三件事：

```python
# ① 决定路由函数读哪些通道（branch 自己的 input_schema，否则用源节点的）
schema = branch.input_schema or self.builder.nodes[start].input_schema ...
channels = list(self.builder.schemas[schema])
# ② 造 reader：ChannelRead.do_read(select=channels, fresh=True, mapper=mapper)
#    fresh=True —— 路由函数读到的是「源节点本次写入合并后」的最新状态，而非节点入参快照
# ③ 把 branch 挂到源节点的 writers 尾部
self.nodes[start].writers.append(branch.run(get_writes, reader))
```

`get_writes` 把路由结果翻译成通道写入：字符串目标 `p` →
`ChannelWriteEntry("branch:to:{p}", None)`（`END` 保持原样），`Send` 对象原样透传
（后续由 Pregel 派发成任务）。

**所以"条件边"的执行本质**：源节点跑完 → 其 writers 链依次执行 → 轮到 branch writer 时
用 reader **新鲜读取**当前状态 → 调路由函数 → 把返回的目标写进对应 `branch:to:*` 通道
→ 下一超步这些通道触发目标节点。路由函数**在源节点的 task 内同步执行**，它不是独立节点
（但因为有 `trace=True`，在 trace 里是源节点下的一个子 span）。

### 6.4 `_route` / `_finish` 执行路径

```python
def _route(self, input, config, *, reader, writer):
    if reader:
        value = reader(config)                       # 新鲜读
        if isinstance(value, dict) and isinstance(input, dict) and self.input_schema is None:
            value = {**input, **value}               # 节点入参里的额外 key 透传给路由函数
    else:
        value = input
    result = self.path.invoke(value, config)
    return self._finish(writer, input, result, config)

def _finish(self, writer, input, result, config):
    if not isinstance(result, (list, tuple)): result = [result]   # 单值 → 单元素列表
    if self.ends:
        destinations = [r if isinstance(r, Send) else self.ends[r] for r in result]
    else:
        destinations = result
    if any(dest is None or dest == START for dest in destinations):
        raise ValueError("Branch did not return a valid destination")
    if any(p.node == END for p in destinations if isinstance(p, Send)):
        raise InvalidUpdateError("Cannot send a packet to the END node")
    entries = writer(destinations, False)
    ...  # 写通道（PASSTHROUGH 情形返回 ChannelWrite 延迟写，否则立即 do_write）
```

规则清单：

- **返回序列 = 并行扇出**：`return ["a", "b"]` 会同时触发 a、b 两个节点。
- 路由结果不能是 `None` 或 `START`；`Send` 不能发往 `END`。
- `Send` 直接混在返回值里合法（`[Send("worker", {...}), "finisher"]`）。
- `_aroute` 是 `_route` 的 async 镜像，路由函数可以是 `async def`。

### 6.5 条件入口

`set_conditional_entry_point(path, path_map)` = `add_conditional_edges(START, path, path_map)`。
`START` 作为 source 时，路由函数在输入写入后、任何节点执行前被调用——适合"按输入分流"
（例如本项目场景：按 `db_name` 是否建模分流到语义层/直连两条链路，就可以做成条件入口）。

### 7.1 签名与参数语义

**checkpointer 三态**（docstring 明确定义，子图行为的关键）：

| 值 | 语义 |
|---|---|
| 一个 `Checkpointer` 实例 | 用它做全版本化"短期记忆"：可暂停、恢复、重放 |

`thread_id` 是 checkpoint 的存取键，复用同一 ID 即跨调用累积状态（会话记忆）。

### 7.3 attach_node：节点如何变成 PregelNode


`START` 节点特殊：`PregelNode(tags=[TAG_HIDDEN], triggers=[START], channels=START, ...)`
——invoke 的输入写进 `START` 通道（`EphemeralValue(input_schema)`）触发它，它唯一的职责是
经 `_get_updates`/`_get_root` 把输入**分发到各 state 通道**，随后被静态出边接续。
`TAG_HIDDEN` 让它不出现在常规 trace/流事件里。

至此可以画出编译后的通道布局（这是理解 LangGraph 调度模型的钥匙）：

```
invoke(input)
   │ 写入
   ▼
[__start__ 通道] ──触发──> START 节点 ──写入各 state key 通道──┐
                                                              │
[a 节点完成] ──writer──> 写 branch:to:b（普通边）              │
[路由函数]   ──writer──> 写 branch:to:x / branch:to:y（条件边）│
[Command.goto="z"] ────> 写 branch:to:z（动态跳转）            │
[Send("w", arg)]  ────> 写 __pregel_tasks（派发 w，输入=arg）  │
[a,b 都完成] ──> 写 join:a+b:c 通道（NamedBarrierValue）──> 触发 c
                                                              │
某节点写入 END 通道 ──> 该分支终止；无待触发任务 ──> 整个 run 结束
```

**核心心智模型**：编译后没有"边"这种运行时对象——所有边都被降解为
"上游节点的 writer 往 `branch:to:{下游}` 通道写一个 `None`，下游节点以该通道为 trigger"。
节点 = `PregelNode`（触发通道 + 读取通道 + runnable + writers），这就是
"graph-style Pregel"的含义。

### 7.4 defer 节点与 AfterFinish 通道

`add_node(..., defer=True)` 的节点，其触发通道从 `EphemeralValue` 换成
`LastValueAfterFinish`，join 边从 `NamedBarrierValue` 换成 `NamedBarrierValueAfterFinish`
——语义是"**推迟到本轮 run 即将结束时执行**"，典型用途是收尾汇总、发通知类节点
（所有常规工作做完后跑一次，且只吃最后一次触发值）。

### 7.5 `_migrate_checkpoint`：checkpoint 布局迁移

`CompiledStateGraph._migrate_checkpoint`（`state.py:1612`）把旧版 checkpoint
（`v < 3`）里的通道布局迁移到新布局：`start:{node}` → `branch:to:{node}`、
`branch:{source}:{condition}:{node}` → `branch:to:{node}`、裸 `{node}` 版本键 →
`branch:to:{end}`。它同时迁移 `channel_values / channel_versions / versions_seen`
三张表。**工程含义**：升级 LangGraph 大版本后，线上旧 checkpoint 通常仍可续跑，
但这层迁移代码是唯一的兼容承诺——排障时若见 `versions_seen` 里出现老式键名，
说明迁移路径没走到。

## 8. UI 消息：ui.py

`graph/ui.py` 提供"生成式 UI"原语：节点内推送前端组件描述，并同步落进图状态。

```python
class UIMessage(TypedDict):
    type: Literal["ui"]; id: str; name: str          # 前端组件名
    props: dict[str, Any]; metadata: dict[str, Any]

class RemoveUIMessage(TypedDict):
    type: Literal["remove-ui"]; id: str
```

**`push_ui_message(name, props, *, id=None, metadata=None, message=None,
state_key="ui", merge=False)`** 的关键实现：

```python
writer = get_stream_writer()          # ① 实时流：custom stream 立刻可见
config = get_config()
evt = {"type": "ui", "id": id or str(uuid4()), "name": name, "props": props,
       "metadata": {"merge": merge, "run_id": ..., "tags": ..., **({"message_id": ...})}}
writer(evt)
if state_key:
    config[CONF][CONFIG_KEY_SEND]([(state_key, evt)])   # ② 状态：写进 state["ui"] 通道
```

即**双写**：既走流式（前端实时渲染），又经 `CONFIG_KEY_SEND`（`"__pregel_send"`，
Pregel 的内部写入泵）落到状态 key（默认 `"ui"`）——刷新页面/断线重连后可从 state 重建 UI。
`delete_ui_message(id)` 同构，发 `remove-ui` 事件。

配套 reducer：

```python
ui: Annotated[list[AnyUIMessage], ui_message_reducer]
```

`ui_message_reducer` 与 `add_messages` 同族：按 `id` 合并/替换/删除；特别地，
同 id 更新且 `metadata.merge=True` 时做 **props 浅合并**（`{**prev_props, **new_props}`），
适合"进度条只更新 percent 字段"这类增量渲染；删除不存在的 id 抛 `ValueError`。

`message.py` 里还有一个同族函数 **`push_message`**：手动向
`messages` / `messages-tuple` 流模式写一条聊天消息（要求显式 `id`），
同样双写（`StreamMessagesHandler._emit` + `CONFIG_KEY_SEND` 到 `state_key="messages"`）。

## 9. 子图嵌套

### 9.1 两种模式

| 模式 | 机制 | 状态 | 适用 |
|---|---|---|---|
| **进程内子图** | `parent.add_node("sub", sub_compiled)` | 与父图同进程、同一次 run，按共享 key 传递 | 模块化拆分、复用子流程 |
| **部署级子图** | 子图注册为独立 graph（`graph_id`），父图工具发起**独立 run** | 两个 run、两份 checkpoint（靠 configurable 透传关联） | 长任务、可取消、跨 worker |

进程内模式的原理很朴素：`CompiledStateGraph` 是 `Pregel` 是 `Runnable`，而
`add_node` 接受任何 `Runnable`（§5.1）——**编译好的子图就是一个普通节点**。

### 9.2 状态传递

- 父图把子图节点当普通节点接线：子图的 `input_channels` 是父图 state 中**与子图
  input_schema 同名的 key**；子图输出 dict 经父图的 `_get_updates` 按 key 写回，
  **走父图的 reducer**。共享 = key 同名；不共享的 key 两边互不可见。
- 子图内部是完整独立的 Pregel run：有自己的通道、自己的 reducer、自己的超步循环。
- 子图 `compile(checkpointer=None)` 时**继承父图 checkpointer**，其 checkpoint 存在
  父图 checkpoint 的命名空间下；`compile(checkpointer=False)` 可显式断开。

### 9.3 跨层通信：`Command(graph=Command.PARENT)`

子图节点返回 `Command(update={...}, goto="parent_node", graph=Command.PARENT)` 时：

- `_get_updates` 对 `graph == PARENT` 的 Command **返回 None**（不写子图自己的状态）；
- `_control_branch` **抛 `ParentCommand(command)` 异常**——这不是错误，而是控制流：
  异常向上传播到父图执行器，由父图应用 `update` 并执行 `goto`。

这是子图"直接指挥父图"的唯一正道（另一种是 `Send` 到父图节点，同样经 `ParentCommand` 上浮）。

### 9.4 命名空间

子图执行的 checkpoint 命名空间由 `NS_SEP = "|"` 拼接（形如
`父ns|子图节点名`），task 路径内部再用 `NS_END = ":"`。证据链：

- `add_node` 禁止节点名含 `|` 和 `:`（否则命名空间无法反解）；
- `push_message` 用 `metadata["langgraph_checkpoint_ns"].split(NS_SEP)` 还原命名空间层级；
- `ExecutionInfo.checkpoint_ns` 暴露给节点（§5.3），本项目可用它判断自己跑在哪层。

**实践含义**：观测面（Langfuse/平台库）里看到带 `|` 的 `checkpoint_ns` 就是子图/子任务的
执行；按 `|` 分段即可还原调用层级。

## 10. 项目实战分析

本项目没有手写 `StateGraph(...).add_node(...)`，而是用 **deepagents 的
`create_deep_agent`**——它内部仍是一个 `StateGraph`（model 节点 + tools 节点 +
中间件钩子），但把建图细节封装掉了。项目对 LangGraph 建图层的介入点集中在三处：
**自定义 state_schema、checkpointer 托管、子图（graph_id）编排**。逐一看。

### 10.1 `main_agent.py`：主智能体

**(1) 自定义状态 Schema —— 教科书级的 reducer 实战**

```python
def _merge_dict_by_key(existing: dict | None, update: dict) -> dict:
    """按 key 合并字典（与 deepagents._tasks_reducer 同语义）。"""
    merged = dict(existing or {})
    merged.update(update)
    return merged

class MainAgentState(DeepAgentState):
    todos: NotRequired[list]
    # ── 并发多查询：按 task_id 键控的合并字段 ──
    query_headers:      Annotated[NotRequired[dict[str, dict]],  _merge_dict_by_key]
    subagent_steps_map: Annotated[NotRequired[dict[str, list]],  _merge_dict_by_key]
    active_queries:     Annotated[NotRequired[dict[str, bool]],  _merge_dict_by_key]
    token_stats:        Annotated[NotRequired[dict], _accumulate_token_stats]
    answer_fingerprints: Annotated[NotRequired[dict[str, dict]], _merge_dict_by_key]
```

对照第 3 章源码逐点验证：

- `_merge_dict_by_key(existing, update)` 恰好两个位置参数——通过 `_is_field_binop`
  的签名校验，编译成 `BinaryOperatorAggregate` 通道；
- **为什么要 reducer**（源码注释写得很清楚）：并发多查询时多个 sync 线程各自
  `update_state` 写自己 `task_id` 的 key。若这些字段是 `LastValue`，一个超步内多写会
  `InvalidUpdateError` 或互相覆盖；挂了按 key 合并的 reducer 后各写各的槽位互不踩踏。
  这与本仓库 memory「async_tasks 写入丢失竞态」是同一问题的状态层解法。
- `NotRequired[...]` 包在 `Annotated` 内层——1.2.9 的 `_get_channel` 显式支持
  `Required/NotRequired` 剥离（`state.py:1840`），甚至 `Annotated[NotRequired[...], reducer]`
  这种嵌套也能正确推断（`_is_field_channel` 里专门 unwrap 了一层）。
- `token_stats` 用累积型 reducer `_accumulate_token_stats`（数值累加而非替换），
  支撑 TokenMeterMiddleware 的跨步累计。

**(2) checkpointer 托管给平台层**

```python
# 注意：checkpointer 不再在 graph 层设置，而是通过 LANGGRAPH_CHECKPOINTER 环境变量
# 在 langgraph_api 层配置。参见 checkpointer_factory.py 和 .env 文件。
```

即 `compile(checkpointer=None)` 的部署形态：langgraph server 平台在 run 期注入
checkpointer。文件里保留的 `SqliteSaver` 注释代码是纯 Python 本地跑的退路。
这正对应 §7.1 的三态语义——**图定义与持久化后端解耦**。

**(3) 子图 = 独立部署图，而非进程内嵌套**

```python
nl2sql_async = AsyncSubAgent(name="nl2sql", description="NL2SQL查询专家",
                             graph_id="nl2sql_agent")
```

主 agent 通过 `start_async_task` 工具对 `graph_id="nl2sql_agent"` 发起**独立 run**
（§9.1 右列模式），配套 `agent.middlewares.deepagents_async_config_patch` 把父 run 的
`configurable`（前端选库 `db_name` 等）透传给子 run——否则子图拿不到库名
（memory「主 agent→子 agent 透传 db_name/thread_id」）。好处：长查询可取消、
可并行、崩了不拖垮主图；代价：两份 checkpoint，状态同步要靠显式协议
（`sync_launcher` 把子图 todos 同步回 `MainAgentState.subagent_steps_map` 等字段，
而这些字段正因为跨 run 并发写入才必须挂 reducer——(1) 与 (3) 在这里闭环）。

**(4) 运行期配置读取**

```python
@dynamic_prompt
def dynamic_prompt(request: ModelRequest) -> str:
    from langgraph.config import get_config as _cfg
    db_name = (_cfg().get("configurable", {}) or {}).get("db_name", "") or ""
```

每次模型请求时经 `get_config()` 的 contextvar 拿最新 `configurable.db_name`，前置注入
系统提示词——`config.py` 在项目里的标准用法（state 存"数据"，configurable 存"运行期开关"）。

**(5) 编译产物再包装**

```python
agent = create_deep_agent(..., state_schema=MainAgentState).with_config({
    "recursion_limit": 500,
    "callbacks": get_langfuse_callbacks(),
})
```

`create_deep_agent` 返回的就是 `CompiledStateGraph`（Runnable），`with_config` 绑定
默认 config：递归上限 500（长任务多轮工具调用），Langfuse 回调全链路埋点。

### 10.2 `graphs/nl2sql_agent.py`：子图

- **独立建图**：另一个 `create_deep_agent(...)`，作为 `graph_id="nl2sql_agent"` 独立部署
  （langgraph.json 注册），工具白名单来自 `nl2sql.yaml`（`resolved_tools`），
  且把同一份白名单注册给运行期工具注册表（`set_sub_tool_filter`），防止动态 MCP 工具绕过过滤。
- **`Runtime` 实战**：

```python
@dynamic_prompt
def dynamic_prompt(request: ModelRequest) -> str:
    execution_info = getattr(request.runtime, 'execution_info', None)
    thread_id = getattr(execution_info, 'thread_id', '') if execution_info else ''
```

  这正是 §5.3 `Runtime.execution_info.thread_id` 的用法（注意它做了 `getattr` 防御——
  无 checkpointer 时 `thread_id` 为 None，`execution_info` 本身在 task 准备前也是 None）。
- **HITL interrupt**：`sql_approval_middleware` 对写/DDL 与疑似全表拉取触发
  `interrupt()`，前端弹审批卡（memory：审批检测必须读 `state.tasks[].interrupts`，
  因为 top-level graph 会抑制 interrupt 冒泡）。
- **中间件栈即"图行为的分层改写"**：20 个中间件的顺序注释本身就是一部
  LangGraph 执行模型应用史——例如 `wrap_tool_call` 链 first=outermost 决定后处理顺序
  （MessageSlimmer 在外层吃瘦身后的文本、LangfuseSpan 吃原始 payload），
  `after_model` 链 index 越大越先跑（CaliberGate 必须放 ProgressBoundary 之前=跑得更晚）。
  中间件最终都被 deepagents 翻译成 StateGraph 的节点/wrap 逻辑。

### 10.3 项目做法 vs 原生做法对照

| 关注点 | 原生 StateGraph 写法 | 本项目写法 |
|---|---|---|
| 建图 | `StateGraph(State).add_node(...).add_edge(...)` | `create_deep_agent(...)`（内部建图） |
| 状态扩展 | TypedDict + Annotated reducer | `MainAgentState(DeepAgentState)` + `_merge_dict_by_key`（同款机制） |
| 路由 | `add_conditional_edges` + 路由函数 | 提示词 + 中间件软闸（QueryGate/CubeRouteGate）+ 模型自主 tool call |
| 子图 | `add_node("sub", sub.compile())` | `AsyncSubAgent(graph_id=...)` 独立 run + configurable 透传 |
| checkpointer | `compile(checkpointer=saver)` | 平台层 `LANGGRAPH_CHECKPOINTER` 注入 |
| HITL | `interrupt_before=[...]` / `interrupt()` | SQL 审批中间件内 `interrupt()` |
| 运行期配置 | `context_schema` + `Runtime.context` | `configurable` + `get_config()`（历史路线） |

## 11. 完整代码示例

### 示例 1：简单链式（TypedDict + add_sequence）

```python
"""场景：抽取 → 分析 → 撰写 三步流水线，无分支。"""
import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class ArticleState(TypedDict):
    topic: str                                # LastValue：输入一次，之后只读
    outline: str                              # LastValue：analyze 覆盖写入
    draft: str
    log: Annotated[list[str], operator.add]   # reducer：每步追加，并行安全

def extract(state: ArticleState) -> dict:
    # 返回「部分 state dict」即可；未提及的 key 不动
    return {"outline": f"大纲({state['topic']}): 1.背景 2.方法 3.结论",
            "log": ["extract done"]}          # log 挂 operator.add → 追加而非覆盖

def analyze(state: ArticleState) -> dict:
    return {"log": [f"analyze: 基于 {len(state['outline'])} 字大纲"]}

def write(state: ArticleState) -> dict:
    return {"draft": f"《{state['topic']}》正文……", "log": ["write done"]}

builder = StateGraph(ArticleState)
# add_sequence 自动按序 add_node + add_edge（名字取函数 __name__）
builder.add_sequence([extract, analyze, write])
builder.add_edge(START, "extract")   # 入口仍要显式接 START（否则 validate 报错）
builder.add_edge("write", END)       # 显式收尾（不接 END 也可以：无出边即自然终止）

graph = builder.compile(name="article-pipeline")
print(graph.invoke({"topic": "LangGraph  internals", "log": []}))
# {'topic': ..., 'outline': ..., 'draft': ..., 'log': ['extract done', 'analyze: ...', 'write done']}
```

要点：`add_sequence` 只负责节点间串联，**START 入口必须自己接**；`log` 演示 reducer
合并，`outline` 演示 LastValue 覆盖。

### 示例 2：条件分支（path_map 与 Literal 注解两种写法）

```python
"""场景：按输入数值分流到三条处理链，其中一条直接结束。"""
from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class S(TypedDict):
    score: int
    result: str

def classify(state: S) -> Literal["high", "low", "__end__"]:
    # 返回注解写成 Literal —— BranchSpec.from_path 会自动推断 path_map（§6.2 来源③），
    # 图渲染也只画这三条边。返回 "__end__"（即 END）表示直接终止。
    if state["score"] >= 90: return "high"
    if state["score"] < 60:  return "__end__"
    return "low"

builder = StateGraph(S)
builder.add_node("high", lambda s: {"result": "优秀"})
builder.add_node("low",  lambda s: {"result": "待改进"})

# 写法 A：靠 Literal 注解（推荐，类型检查器还能校验返回值）
builder.add_conditional_edges(START, classify)

# 写法 B：显式 path_map —— 路由函数返回「业务标签」，映射到节点名
# builder.add_conditional_edges(START, classify,
#     path_map={"high": "high", "low": "low", "__end__": END})

builder.add_edge("high", END)
builder.add_edge("low", END)
graph = builder.compile()

print(graph.invoke({"score": 95}))   # {'score': 95, 'result': '优秀'}
print(graph.invoke({"score": 10}))   # {'score': 10}  ← 路由到 END，没有节点执行
```

要点：条件边挂在 `START` 上即"条件入口"；路由函数**不修改状态**，只返回目的地；
返回值不在 `path_map`/Literal 集合内会直接 `KeyError`（fail-fast，好事）。

### 示例 3：多路由并行（Send 扇出 map-reduce + join 边扇入）

```python
"""场景：把主题列表并行分发给 joke 生成器（map），全部完成后汇总（reduce）。
演示 Send 派发 + add_edge(list, ...) 的 NamedBarrierValue join。"""
import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class Overall(TypedDict):
    subjects: list[str]
    jokes: Annotated[list[str], operator.add]   # 并行写入靠 reducer 合并（LastValue 会炸）
    summary: str

class JokeInput(TypedDict):        # Send 的载荷可以是「与主图不同的形状」（§5.2）
    subject: str

def fan_out(state: Overall) -> list[Send]:
    # 路由函数返回 Send 列表 → 每个 Send 派发 generate 的一次独立执行，输入是 arg
    return [Send("generate", {"subject": s}) for s in state["subjects"]]

def generate(state: JokeInput) -> dict:
    # 注意入参是 Send 的 arg，不是主图 state；返回的 key 仍按主图通道写回
    return {"jokes": [f"关于{state['subject']}的笑话"]}

def summarize(state: Overall) -> dict:
    return {"summary": f"共 {len(state['jokes'])} 条"}

builder = StateGraph(Overall)
builder.add_node("generate", generate)          # input_schema 自动推断为 JokeInput
builder.add_node("summarize", summarize)
builder.add_conditional_edges(START, fan_out, ["generate"])  # list 形 path_map 仅供渲染
# join 边（waiting_edges → NamedBarrierValue）：语义是「generate 的全部并行实例
# 都完成后才触发 summarize」。若写成 add_edge("generate", "summarize")，
# summarize 会被每个实例各触发一次。
builder.add_edge(["generate"], "summarize")
builder.add_edge("summarize", END)
graph = builder.compile()

print(graph.invoke({"subjects": ["猫", "SQL", "LangGraph"], "jokes": []}))
# jokes 三条并行生成后经 operator.add 合并，summary = '共 3 条'
```

要点：`Send` 实现"同一节点 N 份并行、各带私有输入"；并行扇入必须靠
**reducer 通道 + join 边**两件套；`Send` 的 `arg` 形状自由，目标节点的
`input_schema` 会被自动推断（§2.3 第 6 步）。

### 示例 4：子图嵌套 + Command.PARENT 跨层跳转

```python
"""场景：父图负责会话，子图负责「查数据」子流程；
子图节点直接更新父图状态并指挥父图跳转。"""
import operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command

# ---------- 子图 ----------
class SubState(TypedDict):
    query: str                                  # 与父图共享（同名 key）
    rows: int                                   # 子图私有：父图没有这个 key，互不可见
    log: Annotated[list[str], operator.add]     # 与父图共享且同 reducer

def run_sql(state: SubState) -> Command[Literal["reply"]]:
    # graph=Command.PARENT：update 写进父图、goto 跳父图的 "reply" 节点。
    # 子图内 _get_updates 对 PARENT Command 返回 None（不写子图），
    # _control_branch 抛 ParentCommand 上浮给父图执行器（§9.3）。
    return Command(
        update={"log": [f"executed: {state['query']}, rows={state['rows'] + 100}"]},
        goto="reply",
        graph=Command.PARENT,
    )

sub = StateGraph(SubState)
sub.add_node("run_sql", run_sql)
sub.add_edge(START, "run_sql")
sub_compiled = sub.compile()          # checkpointer=None：作为子图时自动继承父图的

# ---------- 父图 ----------
class ParentState(TypedDict):
    query: str
    answer: str
    log: Annotated[list[str], operator.add]

def route(state: ParentState) -> Literal["db_sub", "reply"]:
    return "db_sub" if state["query"].strip().lower().startswith("select") else "reply"

def reply(state: ParentState) -> dict:
    return {"answer": f"已完成：{state['query']}；日志 {len(state['log'])} 条"}

parent = StateGraph(ParentState)
parent.add_node("db_sub", sub_compiled)     # 编译好的子图 = 一个 Runnable 节点（§9.1）
parent.add_node("reply", reply)
parent.add_conditional_edges(START, route)
parent.add_edge("reply", END)
graph = parent.compile()

out = graph.invoke({"query": "SELECT 1", "answer": "", "log": []})
# 执行路径：route → db_sub(子图 run_sql) → ParentCommand → 父图 reply → END
print(out)
```

要点：状态共享 = **同名 key 交集**（`query`/`log` 互通，`rows`/`answer` 各自私有）；
子图写回父图时走**父图的 reducer**（`log` 追加）；`Command(graph=Command.PARENT)`
是唯一"子图指挥父图"的正道；子图 checkpoint 命名空间以 `|` 拼接（§9.4）。

### 示例 5（加餐）：MessagesState 对话图 + 消息删除

```python
"""场景：最小聊天图；演示 add_messages 的同 ID 替换与 RemoveMessage。"""
from typing import Annotated
from langchain_core.messages import AIMessage, RemoveMessage
from langgraph.graph import StateGraph, MessagesState, START, END

class State(MessagesState):            # 继承预置的 messages: Annotated[list, add_messages]
    turn: int                          # 扩展字段：LastValue

def chat(state: State) -> dict:
    last = state["messages"][-1].content
    update = {"turn": state.get("turn", 0) + 1}
    if last == "重写":
        # 同 ID 返回 → 原位替换上一条 AI 回复（add_messages 语义③），而非追加
        prev_id = state["messages"][-1].id
        update["messages"] = [AIMessage(content="（重写后的回答）", id=prev_id)]
    elif last == "清空":
        # RemoveMessage 删除指定 ID（语义④）；也可用 REMOVE_ALL_MESSAGES 全清
        update["messages"] = [RemoveMessage(id=m.id) for m in state["messages"][:-1]]
    else:
        update["messages"] = [AIMessage(content=f"echo: {last}")]  # 无 ID → 自动补 uuid4
    return update

builder = StateGraph(State)
builder.add_node("chat", chat)
builder.add_edge(START, "chat")
builder.add_edge("chat", END)
graph = builder.compile()

s = graph.invoke({"messages": [("user", "你好")]})
print(s["messages"], s["turn"])
# [HumanMessage('你好'), AIMessage('echo: 你好')] 1
```

## 12. 常见错误与最佳实践清单

**建图期（fail-fast，报错清晰）**

| 报错 | 原因 | 出处 |
|---|---|---|
| `Graph must have an entrypoint` | 没有 `add_edge(START, ...)` | `validate()` |
| `Node 'x' is reserved.` | 节点起名 `__start__`/`__end__` | `add_node` |
| `'\|' is a reserved character` | 节点名含命名空间分隔符 | `add_node` |
| `Invalid reducer signature. Expected (a, b) -> c` | reducer 位置参数不是恰好 2 个 | `_is_field_binop` |
| `Channel 'k' already exists with a different type` | 同 key 在多 Schema 中一个带 reducer 一个不带 | `_add_schema` |
| `Branch with name 'x' already exists` | 同源节点两个同名路由函数 | `add_conditional_edges` |
| `Managed channels not permitted in Input/Output schema` | input/output_schema 里有托管值 | `_add_schema(allow_managed=False)` |

**运行期（更容易静默或难查）**

1. **compile 后改 builder 无效**：只有日志警告，不抛错。改图必须重新 `compile()`。
2. **并行写 LastValue 通道** → `InvalidUpdateError`。凡可能被并行节点/多写者触碰的 key，
   一律挂 reducer（本项目 `_merge_dict_by_key` 的存在理由）。
3. **节点返回非 dict/Command/Send** → `InvalidUpdateError`（错误码
   `INVALID_GRAPH_NODE_RETURN_VALUE`）；返回 dict 里**混入 schema 之外的 key 会被静默丢弃**
   ——拼错 key 不报错，是最阴的坑。
4. **路由函数返回值不在 path_map** → `KeyError`；返回 `None`/`START` → `ValueError`。
5. **`get_config()`/`get_store()`/`get_stream_writer()` 只能在 runnable 上下文内调用**；
   Python < 3.11 的 async 下不可用（contextvar 传播限制）。
6. **`from __future__ import annotations` 破坏签名推断**：`add_node` 的 input_schema
   推断和依赖注入都靠真实类型对象，字符串化注解可能静默失败（`except NameError: pass`）。
7. **checkpointer 启用后必须传 `thread_id`**；子图想独立于父图持久化，
   显式 `compile(checkpointer=False)`。
8. **图渲染失真**：条件边既无 `path_map` 也无 `Literal` 返回注解时，渲染会画出
   source → 所有节点的边。给路由函数补返回注解是一行成本的修复。
9. **`timeout` 只对 async 节点生效**（同步节点无法安全取消，docstring 明说）；
   需要"可续命"的超时用 `TimeoutPolicy(idle_timeout=..., refresh_on="heartbeat")`
   配合 `runtime.heartbeat()`。
10. **升级大版本后旧 checkpoint**：`_migrate_checkpoint` 负责 `v<3` 布局迁移，
    但跨大版本升级前仍建议备份 checkpoint 存储（本项目经验：判断线上行为
    永远以运行期证据为准，别信"应该兼容"）。

**设计准则（从本项目沉淀）**

- **state 存数据、configurable 存运行期开关、context 存不可变依赖**——三通道别混。
  本项目 `db_name` 走 configurable + `dynamic_prompt` 注入，就是为了让"切库"
  不必污染会话状态。
- **子流程能独立 run 就独立 run**（AsyncSubAgent 模式）：可取消、可并行、故障隔离；
  进程内子图留给"必须共享超步语义"的紧耦合场景。
- **并发写入的每个 key 都要有明确的合并策略**（reducer），并把策略写成命名函数 +
  注释（`_merge_dict_by_key` 的 docstring 直接引用了 deepagents 同语义函数）。
- **中间件/节点的顺序就是语义**：wrap 链 first=outermost、after_model index 大者先跑——
  调序前先在源码里确认遍历方向（nl2sql_agent.py 里每条顺序注释都是事故换来的）。
