## 1. 函数式图概述：与声明式 StateGraph 的对比

LangGraph 提供两种构建工作流的编程模型：

| 维度 | 声明式 `StateGraph` | 函数式 `@entrypoint` / `@task` |
|------|--------------------|-------------------------------|
| 定义方式 | 显式声明状态 schema、`add_node` / `add_edge` / `add_conditional_edges`，再 `compile()` | 直接写普通 Python 函数，控制流就是原生 `if/for/while`、函数调用 |
| 状态管理 | 图状态（TypedDict/Pydantic/dataclass）+ reducer 合并 | 无显式图状态；`previous` 参数拿到上一轮返回值，`entrypoint.final(value, save)` 分离「返回」与「存档」 |
| 并行 | 同一 superstep 内多节点自动并行；`Send` 动态扇出 | 调用 `@task` 立即返回 future，先发后收即并行 |
| 路由 | 条件边 / `Command(goto=...)` | 原生 Python 分支语句 |
| 可视化 | `get_graph()` 可画出完整拓扑 | 只有一个节点（函数名），拓扑信息在代码里，画不出内部分支 |
| 中断恢复 | `interrupt()` + `Command(resume=...)` | 完全相同（两者共用同一套 Pregel 运行时） |
| 持久化 | checkpointer 按 superstep 落盘 | 相同；`@task` 的输入输出也会被记录，resume 时**已完成 task 不重跑** |

**适用场景**：

- **函数式 API 适合**：控制流本身就用代码表达更自然的场景——顺序流水线、循环重试、动态决定调用哪些子步骤、把「一次 LLM 调用 + 几个工具调用」封装成单个可持久化函数；以及从普通 Python 代码渐进迁移到 LangGraph（先包一层 `@entrypoint` 获得持久化/HITL，再逐步拆 `@task`）。
- **StateGraph 适合**：需要显式拓扑、可视化、多 agent 协作、按节点粒度设置 `interrupt_before/after`、被其他图作为子图复用、或需要精细的通道级状态合并（reducer）的场景。

**关键事实：函数式 API 并不是另一套运行时。** 阅读 `func/__init__.py` 可以看到，`@entrypoint` 装饰后的产物就是一个标准 `Pregel` 图（见第 2 节源码解析），只是自动帮你生成了「单节点 + START/END/PREVIOUS 三通道」的拓扑。因此 checkpointer、`interrupt`、`Command(resume)`、流式（`stream`/`astream`）、`get_state` 等能力两者完全一致。

`typing.py` 定义了贯穿两种模型的类型变量（1.2.9 全文只有 48 行）：

```python
StateT = TypeVar("StateT", bound=StateLike)          # 图状态
StateT_co = TypeVar("StateT_co", bound=StateLike, covariant=True)
StateT_contra = TypeVar("StateT_contra", bound=StateLike, contravariant=True)
ContextT = TypeVar("ContextT", bound=StateLike | None, default=None)  # 运行期上下文，默认 None
InputT = TypeVar("InputT", bound=StateLike, default=StateT)           # StateGraph 输入
OutputT = TypeVar("OutputT", bound=StateLike, default=StateT)         # StateGraph 输出
NodeInputT = TypeVar("NodeInputT", bound=StateLike)                   # 节点输入
```

解析：`InputT`/`OutputT` 的 `default=StateT` 意味着「输入/输出 schema 未显式指定时等于状态 schema」；`ContextT` 默认 `None`，对应 `entrypoint(context_schema=...)` 注入的只读运行上下文（通过 `runtime.context` 访问）。`_co`/`_contra` 后缀是为泛型协议准备的协变/逆变版本，日常使用无需关心。

## 2. @entrypoint 装饰器

### 2.1 为什么 `entrypoint` 是一个类而不是函数

`func/__init__.py` 中有一段注释直接说明了设计动机：

```python
# The decorator was wrapped in a class to support the `final` attribute.
# In this form, the `final` attribute should play nicely with IDE autocompletion,
# and type checking tools.
# In addition, we'll be able to surface this information in the API Reference.
class entrypoint(Generic[ContextT]):
    ...
```

解析：把装饰器做成类，就能在 `entrypoint` 这个「命名空间」上挂 `entrypoint.final` 数据类（见 2.4），同时让 IDE 补全和类型检查器都能识别。这带来一个**使用上的硬性约束**：

> ⚠️ **`@entrypoint` 必须带括号使用**（`@entrypoint()` 或 `@entrypoint(checkpointer=...)`）。裸写 `@entrypoint` 会把你的函数当作 `__init__` 的第一个参数 `checkpointer` 传进去，得到一个 entrypoint 实例而不是 Pregel 图，后续 `invoke` 会莫名其妙地失败。而 `@task` 两种写法都支持（它专门做了 `__func_or_none__` 重载）。

### 2.2 `__init__`：装饰器参数

```python
def __init__(
    self,
    checkpointer: BaseCheckpointSaver | None = None,   # 持久化（跨 run 记忆 / interrupt 恢复的前提）
    store: BaseStore | None = None,                    # 通用 KV 存储（可带语义检索）
    cache: BaseCache | None = None,                    # 结果缓存
    context_schema: type[ContextT] | None = None,      # 运行期上下文 schema
    cache_policy: CachePolicy | None = None,
    retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
    timeout: float | timedelta | TimeoutPolicy | None = None,
    **kwargs: Unpack[DeprecatedKwargs],                # 承接已弃用的 config_schema / retry
) -> None:
```

解析：

- **`checkpointer`**：在装饰器层直接绑定（也可以 `compile` 后再传）。没有 checkpointer 就没有 `previous`、没有 `interrupt` 恢复、没有时间旅行。
- **弃用迁移**：源码中 `config_schema` 被显式拦截并发 `LangGraphDeprecatedSinceV10` 警告，映射到 `context_schema`；旧参数 `retry` 发 `LangGraphDeprecatedSinceV05` 警告，映射到 `retry_policy`。旧代码升级时按此替换即可。
- **`timeout`**：经 `coerce_timeout_policy` 归一为 `TimeoutPolicy`（数字/timedelta 会被解释为硬性 `run_timeout`）。**只支持 async 工作流**——sync 函数无法在进程内被安全取消（`_internal/_timeout.py` 提供了统一的报错文案，见第 12 节）。

### 2.3 `__call__`：函数如何变成一个 Pregel 图（源码解析）

这是理解函数式 API 本质的核心。`entrypoint.__call__` 的关键源码：

```python
def __call__(self, func: Callable[..., Any]) -> Pregel:
    # wrap generators in a function that writes to StreamWriter
    if inspect.isgeneratorfunction(func) or inspect.isasyncgenfunction(func):
        raise NotImplementedError(
            "Generators are not supported in the Functional API."
        )

    bound = get_runnable_for_entrypoint(func)
    stream_mode: StreamMode = "updates"

    # get input and output types
    sig = inspect.signature(func)
    first_parameter_name = next(iter(sig.parameters.keys()), None)
    if not first_parameter_name:
        raise ValueError("Entrypoint function must have at least one parameter")
    input_type = (
        sig.parameters[first_parameter_name].annotation
        if sig.parameters[first_parameter_name].annotation is not inspect.Signature.empty
        else Any
    )

    def _pluck_return_value(value: Any) -> Any:
        """Extract the return_ value the entrypoint.final object or passthrough."""
        return value.value if isinstance(value, entrypoint.final) else value

    def _pluck_save_value(value: Any) -> Any:
        """Get save value from the entrypoint.final object or passthrough."""
        return value.save if isinstance(value, entrypoint.final) else value

    graph: Pregel[Any, ContextT, Any, Any] = Pregel(
        nodes={
            func.__name__: PregelNode(
                bound=bound,
                triggers=[START],
                channels=START,
                timeout=self.timeout,
                writers=[
                    ChannelWrite(
                        [
                            ChannelWriteEntry(END, mapper=_pluck_return_value),
                            ChannelWriteEntry(PREVIOUS, mapper=_pluck_save_value),
                        ]
                    )
                ],
            )
        },
        channels={
            START: EphemeralValue(input_type),
            END: LastValue(output_type, END),
            PREVIOUS: LastValue(save_type, PREVIOUS),
        },
        input_channels=START,
        output_channels=END,
        stream_channels=END,
        stream_mode=stream_mode,
        stream_eager=True,
        checkpointer=self.checkpointer,
        store=self.store,
        cache=self.cache,
        cache_policy=self.cache_policy,
        retry_policy=self.retry_policy or (),
        context_schema=self.context_schema,
    )
    ...
    return graph
```

逐段解析：

1. **生成器函数被拒绝**：`yield` 风格的函数直接 `NotImplementedError`。自定义流式输出应使用注入的 `runtime.stream_writer`（`StreamWriter`），而不是生成器。
2. **签名约束**：入口函数**必须有至少一个参数**（第一个参数即图的输入，其类型注解成为 `START` 通道的 `input_type`）。多参数场景请用 dict/dataclass 打包成一个参数。
3. **单节点拓扑**：整个函数被包成一个名为 `func.__name__` 的 `PregelNode`，`triggers=[START]`、`channels=START`——即「START 通道一有值就触发这个唯一节点」。这就是为什么函数式图无法画出内部拓扑：对 Pregel 而言它就是一个节点。
4. **三通道模型**：
   - `START: EphemeralValue(input_type)` —— 瞬态输入通道（消费即清空）；
   - `END: LastValue(output_type)` —— 图输出；
   - `PREVIOUS: LastValue(save_type)` —— 下一轮 `previous` 参数的来源。
5. **返回值双写**：`ChannelWrite` 带两个 mapper——`_pluck_return_value` 从返回值（或 `entrypoint.final`）中取出 `value` 写入 `END`；`_pluck_save_value` 取出 `save` 写入 `PREVIOUS`。普通返回值时两个 mapper 都是直通（passthrough），所以「返回什么就存什么」。
6. **`stream_eager=True`、`stream_mode="updates"`**：函数式图默认按 updates 语义产出流事件。
7. **返回值类型推导**：如果返回注解是 `entrypoint.final[R, S]`，则 `output_type=R`、`save_type=S`；未参数化的裸 `entrypoint.final` 退化为 `Any`；参数个数不对会直接 `TypeError`（源码中要求必须同时给出 return 和 save 两个类型参数）。
8. **strict msgpack 序列化白名单**：`__call__` 末尾在 `_serde.STRICT_MSGPACK_ENABLED` 时，会用 input/output/save/context 四个 schema 构建 serde 白名单并套在 checkpointer 上——即开启严格序列化模式后，**不在类型注解里的对象将无法落盘**，类型注解写准确在此模式下不只是文档问题。

### 2.4 `previous` 与 `entrypoint.final`：函数式的状态管理

`entrypoint.final` 是一个 frozen dataclass：

```python
@dataclass(**_DC_KWARGS)   # kw_only=True, slots=True, frozen=True
class final(Generic[R, S]):
    value: R
    """Value to return. A value will always be returned even if it is `None`."""
    save: S
    """The value for the state for the next checkpoint.

    A value will always be saved even if it is `None`.
    """
```

解析：`value` 是给调用方看的返回值，`save` 是写进 checkpoint（`PREVIOUS` 通道）的值——下一轮同一 `thread_id` 调用时经 `previous` 参数注入。**两者可以不同类型、不同内容**，这是函数式 API 里唯一的「显式状态」机制。官方 docstring 中的翻倍累加例子：

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint

@entrypoint(checkpointer=InMemorySaver())
def my_workflow(number: int, *, previous: int | None = None) -> entrypoint.final[int, int]:
    previous = previous or 0
    # 返回给调用方的是 previous；存进 checkpoint 的是 2 * number（下一轮的 previous）
    return entrypoint.final(value=previous, save=2 * number)

config = {"configurable": {"thread_id": "1"}}
my_workflow.invoke(3, config)  # 0（首轮 previous 为 None）
my_workflow.invoke(1, config)  # 6（上一轮 save 了 3 * 2）
```

### 2.5 可注入参数

docstring 中给出的注入表（按**参数名**匹配，函数签名里声明了才注入）：

| 参数名 | 类型 | 说明 |
|--------|------|------|
| `config` | `RunnableConfig` | 运行期配置（callbacks、configurable、recursion_limit…） |
| `previous` | 任意 | 同一 thread 上一轮的存档值；**仅当提供 checkpointer 时可用** |
| `runtime` | `Runtime` | 含 `context`（context_schema 实例）、`store`、`stream_writer`，以及 `heartbeat()`（配合 `TimeoutPolicy.idle_timeout` 续命，见第 12 节） |

### 2.6 装饰后的对象是什么

`__call__` 返回 `Pregel`，因此入口函数装饰后拥有全套图方法：`invoke / ainvoke / stream / astream / get_state / get_state_history / update_state / batch / with_config ...`，也**可以直接作为节点塞进另一个 `StateGraph`**（`builder.add_node("sub", my_workflow)`），此时 `Command(graph=Command.PARENT)`、interrupt 冒泡等子图语义全部生效（见第 5、6 节）。

## 3. @task 装饰器

### 3.1 `_TaskFunction`：装饰产物的真身

```python
class _TaskFunction(Generic[P, T]):
    def __init__(self, func, *, retry_policy, cache_policy=None, timeout=None, name=None):
        if name is not None:
            if hasattr(func, "__func__"):
                # handle class methods —— 用 partial 复制一份再改名，
                # 避免污染被多个 task 共享的原类方法
                instance_method = functools.partial(func.__func__, func.__self__)
                instance_method.__name__ = name
                func = instance_method
            else:
                func.__name__ = name
        self.func = func
        self.retry_policy = retry_policy
        self.cache_policy = cache_policy
        self.timeout = timeout
        functools.update_wrapper(self, func)

    def __call__(self, *args: P.args, **kwargs: P.kwargs) -> SyncAsyncFuture[T]:
        return _call_with_options(
            self.func, args, kwargs,
            retry_policy=self.retry_policy,
            cache_policy=self.cache_policy,
            timeout=self.timeout,
        )

    def clear_cache(self, cache: BaseCache) -> None:
        """Clear the cache for this task."""
        if self.cache_policy is not None:
            cache.clear(((CACHE_NS_WRITES, identifier(self.func) or "__dynamic__"),))
```

解析：

- `@task` 把函数包成 `_TaskFunction`，**调用它不再执行函数体，而是返回一个 `SyncAsyncFuture`**（`pregel/_call.py`）。future 既可 `.result()` 同步取值，也可 `await`（`SyncAsyncFuture` 同时继承 `concurrent.futures.Future` 并实现 `__await__`，见第 13 节）。
- `name=` 参数会真的改写函数 `__name__`；对类方法做了防共享污染的 `functools.partial` 复制——这是个容易踩的细节：task 的名字会出现在流事件、trace、checkpoint 写入记录里。
- `clear_cache / aclear_cache` 按 `(CACHE_NS_WRITES, identifier(func))` 命名空间清缓存，`identifier` 是 `模块名.限定名` 字符串（借用 cloudpickle 的算法），**局部函数（`<locals>`）拿不到稳定 identifier，缓存会落在 `"__dynamic__"` 命名空间**。

### 3.2 调用链路：`_call_with_options`

```python
# pregel/_call.py
def _call_with_options(func, args, kwargs, *, retry_policy=None, cache_policy=None, timeout=None):
    if timeout is not None and not is_async_callable(func):
        name = getattr(func, "__name__", func.__class__.__name__)
        raise sync_timeout_unsupported(name, kind="Task")   # sync task + timeout → ValueError
    config = get_config()                    # 从 contextvar 拿当前运行配置
    impl = config[CONF][CONFIG_KEY_CALL]     # "__pregel_call"：Pregel 运行时注入的调度函数
    fut = impl(func, (args, kwargs),
               retry_policy=retry_policy, cache_policy=cache_policy,
               callbacks=config["callbacks"], timeout=timeout)
    return fut
```

解析：`@task` 的实际执行被**委托给 Pregel 运行时**（`config.configurable["__pregel_call"]`）。这就是三条硬约束的来源（docstring 原文）：

1. **只能在 `entrypoint` 或 `StateGraph` 节点内部调用**——脱离图运行时，contextvar 里没有 `__pregel_call`，直接报错；
2. **启用 checkpointer 时，task 的输入输出必须可序列化**——它们会被记入 checkpoint 的 pending writes；
3. **调用产生 future**——这正是并行化的机制：先批量调用拿 future，再统一收结果。

### 3.3 并行执行与结果收集

```python
# 同步：先发后收
@task
def add_one_task(a: int) -> int:
    return a + 1

@entrypoint()
def add_one(numbers: list[int]) -> list[int]:
    futures = [add_one_task(n) for n in numbers]   # 全部先发出 → 并行调度
    results = [f.result() for f in futures]         # 再逐个收集
    return results

add_one.invoke([1, 2, 3])  # [2, 3, 4]
```

```python
# 异步（async task 需要 Python ≥ 3.11）：asyncio.gather 直接收 future
@task
async def add_one_task(a: int) -> int:
    return a + 1

@entrypoint()
async def add_one(numbers: list[int]) -> list[int]:
    futures = [add_one_task(n) for n in numbers]
    return asyncio.gather(*futures)

await add_one.ainvoke([1, 2, 3])
```

> ⚠️ 常见反模式：`[add_one_task(n).result() for n in numbers]`——在列表推导里**立即** `.result()`，每个 task 串行等待，完全失去并行性。务必「先建 future 列表，再收结果」。

### 3.4 断点重放：task 结果缓存

`entrypoint` docstring 中的官方例子点出了函数式 HITL 的关键性质：

```python
@task
def compose_essay(topic: str) -> str:
    time.sleep(1.0)  # 模拟慢操作
    return f"An essay about {topic}"

@entrypoint(checkpointer=InMemorySaver())
def review_workflow(topic: str) -> dict:
    essay = compose_essay(topic).result()
    human_review = interrupt({"question": "Please provide a review", "essay": essay})
    return {"essay": essay, "review": human_review}
```

> *"Upon resuming the workflow, compose_essay task will not be re-executed as its result is cached by the checkpointer."*

解析：`Command(resume=...)` 恢复时，**entrypoint 函数体会从头重新执行**（interrupt 的语义就是重放，见第 6 节），但已完成的 `@task` 的输入输出已在 checkpoint 的 writes 里，重放到同一调用点时直接返回缓存结果，不会真的再跑一遍。**推论：副作用（发邮件、写库）必须放进 `@task` 或 `interrupt` 之后的代码**，否则裸写在 entrypoint 函数体里的副作用会在每次 resume 重放时重复执行。

### 3.5 `task()` 装饰器参数

```python
def task(
    __func_or_none__=None, *,
    name: str | None = None,
    retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
    cache_policy: CachePolicy[Callable[P, str | bytes]] | None = None,
    timeout: float | timedelta | TimeoutPolicy | None = None,
    **kwargs: Unpack[DeprecatedKwargs],      # 旧 `retry=` → LangGraphDeprecatedSinceV05
):
```

- `retry_policy` 可以是单个策略或**策略序列**（内部统一 coerce 成 tuple，`PregelExecutableTask.retry_policy` 字段就是 `Sequence[RetryPolicy]`）；
- `cache_policy`（`types.py`）：

```python
@dataclass(**_DC_KWARGS)
class CachePolicy(Generic[KeyFuncT]):
    key_func: KeyFuncT = default_cache_key   # 默认对输入做 pickle 哈希
    ttl: int | None = None                   # 秒；None = 永不过期
```

- `timeout`：数字/`timedelta` 解释为硬性 `run_timeout`；**只支持 async task**，sync task 传 timeout 会在装饰时刻直接 `ValueError`（`sync_timeout_unsupported`，见 12.3）。

## 4. Send 类型：动态分发与扇出

### 4.1 源码

```python
class Send:
    """A message or packet to send to a specific node in the graph. ..."""

    __slots__ = ("node", "arg", "timeout")

    node: str
    arg: Any
    timeout: TimeoutPolicy | None

    def __init__(self, /, node: str, arg: Any, *,
                 timeout: float | timedelta | TimeoutPolicy | None = None) -> None:
        self.node = node
        self.arg = arg
        self.timeout = TimeoutPolicy.coerce(timeout)

    def __hash__(self) -> int:
        return hash((self.node, self.arg, self.timeout))

    def __eq__(self, value: object) -> bool:
        return (isinstance(value, Send) and self.node == value.node
                and self.arg == value.arg and self.timeout == value.timeout)
```

解析：`Send` 是发给**特定节点**的数据包，`arg` 是该节点这一步的输入。三个要点：

1. **`arg` 可以与图状态 schema 完全不同**——docstring 原文：*"Importantly, the sent state can differ from the core graph's state"*。这让同一个节点可以在一个 superstep 里被以不同输入并行调用 N 次（map-reduce 的 map 腿）。
2. **`__slots__` + `__hash__`/`__eq__`**：轻量、可哈希、可比较——Send 会进入 checkpoint 的 pending writes（`TASKS = "__pregel_tasks"` 保留键），因此必须可序列化且可判等（重放时要能匹配）。
3. **`timeout` 是 per-Send 覆盖**：1.2.9 新增能力，允许对某一个被推送的任务单独设超时；不传则用目标节点自己的 `TimeoutPolicy`。

### 4.2 push vs pull：`_constants.py` 的证据

```python
PUSH = sys.intern("__pregel_push")
# denotes push-style tasks, ie. those created by Send objects
PULL = sys.intern("__pregel_pull")
# denotes pull-style tasks, ie. those triggered by edges
```

解析：这是 Send 与普通条件边**本质区别**的官方注脚——

| | 条件边返回节点名（pull） | `Send`（push） |
|---|---|---|
| 触发方式 | 边被激活后按名拉取节点，输入=当前图状态 | 直接把 `(node, arg)` 推入下一步任务队列 |
| 扇出数量 | 静态：一次返回一组固定节点名 | 动态：运行时决定复制同一节点多少次 |
| 每个实例的输入 | 都是同一份图状态 | 各自携带私有 `arg` |
| 典型用途 | 分支路由 | map-reduce、并行 N 个子查询、动态多 agent 派发 |

### 4.3 扇出（fan-out）标准范式

docstring 内置的 map-reduce 例子（可直接运行）：

```python
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Send

class OverallState(TypedDict):
    subjects: list[str]
    jokes: Annotated[list[str], operator.add]     # reducer：并行写入用 operator.add 合并

def continue_to_jokes(state: OverallState):
    # 条件边函数返回 Send 列表 → 每个 subject 一个并行的 generate_joke 实例
    return [Send("generate_joke", {"subject": s}) for s in state["subjects"]]

builder = StateGraph(OverallState)
builder.add_node("generate_joke",
                 lambda state: {"jokes": [f"Joke about {state['subject']}"]})
builder.add_conditional_edges(START, continue_to_jokes)
builder.add_edge("generate_joke", END)
graph = builder.compile()

graph.invoke({"subjects": ["cats", "dogs"]})
# {'subjects': ['cats', 'dogs'], 'jokes': ['Joke about cats', 'Joke about dogs']}
```

注意 `generate_joke` 节点收到的是 Send 的 `arg`（`{"subject": s}`）而**不是** `OverallState`——所以它的返回 `{"jokes": [...]}` 会经 reducer `operator.add` 汇聚回主状态。没有 reducer 的通道被并行写入会触发 `InvalidUpdateError`（`INVALID_CONCURRENT_GRAPH_UPDATE`）。

`Send` 还可以出现在 `Command(goto=...)` 里（见 5.2），即「节点自己决定动态扇出」，不必借道条件边。

## 5. Command 类型：状态更新与路由控制

### 5.1 源码全貌

```python
@dataclass(**_DC_KWARGS)   # kw_only=True, slots=True, frozen=True
class Command(Generic[N], ToolOutputMixin):
    """One or more commands to update the graph's state and send messages to nodes."""

    graph: str | None = None
    update: Any | None = None
    resume: dict[str, Any] | Any | None = None
    goto: Send | Sequence[Send | N] | N = ()

    def __repr__(self) -> str:
        # get all non-None values
        contents = ", ".join(f"{key}={value!r}" for key, value in asdict(self).items() if value)
        return f"Command({contents})"

    def _update_as_tuples(self) -> Sequence[tuple[str, Any]]:
        if isinstance(self.update, dict):
            return list(self.update.items())
        elif isinstance(self.update, (list, tuple)) and all(
            isinstance(t, tuple) and len(t) == 2 and isinstance(t[0], str) for t in self.update
        ):
            return self.update
        elif keys := get_cached_annotated_keys(type(self.update)):
            return get_update_as_tuples(self.update, keys)
        elif self.update is not None:
            return [("__root__", self.update)]
        else:
            return []

    PARENT: ClassVar[Literal["__parent__"]] = "__parent__"
```

解析：`Command` 是一个 **frozen dataclass**（不可变、可哈希、可安全落 checkpoint），四个字段可以**任意组合**，一次返回同时完成「更新状态 + 路由 + 恢复中断 + 跨图通信」。泛型参数 `N`（`bound=Hashable`）用于给 `goto` 标注合法节点名集合，如 `Command[Literal["good", "bad", "__end__"]]`，纯类型检查用途。

`ToolOutputMixin`（来自 `langchain_core.messages.tool`，导入失败时降级为空基类）标记 Command 可以作为**工具调用的返回内容**——这是 langchain agent 里「工具直接改图状态/路由」的类型基础。

### 5.2 `Command(goto=...)`：路由控制

docstring 定义 goto 的四种形态：

```
goto: Can be one of the following:
    - Name of the node to navigate to next (any node that belongs to the specified `graph`)
    - Sequence of node names to navigate to next
    - `Send` object (to execute a node with the input provided)
    - Sequence of `Send` objects
```

即：**单个节点名 / 节点名列表（多路并行）/ 单个 Send / Send 列表（动态扇出）**。节点函数返回 `Command(goto="b", update={...})` 时，该节点不再需要静态出边——路由完全由返回值决定。`goto=END`（`"__end__"`）即结束。

### 5.3 `Command(update=...)`：状态更新

`_update_as_tuples` 揭示了 update 支持的四种载荷形态：

1. **dict** → 直接 `items()`（最常用）；
2. **`[(key, value), ...]` 二元组序列** → 原样透传（允许同 key 多次写入，按序过 reducer）;
3. **带注解字段的对象**（TypedDict/Pydantic/dataclass）→ `get_update_as_tuples` 按字段拆；
4. **其他任意值** → 包装成 `[("__root__", value)]`，用于 Pydantic 根模型这类「整体即状态」的通道。

update 与节点普通返回 dict 的语义一致（走同样的通道写入与 reducer），区别是它可以和 goto/resume/graph **原子地**组合在一条命令里。

### 5.4 `Command(resume=...)`：中断恢复

```
resume: Value to resume execution with. To be used together with interrupt().
    Can be one of the following:
    - Mapping of interrupt ids to resume values     # {interrupt_id: value} 精确投递
    - A single value with which to resume the next interrupt  # 单值 → 恢复下一个中断
```

两种形态的分工：

- **单值**（最常见）：`graph.invoke(Command(resume="yes"), config)`，按顺序喂给该线程当前挂起的下一个 interrupt；
- **id → 值映射**：并行分支里同时挂了多个 interrupt 时，用 `Interrupt.id`（`interrupt()` 抛出的 `Interrupt.from_ns` 以 checkpoint_ns 的 xxh3_128 哈希为 id，见第 6 节）精确指定恢复哪一个：`Command(resume={"45fda84...": "yes", "9c2be10...": "no"})`。

resume 型 Command 是作为**图的输入**传的（`invoke/stream` 的第一个参数），而 goto/update 型 Command 是**节点的返回值**——同一种类型，两个方向。`RemoteGraph` 对这一区别有硬约束（见 11.5）。

### 5.5 `Command(graph=Command.PARENT)`：父图通信

`PARENT` 是类变量 `"__parent__"`。子图（含函数式 entrypoint 子图、RemoteGraph）中的节点返回 `Command(graph=Command.PARENT, goto="parent_node", update={...})` 时，命令**不作用于当前图**，而是冒泡给最近的父图执行。

底层机制在 `errors.py`：

```python
class ParentCommand(GraphBubbleUp):
    args: tuple[Command]

    def __init__(self, command: Command) -> None:
        super().__init__(command)
```

解析：子图运行时把跨图 Command 包成 `ParentCommand` 异常沿 `GraphBubbleUp`（控制流异常家族）向上冒泡，父图的执行循环捕获后在父图上下文里应用它。远程子图走的是同一套协议的 wire 版本——`pregel/remote.py` 的 stream 循环里：

```python
# raise ParentCommand exception for command events
if mode == "command" and chunk.data.get("graph") == Command.PARENT:
    raise ParentCommand(Command(**chunk.data))
```

即远程图通过 SSE 的 `command` 事件把 Command 传回来，本地适配器重建 `Command` 对象并以同样的 `ParentCommand` 异常注入父图。**本地子图与远程子图的父图通信语义因此完全一致。**

### 5.6 jump_to 机制：它不在 langgraph 里

对 1.2.9 全源码 grep `jump_to|JumpTo` **零命中**——`Command` 没有 jump_to 字段。这个机制实际住在上层 `langchain` 的 agent 中间件层（`langchain/agents/middleware/types.py`）：

```python
JumpTo = Literal["tools", "model", "end"]
"""Destination to jump to when a middleware node returns."""

class AgentState(TypedDict):
    ...
    jump_to: NotRequired[Annotated[JumpTo | None, EphemeralValue, PrivateStateAttr]]
```

用法（同文件 `hook_config` docstring）：

```python
from langchain.agents.middleware import after_model, hook_config

@hook_config(can_jump_to=["end", "model"])
def my_after_model(state, runtime):
    if something_wrong(state):
        return {"jump_to": "end"}     # 跳过 tools，直接结束
```

解析三个要点：

1. `jump_to` 是 **`EphemeralValue` + `PrivateStateAttr`** 注解的状态键——瞬态（下一步即清空）、私有（不出现在对外 schema 里），本质是「中间件钩子向 agent 图的路由条件边发信号」；
2. `can_jump_to`（装饰器 `hook_config(can_jump_to=[...])` 或 `@before_model(can_jump_to=["end"])` 参数）是**白名单**：`langchain/agents/factory.py` 编译 agent 图时只为声明过的跳转目的地生成条件边分支，未声明的 `jump_to` 值不会生效——这是静态编译的图对动态跳转的约束方式；
3. 在纯 langgraph 层的等价物就是 `Command(goto=...)`：`jump_to: "end"` ≈ `Command(goto=END)`，`jump_to: "model"` ≈ `Command(goto="model")`。中间件层选择「返回状态键」而不是「返回 Command」，是因为钩子还要同时返回其他状态更新，由 factory 统一翻译成图路由。

## 6. interrupt() 函数：人机协同的核心

### 6.1 源码全文与逐段解析

`types.py` 中 `interrupt` 的完整实现（1.2.9）：

```python
def interrupt(value: Any) -> Any:
    from langgraph._internal._constants import (
        CONFIG_KEY_CHECKPOINT_NS, CONFIG_KEY_SCRATCHPAD, CONFIG_KEY_SEND, RESUME,
    )
    from langgraph.config import get_config
    from langgraph.errors import GraphInterrupt

    conf = get_config()["configurable"]
    # track interrupt index
    scratchpad = conf[CONFIG_KEY_SCRATCHPAD]        # "__pregel_scratchpad"：任务级可变暂存区
    idx = scratchpad.interrupt_counter()            # 本任务内第几个 interrupt（从 0 递增）
    # find previous resume values
    if scratchpad.resume:
        if idx < len(scratchpad.resume):
            conf[CONFIG_KEY_SEND]([(RESUME, scratchpad.resume)])   # 回写 __resume__ 通道
            return scratchpad.resume[idx]           # ① 已有存档的 resume 值 → 直接返回
    # find current resume value
    v = scratchpad.get_null_resume(True)
    if v is not None:
        assert len(scratchpad.resume) == idx, (scratchpad.resume, idx)
        scratchpad.resume.append(v)
        conf[CONFIG_KEY_SEND]([(RESUME, scratchpad.resume)])
        return v                                    # ② 本次输入携带的 resume 值 → 消费并返回
    # no resume value found
    raise GraphInterrupt(                           # ③ 没有 resume 值 → 抛控制流异常
        (Interrupt.from_ns(value=value, ns=conf[CONFIG_KEY_CHECKPOINT_NS]),)
    )
```

三条路径的语义：

- **路径 ①（重放命中）**：resume 后节点从头重放，第 idx 个 interrupt 在 `scratchpad.resume` 里找到上次的值，**原样返回、不再中断**。这就是「一个节点多个 interrupt，按出现顺序配对 resume 值」的实现；docstring 强调该 resume 列表**按 task 隔离**（"scoped to the specific task executing the node and is not shared across tasks"）。
- **路径 ②（消费新值）**：`Command(resume=v)` 作为本次输入进来，第一个尚未配对的 interrupt 消费它并记入 scratchpad、经 `CONFIG_KEY_SEND` 写回保留通道 `RESUME = "__resume__"`（`_constants.py`："for values passed to resume a node after an interrupt"）持久化。
- **路径 ③（首次中断）**：抛 `GraphInterrupt`，携带 `Interrupt.from_ns(value, ns)`：

```python
@classmethod
def from_ns(cls, value: Any, ns: str) -> Interrupt:
    return cls(value=value, id=xxh3_128_hexdigest(ns.encode()))
```

`Interrupt.id` 是**当前 checkpoint 命名空间的 xxh3-128 哈希**——同一位置的 interrupt 在重放时 id 稳定，因此 `Command(resume={id: value})` 才能精确投递。`Interrupt` 本身只有两个公开字段（`value` + `id`）；v0.6 已删除 `ns/when/resumable`，`interrupt_id` 属性弃用（读它会发 `LangGraphDeprecatedSinceV10` 警告，改用 `.id`）。

### 6.2 使用契约（docstring 归纳）

1. **必须启用 checkpointer**——中断依赖状态持久化，否则直接报错；
2. **首次调用抛 `GraphInterrupt` 挂起整个 run**，`value` 随异常冒泡并最终呈现给客户端；
3. **恢复必须用 `Command(resume=...)`**，且**节点从开头重新执行**（"The graph resumes from the start of the node, **re-executing** all logic"）——interrupt 之前的代码会再跑一遍，务必幂等（副作用放 `@task` 里，见 3.4）；
4. 一个节点多个 interrupt 按顺序配对 resume 值。

### 6.3 顶层抑制：为什么你的代码 catch 不到 GraphInterrupt

`errors.py` 对 `GraphInterrupt` 的定义只有一句但极重要：

```python
class GraphInterrupt(GraphBubbleUp):
    """Raised when a subgraph is interrupted, suppressed by the root graph.
    Never raised directly, or surfaced to the user."""
```

解析：`GraphInterrupt` 是**内部控制流信号**，根图执行循环会把它拦下，绝不抛给 `invoke` 的调用方。对外呈现为三个出口：

- `stream` 的 `updates` 流里出现 `__interrupt__` 键（`INTERRUPT = sys.intern("__interrupt__")` 保留写入键）；
- v2 `invoke` 返回的 `GraphOutput.interrupts`（见下）；
- `get_state()` 快照的 `interrupts` / `tasks[].interrupts` 字段。

> ⚠️ **本项目实测过的坑**（nl2sql HITL 审批链路）：判断「是否有审批挂起」不能靠 try/except，也**不能只看顶层输出**——要读 `state.tasks[].interrupts` 或 `StateSnapshot.interrupts`；这正是「HITL interrupt 被 top-level graph 抑制」的落地形态。远程子图场景同理：`RemoteGraph.stream` 只有当自己作为子图嵌套（`caller_ns` 非空）时才把远程中断转抛为本地 `GraphInterrupt`，独立调用时中断只是安静地出现在 updates 数据里（见 11.3）。

v2 输出容器（`types.py`）：

```python
@dataclass(frozen=True)
class GraphOutput(Generic[OutputT]):
    value: OutputT                      # 图的最终输出
    interrupts: tuple[Interrupt, ...] = ()   # 本次运行发生的中断

    def __getitem__(self, key: str) -> Any:
        """Backward compat: `result['__interrupt__']` and dict-key access."""
        warn("Accessing GraphOutput via `result[key]` is deprecated. ...",
             LangGraphDeprecatedSinceV11, stacklevel=2)
```

即 `invoke(..., version="v2")` 之后应写 `result.interrupts`，旧的 `result["__interrupt__"]` 还能用但每次访问都发 v1.1 弃用警告（ slated v3.0 移除）。

### 6.4 完整 HITL 示例（函数式 API）

`entrypoint` docstring 自带的官方例子（可直接运行）：

```python
import time
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint, task
from langgraph.types import Command, interrupt

@task
def compose_essay(topic: str) -> str:
    time.sleep(1.0)
    return f"An essay about {topic}"

@entrypoint(checkpointer=InMemorySaver())
def review_workflow(topic: str) -> dict:
    essay = compose_essay(topic).result()
    human_review = interrupt({"question": "Please provide a review", "essay": essay})
    return {"essay": essay, "review": human_review}

config = {"configurable": {"thread_id": "some_thread"}}

for result in review_workflow.stream("cats", config):
    print(result)          # 输出包含 __interrupt__，此时 run 已挂起

# 人给出评审意见后恢复：
for result in review_workflow.stream(Command(resume="This essay is great."), config):
    print(result)          # compose_essay 不重跑（checkpoint 缓存），直接得到最终 dict
```

## 7. StateSnapshot：快照、时间旅行与 as_node

### 7.1 字段定义

```python
class StateSnapshot(NamedTuple):
    """Snapshot of the state of the graph at the beginning of a step."""

    values: dict[str, Any] | Any
    """Current values of channels."""
    next: tuple[str, ...]
    """The name of the node to execute in each task for this step."""
    config: RunnableConfig
    """Config used to fetch this snapshot."""
    metadata: CheckpointMetadata | None
    """Metadata associated with this snapshot."""
    created_at: str | None
    """Timestamp of snapshot creation."""
    parent_config: RunnableConfig | None
    """Config used to fetch the parent snapshot, if any."""
    tasks: tuple[PregelTask, ...]
    """Tasks to execute in this step. If already attempted, may contain an error."""
    interrupts: tuple[Interrupt, ...]
    """Interrupts that occurred in this step that are pending resolution."""
```

配套的任务视图：

```python
class PregelTask(NamedTuple):
    id: str
    name: str
    path: tuple[str | int | tuple, ...]
    error: Exception | None = None
    interrupts: tuple[Interrupt, ...] = ()
    state: None | RunnableConfig | StateSnapshot = None   # 子图任务 → 子图快照/其 config
    result: Any | None = None
```

解析：

- `next` 是**将要执行**的节点名元组（不是「已执行」）；`next` 非空即说明该步尚未完成——但注意本项目踩过的「幽灵 next」坑：用 `update_state(as_node="__start__")` 会把 `next` 写回入口，`state.next` 非空 ≠ 一定丢步，要结合 `tasks[].result/error` 判断；
- `tasks[i].state` 是递归结构：子图任务携带子图自己的 `StateSnapshot`（或指向它的 `RunnableConfig`），这是逐层钻取子图状态的入口；
- `interrupts` 是把 `tasks[].interrupts` 摊平后的便捷字段，`RemoteGraph._create_state_snapshot` 里可以看到显式的摊平逻辑：`interrupts=tuple([i for task in tasks for i in task.interrupts])`；
- `config` 里含 `thread_id / checkpoint_ns / checkpoint_id / checkpoint_map` 四元坐标——**拿着某个历史快照的 `.config` 重新 invoke，就是时间旅行/分叉**。

### 7.2 获取快照与历史

```python
snap = graph.get_state(config)                     # 最新快照
for snap in graph.get_state_history(config):       # 由新到旧遍历全部检查点
    print(snap.created_at, snap.next, snap.metadata.get("step"))

# 时间旅行：从历史里挑一个快照，用它的 config 继续跑 → 产生分叉
old = list(graph.get_state_history(config))[-2]
graph.invoke(None, old.config)     # 从该检查点重放/续跑
```

v2 流式里等价的载荷是 `CheckpointPayload`（`stream_mode="checkpoints"`），字段与 StateSnapshot 一一对应（config/metadata/values/next/parent_config/tasks）。

### 7.3 `update_state` 与 `as_node`

```python
class StateUpdate(NamedTuple):
    values: dict[str, Any] | None
    as_node: str | None = None
    task_id: str | None = None
```

`graph.update_state(config, values, as_node="node_x")` 的语义（`RemoteGraph.update_state` docstring 原话）：**"Update the state as if this node had just executed"**——伪造一次「node_x 刚跑完并写出了 values」的检查点。由此产生两个后果：

1. values 按 node_x 的写出路径过 reducer 合入状态；
2. **下一步执行什么由 node_x 的出边推导**——`as_node` 实际是在选择「站在哪个节点之后」续跑。不传时运行时按 values 的键与各节点写出通道的匹配自动猜测。

`task_id` 用于精确指定伪造成哪个并行任务的写出（同节点多实例时）。远程图的 `bulk_update_state` 在 1.2.9 明确 `raise NotImplementedError`——批量伪造检查点只在本地 Pregel 支持。

## 8. 核心异常类型

### 8.1 异常家族总览（errors.py，1.2.9 实际结构）

```
Exception
├── GraphBubbleUp                 # 控制流「冒泡」基类：不是错误，是运行时信号
│   ├── GraphDrained              # 协作式排空退出（SIGTERM/蓝绿发布），检查点已存，可恢复
│   ├── GraphInterrupt            # 中断信号；根图抑制，绝不直接抛给用户
│   │   └── NodeInterrupt         # ⚠️ 已弃用（v1.0），改用 interrupt()
│   └── ParentCommand             # 携带发往父图的 Command（见 5.5）
├── RecursionError
│   └── GraphRecursionError       # 步数耗尽（recursion_limit）
├── InvalidUpdateError            # 非法状态更新
├── EmptyChannelError             # 通道为空（从 checkpoint.base re-export）
├── EmptyInputError               # 图收到空输入
├── TaskNotFound                  # 分布式模式下执行器找不到任务
├── NodeCancelledError            # 节点自己 raise 了 asyncio.CancelledError
├── NodeTimeoutError              # run_timeout / idle_timeout 触发
└── RemoteException               # 远程图报错（定义在 pregel/remote.py）
```

另有非异常的失败上下文载体：

```python
@dataclass(frozen=True, slots=True)
class NodeError:
    """Failure context passed to a node-level error handler. ..."""
    node: str          # 失败节点名
    error: BaseException
```

用于 `StateGraph.add_node(..., error_handler=...)` 的节点级错误处理：handler 签名里声明 `error: NodeError` 参数即可注入（`_constants.py` 中对应注入键 `CONFIG_KEY_NODE_ERROR = "__pregel_node_error"`）。

### 8.2 逐个解析

**`GraphBubbleUp`**——空基类，但语义重大：Pregel 循环对它的子类**按控制流处理**（中断挂起、命令上递、排空退出），不当作节点失败，不触发重试。自己写中间件/运行时扩展时，凡是「要穿透调用栈传给图循环的信号」都应挂在这个家族下。

**`GraphRecursionError`**：

```python
class GraphRecursionError(RecursionError):
    """Raised when the graph has exhausted the maximum number of steps.

    This prevents infinite loops. To increase the maximum number of steps,
    run your graph with a config specifying a higher `recursion_limit`.
    ...
        graph.invoke({"messages": [...]}, {"recursion_limit": 1000})
    """
```

注意它继承内建 `RecursionError`，但含义与 Python 调用栈深度无关——计的是 **superstep 数**。默认上限见 14.3（`DEFAULT_RECURSION_LIMIT = 10007`，可用环境变量 `LANGGRAPH_DEFAULT_RECURSION_LIMIT` 改）。错误信息经 `create_error_message` 附带官方排障链接（`ErrorCode.GRAPH_RECURSION_LIMIT`）。**循环图忘写退出条件时它是唯一的刹车**，捕获它时应把已完成的部分状态从 checkpoint 里读出来，而不是简单重跑。

**`GraphInterrupt` / `NodeInterrupt`**：前者见第 6 节。后者是旧 API（节点手动 `raise NodeInterrupt(value)`），1.2.9 中类装饰器 `@deprecated` + 构造时发 `LangGraphDeprecatedSinceV10` 警告双保险提示迁移到 `interrupt()`：

```python
@deprecated("NodeInterrupt is deprecated. Please use [`interrupt`] instead.", category=None)
class NodeInterrupt(GraphInterrupt):
    def __init__(self, value: Any, id: str | None = None) -> None:
        warn("NodeInterrupt is deprecated. ...", LangGraphDeprecatedSinceV10, stacklevel=2)
```

两者行为差异：`interrupt()` 有 scratchpad 顺序配对与 resume 持久化（重放友好）；`NodeInterrupt` 直接抛异常，恢复语义更粗糙——这是弃用的根本原因。

**`GraphDrained`**：

```python
class GraphDrained(GraphBubbleUp):
    """Raised when a graph run exits early due to a drain request.

    This indicates the graph stopped cooperatively at a superstep boundary
    because `RunControl.request_drain()` was called (e.g., in response to
    SIGTERM). The checkpoint is saved and the run can be resumed later.
    """
    def __init__(self, reason: str = "shutdown") -> None:
```

解析：这是**优雅停机**的信号——收到 SIGTERM 后不打断进行中的 superstep，而是在步边界协作退出，检查点已落盘、run 可恢复。与本项目蓝绿发布「先切流再排空」的设计同源：排空期间的 in-flight run 正是靠这类机制在 superstep 边界安全落地。

**`GraphDelegate`：1.2.9 中已不存在**。对 `.venv` 内 langgraph 全包 grep 零命中。它曾出现在 0.x 版本（同为 `GraphBubbleUp` 子类），用于分布式模式把任务委托给外部执行器；1.x 重构后该职责由 `TaskNotFound`（"Raised when the executor is unable to find a task (for distributed mode)"）与 `GraphDrained` 等分担。**在 1.2.9 上写 `except GraphDelegate` 会直接 ImportError**，迁移时按语义改捕 `GraphBubbleUp` 或上述具体类型。

**`InvalidUpdateError`**：两大高发场景，`ErrorCode` 枚举一一对应官方排障页：

- `INVALID_CONCURRENT_GRAPH_UPDATE`：同一 superstep 内多个并行任务写同一个**无 reducer** 通道（Send 扇出后忘记给汇聚字段加 `Annotated[list, operator.add]` 是最常见原因）；同一通道收到多个 `Overwrite` 也归此类；
- `INVALID_GRAPH_NODE_RETURN_VALUE`：节点返回了不能映射到状态通道的东西（如返回了状态 schema 里不存在的键）。

**`NodeTimeoutError`**——设计上有个精妙的继承决策：

```python
class NodeTimeoutError(Exception):
    """Raised when a node invocation exceeds one of its configured timeouts.

    Does **not** inherit from the built-in `TimeoutError` (a subclass of
    `OSError`) so that the default `RetryPolicy` treats it as retryable.
    ...
    """
    kind: Literal["idle", "run"]     # 哪个超时 firing
    timeout: float                   # 触发的那个阈值
    run_timeout: float | None
    idle_timeout: float | None
    elapsed: float
```

解析：内建 `TimeoutError` 是 `OSError` 子类，而 `default_retry_on` 把 `OSError` 列为**不可重试**（见 12.1）。为了让超时默认走重试，`NodeTimeoutError` 故意只继承 `Exception`。`kind` 区分 `run`（硬墙钟）与 `idle`（无进展），构造时强校验对应阈值必须给出。

**`NodeCancelledError`**：docstring 解释了另一个继承陷阱——`asyncio.CancelledError` 是 `BaseException`，runner 把「被取消的 task future」当作框架级静默拆除（比如兄弟任务失败后停掉其余任务），这是对的；但**节点自己**在函数体里 raise `CancelledError` 不该被静默吞掉。重试层因此把用户抛的 `CancelledError` 转换成本类型，让它走正常错误路径、run 终态报 `error` 而非假成功。

**`EmptyInputError` / `EmptyChannelError` / `TaskNotFound` / `RemoteException`**：分别为空输入、读空通道、分布式任务丢失、远程图 SSE `error` 事件（`raise RemoteException(chunk.data)`，data 为服务端错误载荷）。

## 9. 警告体系（warnings.py）

69 行的小文件，但值得理解——它是判断「这段代码还能活几个大版本」的标尺：

```python
class LangGraphDeprecationWarning(DeprecationWarning):
    """A LangGraph specific deprecation warning.

    Attributes:
        message: Description of the warning.
        since: LangGraph version in which the deprecation was introduced.
        expected_removal: LangGraph version in what the corresponding functionality expected to be removed.

    Inspired by the Pydantic `PydanticDeprecationWarning` class, ...
    """
    def __init__(self, message, *args, since, expected_removal=None):
        super().__init__(message, *args)
        self.message = message.rstrip(".")
        self.since = since
        self.expected_removal = expected_removal if expected_removal is not None else (since[0] + 1, 0)

    def __str__(self) -> str:
        return (f"{self.message}. Deprecated in LangGraph V{self.since[0]}.{self.since[1]}"
                f" to be removed in V{self.expected_removal[0]}.{self.expected_removal[1]}.")
```

三个版本化子类及其移除时间表：

| 警告类 | since | expected_removal | 本教程涉及的实例 |
|--------|-------|------------------|-----------------|
| `LangGraphDeprecatedSinceV05` | v0.5 | **v2.0** | `@task(retry=...)`、`entrypoint(retry=...)` → 改 `retry_policy` |
| `LangGraphDeprecatedSinceV10` | v1.0 | **v2.0** | `config_schema` → `context_schema`；`NodeInterrupt` → `interrupt()`；`Interrupt.interrupt_id` → `.id` |
| `LangGraphDeprecatedSinceV11` | v1.1 | **v3.0** | `GraphOutput.__getitem__`/`__contains__`（`result["__interrupt__"]`）→ `result.value` / `result.interrupts` |

解析：`expected_removal` 缺省规则是「下一个大版本」；由于 `DeprecationWarning` 默认被 Python 过滤器隐藏，**CI 里建议 `-W error::DeprecationWarning` 或 pytest `filterwarnings = error` 才能提前暴露这些迁移点**。升级 langgraph 大版本前，先把测试跑成 warning-as-error 清一遍，是成本最低的迁移策略。

## 10. 回调系统（callbacks.py）

### 10.1 设计定位

模块 docstring 开宗明义：*"defines the public callback surface for observing LangGraph-specific lifecycle transitions such as interrupt and resume"*。它与 langchain_core 的通用 runnable 回调（`on_chain_start` 等）**平行共存**：通过同一个 `config["callbacks"]` 传入，但只有继承 `GraphCallbackHandler` 的 handler 才会收到图生命周期事件——`_configure_graph_callbacks` 里的 `_filter_graph_handlers` 用 `isinstance` 过滤，其他 handler 被静默忽略。

```python
GraphLifecycleStatus: TypeAlias = Literal[
    "input", "pending", "done", "interrupt_before", "interrupt_after", "out_of_steps",
]

@dataclass(frozen=True)
class GraphInterruptEvent:
    run_id: UUID | None            # 当前图执行的 run id
    status: GraphLifecycleStatus   # 捕获中断时循环所处的状态
    checkpoint_id: str             # 中断关联的检查点
    checkpoint_ns: tuple[str, ...] # 当前图/子图的命名空间路径
    interrupts: tuple[Interrupt, ...]  # 导致暂停的中断载荷

@dataclass(frozen=True)
class GraphResumeEvent:
    run_id: UUID | None
    status: GraphLifecycleStatus
    checkpoint_id: str             # 从哪个检查点恢复
    checkpoint_ns: tuple[str, ...]

class GraphCallbackHandler(BaseCallbackHandler):
    """Base class for graph-level lifecycle callbacks. ..."""
    def on_interrupt(self, event: GraphInterruptEvent) -> Any: ...
    def on_resume(self, event: GraphResumeEvent) -> Any: ...
```

解析：两个事件载荷都是 frozen dataclass；`GraphLifecycleStatus` 覆盖了执行循环的全部关键位（输入到达、任务挂起、完成、静态前/后中断、步数耗尽），`status` 字段让 handler 能区分「动态 interrupt() 中断」与「编译期 interrupt_before/after 静态断点」。

### 10.2 分发器：sync/async 双管理器

```python
class _GraphCallbackManager(BaseCallbackManager):
    """Sync dispatcher for graph lifecycle events."""
    def on_interrupt(self, event): handle_event(self.handlers, "on_interrupt", None, event)
    def on_resume(self, event):    handle_event(self.handlers, "on_resume", None, event)

class _AsyncGraphCallbackManager(BaseCallbackManager):
    """Async dispatcher for graph lifecycle events."""
    @property
    def is_async(self) -> bool: return True
    async def on_interrupt(self, event): await ahandle_event(self.handlers, "on_interrupt", None, event)
    async def on_resume(self, event):    await ahandle_event(self.handlers, "on_resume", None, event)
```

以及从 config 构建的公开入口：

```python
def get_sync_graph_callback_manager_for_config(config, *, run_id=None) -> _GraphCallbackManager:
    """... filters `config["callbacks"]` down to handlers that inherit from
    `GraphCallbackHandler` and binds the provided `run_id` onto the returned manager."""
    return _GraphCallbackManager.configure(config.get("callbacks"), run_id=run_id)
```

解析设计要点：

1. **复用 langchain_core 的事件管道**（`handle_event`/`ahandle_event`）——自动获得 handler 异常隔离、`raise_error` 语义等既有行为；
2. **`configure` 的多形态兼容**：callbacks 可以是 `None`、单个 handler、handler 序列、同类型 manager（copy）、**跨类型 manager**（sync↔async 互转时抽取其中 handler 重建）、langchain 通用 `BaseCallbackManager`（同样只抽 `GraphCallbackHandler`）；`str/bytes` 直接 `TypeError`；
3. **`copy(run_id=...)` 用 `_MISSING` 哨兵**区分「不传=沿用原 run_id」与「显式传 None」——嵌套 run 时管理器逐层复制而不互相污染；
4. 事件是**图级**而非节点级：一次 run 的 interrupt/resume 各触发一次，适合做审计日志、通知（如审批提醒）、与 Langfuse 等外部系统对账 run 生命周期。

### 10.3 使用示例

```python
from langgraph.callbacks import GraphCallbackHandler, GraphInterruptEvent, GraphResumeEvent

class AuditHandler(GraphCallbackHandler):
    def on_interrupt(self, event: GraphInterruptEvent):
        for it in event.interrupts:
            print(f"[audit] run={event.run_id} paused at ckpt={event.checkpoint_id}, "
                  f"interrupt_id={it.id}, value={it.value!r}")
    def on_resume(self, event: GraphResumeEvent):
        print(f"[audit] run={event.run_id} resumed from ckpt={event.checkpoint_id}")

graph.invoke(inputs, {
    "configurable": {"thread_id": "t1"},
    "callbacks": [AuditHandler()],      # 与 LangChain 通用 handler 混在同一列表即可
})
```

## 11. RemoteGraph 远程执行

### 11.1 定位与构造

```python
class RemoteGraph(PregelProtocol):
    """The `RemoteGraph` class is a client implementation for calling remote
    APIs that implement the LangGraph Server API specification. ...

    `RemoteGraph` behaves the same way as a `Graph` and can be used directly as
    a node in another `Graph`.
    """

    def __init__(self, assistant_id: str, /, *, url=None, api_key=None, headers=None,
                 client=None, sync_client=None, config=None, name=None,
                 distributed_tracing: bool = False):
```

解析：

- `RemoteGraph` 实现 `PregelProtocol`——**接口上与本地图同形**，`invoke/stream/get_state/update_state/get_graph...` 全都有，因此可以 `builder.add_node("remote", RemoteGraph(...))` 直接当子图节点；
- `assistant_id` 是唯一的位置参数（即远端的 graph_id / assistant 名）；`url/api_key/headers` 用于构建默认 sync+async 客户端（`langgraph_sdk.get_client/get_sync_client`），也可直接注入现成 `client/sync_client`；三者至少给一个，否则调用时 `_validate_client` 抛 ValueError；
- `api_key` 缺省时按 docstring 依次读环境变量 `LANGGRAPH_API_KEY` → `LANGSMITH_API_KEY` → `LANGCHAIN_API_KEY`；
- `name` 用于 `add_node(remote_graph)` 时的节点名（缺省 = assistant_id）；
- `distributed_tracing=True` 时，每次请求经 `_merge_tracing_headers` 把当前 LangSmith run tree 的 trace 头（含 `baggage` 拼接）带上，实现跨服务 trace 串联。

方法与 REST 端点的映射（docstring 内联注明）：

| 方法 | 端点 |
|------|------|
| `get_graph` / `aget_graph` | `GET /assistants/{assistant_id}/graph`（xray 控制子图展开深度） |
| `get_state` / `aget_state` | 带 checkpoint → `POST /threads/{tid}/state/checkpoint`；否则 `GET /threads/{tid}/state` |
| `get_state_history` | `POST /threads/{tid}/history`（默认 limit=10） |
| `update_state` | `POST /threads/{tid}/state`（支持 `as_node`） |
| `stream` / `astream` | `POST /threads/{tid}/runs/stream`（无 thread_id 则 `POST /runs/stream`），SSE |
| `bulk_update_state` | `NotImplementedError` |

### 11.2 配置清洗：`_sanitize_config`

```python
_CONF_DROPLIST = frozenset((
    CONFIG_KEY_CHECKPOINT_MAP, CONFIG_KEY_CHECKPOINT_ID,
    CONFIG_KEY_CHECKPOINT_NS, CONFIG_KEY_TASK_ID,
))

def _sanitize_config_value(v: Any) -> Any:
    """Recursively sanitize a config value to ensure it contains only primitives."""
    if isinstance(v, (str, int, float, bool, UUID)): return v
    elif isinstance(v, dict): ...        # 只保留 str 键 + 可净化值
    elif isinstance(v, (list, tuple)): ...
    return None                          # 其余（函数、对象…）一律丢弃
```

解析：发往远程的 config 只保留 `recursion_limit / tags / metadata / configurable` 四键，且值必须是 JSON 原语——**callbacks、checkpointer 等本地对象根本过不了网络边界**；`checkpoint_id/ns/map/task_id` 被显式丢弃，因为远端 run 有自己的检查点谱系，带过去只会造成坐标错乱。

### 11.3 SSE 流式：`stream/astream` 核心循环

```python
stream_modes, requested, req_single, stream = self._get_stream_modes(stream_mode, config)
if isinstance(input, Command):
    command: CommandSDK | None = cast(CommandSDK, asdict(input))   # Command → SDK dict
    input = None
else:
    command = None
thread_id = sanitized_config.get("configurable", {}).pop("thread_id", None)

for chunk in sync_client.runs.stream(
    thread_id=thread_id, assistant_id=self.assistant_id,
    input=input, command=command, config=sanitized_config, context=context,
    stream_mode=stream_modes,
    interrupt_before=interrupt_before, interrupt_after=interrupt_after,
    stream_subgraphs=subgraphs or stream is not None,
    if_not_exists="create",           # 线程不存在则自动建
    ...
):
    # split mode and ns：事件名形如 "updates|sub:task_id"
    if NS_SEP in chunk.event:
        mode, ns_ = chunk.event.split(NS_SEP, 1)
        ns = tuple(ns_.split(NS_SEP))
    else:
        mode, ns = chunk.event, ()
    # raise ParentCommand exception for command events
    if mode == "command" and chunk.data.get("graph") == Command.PARENT:
        raise ParentCommand(Command(**chunk.data))
    # prepend caller ns (as it is not passed to remote graph)
    if caller_ns := (config or {}).get(CONF, {}).get(CONFIG_KEY_CHECKPOINT_NS):
        ns = tuple(caller_ns.split(NS_SEP)) + ns
    # stream to parent stream
    if stream is not None and mode in stream.modes:
        stream((ns, mode, chunk.data))
    # raise interrupt or errors
    if chunk.event.startswith("updates"):
        if isinstance(chunk.data, dict) and INTERRUPT in chunk.data:
            if caller_ns:
                raise GraphInterrupt([Interrupt(**i) for i in chunk.data[INTERRUPT]])
    elif chunk.event.startswith("error"):
        raise RemoteException(chunk.data)
```

逐条解析（这段是远程/本地语义对齐的关键）：

1. **Command 作为输入**时被 `asdict` 序列化为 SDK 的 command 参数、`input` 置 None——即 `Command(resume=...)` 恢复远程中断走的是 server 的 command 协议；
2. **`_get_stream_modes` 的隐式加料**：无论用户请求什么模式，都会追加 `"updates"`（注释原文：*"'updates' mode is added to the list of stream modes so that interrupts can be detected in the remote graph"*）；本地 `messages` 模式映射为远端的 `messages-tuple`；父图的流模式（`CONFIG_KEY_STREAM`）也会被并进来，产出时再按 `requested` 过滤——**多订阅是为了侦测，不是全吐给你**；
3. **命名空间拼接**：SSE 事件名用 `NS_SEP="|"` 编码 `mode|ns`；作为子图运行时远端不知道 caller 的 ns，本地把自己的 `checkpoint_ns` 前缀拼回去，保证父图流里的 ns 路径连续；
4. **三个「异常化」转换**：`command` 事件且 `graph == "__parent__"` → `ParentCommand`（见 5.5）；`updates` 携带 `__interrupt__` **且存在 caller_ns** → `GraphInterrupt`（让父图挂起）；`error` 事件 → `RemoteException`。注意第二个的条件：**独立调用 RemoteGraph 时中断不抛异常**，只作为普通 updates 块流出——顶层抑制语义与本地一致（6.3）；
5. **版本化产出形态**：`version="v1"`（默认）单模式直接 yield `chunk.data`，多模式 yield `(mode, data)` 或（subgraphs 时）`(ns, mode, data)`；`version="v2"` 统一 yield `{"type": mode, "ns": ns, "data": ..., "interrupts": ...}` 的 `StreamPart` TypedDict，其中 values 模式会把 `__interrupt__` 从 data 里 pop 出来装进 `interrupts` 字段。

### 11.4 `invoke`：流式排空取尾值

```python
def invoke(self, input, config=None, *, ..., version="v1", **kwargs):
    for chunk in self.stream(input, config=config, ..., stream_mode="values",
                             version=version, **kwargs):
        pass                       # 排空流，chunk 停留在最后一个 values 块
    try:
        if version == "v2":
            return GraphOutput(value=chunk["data"],
                               interrupts=tuple(chunk.get("interrupts", ())))
        return chunk
    except UnboundLocalError:
        logger.warning("No events received from remote graph")
        return None
```

解析：远程 `invoke` **没有独立的 wait 端点**，就是把 values 流排空取最后一块。`UnboundLocalError` 兜底（一个事件都没收到）返回 `None` 并打 warning——调用侧应对 `None` 做防御。v2 形态与本地图一致地返回 `GraphOutput`。

### 11.5 v3 运行流适配器（`_remote_run_stream.py`）

`stream_events(version="v3")` 返回 `_RemoteGraphRunStream` / `_AsyncRemoteGraphRunStream`，表面与本地 `GraphRunStream` 对齐。核心约束在输入翻译：

```python
def _translate_command_input(input: Any) -> Any:
    """Translate a local `Command` into the v3 wire `input`, else passthrough.

    The v3 server decides start-vs-resume from thread state (an interrupted
    run or pending interrupts) and, on resume, wraps the whole `input` as
    `{"resume": input}` itself. So a resume `Command` must surface its raw
    `resume` value as the wire `input` (not the serialized dataclass, which
    the server would double-wrap). The v3 `run.start` path has no `goto` /
    `update` channel, so those are rejected.
    """
    if isinstance(input, Command):
        if input.goto or input.update:
            raise NotImplementedError(
                "RemoteGraph v3 streaming supports `Command(resume=...)` only; ...")
        return input.resume
    return input
```

其余要点：

- **上下文管理器协议**：`with rg.stream_events(..., version="v3") as run:`——`__enter__` 里才真正 `run.start(**kwargs)` 拿到 `run_id`；async 版是 `async with await rg.astream_events(...)`（`astream_events` 是 awaitable，返回适配器；v1/v2 直接 `NotImplementedError`，让你改用 `astream`）；
- **投影注册表 `_ProjectionRegistry`**：`run.values / messages / tool_calls / subgraphs` 直通 SDK 的类型化投影；`updates / checkpoints / tasks / custom` 无 SDK 类型化投影，用 `_ChannelProjection` 订阅 wire 通道并经 `DataDecoder` 解码 `params["data"]`，**产出形态与本地对应 transformer 严格一致**；其他名字落到 `sdk.extensions[name]`（自定义扩展通道）。`lifecycle` 与 `debug` 刻意缺席（前者被 SDK 用作控制面驱动 `output/interrupted`，后者不是 v3 wire 通道）；
- **sync/async 语义差异**（docstring 明说）：sync 的 `output`/`interrupted` 是属性，async 的是**方法**（`await run.output()`，防「忘 await 拿到 coroutine」）；远程 `interrupted` 是**非阻塞快照**，与本地「驱动到终态再返回」的语义不同，需要等中断就自己 drain 投影；`abort()` = `runs.cancel(wait=False)` + `close()`，失败只 debug 日志；`interleave(*names)` 仅 sync 版提供（async 用 `asyncio.gather` 组合）。

## 12. 内部重试与超时机制

### 12.1 `default_retry_on`（`_internal/_retry.py` 全文 29 行）

```python
def default_retry_on(exc: Exception) -> bool:
    import httpx
    import requests

    if isinstance(exc, ConnectionError):
        return True
    if isinstance(exc, httpx.HTTPStatusError):
        return 500 <= exc.response.status_code < 600
    if isinstance(exc, requests.HTTPError):
        return 500 <= exc.response.status_code < 600 if exc.response else True
    if isinstance(exc, (
        ValueError, TypeError, ArithmeticError, ImportError, LookupError,
        NameError, SyntaxError, RuntimeError, ReferenceError,
        StopIteration, StopAsyncIteration, OSError,
    )):
        return False
    return True
```

解析（默认重试哲学 = **「网络类默认重试，程序 bug 默认不重试」**）：

- 白名单侧：`ConnectionError`、httpx/requests 的 **5xx** HTTP 错误（4xx 不重试——客户端错误重试无意义）；
- 黑名单侧：`ValueError/TypeError/NameError/SyntaxError/...` 这些是代码错误，重试只会浪费时间；**`OSError` 整族不重试**——这正是 `NodeTimeoutError` 不继承内建 `TimeoutError`（OSError 子类）的原因（8.2），两处在源码里互为印证；
- 兜底 `return True`：未知异常倾向重试（LLM SDK 的各种自定义网络异常多不在黑名单里）。
- `httpx/requests` 在函数体内 import——不用这两个库的环境不为重试判定付出导入成本。

### 12.2 `RetryPolicy`（types.py）

```python
class RetryPolicy(NamedTuple):
    initial_interval: float = 0.5    # 首次重试前等待（秒）
    backoff_factor: float = 2.0      # 每次重试后间隔乘数
    max_interval: float = 128.0      # 间隔上限（秒）
    max_attempts: int = 3            # 总尝试次数（含首次）
    jitter: bool = True              # 间隔加随机抖动，防惊群
    retry_on: (...) = default_retry_on   # 异常类/序列/谓词
```

间隔序列即 `min(initial_interval * backoff_factor**k, max_interval)`（±jitter），默认 0.5s → 1s → 放弃（3 次尝试）。NamedTuple 意味着它不可变、可哈希、可直接进 checkpoint。挂载点：`@task(retry_policy=...)`、`entrypoint(retry_policy=...)`、`StateGraph.add_node(..., retry_policy=...)`；**task/节点级策略优先于图级**。`retry_on` 传谓词函数即可完全自定义（比如只对特定 LLM 限流错误码重试）。

### 12.3 超时：`TimeoutPolicy` 与 sync 限制

```python
@dataclass(**_DC_KWARGS)
class TimeoutPolicy:
    """Configuration for timing out node attempts.

    !!! note "Cooperative cancellation"
        Timeouts rely on asyncio cancellation. If your node uses synchronous
        time.sleep() or other CPU-bound work that blocks the GIL, the timeout will not
        be fired until after the event loop has been released.

    !!! note "Inline callback dispatch"
        Under `refresh_on="auto"`, an internal handler refreshes the timeout on any
        callback event that occurs in the execution of the node or its nested descendants.
    """
    run_timeout: float | timedelta | None = None   # 硬墙钟上限，永不因进展刷新
    idle_timeout: float | timedelta | None = None  # 无「可观察进展」的最长时间
    refresh_on: Literal["auto", "heartbeat"] = "auto"
    # "auto"：标准图进展信号 + 显式心跳都刷新；"heartbeat"：只认 runtime.heartbeat()
```

`coerce()` 类方法把 `float/timedelta/TimeoutPolicy/None` 归一为「正秒数浮点」的 frozen 策略（已归一的实例走 fast path 原样返回——frozen 所以可安全共享；两个超时都为 None 视为无策略；`refresh_on` 非法值报错）。

三个实操结论：

1. **数字/timedelta 形式的 `timeout=` 参数一律解释为 `run_timeout`（硬上限）**。想要「长时间但有进展就不杀」的语义，必须显式用 `TimeoutPolicy(idle_timeout=..., refresh_on="auto")`；长跑且不自然产生回调事件的工作，要在循环里调 `runtime.heartbeat()`（`@task`/`entrypoint` docstring 均点名此机制；`_constants.py` 有配套注入键 `CONFIG_KEY_TIMED_ATTEMPT_OBSERVER`）；
2. **协作式取消**：超时依赖 asyncio cancellation，节点里同步 `time.sleep()`/CPU 密集循环持有 GIL 时，超时要等事件循环重新拿到控制权才 fire——**超时不是抢占式的**，别拿它当硬隔离；
3. **sync 一律不支持**（`_internal/_timeout.py`）：

```python
_SYNC_TIMEOUT_PREFIX = (
    "Node timeouts are only supported for async nodes because sync Python "
    "execution cannot be safely cancelled in-process."
)

def coerce_timeout_policy(value): return TimeoutPolicy.coerce(value)

def sync_timeout_unsupported(name, *, kind="Node"):
    return ValueError(f"{_SYNC_TIMEOUT_PREFIX} {kind} {name!r} is sync.")
```

`@task` 的 decorator 与 `_call_with_options` 各有一道同样的闸（`kind="Task"`），`entrypoint` 在编译期把 timeout 挂到 `PregelNode(timeout=...)`。超时触发后抛 `NodeTimeoutError`，**是否重试交回 retry_policy 决定**（默认策略下会重试，见 8.2/12.1）。

## 13. Future 桥接：@task 并行的底层原理

`@task` 返回的 `SyncAsyncFuture` 为什么既能 `.result()` 又能 `await`？答案在 `pregel/_call.py` 与 `_internal/_future.py`。

```python
# pregel/_call.py
class SyncAsyncFuture(Generic[T], concurrent.futures.Future[T]):
    def __await__(self) -> Generator[T, None, T]:
        yield cast(T, ...)
```

解析：它就是一个 `concurrent.futures.Future`（sync 侧 `.result()` 天然可用），外加一个「yield 一次」的 `__await__`——await 它时协程挂起并把控制权交还 Pregel 的异步 runner，runner 泵动任务队列、完成后 set_result，协程恢复时拿到值。**同一个对象双栖 sync/async 两种收集方式**，这就是 `asyncio.gather(*futures)` 能直接收 `@task` future 的原因（async task 需要 Python ≥3.11 也是这套泵送机制的版本要求）。

`_internal/_future.py` 提供跨线程/跨事件循环的桥接原语（注释自述 adapted from `asyncio.run_coroutine_threadsafe`）：

```python
def _chain_future(source: AnyFuture, destination: AnyFuture) -> None:
    """Chain two futures so that when one completes, so does the other.

    The result (or exception) of source will be copied to destination.
    If destination is cancelled, source gets cancelled too.
    Compatible with both asyncio.Future and concurrent.futures.Future.
    """
    ...
    def _call_check_cancel(destination):        # 反向：目标被取消 → 取消源
        if destination.cancelled():
            if source_loop is None or source_loop is dest_loop:
                source.cancel()
            else:
                source_loop.call_soon_threadsafe(source.cancel)

    def _call_set_state(source):                # 正向：源完成 → 复制状态到目标
        if dest_loop is None or dest_loop is source_loop:
            _set_state(destination, source)
        else:
            dest_loop.call_soon_threadsafe(_set_state, destination, source)

    destination.add_done_callback(_call_check_cancel)
    source.add_done_callback(_call_set_state)
```

要点：

- **双向联动**：结果/异常正向复制，取消反向传播；跨事件循环时用 `call_soon_threadsafe` 保证线程安全，目标 loop 已关闭时静默放弃（防止关闭竞态炸日志）；
- **异常类型翻译**（`_convert_future_exc`）：`concurrent.futures.CancelledError/TimeoutError/InvalidStateError` → 对应 asyncio 类型，两个 Future 世界的异常语义在此对齐；
- **`_ensure_future` 的版本门**：`CONTEXT_NOT_SUPPORTED = sys.version_info < (3, 11)`（context 参数）、`EAGER_NOT_SUPPORTED = < (3, 12)`（`asyncio.eager_task_factory`，lazy=False 时任务立即同步起跑，省一次调度往返）；
- **`run_coroutine_threadsafe`**：目标 loop 就是当前 loop 时直接 `_ensure_future`，否则先建 future 再 `call_soon_threadsafe` 挂链——这是 sync 图在内部线程池里驱动 async 组件（如异步 checkpointer）的通道。

### 14.2 `merge_configs`：五键各有合并语义

```python
def merge_configs(*configs: RunnableConfig | None) -> RunnableConfig:
    base: RunnableConfig = {}
    for config in configs:
        if config is None: continue
        for key, value in config.items():
            if not value: continue                    # 假值直接跳过
            if key == "metadata":
                base[key] = _merge_metadata(base.get(key), value)
            elif key == "tags":
                base[key] = [*base[key], *value] if base.get(key) else value   # 拼接
            elif key == CONF:                          # "configurable"
                base[key] = {**base[key], **value} if base.get(key) else value # 浅合并，后者胜
            elif key == "callbacks":
                base["callbacks"] = _merge_callbacks(base.get("callbacks"), value)
            elif key == "recursion_limit":
                if config["recursion_limit"] != DEFAULT_RECURSION_LIMIT:
                    base["recursion_limit"] = config["recursion_limit"]
            else:
                base[key] = config[key]
    if CONF not in base: base[CONF] = {}
    return base
```

解析四个非平凡点：

1. **`metadata` 深一层合并**（`_merge_metadata`）：顶层键新者胜；**只有 `lc_versions` 例外地再深合并一层**（让各 LangChain 包各自贡献版本号而不互相覆盖）；mapping 值做一层拷贝防共享可变引用——注释特意警告「intentionally more defensive — do not "simplify" back to a shared ref」，且要求与 langchain_core 的同名函数保持同步；
2. **`callbacks` 六路合并**（`_merge_callbacks`，3 种 base × 2 种 new）：list+list 拼接；list 与 `BaseCallbackManager` 相遇时把散的 handler `add_handler(cb, inherit=True)` 收编进 manager 副本；manager+manager 走 `base.merge(new)`——**合并永远产生副本，不改入参**；
3. **`recursion_limit` 的「默认值不覆盖」规则**：等于 `DEFAULT_RECURSION_LIMIT` 的值在合并时被跳过——防止下游自动注入的默认上限悄悄覆盖上游显式设置的小限额；
4. `tags` 拼接、`configurable` 浅合并后者胜。

|------|----|------|
| `INPUT` | `__input__` | 图输入值 |
| `INTERRUPT` | `__interrupt__` | 节点动态抛出的中断 |
| `RESUME` | `__resume__` | 恢复中断的值（interrupt() 路径②写回） |
| `ERROR` / `ERROR_SOURCE_NODE` | `__error__` / `__error_source_node__` | 节点错误及来源节点名（节点级 error_handler 用） |
| `NO_WRITES` | `__no_writes__` | 标记节点什么都没写 |
| `TASKS` | `__pregel_tasks` | Send 对象产生的任务 |
| `RETURN` | `__return__` | 单纯记录 task 返回值 |
| `PREVIOUS` | `__previous__` | 函数式 API 的存档通道（见 2.3） |
| `CACHE_NS_WRITES` | `__pregel_ns_writes` | 节点写入缓存的命名空间（`_TaskFunction.clear_cache` 用它） |

**`config.configurable` 注入键**（运行时把能力经 config 注入节点，节选）：

| 常量 | 注入内容 |
|------|---------|
| `CONFIG_KEY_SEND` / `CONFIG_KEY_READ` / `CONFIG_KEY_CALL` | write 函数 / 读当前状态副本 / **task 调度函数（@task 的落点）** |
| `CONFIG_KEY_CHECKPOINTER` / `CONFIG_KEY_STREAM` / `CONFIG_KEY_CACHE` | 父图传给子图的 checkpointer / 流协议（RemoteGraph 转发靠它）/ 缓存 |
| `CONFIG_KEY_SCRATCHPAD` | **任务级可变暂存区（interrupt 计数与 resume 配对的家）** |
| `CONFIG_KEY_RUNTIME` | `Runtime` 实例（context/store/stream_writer/heartbeat） |
| `CONFIG_KEY_TASK_ID` / `CONFIG_KEY_THREAD_ID` / `CONFIG_KEY_CHECKPOINT_ID` / `CONFIG_KEY_CHECKPOINT_NS` / `CONFIG_KEY_CHECKPOINT_MAP` | 执行坐标五元组 |
| `CONFIG_KEY_RESUMING` / `CONFIG_KEY_RESUME_MAP` / `CONFIG_KEY_REPLAY_STATE` | 恢复/重放相关 |
| `CONFIG_KEY_DURABILITY` | `"sync" / "async" / "exit"`（对应 `Durability` 类型：检查点同步落盘/异步落盘/退出才落盘） |
| `CONFIG_KEY_NODE_ERROR` | 节点级 error_handler 的 `NodeError` 注入 |
| `CONFIG_KEY_TIMED_ATTEMPT_OBSERVER` | idle 超时观测回调（heartbeat 刷新链路） |

**结构常量**：`PUSH`/`PULL`（Send 任务 vs 边触发任务，见 4.2）、`NS_SEP="|"`（checkpoint_ns 层级分隔）、`NS_END=":"`（层内 ns 与 task_id 分隔）、`CONF="configurable"`、`NULL_TASK_ID`（无关联任务写入的占位 task id）、`OVERWRITE="__overwrite__"`、`_CHECKPOINT_COORDINATE_KEYS`（14.3 的坐标重置判据）、`RESERVED`（全部保留键集合，校验用户键名冲突用）。

顺带两个 types.py 里的相关类型：`Durability = Literal["sync", "async", "exit"]`（sync=下一步开始前同步落盘；async=与下一步并行落盘；exit=仅退出时落盘）与 `Overwrite`（绕过 reducer 直写 `BinaryOperatorAggregate` 通道，同 superstep 多个 Overwrite 写同一通道 → `InvalidUpdateError`；其 `type="__overwrite__"` 判别字段专为「dataclass 被 JSON 序列化后类型丢失」的场景保留——例如经 LangGraph API server 转发的 orjson 编码更新）。

## 15. 完整代码示例（3 个场景）

### 场景一：@entrypoint + @task 基础（并行 + previous + interrupt/HITL）

```python
"""函数式 API 综合示例：并行 task、跨轮记忆、人审中断与恢复。"""
import time
from typing import Any

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint, task
from langgraph.types import Command, RetryPolicy, interrupt

checkpointer = InMemorySaver()

@task(retry_policy=RetryPolicy(max_attempts=5, initial_interval=0.2))
def fetch_score(subject: str) -> int:
    time.sleep(0.5)                       # 模拟 IO；放 task 里 → resume 重放不重跑
    return {"math": 91, "english": 78}[subject]

@entrypoint(checkpointer=checkpointer)
def grade_report(
    subjects: list[str],
    *,
    previous: dict[str, Any] | None = None,   # 注入：上一轮的存档
) -> dict[str, Any]:
    futures = [fetch_score(s) for s in subjects]     # 先发 → 并行
    scores = {s: f.result() for s, f in zip(subjects, futures)}  # 后收

    history = (previous or {}).get("history", [])
    history = [*history, scores]

    # 人审：低于 80 分的科目需要人工确认是否放行
    failed = [s for s, v in scores.items() if v < 80]
    if failed:
        decision = interrupt({"question": f"{failed} 不及格，放行吗？", "scores": scores})
        if decision != "pass":
            return {"status": "blocked", "scores": scores, "history": history}

    return {"status": "ok", "scores": scores, "history": history}

if __name__ == "__main__":
    config = {"configurable": {"thread_id": "grade-1"}}

    # 第一轮：math 及格，直接完成
    print(grade_report.invoke(["math"], config))
    # {'status': 'ok', 'scores': {'math': 91}, 'history': [{'math': 91}]}

    # 第二轮：english 不及格 → 挂起在 interrupt（fetch_score 不会因 resume 重跑）
    for chunk in grade_report.stream(["english"], config):
        print(chunk)
    # ... {'__interrupt__': (Interrupt(value={'question': "['english'] 不及格...", ...}, id='...'),)}

    # 人工放行 → 恢复；previous 里能看到第一轮的 history
    result = grade_report.invoke(Command(resume="pass"), config)
    print(result)
    # {'status': 'ok', 'scores': {'english': 78}, 'history': [{'math': 91}, {'english': 78}]}
```

覆盖点：`@task` 先发后收并行、task 级 `retry_policy`、`previous` 跨轮记忆、`interrupt` + `Command(resume)`、resume 重放时 task 结果缓存。

### 场景二：Send 动态扇出（map-reduce 并行检索汇总）

```python
"""模拟 NL2SQL 风格的多库并行探查 + 汇总：Send 动态扇出。"""
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Send

class OverallState(TypedDict):
    question: str
    db_names: list[str]
    findings: Annotated[list[dict], operator.add]   # 并行写入必须给 reducer

def plan(state: OverallState):
    # 条件边函数：运行时才知道扇出几路、每路带什么私有输入
    return [Send("probe_db", {"db": db, "question": state["question"]})
            for db in state["db_names"]]

def probe_db(payload: dict) -> dict:                # 收到的是 Send 的 arg，不是 OverallState
    db, q = payload["db"], payload["question"]
    return {"findings": [{"db": db, "tables": [f"{db}_orders", f"{db}_users"]}]}

def reduce_findings(state: OverallState) -> dict:
    dbs = [f["db"] for f in state["findings"]]
    return {"findings": [{"summary": f"候选库: {dbs}"}]}

builder = StateGraph(OverallState)
builder.add_node("probe_db", probe_db)
builder.add_node("reduce_findings", reduce_findings)
builder.add_conditional_edges(START, plan)          # START → N 个并行 probe_db
builder.add_edge("probe_db", "reduce_findings")     # 全部 probe 完成后进入 reduce
builder.add_edge("reduce_findings", END)
graph = builder.compile()

out = graph.invoke({"question": "上月工时报工量", "db_names": ["wit", "aix", "imdb"]})
print(out["findings"][-1])
# {'summary': "候选库: ['wit', 'aix', 'imdb']"}
```

覆盖点：`Send` 列表扇出、per-Send 私有载荷（schema 外形状）、reducer 汇聚、`INVALID_CONCURRENT_GRAPH_UPDATE` 的规避（`Annotated[..., operator.add]`）。变体：把 `plan` 的逻辑搬进任意节点并 `return Command(goto=[Send("probe_db", {...}), ...])`，即「节点自扇出」，无需条件边。

### 场景三：Command 路由控制（goto + update + 父图通信）

```python
"""Command 三合一：状态更新、动态路由、子图 → 父图通信。"""
import operator
from typing import Annotated, Literal, TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command

class State(TypedDict):
    messages: Annotated[list, operator.add]
    risk_level: str | None

# ---------- 子图：风控检查 ----------
class SubState(TypedDict):
    messages: Annotated[list, operator.add]

def risk_check(state: SubState) -> Command[Literal["__end__"]]:
    text = str(state["messages"][-1])
    if "转账" in text:
        # graph=PARENT：命令冒泡给父图 —— 更新父图状态并跳到父图的 human_review 节点
        return Command(
            graph=Command.PARENT,
            update={"risk_level": "high", "messages": ["[子图] 检测到高风险操作"]},
            goto="human_review",
        )
    return Command(update={"messages": ["[子图] 无风险"]}, goto=END)

sub = StateGraph(SubState)
sub.add_node("risk_check", risk_check)
sub.add_edge(START, "risk_check")
subgraph = sub.compile()

# ---------- 父图 ----------
def agent(state: State):
    return {"messages": [f"处理请求: {state['messages'][-1]}"]}

def human_review(state: State) -> Command[Literal["execute", "__end__"]]:
    # 动态路由：无静态出边，去向完全由返回值决定
    if state.get("risk_level") == "high":
        return Command(goto="execute", update={"messages": ["[人审] 批准执行"]})
    return Command(goto=END, update={"messages": ["[人审] 拒绝"]})

def execute(state: State):
    return {"messages": ["已执行"]}

parent = StateGraph(State)
parent.add_node("agent", agent)
parent.add_node("risk", subgraph)          # 子图作为节点
parent.add_node("human_review", human_review)
parent.add_node("execute", execute)
parent.add_edge(START, "agent")
parent.add_edge("agent", "risk")
graph = parent.compile(checkpointer=InMemorySaver())

out = graph.invoke(
    {"messages": ["帮我转账 1 万元"]},
    {"configurable": {"thread_id": "cmd-demo"}},
)
print(out["risk_level"], "|", out["messages"])
# high | ['帮我转账 1 万元', '处理请求: ...', '[子图] 检测到高风险操作', '[人审] 批准执行', '已执行']
```

覆盖点：节点返回 `Command(update + goto)` 原子组合、`Command(graph=Command.PARENT)` 经 `ParentCommand` 冒泡改写父图状态并路由父图节点（底层机制即子图 `Command.PARENT` 场景，远程子图走 SSE `command` 事件同构实现）、`Command[Literal[...]]` 泛型标注路由白名单、无静态出边的纯动态路由节点。

## 16. 常见陷阱与最佳实践总结

**装饰器层**

1. `@entrypoint` **必须带括号**；`@entrypoint`（裸用）会把函数误当 checkpointer，得到 entrypoint 实例而非图。
2. 入口函数**必须有且仅以第一个参数为输入**（多参数打包成 dict）；**生成器函数不支持**（用 `runtime.stream_writer` 做自定义流式）。
3. `@task` **只能在 entrypoint / StateGraph 节点内部调用**（依赖 contextvar 里的 `__pregel_call`）；开 checkpointer 后 task 入参/返回值必须可序列化。
4. 并行范式 = **先发后收**；在推导式里顺手 `.result()` 会退化为串行。async task 需 Python ≥ 3.11。
5. resume 时 entrypoint **函数体从头重放**：副作用必须包在 `@task` 里或放在 `interrupt()` 之后，否则每次恢复都重复执行。

**控制流层**

6. `interrupt()` 必须有 checkpointer；`GraphInterrupt` 被根图抑制——**不要 try/except 它**，读 `__interrupt__` 流事件 / `GraphOutput.interrupts` / `state.tasks[].interrupts`。
7. 多个并行中断用 `Command(resume={interrupt_id: value})` 精确投递；`Interrupt.id` 是 checkpoint_ns 的 xxh3 哈希，重放稳定。
8. `Send` 扇出的汇聚字段**必须带 reducer**，否则 `InvalidUpdateError(INVALID_CONCURRENT_GRAPH_UPDATE)`。
9. `jump_to` 是 langchain agent 中间件层的约定（`Literal["tools","model","end"]` + `can_jump_to` 白名单），**langgraph 1.2.9 的 Command 没有该字段**；原生等价物是 `Command(goto=...)`。
10. `GraphDelegate` 在 1.2.9 已不存在（0.x 遗留），迁移时改捕 `GraphBubbleUp` / `TaskNotFound` / `GraphDrained`。

**运维层**

11. 超时只对 **async** 节点/task 生效；`timeout=30` 是硬 `run_timeout`，「有进展就不杀」要用 `TimeoutPolicy(idle_timeout=..., refresh_on=...)` + `runtime.heartbeat()`；超时是协作式取消，同步阻塞 GIL 的代码会让它迟到。
12. `NodeTimeoutError` 默认**会被重试**（它故意不继承 `TimeoutError/OSError`）；不想重试就显式 `RetryPolicy(retry_on=...)` 排除。
13. langgraph 1.2.9 默认 `recursion_limit=10007`（env `LANGGRAPH_DEFAULT_RECURSION_LIMIT` 可调）——`GraphRecursionError` 出现基本等于真死循环。
14. `update_state(as_node=...)` 决定「站在哪个节点之后」推导 next；`as_node="__start__"` 会造成「幽灵 next」（本项目实测坑），排查丢步要结合 `tasks[].result/error` 而非只看 `state.next`。
15. RemoteGraph 发出的 config 会被清洗（只留原语、丢弃 checkpoint 坐标四键）；独立调用时远程中断不抛异常、只在 updates 数据里；`invoke` 收不到任何事件会返回 `None`（调用侧防御）。
16. 弃用警告默认不可见：CI 用 `-W error::DeprecationWarning` 暴露 `LangGraphDeprecatedSinceV05/V10/V11`，是大版本升级前最便宜的迁移检查。
