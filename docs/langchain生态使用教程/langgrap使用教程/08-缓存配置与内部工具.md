## 1. Cache 系统概述

**源码位置**：`langgraph/cache/{base,memory,redis,sqlite}/__init__.py`

LangGraph 的 Cache 系统解决的核心问题是：**同一个节点在相同输入下被重复执行时，跳过执行、直接复用上一次的"写入结果"**。典型收益场景：

- **省模型调用**：一个节点内部调 LLM（问数、摘要、翻译），相同问题重复进来时不必再花钱花时间调模型；
- **确定性重放/时间旅行**：从旧 checkpoint 重放时，命中缓存的节点不再产生副作用；
- **调试迭代**：改图结构重跑时，未受影响节点直接命中缓存。

设计上必须澄清一个常见误解：**LangGraph 的 cache 不是"LLM 响应缓存"，而是"节点写入（node writes）缓存"**。缓存的 value 是节点执行后产出的 `writes`（通道写入列表 `list[tuple[str, Any]]`），key 由 `CachePolicy.key_func(节点输入)` 派生。由于节点的模型调用发生在节点体内，缓存节点写入**等价于**缓存了这次模型调用的效果——这就是官方文档所谓"model call caching"的实质。

架构分两层：

| 层 | 组件 | 职责 |
|---|---|---|
| 存储层 | `BaseCache` 及三个实现 | 只管 `get/set/clear`（键值 + TTL），不知道任何图语义 |
| 策略层 | `CachePolicy`（`langgraph/types.py`）+ Pregel loop | 决定"哪个节点、用什么 key、TTL 多少"，在执行循环里做命中匹配与回填 |

存储层的键统一是二元组 `FullKey = (Namespace, str)`，其中 `Namespace = tuple[str, ...]`。Pregel 用命名空间把缓存隔离到"节点粒度"（见第 6 章），`clear(namespaces)` 因此可以精确清某个节点的缓存。

三个实现的选型速记：

| 实现 | 持久化 | 跨进程共享 | TTL | 适用 |
|---|---|---|---|---|
| `InMemoryCache` | ✗ | ✗ | ✓（惰性过期） | 单进程开发/测试 |
| `RedisCache` | ✓（Redis 侧） | ✓ | ✓（原生 `SETEX`） | 多副本分布式部署 |
| `SqliteCache` | ✓（本地文件） | 同机多进程 | ✓（惰性过期） | 单机持久化、重启不丢 |

## 2. BaseCache 基类

**源码**：`langgraph/cache/base/__init__.py`（全文 48 行）

```python
ValueT = TypeVar("ValueT")
Namespace = tuple[str, ...]
FullKey = tuple[Namespace, str]


class BaseCache(ABC, Generic[ValueT]):
    """Base class for a cache."""

    serde: SerializerProtocol = JsonPlusSerializer(pickle_fallback=False)

    def __init__(self, *, serde: SerializerProtocol | None = None) -> None:
        """Initialize the cache with a serializer."""
        self.serde = serde or self.serde

    @abstractmethod
    def get(self, keys: Sequence[FullKey]) -> dict[FullKey, ValueT]: ...
    @abstractmethod
    async def aget(self, keys: Sequence[FullKey]) -> dict[FullKey, ValueT]: ...
    @abstractmethod
    def set(self, pairs: Mapping[FullKey, tuple[ValueT, int | None]]) -> None: ...
    @abstractmethod
    async def aset(self, pairs: Mapping[FullKey, tuple[ValueT, int | None]]) -> None: ...
    @abstractmethod
    def clear(self, namespaces: Sequence[Namespace] | None = None) -> None: ...
    @abstractmethod
    async def aclear(self, namespaces: Sequence[Namespace] | None = None) -> None: ...
```

**逐点解析**：

1. **接口是"批量"的**。`get` 收一个 key 序列、返回"命中的那部分"字典——未命中的 key 直接不出现在结果里，调用方靠 `dict` 缺键判断 miss。`set` 收 `Mapping[FullKey, (value, ttl)]`，TTL 单位秒、`None` 表示永不过期。这套批量签名是为 Pregel 的一个 superstep 里**并行多任务**设计的：一步之内所有待执行任务可以合成一次 `cache.get(keys)`，Redis 实现因此能用一条 `MGET` 打完（见第 4 章）。

2. **同步 + 异步双份抽象方法**。子类必须两两实现；三个内置实现里只有 `SqliteCache` 的异步版是真异步（`asyncio.to_thread` 包同步版），`InMemoryCache`/`RedisCache` 的 `aget/aset/aclear` 都是直接委托同步版。

3. **序列化器是类属性默认值 + 实例覆盖**：`serde: SerializerProtocol = JsonPlusSerializer(pickle_fallback=False)`。复用 checkpoint 体系的 `JsonPlusSerializer`（能序列化 LangChain 消息、datetime、dataclass、Pydantic 模型等），且**显式关掉 pickle 回退**——缓存内容可能落 Redis/SQLite 等进程外存储，禁 pickle 是防反序列化任意对象的安全默认。想缓存不可 JSON 化对象时需自己传 `serde=JsonPlusSerializer(pickle_fallback=True)` 并承担风险。

4. **注意没有 `delete` 单键方法**。抽象接口只有 `clear(namespaces)`：不传 namespaces 清空全部，传了按命名空间整段清。这与 Pregel 的使用模式一致——缓存条目靠 TTL 自然死亡，人工清理按"节点"粒度进行（`Pregel.clear_cache(nodes=[...])`，见第 6 章）。

自定义后端（如 Memcached、数据库表）只需继承 `BaseCache` 实现这六个方法即可插入 Pregel。

## 3. InMemoryCache（内存缓存）

**源码**：`langgraph/cache/memory/__init__.py`（全文 73 行）

```python
class InMemoryCache(BaseCache[ValueT]):
    def __init__(self, *, serde: SerializerProtocol | None = None):
        super().__init__(serde=serde)
        self._cache: dict[Namespace, dict[str, tuple[str, bytes, float | None]]] = {}
        self._lock = threading.RLock()

    def get(self, keys: Sequence[FullKey]) -> dict[FullKey, ValueT]:
        with self._lock:
            if not keys:
                return {}
            now = datetime.datetime.now(datetime.timezone.utc).timestamp()
            values: dict[FullKey, ValueT] = {}
            for ns_tuple, key in keys:
                ns = Namespace(ns_tuple)
                if ns in self._cache and key in self._cache[ns]:
                    enc, val, expiry = self._cache[ns][key]
                    if expiry is None or now < expiry:
                        values[(ns, key)] = self.serde.loads_typed((enc, val))
                    else:
                        del self._cache[ns][key]   # 惰性删除过期条目
            return values

    def set(self, keys: Mapping[FullKey, tuple[ValueT, int | None]]) -> None:
        with self._lock:
            now = datetime.datetime.now(datetime.timezone.utc)
            for (ns, key), (value, ttl) in keys.items():
                expiry = (now + datetime.timedelta(seconds=ttl)).timestamp() if ttl is not None else None
                self._cache.setdefault(ns, {})[key] = (*self.serde.dumps_typed(value), expiry)
```

**解析**：

- **两级字典**：外层按 `Namespace`（元组直接做 dict key），内层 `key -> (encoding, bytes, expiry_ts)`。存的是**序列化后的字节**而非原对象——即使纯内存缓存也走一遍 `dumps_typed/loads_typed`。这有两个作用：① 与 Redis/SQLite 实现行为完全一致（避免"内存版能存、落盘版炸"的实现偏差）；② `loads_typed` 每次返回新对象，天然防止调用方拿到缓存对象后原地修改污染缓存。
- **过期策略是"惰性删除"（lazy expiration），没有 LRU**。⚠️ 这一点必须纠正一个流传很广的说法：1.2.9 的 `InMemoryCache` **不存在 LRU 淘汰、也没有容量上限**——条目只在 `get` 命中且发现过期时才被 `del`；一个再也不被查询的过期键会永远占着内存。长期运行且 key 基数大的服务，要么给所有写入配 TTL 并接受"死键驻留"，要么换 `SqliteCache`/`RedisCache`（后者由 Redis 的主动过期机制回收）。
- **线程安全**：一把 `threading.RLock()` 罩住 get/set/clear。Pregel 同步执行器用线程池并行跑任务，这把锁保证共享缓存不互踩（与本仓 MEMORY 中"SQLite 共享连接 + 一把锁，读也要进锁"的教训同款思路）。
- **异步方法是同步直通**：`aget` 就是 `return self.get(keys)`。纯内存操作微秒级，不会卡事件循环，可以接受。

## 4. RedisCache（Redis 缓存与分布式场景）

**源码**：`langgraph/cache/redis/__init__.py`（全文 144 行）

```python
class RedisCache(BaseCache[ValueT]):
    """Redis-based cache implementation with TTL support."""

    def __init__(self, redis: Any, *, serde: SerializerProtocol | None = None,
                 prefix: str = "langgraph:cache:") -> None:
        super().__init__(serde=serde)
        self.redis = redis
        self.prefix = prefix

    def _make_key(self, ns: Namespace, key: str) -> str:
        ns_str = ":".join(ns) if ns else ""
        return f"{self.prefix}{ns_str}:{key}" if ns_str else f"{self.prefix}{key}"

    def get(self, keys: Sequence[FullKey]) -> dict[FullKey, ValueT]:
        if not keys:
            return {}
        redis_keys = [self._make_key(ns, key) for ns, key in keys]
        try:
            raw_values = self.redis.mget(redis_keys)     # 一次 MGET 批量取
        except Exception:
            return {}                                     # Redis 不可用 → 视为全 miss
        values: dict[FullKey, ValueT] = {}
        for i, raw_value in enumerate(raw_values):
            if raw_value is not None:
                try:
                    encoding, data = raw_value.split(b":", 1)
                    values[keys[i]] = self.serde.loads_typed((encoding.decode(), data))
                except Exception:
                    continue                              # 跳过损坏条目
        return values

    def set(self, mapping: Mapping[FullKey, tuple[ValueT, int | None]]) -> None:
        if not mapping:
            return
        pipe = self.redis.pipeline()                      # pipeline 批量写
        for (ns, key), (value, ttl) in mapping.items():
            redis_key = self._make_key(ns, key)
            encoding, data = self.serde.dumps_typed(value)
            serialized_value = f"{encoding}:".encode() + data   # "encoding:data"
            if ttl is not None:
                pipe.setex(redis_key, ttl, serialized_value)    # 原生 TTL
            else:
                pipe.set(redis_key, serialized_value)
        try:
            pipe.execute()
        except Exception:
            pass                                          # 静默失败
```

**解析**：

1. **值格式 `encoding:data`**。`serde.dumps_typed(value)` 返回 `(encoding, bytes)` 二元组（encoding 如 `"json"`/`"msgpack"`），Redis 只能存字节串，于是把 encoding 名以 `编码名:` 前缀拼进 value，读回时 `split(b":", 1)` 拆开。这是自描述格式：以后换 serde 也能读旧数据。

2. **键格式 `langgraph:cache:<ns各段用:连接>:<key>`**。`prefix` 可构造时改，作用类似 Redis 的 key 命名空间，便于 `clear` 用 `KEYS prefix*` 圈定范围、也便于和其他业务共用一个 Redis 实例时互不干扰。⚠️ 副作用：`Namespace` 元组里的段**不能含 `:`**，否则 `_parse_key` 反解会错位（Pregel 生成的 namespace 段是节点名和 UUID，一般安全；自定义 key_func/ns 时要留意）。

3. **TTL 交给 Redis 原生 `SETEX`**，不像内存/SQLite 那样惰性过期——这是分布式场景最省心的一点：过期键由 Redis 主动回收，不留死键。

4. **全面 fail-open（静默降级）**。`get` 异常返回 `{}`（当作全 miss，节点照常执行）、`set` 异常 `pass`（写缓存失败不影响主流程）、单条反序列化失败 `continue`。**缓存永远只是加速器，挂了退化为"没缓存"，绝不让缓存故障放大成业务故障**——这是缓存层最重要的工程纪律，RedisCache 是三个实现里贯彻得最彻底的。

5. **批量友好**：读一条 `MGET`、写一条 `pipeline`，把一个 superstep 内 N 个任务的缓存操作压成 2 次往返。

6. **⚠️ 两个使用注意**：
   - `aget/aset/aclear` 都是直通同步实现。若在 `ainvoke`/`astream` 异步链路中使用，传入的必须是**同步 redis 客户端**（`redis.Redis`），且这些调用会**阻塞事件循环**——对低延迟 Redis 通常可忍，高延迟网络要评估；传 `redis.asyncio.Redis` 反而会因为 `mget` 返回 coroutine 而直接失效（返回空）。
   - `clear()` 用 `KEYS pattern` 扫全库，`KEYS` 是 O(N) 阻塞命令，生产大库上慎用（官方 Redis 文档建议改 `SCAN`）。清缓存是低频运维操作，一般可接受，但别放进热路径。

## 5. SqliteCache（持久化缓存）

**源码**：`langgraph/cache/sqlite/__init__.py`（全文 120 行）

```python
class SqliteCache(BaseCache[ValueT]):
    """File-based cache using SQLite."""

    def __init__(self, *, path: str, serde: SerializerProtocol | None = None) -> None:
        super().__init__(serde=serde)
        self._conn = sqlite3.connect(path, check_same_thread=False)
        # Serialize access to the shared connection across threads
        self._lock = threading.RLock()
        # Better concurrency & atomicity
        self._conn.execute("PRAGMA journal_mode=WAL;")
        self._conn.execute(
            """CREATE TABLE IF NOT EXISTS cache (
                ns TEXT, key TEXT, expiry REAL,
                encoding TEXT NOT NULL, val BLOB NOT NULL,
                PRIMARY KEY (ns, key)
            )"""
        )
        self._conn.commit()

    def get(self, keys: Sequence[FullKey]) -> dict[FullKey, ValueT]:
        with self._lock, self._conn:
            now = datetime.datetime.now(datetime.timezone.utc).timestamp()
            placeholders = ",".join("(?, ?)" for _ in keys)
            params = []
            for ns_tuple, key in keys:
                params.extend((",".join(ns_tuple), key))
            cursor = self._conn.execute(
                f"SELECT ns, key, expiry, encoding, val FROM cache WHERE (ns, key) IN ({placeholders})",
                tuple(params))
            ...
            for ns, key, expiry, encoding, raw in rows:
                if expiry is not None and now > expiry:
                    self._conn.execute("DELETE FROM cache WHERE (ns, key) = (?, ?)", (ns, key))
                    continue        # 读到过期条目 → 顺手删掉
                values[(tuple(ns.split(",")), key)] = self.serde.loads_typed((encoding, raw))
            return values

    async def aget(self, keys): return await asyncio.to_thread(self.get, keys)
```

**解析**：

- **表结构**：`(ns TEXT, key TEXT, expiry REAL, encoding TEXT, val BLOB)`，联合主键 `(ns, key)`。namespace 元组以**逗号连接**压平成一列（与 Redis 用 `:` 类似）；`expiry` 存 UTC 时间戳，`NULL` 表示永不过期。
- **构造时即建表 + WAL**：`PRAGMA journal_mode=WAL` 提升"多读一写"并发；`check_same_thread=False` + `threading.RLock` 是**共享单连接、所有读写都进锁**的模式——和本仓 MEMORY 里 `sqlite-shared-conn-lock-all-access.md` 记录的教训完全同构（并发读同一连接也会互踩，所以**读也要拿锁**）。`with self._lock, self._conn` 双上下文：锁保线程安全，连接上下文保事务提交/回滚。
- **批量读用行值构造器** `WHERE (ns, key) IN ((?,?),(?,?),...)`，一条 SQL 查完整个 superstep 的 keys；**惰性过期**：读到过期行当场 `DELETE`（与 InMemoryCache 同策略，同样没有后台清扫，死键会驻留文件直到被再次读到）。
- **异步是真卸载**：`aget/aset/aclear` 用 `asyncio.to_thread` 把 SQLite I/O 丢到线程池，不阻塞事件循环——三个实现中异步语义最正确的一个。
- **持久化价值**：进程重启缓存不丢。配合 `Pregel.compile(cache=SqliteCache(path=...))`，开发期反复重启调试时，昂贵节点（LLM 调用）跨重启命中。⚠️ 与本仓 MEMORY `sqlite-store-one-dir-per-store.md` 的经验一致：SQLite 文件要放**每环境独立**的路径（容器内注意 bind mount / 卷），并留意 `-wal`/`-shm` 伴生文件。
- `__del__` 里尽力关连接，异常吞掉——析构期抛错没有意义。

## 6. Cache 在 Pregel 中的使用：如何启用节点缓存

存储层只是"傻 KV"，真正让缓存生效的是三个协作组件：**`CachePolicy`（策略）→ `_algo.py`（造 key）→ `_loop.py`（命中/回填）**。

### 6.1 CachePolicy 与默认 key 函数

`langgraph/types.py`：

```python
@dataclass(**_DC_KWARGS)   # kw_only, slots, frozen
class CachePolicy(Generic[KeyFuncT]):
    """Configuration for caching nodes."""

    key_func: KeyFuncT = default_cache_key
    """Function to generate a cache key from the node's input.
    Defaults to hashing the input with pickle."""

    ttl: int | None = None
    """Time to live for the cache entry in seconds. If None, the entry never expires."""
```

默认 key 函数在 `langgraph/_internal/_cache.py`（全文 31 行，本仓教程任务清单第 6 项）：

```python
def _freeze(obj: Any, depth: int = 10) -> Hashable:
    if isinstance(obj, Hashable) or depth <= 0:
        return obj                                   # 已可哈希，直接用
    elif isinstance(obj, Mapping):
        # sort keys so {"a":1,"b":2} == {"b":2,"a":1}
        return tuple(sorted((k, _freeze(v, depth - 1)) for k, v in obj.items()))
    elif isinstance(obj, Sequence):
        return tuple(_freeze(x, depth - 1) for x in obj)
    elif hasattr(obj, "tobytes"):                    # numpy / pandas
        return (type(obj).__name__, obj.tobytes(),
                obj.shape if hasattr(obj, "shape") else None)
    return obj


def default_cache_key(*args: Any, **kwargs: Any) -> str | bytes:
    import pickle
    # protocol 5 strikes a good balance between speed and size
    return pickle.dumps((_freeze(args), _freeze(kwargs)), protocol=5, fix_imports=False)
```

**解析**：缓存 key 的本质是"把任意节点输入规范化成可哈希、可比较的字节串"。难点在 dict 无序、list 不可哈希、numpy 数组不可 pickle 高效比较——`_freeze` 递归处理：dict → **排序后的 tuple**（消除键序影响）、序列 → tuple、数组 → `(类名, tobytes(), shape)` 指纹、深度限 10 层防环。最后 `pickle.dumps(protocol=5)` 一次性字节化。protocol 5 支持 out-of-band buffer，对大对象更快。⚠️ 推论：**默认 key 对输入中的随机量（时间戳、uuid）敏感**——输入里带 `datetime.now()` 之类就永远不命中，需要自定义 `key_func` 只挑业务相关字段。

### 6.2 Pregel 造缓存 key：节点粒度的三元命名空间

`pregel/_algo.py`（prepare_single_task，pull 型任务分支）：

```python
cache_policy = proc.cache_policy or cache_policy        # 节点级覆盖图级默认
if cache_policy:
    args_key = cache_policy.key_func(val)               # val = 节点输入
    cache_key = CacheKey(
        (
            CACHE_NS_WRITES,                             # "__pregel_ns_writes"
            (identifier(proc) or "__dynamic__"),         # 节点实现的身份指纹
            name,                                        # 节点名
        ),
        xxh3_128_hexdigest(args_key.encode() if isinstance(args_key, str) else args_key),
        cache_policy.ttl,
    )
else:
    cache_key = None
```

**解析**：

- 缓存命名空间是三元组 `("__pregel_ns_writes", 节点代码身份, 节点名)`。`identifier(proc)` 对节点底层函数/Runnable 取稳定标识——意味着**你改了节点函数的代码，旧缓存自动失效**（namespace 变了），这是非常聪明的防陈旧设计；无法取到身份时用 `"__dynamic__"` 兜底。
- key 本体用 **xxh3 128 位哈希**把 pickle 字节压成定长 hex 串——快、碰撞概率可忽略。
- `Send`（push 型任务）、functional API 的 `Call`、error-handler 任务各有同构代码路径（`_algo.py` 859/1019/1167 行附近），key_func 的入参分别是 `(*call.input[0], **call.input[1])`、`packet.arg`、`failed_task.input`。

### 6.3 命中匹配与回填：`pregel/_loop.py`

```python
def match_cached_writes(self) -> Sequence[PregelExecutableTask]:
    if self.cache is None:
        return ()
    matched = []
    if cached := {
        (t.cache_key.ns, t.cache_key.key): t
        for t in self.tasks.values()
        if t.cache_key and not t.writes          # 只查"还没产出写入"的任务
    }:
        for key, values in self.cache.get(tuple(cached)).items():
            task = cached[key]
            task.writes.extend(values)           # 缓存值 = 上次的 writes，直接灌回任务
            matched.append(task)
    return matched
```

```python
def put_writes(self, task_id: str, writes: WritesT) -> None:
    super().put_writes(task_id, writes)
    if not writes or self.cache is None or not hasattr(self, "tasks"):
        return
    task = self.tasks.get(task_id)
    if task is None or task.cache_key is None:
        return
    self.submit(self.cache.set, {                 # 异步回填，不阻塞执行循环
        (task.cache_key.ns, task.cache_key.key): (task.writes, task.cache_key.ttl)
    })
```

**解析**：每个 tick 计划完任务后、真正执行前，loop 调 `match_cached_writes()` 一次性批量查缓存；命中的任务被直接标记为"已有写入"，**runner 根本不会调度它执行**（`main.py` 2965 行：`for task in loop.match_cached_writes(): loop.output_writes(task.id, task.writes, cached=True)`——注意 `cached=True`，流式输出仍会把命中结果发出去，下游观感与真执行一致）。任务真执行完，`put_writes` 把本次 writes 用 `self.submit`（后台执行器）**异步回填**，缓存写入不拖慢主循环。

## 8. 内部配置系统 `_internal/_config.py`

这是全篇最重要的文件之一（474 行）：LangGraph 对 langchain-core `RunnableConfig` 的**合并、修补、补全、回调装配**全在这里。

### 8.1 模块级默认值【本地补丁】

```python
DEFAULT_RECURSION_LIMIT = int(getenv("LANGGRAPH_DEFAULT_RECURSION_LIMIT", "10007"))
```

### 8.2 merge_configs：多份 config 合一

```python
def merge_configs(*configs: RunnableConfig | None) -> RunnableConfig:
    base: RunnableConfig = {}
    for config in configs:
        if config is None: continue
        for key, value in config.items():
            if not value: continue                    # 空值直接跳过
            if key == "metadata":
                base[key] = _merge_metadata(base.get(key), value)
            elif key == "tags":
                base[key] = [*base[key], *value] if base.get(key) else value   # 拼接
            elif key == CONF:
                base[key] = {**base[key], **value} if base.get(key) else value # 浅合并
            elif key == "callbacks":
                base["callbacks"] = _merge_callbacks(base.get("callbacks"), value)
            elif key == "recursion_limit":
                if config["recursion_limit"] != DEFAULT_RECURSION_LIMIT:
                    base["recursion_limit"] = config["recursion_limit"]        # 见下
            else:
                base[key] = config[key]                # 其余键后者覆盖前者
    if CONF not in base: base[CONF] = {}
    return base
```

**逐键语义**（后面参数赢，但各键"赢"的方式不同）：

- `metadata`：经 `_merge_metadata` 顶层合并，**唯一例外是 `lc_versions` 键多合并一层**（让各 LangChain 包都能贡献自己的版本号）。docstring 特别强调 mapping 值要**复制一层**（"intentionally more defensive — do not 'simplify' back to a shared ref"），防止合并结果与输入共享可变引用。
- `tags`：**列表拼接**而非覆盖——`with_config(tags=["a"])` 绑定的 tag 不会因 invoke 时再传 tags 而丢失。
- `configurable`：浅合并（后者同键覆盖）。
- `callbacks`：`_merge_callbacks` 处理 `None / list / BaseCallbackManager` 的 3×2 共六种组合——list+list 拼接、manager+list 逐个 `add_handler(inherit=True)`、manager+manager 用 `merge()`，其余组合 `NotImplementedError`。
- `recursion_limit` 有一处反直觉逻辑：**等于默认值的 recursion_limit 会被忽略**（不写入 base）。意图是"没人显式设置时不要用一个 25/10007 去压掉别处传来的真实设置"，代价是你**无法通过 merge 把 limit 显式改回默认值**。

### 8.3 patch_config / patch_configurable / patch_checkpoint_map

```python
def patch_config(config, *, callbacks=None, recursion_limit=None,
                 max_concurrency=None, run_name=None, configurable=None):
    config = config.copy() if config is not None else {}
    if callbacks is not None:
        # If we're replacing callbacks, we need to unset run_name
        # As that should apply only to the same run as the original callbacks
        config["callbacks"] = callbacks
        config.pop("run_name", None); config.pop("run_id", None)
    if recursion_limit is not None: config["recursion_limit"] = recursion_limit
    if max_concurrency is not None: config["max_concurrency"] = max_concurrency
    if run_name is not None: config["run_name"] = run_name
    if configurable is not None: config[CONF] = {**config.get(CONF, {}), **configurable}
    return config
```

`patch_config` 是**非破坏性单点修补**：copy 后按传入参数逐项覆盖。最精妙的是替换 callbacks 时**连带删掉 `run_name`/`run_id`**——run 名属于原来那棵回调树，换了 handler 还带着旧 run_name 会让新 run 顶着别人的名字出现在追踪里。Pregel 内部大量使用：每个 `seq:step:N` 子运行、每次任务执行前都会 `patch_config(config, callbacks=run_manager.get_child(...))`。

`patch_configurable` 只管 `configurable` 子字典的浅合并（config 为 None 时新建）；`patch_checkpoint_map` 在进入子图前把 `{当前 ns: 当前 checkpoint_id}` 并入 `checkpoint_map`（子图回溯父图 checkpoint 用），数据来自 checkpoint metadata 的 `parents`。

`recast_checkpoint_ns(ns)` 把带 task_id 的运行时命名空间（`node1:uuid|node2:uuid`）还原为稳定命名空间（`node1|node2`）：按 `NS_SEP` 切段、每段截掉 `NS_END` 之后、丢弃纯数字段。

### 8.4 ensure_config：补全 + 环境继承 + 谱系判定

`ensure_config(*configs)` 是节点/Runnable 拿到"完整可用 config"的总入口，逻辑四步：

```python
def ensure_config(*configs: RunnableConfig | None) -> RunnableConfig:
    empty = RunnableConfig(tags=[], metadata=ChainMap(), callbacks=None,
                           recursion_limit=DEFAULT_RECURSION_LIMIT, configurable={})
    if var_config := var_child_runnable_config.get():        # ① 继承环境 contextvar
        empty.update({k: v.copy() if k in COPIABLE_KEYS else v
                      for k, v in var_config.items() if _is_not_empty(v)})
    if empty.get(CONF):                                       # ② 谱系判定【本地补丁增强】
        for config in configs:
            explicit_configurable = (config or {}).get(CONF)
            if not explicit_configurable: continue
            if any(_is_not_empty(explicit_configurable.get(k))
                   for k in _CHECKPOINT_COORDINATE_KEYS):
                empty[CONF] = {}          # 显式指定 thread_id/checkpoint_* → 丢弃环境继承
                break
    for config in configs:                                    # ③ 逐份浅合并
        for k, v in config.items():
            if _is_not_empty(v) and k in CONFIG_KEYS:
                if k == CONF:   empty[k] = {**existing, **v} if existing else v.copy()
                elif k == "callbacks": empty["callbacks"] = _merge_callbacks(...)
                elif k == "metadata":  empty["metadata"] = _merge_metadata(...)
                elif k == "tags":      empty["tags"] = [*existing_tags, *v] ...
                else: empty[k] = v
        for k, v in config.items():                           # ④ 非标准键 → 塞进 configurable
            if _is_not_empty(v) and k not in CONFIG_KEYS:
                empty[CONF][k] = v
    ...
    for key in _PROPAGATE_TO_METADATA:                        # ⑤ 关键 id 回填 metadata
        if key in metadata: continue
        if value := configurable.get(key): metadata[key] = value
    return empty
```

要点解析：

- **① 环境继承**：`var_child_runnable_config` 是 langchain-core 的 contextvar，Pregel 执行节点时已把该任务的 config set 进去（见第 14 章 `set_config_context`）。所以**节点里裸调 `ensure_config()` 也能拿到 thread_id、callbacks**——这是"config 自动透传"魔法的根源。
- **② 谱系判定**：源码注释写得很清楚——如果显式 config 自带 checkpoint 坐标（`thread_id` 或任一 `checkpoint_ns/id/map`），说明调用方在寻址**自己的** checkpoint 谱系，此时把继承来的环境 configurable **整个丢弃**而不是合并覆盖。否则"父图节点里 invoke 一个子图并给它传 thread_id"会把子图 checkpoint 写进父图命名空间下、再也找不回来。**即使显式 thread_id 与环境值相同也要重置**（子图复用父 thread_id 时仍应写自己的根命名空间）。`configurable` 其余键（如【本地补丁】注释里举例的 `ls_agent_type`）保持浅合并，`with_config` 绑定的值不被 invoke 时的部分覆盖丢掉。
- **④ 兜底搬运**：传入 config 里不属于 `CONFIG_KEYS` 的键（用户随手放的自定义键）统一搬进 `configurable`——所以 `graph.invoke(x, {"my_key": 1})` 里 `my_key` 会出现在 `configurable` 中。
- **⑤ metadata 回填**：`_PROPAGATE_TO_METADATA = {thread_id, checkpoint_id, checkpoint_ns, task_id, run_id, assistant_id, graph_id}` 从 configurable 复制进 metadata（metadata 已有则不覆盖），保证追踪/流事件里始终能看到这些身份字段。
- **秘密过滤**：`_get_tracing_metadata_defaults` 把 configurable 里可安全公开的标量作为 **tracer-only** metadata（LangSmith 继承元数据），但 `_exclude_as_metadata` 排除三类键：`__` 开头（框架内部键）、非标量（str/int/float/bool 之外）、以及命中 `_OMIT = ("key", "token", "secret", "password", "auth")` 子串的键（大小写不敏感）——**API key 之类不会被打进追踪 metadata**，这是防泄密设计。
- `filter_to_user_tags(tags)`：滤掉 `seq:step:*` 内部记账 tag（`RunnableSeq` 每步都会打，见第 14 章），`messages`/`tasks` 两种 stream 模式共用它对外呈现干净的 tag 集。

### 8.5 回调管理器装配

`get_callback_manager_for_config(config, tags)` / `get_async_callback_manager_for_config`：把 config 里的 `callbacks + tags + metadata` 装配成 `CallbackManager`。若 callbacks 已经是 Manager 实例就复用（`add_tags`/`add_metadata` 追加），否则 `CallbackManager.configure(inheritable_callbacks=..., inheritable_tags=..., langsmith_inheritable_metadata=_get_tracing_metadata_defaults(config))` 新建。每个节点执行的 tracing（`on_chain_start` 拿 `run_manager`）都从这里出发。

## 9. 字段处理 `_internal/_fields.py`

213 行，职责：**从状态 schema（TypedDict / dataclass / Pydantic）的类型注解中提取语义**——哪些字段必填、默认值是什么、注解了什么。StateGraph 编译期把 `Annotated[list, add_messages]` 这类声明翻译成通道（channel）与 reducer 时，底层类型判定就靠这个模块。

### 9.1 三个类型谓词

```python
def _is_optional_type(type_: Any) -> bool:
    if isinstance(type_, types.UnionType):        # PEP 604: str | None
        return any(arg is type(None) or _is_optional_type(arg) for arg in type_.__args__)
    if hasattr(type_, "__origin__") and hasattr(type_, "__args__"):
        origin = get_origin(type_)
        if origin is Optional: return True
        if origin is Union:
            return any(arg is type(None) or _is_optional_type(arg) for arg in type_.__args__)
        if origin is Annotated:                   # Annotated[Optional[int], reducer] 也要剥开
            return _is_optional_type(type_.__args__[0])
        return origin is None
    if hasattr(type_, "__bound__") and type_.__bound__ is not None:
        return _is_optional_type(type_.__bound__) # TypeVar bound
    return type_ is None
```

递归剥 `Union`/`Optional`/`Annotated`/`TypeVar bound`，兼容新旧两种 union 语法。`_is_required_type` 识别 `typing.Required[...]`/`NotRequired[...]`（返回 True/False/None 三态，None = 没标注），同样递归穿 `Annotated`；`_is_readonly_type` 识别 `ReadOnly[...]`——但源码注释明说 **ReadOnly 被忽略**："we don't care if you mutate the state in your node … mutating state in your node has no effect on our graph state"（节点内改 state 对象不影响图状态，因为更新走返回值 + reducer）。

### 9.2 get_field_default：字段默认值裁决

优先级链条（返回 `...` 表示"无默认、必填"，返回 `None` 表示"缺省为空"）：

1. TypedDict 的 `__optional_keys__`（`total=False` 或显式 `NotRequired`）→ `None`；但若同时显式 `Required[...]` → `...`；
2. 显式 `Required` → `...`；显式 `NotRequired`（老 Python 写法）→ `None`；
3. dataclass：字段的 `default`（非 MISSING 且非 `...`）或 `default_factory()`；
4. 兜底看注解：`Optional`/含 None 的 Union → `None`，否则 → `...`。

这张裁决表决定了 `StateGraph` 里"节点没写这个 key 时，通道初值是什么"。

### 9.3 其余两个工具

- `get_enhanced_type_hints(type)`：为 config schema 抽取 `(name, typ, default, description)` 四元组——Pydantic 走 `model_fields`（默认值若是 `PydanticUndefinedType` 置 None），TypedDict/dataclass 走 `__dict__` 里的类属性。
- `get_update_as_tuples(input, keys)`：把状态更新（可能是 Pydantic 模型）转成 `[(key, value)]`。对 Pydantic 有特殊兼容逻辑：**只保留 `model_fields_set` 里显式设置过的、或值非 None、或默认值非 None 的字段**——避免"模型实例化时未赋值字段以 None 形态覆盖图状态"。源码自嘲 "This behavior for Pydantic is somewhat inelegant, but we keep around for backwards compatibility"。
- `get_cached_annotated_keys(obj)`：沿 `__mro__` 逆序收集所有 `__annotations__` 键名，结果放 **`WeakKeyDictionary` 缓存**（类被回收缓存自动消失）。里面有两个兼容性细节：Python 3.14+ 的 Pydantic 模型 `__annotations__` 是描述符，`__dict__.get` 拿不到要 fallback `getattr`；`types.GetSetDescriptorType` 要跳过。

**与 Annotated reducer 的关系**：本模块负责"把 `Annotated[X, ...]` 剥开看 X 是什么"；真正把第二个元素识别为 reducer（`operator.add`、`add_messages`、自定义函数）并映射到 `BinaryOperatorAggregate`/`Topic` 等通道的逻辑在 `langgraph/graph/_node.py` 与 `langgraph/channels/` 中，编译期调用链是 `StateGraph.add_node/compile → 状态 schema 注解分析（借助本模块）→ 每字段一个 channel + reducer`。

## 10. 重试机制：`_internal/_retry.py` 与 RetryPolicy

### 10.1 RetryPolicy（`langgraph/types.py`）

```python
class RetryPolicy(NamedTuple):
    """Configuration for retrying nodes. (Added in 0.2.24)"""
    initial_interval: float = 0.5   # 首次重试前等待秒数
    backoff_factor: float = 2.0     # 每次重试间隔乘数
    max_interval: float = 128.0     # 重试间隔上限（秒）
    max_attempts: int = 3           # 总尝试次数（含第一次）
    jitter: bool = True             # 间隔上加随机抖动
    retry_on: type[Exception] | Sequence[type[Exception]] | Callable[[Exception], bool] \
        = default_retry_on          # 哪些异常触发重试
```

NamedTuple + 全默认值：`RetryPolicy()` 即得"0.5s 起、×2 退避、封顶 128s、共 3 次、带抖动"。

### 10.2 default_retry_on（`_internal/_retry.py`，全文 29 行）

```python
def default_retry_on(exc: Exception) -> bool:
    import httpx
    import requests
    if isinstance(exc, ConnectionError):
        return True                                        # 连接错误 → 重试
    if isinstance(exc, httpx.HTTPStatusError):
        return 500 <= exc.response.status_code < 600       # 仅 5xx 重试
    if isinstance(exc, requests.HTTPError):
        return 500 <= exc.response.status_code < 600 if exc.response else True
    if isinstance(exc, (ValueError, TypeError, ArithmeticError, ImportError,
                        LookupError, NameError, SyntaxError, RuntimeError,
                        ReferenceError, StopIteration, StopAsyncIteration, OSError)):
        return False                                       # 程序性错误 → 不重试
    return True                                            # 其余默认重试
```

**设计哲学：黑名单排除"重试也没用"的确定性错误**（类型错、语法错、名字错……），白名单点名网络类错误，其余（含各类 SDK 自定义异常、超时异常）宁可多重试。⚠️ 注意 `OSError` 在**不重试**名单里，而 `ConnectionError` 是 `OSError` 的子类却被前置分支放行——顺序敏感。`httpx`/`requests` 是函数内延迟 import：没装 requests 的环境不会因导入本模块而炸，但**异常真的进来时若 httpx 未安装会 ImportError**——LangGraph 视 httpx 为事实依赖（langchain-core 需要它）。对本项目的启示：MEMORY 中 P2-11/P3-4 的"先判超时再判连接"的 LLM 退避闸，与这里的异常分类是同一课题。

### 10.3 执行循环（`pregel/_retry.py::run_with_retry`）

```python
def run_with_retry(task, retry_policy, configurable=None) -> None:
    retry_policy = task.retry_policy or retry_policy    # 节点级覆盖图级
    if task.timeout is not None:
        raise sync_timeout_unsupported(task.name)       # 同步节点+超时 → 直接拒绝（见第 11 章）
    attempts = 0
    while True:
        try:
            task.writes.clear()                          # 关键：清掉上次尝试的半成品写入
            return task.proc.invoke(task.input, config)
        except ParentCommand as exc:                     # Command(graph=PARENT) 特殊冒泡
            ...
        except GraphBubbleUp:                            # interrupt 等：不算失败，直接上抛
            raise
        except Exception as exc:
            matching_policy = ...                        # 从策略序列里找 retry_on 命中的那个
            if matching_policy is None or not _should_retry_on(matching_policy, exc):
                raise
            attempts += 1
            if attempts >= matching_policy.max_attempts:
                raise
            interval = matching_policy.initial_interval
            sleep_time = min(matching_policy.max_interval,
                             interval * (matching_policy.backoff_factor ** (attempts - 1)))
            if matching_policy.jitter:
                sleep_time += random.uniform(0, 1)
            time.sleep(sleep_time)                       # 异步版为 await asyncio.sleep
```

要点：

- **指数退避公式**：`initial_interval × backoff_factor^(attempts-1)`，封顶 `max_interval`，jitter 为 `+U(0,1)` 秒（加性抖动，防惊群）。默认参数下三次尝试间隔约 0.5~1.5s、1~2s。
- **`task.writes.clear()`**：每次重试前清空上一轮的通道写入，保证失败尝试的半成品不泄漏进图状态——重试语义是"整个节点重新执行"。
- **不重试的控制流异常**：`GraphBubbleUp`（interrupt/命令冒泡）与发给本图的 `ParentCommand` 走各自分支，不落入重试。
- **retry_policy 是序列**：类型是 `Sequence[RetryPolicy] | None`，多个策略按序找第一个 `retry_on` 命中的生效（图级默认 + 节点级覆盖的组合由 `task.retry_policy or retry_policy` 决定）。
- 每次尝试会把 `node_attempt`（1 起）、`node_first_attempt_time` 写进 `Runtime.execution_info`，供观测（对应 MEMORY 里失败熔断中间件那类"第几次失败"的判定素材）。

启用方式：`builder.compile(retry_policy=RetryPolicy(...))`（图级默认，**含 error-handler 节点**）或 `add_node("n", fn, retry_policy=RetryPolicy(max_attempts=5, retry_on=(httpx.TimeoutException,)))`（节点级覆盖）。

## 11. 超时处理：`_internal/_timeout.py` 与 TimeoutPolicy

`_internal/_timeout.py` 只有 25 行，是两个"规范化/报错"辅助：

```python
_SYNC_TIMEOUT_PREFIX = (
    "Node timeouts are only supported for async nodes because sync Python "
    "execution cannot be safely cancelled in-process.")

def coerce_timeout_policy(value: float | timedelta | TimeoutPolicy | None) -> TimeoutPolicy | None:
    """Normalize a timeout value to positive-second policy fields."""
    return TimeoutPolicy.coerce(value)

def sync_timeout_unsupported(name, *, kind="Node") -> ValueError:
    return ValueError(f"{_SYNC_TIMEOUT_PREFIX} {kind} {name!r} is sync.")
```

真正的策略类型在 `types.py`：

```python
@dataclass(**_DC_KWARGS)   # kw_only, slots, frozen
class TimeoutPolicy:
    run_timeout: float | timedelta | None = None
    """Hard wall-clock cap for a single node attempt. 永不被进度信号/heartbeat 刷新。"""
    idle_timeout: float | timedelta | None = None
    """单次尝试允许的最大"无可见进度"时长。"""
    refresh_on: Literal["auto", "heartbeat"] = "auto"
    """"auto"=图进度信号+显式心跳都刷新 idle_timeout；"heartbeat"=只认 runtime.heartbeat()。"""
```

**解析**：

- **两种超时互补**：`run_timeout` 是硬顶（无论节点多活跃，到点就杀）；`idle_timeout` 是活跃度检测（只要 LLM 还在吐 token / 还在 heartbeat 就续命，卡死才杀）。对"调大模型"的节点，`idle_timeout + refresh_on="auto"` 是更贴合的策略——长回答不该被硬顶误杀，真挂起才会触发。
- `TimeoutPolicy.coerce` 把裸 `float`/`timedelta` 升格为 `run_timeout` 策略（所以 `add_node(..., timeout=30)` 合法）；对已是规范形态的实例走快路径原样返回（`frozen=True` 保证可安全共享）；两个超时都为空返回 `None`；非正数抛 `ValueError`。
- **同步节点不支持超时**：编译期 `validate_timeout_supported` 拦截，运行期 `run_with_retry` 再兜底一次（第 10.3 节代码里的 `raise sync_timeout_unsupported(task.name)`）。原因是文档写明的：*"sync Python execution cannot be safely cancelled in-process"*——Python 无法从外部安全打断一段同步代码（强杀线程会破坏解释器状态），而 asyncio 任务可以 `task.cancel()` 协作取消。TimeoutPolicy docstring 同样提醒：**超时依赖 asyncio 取消，节点里同步 `time.sleep()` 或 GIL 密集计算会把超时推迟到事件循环重新获得控制权之后**。
- 超时触发抛 `NodeTimeoutError`（`langgraph.errors`），会走正常的重试/错误处理链路；`CONFIG_KEY_TIMED_ATTEMPT_OBSERVER` 常量（第 7 章）用于向 langgraph-server 上报"带超时的尝试"的 start/progress/finish 事件（`_retry.py` 里的 `_AttemptContext/_AttemptEvent`，源码注释明确它们是 server 依赖的内部契约，不许搬去 `langgraph.types`）。
- **图级超时**：整图时限不在这套机制里，惯例是 `asyncio.wait_for(graph.ainvoke(...), timeout=...)` 或平台侧（如 langgraph-server 的 run 超时）。本项目 MEMORY 的 P2-8"目标库两道闸：超时 240s < 工具超时 300s"就是这种**外层预算必须大于内层预算**的分层超时实践。

## 12. 草稿板 `_internal/_scratchpad.py`

全文 19 行，但它是 `interrupt()`/`Command(resume=...)` 机制的支点：

```python
import dataclasses
from langgraph.types import _DC_KWARGS

@dataclasses.dataclass(**_DC_KWARGS)     # kw_only, slots, frozen
class PregelScratchpad:
    step: int                             # 当前 superstep 序号
    stop: int                             # 递归上限（recursion_limit）
    # call
    call_counter: Callable[[], int]       # functional API：本任务内第几次 call()
    # interrupt
    interrupt_counter: Callable[[], int]  # 本任务内第几次 interrupt()
    get_null_resume: Callable[[bool], Any]
    resume: list[Any]                     # 恢复时传入的 resume 值队列
    # subgraph
    subgraph_counter: Callable[[], int]   # 本任务内第几次调用子图
```

**工作原理**：Pregel 为**每个任务**创建一个 scratchpad，经 `configurable["__pregel_scratchpad"]`（`CONFIG_KEY_SCRATCHPAD`，常量注释："holds a mutable dict for temporary storage scoped to the current task"）注入节点执行上下文。三个 counter 是闭包计数器，节点每次调用 `interrupt(value)` / `call()` / 子图时自增取号：

- **interrupt 的确定性恢复**就靠 `interrupt_counter`：同一任务重放时，第 N 次 `interrupt()` 调用去 `resume` 列表里取第 N 个值——前 N-1 个中断已有答案直接返回（不真正暂停），第 N 个没有答案才再次抛出中断。这就是"一个节点里可以写多个 `interrupt()`"还能正确逐个恢复的原因。
- `get_null_resume` 处理"整体 resume 值"（非按 interrupt 序号的恢复）。
- dataclass 用 `kw_only+slots+frozen`（`_DC_KWARGS`）：字段名 `step`/`stop` 太通用，强制关键字传参防错位；slots 省内存（每任务一个）；frozen 防节点篡改——counter 本身是可变闭包，冻结的是容器不是状态。

## 13. 重放机制 `_internal/_replay.py`

90 行，解决**时间旅行（time travel）重放时子图 checkpoint 的选取**问题：

```python
class ReplayState:
    """Tracks which subgraphs have already loaded their pre-replay checkpoint.

    During a parent replay, each subgraph's first invocation should restore the
    checkpoint from before the replay point. Subsequent invocations of the same
    subgraph (e.g. in a loop) should use normal checkpoint loading ...
    """
    __slots__ = ("checkpoint_id", "_visited_ns")

    def __init__(self, checkpoint_id: str) -> None:
        self.checkpoint_id = checkpoint_id
        # DO NOT CHANGE THIS VARIABLE – it may need to be rehydrated in other runtimes
        self._visited_ns: set[str] = set()

    def _is_first_visit(self, checkpoint_ns: str) -> bool:
        # "sub_node:task_id" -> "sub_node"   （剥掉 task_id 后缀）
        stable_ns = checkpoint_ns.rsplit(NS_END, 1)[0] if NS_END in checkpoint_ns else checkpoint_ns
        if stable_ns in self._visited_ns:
            return False
        self._visited_ns.add(stable_ns)
        return True

    def get_checkpoint(self, checkpoint_ns, checkpointer, checkpoint_config):
        if self._is_first_visit(checkpoint_ns):
            for saved in checkpointer.list(checkpoint_config,
                    before={"configurable": {"checkpoint_id": self.checkpoint_id}},
                    limit=1):
                return saved          # 重放点之前的最后一个 checkpoint
            return None
        return checkpointer.get_tuple(checkpoint_config)   # 之后走正常"取最新"
```

**场景解析**：用户从历史 checkpoint X 重放父图。父图某节点内嵌子图：

- 子图**本轮第一次**被调用时，应恢复到"X 之前"的状态（即时间旅行语义——回到那一刻子图的样子），所以用 `checkpointer.list(before=X, limit=1)` 取重放点上界之前的最新 checkpoint；
- 同一轮里子图**再次**被调用（比如循环里每圈都进子图），此时前一圈已经产生了**新** checkpoint，应走正常的 `get_tuple`（取最新），否则循环永远回到同一旧状态。

区分"第一次/后续"的键是**剥掉 task_id 的稳定命名空间**（`sub_node:uuid` → `sub_node`），因为循环每圈的 task_id 不同但逻辑上是同一子图。单一 `ReplayState` 实例在一次父图执行内**按引用共享**给所有派生 config——通过 `CONFIG_KEY_REPLAY_STATE`（`"__pregel_replay_state"`，常量注释与 `_constants.py` 47-49 行一致）传递。`_visited_ns` 上的 "DO NOT CHANGE" 注释警告：langgraph-server 等其他运行时可能需要重建（rehydrate）这个集合，字段名与语义是跨运行时契约。异步版 `aget_checkpoint` 用 `alist`/`aget_tuple`，逻辑同构。

- **invoke 流程**：`ensure_config()` 补全 → 合并 kwargs → 注入 func_accepts 登记的参数 → 若 `trace=True`：`get_callback_manager_for_config` 起 `on_chain_start`（run 名取 `config["run_name"] or self.get_name()`），`patch_config(callbacks=run_manager.get_child())` 造子 config，从 `LangChainTracer.run_map` 摸出 run 对象，`set_config_context` 中执行，异常 `on_chain_error`、成功 `on_chain_end` → 若返回值本身是 Runnable 且 `recurse=True`，**用同一输入再 invoke 该 Runnable**（节点函数返回一个图/链时自动展开执行）。

- **`coerce_to_runnable`** 是 `add_node` 接受任意可调用对象的秘密：

```python
def coerce_to_runnable(thing, *, name, trace) -> Runnable:
    if isinstance(thing, Runnable):            return thing
    elif is_async_generator(thing) or inspect.isgeneratorfunction(thing):
        return RunnableLambda(thing, name=name)          # 生成器交给 LC 的 Lambda
    elif callable(thing):
        if is_async_callable(thing):
            return RunnableCallable(None, thing, name=name, trace=trace)
        else:
            return RunnableCallable(thing,
                wraps(thing)(partial(run_in_executor, None, thing)),  # 同步函数自动生成
                name=name, trace=trace)                                 # 线程池版 afunc！
    elif isinstance(thing, dict):              return RunnableParallel(thing)
```

**同步节点函数会被自动包一层 `run_in_executor` 作为 afunc**——这就是"同步节点在 `ainvoke` 下不阻塞事件循环"的实现点（也呼应 MEMORY P1-14"同步阻塞搬离事件循环"的思路：框架已对节点做了，工具函数要自己保证）。`is_async_callable` 同时识别 async def 函数与 `__call__` 为协程的可调用对象。

### 14.4 RunnableSeq 与 `seq:step:N`

`RunnableSeq` 是内部精简版 `RunnableSequence`（"the output of each is the input of the next"）：

- 构造时**扁平化**嵌套的 `RunnableSequence`/`RunnableSeq`，至少 2 步否则 `ValueError`；Pregel 用它把"节点本体 + 若干 channel writer"串成一个任务（`_algo.py` 里 task.proc 即 `PregelNode` 读入 → `RunnableSeq(节点, writers...)`）。
- `invoke/ainvoke` 里每步 `patch_config(config, callbacks=run_manager.get_child(f"seq:step:{i+1}"))`——**这就是第 8.5 节 `filter_to_user_tags` 要过滤的 `seq:step:*` tag 的产地**。只有第 1 步（真正的节点）在 `set_config_context` 里跑，后续 writer 步骤不需要上下文。
- `stream/astream` 用 `step.transform(iterator, config)` 把上一步的输出流喂给下一步（不支持流式转换的步骤会自动缓冲）；`_consume_iter/_consume_aiter` 消费整条流并尽力用 `+` 聚合出最终输出（`add_supported` 标志在第一次 TypeError 后放弃拼接、只留最后一个 chunk）。`astream` 里用 `AsyncExitStack` 登记每个迭代器的 `aclose`，保证取消/异常时流被正确关闭。
- `__or__`/`__ror__` 支持与 `RunnableSequence` 混拼。

### 14.5 RunnableLike 协议族

## 15. 队列 `_internal/_queue.py`

三个小工具，共同点是给标准容器**加一个"等但不取"的 `wait()`**——Pregel 的流式输出（stream producer 等 consumer、runner 等任务完成）需要"知道有东西了"而不立刻消费：

- **`AsyncQueue(asyncio.Queue)`**：`async wait()` 复制了 `Queue.get()` 的等待逻辑但**去掉了 `get_nowait()`**——队列空时挂一个 future 进 `_getters` 等唤醒，醒来后不取走元素。异常路径处理得很细：取消时把自己从 `_getters` 摘除（容忍已被 `put_nowait` 摘走的 ValueError），若"被唤醒但拿不到"还要 `_wakeup_next` 让位给下一个等待者。
- **`Semaphore(threading.Semaphore)`**：`wait(blocking, timeout)` 在 `self._cond` 上等 `self._value > 0` 但**不 acquire**；带 timeout 时用 `monotonic()` 计算 endtime 循环等待。
- **`SyncQueue`**：`deque + Semaphore(0)` 的无界 FIFO（改编自 `queue.SimpleQueue` 的纯 Python 实现）：`put` 永不阻塞（append + release）、`get(block, timeout)` 先 acquire 计数再 popleft、`wait()` 委托给上面的 Semaphore.wait。`empty()/qsize()` 注释明说 "not reliable!"（并发下瞬时值）。`__class_getitem__ = classmethod(types.GenericAlias)` 让 `SyncQueue[X]` 可写下标。

## 17. 其他内部工具：`_cache` / `_serde` / `_future` / `_typing`

- **`_internal/__init__.py`**：仅 4 行 docstring——"not part of the public API, stability not guaranteed"。
- **`_cache.py`**：`_freeze` + `default_cache_key`，已在第 6.1 节详解。
- **`_serde.py`（253 行）——严格 msgpack 的反序列化白名单**。背景：checkpoint 序列化若开 `STRICT_MSGPACK_ENABLED`，反序列化只允许白名单内的类（防 pickle 式任意类实例化攻击）。本模块负责**从图的状态 schema 自动推导白名单**：
  - `curated_core_allowlist()`：预置 15 个 LangChain 消息类（`HumanMessage/AIMessage/ToolMessage/RemoveMessage` 及各 Chunk 变体），按 `(__module__, __name__)` 二元组登记；

  - `apply_checkpointer_allowlist(checkpointer, allowlist)`：checkpointer 不支持 `with_allowlist` 时打一次 warning 后跳过（`_warned_allowlist_unsupported` 全局标志防刷屏）。
  - **实践含义**：状态里放了自定义类，strict msgpack 模式下它会被自动进白名单；但**运行时才出现的类**（节点里临时构造、不在 schema 注解中）不会——遇到反序列化拒绝要往 schema 注解上想办法。
- **`_future.py`（220 行）——跨循环 Future 桥接**。核心是 `chain_future(source, destination)`（改编自 `asyncio.run_coroutine_threadsafe`）：两个 future（asyncio 与 concurrent.futures 任意组合）状态联动——source 完成把结果/异常拷给 destination（`_convert_future_exc` 把 concurrent 的 CancelledError/TimeoutError/InvalidStateError 转成 asyncio 对应类型），destination 被取消则反向取消 source；跨事件循环时用 `call_soon_threadsafe` 调度。`run_coroutine_threadsafe(coro, loop, lazy=, ...)`：目标 loop 就是当前 loop 时直接 `_ensure_future`，否则建裸 Future + `call_soon_threadsafe` 里 chain。`_ensure_future` 处理 Python 版本差异：≥3.12 且非 lazy 可用 `asyncio.eager_task_factory`（协程第一个 await 前同步执行，省一次调度），≥3.11 支持 `context=` 传 contextvars。这是**同步 `invoke` 内部驱动异步 Pregel loop**（以及子图跨线程调用）的地基。
- **`_typing.py`（54 行）**：`TypedDictLikeV1/V2`（有无 ClassVar 两版协议，兼容 typing 与 typing_extensions 的 TypedDict）、`DataclassLike`（有 `__dataclass_fields__` 即算）、聚合别名 `StateLike = TypedDictLikeV1 | TypedDictLikeV2 | DataclassLike | BaseModel`——"合法状态 schema"的类型级定义；哨兵 `MISSING = object()`（区分"没值"与"值是 None"，`_fields.py`/`_runnable.py` 都在用）；`EMPTY_SEQ`、`DeprecatedKwargs`（空 TypedDict，用作 `**kwargs: DeprecatedKwargs` 让废弃参数获得类型检查告警）。

## 18. Config 公开 API（`langgraph/config.py`）

196 行，节点/任务内获取运行时能力的**三个公开函数**，全部构建在 contextvar 之上：

```python
def get_config() -> RunnableConfig:
    if sys.version_info < (3, 11):
        try:
            if asyncio.current_task():
                raise RuntimeError("Python 3.11 or later required to use this in an async context")
        except RuntimeError:
            pass
    if var_config := var_child_runnable_config.get():
        return var_config
    else:
        raise RuntimeError("Called get_config outside of a runnable context")

def get_store() -> BaseStore:
    return get_config()[CONF][CONFIG_KEY_RUNTIME].store

def get_stream_writer() -> StreamWriter:
    runtime = get_config()[CONF][CONFIG_KEY_RUNTIME]
    return runtime.stream_writer
```

**解析**：

- `get_config()` 直接读 langchain-core 的 `var_child_runnable_config` contextvar——即第 14.1 节 `set_config_context` 在执行节点前 set 进去的那份 config。**脱离 runnable 上下文调用抛 RuntimeError**（比如在图外裸调）。Python<3.11 的异步环境直接拒绝：contextvar 跨 `asyncio.create_task` 的传播是 3.11 才有的（docstring 的 warning 块反复强调这一点）。
- `get_store()` / `get_stream_writer()` 是 `config["configurable"]["__pregel_runtime"]`（`CONFIG_KEY_RUNTIME`）里 `Runtime` 实例的便捷投影。前提是 `compile(store=...)` 配过 store；`get_stream_writer()` 不需要 store，配合 `graph.stream(..., stream_mode="custom")` 使用（docstring 示例：节点里 `writer({"custom_data": "Hello!"})`，流端收到该 dict）。
- 与第 14.2 节的**注入式**（签名声明 `store: BaseStore` / `writer: StreamWriter`）等价，选择只是风格问题：注入式在签名上自文档化；`get_*` 式适合深层辅助函数不想层层传参的场景。
- `utils/config.py` 是向后兼容 shim：`from langgraph._internal._config import ensure_config, patch_configurable` + `from langgraph.config import get_config, get_store`，docstring 注明 "to be removed in v1"——新代码应从 `langgraph.config` 与 `langchain_core.runnables` 导入。

### 场景 1：节点缓存（SQLite 持久化 + 自定义 key + TTL + 运维清理）

```python
"""缓存昂贵 LLM 节点：相同问题 1 小时内不再调模型。"""
import operator
from typing import Annotated, Any
from typing_extensions import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.cache.sqlite import SqliteCache
from langgraph.types import CachePolicy


class State(TypedDict):
    question: str
    asked_at: str          # 每次请求都不同的时间戳 —— 必须从 cache key 里排除！
    answer: str


def expensive_llm_node(state: State) -> dict:
    # 真实场景：这里调 LLM（本项目里对应一次问数 run）
    print(">>> 真的调用了模型：", state["question"])
    return {"answer": f"答：{state['question']}"}


def question_only_key(*args: Any, **kwargs: Any) -> bytes:
    """自定义 key_func：只对 question 做 key，忽略 asked_at 等噪声字段。

    签名必须与 default_cache_key 一致（*args, **kwargs），
    Pregel 以 key_func(节点输入) 调用，输入是 (state_dict,) 形式。
    """
    import pickle
    (state,) = args
    return pickle.dumps({"q": state.get("question")}, protocol=5)


builder = StateGraph(State)
builder.add_node(
    "llm",
    expensive_llm_node,
    cache_policy=CachePolicy(key_func=question_only_key, ttl=3600),  # 节点级策略
)
builder.add_edge(START, "llm")
builder.add_edge("llm", END)

graph = builder.compile(
    cache=SqliteCache(path="/tmp/nl2sql_node_cache.sqlite"),  # 图级：存储后端
)

# 第一次：真执行，打印 ">>> 真的调用了模型"
graph.invoke({"question": "上月销售额多少", "asked_at": "2026-10-14T10:00"})
# 第二次：asked_at 不同也命中缓存，无打印；流式输出仍会带出结果（cached=True）
graph.invoke({"question": "上月销售额多少", "asked_at": "2026-10-14T11:00"})

# 运维：只清 llm 节点的缓存（按 (CACHE_NS_WRITES, identifier, "llm") 命名空间）
graph.clear_cache(nodes=["llm"])
```

要点复盘：`cache=` 给存储、`cache_policy=` 给策略，缺一不可；节点级策略覆盖图级（`proc.cache_policy or cache_policy`）；默认 `default_cache_key` 会对**整个输入** pickle，输入含时间戳/uuid 就永不命中——所以自定义 `key_func` 只取业务字段；改了 `expensive_llm_node` 的函数体，`identifier(proc)` 变化自动作废旧缓存。

### 场景 2：重试 + 超时组合（异步节点、LLM 网络抖动）

```python
"""对 LLM 节点：5xx/超时重试 4 次指数退避；空闲 60s 判卡死；硬顶 5 分钟。"""
import asyncio, httpx
from langgraph.graph import StateGraph, START, END
from langgraph.types import RetryPolicy, TimeoutPolicy


def llm_retry_on(exc: Exception) -> bool:
    """自定义 retry_on：只重试网络类错误；业务错误（ValueError 等）立即失败。"""
    if isinstance(exc, (httpx.TimeoutException, httpx.TransportError, ConnectionError)):
        return True
    if isinstance(exc, httpx.HTTPStatusError):
        return 500 <= exc.response.status_code < 600
    return False


async def call_llm(state: dict) -> dict:
    # 必须是 async 节点：同步节点配 timeout 会在编译/运行期被
    # sync_timeout_unsupported 拒绝（sync Python 无法被安全取消）
    async with httpx.AsyncClient() as client:
        r = await client.post("https://llm.internal/chat", json={"q": state["q"]})
        r.raise_for_status()
        return {"a": r.json()["a"]}


builder = StateGraph(dict)
builder.add_node(
    "llm",
    call_llm,
    retry_policy=RetryPolicy(
        initial_interval=1.0,     # 首次重试等 1s
        backoff_factor=2.0,       # 1s → 2s → 4s（封顶 max_interval）
        max_interval=8.0,
        max_attempts=4,           # 总共试 4 次
        jitter=True,              # 每次 +U(0,1)s 防惊群
        retry_on=llm_retry_on,
    ),
    timeout=TimeoutPolicy(
        run_timeout=300,          # 硬顶 5 分钟，heartbeat 也不续
        idle_timeout=60,          # 60s 无任何进度信号 → NodeTimeoutError
        refresh_on="auto",        # 回调事件 + runtime.heartbeat() 都刷新 idle
    ),
)
builder.add_edge(START, "llm")
builder.add_edge("llm", END)
graph = builder.compile(retry_policy=RetryPolicy())   # 图级兜底策略（含 error-handler）

asyncio.run(graph.ainvoke({"q": "上月销售额"}))
```

要点复盘：每次重试前框架 `task.writes.clear()`，失败尝试的半成品写入不会漏进状态；`GraphBubbleUp`（interrupt）永远不触发重试；`TimeoutPolicy` 依赖 asyncio 协作取消，节点里同步阻塞会推迟超时触发；超时的 `NodeTimeoutError` 本身还会再过一遍 retry_on（`TimeoutPolicy` 与 `RetryPolicy` 是正交叠加的）。

### 场景 3：自定义配置（configurable 透传 + 节点内三大 get_* + 流式）

```python
"""把租户/库名经 configurable 传进图；节点内用 get_config/get_store/get_stream_writer。"""
from typing import Any
from typing_extensions import TypedDict

from langgraph.config import get_config, get_store, get_stream_writer
from langgraph.graph import StateGraph, START, END
from langgraph.store.memory import InMemoryStore
from langgraph._internal._config import merge_configs, patch_config  # 演示用；生产从公开路径导入


class State(TypedDict):
    db_name: str
    out: str


def route_node(state: State) -> dict:
    config = get_config()                       # contextvar 里取本任务完整 config
    conf = config["configurable"]
    tenant = conf["tenant"]                     # 场景入口传入的自定义键
    # 非 CONFIG_KEYS 的自定义顶层键也会被 ensure_config 搬进 configurable
    writer = get_stream_writer()                # stream_mode="custom" 的写入口
    writer({"progress": f"tenant={tenant} 开始查询 {state['db_name']}"})
    store = get_store()                         # compile(store=...) 注入的 BaseStore
    store.put(("tenants", tenant), "last_db", {"db": state["db_name"]})
    return {"out": f"{tenant}/{state['db_name']} 完成"}


builder = StateGraph(State)
builder.add_node("route", route_node)
builder.add_edge(START, "route")
builder.add_edge("route", END)
graph = builder.compile(store=InMemoryStore())

# 调用侧：configurable 里放 thread_id + 业务自定义键
for chunk in graph.stream(
    {"db_name": "WIT", "out": ""},
    config={
        "configurable": {"thread_id": "t-001", "tenant": "weint"},
        "tags": ["nl2sql"],
        "metadata": {"source": "tutorial"},
        "recursion_limit": 50,
    },
    stream_mode="custom",
):
    print(chunk)     # {'progress': 'tenant=weint 开始查询 WIT'}

# —— 配置合并/修补的两个常用手工场景 ——
base = {"configurable": {"tenant": "weint"}, "tags": ["nl2sql"]}
per_run = {"configurable": {"thread_id": "t-002"}, "tags": ["retry"]}
merged = merge_configs(base, per_run)
# tags 拼接 → ["nl2sql", "retry"]；configurable 浅合并 → tenant 保留、thread_id 新增
scoped = patch_config(merged, run_name="tenant-job", max_concurrency=4)
# 注意：patch_config 换 callbacks 时会自动清掉 run_name/run_id（run 名属于原回调树）
```

要点复盘：`thread_id` 属于 `_CHECKPOINT_COORDINATE_KEYS`——显式传它会**重置**从环境 contextvar 继承的 configurable（子图寻址自己的 checkpoint 谱系），而 `tenant` 这类普通键走浅合并得以保留；`tenant` 是标量且键名不含 key/token/secret/password/auth，会被 `_get_tracing_metadata_defaults` 自动送进 LangSmith 追踪 metadata（`_PROPAGATE_TO_METADATA` 里的 thread_id 等也会回填 metadata）；`get_*` 三函数只能在节点/任务执行上下文内调用，图外调用抛 `RuntimeError("Called get_config outside of a runnable context")`。

## 21. 速查表与总结

### 21.1 模块 → 职责 → 公开入口速查

| 内部模块 | 职责 | 用户侧对应物 |
|---|---|---|
| `cache/base` | 缓存抽象（批量 get/set + ns clear + serde） | `compile(cache=...)` |
| `cache/memory` | 进程内缓存（RLock + TTL 惰性过期，**无 LRU**） | `InMemoryCache()` |
| `cache/redis` | Redis 缓存（MGET/pipeline/SETEX，全面 fail-open） | `RedisCache(client)` |
| `cache/sqlite` | SQLite 缓存（WAL + 共享连接单锁 + to_thread 真异步） | `SqliteCache(path=...)` |
| `_internal/_cache` | `_freeze` + `default_cache_key`（pickle p5） | `CachePolicy.key_func` 默认值 |
| `_internal/_constants` | 保留写入键 / configurable 键 / NS 分隔符 / RESERVED | `langgraph.constants` 的 START/END/TAG_HIDDEN |
| `_internal/_config` | merge/patch/ensure_config + 回调装配 + 秘密过滤 | `RunnableConfig` 各键语义 |
| `_internal/_fields` | 注解分析（Optional/Required/默认值/注解键缓存） | 状态 schema 声明 |
| `_internal/_retry` | `default_retry_on` 异常分类 | `RetryPolicy.retry_on` 默认值 |
| `_internal/_timeout` | TimeoutPolicy 规范化 + 同步节点拒绝文案 | `add_node(timeout=...)` |
| `_internal/_scratchpad` | 任务级计数器（interrupt/call/subgraph 序号） | `interrupt()` 确定性恢复 |
| `_internal/_replay` | 时间旅行时子图 checkpoint 选取（首访 vs 后续） | 从历史 checkpoint 重放 |
| `_internal/_runnable` | 函数→Runnable、参数注入表、seq:step 追踪 | `add_node(fn)` 的一切签名魔法 |
| `_internal/_queue` | 带 `wait()`（等而不取）的队列/信号量 | 流式输出内部机制 |
| `_internal/_pydantic` | 动态建模 + 保留名重映射 + 类型探测 | Pydantic 状态 schema |
| `_internal/_serde` | strict msgpack 反序列化白名单推导 | checkpoint 安全序列化 |
| `_internal/_future` | 跨循环 chain_future / 线程安全提交协程 | 同步 invoke 驱动异步 loop |
| `_internal/_typing` | StateLike 协议族 + MISSING 哨兵 | 状态类型校验 |
| `config.py` | get_config / get_store / get_stream_writer | 节点内运行时访问 |
| `utils/config.py`、`utils/runnable.py` | 向后兼容 re-export（v1 移除） | 请勿在新代码使用 |

### 21.2 十条核心结论

1. LangGraph 的 cache 缓存的是**节点写入**而非 LLM 响应本身；namespace = `(CACHE_NS_WRITES, 节点代码身份, 节点名)`，**改节点代码自动失效旧缓存**。
2. 缓存三实现的过期机制不同：Redis 原生 SETEX 主动回收；InMemory/SQLite 惰性过期、**无 LRU、无容量上限**，死键驻留。
3. RedisCache 全面 fail-open（缓存挂了退化为无缓存），但其 `aget` 是同步直通、`clear` 用 KEYS——异步链路和大库场景要留意。
4. 命中缓存的任务**不进 runner**，writes 直接灌回并以 `cached=True` 输出；回填走后台 submit，不阻塞主循环。
5. 默认 cache key = `_freeze`（dict 排序、numpy 取 tobytes 指纹）+ pickle protocol 5 + xxh3-128；**输入含时间戳/uuid 必须自定义 key_func**。
6. config 三件套分工：`merge_configs`（多份合一，tags 拼接、metadata 顶层合并、callbacks 六情形）、`patch_config`（单点修补，换 callbacks 清 run_name/run_id）、`ensure_config`（补全默认 + contextvar 环境继承 + checkpoint 坐标显式化时丢弃继承 + 非标键搬进 configurable + 秘密键不进追踪）。
7. 节点签名的 `config/writer/store/runtime/previous/error` 注入由 `KWARGS_CONFIG_KEYS` 表驱动，**按参数名 + 注解字面形态匹配**——注解写错（或被 `from __future__ import annotations` 字符串化后形态不在表内）会静默不注入。
8. 重试是"节点整体重执行"：每次尝试前 `task.writes.clear()`；退避 = `initial × factor^(n-1)` 封顶 + 加性 jitter；`GraphBubbleUp`/interrupt 不重试；`default_retry_on` 黑名单排除程序性错误、仅 5xx 与连接类重试。
9. 超时**只支持异步节点**（同步 Python 不可安全取消）；`run_timeout` 硬顶 + `idle_timeout` 活跃度（`refresh_on="auto"|"heartbeat"`），超时依赖 asyncio 协作取消，同步阻塞会推迟触发。
10. `get_config()/get_store()/get_stream_writer()` 全部构建在 `var_child_runnable_config` contextvar 上，只能在节点/任务上下文内用；Python<3.11 的异步环境不可用。本仓 `.venv` 的 langgraph 带本地补丁（`DEFAULT_RECURSION_LIMIT=10007` 等），**判线上行为以容器内实际文件为准**。
