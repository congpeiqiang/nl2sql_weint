## 0. 包总览与重要迁移提示

### 0.1 导出面

`langgraph/prebuilt/__init__.py` 全文只有 23 行，它就是整个预构建层的「公共 API 清单」：

```python
"""langgraph.prebuilt exposes a higher-level API for creating and executing agents and tools."""

from langgraph.prebuilt._tool_call_transformer import ToolCallTransformer
from langgraph.prebuilt.chat_agent_executor import create_react_agent
from langgraph.prebuilt.tool_node import (
    InjectedState,
    InjectedStore,
    ToolNode,
    ToolRuntime,
    tools_condition,
)
from langgraph.prebuilt.tool_validator import ValidationNode

__all__ = [
    "create_react_agent",
    "ToolNode",
    "ToolCallTransformer",
    "tools_condition",
    "ValidationNode",
    "InjectedState",
    "InjectedStore",
    "ToolRuntime",
]
```

**解析**：

- 公开 8 个符号：1 个 Agent 工厂（`create_react_agent`）、1 个执行节点（`ToolNode`）、1 个验证节点（`ValidationNode`）、1 个路由函数（`tools_condition`）、3 个注入标注（`InjectedState` / `InjectedStore` / `ToolRuntime`）、1 个流变换器（`ToolCallTransformer`）。
- `_tool_call_stream.py` 里的 `ToolCallStream` **不在** `__all__` 中——它不由用户构造，只作为 `ToolCallTransformer` 的产物出现在流上（下划线前缀模块也表明是内部实现）。
- `interrupt.py` 里的 4 个 HITL 类型（`HumanInterrupt` 等）同样**没有**从 `__init__.py` 导出，需要 `from langgraph.prebuilt.interrupt import HumanInterrupt` 显式导入。

### 0.2 ⚠️ v1.0 迁移提示：整包已进入弃用通道

LangGraph 1.x 中，prebuilt 的核心符号都挂上了 `LangGraphDeprecatedSinceV10` 弃用标记：

```python
@deprecated(
    "create_react_agent has been moved to `langchain.agents`. "
    "Please update your import to `from langchain.agents import create_agent`.",
    category=LangGraphDeprecatedSinceV10,
)
def create_react_agent(...)
```

迁移对照表：

| langgraph.prebuilt（旧） | 新位置 |
|---|---|
| `create_react_agent` | `langchain.agents.create_agent` |
| `AgentState` | `langchain.agents.AgentState` |
| `HumanInterrupt` / `ActionRequest` / `HumanInterruptConfig` | `langchain.agents.interrupt` |
| `ValidationNode` | `create_agent` + 自定义工具错误处理 |
| `ToolNode` / `InjectedState` / `InjectedStore` / `ToolRuntime` / `tools_condition` | 仍可用，同时从 `langchain.tools` 再导出 |

**在 1.2.9 上这些组件功能完好**，本项目（nl2sql 后端）也仍在使用；但新代码建议直接写 `langchain.agents.create_agent`。本文以 prebuilt 源码为准讲解——`create_agent` 内部复用的正是同一套 `ToolNode` 机制，理解了本文即理解了新 API 的底座。

## 1. create_react_agent 完全解析

`create_react_agent` 是一个**图工厂**：输入模型和工具，输出一张编译好的 `CompiledStateGraph`（即一个标准的 LangChain `Runnable`），实现「LLM → 工具 → LLM → …」的 ReAct 循环。

### 1.1 完整函数签名

源码 `chat_agent_executor.py` 第 278–308 行：

```python
def create_react_agent(
    model: str
    | LanguageModelLike
    | Callable[[StateSchema, Runtime[ContextT]], BaseChatModel]
    | Callable[[StateSchema, Runtime[ContextT]], Awaitable[BaseChatModel]]
    | Callable[[StateSchema, Runtime[ContextT]], Runnable[LanguageModelInput, BaseMessage]]
    | Callable[[StateSchema, Runtime[ContextT]], Awaitable[Runnable[LanguageModelInput, BaseMessage]]],
    tools: Sequence[BaseTool | Callable | dict[str, Any]] | ToolNode,
    *,
    prompt: Prompt | None = None,
    response_format: StructuredResponseSchema | tuple[str, StructuredResponseSchema] | None = None,
    pre_model_hook: RunnableLike | None = None,
    post_model_hook: RunnableLike | None = None,
    state_schema: StateSchemaType | None = None,
    context_schema: type[Any] | None = None,
    checkpointer: Checkpointer | None = None,
    store: BaseStore | None = None,
    interrupt_before: list[str] | None = None,
    interrupt_after: list[str] | None = None,
    debug: bool = False,
    version: Literal["v1", "v2"] = "v2",
    name: str | None = None,
    **deprecated_kwargs: Any,
) -> CompiledStateGraph:
```

参数速查：

| 参数 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `model` | str / ChatModel / Runnable / 动态可调用 | 必填 | 语言模型，支持静态与运行期动态选择 |
| `tools` | 工具序列 / `ToolNode` | 必填 | 工具面；空列表 = 纯 LLM 单节点图 |
| `prompt` | str / SystemMessage / Callable / Runnable | `None` | 系统提示词或状态→模型输入的变换 |
| `response_format` | schema 或 `(prompt, schema)` 元组 | `None` | 循环结束后追加一次结构化输出调用 |
| `pre_model_hook` | RunnableLike | `None` | agent 节点前置节点（裁剪/摘要消息） |
| `post_model_hook` | RunnableLike | `None` | agent 节点后置节点（护栏/HITL，仅 v2） |
| `state_schema` | TypedDict / Pydantic 类 | `AgentState` | 自定义状态，**必须含 `messages` 与 `remaining_steps`** |
| `context_schema` | type | `None` | 运行期上下文 schema（取代已弃用的 `config_schema`） |
| `checkpointer` | Checkpointer | `None` | 线程内状态持久化（会话记忆 / interrupt 的前提） |
| `store` | BaseStore | `None` | 跨线程持久化存储（`InjectedStore` 的前提） |
| `interrupt_before` | `list[str]` | `None` | 在 `"agent"` / `"tools"` 节点前静态暂停 |
| `interrupt_after` | `list[str]` | `None` | 在 `"agent"` / `"tools"` 节点后静态暂停 |
| `debug` | bool | `False` | 调试模式 |
| `version` | `"v1"` / `"v2"` | `"v2"` | 工具节点执行形态（见 §1.11） |
| `name` | str | `None` | 编译图命名；作为子图嵌入多 Agent 系统时使用 |

另外 `**deprecated_kwargs` 只兜一个历史参数：`config_schema`（v0.6.0 起弃用，自动折算成 `context_schema`），传其它任何多余关键字直接 `TypeError`：

```python
if (config_schema := deprecated_kwargs.pop("config_schema", MISSING)) is not MISSING:
    warnings.warn("`config_schema` is deprecated ... use `context_schema` instead.", ...)
    if context_schema is None:
        context_schema = config_schema

if len(deprecated_kwargs) > 0:
    raise TypeError(f"create_react_agent() got unexpected keyword arguments: {deprecated_kwargs}")
```

### 1.2 model 参数：四种形态

`model` 的类型标注很长，归纳为四类：

**① 字符串标识符**（`"openai:gpt-4"`、`"anthropic:claude-3-7-sonnet-latest"`）：

```python
if isinstance(model, str):
    try:
        from langchain.chat_models import init_chat_model
    except ImportError:
        raise ImportError(
            "Please install langchain (`pip install langchain`) to "
            "use '<provider>:<model>' string syntax for `model` parameter."
        )
    model = cast(BaseChatModel, init_chat_model(model))
```

字符串走 `langchain` 包的 `init_chat_model` 惰性初始化——**没装 langchain 主包会直接 ImportError**。

**② ChatModel 实例 / Runnable**：最常见形态。工厂随后做「是否已绑工具」的探测：

```python
def _should_bind_tools(model, tools, num_builtin=0) -> bool:
    if isinstance(model, RunnableSequence):
        model = next((step for step in model.steps
                      if isinstance(step, (RunnableBinding, BaseChatModel))), model)
    if not isinstance(model, RunnableBinding):
        return True                      # 裸模型 → 需要绑定
    if "tools" not in model.kwargs:
        return True                      # bind 了其它东西但没绑 tools → 需要绑定
    bound_tools = model.kwargs["tools"]
    if len(tools) != len(bound_tools) - num_builtin:
        raise ValueError("Number of tools in the model.bind_tools() and tools "
                         "passed to create_react_agent must match ...")
    ...
    if missing_tools := tool_names - bound_tool_names:
        raise ValueError(f"Missing tools '{missing_tools}' in the model.bind_tools()")
    return False                         # 已经绑好了 → 不再重复绑定
```

**解析**：这段是「双绑防护」。你可以传 `model.bind_tools(tools)` 也可以传裸模型，但两者工具面必须一致——数量对不上或名字缺失都会抛 `ValueError`。它同时认识 OpenAI 风格（`{"type": "function", "function": {"name": ...}}`）和 Anthropic 风格（`{"name": ...}`）的已绑工具 schema。`num_builtin` 用于扣除「LLM 内建工具」（见 §1.3）。

**③ 动态模型可调用**：`(state, runtime) -> BaseChatModel`，支持协程版本。判定逻辑：

```python
is_dynamic_model = not isinstance(model, (str, Runnable)) and callable(model)
is_async_dynamic_model = is_dynamic_model and inspect.iscoroutinefunction(model)
```

动态模式下不会在编译期构建 `static_model`，而是每次进 agent 节点时现算：

```python
def _resolve_model(state, runtime) -> LanguageModelLike:
    if is_dynamic_model:
        return _get_prompt_runnable(prompt) | model(state, runtime)
    else:
        return static_model
```

这允许按 `runtime.context`（如用户配置的模型名）在运行期切换模型。**约束**：返回的模型必须自己 `.bind_tools(...)`，且绑定的工具须是 `tools` 参数的子集。**坑**：如果传的是 async 动态模型却用同步 `invoke()` 调图，`call_model` 会抛：

```python
if is_async_dynamic_model:
    raise RuntimeError("Async model callable provided but agent invoked synchronously. "
                       "Use agent.ainvoke() or agent.astream(), ...")
```

**④ 最终组装**：静态路径下，模型与 prompt 管道在编译期一次性拼好：

```python
static_model: Runnable | None = _get_prompt_runnable(prompt) | model
```

即 `agent` 节点执行的 Runnable 是 `prompt_runnable | model`——prompt 永远作用在模型之前，把 state 变成消息列表。

### 1.3 tools 参数：列表 / ToolNode / 内建工具 dict

```python
llm_builtin_tools: list[dict] = []
if isinstance(tools, ToolNode):
    tool_classes = list(tools.tools_by_name.values())
    tool_node = tools
else:
    llm_builtin_tools = [t for t in tools if isinstance(t, dict)]
    tool_node = ToolNode([t for t in tools if not isinstance(t, dict)])
    tool_classes = list(tool_node.tools_by_name.values())
```

**解析**，三种玩法：

1. **普通工具列表**（`BaseTool` / 裸函数）：自动包一层 `ToolNode`。裸函数由 `ToolNode.__init__` 里的 `create_tool()` 转成 `BaseTool`（从签名和 docstring 推断 schema）。
2. **直接传 `ToolNode` 实例**：当你需要自定义 `handle_tool_errors`、`messages_key`、`wrap_tool_call` 拦截器时，自己构造 `ToolNode` 再传进来（见 §2、§6.4）。
3. **dict 元素 = LLM 内建工具**（如 OpenAI 的 web search、代码解释器）：这类工具**由模型服务商执行**，所以只参与 `bind_tools`（`tool_classes + llm_builtin_tools`），**不进 ToolNode**——图里没有对应的执行体。

工具面还有一个副作用开关——`return_direct`：

```python
should_return_direct = {t.name for t in tool_classes if t.return_direct}
```

任何声明了 `return_direct=True` 的工具执行完后**不再回 LLM**，直接 END（路由细节见 §1.10）。

`tools=[]`（空列表）时 `tool_calling_enabled = False`，工厂走一条特殊分支：只建 `agent`（+ 可选 hook / 结构化输出）节点、**没有任何边回到工具**的单发图（源码 787–828 行）。

### 1.4 prompt 参数

`Prompt` 类型别名：

```python
Prompt = (
    SystemMessage
    | str
    | Callable[[StateSchema], LanguageModelInput]
    | Runnable[StateSchema, LanguageModelInput]
)
```

`_get_prompt_runnable` 把四种形态统一归一成 Runnable（名字固定为 `"Prompt"`）：

```python
def _get_prompt_runnable(prompt: Prompt | None) -> Runnable:
    if prompt is None:
        prompt_runnable = RunnableCallable(
            lambda state: _get_state_value(state, "messages"), name=PROMPT_RUNNABLE_NAME)
    elif isinstance(prompt, str):
        _system_message: BaseMessage = SystemMessage(content=prompt)
        prompt_runnable = RunnableCallable(
            lambda state: [_system_message] + _get_state_value(state, "messages"), ...)
    elif isinstance(prompt, SystemMessage):
        prompt_runnable = RunnableCallable(
            lambda state: [prompt] + _get_state_value(state, "messages"), ...)
    elif inspect.iscoroutinefunction(prompt):
        prompt_runnable = RunnableCallable(None, prompt, ...)
    elif callable(prompt):
        prompt_runnable = RunnableCallable(prompt, ...)
    elif isinstance(prompt, Runnable):
        prompt_runnable = prompt
    else:
        raise ValueError(f"Got unexpected type for `prompt`: {type(prompt)}")
    return prompt_runnable
```

**解析**：

- `str` / `SystemMessage`：**前置拼接**到 `state["messages"]`，不落状态、每轮都拼。
- `Callable` / `Runnable`：拿到**完整图状态**，返回什么模型就吃什么——这是做「运行期动态系统提示」「消息裁剪」的入口。
- `_get_state_value` 同时兼容 dict 状态与 Pydantic/dataclass 状态：

```python
def _get_state_value(state, key, default=None):
    return state.get(key, default) if isinstance(state, dict) else getattr(state, key, default)
```

### 1.5 state_schema 自定义状态

默认状态是内置的 `AgentState`：

```python
class AgentState(TypedDict):
    """The state of the agent."""
    messages: Annotated[Sequence[BaseMessage], add_messages]
    remaining_steps: NotRequired[RemainingSteps]
```

若指定 `response_format`，默认换成 `AgentStateWithStructuredResponse`（多一个 `structured_response` 键）。自定义 schema 有**硬校验**：

```python
if state_schema is not None:
    required_keys = {"messages", "remaining_steps"}
    if response_format is not None:
        required_keys.add("structured_response")
    schema_keys = set(get_type_hints(state_schema))
    if missing_keys := required_keys - set(schema_keys):
        raise ValueError(f"Missing required key(s) {missing_keys} in state_schema")
```

**解析**：自定义状态必须包含：

1. `messages`——用 `Annotated[..., add_messages]` 标注以获得消息合并 reducer（按 id 去重/追加/删除）；
2. `remaining_steps`——托管值 `RemainingSteps`，由 LangGraph 自动填充为 `recursion_limit - 已走步数`，用于「步数不够时体面收尾」（§1.12）；
3. `structured_response`——**仅当**传了 `response_format` 时必需。

TypedDict 和 Pydantic `BaseModel` 两种风格都支持（代码里到处用 `_get_state_value` / `issubclass(state_schema, BaseModel)` 双轨处理）。注意所有内置 State 类在 1.x 都已弃用，官方指向 `langchain.agents.AgentState`。

若配了 `pre_model_hook`，工厂还会**动态派生一个输入 schema**，追加 `llm_input_messages` 键：

```python
if isinstance(state_schema, type) and issubclass(state_schema, BaseModel):
    from pydantic import create_model
    input_schema = create_model("CallModelInputSchema",
                                llm_input_messages=(list[AnyMessage], ...),
                                __base__=state_schema)
else:
    class CallModelInputSchema(state_schema):  # type: ignore
        llm_input_messages: list[AnyMessage]
    input_schema = CallModelInputSchema
```

这个 `input_schema` 只挂在 `agent` 节点上（`workflow.add_node("agent", ..., input_schema=input_schema)`），让 hook 能把「喂给 LLM 的消息」与「状态里的消息」解耦。注意 `StateGraph.add_node` 收到显式 `input_schema` 时会调用 `_add_schema(input_schema)` 把新增键**自动注册为图通道**——所以使用默认 `AgentState` 时 `pre_model_hook` 返回 `llm_input_messages` 也不会丢，用户无需（也不应）在自己的 state_schema 里重复声明。

### 1.6 response_format 结构化返回

接受形态：OpenAI function/tool schema（dict）、JSON Schema（dict）、TypedDict、Pydantic 类，或元组 `(prompt, schema)`。实现是一个**独立节点**：

```python
def generate_structured_response(state, runtime, config) -> StateSchema:
    messages = _get_state_value(state, "messages")
    structured_response_schema = response_format
    if isinstance(response_format, tuple):
        system_prompt, structured_response_schema = response_format
        messages = [SystemMessage(content=system_prompt)] + list(messages)

    resolved_model = _resolve_model(state, runtime)
    model_with_structured_output = _get_model(resolved_model).with_structured_output(
        cast(StructuredResponseSchema, structured_response_schema))
    response = model_with_structured_output.invoke(messages, config)
    return {"structured_response": response}
```

**解析**：

- ReAct 循环结束（AIMessage 不再带 tool_calls）后，图路由到 `generate_structured_response` 节点，**对模型再发起一次独立调用**，用 `.with_structured_output(schema)` 把整个消息历史压成结构化对象，写入 `structured_response` 状态键。
- 元组形态的 `prompt` 只作用于这最后一次调用（作为 SystemMessage 前置），不影响循环中的 agent prompt。
- `_get_model` 负责从 `RunnableBinding` / `RunnableSequence` 里剥出裸 `BaseChatModel`——因为 `with_structured_output` 只能在 ChatModel 上调，不能在已 bind 的 Runnable 上调。剥不出来就 `TypeError`。
- **成本提示**：这是一次额外 LLM 调用；模型必须支持 `with_structured_output`。

### 1.7 checkpointer / store 注入

两者都直接透传给 `workflow.compile(...)`：

```python
return workflow.compile(
    checkpointer=checkpointer,
    store=store,
    interrupt_before=interrupt_before,
    interrupt_after=interrupt_after,
    debug=debug,
    name=name,
)
```

- **checkpointer**：单线程（thread）内的状态持久化。给了它才有：多轮会话记忆（同一 `thread_id` 续聊）、`interrupt()` 暂停/恢复、`get_state()` / `update_state()`、时间旅行。**不配 checkpointer，一切 HITL 功能不可用**。
- **store**：跨线程（跨会话/跨用户）的 KV 持久化。工具里用 `Annotated[Any, InjectedStore()]` 声明后由 `ToolNode` 自动注入；**图没配 store 而工具声明了 InjectedStore，会在执行时抛 ValueError**（见 §2.6）。

### 1.8 interrupt_before / interrupt_after 审批配置

```python
interrupt_before: list[str] | None = None,   # 取值 "agent" / "tools"
interrupt_after: list[str] | None = None,    # 取值 "agent" / "tools"
```

这是**静态中断**：编译期声明，每次执行到该节点前/后无条件暂停（需 checkpointer）。典型审批流：`interrupt_before=["tools"]`——LLM 决定调工具后、真正执行前暂停，人检查 `get_state()` 里 AIMessage 的 `tool_calls`，然后：

- `graph.invoke(None, config)` 放行继续执行；
- 或 `graph.update_state(config, {...})` 改写状态后再放行；
- 或干脆不再恢复（放弃本轮）。

与之互补的是**动态中断** `interrupt()`（在节点/工具内部按条件暂停，见 §3）。两者可以叠加。

### 1.9 pre_model_hook / post_model_hook

**pre_model_hook**——每次进 agent 节点前执行，官方定位是长消息管理（裁剪、摘要）。契约（docstring 原文归纳）：

```python
# 返回值：至少提供 messages 或 llm_input_messages 之一
{
    # 提供则【更新】状态里的 messages
    "messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), ...],
    # 提供则只作为 LLM 输入，【不更新】状态 messages
    "llm_input_messages": [...],
    ...
}
```

agent 节点取输入时优先用 `llm_input_messages`：

```python
def _get_model_input_state(state):
    if pre_model_hook is not None:
        messages = (_get_state_value(state, "llm_input_messages")
                    or _get_state_value(state, "messages"))
    ...
    _validate_chat_history(messages)
    state["messages"] = messages   # 以 messages 键传给 prompt runnable
    return state
```

⚠️ **若要真改写状态消息，必须以 `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 开头整体覆盖**——否则 `add_messages` reducer 会把你返回的消息**追加**到旧历史后面，越滚越长。

**post_model_hook**——agent 节点之后执行（**仅 v2 可用**），定位是 HITL、护栏、输出校验。它比 pre hook 复杂在：后面接的是一个**条件路由器**，而不是固定边：

```python
def post_model_hook_router(state) -> str | list[Send]:
    """Routes to one of:
    * "tools": if there are pending tool calls without a corresponding message.
    * "generate_structured_response": if no pending tool calls and response_format given.
    * END: if no pending tool calls and no response_format.
    """
    messages = _get_state_value(state, "messages")
    tool_messages = [m.tool_call_id for m in messages if isinstance(m, ToolMessage)]
    last_ai_message = next(m for m in reversed(messages) if isinstance(m, AIMessage))
    pending_tool_calls = [c for c in last_ai_message.tool_calls if c["id"] not in tool_messages]

    if pending_tool_calls:
        return [Send("tools", ToolCallWithContext(__type="tool_call_with_context",
                                                  tool_call=call, state=state))
                for call in pending_tool_calls]
    elif isinstance(messages[-1], ToolMessage):
        return entrypoint
    elif response_format is not None:
        return "generate_structured_response"
    else:
        return END
```

**解析**：post hook 里可以「截胡」——比如把危险 tool_calls 从 AIMessage 里删掉或直接补写拒绝 ToolMessage；路由器按「**是否存在没有对应 ToolMessage 的 pending tool call**」决定去 tools、回 entrypoint、去结构化输出还是 END。这个「pending = 有 call 无 result」的判据和 §1.13 的历史校验一脉相承。

### 1.10 内部图结构（agent → tools 循环）

核心路由函数 `should_continue`：

```python
def should_continue(state) -> str | list[Send]:
    messages = _get_state_value(state, "messages")
    last_message = messages[-1]
    if not isinstance(last_message, AIMessage) or not last_message.tool_calls:
        if post_model_hook is not None:
            return "post_model_hook"
        elif response_format is not None:
            return "generate_structured_response"
        else:
            return END
    else:
        if version == "v1":
            return "tools"
        elif version == "v2":
            if post_model_hook is not None:
                return "post_model_hook"
            return [Send("tools", ToolCallWithContext(__type="tool_call_with_context",
                                                      tool_call=call, state=state))
                    for call in last_message.tool_calls]
```

`return_direct` 工具的收尾路由：

```python
def route_tool_responses(state) -> str:
    for m in reversed(_get_state_value(state, "messages")):
        if not isinstance(m, ToolMessage):
            break
        if m.name in should_return_direct:
            return END
    # handle a case of parallel tool calls where
    # the tool w/ `return_direct` was executed in a different `Send`
    if isinstance(m, AIMessage) and m.tool_calls:
        if any(call["name"] in should_return_direct for call in m.tool_calls):
            return END
    return entrypoint

**解析**：`return_direct` 判定要倒着扫「最近一段连续 ToolMessage」，因为 v2 下并行工具调用各自跑在独立的 Send 任务里，`return_direct` 工具的结果可能不在本任务的消息尾部——所以再补一层「AIMessage 的 tool_calls 里有没有 return_direct 工具」的兜底。

```

pre_model_hook ──────────► agent ──(条件: should_continue)──┬─► tools ×N (Send, v2)

def call_model(state, runtime, config) -> StateSchema:
    model_input = _get_model_input_state(state)      # 校验历史 + 组装 messages
    if is_dynamic_model:
        dynamic_model = _resolve_model(state, runtime)
        response = cast(AIMessage, dynamic_model.invoke(model_input, config))
    else:

    response.name = name                              # 把 agent 名写到 AIMessage 上

### 1.11 v1 vs v2 差异

| 维度 | `version="v1"` | `version="v2"`（默认） |
|---|---|---|
| 工具节点粒度 | **一条消息一个任务**：`should_continue` 返回字符串 `"tools"`，ToolNode 收到完整状态，自己从最后一条 AIMessage 抽出全部 tool_calls | **一个 tool_call 一个任务**：`should_continue` 返回 `[Send("tools", ToolCallWithContext...), ...]`，每个 Send 只带一个 tool_call + 状态快照 |
| 节点内并行 | ToolNode 内部用线程池 `executor.map` / `asyncio.gather` 并行执行多个调用 | 并行发生在**图层**（多个 Send 任务并行调度），每个 ToolNode 实例只执行一个调用 |
| 输入形态 | `{"messages": [...]}` dict | `{"__type": "tool_call_with_context", "tool_call": {...}, "state": {...}}` |
| HITL / 中断 | 中断以「整个 tools 节点」为单位 | 中断以「单个工具调用」为单位——一个调用 interrupt 挂起，不影响同批其它调用的完成与落盘 |
| post_model_hook | 不支持 | 支持（docstring 明确 "Only available with version='v2'"） |

v2 的 Send 载荷 `ToolCallWithContext` 定义在 `tool_node.py`：

```python
class ToolCallWithContext(TypedDict):
    tool_call: ToolCall
    __type: Literal["tool_call_with_context"]
    """Type to parameterize the payload.
    Using "__" as a prefix to be defensive against potential name collisions with
    regular user state."""
    state: Any
    """The state is provided as additional context."""
```

docstring 点明了动机：*"The Send API is used in create_agent to distribute tool calls in parallel and support human-in-the-loop workflows where graph execution may be paused for an indefinite time."*——**为无限期挂起的 HITL 而生**。

### 1.12 步数保护：remaining_steps

```python
def _are_more_steps_needed(state, response) -> bool:
    has_tool_calls = isinstance(response, AIMessage) and response.tool_calls
    all_tools_return_direct = (
        all(call["name"] in should_return_direct for call in response.tool_calls)
        if isinstance(response, AIMessage) else False)
    remaining_steps = _get_state_value(state, "remaining_steps", None)
    if remaining_steps is not None:
        if remaining_steps < 1 and all_tools_return_direct:
            return True
        elif remaining_steps < 2 and has_tool_calls:
            return True
    return False
```

**解析**：`remaining_steps` 是托管值（≈ `recursion_limit - 已走步数`）。当模型还想调工具但剩余步数不足 2（一轮「调工具 + 回 LLM」至少 2 步；全是 return_direct 工具时只需 1 步）时，agent 节点**丢弃模型响应**，改写入一条固定 AIMessage：

> `"Sorry, need more steps to process this request."`

然后自然走向 END。这是一个**软着陆**设计：不抛 `GraphRecursionError`，调用方总能拿到合法的消息历史（不会出现有 tool_calls 却无 ToolMessage 的残缺尾巴）。

### 1.13 历史校验：_validate_chat_history

每次调模型前强制检查「每个 AIMessage 的 tool_call 都有对应 ToolMessage」：

```python
def _validate_chat_history(messages) -> None:
    all_tool_calls = [tc for m in messages if isinstance(m, AIMessage) for tc in m.tool_calls]
    tool_call_ids_with_results = {m.tool_call_id for m in messages if isinstance(m, ToolMessage)}
    tool_calls_without_results = [tc for tc in all_tool_calls
                                  if tc["id"] not in tool_call_ids_with_results]
    if tool_calls_without_results:
        raise ValueError(create_error_message(
            "Found AIMessages with tool_calls that do not have a corresponding ToolMessage. ...",
            error_code=ErrorCode.INVALID_CHAT_HISTORY))
```

**解析**：绝大多数 LLM 供应商要求 tool_call / ToolMessage 严格配对，否则 API 直接 400。这条校验把错误**提前到进模型之前**、并给出带排查链接的明确报错（`INVALID_CHAT_HISTORY`）。实践中最常见的触发方式：用 `update_state` 手工往历史里塞了带 tool_calls 的 AIMessage 却没补 ToolMessage。

## 2. ToolNode 完全解析

`ToolNode` 是 prebuilt 里最重的类（`tool_node.py` 全文 2030 行），承担：工具查找与校验、参数注入、并行执行、错误处理、Command 归一、流式输出、拦截器。它继承 `RunnableCallable`，因此本身就是一个可 `invoke` / `ainvoke` 的 Runnable，可独立于 `create_react_agent` 使用。

### 2.1 构造方法和参数

```python
class ToolNode(RunnableCallable):
    name: str = "tools"

    def __init__(
        self,
        tools: Sequence[BaseTool | Callable],
        *,
        name: str = "tools",
        tags: list[str] | None = None,
        handle_tool_errors: bool | str | Callable[..., str]
            | type[Exception] | tuple[type[Exception], ...] = _default_handle_tool_errors,
        messages_key: str = "messages",
        wrap_tool_call: ToolCallWrapper | None = None,
        awrap_tool_call: AsyncToolCallWrapper | None = None,
    ) -> None:
        super().__init__(self._func, self._afunc, name=name, tags=tags, trace=False)
        self._tools_by_name: dict[str, BaseTool] = {}
        self._injected_args: dict[str, _InjectedArgs] = {}
        self._handle_tool_errors = handle_tool_errors
        self._messages_key = messages_key
        self._wrap_tool_call = wrap_tool_call
        self._awrap_tool_call = awrap_tool_call
        for tool in tools:
            if not isinstance(tool, BaseTool):
                tool_ = create_tool(cast("type[BaseTool]", tool))
            else:
                tool_ = tool
            self._tools_by_name[tool_.name] = tool_
            # Build injected args mapping once during initialization in a single pass
            self._injected_args[tool_.name] = _get_all_injected_args(tool_)
```

参数说明：

| 参数 | 作用 |
|---|---|
| `tools` | `BaseTool` 或裸函数序列；裸函数经 `create_tool` 自动转换（从类型注解 + docstring 推断 schema） |
| `name` / `tags` | 节点标识与元数据（调试、可视化、LangSmith 过滤） |
| `handle_tool_errors` | 错误处理策略，六种取值见 §2.5；**默认不是 True**，而是只兜参数校验错的 `_default_handle_tool_errors` |
| `messages_key` | 状态里消息列表的键名，输入输出都用它；自定义 state schema 用别的键名时改这里 |
| `wrap_tool_call` / `awrap_tool_call` | 同步/异步工具调用拦截器（§2.8）；async 版缺省时异步路径回落到同步版 |

两个关键的**编译期预处理**：

1. `tools_by_name`：名字→工具的路由表（公开只读 property）；
2. `_injected_args`：**每个工具的注入需求在构造时一次性反射完成**（`_get_all_injected_args`），执行期零反射开销——源码注释原话 *"Build injected args mapping once during initialization in a single pass"*。

### 2.2 输入 / 输出格式

类 docstring 定义了三种输入形态，`_parse_input` 是判别器：

```python
def _parse_input(self, input) -> tuple[list[ToolCall], Literal["list", "dict", "tool_calls"]]:
    if isinstance(input, list):
        if isinstance(input[-1], dict) and input[-1].get("type") == "tool_call":
            input_type = "tool_calls"                 # ③ 直接给 ToolCall 列表
            return cast("list[ToolCall]", input), input_type
        input_type = "list"                           # ② 消息列表
        messages = input
    elif isinstance(input, dict) and input.get("__type") == "tool_call_with_context":
        input_with_ctx = cast("ToolCallWithContext", input)
        input_type = "tool_calls"                     # ④ v2 Send 载荷（单调用）
        return [input_with_ctx["tool_call"]], input_type
    elif isinstance(input, dict) and (messages := input.get(self._messages_key, [])):
        input_type = "dict"                           # ① 图状态 dict
    elif messages := getattr(input, self._messages_key, []):
        input_type = "dict"                           # ①' dataclass/Pydantic 状态
    else:
        raise ValueError("No message found in input")

    latest_ai_message = next(m for m in reversed(messages) if isinstance(m, AIMessage))
    return list(latest_ai_message.tool_calls), input_type
```

| 输入 | input_type | 说明 |
|---|---|---|
| `{"messages": [AIMessage(..., tool_calls=[...])]}` | `"dict"` | 图状态，最常见 |
| `[AIMessage(..., tool_calls=[...])]` | `"list"` | 裸消息列表 |
| `[{"name": ..., "args": ..., "id": ..., "type": "tool_call"}]` | `"tool_calls"` | 直接下发调用（程序化调用 / 测试） |
| `{"__type": "tool_call_with_context", "tool_call": ..., "state": ...}` | `"tool_calls"` | v2 Send 载荷，**单调用 + 内联状态快照** |

注意 ①② 形态取的是**倒序第一条 AIMessage** 的 tool_calls——ToolNode 只执行「最新一轮」的调用。输出与 input_type 对称：

- `"dict"` 输入 → `{"messages": [ToolMessage, ...]}`（键名 = `messages_key`）
- `"list"` / `"tool_calls"` 输入 → `[ToolMessage, ...]`
- 工具返回 `Command` 时 → `[Command | {"messages": [...]} ...]` 混合列表，交给 LangGraph 归并（§2.7）

### 2.3 工具执行流程（同步路径逐步拆解）

`_func` 主流程：

```python
def _func(self, input, config, runtime) -> Any:
    tool_calls, input_type = self._parse_input(input)
    config_list = get_config_list(config, len(tool_calls))

    # Construct ToolRuntime instances at the top level for each tool call
    tool_runtimes = []
    for call, cfg in zip(tool_calls, config_list, strict=False):
        state = self._extract_state(input, cfg)
        tool_runtime = ToolRuntime(
            state=state, tool_call_id=call["id"], config=cfg,
            context=runtime.context, store=runtime.store,
            stream_writer=runtime.stream_writer,
            tools=list(self.tools_by_name.values()),
            execution_info=runtime.execution_info, server_info=runtime.server_info,
        )
        tool_runtimes.append(tool_runtime)

    with get_executor_for_config(config) as executor:
        outputs = list(executor.map(self._run_one, tool_calls, input_types, tool_runtimes))

    return self._combine_tool_outputs(outputs, input_type)
```

`_extract_state` 决定每个调用看到的「状态」是什么：

```python
def _extract_state(self, input, config):
    """Three input shapes:
    - `ToolCallWithContext` dict — legacy Send payload carrying an inlined
      state snapshot; return `input["state"]`.
    - list of `ToolCall` dicts — new Send payload with no inlined state;
      hydrate state from channels via `CONFIG_KEY_READ`.
    - regular graph state (dict/list/BaseModel) — return `input` as-is."""
    if isinstance(input, dict) and input.get("__type") == "tool_call_with_context":
        return input["state"]
    if (isinstance(input, list) and input and isinstance(input[-1], dict)
            and input[-1].get("type") == "tool_call"):
        read = config.get(CONF, {}).get(CONFIG_KEY_READ)
        if read is None:
            return {}
        channels = read.args[1]
        return cast("dict[str, Any]", read(list(channels), True))
    return input
```

**解析**：直接给 ToolCall 列表（无状态载荷）时，ToolNode 会尝试通过 Pregel 安装在 config 里的 `CONFIG_KEY_READ` 回调**从图通道现读一份状态**，保证 `InjectedState` 依然可用；脱离图运行（read 为 None）则给空 dict。

单个调用的执行 `_run_one` → `_execute_tool_sync`：

```python
def _run_one(self, call, input_type, tool_runtime):
    # Validation is deferred to _execute_tool_sync to allow interceptors
    # to short-circuit requests for unregistered tools
    tool = self.tools_by_name.get(call["name"])
    tool_request = ToolCallRequest(tool_call=call, tool=tool,
                                   state=tool_runtime.state, runtime=tool_runtime)
    if self._wrap_tool_call is None:
        return self._execute_tool_sync(tool_request, input_type, tool_runtime.config)
    def execute(req):  # Can be called multiple times
        return self._execute_tool_sync(req, input_type, config)
    try:
        return self._wrap_tool_call(tool_request, execute)
    except Exception as e:
        if not self._handle_tool_errors:
            raise
        content = _handle_tool_error(e, flag=self._handle_tool_errors)
        return ToolMessage(content=content, name=..., tool_call_id=..., status="error")
```

```python
def _execute_tool_sync(self, request, input_type, config):
    call, tool = request.tool_call, request.tool
    if tool is None:                                  # ① 工具未注册
        if invalid_tool_message := self._validate_tool_call(call):
            return invalid_tool_message
        raise TypeError(f"Tool {call['name']} is not registered with ToolNode")

    injected_call = self._inject_tool_args(call, request.runtime, tool)   # ② 注入
    call_args = {**injected_call, "type": "tool_call"}

    try:
        try:
            response = tool.invoke(call_args, config)                     # ③ 执行
        except ValidationError as exc:                                    # ④ 参数校验错
            injected = self._injected_args.get(call["name"])
            filtered_errors = _filter_validation_errors(exc, injected)
            raise ToolInvocationError(call["name"], exc, call["args"], filtered_errors) from exc
        return self._normalize_tool_response(response, request.tool_call, input_type)  # ⑤ 归一
    except GraphBubbleUp:                                                 # ⑥ interrupt 直通
        raise
    except Exception as e:                                                # ⑦ 策略化错误处理
        ...
        return ToolMessage(content=content, name=call["name"],
                           tool_call_id=call["id"], status="error")
```

七步流水线小结：

1. **工具名校验**——模型幻觉出不存在的工具名时不抛异常，而是回一条 `status="error"` 的 ToolMessage，模板：`"Error: {requested_tool} is not a valid tool, try one of [{available_tools}]."`，让模型自纠。校验**故意推迟**到 execute 阶段，好让拦截器能对未注册工具短路处理（`ToolCallRequest.tool` 允许为 `None`）。
2. **参数注入**——state / store / runtime（§2.6）。
3. **执行**——`tool.invoke(call_args, config)`。
4. **ValidationError 包装**——转成 `ToolInvocationError`，并**过滤掉注入参数相关的错误条目**（`_filter_validation_errors`）：LLM 控制不了的参数（state/store/runtime）不应出现在给 LLM 看的报错里，避免它试图「修复」根本看不见的参数。
5. **响应归一**——ToolMessage / Command / 列表 三态校验（§2.7）。
6. **GraphBubbleUp 直通**——interrupt 异常永远原样上抛，**任何错误处理策略都吞不掉它**（§2.9）。
7. **策略化错误处理**——按 `handle_tool_errors` 决定吞掉（回 error ToolMessage）还是上抛（§2.5）。

### 2.4 多工具并行执行

- **同步**：`get_executor_for_config(config)` 建线程池，`executor.map(self._run_one, ...)` 并行跑所有调用。
- **异步**：`_afunc` 里构造协程列表后 `asyncio.gather(*coros)` 并发。

```python
coros = []
for call, tool_runtime in zip(tool_calls, tool_runtimes, strict=False):
    coros.append(self._arun_one(call, input_type, tool_runtime))
outputs = await asyncio.gather(*coros)
```

`get_config_list(config, len(tool_calls))` 为每个调用复制出独立 config（独立 run_id / 回调链），保证并行调用在追踪系统里是**并列的兄弟 span** 而不是互相嵌套。v2 模式下并行进一步上升到图层：每个 Send 是独立 Pregel 任务，可独立重试、独立 interrupt。

### 2.5 error_handling 错误处理策略

`handle_tool_errors` 支持六种取值，语义在 docstring 中列明：

| 取值 | 行为 |
|---|---|
| `True` | 捕获**所有**异常，用默认模板 `"Error: {error}\n Please fix your mistakes."`（error 为 `repr(e)`）回 error ToolMessage |
| `str` | 捕获所有异常，用这个固定字符串作为错误消息 |
| `type[Exception]` | **只**捕获该类型异常，默认模板；其它类型上抛 |
| `tuple[type[Exception], ...]` | 只捕获元组内类型 |
| `Callable[..., str]` | 捕获「函数签名标注的异常类型」，以 `handler(e)` 的返回值为错误消息 |
| `False` | 完全关闭错误处理，一切异常直接上抛 |

**默认值**是个精确的函数而非 `True`：

```python
def _default_handle_tool_errors(e: Exception) -> str:
    """Default error handler for tool errors.
    If the tool is a tool invocation error, return its message.
    Otherwise, raise the error."""
    if isinstance(e, ToolInvocationError):
        return e.message
    raise e
```

即**默认只兜「模型传参不合法」（ToolInvocationError，可自纠），工具运行时错误（网络炸、数据库炸）一律上抛**——这是个容易被误解的重要默认值：`ToolNode` 默认**不是**「所有错误都变成 ToolMessage」。

可调用处理器的类型推断 `_infer_handled_types` 值得一看：

```python
def _infer_handled_types(handler) -> tuple[type[Exception], ...]:
    sig = inspect.signature(handler)
    params = list(sig.parameters.values())
    if params:
        if params[0].name in ["self", "cls"] and len(params) == 2:
            first_param = params[1]
        else:
            first_param = params[0]
        type_hints = get_type_hints(handler)
        if first_param.name in type_hints:
            origin = get_origin(first_param.annotation)
            if origin in [Union, UnionType]:
                args = get_args(first_param.annotation)
                if all(issubclass(arg, Exception) for arg in args):
                    return tuple(args)
                raise ValueError("All types in the error handler error annotation must be Exception types...")
            exception_type = type_hints[first_param.name]
            if Exception in exception_type.__mro__:
                return (exception_type,)
            raise ValueError("Arbitrary types are not supported in the error handler signature...")
    return (Exception,)   # 无标注 ⇒ 兜全部（向后兼容）
```

**解析**：处理器**第一个参数的类型注解**决定它接管哪些异常。写 `def h(e: ValueError) -> str` 就只兜 ValueError；写 `def h(e: Union[ValueError, TypeError])` 兜两种；不写注解兜全部。这样「按类型分流」可以叠多个策略时不互相干扰。执行时的匹配逻辑（`_execute_tool_sync` 第 ⑦ 步）：

```python
handled_types = ...  # 依 handle_tool_errors 形态推导
if not self._handle_tool_errors or not isinstance(e, handled_types):
    raise
content = _handle_tool_error(e, flag=self._handle_tool_errors)
return ToolMessage(content=content, name=call["name"],
                   tool_call_id=call["id"], status="error")
```

错误消息生成 `_handle_tool_error`：

```python
if isinstance(flag, (bool, tuple)) or (isinstance(flag, type) and issubclass(flag, Exception)):
    content = TOOL_CALL_ERROR_TEMPLATE.format(error=repr(e))
elif isinstance(flag, str):
    content = flag
elif callable(flag):
    content = flag(e)
else:
    raise ValueError("Got unexpected type of `handle_tool_error`. ...")
```

最终错误 ToolMessage 都带 `status="error"`——下游（模型或应用代码）可据此区分成败。

`ToolInvocationError` 本体（继承 `ToolException`）保存了结构化上下文：`tool_name`、`tool_kwargs`、原始 `source: ValidationError`、过滤后的 `filtered_errors`，消息模板：

```python
TOOL_INVOCATION_ERROR_TEMPLATE = (
    "Error invoking tool '{tool_name}' with kwargs {tool_kwargs} with error:\n"
    " {error}\n Please fix the error and try again.")
```

### 2.6 auto-inject：状态 / 存储 / 运行时注入

这是 ToolNode 最有特色的机制：**让工具拿到图上下文，同时对 LLM 完全不可见**。三个标注：

**① `InjectedState(field=None)`**——注入整个状态或某个字段：

```python
@tool
def state_tool(x: int, state: Annotated[dict, InjectedState]) -> str:
    """Do something with state."""
    ...

@tool
def foo_tool(x: int, foo: Annotated[str, InjectedState("foo")]) -> str:
    """Extract only state["foo"]."""
    ...
```

它继承 `InjectedToolArg`，因此**自动从呈现给模型的 tool schema 中剔除**——模型只看到 `x`。

**② `InjectedStore()`**——注入编译时传入的 `BaseStore`（跨会话持久化）。图没配 store 时执行期抛：

```python
if injected.store:
    if tool_runtime.store is None:
        raise ValueError("Cannot inject store into tools with InjectedStore annotations - "
                         "please compile your graph with a store.")
    injected_args[injected.store] = tool_runtime.store
```

**③ `ToolRuntime`**——1.x 新增的「全家桶」注入，一个 dataclass 打包所有运行时上下文：

```python
@dataclass
class ToolRuntime(_DirectlyInjectedToolArg, Generic[ContextT, StateT]):
    state: StateT                       # 当前图状态
    context: ContextT                   # 运行期上下文（与 Runtime 共享）
    config: RunnableConfig              # 当前执行的 config
    stream_writer: StreamWriter         # 自定义流写入
    tool_call_id: str | None            # 本次调用 id
    store: BaseStore | None             # 持久化存储
    tools: list[BaseTool] = field(default_factory=list)   # 全部可用工具
    execution_info: ExecutionInfo | None = None
    server_info: ServerInfo | None = None
```

用法**无需 Annotated**：`def my_tool(x: int, runtime: ToolRuntime) -> str`。docstring 特别强调它与 `langgraph.runtime.Runtime` 的区别：`ToolRuntime` 多了 `config`、`state`、`tool_call_id` 三个工具专属字段。

**注入需求的反射分析**在构造期完成，`_get_all_injected_args`：

```python
def _get_all_injected_args(tool: BaseTool) -> _InjectedArgs:
    full_schema = tool.get_input_schema()
    schema_annotations = get_all_basemodel_annotations(full_schema)
    func = getattr(tool, "func", None) or getattr(tool, "coroutine", None)
    func_annotations = get_type_hints(func, include_extras=True) if func else {}
    # Combine both annotation sources, preferring schema annotations
    all_annotations = {**func_annotations, **schema_annotations}

    for name, type_ in all_annotations.items():
        if _is_injected_arg_type(type_):
            all_injected_keys.add(name)          # 含自定义 InjectedToolArg 子类
        if name == "runtime":
            runtime_arg = name                   # 参数名叫 runtime 即视为运行时注入
        if state_inj := _get_injection_from_type(type_, InjectedState):
            if isinstance(state_inj, InjectedState) and state_inj.field:
                state_args[name] = state_inj.field
                field_info = full_schema.model_fields.get(name)
                if field_info and not field_info.is_required():
                    _optional_state_args.add(name)   # 可选字段缺失不报错
            else:
                state_args[name] = None          # None ⇒ 注入整个 state
        if _get_injection_from_type(type_, InjectedStore):
            store_arg = name
        if _get_injection_from_type(type_, ToolRuntime):
            runtime_arg = name
    return _InjectedArgs(state=state_args, store=store_arg, runtime=runtime_arg,
                         all_injected_keys=all_injected_keys,
                         _optional_state_args=_optional_state_args)
```

产物 `_InjectedArgs` 是「参数名 → 注入来源」的映射表，注释里给了直观示例：

```python
# def my_tool(x: int,
#             messages: Annotated[list, InjectedState("messages")],
#             full_state: Annotated[dict, InjectedState()],
#             store: Annotated[BaseStore, InjectedStore()],
#             runtime: ToolRuntime) -> str: ...
#
# _InjectedArgs(state={"messages": "messages", "full_state": None},
#               store="store", runtime="runtime")
```

执行期注入 `_inject_tool_args` 的核心片段：

```python
# Inject state（dict 状态按字段取值；缺字段且非可选 ⇒ KeyError）
for tool_arg, state_field in injected.state.items():
    if not state_field:
        injected_args[tool_arg] = state
    elif state_field in state:
        injected_args[tool_arg] = state[state_field]
    elif tool_arg not in injected._optional_state_args:
        raise KeyError(state_field)

# Strip any caller-supplied values for injected args, then add
# back only trusted values. This prevents an LLM from forging
# hidden InjectedToolArg fields via ToolCall.args.
stripped_args = {k: v for k, v in tool_call_copy["args"].items()
                 if k not in injected.all_injected_keys}
tool_call_copy["args"] = {**stripped_args, **injected_args}
```

**解析**：最后这段「先剥离再回填」是**安全设计**——即使 LLM 在 tool_call 的 args 里伪造 `{"state": {...}}`，也会被剥掉、只留系统注入的可信值。注入发生在「模型产出 tool_call 之后、工具执行之前」。

> ⚠️ **本项目实测过的坑**：用户工具模块顶部**不要写 `from __future__ import annotations`**——它使注解变成惰性字符串，`ToolRuntime` 注入会**静默失效**（工具收到的是字符串而非 runtime 对象，或注入被跳过）。判据：`'runtime' in tool._injected_args_keys`。库自身模块（如 tool_node.py）带这行没问题，坑只在**用户工具定义模块**。

### 2.7 Command 返回值与输出归一

工具除了返回普通值（经 `msg_content_output` 转成字符串/内容块），还可以返回 `Command` 直接操纵图——更新状态、跳转节点、甚至指挥父图。`_normalize_tool_response` 是三态分派：

```python
def _normalize_tool_response(self, response, tool_call, input_type):
    if isinstance(response, Command):
        return self._validate_tool_command(response, tool_call, input_type)
    if isinstance(response, ToolMessage):
        response.content = cast("str | list", msg_content_output(response.content))
        return response
    if isinstance(response, list):
        if all(isinstance(r, (Command, ToolMessage)) for r in response):
            return self._validate_tool_command_list(response, tool_call, input_type)
        raise TypeError(f"Tool {tool_call['name']} returned a list with invalid element types...")
    raise TypeError(f"Tool {tool_call['name']} returned unexpected type: {type(response)}")
```

`_validate_tool_command` 的三条硬规则：

1. `Command.update` 是 dict ⇒ 只允许 dict/`tool_calls` 输入形态；是 list ⇒ 只允许 list 输入形态（防止 update 形态与图状态形态错配）；
2. update 里的消息会被 `convert_to_messages` 归一，且**必须包含一条 `tool_call_id` 与本次调用匹配的 ToolMessage**（发给当前图时），否则 `ValueError`——依旧是「call/result 必须配对」铁律；例外：`Command(graph=Command.PARENT, ...)`（指挥父图，本次调用由父图层面收尾）和 `[RemoveMessage(id=REMOVE_ALL_MESSAGES)]`（清空全部消息）；
3. 匹配的 ToolMessage 会被自动补上 `name`。

一个工具返回**多条** Command/ToolMessage 的列表时，`_validate_tool_command_list` 要求全列表中**恰好一条**终结 ToolMessage（可在顶层或嵌在某个 Command.update 里）。

多调用输出合并 `_combine_tool_outputs`：

```python
# combine all parent commands with goto into a single parent command
parent_command: Command | None = None
for output in flat_outputs:
    if isinstance(output, Command):
        if (output.graph is Command.PARENT and isinstance(output.goto, list)
                and all(isinstance(send, Send) for send in output.goto)):
            if parent_command:
                parent_command = replace(parent_command,
                                         goto=parent_command.goto + output.goto)
            else:
                parent_command = Command(graph=Command.PARENT, goto=output.goto)
        else:
            combined_outputs.append(output)
    else:
        combined_outputs.append([output] if input_type == "list"
                                else {self._messages_key: [output]})
if parent_command:
    combined_outputs.append(parent_command)
```

**解析**：并行工具各自返回「发给父图的 Send 命令」时，把它们**合并成一个** parent Command——因为同一超步里对父图的多条 goto 指令必须归并成一个更新，否则父图状态机会拒绝。无任何 Command 时走兼容老路：直接 `{messages_key: [...]}`。

`msg_content_output` 处理普通返回值：str 和「内容块列表」原样通过；其它对象 `json.dumps(output, ensure_ascii=False)`（中文不转义）；JSON 序列化失败退到 `str(output)`。

### 2.8 wrap_tool_call：工具调用拦截器

1.x 新增的中间件挂点，签名：

```python
ToolCallWrapper = Callable[
    [ToolCallRequest, Callable[[ToolCallRequest], ToolMessage | Command]],
    ToolMessage | Command,
]
```

拦截器拿到 `ToolCallRequest`（含 `tool_call` / `tool` / `state` / `runtime` 四元组）和一个**可多次调用**的 `execute` 回调。docstring 给出的四种典型模式：

```python
# ① 直通
def handler(request, execute):
    return execute(request)

# ② 改写请求（不可变模式：request.override() 返回新实例）
def handler(request, execute):
    modified_call = {**request.tool_call, "args": {...}}
    return execute(request.override(tool_call=modified_call))

# ③ 重试（execute 可多次调用，每次独立无状态）
def handler(request, execute):
    for attempt in range(3):
        result = execute(request)
        if isinstance(result, ToolMessage) and result.status != "error":
            return result
    return result

# ④ 缓存短路（根本不调 execute）
def handler(request, execute):
    if cached := get_cache(request):
        return ToolMessage(content=cached, tool_call_id=request.tool_call["id"])
    result = execute(request)
    save_cache(request, result)
    return result
```

`ToolCallRequest` 直接赋值属性会触发 DeprecationWarning，官方要求走 `override()`（内部 `dataclasses.replace`，保持不可变）。注意拦截器自己抛的异常同样落入 `handle_tool_errors` 策略（`_run_one` 的 try/except）。`langchain.agents.create_agent` 的 `AgentMiddleware.wrap_tool_call` 就是这一机制的类型安全包装。

### 2.9 与 interrupt 的集成

`_execute_tool_sync` / `_execute_tool_async` 里那段注释是官方对「interrupt 为什么穿透错误处理」的权威解释：

```python
# GraphInterrupt is a special exception that will always be raised.
# It can be triggered in the following scenarios,
# Where GraphInterrupt(GraphBubbleUp) is raised from an `interrupt` invocation
# most commonly:
# (1) a GraphInterrupt is raised inside a tool
# (2) a GraphInterrupt is raised inside a graph node for a graph called as a tool
# (3) a GraphInterrupt is raised when a subgraph is interrupted inside a graph
#     called as a tool
# (2 and 3 can happen in a "supervisor w/ tools" multi-agent architecture)
except GraphBubbleUp:
    raise
```

**解析**：

- `GraphInterrupt` 继承 `GraphBubbleUp`，ToolNode 对 `GraphBubbleUp` **无条件重抛**，排在所有错误处理之前——所以 `handle_tool_errors=True` 也**不会**把人工中断吞成 error ToolMessage。
- 三种触发场景：工具内直接 `interrupt()`；工具本身是子图、子图节点内 interrupt；子图内部再嵌套中断。「supervisor 把 agent 当工具调」的多 Agent 架构属于 ②③。
- v2 的「一 call 一 Send」设计让中断粒度细化到单个工具调用：同批的其它调用正常完成并写入 checkpoint，被中断的调用挂起等 `Command(resume=...)`。

### 2.10 tools_condition 路由函数

自建图时与 ToolNode 配对的标准条件边：

```python
def tools_condition(state, messages_key="messages") -> Literal["tools", "__end__"]:
    if isinstance(state, list):
        ai_message = state[-1]
    elif (isinstance(state, dict) and (messages := state.get(messages_key, []))) or (
            messages := getattr(state, messages_key, [])):
        ai_message = messages[-1]
    else:
        raise ValueError(f"No messages found in input state to tool_edge: {state}")
    if hasattr(ai_message, "tool_calls") and len(ai_message.tool_calls) > 0:
        return "tools"
    return "__end__"
```

逻辑一句话：**最后一条消息带 tool_calls 就去 `"tools"`，否则 `"__end__"`**。支持 list / dict / 对象属性三种状态形态，`messages_key` 可定制。它就是 `create_react_agent` 里 `should_continue` 的极简公开版。

## 3. interrupt 机制详解

### 3.1 prebuilt/interrupt.py：HITL 协议类型

这个文件**不含任何执行逻辑**，只定义「人机审批协议」的四个 TypedDict（前三个已弃用，迁往 `langchain.agents.interrupt`）：

```python
class HumanInterruptConfig(TypedDict):
    """Configuration that defines what actions are allowed for a human interrupt."""
    allow_ignore: bool     # 人可以选择忽略/跳过本步
    allow_respond: bool    # 人可以给出文字反馈
    allow_edit: bool       # 人可以编辑内容/状态
    allow_accept: bool     # 人可以直接批准

class ActionRequest(TypedDict):
    action: str            # 请求的动作名，如 "run_command"
    args: dict             # 动作参数

class HumanInterrupt(TypedDict):
    action_request: ActionRequest
    config: HumanInterruptConfig
    description: str | None
```

docstring 中的标准用法——**把结构化的审批请求作为 `interrupt()` 的载荷**：

```python
request = HumanInterrupt(
    action_request=ActionRequest(action="run_command",
                                 args={"command": "ls", "args": ["-l"]}),
    config=HumanInterruptConfig(allow_ignore=True, allow_respond=True,
                                allow_edit=False, allow_accept=True),
    description="Please review the command before execution",

```

人的答复用 `HumanResponse` 表达（这个类未弃用）：

```python
class HumanResponse(TypedDict):
    type: Literal["accept", "ignore", "response", "edit"]
    args: None | str | ActionRequest
    # accept/ignore ⇒ None；response ⇒ str；edit ⇒ 修改后的 ActionRequest
```

**解析**：这套类型的价值在于**前端通用化**——审批 UI 只要认识 `HumanInterrupt` 结构，就能对任何图渲染「批准 / 忽略 / 回复 / 编辑」四种操作，而不需要为每个业务定制协议。`langchain.agents` 的 HITL 中间件即以此为载荷。

### 3.2 interrupt() 函数（langgraph.types）

真正的执行原语在 `langgraph/types.py`（prebuilt 只是重用了它）。函数文档的关键承诺：

> In a given node, the first invocation of this function raises a `GraphInterrupt` exception, halting execution. ... A client resuming the graph must use the `Command` primitive ... **The graph resumes from the start of the node, re-executing all logic.**

实现（1.2.9 源码）：

```python
def interrupt(value: Any) -> Any:
    from langgraph._internal._constants import (
        CONFIG_KEY_CHECKPOINT_NS, CONFIG_KEY_SCRATCHPAD, CONFIG_KEY_SEND, RESUME)
    from langgraph.config import get_config
    from langgraph.errors import GraphInterrupt

    conf = get_config()["configurable"]
    # track interrupt index
    scratchpad = conf[CONFIG_KEY_SCRATCHPAD]
    idx = scratchpad.interrupt_counter()
    # find previous resume values
    if scratchpad.resume:
        if idx < len(scratchpad.resume):
            conf[CONFIG_KEY_SEND]([(RESUME, scratchpad.resume)])
            return scratchpad.resume[idx]
    # find current resume value
    v = scratchpad.get_null_resume(True)
    if v is not None:
        assert len(scratchpad.resume) == idx, (scratchpad.resume, idx)
        scratchpad.resume.append(v)
        conf[CONFIG_KEY_SEND]([(RESUME, scratchpad.resume)])
        return v
    # no resume value found
    raise GraphInterrupt((Interrupt.from_ns(...),))
```

**逐段解析**：

1. **`idx = scratchpad.interrupt_counter()`**——每个任务有自己的 scratchpad（草稿区），记录本任务内 `interrupt()` 的调用序号。同一节点里多个 interrupt 靠这个序号与 resume 值**按序配对**（docstring："LangGraph matches resume values to interrupts based on their order in the node"）。
2. **历史 resume 命中**——节点被恢复后是**从头重放**的：先前已消费过的 resume 值存在 `scratchpad.resume` 列表里，重放到第 idx 个 interrupt 时直接返回旧值，不再暂停。这就是「恢复 = 重执行整个节点」却不会反复弹审批的原因。
3. **当前 resume 值**——`get_null_resume` 取出客户端本次通过 `Command(resume=...)` 送进来的值，追加进 resume 列表并**回写通道**（`CONFIG_KEY_SEND [(RESUME, ...)]`，随 checkpoint 持久化），然后作为返回值。
4. **无值可恢复**——抛 `GraphInterrupt`，携带 `Interrupt.from_ns(value, ns)`；其 `id` 是命名空间的 xxh3_128 哈希：

```python
@classmethod
def from_ns(cls, value: Any, ns: str) -> Interrupt:
    return cls(value=value, id=xxh3_128_hexdigest(ns.encode()))
```

`Interrupt` 数据类只有两个字段：`value`（要展示给人的载荷）和 `id`（可用于定向恢复）。

**⚠️ 副作用警告**：由于恢复时**节点从头重放**，interrupt 之前的所有代码会执行两次以上。有副作用的操作（写库、发消息、扣款）必须放在 interrupt **之后**，或自行做幂等。

### 3.3 Command(resume=...) 恢复

`Command` 的 resume 字段（`langgraph/types.py`）：

```python
@dataclass
class Command(Generic[N], ToolOutputMixin):
    graph: str | None = None        # None=当前图；Command.PARENT=最近的父图
    update: Any | None = None       # 状态更新
    resume: dict[str, Any] | Any | None = None
    """Value to resume execution with. To be used together with interrupt().
    Can be one of the following:
    - Mapping of interrupt ids to resume values
    - A single value with which to resume the next interrupt"""
    goto: Send | Sequence[Send | N] | N = ()
```

两种恢复方式：

```python
# ① 单值：恢复下一个（按序）未决 interrupt
graph.invoke(Command(resume="yes"), config)

# ② 按 id 定向：多个并行 interrupt 时精确分发
graph.invoke(Command(resume={"<interrupt_id>": "yes", "<other_id>": "no"}), config)
```

流式调用时的完整交互回路：

```python
for chunk in graph.stream(inputs, config):
    ...
# chunk 里出现: {'__interrupt__': (Interrupt(value='what is your age?', id='45fda847...'),)}

for chunk in graph.stream(Command(resume="some input from a human!!!"), config):
    ...
# > Received an input from the interrupt: some input from a human!!!
# > {'node': {'human_value': 'some input from a human!!!'}}
```

暂停信息通过两个渠道暴露：流输出的 `__interrupt__` 键；以及状态快照 `graph.get_state(config)` 的 `tasks[].interrupts`（`StateSnapshot` 也带顶层 `interrupts` 字段）。

> **本项目相关经验**：在 langgraph API server 托管的顶层图里，interrupt 可能被 top-level graph 抑制、不出现在常规位置——审批检测必须读 `state.tasks[].interrupts` 而不是只看 `__interrupt__`。

### 3.4 与 checkpointer 的配合

`interrupt()` docstring 原文：**"To use an `interrupt`, you must enable a checkpointer, as the feature relies on persisting the graph state."**

配合关系拆开看：

1. 抛 `GraphInterrupt` 前，Pregel 已把当前超步的状态写入 checkpoint——暂停点即持久点，进程重启后仍可恢复；
2. resume 值消费记录（`RESUME` 通道写入）同样落 checkpoint，保证「重放不重弹」；
3. 恢复必须带同一 `thread_id` 的 config——checkpointer 按线程找回暂停现场；
4. 没有 checkpointer 时 `interrupt()` 的 GraphInterrupt 无处安放，图直接失败。

### 3.5 GraphInterrupt 异常链

```python
# langgraph/errors.py
class GraphBubbleUp(Exception):
    pass

class GraphInterrupt(GraphBubbleUp):
    """Raised when a subgraph is interrupted, suppressed by the root graph.
    Never raised directly, or surfaced to the user."""
    def __init__(self, interrupts: Sequence[Interrupt] = ()) -> None:
        super().__init__(interrupts)
```

完整链条：

```
interrupt(value)
   └─ raise GraphInterrupt((Interrupt(value, id=xxh3(ns)),))
        └─ GraphInterrupt ⊂ GraphBubbleUp ⊂ Exception
             ├─ ToolNode：except GraphBubbleUp: raise   （错误处理吞不掉，§2.9）
             ├─ 子图：向上冒泡到父图（父图工具/节点里表现为「子图中断」）
             └─ 根图 Pregel：捕获并【抑制】，不再上抛给用户，
                            转为 __interrupt__ 流事件 + snapshot.tasks[].interrupts，
                            保存 checkpoint，本次 invoke/stream 正常返回
```

同族的 `GraphDrained`（优雅停机排空）、`ParentCommand`（子图向父图发命令）也继承 `GraphBubbleUp`，共享「基础设施异常，用户代码不得拦截」的语义。旧 API `NodeInterrupt` 已弃用，指向 `interrupt()`。

**实践守则**：在自己的节点/中间件里写 `except Exception` 时，务必先放行 `GraphBubbleUp`（`except GraphBubbleUp: raise` 在前），否则会静默破坏中断机制。

### 3.6 静态中断与动态中断对照

| | `interrupt_before/after=["tools"]` | 节点内 `interrupt(value)` |
|---|---|---|
| 声明位置 | 编译期（`compile()` / `create_react_agent` 参数） | 运行期代码中，可带条件 |
| 暂停粒度 | 整个节点前/后 | 任意代码点，粒度到单个工具调用（v2） |
| 载荷 | 无（人自己去看 state） | 任意值（如 `HumanInterrupt`），随 `__interrupt__` 事件浮出到客户端 |
| 恢复 | `invoke(None, config)`（也可先 `update_state`） | `invoke(Command(resume=...), config)`，值成为 `interrupt()` 返回值 |
| 典型场景 | 兜底审批、调试观察 | 按工具危险性分级审批、请求补充信息 |

## 4. ToolValidator（ValidationNode）

`tool_validator.py` 提供 `ValidationNode`——一个**只验证、不执行**的节点：对最后一条 AIMessage 的所有 tool_calls 套用 Pydantic schema，通过则回「验证后的 JSON」ToolMessage，失败则回带错误信息的 ToolMessage 供模型重试。整个类已弃用（"Please use `create_agent` from `langchain.agents` with custom tool error handling"），但「生成 → 验证 → 重提示」的模式仍是结构化抽取的标准做法。

构造器接受三种 schema 来源：

```python
def __init__(self, schemas: Sequence[BaseTool | type[BaseModel] | Callable], *,
             format_error=None, name="validation", tags=None) -> None:
    super().__init__(self._func, None, name=name, tags=tags, trace=False)
    self._format_error = format_error or _default_format_error
    self.schemas_by_name: dict[str, type[BaseModel]] = {}
    for schema in schemas:
        if isinstance(schema, BaseTool):
            if schema.args_schema is None:
                raise ValueError(f"Tool {schema.name} does not have an args_schema defined.")
            elif not isinstance(schema.args_schema, type) or not is_basemodel_subclass(schema.args_schema):
                raise ValueError("Validation node only works with tools that have a pydantic BaseModel args_schema...")
            self.schemas_by_name[schema.name] = schema.args_schema
        elif isinstance(schema, type) and issubclass(schema, (BaseModel, BaseModelV1)):
            self.schemas_by_name[schema.__name__] = cast(type[BaseModel], schema)
        elif callable(schema):
            base_model = create_schema_from_function("Validation", schema)
            self.schemas_by_name[schema.__name__] = base_model
        else:
            raise ValueError("Unsupported input to ValidationNode. ...")
```

- `BaseTool` ⇒ 取其 `args_schema`（必须是 Pydantic 类）；
- Pydantic 类（v2 或 v1 均可）⇒ 以类名为键；
- 普通函数 ⇒ `create_schema_from_function` 从签名生成 schema。

核心执行 `_func`：

```python
def _func(self, input, config) -> Any:
    output_type, message = self._get_message(input)   # 取最后一条 AIMessage，否则 ValueError

    def run_one(call: ToolCall) -> ToolMessage:
        schema = self.schemas_by_name[call["name"]]
        try:
            if issubclass(schema, BaseModel):
                output = schema.model_validate(call["args"])
                content = output.model_dump_json()
            elif issubclass(schema, BaseModelV1):
                output = schema.validate(call["args"])
                content = output.json()
            return ToolMessage(content=content, name=call["name"],
                               tool_call_id=cast(str, call["id"]))
        except (ValidationError, ValidationErrorV1) as e:
            return ToolMessage(content=self._format_error(e, call, schema),
                               name=call["name"], tool_call_id=cast(str, call["id"]),
                               additional_kwargs={"is_error": True})

    with get_executor_for_config(config) as executor:
        outputs = [*executor.map(run_one, message.tool_calls)]   # 多调用并行验证
        return outputs if output_type == "list" else {"messages": outputs}
```

**解析**：

- **验证成功**：ToolMessage 内容是 `model_dump_json()`——即经过 validator 清洗后的规范化 JSON，下游可安全 `json.loads`；
- **验证失败**：默认错误文案 `f"{repr(error)}\n\nRespond after fixing all validation errors."`（可用 `format_error` 自定义），并打 `additional_kwargs={"is_error": True}` 标记——**重试路由靠这个标记**（见下方示例的 `should_reprompt`）；
- 多个 tool_calls 用线程池**并行验证**；
- 与 `ToolNode` 的本质区别：**不调用任何工具函数**，保留原始消息与 tool_call id，适合「用 tool-calling 协议做结构化抽取 + 校验重试环」的场景。

docstring 自带的重提示环示例（模型 ⇄ 验证节点循环直到合法）：

```python
builder = StateGraph(Annotated[list, add_messages])
llm = ChatAnthropic(model="claude-3-5-haiku-latest").bind_tools([SelectNumber])
builder.add_node("model", llm)
builder.add_node("validation", ValidationNode([SelectNumber]))
builder.add_edge(START, "model")
builder.add_conditional_edges("model", should_validate)    # 有 tool_calls → validation，否则 END
builder.add_conditional_edges("validation", should_reprompt)  # 有 is_error → 回 model，否则 END
```

## 5. 工具调用流式和变换

这两个下划线模块是 1.x 的新增件，解决「**工具执行过程的增量输出**如何流给消费者」：长跑工具（爬取、生成、批处理）不必等最终结果，可以边跑边吐 delta。三个角色分工：

```
工具代码                     流事件（tools 通道）                 消费端
runtime.emit_output_delta(d) ─► tool-output-delta ─► ToolCallTransformer ─► ToolCallStream.output_deltas
（框架自动）                    tool-started / tool-finished / tool-error       （run.tool_calls 投影）
```

### 5.1 ToolCallStream（_tool_call_stream.py）

模块 docstring：*"In-process handle for a single tool call's streaming execution. Mirrors the shape of `ChatModelStream` from langchain-core but simpler — a tool has one output channel, no content-block multiplexing."*

```python
class ToolCallStream:
    """Scoped view of a single tool call's lifecycle.
    Yielded on `run.tool_calls` once per `tool-started` event. Fields
    are populated as events arrive:
    - `tool_call_id`, `tool_name`, `input`: stable from the start event.
    - `output_deltas`: a `StreamChannel` of delta chunks. ...
    - `output`: terminal payload from `tool-finished`, or `None` ...
    - `error`: terminal error string from `tool-error`, or `None` ...
    - `completed`: True once a terminal event has been observed.
    """
    def __init__(self, tool_call_id: str, tool_name: str,
                 input: dict[str, Any] | None = None) -> None:
        self.tool_call_id = tool_call_id
        self.tool_name = tool_name
        self.input = input
        self._output_deltas: StreamChannel[Any] = StreamChannel()
        self.output: Any = None
        self.error: str | None = None
        self.completed = False
```

生命周期由三个内部方法驱动（只能由 Transformer 调用）：

```python
def _push_delta(self, delta: Any) -> None:
    self._output_deltas.push(delta)

def _finish(self, output: Any) -> None:
    self.output = output
    self.completed = True
    self._output_deltas.close()      # 关闭通道 ⇒ 消费者迭代自然结束

def _fail(self, message: str) -> None:
    self.error = message
    self.completed = True
    self._output_deltas.close()
```

消费方式：`__iter__` / `__aiter__` 直接迭代 delta（同步或异步取决于 run 的启动方式，绑错模式抛 `TypeError`）。`__repr__` 会显示 `running / completed / failed` 三态。docstring 明示：**不由终端用户构造**，只在事件流经 mux 时由 `ToolCallTransformer` 产出。

### 5.2 ToolCallTransformer（_tool_call_transformer.py）

```python
class ToolCallTransformer(StreamTransformer):
    """Project `tools` channel events into `ToolCallStream` handles. ...
    Registered explicitly by users at compile time via
    `builder.compile(transformers=[ToolCallTransformer])` — not a
    default built-in, so the `tools` channel is user-opt-in."""

    _native = True
    required_stream_modes = ("tools",)
```

关键设计点（都来自类 docstring 与源码）：

1. **opt-in**：不是默认变换器，要 `compile(transformers=[ToolCallTransformer])` 显式注册；`required_stream_modes = ("tools",)` 声明它依赖 tools 流模式，框架自动开启。
2. **native 投影**：`_native = True` + `init()` 返回 `{"tool_calls": self._log}`——投影结果作为 `run.tool_calls` 属性直接暴露。
3. **不进主事件日志**：内部用**无名** `StreamChannel[ToolCallStream]`，因为活句柄不可序列化，"should not be injected into the main event log"。线上消费者（wire clients）应订阅原始 `tools` 通道自行重建。
4. **事件分派**（`process`）：

```python
def process(self, event: ProtocolEvent) -> bool:
    if event["method"] != "tools":
        return True
    # Only project events emitted at this transformer's scope. Subgraph
    # events still flow through the parent's mux ... but they belong to
    # the child mini-mux's `tool_calls` projection, not the parent's.
    if tuple(event["params"]["namespace"]) != self.scope:
        return True
    data = event["params"]["data"]
    tool_call_id = data.get("tool_call_id")
    if tool_call_id is None:
        return True
    event_type = data.get("event")

    if event_type == "tool-started":
        stream = self._new_stream(tool_call_id, data.get("tool_name", ""), data.get("input"))
        self._active[tool_call_id] = stream
        self._log.push(stream)                       # 新句柄推上 run.tool_calls
    elif event_type == "tool-output-delta":
        stream = self._active.get(tool_call_id)
        if stream is not None:
            stream._push_delta(data.get("delta"))
    elif event_type == "tool-finished":
        stream = self._active.pop(tool_call_id, None)
        if stream is not None:
            stream._finish(data.get("output"))
    elif event_type == "tool-error":
        stream = self._active.pop(tool_call_id, None)
        if stream is not None:
            stream._fail(data.get("message", ""))
    return True   # Pass-through — wire consumers subscribe to the `tools` channel directly
```

5. **作用域隔离**：子图事件按 `namespace` 匹配分流给子图自己的 mini-mux，父图投影不混入。
6. **收尾兜底**：`finalize()` 把 run 结束时仍未完成的流以 `_finish(None)` 关闭；`fail(err)` 在 run 报错时把所有在飞的流标记 `_fail(str(err))`——**保证消费者的迭代永远能终止**，不会悬挂。

### 5.3 工具侧发射：ToolRuntime.emit_output_delta

delta 的生产端在 `tool_node.py` 的 `ToolRuntime` 上：

```python
def emit_output_delta(self, delta: Any) -> None:
    """Stream a partial output chunk on the `tools` stream channel.
    Reads the per-tool-call writer that `StreamToolCallHandler`
    installs on a ContextVar at `on_tool_start` ... Silent no-op when
    the graph was not run with `"tools"` in `stream_mode` ..."""
    writer = _tool_call_writer.get()
    if writer is None:
        return
    writer(delta)
```

**解析**：工具作者只需 `runtime.emit_output_delta({...})`；writer 由框架在 `on_tool_start` 时通过 ContextVar（`langgraph.pregel._tools._tool_call_writer`）按调用安装。**没开 tools 流模式时静默 no-op**——工具代码里可以无条件保留发射语句，不用判流模式。delta 是任意 JSON 可序列化值，原样出现在 `tool-output-delta` 事件的 `"delta"` 字段。

### 6.2 场景二：带审批的 Agent（HITL）

两种审批方式并示：**静态中断**（tools 节点前无条件停）与**动态中断**（工具内按危险等级停）。

"""方式 B：工具内 interrupt() 动态审批（v2 下粒度=单个工具调用）。"""

### 6.3 场景三：自定义状态 Agent（state_schema + response_format + hooks）

```python
"""自定义状态键 + 消息裁剪 pre hook + 结构化最终输出。"""
from typing import Annotated, NotRequired
from typing_extensions import TypedDict

from langchain_core.messages import AnyMessage, RemoveMessage, SystemMessage
from langgraph.graph.message import add_messages
from langgraph.managed import RemainingSteps
from langgraph.prebuilt import create_react_agent
from pydantic import BaseModel

# ① 自定义状态：必须含 messages / remaining_steps；用 response_format 则还需 structured_response
class MyState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    remaining_steps: NotRequired[RemainingSteps]
    structured_response: NotRequired[dict]     # response_format 的落点
    user_tier: str                             # 业务自定义键
# 注：无需声明 llm_input_messages——配了 pre_model_hook 时，工厂会派生
# CallModelInputSchema（含该键）挂到 agent 节点的 input_schema 上，
# StateGraph.add_node 会把它注册为图通道（state.py: _add_schema(input_schema)）。

# ② pre_model_hook：只保留最近 20 条消息喂 LLM，不改状态
def trim_messages(state: MyState) -> dict:
    msgs = state["messages"]
    return {"llm_input_messages": msgs[-20:] if len(msgs) > 20 else msgs}

# ③ post_model_hook：护栏——禁止模型泄露内部工具名
def guardrail(state: MyState) -> dict:
    last = state["messages"][-1]
    if "delete_table" in str(last.content):
        return {"messages": [RemoveMessage(id=last.id)]}
    return {}

# ④ 结构化输出 schema
class FinalAnswer(BaseModel):
    summary: str
    confidence: float
    next_actions: list[str]

agent = create_react_agent(
    model="openai:gpt-4o",
    tools=[],                        # 演示用，可换成真实工具
    state_schema=MyState,
    pre_model_hook=trim_messages,
    post_model_hook=guardrail,
    response_format=("请把最终结论整理为 JSON。", FinalAnswer),  # (prompt, schema) 元组
)

out = agent.invoke({
    "messages": [{"role": "user", "content": "分析一下本季度销售下滑的原因"}],
    "user_tier": "vip",
})
print(out["structured_response"])    # FinalAnswer(summary=..., confidence=..., next_actions=[...])
```

要点：`response_format` 会在循环结束后**额外调一次** LLM（`with_structured_output`），结果写入 `structured_response`；pre hook 用 `llm_input_messages` 实现「只影响模型输入、不污染状态历史」；若要真改历史，必须以 `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 开头整体重写。

### 6.4 场景四：多工具 Agent（并行 + 注入 + return_direct + 错误策略 + 拦截器）

```python
"""自建 ToolNode 精细控制，再塞回 create_react_agent；或直接手工建图。"""
from typing import Annotated, Any
from typing_extensions import TypedDict

from langchain_core.messages import AIMessage
from langchain_core.tools import tool
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import InjectedState, InjectedStore, ToolNode, ToolRuntime, tools_condition
from langgraph.store.memory import InMemoryStore

# ⚠️ 本模块不要写 `from __future__ import annotations`，否则 ToolRuntime 注入静默失效

@tool
def query_orders(user_query: str, db_name: Annotated[str, InjectedState("db_name")]) -> str:
    """Query orders. db_name is injected by the system, invisible to the LLM."""
    return f"[{db_name}] 3 rows matched: ..."

@tool
def remember(key: str, value: str, store: Annotated[Any, InjectedStore()]) -> str:
    """Persist a fact across sessions."""
    store.put(("user", "facts"), key, {"value": value})
    return f"saved {key}"

@tool
def finalize_report(report: str) -> str:
    """Produce the final report and stop the loop."""
    return report

finalize_report.return_direct = True   # 执行完直接 END，不再回 LLM

@tool
def progress_tool(n: int, runtime: ToolRuntime) -> str:
    """Long-running tool that streams progress deltas."""
    for i in range(n):
        runtime.emit_output_delta({"progress": i + 1, "total": n})  # tools 流通道
    return f"done {n} steps"

def log_retry_wrapper(request, execute):
    """wrap_tool_call 拦截器：失败自动重试一次并留痕。"""
    result = execute(request)
    if getattr(result, "status", None) == "error":
        print(f"[retry] {request.tool_call['name']} failed, retrying once...")
        result = execute(request)
    return result

tool_node = ToolNode(
    [query_orders, remember, finalize_report, progress_tool],
    handle_tool_errors=True,          # 演示：吞掉一切工具异常，回 error ToolMessage
    wrap_tool_call=log_retry_wrapper,
)

class State(TypedDict):
    messages: Annotated[list, add_messages]
    db_name: str

# —— 用法一：把定制 ToolNode 塞回 create_react_agent ——
from langgraph.prebuilt import create_react_agent
agent = create_react_agent(
    "openai:gpt-4o",
    tools=tool_node,                  # tools 参数直接接受 ToolNode
    store=InMemoryStore(),            # remember 工具的 InjectedStore 依赖它
)
agent.invoke({"messages": [{"role": "user", "content": "记住：我的报销上限是 5000"}],
              "db_name": "sales_db"},
             {"configurable": {"thread_id": "t1"}})

# —— 用法二：手工建图（ToolNode + tools_condition 经典组合）——
builder = StateGraph(State)
builder.add_node("llm", lambda s: {"messages": [
    _llm_with_tools.invoke(s["messages"])]})   # _llm_with_tools = model.bind_tools([...])
builder.add_node("tools", tool_node)
builder.add_edge(START, "llm")
builder.add_conditional_edges("llm", tools_condition)   # "tools" 或 "__end__"
builder.add_edge("tools", "llm")
graph = builder.compile(store=InMemoryStore())

# —— 用法三：绕过图直接调 ToolNode（测试利器）——
direct = tool_node.invoke([
    {"name": "query_orders", "args": {"user_query": "last week"},
     "id": "call_1", "type": "tool_call"},
])
print(direct)   # [ToolMessage(...)]；注意 db_name 注入此时拿不到状态，会 KeyError
```

要点：

- `InjectedState("db_name")` / `InjectedStore()` 参数对模型 schema **不可见**，模型只填自己该填的；即便模型伪造这些参数名也会被 ToolNode 剥离（§2.6）。
- `return_direct` 工具（`finalize_report`）在 `create_react_agent` 图里由 `route_tool_responses` 路由到 END；手工建图则需自己接条件边。
- `handle_tool_errors=True` 与默认值行为不同（默认只兜参数校验错）；生产上更推荐 `Callable` 形态按异常类型精确分流。
- 多工具并行是默认行为：一轮 AIMessage 里 N 个 tool_calls，v2 下 N 个 Send 任务并发，v1 下 ToolNode 内部线程池并发。

## 7. 总结与实战建议

**组件选型速查**：

| 需求 | 用什么 |
|---|---|
| 标准工具循环 Agent | `create_react_agent`（新项目：`langchain.agents.create_agent`） |
| 自定义循环/路由的工具执行 | `ToolNode` + `tools_condition` 手工建图 |
| 执行前人工审批 | `interrupt_before=["tools"]`（粗粒度）或工具内 `interrupt()`（细粒度，v2） |
| 工具访问状态/存储/上下文 | `InjectedState` / `InjectedStore` / `ToolRuntime` |
| 工具级重试/缓存/改写/审计 | `ToolNode(wrap_tool_call=...)` |
| 结构化抽取 + 校验重试环 | `ValidationNode`（旧）/ ToolNode 错误处理 + 重提示（新） |
| 长跑工具进度流 | `runtime.emit_output_delta` + `ToolCallTransformer`（compile 时注册） |

**十条实战守则**（均出自上文源码事实）：

1. **HITL 必须配 checkpointer**——`interrupt()` 的暂停/恢复完全建立在状态持久化上。
2. **`interrupt()` 之前的代码会重放**——副作用放 interrupt 之后，或做幂等。
3. **`except GraphBubbleUp: raise` 永远排在最前**——否则你的异常处理会吞掉中断/排空/父命令信号。
4. **ToolNode 默认只兜参数错**——`handle_tool_errors` 默认是 `_default_handle_tool_errors`（仅 `ToolInvocationError`），运行时异常照常上抛；想全兜要显式传 `True`。
5. **消息历史 call/result 必须配对**——`_validate_chat_history` 与 Command 校验都强制这一点；手工 `update_state` 塞 AIMessage 时记得补 ToolMessage。
6. **自定义 state_schema 三件套**——`messages`、`remaining_steps`（+ 用 response_format 时的 `structured_response`），缺一编译期就 `ValueError`。
7. **pre_model_hook 改写历史必须整体覆盖**——`[RemoveMessage(id=REMOVE_ALL_MESSAGES), *new]`；只影响模型输入请用 `llm_input_messages`。
8. **`remaining_steps < 2` 时 Agent 软着陆**——返回 "Sorry, need more steps..." 而非 `GraphRecursionError`；长任务记得调 `recursion_limit`。
9. **用户工具模块禁用 `from __future__ import annotations`**——本项目实测会使 `ToolRuntime` 注入静默失效（判据：`'runtime' in tool._injected_args_keys`）。
10. **动态模型必须自绑工具**——`(state, runtime) -> model.bind_tools(...)`，且绑定面须为 `tools` 参数子集；async 动态模型只能用 `ainvoke` / `astream` 驱动。
