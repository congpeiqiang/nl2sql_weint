## 1. 流式系统架构概述：三层设计

### 1.1 两代流式协议并存

LangGraph 1.2.9 里同时存在**两代流式协议**，理解这一点是读懂整个 `langgraph.stream` 子包的前提：

| | v1 / v2（`stream()` / `astream()`） | v3（`stream_events(version="v3")`） |
|---|---|---|
| 输出形态 | **扁平数据块**：v1 是裸 payload 或 `(mode, data)` 元组；v2 是类型化 `StreamPart` dict（`{"type","ns","data"}`） | **投影对象**：返回 `GraphRunStream`，上面挂着 `run.values` / `run.messages` / `run.subgraphs` 等强类型通道 |
| 多模式混流 | 靠元组前缀区分，消费者自己写 `if mode == ...` 分派 | 每个模式一条独立的 `StreamChannel`，天然分离 |
| 子图 | `subgraphs=True` 时给元组再加一层 `ns` 前缀 | `SubgraphTransformer` 自动发现子图，生成可下钻的 handle 对象 |
| 扩展点 | 无（模式集合是硬编码的） | `StreamTransformer` 插件体系，编译期/调用期都可注册 |
| 稳定性 | 稳定 API | `@beta`——源码里明确标注 "The v3 streaming protocol on Pregel is experimental" |

关键实现事实：**v3 不是另起炉灶，而是架在 v2 之上的「投影层」**。`_pregel_stream_v3` 内部就是调 `self.stream(..., version="v2", subgraphs=True)` 拿到一个 v2 迭代器，再用泵 + 多路复用器 + Transformer 把扁平事件流「立起来」变成结构化投影。

### 1.2 三层架构：Pregel 泵 → StreamChannel 缓冲 → StreamTransformer 投影

整个 v3 流式系统可以概括为三层（外加最底下的事件源）：

```
┌────────────────────────────────────────────────────────────────┐
│  消费者：for / async for / run.output / interleave / tee        │
└──────────────▲─────────────────────────────────────────────────┘
               │ ⑥ 游标缓冲区空时回调 _request_more()（拉动泵）
┌──────────────┴─────────────────────────────────────────────────┐
│  【缓冲层】StreamChannel（单消费者投影队列）                      │
│    run.values / run.messages / run.lifecycle / run.subgraphs    │
│    + 主事件日志 mux._events（也是一条 StreamChannel）             │
└──────────────▲─────────────────────────────────────────────────┘
               │ ⑤ transformer 向自己的投影 push()
               │    （命名通道同时 auto-forward 回主日志）
┌──────────────┴─────────────────────────────────────────────────┐
│  【投影层】StreamTransformer 管线                                │
│    before_builtins 先行区 → Values → Messages → Lifecycle        │
│    → Subgraph → 编译期 transformers → 调用期 transformers        │
└──────────────▲─────────────────────────────────────────────────┘
               │ ④ StreamMux.push/apush：按注册序调 process/aprocess
┌──────────────┴─────────────────────────────────────────────────┐
│  【分发层】StreamMux ＋ 【泵】GraphRunStream._pump_next          │
│    ③ _convert.convert_to_protocol_event：StreamPart→ProtocolEvent│
└──────────────▲─────────────────────────────────────────────────┘
               │ ② next(graph_iter)：拉一个 v2 StreamPart
┌──────────────┴─────────────────────────────────────────────────┐
│  【事件源层】Pregel.stream(version="v2", subgraphs=True)         │
│    SyncPregelLoop/AsyncPregelLoop + PregelRunner                 │
│    + StreamProtocol(队列) + 各 callback handler                   │
└────────────────────────────────────────────────────────────────┘
```

这套设计最核心的决策是 **「调用者驱动泵」（caller-driven pump），全程没有后台线程/后台任务**。`run_stream.py` 的类文档写得很直白：

```python
@beta(message="The v3 streaming protocol on Pregel is experimental.")
class GraphRunStream:
    """Sync run stream with caller-driven pumping.

    The caller's iteration on any projection (`values`, `messages`,
    raw events, or `output`) drives the graph forward. No background
    thread is used — the caller's `for` loop is the pump.
    """
```

**解析**：消费者的 `for` 循环本身就是泵。当你迭代 `run.values` 而缓冲区为空时，游标回调 `_request_more()`（即 `_pump_next`），泵从 Pregel 的 v2 迭代器里 `next()` 出一个 `StreamPart`，转换成 `ProtocolEvent`，推入 mux 走一遍 Transformer 管线——这个事件可能落到 `values` 通道（你的循环随即拿到它），也可能落到 `messages`/`lifecycle` 等别的通道（那些通道的消费者下次迭代时拿到）。每前进一步游标，最多产生一个图事件，**内存天然被消费速度限界**，这就是文档说的 "Memory is bounded by caller pace"。

泵的核心只有 20 来行：

```python
def _pump_next(self) -> bool:
    if self._exhausted or self._graph_iter is None:
        return False
    try:
        part = next(self._graph_iter)               # ② 从 Pregel v2 流拉一块
        event = convert_to_protocol_event(part)     # ③ v2 StreamPart → ProtocolEvent
        self._observe_event(event)                  # 记录 values 快照（供 output/interrupts）
        self._mux.push(event)                       # ④ 走 Transformer 管线 + 入主日志
        return True
    except StopIteration:
        self._mux.close()                           # 正常收尾：finalize 所有 transformer
        self._exhausted = True
        return False
    except Exception as e:
        self._mux.fail(e)                           # 失败收尾：fail 所有通道
        self._exhausted = True
        return False
```

**解析**：三个终态各自闭环——图迭代器耗尽触发 `mux.close()`（依次调用每个 Transformer 的 `finalize()`、自动关闭所有投影通道和主日志）；图内抛异常触发 `mux.fail(e)`（调用 `fail()` 钩子、把异常注入所有通道，正在迭代的消费者会在游标处收到该异常）。**流的生命周期管理完全收敛在泵的三个出口上**，Transformer 作者不需要自己关通道。

### 1.3 一次事件的完整旅程

以「节点里的 LLM 吐了一个 token」为例，走一遍全链路：

1. **事件源层**：`BaseChatModel.invoke`（被 v2 标记改道到 `_stream_chat_model_events`）触发 `on_stream_event` 回调 → `StreamMessagesHandlerV2.on_stream_event` 把 content-block 事件包成 `(event, meta)`，`self.stream((ns, "messages", (event, meta)))` 写进 Pregel 内部队列（`SyncQueue`/`AsyncQueue`）。
2. **泵**：`Pregel.stream` 生成器的 `_output()` 从队列弹出，yield 出 v2 `StreamPart`：`{"type": "messages", "ns": (...), "data": (event, meta)}`；`_pump_next` 的 `next()` 收到它。
3. **协议转换**：`convert_to_protocol_event` 包上统一信封 → `{"type": "event", "method": "messages", "params": {"namespace": [...], "timestamp": ms, "data": ...}}`。
4. **分发**：`mux.push(event)` 按注册序调用每个 Transformer 的 `process(event)`。`MessagesTransformer` 按 `metadata["run_id"]` 找到对应的 `ChatModelStream`，`stream.dispatch(event)` 把 token 塞进它的内部缓冲。
5. **缓冲**：`ChatModelStream` 的 `.text` 投影收到新的字符串增量；若主日志被保留（`process` 返回 `True`），mux 给事件盖上单调递增的 `seq` 后 `self._events.push(event)`。
6. **消费**：正在 `for delta in chat.text:` 的消费者游标从缓冲弹出一项；缓冲再空时又回调泵——循环往复直到 `message-finish`。

## 2. StreamMode 全模式详解

### 2.1 进程内 StreamMode：7 个正名 + 1 个「编外」

`langgraph/types.py` 里的正式定义是一个 `Literal`（不是 `Enum`）：

```python
StreamMode = Literal[
    "values", "updates", "checkpoints", "tasks", "debug", "messages", "custom"
]
"""How the stream method should emit outputs.

- `"values"`: Emit all values in the state after each step, including interrupts.
- `"updates"`: Emit only the node or task names and updates returned by the nodes or tasks after each step.
- `"custom"`: Emit custom data using from inside nodes or tasks using `StreamWriter`.
- `"messages"`: Emit LLM messages token-by-token together with metadata ...
- `"checkpoints"`: Emit an event when a checkpoint is created, in the same format as returned by `get_state()`.
- `"tasks"`: Emit events when tasks start and finish, including their results and errors.
- `"debug"`: Emit `"checkpoints"` and `"tasks"` events for debugging purposes.
"""
```

逐个说明（含每种模式的 `StreamPart` 载荷形状）：

| 模式 | 发射时机 | v2 载荷（`data` 字段） | 对应内置 Transformer |
|---|---|---|---|
| `values` | 每步结束后的**完整状态快照**（functional API 只在结束时发一次） | 全量 state；v2 时 `__interrupt__` 被弹出到独立的 `interrupts` 元组字段 | `ValuesTransformer` → `run.values` |
| `updates` | 每个节点/任务返回的**增量更新**，同一步多个节点分别发 | `{节点名: 该节点返回值}`，可能含 `__interrupt__` / `__metadata__` 键 | `UpdatesTransformer` → `run.updates` |
| `messages` | LLM 逐 token（v1 是 `(AIMessageChunk, metadata)` 二元组；v2/v3 是 content-block 协议事件） | `(payload, metadata)`，metadata 含 `langgraph_node` / `langgraph_step` / `run_id` 等 | `MessagesTransformer` → `run.messages` |
| `custom` | 节点内调 `get_stream_writer()` 写入的任意业务数据 | 任意对象 | `CustomTransformer` → `run.custom` |
| `checkpoints` | 每次 checkpoint 落盘 | `CheckpointPayload`（config/metadata/values/next/tasks，同 `get_state()`） | `CheckpointsTransformer` → `run.checkpoints` |
| `tasks` | 任务开始/结束 | `TaskPayload`（id/name/input/triggers/metadata）或 `TaskResultPayload`（id/name/error/interrupts/result） | `TasksTransformer` → `run.tasks`；同时被 `LifecycleTransformer`/`SubgraphTransformer` 消费用于子图发现 |
| `debug` | 调试聚合：checkpoint/task/task_result 三种事件加 `step`+`timestamp` 包装 | `DebugPayload`（判别 `type` 字段） | `DebugTransformer` → `run.debug` |

**「编外」的 `tools` 模式**：`pregel/main.py` 的 `stream()`/`astream()` 里有 `if "tools" in stream_modes:` 分支（挂载 `StreamToolCallHandler`），但它**不在 `StreamMode` Literal 里**——`_defaults()` 只做 `set(stream_mode)` 不做字面量校验，所以运行时是通的，类型检查器会报错。它发射 `tool-started` / `tool-output-delta` / `tool-finished` / `tool-error` 四种事件，按 `tool_call_id` 关联，配套的 v3 投影是 `langgraph.prebuilt` 里的 `ToolCallTransformer`（见 §7.3.10）。

### 2.2 `lifecycle` / `events` / `messages-tuple`：它们不是进程内 StreamMode

用户视角常见的另外三个「模式名」住在别的层：

- **`lifecycle`**：不是图的 stream mode，而是 v3 里 `LifecycleTransformer` 产出的**命名通道**——它创建 `StreamChannel("lifecycle")`，经 mux auto-forward 以 `method="lifecycle"` 进入主事件日志（native transformer 不加 `custom:` 前缀），远程 SDK 客户端和进程内 `run.lifecycle` 看到的是同一份数据。载荷 `LifecyclePayload` = `{event: started|completed|failed|interrupted|drained, namespace, graph_name?, trigger_call_id?, cause?, error?}`。
- **`events`**：LangGraph Platform **wire 协议**的模式（`langgraph_sdk/schema.py` 的 `StreamMode` Literal：`values/messages/updates/events/tasks/checkpoints/debug/custom/messages-tuple`）。进程内对应物就是 v3 的**原始主事件日志**——`for event in run:` / `async for event in run:` 迭代出的 `ProtocolEvent` 流。
- **`messages-tuple`**：同样是 wire 层名字，指 v1 `messages` 模式的 `(AIMessageChunk, metadata)` 二元组形状（本项目前端 token 流式链路用的就是它）。v3 进程内没有这个名字——`MessagesTransformer` 明确**不消费** v1 形状的 chunk 元组（见 §9）。

另有一个 `ThreadStreamMode = Literal["run_modes", "lifecycle", "state_update"]` 是 SDK 里**线程级**（跨 run）订阅的模式，与图执行流式无关，不要混淆。

### 2.3 StreamChunk 与 v2 StreamPart：事件源层的两种载荷

Pregel 内部队列里流动的统一形状是三元组 `StreamChunk = (ns, mode, payload)`（`pregel/protocol.py`）。`stream()` 出口处的 `_output()` 函数负责把它整形成用户可见的形状：

```python
if mode in stream_mode:
    if version == "v2":
        if mode == "values":
            ints: tuple[Interrupt, ...] = ()
            if isinstance(payload, dict):
                ints = payload.pop(INTERRUPT, ())          # __interrupt__ 弹成独立字段
                if output_mapper:
                    payload = output_mapper(payload)        # pydantic/dataclass 状态 coerce
            yield {"type": mode, "ns": ns, "data": payload, "interrupts": ints}
        ...
    elif stream_subgraphs and isinstance(stream_mode, list):
        yield (ns, mode, payload)      # v1 + 多模式 + 子图：三元组
    elif isinstance(stream_mode, list):
        yield (mode, payload)          # v1 + 多模式：二元组
    elif stream_subgraphs:
        yield (ns, payload)            # v1 + 单模式 + 子图：二元组
    else:
        yield payload                  # v1 + 单模式：裸 payload
```

v2 的 `StreamPart` 是一个按 `part["type"]` 判别的 TypedDict 联合（`ValuesStreamPart` / `UpdatesStreamPart` / `MessagesStreamPart` / `CustomStreamPart` / `CheckpointStreamPart` / `TasksStreamPart` / `DebugStreamPart`），每个成员都带 `ns: tuple[str, ...]`。**v3 的 `ProtocolEvent` 就是在它外面再包一层信封**（见 §8）。

## 3. stream() / astream() 方法详解

### 3.1 完整签名

`Pregel.stream`（`pregel/main.py:2655`，`astream` 在 3063 行，签名完全对称）：

```python
def stream(
    self,
    input: InputT | Command | None,
    config: RunnableConfig | None = None,
    *,
    context: ContextT | None = None,
    stream_mode: StreamMode | Sequence[StreamMode] | None = None,
    print_mode: StreamMode | Sequence[StreamMode] = (),
    output_keys: str | Sequence[str] | None = None,
    interrupt_before: All | Sequence[str] | None = None,
    interrupt_after: All | Sequence[str] | None = None,
    durability: Durability | None = None,
    control: RunControl | None = None,
    subgraphs: bool = False,
    debug: bool | None = None,
    version: Literal["v1", "v2"] = "v1",
    **kwargs: Unpack[DeprecatedKwargs],
) -> Iterator[dict[str, Any] | Any]: ...
```

通过 `@overload` 细化返回类型：`version="v2"` 时返回 `Iterator[StreamPart[StateT, OutputT]]`（类型化 dict）；`version="v1"`（默认）返回 `Iterator[dict | Any]`（形状随参数组合变化，见 §2.3）。`astream` 对应返回 `AsyncIterator`。

### 3.2 参数详解

| 参数 | 说明 |
|---|---|
| `input` | 图输入；`None` 表示从 checkpoint 恢复；`Command` 用于 resume/导航 |
| `config` | RunnableConfig（`thread_id` 等 configurable、`recursion_limit`、callbacks） |
| `context` | 静态上下文（0.6.0+），经 `context_schema` coerce 后放进 `Runtime.context` |
| `stream_mode` | 单模式或模式列表；`None` 时的默认逻辑见下文源码摘录 |
| `print_mode` | 与 `stream_mode` 同值域，但**只打印到控制台**、不影响 yield；`debug=True` 等价于 `print_mode=["updates","values"]` |
| `output_keys` | 只流哪些 state 通道，默认全部非 context 通道 |
| `interrupt_before` / `interrupt_after` | 在指定节点前/后断点（HITL） |
| `durability` | checkpoint 持久化时机：`"sync"`（下一步开始前落盘）/ `"async"`（默认，与下一步并行落盘）/ `"exit"`（仅退出时）；无 checkpointer 时传值会告警 |
| `control` | `RunControl`，请求协作式排空（drain）；结束时 `loop.status == "draining"` 会抛 `GraphDrained` |
| `subgraphs` | 是否穿透子图；`True` 时事件带 `ns` 命名空间前缀（见 §10） |
| `version` | `"v1"`（默认，兼容形状）/ `"v2"`（类型化 `StreamPart`） |
| `**kwargs` | 只接已废弃参数（如 `checkpoint_during` → 折算成 `durability`，同时传两个会 `ValueError`） |

`stream_mode=None` 时的默认值有一个容易忽略的分支：

```python
if stream_mode is None:
    # if being called as a node in another graph, default to values mode
    stream_mode = (
        "values"
        if config is not None and CONFIG_KEY_TASK_ID in config.get(CONF, {})
        else self.stream_mode
    )
```

**解析**：如果这个图是**作为另一个图的节点**被调用的（config 里带 task id），默认切成 `values`——这是子图向父图上报状态的通道；根调用则用编译期默认（`StateGraph.compile()` 产出的是 `"updates"`）。

### 3.3 内部执行流程（源码走读）

`stream()` 主体可以拆成六步：

**① 建队列与回调管理器。** `stream = SyncQueue()`；`astream` 用 `AsyncQueue` 并把 put 包成线程安全的：

```python
stream = AsyncQueue()
aioloop = asyncio.get_running_loop()
stream_put = cast(
    Callable[[StreamChunk], None],
    partial(aioloop.call_soon_threadsafe, stream.put_nowait),
)
```

**解析**：节点可能跑在线程池里（同步节点 offload），`call_soon_threadsafe` 保证跨线程写队列安全。这个 `stream_put` 之后被交给各 callback handler。

**② 按模式挂载 handler。** v1 分支先做一件防御性的事——把继承来的 v2 messages handler 摘掉：

```python
if "messages" in stream_modes and version != "v2":
    # Strip any inherited v2 messages handler so a v1 stream
    # does not get routed through the content-block event protocol.
    callback_manager.handlers = [
        h for h in callback_manager.handlers
        if not isinstance(h, StreamMessagesHandlerV2)
    ]
```

然后按需挂载：

- `"messages"` → `run_manager.inheritable_handlers.append(StreamMessagesHandler(stream.put, subgraphs, parent_ns=...) 或 StreamMessagesHandlerV2(...))`。v2 handler 只在 `version=="v2"` 且 config 带 `CONFIG_KEY_STREAM_MESSAGES_V2` 时选用（v3 入口会注入这个标记，见 §4.1）。**inheritable** 是关键：它会随 config 传播进子图/子 LLM 调用，这就是 token 能「穿透」的机制。
- `"tools"` → 挂 `StreamToolCallHandler`（同样的 subgraphs/parent_ns 语义）。
- `"custom"` → 定义 `stream_writer` 闭包，从**当前任务的 config** 里取 checkpoint ns 作为事件命名空间：

```python
def stream_writer(c: Any) -> None:
    stream.put((
        tuple(get_config()[CONF][CONFIG_KEY_CHECKPOINT_NS].split(NS_SEP)[:-1]),
        "custom", c,
    ))
```

没开 custom 模式时，`stream_writer` 是 no-op 函数（或者继承父图的 writer）——这就是「`StreamWriter` 在非 custom 模式下是 no-op」的出处。writer 被塞进 `Runtime(stream_writer=...)` 并写入 config，节点里 `get_stream_writer()` 取到的就是它（见 §11）。

**③ 建 Pregel 循环，注入 StreamProtocol。**

```python
with SyncPregelLoop(
    input,
    stream=StreamProtocol(stream.put, stream_modes),
    ...
) as loop:
```

`StreamProtocol` 只是「一个 callable + 它接受的模式集合」的轻包装（`__slots__ = ("modes", "__call__")`）。循环内部（values/updates/checkpoints/tasks/debug 事件）都通过它写队列，**并在写入前按 `modes` 过滤**——没人订阅的模式根本不产生载荷。`subgraphs=True` 时还会把这个协议塞进 config：`loop.config[CONF][CONFIG_KEY_STREAM] = loop.stream`，子图循环从 config 里继承它，事件就能带着子图 ns 冒泡到同一个队列（见 §10.1）。

**④ 并发流式（waiter 机制）。** 默认情况下 BSP 循环要等一个 super-step 的所有任务跑完才 yield；但四种情况开启「边跑边吐」：

```python
if (
    self.stream_eager
    or subgraphs
    or "messages" in stream_modes
    or "custom" in stream_modes
):
    waiter: concurrent.futures.Future | None = None
    loop.stack.callback(stream._count.release)   # 退出时释放信号量，唤醒挂起的 waiter

    def get_waiter() -> concurrent.futures.Future[None]:
        nonlocal waiter
        if waiter is None or waiter.done():
            waiter = loop.submit(stream.wait)
            return waiter
        else:
            return waiter
```

**解析**：`get_waiter` 交给 `PregelRunner.tick()`，runner 在等任务完成的 select 里同时等「队列非空」——一旦 handler 往队列写了 token/custom 事件，tick 立即 yield 一次让 `_output()` 排水。注意注释强调**同一时刻只允许一个 waiter 存活**（同步 Future 不能 cancel，靠退出时 `stream._count.release()` 兜底唤醒）。`astream` 的对应版本用 `aioloop.create_task(stream.wait())` + `_cleanup_waiter()` 收尾。

**⑤ 主循环排水。** BSP（Bulk Synchronous Parallel）模型：

```python
while loop.tick():
    for task in loop.match_cached_writes():
        loop.output_writes(task.id, task.writes, cached=True)
    for _ in runner.tick(
        [t for t in loop.tasks.values() if not t.writes],
        timeout=self.step_timeout,
        get_waiter=get_waiter,
        schedule_task=loop.accept_push,
    ):
        yield from _output(stream_mode, print_mode, subgraphs,
                           stream.get, queue.Empty, version, ...)
    loop.after_tick()
    ...
```

**解析**：`runner.tick` 每让出一次（有任务完成或 waiter 醒来），就调一轮 `_output()` 把队列排空并 yield。第 N 步的通道更新只在第 N+1 步可见——这是 Pregel 模型的不变量。循环结束后还有最后一次 `_output()` 兜底排水。

**⑥ 终态处理。**

```python
if loop.status == "out_of_steps":
    raise GraphRecursionError(msg)      # recursion_limit 用尽
elif loop.status == "draining":
    raise GraphDrained(loop.control.drain_reason or "shutdown")
run_manager.on_chain_end(loop.output)   # 正常收尾，最终状态作为 run output
```

异常路径统一走 `except BaseException` → `run_manager.on_chain_error(e)` → re-raise（`astream` 里还套了 `asyncio.shield`，保证取消时错误回调能跑完）。

## 4. stream_events(version="v3")：运行流对象

### 4.1 入口与装配：`_pregel_stream_v3`

`stream_events` / `astream_events` 是分派器：`version="v1"/"v2"` 走 LangChain `Runnable` 的老 `StreamEvent` 协议；`version="v3"` 走新体系。分派前先执行不变量检查：

```python
_V3_INVARIANT_KWARGS: tuple[str, ...] = ("stream_mode", "subgraphs")

def _reject_v3_invariant_kwargs(kwargs: dict[str, Any]) -> None:
    collisions = [k for k in _V3_INVARIANT_KWARGS if k in kwargs]
    if collisions:
        raise TypeError(
            "stream_events(version='v3') / astream_events(version='v3') do "
            f"not accept {', '.join(collisions)}; v3 owns these ..."
        )
```

**解析**：v3 **自己拥有** `stream_mode` 和 `subgraphs` 两个参数——前者由 Transformer 管线推导，后者恒为 `True`。用户传了直接 `TypeError`，防止静默破坏 v3 的不变量。

v3 装配核心（`_pregel_stream_v3`，async 版对称）：

```python
parent_ns = _resolve_parent_ns(self.config, config)
compiled_factories = _normalize_stream_transformer_factories(self.stream_transformers)
extra_factories = _normalize_stream_transformer_factories(transformers)
mux = StreamMux(
    factories=[
        ValuesTransformer,
        MessagesTransformer,
        LifecycleTransformer,
        SubgraphTransformer,
        *compiled_factories,
        *extra_factories,
    ],
    scope=parent_ns,
    is_async=False,
)
graph_iter = iter(
    self.stream(
        input,
        patch_configurable(config, {CONFIG_KEY_STREAM_MESSAGES_V2: True}),
        stream_mode=_collect_stream_modes(mux),
        subgraphs=True,
        version="v2",
        ...
    )
)
return GraphRunStream(graph_iter, mux)
```

四个要点：

1. **默认只注册 4 个 Transformer**：`Values` / `Messages` / `Lifecycle` / `Subgraph`。`UpdatesTransformer`、`CustomTransformer`、`DebugTransformer`、`CheckpointsTransformer`、`TasksTransformer` 虽然都在 `langgraph.stream.transformers` 里实现并从 `langgraph.stream` 导出，但**不在默认工厂列表里**——想要 `run.updates` / `run.custom` 等投影必须显式注册（编译期 `compile(transformers=[...])` 或调用期 `stream_events(..., transformers=[...])`）。
2. **`stream_mode` 按需推导**（`_collect_stream_modes`）：

```python
def _collect_stream_modes(mux: Any) -> list[StreamMode]:
    """Return the union of `required_stream_modes` across registered transformers.

    Transformers declare the stream modes they need to function, and
    stream_events(version="v3") asks the graph for exactly that union — no hardcoded
    default set. If zero transformers declare a given mode, the graph
    does not stream events for it.
    """
    modes: set[StreamMode] = set()
    for transformer in mux._transformers:
        modes.update(getattr(transformer, "required_stream_modes", ()))
    return list(modes)
```

**解析**：默认装配下 union = `{"values", "messages", "tasks"}`（Lifecycle/Subgraph 都声明 `("tasks",)`）。**没有任何 Transformer 声明的模式，图根本不会发**——省掉序列化开销。注册 `CustomTransformer`（`required_stream_modes = ("custom",)`）后 `custom` 才被加进请求集合，`get_stream_writer()` 才从 no-op 变成真写入。
3. **`CONFIG_KEY_STREAM_MESSAGES_V2: True`**：让内层 `stream()` 挂 `StreamMessagesHandlerV2`，即 messages 模式改走 content-block 协议（§9.2）。
4. **`scope=parent_ns`**（`_resolve_parent_ns`）：如果 `stream_events(version="v3")` 是在某个节点**内部**调用的（嵌套图），scope 取调用者的 checkpoint 命名空间，保证原生投影只捕获「自己这一层」的事件。

`_normalize_stream_transformer_factories` 规定注册物必须是 **scope 感知的可调用**（类本身即可，因为构造函数签名就是 `(scope)`；或 `lambda scope: MyTransformer(scope, foo=...)`）。**预构建实例直接拒绝**：

```python
if isinstance(spec, StreamTransformer):
    raise TypeError(
        "stream_events(version='v3') transformers must be scope-aware callables, "
        f"got pre-built instance {type(spec).__name__}. ..."
    )
```

原因见 §6.5：子图 mini-mux 需要用同一份工厂**逐 scope 克隆**出新实例，实例没法克隆。

### 4.2 GraphRunStream：同步运行流

构造时把 mux 的投影面暴露出来：

```python
self._graph_iter = graph_iter
self._mux = mux
self.extensions: Mapping[str, Any] = MappingProxyType(mux.extensions)
...
for key in mux.native_keys:
    setattr(self, key, mux.extensions[key])
if wire_pump:
    self._wire_request_more(mux)      # → mux.bind_pump(self._pump_next)
```

**解析**：
- `extensions` 是**全部**投影的只读映射（native + 非 native），`MappingProxyType` 防止外部改。
- `_native = True` 的 Transformer 的投影键额外 `setattr` 成直接属性——这就是 `run.values` / `run.messages` / `run.lifecycle` / `run.subgraphs` 的来历。
- 泵回调经 `mux.bind_pump` 注册（而不是直接写到各通道），这样 `_make_child` 造出的子图 mini-mux 能**继承同一个泵**（§10.2）。

三个「驱动到底」的终态属性（sync 版是 property，async 版是方法——源码注释解释：让漏写 `await` 的 `run.output` 在类型检查期就报错，而不是静默返回一个协程对象）：

```python
@property
def output(self) -> dict[str, Any] | None:
    """Drive the run to completion and return the final state."""
    _drive_until_done(self._pump_next)          # while pump(): pass
    if (err := self._mux._events._error) is not None:
        raise err
    return self._latest                          # 最近一次 values 快照
```

`interrupted` / `interrupts` 同构：先驱动到底，再读 `_observe_event` 沿途记下的中断状态。**注意语义**：访问这三个成员会把整个 run 跑完——它们是「只要结果」的快捷方式，不是流式消费。

其他成员：
- `__iter__` → `iter(self._mux._events)`：订阅**主事件日志**，迭代原始 `ProtocolEvent`（等价于 wire 上的 `events` 模式）。
- `abort()`：提前终止。关闭底层图迭代器（`GeneratorExit` 传播进在跑的节点/子图）、关 mux、标记耗尽，幂等。
- `__enter__/__exit__`：上下文管理器，退出即 `abort()`——**提前 break 出循环时保证图被干净取消**的推荐写法。
- `interleave(*names)`：多个投影**按到达序**交错消费（见 §12.3），只存在于同步版。

### 4.3 AsyncGraphRunStream：单飞泵与 take-a-number

异步版多了一个关键机制——**多个并发消费者共享一个「单飞」泵**：

```python
async def _apump_next(self) -> bool:
    async with self._pump_cond:
        if self._exhausted or self._graph_aiter is None:
            return False
        if self._pumping:
            # Another task is pumping; wait for its progress signal.
            await self._pump_cond.wait()
            return not self._exhausted
        self._pumping = True
    try:
        try:
            self._anext_task = asyncio.ensure_future(self._graph_aiter.__anext__())
            try:
                part = await self._anext_task
            except asyncio.CancelledError:
                if self._aborting:
                    self._exhausted = True
                    return False
                self._anext_task.cancel()
                raise
            finally:
                self._anext_task = None
            event = convert_to_protocol_event(part)
            self._observe_event(event)
            await self._mux.apush(event)
            return True
        except StopAsyncIteration:
            self._exhausted = True
            await self._mux.aclose()
            return False
        except Exception as e:
            self._exhausted = True
            await self._mux.afail(e)
            return False
    finally:
        async with self._pump_cond:
            self._pumping = False
            self._pump_cond.notify_all()
```

**解析**（docstring 称之为 "take-a-number" 语义）：
- asyncio 迭代器**不能并发 `__anext__`**，所以同一时刻最多一个任务真正拉图（`self._pumping` 标志）；其他任务在 `asyncio.Condition` 上等，活跃泵每推进一步就 `notify_all()`。
- 好处：一个「被动」消费者（它订阅的通道正被活跃泵的 push 填充）能在**数据落地的瞬间**被唤醒，而不是排队等下一轮泵、晚一个图事件才看到数据。
- `except Exception` 是刻意的——`CancelledError` 等 `BaseException` 直接穿透，符合 asyncio 取消契约。
- `__anext__` 被包成子任务 `_anext_task`，是为了让 `abort()` 能**在拉取中途取消**：取消会把 `CancelledError` 传播进图生成器帧 → Pregel 循环 → 嵌套子图节点；裸 `aclose()` 在生成器运行中是做不到的（会报 "asynchronous generator is already running"）。

`abort()` 的顺序因此是：置 `_exhausted/_aborting` → `notify_all()` 唤醒等泵者 → cancel 并 await `_anext_task` → `aclose()` 生成器（此时已不在运行，安全兜底）→ `mux.aclose()`（阻塞在背压上的 `apush` 会醒来并放弃追加）。

### 4.4 子图 handle：SubgraphRunStream / AsyncSubgraphRunStream

```python
class SubgraphRunStream(GraphRunStream, _SubgraphRunStreamMixin):
    def __init__(self, mux, *, path, graph_name=None, trigger_call_id=None):
        # Capture the parent-inherited pump before super().__init__ touches anything
        self._parent_pump_fn: Callable[[], bool] | None = mux._pump_fn
        super().__init__(graph_iter=None, mux=mux, wire_pump=False)
        self.path = path                      # 命名空间元组，如 ("agent:task_id",)
        self.graph_name = graph_name          # 子图/子 agent 名
        self.trigger_call_id = trigger_call_id
        self.status = "started"               # → completed/failed/interrupted/drained
        self.error = None
        self._seen_terminal = False

    def _pump_next(self) -> bool:
        if (self._exhausted or self._seen_terminal
                or self._mux._events._closed or self._parent_pump_fn is None):
            return False
        return self._parent_pump_fn()         # 委托父泵
```

**解析**：handle 是一个「没有自己的事件源」的 `GraphRunStream`——`graph_iter=None` + `wire_pump=False`，它的 mini-mux 由 `SubgraphTransformer` 从父 mux 转发事件来填充；它的游标缓冲空时**委托父泵**，拉动的仍是根图。因此 `handle.values` / `handle.output` 用起来和根 run 完全一样，透明地推进整个运行。`status` 字段由 `SubgraphTransformer` 原地更新（§10.2）。

## 5. StreamChannel：流式通道

`stream_channel.py` 的 `StreamChannel[T]` 是整个 v3 体系的**唯一缓冲原语**：一个「单消费者、可排水、可选协议自动转发」的队列。主事件日志、每个 Transformer 投影、`ToolCallStream.output_deltas`，全都是它的实例。

### 5.1 构造与内部状态

```python
class StreamChannel(Generic[T]):
    def __init__(self, name: str | None = None, *, maxlen: int | None = None) -> None:
        if maxlen is not None and maxlen <= 0:
            raise ValueError("StreamChannel maxlen must be a positive int or None")
        self.name = name                       # None=本地通道；有名字=自动转发到主日志
        self._items: deque[tuple[int, T]] = deque()   # (push戳, 条目)
        self._maxlen: int | None = maxlen      # 当前未使用（见 5.5）
        self._closed = False
        self._error: BaseException | None = None
        self._is_async: bool | None = None     # 未绑定
        self._subscribed = False
        self._request_more: Callable[[], bool] | None = None        # 同步泵
        self._arequest_more: Callable[[], Awaitable[bool]] | None = None  # 异步泵
        self._wire_fn: Callable[[T], None] | None = None            # 自动转发钩子
        self._mux: StreamMux | None = None                          # 戳计数器来源
```

四个设计约束（全部来自类 docstring，逐条对应实现）：

1. **单消费者**：`__iter__` / `__aiter__` 第二次调用直接 `RuntimeError`（"already has a subscriber; use .tee(n) for fan-out"）。
2. **绑定后才可迭代**：通道创建时是「未绑定」态，`StreamMux._bind_and_wire` 调 `_bind(is_async=...)` 后，只有匹配一侧的迭代协议可用，另一侧 `TypeError`。这防止同一条通道被 sync/async 混用。
3. **懒订阅（lazy-subscribe）**：`push()` 只在**已有订阅者**时追加本地缓冲；但 `_wire_fn` 自动转发**无论是否有人订阅都会执行**。
4. **生命周期归 mux**：`close()` / `fail(err)` 由 mux 在收尾时统一调用，Transformer 作者不需要手动关。

### 5.2 push：戳与转发

```python
def push(self, item: T) -> None:
    if self._subscribed:
        if self._closed:
            raise RuntimeError("Cannot push to a closed StreamChannel")
        stamp = self._mux._next_push_seq() if self._mux is not None else 0
        self._items.append((stamp, item))
    if self._wire_fn is not None:
        self._wire_fn(item)
```

**解析**：
- 条目以 `(stamp, item)` 存储，`stamp` 是 mux 全局单调计数（`_next_push_seq`）。默认游标会把戳剥掉再 yield；戳的真正用途是 `GraphRunStream.interleave()` 的**跨投影到达排序**（§12.3）——比轮询（round-robin）严格，因为它反映真实的 push 顺序。
- 「已关闭还 push」只在有订阅者时才炸——没人订阅时本地缓冲本来就是丢弃的，不必报错。
- **懒订阅的含义要划重点**：如果一条通道还没人 `iter()`，泵已经在跑（比如你在消费投影 A），那么途经的 B 投影数据**不会为 B 缓冲**，等你回头再迭代 B 时早期数据已经没了。多投影消费必须**先全部订阅、再开始拉泵**（`interleave` / `tee` / 预先调用 `__aiter__()` 都满足这一点）。

### 5.3 游标：调用者驱动泵

同步游标（异步版逐行对称，只是 `_arequest_more` 换成 await）：

```python
def _sync_cursor(self) -> Iterator[T]:
    while True:
        if self._items:
            _stamp, item = self._items.popleft()
            yield item
        elif self._closed:
            if self._error is not None:
                raise self._error          # fail 的通道把异常抛给订阅者
            return
        elif self._request_more is not None:
            if not self._request_more():    # 拉一次泵
                if not self._items and not self._closed:
                    return                  # 泵说没有了且确实空 → 流结束
        else:
            return                          # 没接泵的通道：排空即止
```

**解析**：状态机就三条路——有货弹货、关闭收尾（可能带异常）、空了拉泵。泵每被调一次最多产生一个图事件，事件的落点可能是本通道（下轮循环弹出）也可能是别的通道（本通道继续拉泵）。**背压是隐式的**：消费者不迭代，泵就不转，图就不前进。

### 5.4 tee / atee：受控扇出

单消费者约束的官方逃生门。`tee(n)` 返回 n 个独立同步迭代器：

```python
def tee(self, n: int = 2) -> tuple[Iterator[T], ...]:
    source = self.__iter__()                 # 占用唯一订阅位
    buffers: list[deque[T]] = [deque() for _ in range(n)]
    exhausted = [False]

    def branch(i: int) -> Iterator[T]:
        buf = buffers[i]
        while True:
            if buf:
                yield buf.popleft()
            elif exhausted[0]:
                return
            else:
                try:
                    item = next(source)      # 任一分支拉源
                except StopIteration:
                    exhausted[0] = True
                    return
                for b in buffers:
                    b.append(item)           # 复制到所有分支缓冲
```

**解析**：谁先要货谁去拉底层游标，拉到的条目**复制进每个分支自己的缓冲**。分支间进度可以不同，但都受调用节奏限界。`atee(n)` 是异步版，加了三个东西：`asyncio.Lock` 保证同一时刻只有一个分支拉源（拉完还要重查自己的缓冲——锁内二次检查 `if buf or exhausted[0]: continue`）；`error` 列表把源异常广播给每个分支；`StopAsyncIteration` 置共享的 `exhausted` 标志。

### 5.5 maxlen：接受但未实现

docstring 原文：`"maxlen: Accepted for forward compatibility; currently unused. The caller-driven pump bounds memory naturally for single-consumer use."`——**当前版本 `maxlen` 只做正整数校验，不参与任何限界逻辑**。理由：调用者驱动泵下，单消费者场景每次游标前进最多产生一个事件，缓冲深度≈消费滞后量，天然有界。

> ⚠️ 注意一处**文档与实现的漂移**：`AsyncGraphRunStream` 的类 docstring 说 "when a subscribed log's buffer reaches `maxlen`, `apush` awaits the subscriber to drain"——这在 1.2.9 的 `StreamChannel` 里**并没有实现**（`apush` 对主日志的追加也是非阻塞 `push`，`_mux.py` 注释自己承认："The main log append is a non-blocking push — matching v1's put_nowait shape"）。同理其 docstring 说并发消费者用 `asyncio.Lock` 共享泵，实现用的是 `asyncio.Condition`。读源码时以代码为准。

## 6. StreamMux：多路复用器

`_mux.py` 的 `StreamMux` 是「中央事件分发器」：持有主事件日志、管理 Transformer 注册表、把事件路由过管线、负责全部生命周期收尾，并且是子图 mini-mux 的母体。

### 6.1 构造与注册顺序

```python
def __init__(self, transformers=None, *, is_async=False, factories=None,
             scope=(), _assign_seq=True):
    self.is_async = is_async
    self.scope: tuple[str, ...] = scope
    self._assign_seq = _assign_seq
    self._events: StreamChannel[ProtocolEvent] = StreamChannel()   # 主事件日志
    self._events._bind(is_async=is_async)
    self._events._bind_mux(self)
    ...
    pre: list[StreamTransformer] = []
    rest: list[StreamTransformer] = []
    if factories is not None:
        for factory in factories:
            transformer = factory(scope)       # 工厂以 scope 为唯一位置参数调用
            (pre if getattr(transformer, "before_builtins", False) else rest
             ).append(transformer)
        for transformer in (*pre, *rest):
            self._register(transformer)
    for transformer in transformers or ():
        (pre if ... else rest).append(transformer)
    for transformer in (*pre, *rest):
        self._register(transformer)
```

**解析**，三条注册规则：
1. **factories 先于 pre-built**：`factories=` 的产物会被 `_make_child` 克隆进每个子图 scope；`transformers=`（预构建实例）只注册在根 mux，不下传。
2. **`before_builtins = True` 的排在最前**：mux 在注册时按这个类属性把工厂分成 pre/rest 两条道，pre 道整体先注册，道内保持传入顺序。这是给「内容改写型」Transformer（PII 脱敏、脏词过滤）留的官方钩子——它们必须赶在 `MessagesTransformer` 等内置件**急切快照文本字段之前**完成改写（详见 §7.2 的 foot-gun 警告）。
3. **主日志本身就是一条无名 `StreamChannel`**，构造时即绑定 sync/async 模式——`for event in run` 迭代的就是它。

### 6.2 `_register`：注册一个 Transformer 发生的六件事

```python
def _register(self, transformer: StreamTransformer) -> None:
    if transformer_requires_async(transformer) and not self.is_async:
        raise RuntimeError(
            f"{type(transformer).__name__} requires an async run — ... "
            "Use astream(), not stream()."
        )
    projection = transformer.init()
    if not isinstance(projection, dict):
        raise TypeError(...)
    conflicts = set(projection) & set(self.extensions)
    if conflicts:
        attributions = ", ".join(
            f"{key!r} (owned by {self._projection_owners[key]})"
            for key in sorted(conflicts)
        )
        raise ValueError(f"Transformer ... projection keys that conflict ...: {attributions}")
    is_native = bool(getattr(transformer, "_native", False))
    self._transformers.append(transformer)
    self._bind_and_wire(projection, native=is_native)
    self.extensions.update(projection)
    ...
    transformer._on_register(self)
```

按序：① **async 守卫**——`transformer_requires_async()`（`_types.py`）判定：显式 `requires_async=True`，或覆写了 `aprocess/afinalize/afail` 任一且未声明 `supports_sync=True`（用 `getattr(cls, name) is not getattr(StreamTransformer, name)` 做「是否覆写」的同一性检测）；这类 Transformer 注册进同步 mux 直接 `RuntimeError`，**fail fast 而不是首个事件时才炸**。② 调 `init()` 拿投影 dict。③ **键冲突检测**——报错信息会指名冲突键现在归谁所有（`_projection_owners`）。④ `_bind_and_wire` 绑定/接线投影里的所有 StreamChannel（§6.3）。⑤ 合并进 `extensions`，native 键记入 `native_keys`。⑥ 回调 `_on_register(self)`——默认 no-op，`SubgraphTransformer` 覆写它来抓 mux 引用（造 mini-mux 用）。

### 6.3 `_bind_and_wire` 与 channel 命名规则

```python
def _bind_and_wire(self, projection: dict[str, Any], *, native: bool = False) -> None:
    for value in projection.values():
        if isinstance(value, StreamChannel):
            value._bind(is_async=self.is_async)     # 绑定迭代协议
            value._bind_mux(self)                   # 挂戳计数器
            self._channels.append(value)            # 登记，收尾时自动 close/fail
            if value.name is not None:
                method = value.name if native else f"custom:{value.name}"

                def _make_forward(method_name: str) -> Callable[[Any], None]:
                    def _forward(item: Any) -> None:
                        self._forward(method_name, item)
                    return _forward

                value._wire(_make_forward(method))
```

**channel 命名规则**（用户教程里最需要记住的一张表）：

| 通道形态 | 主日志里的 `method` | 例子 |
|---|---|---|
| 无名通道（`StreamChannel()`） | **不转发**，纯本地投影 | `run.values`、`run.messages`、`run.subgraphs`、`ToolCallStream.output_deltas` |
| 命名通道 + native Transformer（`_native=True`） | `<name>` 原样 | `LifecycleTransformer` 的 `StreamChannel("lifecycle")` → `method="lifecycle"` |
| 命名通道 + 用户 Transformer | `custom:<name>` | 自定义 `StreamChannel("progress")` → `method="custom:progress"` |

`_make_forward` 用闭包工厂冻结 `method_name`——经典的循环变量捕获陷阱防御（直接在循环里写 lambda 会全部绑到最后一个值）。

### 6.4 `_forward` 与 `push`/`apush`：seq 的时机

```python
def _forward(self, method: str, item: Any) -> None:
    """Inject a ProtocolEvent for a StreamChannel push.

    Forwarded events bypass the transformer pipeline to avoid
    infinite recursion (a transformer that pushes to a channel
    during `process()` would re-trigger itself). ...
    """
    event: ProtocolEvent = {
        "type": "event", "method": method,
        "params": {"namespace": [], "timestamp": int(time.time() * 1000), "data": item},
    }
    if self._assign_seq:
        self._seq += 1
        event["seq"] = self._seq
    self._events.push(event)
```

```python
def push(self, event: ProtocolEvent) -> None:
    keep = True
    for transformer in self._transformers:
        if not transformer.process(event):
            keep = False
    if keep:
        if self._assign_seq:
            self._seq += 1
            event["seq"] = self._seq
        self._events.push(event)
```

三个精妙细节：

1. **转发事件绕过 Transformer 管线**——否则「Transformer 在 `process()` 里向命名通道 push」会再次触发自己的 `process()`，无限递归。代价是转发事件不经过任何过滤/改写，直接进主日志（wire 消费者看到的就是通道原始载荷）。
2. **seq 在管线之后、入主日志之前才赋值**。docstring 解释了为什么：Transformer 在 `process()` 期间向命名通道 push 产生的转发事件（走 `_forward`，立即拿号）会拿到**比触发它的原始事件更早**的 seq——保证主日志里 seq 单调且符合真实到达序。`ProtocolEvent.seq` 是跨根事件的唯一全序依据；`params.timestamp` 是墙钟毫秒，NTP 校时可能回拨，**不能用来排序**（`_types.py` docstring 明示）。
3. **抑制语义**：任一 Transformer 返回 `False`，事件不进主日志，但**排它后面的 Transformer 依然全部看到该事件**，且已看到者的副作用保留。`_TasksLifecycleBase` 就靠这个把 `tasks` 事件从主日志里折叠掉（§7.3.8）。

`apush` 是异步镜像：`await transformer.aprocess(event)` 逐个来——**慢的 `aprocess` 会串行化整条管线，这是特性不是缺陷**（docstring：这正是「后一个 Transformer 或同步消费者能看到异步改写结果」的保证）。解耦型异步工作应该用 `schedule()`（§7.2）。

### 6.5 收尾四重奏：close / fail / aclose / afail

```python
def close(self) -> None:
    first_error: BaseException | None = None
    for transformer in self._transformers:
        try:
            transformer.finalize()
        except BaseException as e:
            if first_error is None:
                first_error = e
    for ch in self._channels:
        if not ch._closed:
            ch.close()
    self._events.close()
    if first_error is not None:
        raise first_error
```

**解析**：`finalize()` 逐个跑，**任何一个炸了都不中断清理**——其余 Transformer、所有投影通道、主日志照样关闭，第一个错误在清理完成后重抛（泵会把它转成 fail 路径）。`fail(err)` 同构但更宽容：Transformer 的 `fail()` 钩子异常直接吞掉，通道逐个 `ch.fail(err)`，最后主日志 `fail`——订阅者在游标处收到原始异常。

异步版多一步**计划任务管理**：
- `aclose()`：先收集所有 Transformer 经 `schedule()` 挂起的 asyncio Task（`_collect_scheduled_tasks`），`asyncio.gather(..., return_exceptions=True)` **等它们全部落地**，有 `on_error="raise"` 的任务抛了就转成错误；然后才 `afinalize()` → 关通道 → 关主日志。这消除了「最后一个任务还没写完通道就被关」的竞态——`_types.py` 里 `afinalize` 的 docstring 专门强调 "By the time this runs, the mux has already awaited every task started via schedule(), so StreamChannels can be closed here without a last-task-wins race."
- `afail(err)`：先 **cancel 并 await** 所有计划任务（清理不与在飞任务竞态），再跑 `afail` 钩子、fail 所有通道。

### 6.6 bind_pump / bind_apump 与 `_make_child`

```python
def bind_pump(self, fn: Callable[[], bool]) -> None:
    self._pump_fn = fn
    self._events._request_more = fn          # 主日志
    for ch in self._channels:                # 每条投影通道
        ch._request_more = fn
    for transformer in self._transformers:   # 声明了 _bind_pump 的 transformer
        bind = getattr(transformer, "_bind_pump", None)
        if bind is not None:
            bind(fn)
```

**解析**：泵绑定要传播到三类对象——主日志、所有已登记通道、以及**鸭子类型的 `_bind_pump`/`_bind_apump` 钩子**。第三类是给「在事件处理过程中动态创建子流对象」的 Transformer 用的：`MessagesTransformer` 收到 `message-start` 才创建 `ChatModelStream`，创建时把泵塞给它（`stream.set_request_more(fn)`），于是消费者迭代 `chat.text` 就能驱动整张图；`ToolCallTransformer` 对 `ToolCallStream._output_deltas` 做同样的事。

```python
def _make_child(self, scope: tuple[str, ...]) -> StreamMux:
    if self._factories is None:
        raise RuntimeError(
            "StreamMux._make_child requires the mux to be constructed "
            "with `factories=`; pre-built transformers can't be cloned ..."
        )
    child = StreamMux(
        factories=self._factories,
        is_async=self.is_async,
        scope=scope,
        _assign_seq=False,        # 子 mux 不给转发事件盖号
    )
    if self._pump_fn is not None:
        child.bind_pump(self._pump_fn)     # 继承父泵
    if self._apump_fn is not None:
        child.bind_apump(self._apump_fn)
    return child
```

**解析**：mini-mux 三要素——**同一份工厂列表**（每个 scope 得到全新的 Transformer 实例，且工厂列表继续下传，孙图还能再克隆）、**继承泵绑定**（子图投影的游标驱动的是根泵）、**`_assign_seq=False`**（子 mux 转发的事件对象与父日志**共享同一个 dict**，不允许改写信封；seq 只属于根）。这也回收了 §4.1 的伏笔：为什么 v3 拒绝预构建 Transformer 实例——没有工厂就没法 `_make_child`。

## 7. `_convert.py`：v2 StreamPart → v3 ProtocolEvent 协议桥

> **命名澄清**：这一层常被笼统称作「v1 → v2 协议转换」。**以源码为准**：`_convert.py` 做的是 **v2 `StreamPart` → v3 `ProtocolEvent`** 的信封转换——把 §3 里 `Pregel._output` 产出的类型化 stream part 包上一层统一协议信封，供 v3 的 `StreamMux` 消费。它是「v2 扁平事件」与「v3 投影层」之间唯一的桥。

### 7.1 整个转换层只有一个函数

`_convert.py` 全文只有 **33 行**，公共符号仅 `convert_to_protocol_event` 一个。原因：**繁重的规范化已经在上一站做完**——`Pregel._output`（`pregel/main.py:4184`）在 `version="v2"` 分支里已经产出 `{"type", "ns", "data"[, "interrupts"]}` 形状的 `StreamPart`，`_convert` 只负责「**换信封**」，不做类型判别、不做载荷搬运。

```python
# 文件：langgraph/stream/_convert.py:1-33（全文）
from __future__ import annotations

import time
from typing import Any, cast

from langgraph.stream._types import ProtocolEvent, _ProtocolEventParams
from langgraph.types import StreamPart


def convert_to_protocol_event(part: StreamPart) -> ProtocolEvent:
    """Convert a v2 StreamPart to a ProtocolEvent."""
    part_dict = cast(dict[str, Any], part)
    params: _ProtocolEventParams = {
        "namespace": list(part_dict["ns"]),      # ① tuple → list：对齐线上 list[str] 形状
        "timestamp": int(time.time() * 1000),    # ② 墙钟毫秒——注意它**非单调**
        "data": part_dict["data"],               # ③ 载荷原样透传，零拷贝
    }
    if "interrupts" in part_dict:                # ④ 只有 values part 才带这个键
        params["interrupts"] = part_dict["interrupts"]
    return {
        "type": "event",                         # ⑤ 统一信封判别式（常量）
        "method": part_dict["type"],             # ⑥ v2 的 type 直接升格为协议 method
        "params": params,
    }
```

### 7.2 三次字段搬运，一张表看清

| 步骤 | 来源（v2 `StreamPart`） | 去向（v3 `ProtocolEvent`） | 说明 |
|---|---|---|---|
| ① 命名空间 | `part["ns"]`（`tuple[str, ...]`） | `params["namespace"]`（`list[str]`） | **拷贝**成 list——避免与 tuple 共享可变引用；协议线上字段是 `list[str]` |
| ② 时间戳 | ——（v2 无此字段） | `params["timestamp"]` = `int(time.time() * 1000)` | **新生成**，墙钟毫秒 |
| ③ 载荷 | `part["data"]` | `params["data"]` | 原样透传，不做深拷贝（`data` 可能是任意对象） |
| ④ 中断 | `part["interrupts"]`（可选，`tuple`） | `params["interrupts"]` | 仅 `values` part 带；`in` 判定避免 KeyError |
| ⑤ 判别式 | —— | `type = "event"`（字面量） | 固定值——`ProtocolEvent` 是唯一事件形状 |
| ⑥ 方法名 | `part["type"]`（`"values"`/`"messages"`/…） | `method` | v2 的类型标签直接成为协议方法名 |

**注意 ③ 是「零拷贝」**：`data` 不复制。这也是为什么 `ProtocolEvent` 会被称为「信封」——它只是给原有载荷套了一层地址（`namespace` + `timestamp` + `method`），载荷本体仍由下游 Transformer 各自解释。

### 7.3 信封的类型定义：`_types.py` 的两个 TypedDict

信封的形状由 `_types.py` 里一对 TypedDict 固定。先看参数体：

```python
# 文件：langgraph/stream/_types.py:14-26
class _ProtocolEventParams(TypedDict):
    """Parameters for a protocol event.

    `timestamp` is wall-clock milliseconds since the epoch and can go
    backwards across NTP adjustments — use `ProtocolEvent.seq` for
    ordering.
    """

    namespace: list[str]
    timestamp: int
    data: Any
    interrupts: NotRequired[tuple[Any, ...]]   # 只有 values 事件带
```

再看事件本体：

```python
# 文件：langgraph/stream/_types.py:28-41
class ProtocolEvent(TypedDict):
    """A protocol event emitted by the streaming infrastructure.

    Wraps a raw stream part (values, messages, custom, etc.) in a uniform
    envelope with a monotonic sequence number assigned by the root StreamMux.
    Consumers that need a total order across root events should use `seq`, not
    `params.timestamp` (which is wall-clock and not monotonic).
    """

    type: Literal["event"]
    event_id: NotRequired[str]  # snake_case，对齐 langchain-protocol 线上字段名
    seq: NotRequired[int]
    method: str  # StreamMode 值："values"、"messages"、"custom" 等
    params: _ProtocolEventParams
```

**两个时间字段的语义差异**（这是整个 v3 排序逻辑的地基）：

| 字段 | 来源 | 单调性 | 用途 |
|---|---|---|---|
| `params["timestamp"]` | `_convert` 里 `time.time()*1000` | ❌ NTP 回拨会倒退 | 墙钟展示，或跨进程/跨节点时的近似时间 |
| `seq` | **根 `StreamMux` 分配**（不是 `_convert`） | ✅ 单调递增 | 根事件**全序**——`run.interleave()` 就是按它排序的（见 §4.2） |

关键事实：**`_convert` 不写 `seq`**。`seq` 由根 mux 的 `push()`/`apush()` 在事件进入主日志**前一刻**赋号（`_mux.py:293-295`、`375-378`），子 mux（`_make_child`）则以 `_assign_seq=False` 构造，转发的子图事件**共享同一份 dict、不再编号**。也就是说：`_convert` 产出的是一个**没有 seq 的信封**，`seq` 是「根日志注脚」，不是「事件属性」。

### 7.4 v2 type → v3 method：七种 part 的映射

`_convert` 里 `method = part["type"]` 是直通映射。v2 侧 `StreamPart` 家族（`types.py:341-351`）与协议侧 method 一一对应：

| v2 `StreamPart.type` | v3 `ProtocolEvent.method` | 载荷 `data` 形状 | 消费它的内置 Transformer |
|---|---|---|---|
| `"values"` | `"values"` | 完整 state（`read_channels()`） | `ValuesTransformer` |
| `"updates"` | `"updates"` | `{node_name: update}` | `UpdatesTransformer` |
| `"messages"` | `"messages"` | `(message, metadata)` 二元组 | `MessagesTransformer` |
| `"custom"` | `"custom"` | 节点里 `StreamWriter` 推的任意值 | `CustomTransformer` |
| `"checkpoints"` | `"checkpoints"` | `get_state()` 同构快照 | `CheckpointsTransformer` |
| `"tasks"` | `"tasks"` | `TaskPayload` / `TaskResultPayload` | `TasksTransformer`、`LifecycleTransformer`、`SubgraphTransformer` |
| `"debug"` | `"debug"` | `checkpoint`/`task`/`task_result` 包装 | `DebugTransformer` |

> **`interrupts` 从哪来**：v2 的 `values` part 在 `_output` 里把 state 里的 `__interrupt__` **pop** 出来，单独塞进 `part["interrupts"]`（`main.py:4221-4228`）。`_convert` 的 ④ 步就是把它抬进 `params`。`ValuesTransformer.process` 随后读 `params.get("interrupts", ())` 累计到 `run.interrupted` / `run.interrupts`（`transformers.py:77-81`）。

### 7.5 调用点：泵里就两个地方

`convert_to_protocol_event` 全项目只有两处调用，都在 `run_stream.py` 的「泵」里：

```python
# 文件：langgraph/stream/run_stream.py:117-122（同步泵）
        try:
            part = next(self._graph_iter)
            event = convert_to_protocol_event(part)   # ← 同步调用点
            self._observe_event(event)
            self._mux.push(event)
            return True
```

```python
# 文件：langgraph/stream/run_stream.py:441-443（异步泵）
                event = convert_to_protocol_event(part)   # ← 异步调用点
                self._observe_event(event)
                await self._mux.apush(event)
```

**设计含义**：转换是**每次拉取一事件、拉一次转一次**的惰性过程——没有「先把整条流读完再统一转换」的批处理。这也印证了 §1.2 的「调用者驱动泵」：`graph_iter` 每 `next` 一个 v2 part，立刻封成协议事件、喂给 mux、再交给 Transformer 管线。

### 7.6 为什么这一层必须拆出来

| 若把转换内联进泵 | 抽成独立函数的收益 |
|---|---|
| 同步/异步两个泵各写一份信封拼装代码，易漂移 | 一份实现，两处复用 |
| 无法单测「v2 part → 协议信封」而不启动整张图 | 纯函数（除 `time.time()`），可直接断言 |
| 线上字段（`namespace` 的 list 形状、`event_id` 命名）散落 | 信封契约集中在 `_types.py` 两个 TypedDict + 一个函数 |

一句话收束：**`_convert.py` 是 v3「协议立起来」的第一个动词**——它把 v2 的「扁平数据块」翻译成 v3 管线认识的「统一事件」，之后的 Transformer 才可能对着 `event["method"]` 做分派。

## 8. 逐 token 流式：messages 模式与 content-block 协议

逐 token（token-by-token）流式是 LLM 应用最直观的能力——用户边看模型「打字」边阅读。LangGraph 1.2.9 里它有一套**双轨**实现：**v1 的 `AIMessageChunk` 轨**（`stream_mode="messages"` 直接产 `(message, metadata)` 元组）与**v2 的 content-block 协议轨**（`stream_events(version="v3")` 产结构化 content-block 事件）。本章把两条轨的**回调机制（Handler）、事件形状、投影对象（Transformer）**一次讲透。

> **命名澄清**：任务提到「`MessagesTransformerV2`」。**源码里没有这个类**——`transformers.py` 只有一个 `MessagesTransformer`（它同时处理 v1 整条 message 与 v2 协议事件两种载荷）。V2 的差异全部落在 **Handler 层**：`StreamMessagesHandlerV2`（`pregel/_messages.py:259`）。请记住这个分工：**Handler 决定「发什么事件」，Transformer 决定「怎么投影」**。

### 8.1 v1 轨：`StreamMessagesHandler`

`stream_mode="messages"` 的产出来自 `pregel/_messages.py` 的 `StreamMessagesHandler`——一个 LangChain 回调处理器，`run_inline = True`（强制在主线程跑，避免顺序/锁问题）。

```python
# 文件：langgraph/pregel/_messages.py:49-104（节选）
class StreamMessagesHandler(BaseCallbackHandler, _StreamingCallbackHandler):
    """A callback handler that implements stream_mode=messages.

    Collects messages from:
    (1) chat model stream events; and
    (2) node outputs.
    """

    run_inline = True

    def __init__(self, stream, subgraphs, *, parent_ns=None) -> None:
        self.stream = stream          # Callable[[StreamChunk], None]：往流里投事件
        self.subgraphs = subgraphs    # 是否发子图里的消息
        self.metadata: dict[UUID, Meta] = {}   # run_id → (ns, metadata)
        self.seen: set[int | str] = set()      # 已发过的 message.id，用于去重
        self.parent_ns = parent_ns
```

它挂的四个回调，各管一段生命周期：

| 回调 | 触发时机 | 动作 | 源码行 |
|---|---|---|---|
| `on_chat_model_start` | LLM 开始调用 | 由 `metadata["langgraph_checkpoint_ns"]` 推出 ns；按 `subgraphs` 过滤；记 `run_id → (ns, metadata)` | `_messages.py:130-149` |
| `on_llm_new_token` | 每来一个 token | 把 `chunk.message`（一个 `AIMessageChunk`）**逐块** `_emit` | `_messages.py:151-164` |
| `on_llm_end` | LLM 结束 | 发最终完整消息（`dedupe=True`），清理 `metadata[run_id]` | `_messages.py:166-179` |
| `on_chain_end` | 节点返回 | 扫节点输出里所有 `BaseMessage` 发出去（覆盖「节点直接返回消息」的场景） | `_messages.py:223-246` |

**「逐 token」的实现**就在 `on_llm_new_token`：

```python
# 文件：langgraph/pregel/_messages.py:151-164
    def on_llm_new_token(
        self, token, *, chunk=None, run_id, parent_run_id=None, tags=None, **kwargs
    ) -> Any:
        if not isinstance(chunk, ChatGenerationChunk):
            return
        if meta := self.metadata.get(run_id):
            self._emit(meta, chunk.message)   # ← 每个 token 一个 AIMessageChunk
```

投出去的 `StreamChunk` 是 `(ns, "messages", (message, metadata))` 三元组：

```python
# 文件：langgraph/pregel/_messages.py:97-104
    def _emit(self, meta: Meta, message: BaseMessage, *, dedupe: bool = False) -> None:
        if dedupe and message.id in self.seen:
            return
        else:
            if message.id is None:
                message.id = str(uuid4())     # 无 id 就补一个，保证可去重
            self.seen.add(message.id)
            self.stream((meta[0], "messages", (message, meta[1])))
```

**去重（dedupe）机制**：流式 token 已经把消息「边到边发」过了；`on_llm_end` / `on_chain_end` 又要把最终消息发一次。为避免**同一消息发两遍**，Handler 维护 `seen: set[message.id]`——发最终版时 `dedupe=True`，命中 `seen` 就跳过。`on_chain_start` 还会把**输入里已有的消息 id** 预登记进 `seen`（`_messages.py:213-221`），防止回显。

### 8.2 ns 推导：`langgraph_checkpoint_ns` 去掉尾段

`on_chat_model_start` 里有一句关键的 ns 推导：

```python
# 文件：langgraph/pregel/_messages.py:141-149
        if metadata and (not tags or (TAG_NOSTREAM not in tags)):
            ns = tuple(cast(str, metadata["langgraph_checkpoint_ns"]).split(NS_SEP))[:-1]
            if not self.subgraphs and len(ns) > 0 and ns != self.parent_ns:
                return
            if (filtered_tags := filter_to_user_tags(tags)) is not None:
                metadata["tags"] = filtered_tags
            self.metadata[run_id] = (ns, metadata)
```

三件事：
1. **`NS_SEP`（`"|"`）切分** `langgraph_checkpoint_ns`——该字段结尾是 `节点名:任务id`，`[:-1]` 丢掉尾段，得到**该 LLM 调用所属子图自己的 ns**。
2. **`subgraphs` 过滤**：`subgraphs=False` 且 ns 非空（即调用发生在子图里）且不等于 `parent_ns`，直接 `return` 不发。
3. **`parent_ns` 逃生口**：让「节点里显式 `stream_mode="messages"` 拉某个子图」的调用仍能看到自己的消息。

`TAG_NOSTREAM`、`TAG_HIDDEN` 是「显式退出流式」的标签闸——带了这些 tag 的调用不发事件。

### 8.3 v2 轨：`StreamMessagesHandlerV2` 与 content-block 协议

要拿到 v3 的**结构化 content-block**（而不是裸 `AIMessageChunk`），必须让 chat model 走「事件生成器」而不是「token 回调」。`StreamMessagesHandlerV2` 通过**声明第二个基类**来翻转这条路由：

```python
# 文件：langgraph/pregel/_messages.py:259-272
class StreamMessagesHandlerV2(StreamMessagesHandler, _V2StreamingCallbackHandler):
    """v2 variant of `StreamMessagesHandler`.

    Declaring `_V2StreamingCallbackHandler` as a base flips
    `BaseChatModel.invoke` to route through `_stream_chat_model_events`
    (firing `on_stream_event`) instead of `_stream` (firing
    `on_llm_new_token`). ...
    """
```

**机制要点**：
- `_V2StreamingCallbackHandler` 是一个**标记基类**。`BaseChatModel` 检测到处理器链里存在它，就把 `invoke` 改走 `_stream_chat_model_events` → 逐块触发 **`on_stream_event`**（content-block 协议事件），而不再是 `_stream` → `on_llm_new_token`。
- V2 handler 里 `on_llm_new_token` 被**故意覆盖成空操作**（`_messages.py:275-295`），防止任何残留的 v1 chunk 泄漏进消息通道。
- **谁来决定挂哪个 handler**：不是用户，而是 `_pregel_stream_v3` / `_apregel_stream_v3`——它们把 `CONFIG_KEY_STREAM_MESSAGES_V2=True` 打进 configurable（`main.py:3548`、`3603`），`pregel` 内层据此外挂 V2 handler。这就是为什么**直接调 `graph.stream(stream_mode="messages")` 仍是 v1 形状**——那条路没打这个 key。
- `on_stream_event`（`_messages.py:373-408`）把协议事件**原样**塞进同一个 messages 流通道，并在 metadata 里补 `run_id`（供 Transformer 关联）：

```python
# 文件：langgraph/pregel/_messages.py:397-408
        if meta := self.metadata.get(run_id):
            if event.get("event") == "message-start":
                self._streamed_run_ids.add(run_id)   # 标记：这条 run 走了流式
                msg_id = event.get("message_id")
                if msg_id:
                    self.seen.add(msg_id)            # 让 on_chain_end 去重跳过最终消息
            v2_meta = {**meta[1], "run_id": str(run_id)}
            self.stream((meta[0], "messages", (event, v2_meta)))
```

注意 V2 的 `_find_and_emit_messages` 会**跳过 `ToolMessage`**（`_messages.py:307-334`）——工具结果属于 `tools` 通道 / state，不属于聊天 token 流。v1 轨仍会发 `ToolMessage`（兼容旧行为）。

### 8.4 content-block 协议：五类事件

content-block 协议是 `langchain_protocol` 定义的**单消息生命周期**。核心 docstring 一句话概括（`langchain_core/language_models/_compat_bridge.py:17-23`）：

```text
Lifecycle::

    message-start
      -> content-block-start   (first time each index is observed)
      -> content-block-delta*  (per chunk, carrying the slice)
      -> content-block-finish  (finalized block)
    -> message-finish
```

| 事件 | `event` 值 | 携带关键字段 | 语义 |
|---|---|---|---|
| 消息开始 | `"message-start"` | `role`、`id`、`metadata`（provider/model） | 一次 LLM 调用开始 |
| 内容块开始 | `"content-block-start"` | `index`、块类型（`text`/`reasoning`/…） | 某索引的块首次出现（**信息性**，不累积） |
| 内容块增量 | `"content-block-delta"` | `index`、`delta`（`text-delta`/`reasoning-delta`/`block-delta`/`data-delta`） | 一次 token 切片 |
| 内容块完成 | `"content-block-finish"` | `index`、`content`（终结块，如 `tool_call` 已解析的 args） | 该块定稿 |
| 消息结束 | `"message-finish"` | `usage`、`metadata`、`additional_kwargs` | 消息收尾，附 usage |

**内容块类型**（`langchain_protocol/protocol.py`）覆盖 text / reasoning / tool_call / invalid_tool_call / server_tool_call(+result/chunk) / image / audio / video / file / non_standard——即 `AIMessage.content_blocks` 的完整谱系。

### 8.5 `MessagesTransformer`：把两类载荷投影成 `ChatModelStream`

`MessagesTransformer`（`transformers.py:155`）是原生（`_native=True`）内置 Transformer，`required_stream_modes=("messages",)`。它的 `process` 每次面对 `params["data"] = (payload, metadata)`，按**两类载荷**分派：

```python
# 文件：langgraph/stream/transformers.py:265-290（节选）
    def process(self, event: ProtocolEvent) -> bool:
        if event["method"] != "messages":
            return True
        params = event["params"]
        if params["namespace"] != self._scope_list:   # 只管自己这一层
            return True

        payload, metadata = params["data"]
        node = metadata.get("langgraph_node")
        run_id = str(metadata.get("run_id", "")) if metadata else ""

        if isinstance(payload, dict) and "event" in payload:       # 载荷①：协议事件
            self._route_protocol_event(cast("MessagesData", payload), run_id=run_id, node=node)
        elif (isinstance(payload, BaseMessage)
              and not isinstance(payload, AIMessageChunk)
              and not isinstance(payload, ToolMessage)):           # 载荷②：整条 BaseMessage
            self._route_whole_message(payload, node=node)
        return True
```

| 载荷形状 | 来源回调 | 处理路径 | 结果 |
|---|---|---|---|
| `dict` 带 `"event"` 键（`MessagesData`） | `on_stream_event`（V2） | `_route_protocol_event`：按 `run_id` 找到/新建 `ChatModelStream`，`dispatch` 事件 | 逐 token 累积的**活**流对象 |
| 整条 `BaseMessage`（非 chunk、非 tool） | `on_chain_end`（节点返回消息） | `_route_whole_message`：用 `message_to_events` **合成**一遍协议生命周期，再 push 一个已完成的流 | 已完成消息的**回放**流 |
| 裸 `AIMessageChunk`（v1 token） | `on_llm_new_token` | **忽略**——不在 `.messages` 投影里 | 需 v1 形状请直接用 `stream_mode="messages"` |

**逐 token 的核心是 `_route_protocol_event`**（`transformers.py:292-322`）：`message-start` 时创建 `ChatModelStream`、塞进 `_by_run[run_id]`、push 到日志；后续事件按 `run_id` 找到该流并 `dispatch`；`message-finish` 时从 `_by_run` 删除。`role == "tool"` 的 `message-start` 会被加入 `_ignored_runs` 直接丢弃（工具结果不算聊天 token）。

**两类载荷共存的根因**：`stream_events(version="v3")` 里 LLM 走 V2 handler 产协议事件（载荷①），但节点若直接 `return {"messages": [AIMessage(...)]}`，那个最终消息从 `on_chain_end` 来（载荷②）。`_streamed_run_ids` + `seen` 去重保证同一条消息不双计。

### 8.6 `ChatModelStream`：投影对象长什么样

`_make_stream`（`transformers.py:229-263`）新建 `ChatModelStream`（同步）或 `AsyncChatModelStream`（异步），并把**图泵**塞给它（`set_request_more` / `set_arequest_more`）——于是**消费者迭代 `chat.text` 就能驱动整张图**（回到 §1.2「调用者驱动泵」）。两个类都在 `langchain_core/language_models/chat_model_stream.py`。

投影只读属性与用法（`chat_model_stream.py:1042-1151`）：

| 属性 | 同步返回 | 异步返回 | 用法 |
|---|---|---|---|
| `.text` | `SyncTextProjection` | `AsyncProjection` | `for d in msg.text` 逐 delta；`str(msg.text)` 拿全文 |
| `.reasoning` | `SyncTextProjection` | `AsyncProjection` | 推理链内容，接口同 `.text` |
| `.tool_calls` | `SyncProjection` | `AsyncProjection` | 迭代拿 `ToolCallChunk` 增量；`.get()`/`await` 拿 `list[ToolCall]` |
| `.output` | `AIMessage`（属性，**阻塞**到结束） | `AsyncProjection`（**await**） | 组装好的完整 `AIMessage` |
| `msg`（流本体） | 可迭代 | 可异步迭代 | **原始协议事件回放**（`_events` 缓冲，多消费者可重放） |

**usage** 不在单独投影上——结束后在 `msg.output.usage_metadata`（`_finish` 把 `data["usage"]` 存进 `_usage_value`，`chat_model_stream.py:898`）。

**累积内部的三个关键不变量**（`_ChatModelStreamBase`）：
1. **每块独立存储**：`_text_per_block` / `_reasoning_per_block` 按 wire `index` 分桶——避免消息级累加器把先前的块文本「串味」到后一块。
2. **tool_call_chunk 合并黏性**：`_merge_chunk_into_store` 保持 `id`/`name` 只取首个非空、`args` **累加拼接**（`chat_model_stream.py:53-65`），与 v1 `AIMessageChunk.__add__` 语义一致。
3. **收尾 sweep**：`message-finish` 时对未定稿的 chunk 调 `finalize_tool_call_chunk` 解析 args，非法者归入 `invalid_tool_calls`（`chat_model_stream.py:910-924`）。

**`.output.content` 恒为 v1 块列表**——这是硬契约（`chat_model_stream.py:1059-1066`）：无论底层模型 `output_version` 设成什么，`ChatModelStream` 都按 content-block 协议组装，并在 `response_metadata["output_version"] = "v1"` 钉死，防止下游翻译器二次解释。

### 8.7 「messages-tuple」这个叫法

项目 §2.2 已指出：`messages-tuple` **不是进程内 `StreamMode`**（进程内的正名是 `messages`）。它是对 `stream_mode="messages"` **输出形状**的口语化称呼——每个事件是 `(message, metadata)` **二元元组**（见 `types.py:286-296` 的 `MessagesStreamPart`）。前端 `useChat` 之所以要显式请求 `messages-tuple`，正是为了拿到这个二元组形状来逐 token 渲染。v3 里这个形状被 `MessagesTransformer` 消化成 `ChatModelStream` 对象，不再暴露裸元组。

### 8.8 已知限制（源码明说）

`stream_events(version="v3")` 的 docstring（`main.py:3667-3676`）明确：**在 v3 运行的节点里再嵌 v1 `stream(stream_mode="messages")` 不能完全工作**——外层 V2 handler 已经把 `invoke` 改道，内层 v1 handler 收不到 `on_llm_new_token`；内层仍能通过 `on_llm_end` 拿到最终消息。要在嵌套里拿 token，要么内层也走 `stream_events(version="v3")`，要么直接 `chat_model.stream(...)`。

## 9. 子图流式穿透：`subgraphs=True`、命名空间与子 agent 识别

主图里嵌子图（`StateGraph` 作为节点、`create_agent` 作为工具、deepagents 的子 agent……）之后，一个自然的问题是：**怎么把子图内部的事件也流出来，并知道它来自哪一层**？回答是三项机制的组合：**命名空间（ns）**、**`subgraphs=True`**、**mini-mux 与 `SubgraphTransformer`**。本章顺着这三项逐一拆解，并说明「**`lc_agent_name` 识别子 agent**」的真实实现。

> **命名澄清**：任务里的「`LC_AGENT_NAME`」**不是常量**。源码里它是 metadata 里的字符串键 **`"lc_agent_name"`**（由 `create_agent` 写入子 agent 的 config metadata），`LifecycleTransformer`/`SubgraphTransformer` 读它来判断一个嵌套 run 是不是一个「有名字的子 agent」。全项目没有 `LC_AGENT_NAME` 这一符号。

### 9.1 命名空间（ns）：`|` 分隔、每段 `node:task_id`

LangGraph 用**检查点命名空间**表示「当前在第几层子图」。分隔符是 `NS_SEP = "|"`（`_constants.py:87`）；每段形如 `节点名:任务id`（`NS_END = ":"`，`_constants.py:89`，由 `prepare_next_tasks` 拼成）。例如：

```text
()                                      根图
("planner:3f9a")                         根图里 planner 节点拉起的第一个子图
("planner:3f9a", "search_tool:7c21")     该子图里 search_tool 拉起的孙图
```

`StreamChunk` 里的 ns 是 `tuple[str, ...]`；`_convert` 把它拷成 `list[str]` 放进协议事件（§7.2）。

**v2 输出里 ns 怎么露面**（`pregel/main.py:4184-4243`）：

| `stream_mode` | `stream_subgraphs` | v1 产出形状 | v2 产出形状 |
|---|---|---|---|
| 单值 | False | `payload` | `{"type", "ns", "data"}` |
| 多模式 | False | `(mode, payload)` | 同上（`type`=`mode`） |
| 单值 | True | `(ns, payload)` | 同上 |
| 多模式 | True | `(ns, mode, payload)` | 同上 |

即：v1 靠**元组层数**区分「有没有 ns / 有没有 mode」；v2 一律是带 `ns` 字段的 dict。v3 走 v2，所以协议事件天然带 `params["namespace"]`。

### 9.2 `subgraphs=True` 强制打开：v3 的不变式

`_pregel_stream_v3` / `_apregel_stream_v3` 调内层 `self.stream(..., subgraphs=True, version="v2")`——**v3 总是 `subgraphs=True`**，且**拒绝调用者再传** `stream_mode` / `subgraphs`（`main.py:384-395` 的 `_V3_INVARIANT_KWARGS` 抛 `TypeError`）。原因：v3 的 `stream_mode` 由 Transformer 的 `required_stream_modes` 并集算出（`_collect_stream_modes`，`main.py:398-414`），而子图穿透由 scoped mux 接管——两者都由 v3 自己拥有，放给调用者会破坏不变式。

```python
# 文件：langgraph/pregel/main.py:3533-3558（同步装配，异步同构）
        mux = StreamMux(
            factories=[
                ValuesTransformer,
                MessagesTransformer,
                LifecycleTransformer,
                SubgraphTransformer,
                *compiled_factories,
                *extra_factories,
            ],
            scope=parent_ns,
            is_async=False,
        )
        graph_iter = iter(
            self.stream(
                input,
                patch_configurable(config, {CONFIG_KEY_STREAM_MESSAGES_V2: True}),
                stream_mode=_collect_stream_modes(mux),
                subgraphs=True,
                version="v2",
                ...
            )
        )
        return GraphRunStream(graph_iter, mux)
```

注意这里用 `factories=`（不是 `transformers=`）——**这是子图穿透能成立的前提**：只有 `factories=` 构造的 mux 才能 `_make_child` 出 mini-mux（§6.6）。

### 9.3 `SubgraphTransformer`：把「发现子图」变成「可下钻 handle」

`SubgraphTransformer`（`transformers.py:670`）是原生 Transformer，`supports_sync=True`（同步/异步两车道都支持）。它**不消费任何数据流模式**（`required_stream_modes` 继承自基类，未声明），而是**监听 `tasks` 事件**来发现子图：`tasks` 在 `_TasksLifecycleBase` 里被 `process` 抑制（return False），不落到主日志，只在内部折叠成子图语义。

它的发现与建 handle 逻辑：

```python
# 文件：langgraph/stream/transformers.py:707-736（节选）
    def _should_track(self, ns: tuple[str, ...]) -> bool:
        # 只认「直接子图」——孙图交给子 mini-mux 自己的 SubgraphTransformer
        depth = len(self.scope)
        return len(ns) == depth + 1 and ns[:depth] == self.scope

    def _on_started(self, ns, graph_name, trigger_call_id) -> None:
        if self._mux is None:
            return
        try:
            child_mux = self._mux._make_child(ns)      # ← 关键：克隆一份 scoped mux
        except RuntimeError:
            return
        handle_cls = AsyncSubgraphRunStream if child_mux.is_async else SubgraphRunStream
        handle = handle_cls(mux=child_mux, path=ns,
                            graph_name=graph_name, trigger_call_id=trigger_call_id)
        self._handles[ns] = handle
        self._log.push(handle)                          # handle 进 run.subgraphs
```

**「直接子图」是刻意的**：每个子图 handle 的 mini-mux 里也有一个 `SubgraphTransformer`（因为 factories 下传），所以**孙图挂在子 handle 的 `.subgraphs` 上，永远不出现在根的 `.subgraphs` 日志里**——这让 `run.subgraphs` 的每一项都是「根的直接子图」，层级清晰。

### 9.4 mini-mux 三要素与事件转发

`_make_child`（`_mux.py:193-225`）建的子 mux 有三个特征（§6.6 已列，这里是**子图视角**的复述）：

| 特征 | 值 | 对子图流式的意义 |
|---|---|---|
| 工厂列表 | `self._factories`（原样下传） | 每个 scope 得到**全新** Transformer 实例，孙图还能再克隆 |
| 泵绑定 | 继承父 `_pump_fn` / `_apump_fn` | 子 handle 的游标**驱动根泵**（整个 run 前进） |
| `_assign_seq` | `False` | 转发事件共享同一 dict，不重复编号 |

**事件如何流进子 handle**：`SubgraphTransformer.process` 先跑 tasks bookkeeping（保证 handle 已存在），再**把事件同时转发给子 mini-mux**：

```python
# 文件：langgraph/stream/transformers.py:813-821（同步）
    def process(self, event: ProtocolEvent) -> bool:
        keep = super().process(event)          # 先处理 tasks（可能新建 handle）
        handle = self._handle_for_event(event) # 按 ns[:depth+1] 找到所属子 handle
        if handle is not None:
            handle._observe_event(event)
            handle._mux.push(event)            # ← 事件灌进子 mini-mux
        return keep
```

`_handle_for_event`（`transformers.py:801-811`）用 `ns[: depth + 1]` 取**该事件的直接所属子图**前缀，命中 `_handles` 就转进去——这就是「**按 ns 前缀路由事件**」。子 mini-mux 里的 `ValuesTransformer` / `MessagesTransformer` 等（scope=该子图 ns）于是只投影属于它这一层的事件；父 mux 的主日志仍然保留全部事件（父 `process` 返回 True 时）。

**handle 的泵委托**：`SubgraphRunStream` 用 `graph_iter=None` + `wire_pump=False` 构造，`_pump_next` **委托父泵**（`run_stream.py:613-627`）：

```python
# 文件：langgraph/stream/run_stream.py:613-627
    def _pump_next(self) -> bool:
        """Delegate to the parent's pump."""
        if (self._exhausted or self._seen_terminal
                or self._mux._events._closed or self._parent_pump_fn is None):
            return False
        return self._parent_pump_fn()
```

所以「迭代 `handle.values`」和「迭代 `run.values`」驱动的是**同一根泵**——子图投影不是独立的流，而是根流的一个 scoped 切面。

### 9.5 `lc_agent_name`：识别「这是一次子 agent 调用」

`_TasksLifecycleBase._handle_task_start`（`transformers.py:518-546`）从 task 事件的 metadata 里读 `lc_agent_name`，判定子 agent 边界：

```python
# 文件：langgraph/stream/transformers.py:522-543（节选）
        parsed_name, trigger_call_id = _parse_ns_segment(ns[-1])
        metadata = data.get("metadata") or {}
        child_lc = metadata.get("lc_agent_name")
        # 任何带 lc_agent_name 的嵌套 run 都是子 agent 边界（由 create_agent 设置）。
        # 无名的 run（lc_agent_name 为 None）被排除。
        is_subagent = child_lc is not None
        graph_name = child_lc if is_subagent else (parsed_name or None)
        cause: LifecycleCause | None = None
        if is_subagent and trigger_call_id is not None:
            tool_call_id = self._pending_tool_calls.get(trigger_call_id)
            if tool_call_id:
                cause = {"type": "toolCall", "tool_call_id": str(tool_call_id)}
```

要点：
- **`graph_name` 的来源**：有 `lc_agent_name` 就用它（子 agent 名）；否则退回 ns 段里的节点名（`_parse_ns_segment`：`"planner:3f9a"` → `("planner", "3f9a")`，`transformers.py:346-353`）。
- **`cause` 的溯源**：`_record_pending_tool_calls` 从一个 tool-dispatch task 的 `input` 里**收走 `tool_call_id`**，按 `task_id` 存表（`transformers.py:488-516`）。当子 agent 的 ns 段 `node:<task_id>` 命中这个 id 时，就恢复出「**是哪个 tool call 催生了这个子 agent**」，装成 `{"type": "toolCall", "tool_call_id": ...}` 挂到 lifecycle payload 上。
- **边界语义的取舍**（源码注释原话）：同名嵌套 agent（子 agent 调自己）会**再次**冒出来；而「工具里调用的普通子图」会**继承父的 `lc_agent_name`**，于是也会被当成子 agent 上报（名字是父的）。要排除，就在调用该图时把 config 里的 `lc_agent_name` 置空。
- **`_record_identity`**（`transformers.py:475-486`）为每个 ns 记录首个 task 事件的 `lc_agent_name`，存在 `_lc_by_ns`，供需要「按名过滤子 agent」的派生 Transformer（如 deepagents 的 `SubagentTransformer`）使用。

### 9.6 生命周期三态：`LifecycleTransformer` 与 `SubgraphStatus`

`LifecycleTransformer`（`transformers.py:608`）与 `SubgraphTransformer` 共用 `_TasksLifecycleBase`，但用途不同：前者产**线路可序列化**的 `lifecycle` 事件，后者产**进程内导航 handle**。

| 维度 | `LifecycleTransformer` | `SubgraphTransformer` |
|---|---|---|
| 投影键 | `run.lifecycle`（`StreamChannel[LifecyclePayload]`，**具名** → 自动转发到主日志，method=`"lifecycle"`） | `run.subgraphs`（无名 channel，**本地**，不转发活 handle） |
| 追踪范围 | **所有深度**（scope 以下任意层：`_should_track` 用 `>`，`transformers.py:634-636`） | **仅直接子图**（`== depth + 1`） |
| 每层产物 | `LifecyclePayload` dict | `SubgraphRunStream` / `AsyncSubgraphRunStream` |
| 终端动作 | push `{"event": status, ...}` | 标记 handle `status`/`error`，关/失败 mini-mux |

`LifecyclePayload` 与 `SubgraphStatus`（`transformers.py:343-371`）：

```python
SubgraphStatus = Literal["started", "completed", "failed", "interrupted", "drained"]

class LifecyclePayload(TypedDict, total=False):
    event: SubgraphStatus
    namespace: list[str]
    graph_name: NotRequired[str]
    trigger_call_id: NotRequired[str]
    cause: NotRequired[LifecycleCause]     # toolCall / send / edge
    error: NotRequired[str]
```

**状态是怎么算出来的**：

| 场景 | 判定函数 | 结果 |
|---|---|---|
| 父 task 的 `TaskResultPayload` 带 `interrupts` | `_terminal_from_result`（`transformers.py:591-605`） | `"interrupted"`（**优先**于 error——因为 `GraphInterrupt` 表现为 interrupts 而非 error） |
| 同 result 带 `error` | 同上 | `"failed"`，`error=str(...)` |
| 同 result 都没带 | 同上 | `"completed"` |
| run 抛 `GraphDrained` | `_status_from_exception`（`transformers.py:582-588`） | `"drained"` |
| run 抛 `GraphInterrupt` | 同上 | `"interrupted"` |
| run 抛其它异常 | 同上 | `"failed"`，`error=str(err)` |
| 收尾时仍开着（无父 result） | `finalize` / `_complete_open_handles` | 补 `"completed"` |

**终端只会触发一次**：`_mark_terminal` 用 `handle._seen_terminal` 做一次性闸（`transformers.py:760-773`），避免「父 result 到达」与「finalize 兜底」重复上报。

### 9.7 一次子图子 agent 调用的完整流式时序

把上面拼起来，一次「主图 → 工具 → 子 agent」的 v3 流式时序是：

```text
1. 主图调度一个 tool-dispatch task
   → tasks(start) 事件，input 是 tool_call_with_context → _record_pending_tool_calls 记 tool_call_id
2. 子 agent 子图首次出现，ns = ("tool_name:task_id",)
   → tasks(start) 事件，metadata.lc_agent_name = "researcher"
   → _handle_task_start：is_subagent=True，graph_name="researcher"，cause={toolCall}
   → LifecycleTransformer：push {"event":"started", graph_name, cause}
   → SubgraphTransformer：_make_child(ns) → handle 进 run.subgraphs
3. 子 agent 内的 LLM 调用、节点更新，ns 前缀都带 ("tool_name:task_id",)
   → 事件按 ns[:depth+1] 路由进子 mini-mux → 填充 handle.messages / handle.values
4. 子 agent 结束，父 task 的 TaskResultPayload 到达
   → _pop_terminal_transitions 识别 → _on_terminal → handle.status="completed"
   → LifecycleTransformer：push {"event":"completed"}
```

**消费端有两种口味**：要**线路可序列化**的扁平生命周期，就 `for ev in run.lifecycle`；要**在进程内下钻**子图内容，就 `for handle in run.subgraphs: async for chunk in handle.messages: ...`（下钻必须在循环体内、下一个泵周期前完成——同 §5「惰性订阅」约束）。

## 10. 自定义流式通道：`get_stream_writer()` / `StreamWriter` / `emit_output_delta`

前九章讲的都是「**框架往你手里推事件**」。这一章反过来：**你怎么往流里推自己的事件**。三条通道，三种粒度：

| 通道 | API | 载体 | 典型用途 | 对应 StreamMode |
|---|---|---|---|---|
| 节点级自定义数据 | `get_stream_writer()` → `StreamWriter` | configurable 里的 `runtime.stream_writer` | 节点内上报进度、中间结果 | `custom` |
| 工具级增量输出 | `ToolRuntime.emit_output_delta(delta)` | ContextVar `_tool_call_writer` | 长跑工具边跑边吐日志 | `tools` |
| 自定义投影 | 子类化 `StreamTransformer` + `StreamChannel` | mux 工厂注册 | 派生新的强类型投影 | 由 `required_stream_modes` 声明 |

### 10.1 `get_stream_writer()`：从 configurable 取 writer

`get_stream_writer()` 在 `langgraph/config.py:126-196`，本体只有两行：

```python
# 文件：langgraph/config.py:195-196
    runtime = get_config()[CONF][CONFIG_KEY_RUNTIME]
    return runtime.stream_writer
```

- `get_config()` 读的是 `var_child_runnable_config`（LangChain 的 **ContextVar**）——所以 `get_stream_writer()` **必须在 runnable 上下文里调用**（节点/任务体内），图外调用抛 `RuntimeError("Called get_config outside of a runnable context")`。
- `CONFIG_KEY_RUNTIME`（`_constants.py:70`）指向一个 `Runtime` 实例，其 `.stream_writer` 就是节点级的写入口。
- `StreamWriter` 的类型（`types.py:136-139`）就是 `Callable[[Any], None]`：

```python
StreamWriter = Callable[[Any], None]
"""`Callable` that accepts a single argument and writes it to the output stream.
Always injected into nodes if requested as a keyword argument, but it's a no-op
when not using `stream_mode="custom"`."""
```

**ContextVar 传播的硬约束**（docstring 反复强调，`config.py:132-135`）：Python `<3.11` 时，`asyncio.create_task` **不复制** contextvar，异步场景下 `get_stream_writer()` 会失效。所以本项目（Python 3.11+）才能安全地在 async 节点里用它；跨版本部署时这是首要排查点。

**它什么时候真的推送**：writer 是**一直在的**（`custom` 是否在 `stream_mode` 里不影响 `get_stream_writer()` 拿到对象），但**只有 `custom` 被订阅时才有消费者**——没开 `custom` 时写入被静默丢弃。这正是 docstring 说的「no-op when not using `stream_mode='custom'`」。

### 10.2 `custom` 模式：v1 裸值 vs v2 类型化 part

| 版本 | 调用 | 产出 |
|---|---|---|
| v1 | `graph.stream(input, stream_mode="custom")` | 裸值 `payload`（节点推什么就是什么） |
| v2 | `graph.stream(input, stream_mode="custom", version="v2")` | `{"type": "custom", "ns": ns, "data": payload}`（`CustomStreamPart`，`types.py:299-307`） |
| v3 | `stream_events(version="v3")` | `run.custom`（`CustomTransformer` 投影），且 `custom` 协议事件可在主日志里 `for ev in run` |

`CustomTransformer`（`transformers.py:85-117`）只抓**自己 scope 这一层**的 `custom` 事件：

```python
# 文件：langgraph/stream/transformers.py:110-117
    def process(self, event: ProtocolEvent) -> bool:
        if event["method"] != "custom":
            return True
        params = event["params"]
        if params["namespace"] != self._scope_list:   # 只认本层
            return True
        self._log.push(params["data"])
        return True
```

子图里的 `custom` 数据会出现在**对应子图 handle 的 `.custom`** 上（因为事件按 ns 路由进子 mini-mux，见 §9.4）。

### 10.3 `StreamChannel` 命名规则：`custom:` 前缀

自定义投影要把事件「顺带」转发到**主事件日志**（让远端 SDK 也能收到）时，靠的是 `StreamChannel(name=...)`。命名前缀由**发射方是不是原生 Transformer** 决定：

```python
# 文件：langgraph/stream/_mux.py:485-494（节选）
                if value.name is not None:
                    method = value.name if native else f"custom:{value.name}"

                    def _make_forward(method_name: str) -> Callable[[Any], None]:
                        def _forward(item: Any) -> None:
                            self._forward(method_name, item)
                        return _forward

                    value._wire(_make_forward(method))
```

| 发射方 | `_native` | channel 名 `"lifecycle"` 转发成的 method |
|---|---|---|
| 内置/原生 Transformer | `True` | `"lifecycle"`（原名） |
| 用户自定义 Transformer | 默认 `False` | `"custom:lifecycle"`（加前缀） |

**为什么加前缀**：用户通道的 method 不能撞上内置的 7 个正名；统一挂到 `custom:` 命名空间下，消费端能按前缀区分「框架事件」与「用户扩展事件」。`_forward`（`_mux.py:496-523`）注入的转发事件**绕过 Transformer 管线**（避免「在 `process` 里 push 又触发自己」的无限递归），只在主日志可见。

**无名 channel** 则纯本地（如 `MessagesTransformer._log`、`SubgraphTransformer._log`）——活对象不可序列化，不该进线路。

### 10.4 工具级流式：`emit_output_delta` 与 ContextVar

让一个**长跑工具**边执行边吐输出，用 `ToolRuntime.emit_output_delta(delta)`（`prebuilt/tool_node.py:1732-1750`）：

```python
# 文件：langgraph/prebuilt/tool_node.py:1732-1750
    def emit_output_delta(self, delta: Any) -> None:
        """Stream a partial output chunk on the `tools` stream channel.
        ...
        Silent no-op when the graph was not run with
        `"tools"` in `stream_mode` (no writer is set) ...
        """
        writer = _tool_call_writer.get()
        if writer is None:
            return
        writer(delta)
```

它读的是 `_tools.py` 里一个 **ContextVar**：

```python
# 文件：langgraph/pregel/_tools.py:22-32
ToolCallWriter = Callable[[Any], None]

_tool_call_writer: ContextVar[ToolCallWriter | None] = ContextVar(
    "langgraph_tool_call_writer", default=None
)
"""ContextVar holding the writer for the currently-executing tool call.

Set by `StreamToolCallHandler.on_tool_start` and reset on end/error.
Read by `ToolRuntime.emit_output_delta` (in `langgraph.prebuilt`)."""
```

**设置/复位闭环**由 `StreamToolCallHandler` 完成（`_tools.py:35-269`）：

```python
# 文件：langgraph/pregel/_tools.py:142-166（节选）
        def writer(delta: Any) -> None:
            self.stream((ns, "tools",
                {"event": "tool-output-delta",
                 "tool_call_id": tool_call_id, "delta": delta}))

        token = _tool_call_writer.set(writer)     # ← on_tool_start 时装入
        self._run_to_call[run_id] = (ns, tool_call_id, token)
        ...
        self.stream((ns, "tools", {"event": "tool-started", ...}))
```

`on_tool_end` / `on_tool_error` 里用 `_reset_writer(token)` 复位（`_tools.py:213-222`）——注意它 `try/except ValueError` 兜住「`on_tool_end` 跑在不同 context」的情况（LangChain 可能把回调交给线程 worker 而不复制 context）。

**`tools` 通道的四类事件**：

| `event` | 触发回调 | 字段 |
|---|---|---|
| `tool-started` | `on_tool_start` | `tool_call_id`、`tool_name`、`input` |
| `tool-output-delta` | `emit_output_delta` | `tool_call_id`、`delta` |
| `tool-finished` | `on_tool_end` | `tool_call_id`、`output` |
| `tool-error` | `on_tool_error` | `tool_call_id`、`message` |

**ns 解析与过滤**（`_ns_for_emit`，`_tools.py:87-119`）与 `StreamMessagesHandler` 同构：解析 `langgraph_checkpoint_ns`、丢尾段、`subgraphs=False` 且不在 `parent_ns` 时抑制、带 `TAG_NOSTREAM` 抑制。

`emit_output_delta` 的**静默 no-op** 语义很重要：工具作者可以无条件写 `runtime.emit_output_delta(...)`，不必自己判断 `"tools"` 在不在 `stream_mode` 里——没装 writer 就自动丢弃。

### 10.5 `ToolCallTransformer` 与 `ToolCallStream`

要**在进程内**消费工具流，注册 `ToolCallTransformer`（`prebuilt/_tool_call_transformer.py`）——它**不是默认内置**，需 `builder.compile(transformers=[ToolCallTransformer])` 显式开启（`tools` 通道是用户 opt-in）。它把 `tools` 事件投影成 `ToolCallStream` 句柄，挂在 `run.tool_calls`：

| `ToolCallStream` 字段 | 含义 |
|---|---|
| `tool_call_id` / `tool_name` / `input` | 从 `tool-started` 起就稳定 |
| `output_deltas` | `StreamChannel`，迭代消费增量（同步/异步随 run） |
| `output` | `tool-finished` 的终结载荷，未结束/失败为 `None` |
| `error` | `tool-error` 的错误串 |
| `completed` | 观察到终结事件后为 `True` |

投影逻辑（`_tool_call_transformer.py:79-120`）：`tool-started` → 建流并 push；`tool-output-delta` → `_push_delta`；`tool-finished` → `_finish(output)`；`tool-error` → `_fail(message)`。它在 `process` 里**永远返回 True**——原始 `tools` 事件仍留在主日志，线路消费者可自行重建句柄。

**泵绑定**：`ToolCallTransformer` 用 `_bind_pump` / `_bind_apump` 记录泵（`_tool_call_transformer.py:50-63`），`_new_stream` 时把泵塞进 `output_deltas`，于是迭代增量能驱动根图——和 `MessagesTransformer` 同一套「`_bind_pump` 鸭子类型钩子」机制（§6.6）。

### 10.6 写一个自定义 `StreamTransformer` 的骨架

自定义投影的完整契约（`_types.py:44-330`）已经写在 `StreamTransformer` 的 ABC docstring 里。最小实现只需 `init` + `process`：

```python
from langgraph.stream import StreamTransformer, StreamChannel

class CostTransformer(StreamTransformer):
    """统计每个节点上报的成本事件，投影成 run.cost。"""
    _native = True                              # 让 run.cost 成为直接属性
    required_stream_modes = ("custom",)         # 需要图产出 custom 事件

    def __init__(self, scope=()):
        super().__init__(scope)
        self._log = StreamChannel("cost")       # 具名 → 自动转发为 custom:cost

    def init(self):
        return {"cost": self._log}

    def process(self, event):
        if event["method"] == "custom":
            # 只统计本层；子图的事件会走子 mini-mux
            if event["params"]["namespace"] == list(self.scope):
                self._log.push(event["params"]["data"])
        return True                             # True=保留进主日志
```

**可选钩子与车道选择**（`_types.py:61-115`）：

| 成员 | 默认 | 何时覆盖 |
|---|---|---|
| `init()` | 抽象 | 必写，返回投影 dict |
| `process()` / `aprocess()` | `process` 抽象；`aprocess` 委托 `process` | 至少覆盖一个 |
| `finalize()` / `fail(err)` | 空 | 要收尾/处理错误时（投影里的 `StreamChannel` 会被 mux **自动** close/fail，通常不用写） |
| `schedule(coro)` | —— | 需要「解耦的异步副作用」（异步打分、外部追踪）；mux 持有任务、`aclose` 时统一 await |
| `requires_async` | `False` | 用了 `schedule()` 但没覆盖 `aprocess` 时须显式 `True`，否则同步车道注册会报错 |
| `supports_sync` | `False` | 覆盖了异步钩子但仍想支持同步车道时置 `True`（`SubgraphTransformer` 即如此） |
| `before_builtins` | `False` | 内容改写型（PII 脱敏、脏词过滤）须**早于** `MessagesTransformer` 这类「急切快照文本」的内置 Transformer |

**`before_builtins` 的脚枪**（源码原文，`_types.py:100-109`）：这一车道的 Transformer **先于** `LifecycleTransformer` / `SubgraphTransformer` 看到 `tasks` 事件——改 `namespace` 或 data 里的 `id`/`result`/`error`/`interrupts` 会**打乱它们记账**。只观察、或只改无内置读取的字段（如 `messages` 事件的 `delta.text`）。

### 10.7 注册路径：编译期 vs 调用期

自定义 Transformer 有两条注册路径，**工厂签名一致**（`(scope) -> StreamTransformer`）：

```python
# 编译期：所有 v3 run 都带上它
graph = builder.compile(transformers=[CostTransformer])

# 调用期：仅本次 run 带（追加在编译期工厂之后）
run = graph.stream_events(input, version="v3", transformers=[lambda scope: CostTransformer(scope)])
```

`_normalize_stream_transformer_factories`（`main.py:417-447`）把两种写法都规整成 scoped 工厂；**预构建实例会被拒**（`TypeError`，`main.py:430-436`）——因为它无法被 `_make_child` 克隆到子图 scope。要传配置就写 `lambda scope: MyTransformer(scope, foo=...)`。

## 11. 完整代码示例

三个例子从易到难：**① 基础多模式流式**（值/更新/自定义）→ **② 自定义 Transformer**（走公开导出路径 `langgraph.stream`）→ **③ 多消费者并发读取**（`asyncio.gather` / `tee`）。每个例子都可直接改自一个 `StateGraph`，注释说明每一步背后的源码机制（回指前文小节）。

> 约定：本项目默认 **Python 3.11+**（`get_stream_writer()` 的 ContextVar 传播依赖此版本，见 §10.1）。

### 11.1 示例 ①：基础 `astream` 多模式流式（values + updates + custom）

目标：一个问题 + 两个节点的小图，同时订阅 **values**（完整状态快照）、**updates**（节点增量）、**custom**（节点内上报的进度）。三个模式各用各的消费者逻辑——攒状态、看更新、打印进度条。

```python
import asyncio
from typing import TypedDict, Annotated
from operator import add

from langgraph.graph import StateGraph, START, END
from langgraph.config import get_stream_writer          # §10.1：节点内拿 StreamWriter


class State(TypedDict):
    query: str                      # 原始问题
    steps: Annotated[list[str], add]  # 用 add reducer 累加每一步说明


async def plan_node(state: State) -> dict:
    """规划节点：演示 custom 模式上报进度。"""
    writer = get_stream_writer()                 # 取节点级 writer
    writer({"progress": "planning", "pct": 10})  # → stream_mode="custom" 的消费者
    await asyncio.sleep(0.05)                    # 假装干活
    writer({"progress": "planning", "pct": 100})
    return {"steps": ["planned"]}                # → updates 模式能收到


async def answer_node(state: State) -> dict:
    """回答节点：也上报一段 custom。"""
    writer = get_stream_writer()
    writer({"progress": "answering"})
    return {"steps": ["answered"]}


builder = StateGraph(State)
builder.add_node("plan", plan_node)
builder.add_node("answer", answer_node)
builder.add_edge(START, "plan")
builder.add_edge("plan", "answer")               # 顺序执行，便于观察事件顺序
builder.add_edge("answer", END)
graph = builder.compile()


async def main() -> None:
    # 多模式 = 传 list；开 custom 才能收到 writer 推的数据（§10.2）
    stream_modes = ["values", "updates", "custom"]

    # astream 返回的是「每个事件一层」的扁平流；
    # 多模式时每个事件形如 (mode, payload)（§3.2 / §9.1）
    async for mode, payload in graph.astream(
        {"query": "Q3 各部门工时"},
        stream_mode=stream_modes,
    ):
        if mode == "values":
            # values：每步之后的完整状态快照（含本次全部字段）
            print(f"[values]   steps={payload['steps']}")
        elif mode == "updates":
            # updates：{节点名: 该节点返回的增量}，只发变化的字段（§2.1）
            for node_name, update in payload.items():
                print(f"[updates]  {node_name} -> {update}")
        elif mode == "custom":
            # custom：节点里 writer(...) 推什么就是什么（§10.1）
            print(f"[custom]   {payload}")

    # 若只想要最终状态，直接 await 一次 invoke 即可（不需要驱动流）：
    final = await graph.ainvoke({"query": "Q3 各部门工时"})
    print("final:", final["steps"])


if __name__ == "__main__":
    asyncio.run(main())
```

**运行时的典型输出**（顺序即事件到达顺序）：

```text
[custom]   {'progress': 'planning', 'pct': 10}
[updates]  plan -> {'steps': ['planned']}
[custom]   {'progress': 'planning', 'pct': 100}
[values]   steps=['planned']
[custom]   {'progress': 'answering'}
[updates]  answer -> {'steps': ['answered']}
[values]   steps=['planned', 'answered']
final: ['planned', 'answered']
```

**要点**：
- 多模式时**每个事件是二元元组 `(mode, payload)`**；单模式时直接是 payload。想再带上子图 ns，加 `subgraphs=True`，形状变成 `(ns, mode, payload)`（§9.1 的表）。
- `custom` 必须在 `stream_mode` 列表里，否则 `writer(...)` 的调用被静默丢弃（§10.1）。
- `values` 与 `updates` 的差别：前者是**全量快照**，后者是**节点增量**。

### 11.2 示例 ②：自定义 `StreamTransformer`（公开导出路径 `langgraph.stream`）

目标：写一个「成本/耗时」Transformer，把节点通过 `custom` 上报的耗时聚合成 `run.timings`，并让每个耗时也以 `custom:timings` 转发到主日志（供远端 SDK 订阅）。Transformer 从**公开导出面** `langgraph.stream` 导入（不是 `langgraph.stream.transformers` 私有模块）。

```python
import asyncio
import time
from typing import TypedDict

# ① 公开导出路径：langgraph.stream 的 __init__ 已导出 StreamTransformer / StreamChannel（§10.6）
from langgraph.stream import StreamChannel, StreamTransformer

from langgraph.graph import StateGraph, START, END
from langgraph.config import get_stream_writer


class State(TypedDict):
    tick: int


async def slow_node(state: State) -> dict:
    """上报一个节点耗时事件（custom 载荷是 dict）。"""
    writer = get_stream_writer()
    t0 = time.perf_counter()
    await asyncio.sleep(0.08)
    writer({"event": "timing", "node": "slow", "ms": (time.perf_counter() - t0) * 1000})
    return {"tick": state["tick"] + 1}


class TimingTransformer(StreamTransformer):
    """把 custom 里的 timing 事件投影成 run.timings。

    两个投影键：
      - "timings"  ：数据流（本进程内 iterate run.timings 消费）
      - "total_ms" ：mux 关闭时算出的总耗时（在 finalize 里写入 StreamChannel 的收尾）
    这里演示「一个 Transformer 同时暴露多条投影」。
    """

    _native = True                       # 让 run.timings 直接可用（§10.6）
    required_stream_modes = ("custom",)  # 告诉 v3：本图必须产出 custom 事件

    def __init__(self, scope: tuple[str, ...] = ()) -> None:
        super().__init__(scope)
        # 具名 channel：push 时会自动转发为 protocol method（§10.3）
        # 按「默认非原生（无 _native）」的规则，会转发成 "custom:timings"
        self._timings: StreamChannel[dict] = StreamChannel("timings")
        self._scope_list = list(scope)
        self._total = 0.0

    def init(self) -> dict:
        return {"timings": self._timings}

    def process(self, event) -> bool:
        # 只认本层（child scope 的事件走子 mini-mux，§9.4）
        if event["method"] == "custom":
            if event["params"]["namespace"] == self._scope_list:
                payload = event["params"]["data"]
                if isinstance(payload, dict) and payload.get("event") == "timing":
                    self._total += payload.get("ms", 0.0)
                    self._timings.push(payload)     # 转发 + 本地订阅
        return True                                 # True=事件保留进主日志

    def finalize(self) -> None:
        # 收尾：把总量塞进 channel 尾部（channel 会被 mux 自动 close，§6.5）
        self._timings.push({"event": "timing_total", "ms": self._total})


builder = StateGraph(State)
builder.add_node("slow", slow_node)
builder.add_edge(START, "slow")
builder.add_edge("slow", END)

# ② 编译期注册：所有 v3 run 都带 TimingTransformer（§10.7）
graph = builder.compile(transformers=[TimingTransformer])


async def main() -> None:
    # v3 入口：返回 AsyncGraphRunStream，投影通过 run.xxx 访问（§4.3）
    run = await graph.astream_events({"tick": 0}, version="v3")

    # 投影是「调用者驱动泵」：迭代 run.timings 会把整张图跑完（§1.2）
    async for item in run.timings:
        if item["event"] == "timing":
            print(f"[timing]  {item['node']}: {item['ms']:.1f} ms")
        else:
            print(f"[timing]  total: {item['ms']:.1f} ms")

    # 主日志里也能看到转发事件（method="custom:timings"）——断开本地订阅后仍可见
    # output 属性把 run 跑到结束并返回最终状态（§4.3）
    print("final state:", await run.output())


if __name__ == "__main__":
    asyncio.run(main())
```

**投影访问的两条路径**（都成立）：

| 路径 | 写法 | 适用 |
|---|---|---|
| 直接属性 | `run.timings`（因为 `_native=True`） | 本进程内消费 |
| extensions 映射 | `run.extensions["timings"]` | 统一遍历所有投影（含非 native 的） |

**主日志订阅**（原始协议事件流）：

```python
    # 若换成 async for ev in run：拿到的是 ProtocolEvent
    #   {"type":"event","method":"custom:timings","params":{...},"seq":N}
    #   —— 用户自定义具名 channel 的转发 method 一定带 "custom:" 前缀（§10.3）
```

### 11.3 示例 ③：多消费者并发读取（`asyncio.gather` / `tee`）

目标：**同一个 run 上两条投影同时被两个协程消费**。由于每个投影是**单消费者**（第二次 `aiter` 会抛 `RuntimeError`），要么「不同投影各一个消费者」（`gather` 天然可行），要么「同一条投影要扇出」（用 `.atee(n)`）。

```python
import asyncio
from typing import TypedDict
from operator import add
from typing_extensions import Annotated

from langgraph.graph import StateGraph, START, END
from langgraph.config import get_stream_writer


class State(TypedDict):
    log: Annotated[list[str], add]


def node_a(state: State) -> dict:
    get_stream_writer()({"from": "a"})       # custom 事件
    return {"log": ["a"]}


def node_b(state: State) -> dict:
    get_stream_writer()({"from": "b"})
    return {"log": ["b"]}


builder = StateGraph(State)
builder.add_node("a", node_a)
builder.add_node("b", node_b)
builder.add_edge(START, "a")
builder.add_edge("a", "b")
builder.add_edge("b", END)
graph = builder.compile()


async def consume_custom(run) -> list:
    """消费者 1：只盯 run.custom 投影。"""
    out = []
    async for item in run.custom:            # 驱动共享泵（§4.3）
        print(f"[custom-consumer] {item}")
        out.append(item)
    return out


async def consume_updates(run) -> list:
    """消费者 2：只盯 run.updates 投影。"""
    out = []
    async for item in run.updates:
        print(f"[updates-consumer] {item}")
        out.append(item)
    return out


async def main() -> None:
    run = await graph.astream_events({"log": []}, version="v3")

    # —— 场景 A：两个消费者各读一条投影 ——
    # 两条投影各自的缓冲独立，多个等待者（await 泵）时靠 asyncio.Condition
    # 「take-a-number」串行化对 graph_aiter 的推进（§4.3），互不丢事件。
    customs, updates = await asyncio.gather(
        consume_custom(run),
        consume_updates(run),
    )
    print("custom 事件数:", len(customs), " update 事件数:", len(updates))


async def main_tee() -> None:
    """场景 B：同一条投影要两个消费者 ⇒ 用 atee(n) 扇出（§5.4）。"""
    run = await graph.astream_events({"log": []}, version="v3")

    branches = run.values.atee(2)             # 同一条 values 流 → 2 个独立异步迭代器

    async def drain(name, it):
        n = 0
        async for _ in it:
            n += 1
        print(f"[{name}] drained {n} values")

    # 两个分支共用一个 asyncio.Lock 拉底层游标、分发到各自缓冲，天然背压（§5.4）
    await asyncio.gather(drain("A", branches[0]), drain("B", branches[1]))


if __name__ == "__main__":
    asyncio.run(main())
    asyncio.run(main_tee())
```

**多消费者的三条铁律**：

| 铁律 | 依据 |
|---|---|
| **每个投影只能有一个订阅者**；第二次 `__aiter__` 抛 `RuntimeError` | `stream_channel.py:218-221` |
| 不同投影可以有各自的订阅者并发跑（`gather` 可行） | `AsyncGraphRunStream._apump_next` 的 `asyncio.Condition`「take-a-number」保证同一时刻只有一个任务推进 `graph_aiter`，其余等待（§4.3） |
| 同一条投影要扇出，用 `.atee(n)`（异步）/ `.tee(n)`（同步） | `stream_channel.py:288-341` |

**背压**：async 迭代下，当某订阅者消费慢、其缓冲涨到 `maxlen` 时，`apush` 会 `await` 该订阅者 drain，从而**顶住泵、减速整张图**（`AsyncGraphRunStream` docstring，`run_stream.py:307-312`）。`maxlen=None`（默认）则不触发这层背压，靠调用者节奏自然限速。

**提前退出**：用 `async with` 保证早退时干净收尾（取消在途拉取、关闭 mux）：

```python
    async with await graph.astream_events(input, version="v3") as run:
        async for msg in run.messages:
            if "done" in str(msg):     # 只看一条就退出
                break                  # __aexit__ → run.abort() → 取消在途 pull
    # 这里 run 已安全关闭
```

## 12. 总结与最佳实践

### 12.1 全链回顾：一次事件的完整旅程（v3）

```text
① 图内动作
   节点执行 / LLM 产 token / writer(...) 推 custom / task 起止
        │  （LangChain 回调 + Pregel 循环投递 StreamChunk）
        ▼
② Pregel._output  v2 分支（main.py:4184）
   StreamChunk → {"type","ns","data"[,"interrupts"]}   （StreamPart，类型化扁平块）
        │
        ▼
③ run_stream 泵（同步 _pump_next / 异步 _apump_next）
   next(graph_iter) → convert_to_protocol_event（_convert.py）→ ProtocolEvent（统一信封，无 seq）
        │
        ▼
④ StreamMux.push / apush（根 mux）
   逐 Transformer 过 process/aprocess（可 return False 抑制）→ 根日志赋 seq → 追加
        │  同时：
        ├─ 具名 StreamChannel 的 push 自动转发回主日志（native=原名，用户=custom:前缀）
        └─ ns 命中子图前缀 → 事件转发进子 mini-mux（子图穿透）
        │
        ▼
⑤ Transformer 投影
   ValuesTransformer→run.values  MessagesTransformer→run.messages(ChatModelStream)
   SubgraphTransformer→run.subgraphs(handle)  LifecycleTransformer→run.lifecycle ...
        │
        ▼
⑥ 消费者（调用者驱动泵）
   for/async for run.<投影>  → 迭代即驱动 graph_iter → 循环回 ③
```

**核心不变量**：**没有后台线程/任务**（同步车道）——消费者的 `for` 循环就是泵；v3 不新增事件源，只是「把 v2 扁平流立起来」。

### 12.2 内置 Transformer 速查表

全部在 `langgraph/stream/transformers.py`（`ToolCallTransformer` 在 `prebuilt/_tool_call_transformer.py`）。「原生」=`_native=True`，投影键直接挂成 `run.<key>`。

| Transformer | 投影键 | 原生 | `required_stream_modes` | 一句话职责 | 源码 |
|---|---|---|---|---|---|
| `ValuesTransformer` | `values` | ✅ | `("values",)` | 状态快照流；顺带维护 interrupted/interrupts | `:28` |
| `CustomTransformer` | `custom` | ✅ | `("custom",)` | 节点 `StreamWriter` 推的任意值 | `:85` |
| `UpdatesTransformer` | `updates` | ✅ | `("updates",)` | 节点增量 `{node: update}` | `:120` |
| `MessagesTransformer` | `messages` | ✅ | `("messages",)` | 每 LLM 调用一个 `ChatModelStream`（协议事件 / 整条消息两形态） | `:155` |
| `CheckpointsTransformer` | `checkpoints` | ✅ | `("checkpoints",)` | `get_state()` 同构快照（需 checkpointer） | `:927` |
| `DebugTransformer` | `debug` | ✅ | `("debug",)` | checkpoint+task 带 step/timestamp 的调试事件 | `:966` |
| `TasksTransformer` | `tasks` | ✅ | `("tasks",)` | 原始 task 起止载荷 | `:1002` |

| `ToolCallTransformer` | `tool_calls` | ✅ | `("tools",)` | `ToolCallStream` 句柄；**需显式注册** | `prebuilt/_tool_call_transformer.py:14` |

**默认装配**（`_pregel_stream_v3`）：`ValuesTransformer` + `MessagesTransformer` + `LifecycleTransformer` + `SubgraphTransformer`，再拼编译期/调用期自定义工厂。**其余内置**（`Custom`/`Updates`/`Checkpoints`/`Debug`/`Tasks`/`ToolCall`）要显式注册才会进 mux——它们的 `required_stream_modes` 也只有被注册了才会并入内层 `stream_mode` 请求集。

### 12.3 选哪条 API：三档对照

| 需求 | 用 | 备注 |
|---|---|---|
| 只要扁平多模式数据（值/更新/自定义/消息元组） | `graph.stream(input, stream_mode=[...])` | v1 最稳；token 用 `messages` 拿 `(AIMessageChunk, metadata)` |
| 要类型化 part（带 ns 字段，便于自建消费） | `graph.stream(input, version="v2")` | 产出 `StreamPart` dict |
| 要结构化投影 / 子图下钻 / 自定义通道 / 内容块 | `graph.stream_events(input, version="v3")`（或 `astream_events`） | **`@beta`**；投影单消费者；调用者驱动泵 |
| 只要最终态 | `await graph.ainvoke(input)` | 不订阅任何投影 |

### 12.4 常见陷阱清单

1. **v3 拒绝 `stream_mode=` / `subgraphs=`**：它们由 v3 自持，传了报 `TypeError`（`main.py:387-395`）。想产某模式 ⇒ 注册声明该模式的 Transformer。
2. **投影单消费者**：第二次迭代同一投影抛 `RuntimeError`；要扇出用 `.tee(n)` / `.atee(n)`（§5.4、§11.3）。
3. **`seq` 不是事件属性**：`_convert` 不写 `seq`；它由根 mux 赋号，子 mux 不赋。要排序用 `seq`，**别用 `params["timestamp"]`**（墙钟非单调，`_types.py:14-25`）。
4. **`get_stream_writer()` 是 ContextVar**：必须在 runnable 上下文调用；Python `<3.11` 异步场景失效（§10.1）。
5. **`custom` 必须被订阅**：`writer(...)` 一直在，但没在 `stream_mode` 里就没有消费者——写入静默丢弃。`emit_output_delta` 同理（没开 `tools` 就是 no-op）。
6. **Transformer 必须传工厂/类，不能传实例**：v3 要 `_make_child` 克隆到子图 scope，预构建实例被拒（`main.py:430-436`）；且 `StreamMux` 只有 `factories=` 构造才能建子 mux（§6.6）。
7. **`before_builtins` 别乱改字段**：该车道先于 `LifecycleTransformer`/`SubgraphTransformer` 看 `tasks`；改 `namespace` 或 `id`/`result`/`error`/`interrupts` 会打乱它们记账（`_types.py:100-109`）。
8. **嵌套 v3 里的 v1 `messages` 不产 token**：外层 V2 handler 改道了 `invoke`；内层改用 v3 或直接 `chat_model.stream(...)`（§8.8）。
9. **子图投影的惰性订阅窗口**：`handle.messages` 等要在 `run.subgraphs` 的循环体内、下一泵周期**前**订阅并消费，否则可能错过窗口（§9.7）。
10. **v3 全系 `@beta`**：`GraphRunStream` / `AsyncGraphRunStream` / `_pregel_stream_v3` 都带 `@beta("... experimental ...")`；上生产要留迁移余量。
11. **`ToolMessage` 不进消息投影**：v2 轨刻意排除，工具结果去 `tools` 通道 / state（§8.3、§8.5）。
12. **`lifecycle` vs `subgraphs` 深度语义不同**：`lifecycle` 追踪**所有深度**，`subgraphs` 只给**直接子图**（孙图要下钻子 handle，§9.6）。

### 12.5 一句话总结

**LangGraph 1.2.9 的流式系统 =「v2 泵（扁平事件）+ 调用者驱动 + Transformer 投影管线」。** `_convert` 把 v2 part 封成协议事件，`StreamMux` 按 ns 分派给根/子 mux 的 Transformer，Transformer 用 `StreamChannel` 兜出可迭代的强类型投影，消费者迭代投影即反向驱动整张图；扩展点则是 `StreamTransformer`（工厂注册 + `StreamChannel`），逐 token 走 `messages`、子图穿透走 `subgraphs=True` + mini-mux、自定义数据走 `get_stream_writer()` / `emit_output_delta`。理解了「**泵—mux—投影—消费者**」这条闭环，就理解了 v3 的全部设计权衡。
