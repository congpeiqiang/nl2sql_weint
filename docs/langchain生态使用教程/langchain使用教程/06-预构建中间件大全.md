## 一、中间件机制基础

### 1.1 什么是中间件

在 LangChain 1.x 的 `create_agent()` 中，**中间件（Middleware）是插在"模型调用"与"工具调用"生命周期各个阶段的钩子对象**。它可以在不修改 Agent 核心循环代码的前提下，实现：改写系统提示词、过滤工具、重试/降级模型调用、拦截工具执行、压缩上下文、脱敏、人工审批等能力。

所有中间件都继承自 `langchain.agents.middleware.types.AgentMiddleware`：

```python
class AgentMiddleware(
    Generic[StateT, ContextT, ResponseT],
):
    state_schema: type[StateT] = AgentState   # 中间件可向 Agent State 追加字段
    tools: Sequence[BaseTool] = []            # 中间件可注册自己的工具
    transformers: Sequence[TransformerFactory] = []  # 流式输出转换器（PII 用）

    @property
    def name(self) -> str: ...                # 默认为类名

    # 六个生命周期钩子（每个都有同步 + 异步版本）：
    def before_agent(self, state, runtime) -> dict | None: ...
    async def abefore_agent(...): ...
    def before_model(self, state, runtime) -> dict | None: ...
    async def abefore_model(...): ...
    def after_model(self, state, runtime) -> dict | None: ...
    async def aafter_model(...): ...
    def after_agent(self, state, runtime) -> dict | None: ...
    async def aafter_agent(...): ...
    def wrap_model_call(self, request, handler) -> ModelCallResult: ...
    async def awrap_model_call(...): ...
    def wrap_tool_call(self, request, handler) -> ToolMessage | Command: ...
    async def awrap_tool_call(...): ...
```

要点：

- **钩子型**（`before_agent` / `before_model` / `after_model` / `after_agent`）：返回一个 state 更新字典（或 `None`），运行在图节点的前后。
- **包裹型**（`wrap_model_call` / `wrap_tool_call`）：拿到 `request` 与 `handler`（下一层回调），可以**修改请求、多次调用 handler（重试）、替换模型、甚至完全不调 handler（短路）**。基类的同步默认实现直接 `raise NotImplementedError`，并提示三种做法：实现同步版、用装饰器、或在同步版里调异步实现。

### 1.2 ModelRequest / ModelResponse

`wrap_model_call` 的核心数据结构是**不可变 dataclass** `ModelRequest`：

```python
class ModelRequest(Generic[ContextT]):
    model: BaseChatModel
    messages: list[AnyMessage]        # 不含 system message
    system_message: SystemMessage | None
    tool_choice: str | dict | None
    tools: Sequence[BaseTool | dict]
    response_format: ... | None
    state: AgentState
    runtime: Runtime[ContextT]
    model_settings: dict[str, Any]

    def override(self, **kwargs) -> ModelRequest:  # 内部用 dataclasses.replace
        ...
```

修改请求**必须**用 `request.override(model=..., messages=..., tools=...)` 生成新对象，直接给属性赋值已被弃用。`request.system_prompt` 是拼接后的字符串只读属性。

模型节点的返回值有三种形态（联合类型 `ModelCallResult`）：

```python
class ModelResponse(Generic[ResponseT]):
    result: list[BaseMessage]          # 通常是 [AIMessage]
    structured_response: ResponseT | None

class ExtendedModelResponse(ModelResponse):
    command: Command | None            # 额外携带 state 更新（不支持 goto/resume/graph）
```

`wrap_model_call` 允许直接返回裸 `AIMessage`（会被自动包成 `ModelResponse`），也可以返回 `ExtendedModelResponse` 在模型节点之后通过 reducer 追加 state 更新——DeepAgents 的 `FilesystemMiddleware` 就用它把"大消息已驱逐到文件"的标记写回 state。

### 1.3 ToolCallRequest

`wrap_tool_call` 收到的请求对象：

```python
class ToolCallRequest(Generic[ContextT]):
    tool_call: ToolCall            # {"name", "args", "id", "type"}
    tool: BaseTool | None
    state: AgentState
    runtime: ToolRuntime
    tool_call_id: str
```

### 1.4 AgentState 与 jump_to

中间件共享的 Agent State 定义在 `types.py`：

```python
class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    jump_to: Annotated[JumpTo, EphemeralValue, PrivateStateAttr]  # "tools" | "model" | "end"
    structured_response: Any
```

- `messages` 用 `add_messages` reducer 合并（按 id 去重/替换）。
- `jump_to` 是**瞬时值**：钩子返回 `{"jump_to": "end"}` 可以让图跳到终点；但钩子必须用 `@hook_config(can_jump_to=[...])` 声明，框架才会为它建立对应的条件边。
- State 注解 `OmitFromInput` / `OmitFromOutput` / `PrivateStateAttr` 控制字段是否出现在图的输入/输出 schema 中；`UntrackedValue` 通道用于**不持久化**的每轮计数器（如 `run_model_call_count`）。

### 1.5 函数式装饰器

不想写类时，`types.py` 提供 8 个装饰器，它们在运行时用 `type(...)` 动态合成一个中间件类：

```python
from langchain.agents.middleware import before_model, after_model, wrap_model_call, dynamic_prompt, hook_config

@before_model(can_jump_to=["end"])
def guard(state, runtime):
    if len(state["messages"]) > 100:
        return {"jump_to": "end"}
    return None

@dynamic_prompt
def inject_context(request) -> str:
    return f"当前用户: {request.runtime.context.user}"

@wrap_model_call
def retry_twice(request, handler):
    return handler(request.override(model=cheap_model))
```

可用装饰器：`@before_agent`、`@before_model`、`@after_model`、`@after_agent`、`@dynamic_prompt`（专用于动态系统提示词，函数收到 `ModelRequest`、返回 `str | SystemMessage`，内部转成 `request.override(system_message=...)` 再调 handler）、`@wrap_model_call`、`@wrap_tool_call`、`@hook_config`。装饰器都接受 `state_schema=`、`tools=`、`can_jump_to=`、`name=` 关键字参数；被装饰函数若是协程函数（`iscoroutinefunction` 判定），会自动绑定到对应的异步钩子（`abefore_model` 等）。

## 二、中间件执行顺序（Pipeline 调用链）

`create_agent(model, tools, middleware=[m1, m2, m3])` 构建的 LangGraph 图，一次完整运行的调用链如下：

```
before_agent:   m1 → m2 → m3          （按列表顺序，正序）
┌────────────────────────── Agent Loop ─────────────────────────┐
│ before_model:  m1 → m2 → m3          （正序；可返回 jump_to）      │
│                                                              │
│ model 节点（wrap_model_call 洋葱模型）:                          │
│   m1.wrap_model_call(                                        │
│     m2.wrap_model_call(                                      │
│       m3.wrap_model_call( 实际调用 LLM )))                     │
│   ★ 列表中第一个中间件 = 最外层                                   │
│                                                              │
│ after_model:   m1 → m2 → m3          （正序；可返回 jump_to）     │
│                                                              │
│ tools 节点（wrap_tool_call 洋葱模型，每个 tool_call 各走一遍）:     │
│   m1.wrap_tool_call(                                         │
│     m2.wrap_tool_call(                                       │
│       m3.wrap_tool_call( 实际执行工具 )))                        │
│   ★ 同样是第一个 = 最外层                                        │
└──────────────────────────────────────────────────────────────┘
after_agent:    m1 → m2 → m3           （正序）
```

理解顺序的三条铁律：

1. **钩子按列表正序执行**；`before_*` 的返回值在进入下一环节前已合并进 state。
2. **`wrap_*` 是洋葱模型，列表第一个是最外层**。外层能看见并改写内层的一切：外层 `ModelRetryMiddleware` 重试时，内层的提示词注入、工具过滤会跟着重跑一遍。
3. **handler 可以被调用 0 次、1 次或多次**：0 次 = 短路（如 `LLMToolEmulator` 用 LLM 模拟工具结果、HITL reject 后不执行真工具）；多次 = 重试（`ModelRetryMiddleware` / `ToolRetryMiddleware`）或降级（`ModelFallbackMiddleware` 换模型再调）。

`jump_to` 的生效方式：钩子函数需 `@hook_config(can_jump_to=["end"])`（类实现则在类上标注），框架据此在图里建条件边；`jump_to` 是 `EphemeralValue`，用完即清，不会污染下一轮。

另外注意 **GraphBubbleUp 异常**（`interrupt()`、`Command(goto=...)` 等控制流信号在内部以异常形式冒泡）：所有重试/错误处理中间件（`ModelRetryMiddleware`、`ToolRetryMiddleware`、`ToolErrorMiddleware`）都必须无条件放行这类异常，否则会把 HITL 中断误当作失败重试。

## 三、LangChain 预构建中间件详解

`langchain.agents.middleware.__init__` 公开导出 16 个中间件类及配套类型。以下按功能重要性逐一讲解。

### 3.1 SummarizationMiddleware

**一句话用途**：当对话历史超过阈值时，自动用 LLM 把旧消息压缩成一段摘要，防止上下文窗口溢出。

**源码位置**：`langchain/agents/middleware/summarization.py`

**关键签名**：

```python
class SummarizationMiddleware(AgentMiddleware):
    def __init__(
        self,
        model: str | BaseChatModel,
        *,
        trigger: ContextSize | TriggerClause | list[TriggerClause] | None = None,
        keep: ContextSize = ("messages", 20),
        token_counter: Callable = count_tokens_approximately,
        summary_prompt: str = DEFAULT_SUMMARY_PROMPT,
        trim_tokens_to_summarize: int = 4000,
        # 已弃用别名:
        max_tokens_before_summary: int | None = None,
        messages_to_keep: int | None = None,
    ): ...
```

**构造参数详解**：

| 参数 | 说明 |
|---|---|
| `model` | 用于生成摘要的模型（可与主模型不同，通常用便宜模型）；传字符串则内部 `init_chat_model` |
| `trigger` | 触发条件。三种写法：① 元组 `ContextSize`，如 `("tokens", 170_000)`、`("fraction", 0.8)`、`("messages", 60)`；② `TriggerClause` 字典（**同一字典内多条件是 AND**），如 `{"tokens": 100_000, "messages": 50}`；③ 字典列表（**列表之间是 OR**）。`fraction` 需要 `model.profile["max_input_tokens"]` 可用，否则初始化即 `ValueError` |
| `keep` | 摘要后保留多少最近消息，同为 `ContextSize` 元组；默认保留最后 20 条 |
| `token_counter` | token 计数函数；默认 `count_tokens_approximately`（针对 Anthropic 调优，chars_per_token=3.3） |
| `summary_prompt` | 摘要提示词模板，**必须含 `{messages}` 占位符**；默认模板分四节：SESSION INTENT / SUMMARY / ARTIFACTS / NEXT STEPS，并以 `<messages>` 标记分隔指令与消息体 |
| `trim_tokens_to_summarize` | 送去摘要的消息最多裁剪到多少 token（默认 4000），用 `trim_messages(strategy="last", start_on="human")` 裁剪，失败则退化为取最后 15 条 |

**工作原理**（`before_model` 钩子）：

1. `_should_summarize`：计算当前消息 token 数 ≥ 阈值，**或**最后一条 AIMessage 的 `usage_metadata.total_tokens` ≥ 阈值（且 provider 匹配，含 bedrock 别名归一）即触发。
2. 计算截断点 cutoff：`keep` 为 token/fraction 时用**二分查找**找到"后缀恰好放得下预算"的最早索引；为 messages 时直接 `len - messages_to_keep`。
3. `_find_safe_cutoff_point` 修正：**绝不把 AIMessage 和它的 ToolMessage 拆开**——若 cutoff 落在 ToolMessage 上，回退到发起该 tool_call 的 AIMessage；兜底则前移跳过 ToolMessage。
4. 对 cutoff 之前的消息做 `trim_messages` + `get_buffer_string(format="xml")`，调用摘要模型（带 `metadata={"lc_source": "summarization"}` 标记）；摘要模型抛异常时降级为 `"Error generating summary: ..."` 文本，不中断主流程。
5. 返回 state 更新：

```python
{"messages": [
    RemoveMessage(id=REMOVE_ALL_MESSAGES),
    HumanMessage(content="Here is a summary of the conversation to date:\n\n" + summary,
                 additional_kwargs={"lc_source": "summarization"}),
    *preserved_messages,   # cutoff 之后保留的消息
]}
```

**使用示例**：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware

agent = create_agent(
    model="anthropic:claude-sonnet-4-5",
    tools=[...],
    middleware=[
        SummarizationMiddleware(
            model="openai:gpt-4o-mini",
            trigger={"tokens": 100_000},      # 10 万 token 触发
            keep=("messages", 20),
        ),
    ],
)
```

**配合关系**：

- 与 `ContextEditingMiddleware` 互补：后者只清理工具结果且**仅作用于本次请求**（不改 state），前者真正改写消息历史。二者可叠加（先编辑清工具结果、再摘要）。
- 摘要产生的 `HumanMessage` 带 `lc_source="summarization"` 标记，DeepAgents 的 `RubricMiddleware` 等下游组件据此跳过摘要消息。
- **公开契约**：`DEFAULT_SUMMARY_PROMPT` 中的 `<messages>` 标记被 DeepAgents 依赖——deepagents 版 `SummarizationMiddleware` 用 `str.replace` 把自定义指令拼接到该标记之前，升级时不可随意改动默认模板。

### 3.2 ContextEditingMiddleware

**一句话用途**：在每次模型调用前，把历史中旧的工具执行结果替换为占位符（如 `[cleared]`），按需回收上下文空间，且不改动 state。

**源码位置**：`langchain/agents/middleware/context_editing.py`

**关键签名**：

```python
@dataclass
class ClearToolUsesEdit:
    trigger: int = 100_000          # 超过该 token 数才开始清理
    clear_at_least: int = 0         # 至少回收多少 token 才停手
    keep: int = 3                   # 最近 N 条 ToolMessage 永远保留
    clear_tool_inputs: bool = False # 是否连 AIMessage 里的 tool_call args 一起清空
    exclude_tools: tuple[str, ...] = ()
    placeholder: str = "[cleared]"

class ContextEditingMiddleware(AgentMiddleware):
    def __init__(self, *, edits: list[ClearToolUsesEdit] | None = None,
                 token_count_method: Literal["approximate", "model"] = "approximate"): ...
```

**构造参数详解**：`edits` 默认 `[ClearToolUsesEdit()]`；`token_count_method="model"` 时调用 `model.get_num_tokens_from_messages(system + msgs, tools)` 精确计数（更慢）。

**工作原理**（`wrap_model_call`）：

1. 深拷贝 `request.messages`，逐条 edit 策略应用。
2. `ClearToolUsesEdit`：先数 token，超过 `trigger` 才动手；从旧到新遍历 ToolMessage，**跳过最近 `keep` 条**、跳过已带 `response_metadata.context_editing.cleared` 标记的、跳过 `exclude_tools` 名单内工具的结果；对每条命中的消息 `model_copy(update={"content": placeholder, "artifact": None, "response_metadata": {..., "cleared": True, "strategy": "clear_tool_uses"}})`。
3. `clear_tool_inputs=True` 时，同时找到发起调用的 AIMessage，把对应 tool_call 的 `args` 清空并记录 `cleared_tool_inputs` id。
4. 回收到 ≥ `clear_at_least` 即停；最后 `handler(request.override(messages=edited))`。

**关键特性**：修改**只作用于本次模型请求**，state 里的原始消息完好无损——下轮对话仍可完整回放。这是它与 Summarization 最大的区别。

**使用示例**：

```python
from langchain.agents.middleware import ContextEditingMiddleware, ClearToolUsesEdit

agent = create_agent(model, tools, middleware=[
    ContextEditingMiddleware(edits=[
        ClearToolUsesEdit(trigger=80_000, keep=5, exclude_tools=("write_todos",)),
    ]),
])
```

**配合关系**：与 `SummarizationMiddleware` 组合时把 ContextEditing 放在**摘要触发阈值之下**（例如 80k 清工具结果、120k 才摘要），能显著推迟昂贵的摘要调用。与 `TodoListMiddleware` 组合时应把 `write_todos` 加入 `exclude_tools`，避免清掉计划状态。

### 3.3 HumanInTheLoopMiddleware

**一句话用途**：在指定工具真正执行前用 `interrupt()` 暂停图，把工具调用送人工审批（批准/编辑/拒绝/代答）。

**源码位置**：`langchain/agents/middleware/human_in_the_loop.py`

**关键签名**：

```python
DecisionType = Literal["approve", "edit", "reject", "respond"]

@dataclass
class InterruptOnConfig:
    allowed_decisions: list[DecisionType] = ["approve", "edit", "reject", "respond"]
    description: str | Callable[[ToolCall, AgentState, Runtime], str] | None = None
    args_schema: type[BaseModel] | None = None
    when: Callable[[ToolCallRequest], bool] | None = None   # 逐调用过滤谓词

@dataclass
class HITLRequest:
    action_requests: list[ActionRequest]
    review_configs: list[ReviewConfig]

class HumanInTheLoopMiddleware(AgentMiddleware):
    def __init__(self, interrupt_on: dict[str, bool | InterruptOnConfig], *,
                 description_prefix: str = "Tool execution requires approval"): ...
```

**构造参数详解**：

| 参数 | 说明 |
|---|---|
| `interrupt_on` | 工具名 → `True`（四种决策全开）或 `InterruptOnConfig`；值为 `False` 或 `allowed_decisions` 为空 = 该工具自动放行（从 resolved 配置中剔除） |
| `when` | 细粒度谓词：即使工具在名单里，逐次调用也可跳过审批（DeepAgents 的文件权限就靠它） |
| `description` | 给审批人看的说明，可以是根据 tool_call/state 动态生成的函数 |

**工作原理**（实现在 `after_model` 钩子，`aafter_model` 委托同步版）：

1. 扫描最后一条 AIMessage 的 `tool_calls`，对每个调用构造 `ToolCallRequest`（此时 `tool=None`）并跑 `when` 谓词，筛出需要审批的调用。
2. 若有命中，**一次批量** `interrupt(hitl_request)`，等待 `{"decisions": [...]}`；决策数量必须与请求数量一致，否则 `ValueError`。
3. 按决策类型处理：
   - **approve**：原样执行；
   - **edit**：用 `edited_action{name, args}` 替换该 tool_call（保留原 id）；
   - **reject**：不执行，注入 `ToolMessage(status="error")`，默认文案告知模型"用户拒绝，除非用户明确要求否则不要重试"；
   - **respond**：不执行，注入 `ToolMessage(status="success")`，内容是人工代答文本。
4. 按原始顺序重建 `last_ai_msg.tool_calls`，返回 `{"messages": [last_ai_msg, *artificial_tool_messages]}`。

**使用示例**：

```python
from langchain.agents.middleware import HumanInTheLoopMiddleware, InterruptOnConfig

agent = create_agent(model, tools=[delete_record, send_email, search], middleware=[
    HumanInTheLoopMiddleware(interrupt_on={
        "delete_record": True,                     # 全决策审批
        "send_email": InterruptOnConfig(
            allowed_decisions=["approve", "edit"],  # 只许批准或改参
            when=lambda req: "@" not in req.tool_call["args"].get("to", ""),
        ),
        "search": False,                            # 明确放行
    }),
])
# 恢复执行：Command(resume={"decisions": [{"type": "approve"}]})
```

**配合关系**：

- 依赖 langgraph 的 `interrupt()`，因此**必须配 checkpointer** 使用；恢复时用 `Command(resume=...)`。
- `interrupt()` 抛出的 `GraphBubbleUp` 控制流异常，要求外层的 `ToolRetryMiddleware` / `ToolErrorMiddleware` 放行（它们已内置处理）。
- DeepAgents `_fs_interrupt.py` 会从 `FilesystemPermission(mode="interrupt")` 规则自动生成 `interrupt_on` 配置——这是两个库之间最重要的桥接点。
- 与 `TodoListMiddleware` 同在 `after_model` 阶段操作"最后一条 AIMessage 的 tool_calls"，注意二者顺序：HITL 应放前面（更靠近模型），避免对已被改写的调用做审批。

### 3.4 ModelCallLimitMiddleware

**一句话用途**：限制每个线程（thread）或每次运行（run）的模型调用次数，超限后结束对话或抛错。

**源码位置**：`langchain/agents/middleware/model_call_limit.py`

**关键签名**：

```python
class ModelCallLimitState(AgentState):
    thread_model_call_count: Annotated[int, Private]           # 持久化计数
    run_model_call_count: Annotated[int, UntrackedValue, Private]  # 每次 run 重置

class ModelCallLimitMiddleware(AgentMiddleware[ModelCallLimitState]):
    def __init__(self, *, thread_limit: int | None = None,
                 run_limit: int | None = None,
                 exit_behavior: Literal["end", "error"] = "end"): ...
```

**构造参数详解**：`thread_limit` 与 `run_limit` 至少给一个（跨会话累计 vs 单次运行）；`exit_behavior="error"` 抛 `ModelCallLimitExceededError`，`"end"` 则优雅收尾。

**工作原理**：

- `before_model`（带 `@hook_config(can_jump_to=["end"])`）：计数 ≥ 限额时，`"error"` 直接抛异常；`"end"` 返回 `{"jump_to": "end", "messages": [AIMessage("Model call limits exceeded: thread limit (n/m), run limit (n/m)")]}`。
- `after_model`：两个计数各 +1。
- 注意 `run_model_call_count` 用 `UntrackedValue` 通道，**不落 checkpoint**，每次新 run 从 0 开始；`thread_model_call_count` 持久化在线程 state 里。

**使用示例**：

```python
agent = create_agent(model, tools, middleware=[
    ModelCallLimitMiddleware(thread_limit=50, run_limit=10, exit_behavior="end"),
])
```

**配合关系**：这是防"死循环烧钱"的第一道闸。与 `ToolCallLimitMiddleware` 一个管模型一个管工具，常成对出现；`exit_behavior="end"` 会注入一条收尾 AIMessage，前端可正常渲染。

### 3.5 ToolCallLimitMiddleware

**一句话用途**：按工具名（或全局）限制工具调用次数，超限后可继续（注入错误 ToolMessage 劝退模型）、结束或抛错。

**源码位置**：`langchain/agents/middleware/tool_call_limit.py`

**关键签名**：

```python
class ToolCallLimitState(AgentState):
    thread_tool_call_count: Annotated[dict[str, int], Private]
    run_tool_call_count: Annotated[dict[str, int], UntrackedValue, Private]

class ToolCallLimitMiddleware(AgentMiddleware[ToolCallLimitState]):
    def __init__(self, *, tool_name: str | None = None,     # None = 统计所有工具（键 "__all__"）
                 thread_limit: int | None = None,
                 run_limit: int | None = None,
                 exit_behavior: Literal["continue", "error", "end"] = "continue"): ...
    @property
    def name(self): return f"ToolCallLimitMiddleware[{self.tool_name}]"
```

**构造参数详解**：校验 `run_limit ≤ thread_limit`；`name` 属性带工具名后缀，因此**同一工具链可以放多个实例分别限制不同工具**。

**工作原理**（`after_model`，`can_jump_to=["end"]`）：

1. `_separate_tool_calls` 遍历最后一条 AIMessage 的 tool_calls，逐个累加假设计数，`count + 1 > limit` 的调用被标记 blocked。
2. 三种行为：
   - `"continue"`：只给 blocked 的调用注入错误 ToolMessage（`"Tool call limit exceeded. Do not call 'X' again."` 或全局版 `"...Do not make additional tool calls."`），**模型继续运行**，有机会自己收尾；
   - `"error"`：抛 `ToolCallLimitExceededError`（含推算的 thread 计数）；
   - `"end"`：注入 ToolMessage + 一条说明细节的最终 AIMessage + `jump_to: "end"`；若同批还有别的未处理工具调用则 `NotImplementedError`。
3. 计数口径：thread 只记 allowed，run 记 allowed + blocked。

**使用示例**：

```python
agent = create_agent(model, tools, middleware=[
    ToolCallLimitMiddleware(tool_name="expensive_search", thread_limit=5, exit_behavior="continue"),
    ToolCallLimitMiddleware(thread_limit=100, run_limit=30, exit_behavior="end"),
])
```

**配合关系**：与 `ModelCallLimitMiddleware` 互补。`"continue"` 模式的劝退文案会进消息历史，模型看得到，因此对"重复问同一题不重跑工具"这类行为友好；而 `"end"` 模式的收尾 AIMessage 是终态。

### 3.6 ModelFallbackMiddleware

**一句话用途**：主模型调用抛异常时，按顺序切换到备用模型重试，并自动清理跨提供商不兼容的 Anthropic 缓存标记。

**源码位置**：`langchain/agents/middleware/model_fallback.py`

**关键签名**：

```python
class ModelFallbackMiddleware(AgentMiddleware):
    def __init__(self, first_model: str | BaseChatModel,
                 *additional_models: str | BaseChatModel): ...
```

**构造参数详解**：至少两个模型；字符串在构造时就 `init_chat_model` 解析（**导入期解析**，配置错误立即暴露）。

**工作原理**（`wrap_model_call`）：

1. 先 `handler(request)` 用主模型。
2. 捕获任意 `Exception` 后遍历 fallback 模型：
   - **缓存标记清理**：仅当目标模型 `_llm_type` 不在 `{anthropic-chat, anthropic-bedrock-chat, anthropic-chat-vertexai}` 时，递归剥离 `model_settings`、`system_message` content blocks（含嵌套 extras/metadata）、`messages`、`tools`（含 `BaseTool.extras`）里的 `cache_control` 字段——因为 Anthropic 专有的 prompt caching 标记发给 OpenAI 等会报错。
   - `handler(request.override(model=fallback))`。
3. 全部失败则 re-raise 最后一个异常。清理逻辑刻意放在 try 之外，其自身 bug 能直接暴露。

**使用示例**：

```python
agent = create_agent(
    model="anthropic:claude-sonnet-4-5",
    tools=tools,
    middleware=[ModelFallbackMiddleware(
        "anthropic:claude-sonnet-4-5",
        "openai:gpt-4o",
        "openai:gpt-4o-mini",
    )],
)
```

**配合关系**：

- 与 `ModelRetryMiddleware` 组合时，**fallback 放外层**（列表更靠前）：先对每个模型做 N 次重试，都失败再换下一个模型；反过来的顺序会导致"换模型"发生在每次重试内部，语义混乱。
- 缓存标记清理与 Anthropic prompt-caching 中间件相互作用：若你的自定义中间件在更内层注入 `cache_control`，fallback 到非 Anthropic 模型时会被自动剥掉，无需手动处理。

### 3.7 ModelRetryMiddleware

**一句话用途**：模型调用失败时按指数退避自动重试，重试耗尽后可继续（注入失败 AIMessage）或抛错。

**源码位置**：`langchain/agents/middleware/model_retry.py`（重试数学在 `_retry.py`）

**关键签名**：

```python
class ModelRetryMiddleware(AgentMiddleware):
    def __init__(self, *,
                 max_retries: int = 2,
                 retry_on: tuple[type[Exception], ...] | Callable[[Exception], bool] = (Exception,),
                 on_failure: Literal["error", "continue"] | Callable[[Exception], str] = "continue",
                 backoff_factor: float = 2.0,
                 initial_delay: float = 1.0,
                 max_delay: float = 60.0,
                 jitter: bool = True): ...
```

**构造参数详解**：

| 参数 | 说明 |
|---|---|
| `retry_on` | 异常类型元组（isinstance 判定）或谓词函数；`GraphBubbleUp` 永远放行不重试 |
| `on_failure` | `"error"` 重新抛出；`"continue"` 注入 `AIMessage("Model call failed after N attempt(s) with ExcType: msg")` 包成 `ModelResponse` 让流程继续；也可传可调用对象，其返回字符串作为 AIMessage 内容 |
| 退避参数 | 延迟 = `initial_delay * backoff_factor ** retry_number`，封顶 `max_delay`，`jitter=True` 时加 ±25% 抖动；`backoff_factor=0` 即恒定延迟。同步路径 `time.sleep`，异步 `asyncio.sleep` |

**工作原理**（`wrap_model_call`）：`for attempt in range(max_retries + 1)` 循环调 `handler(request)`；**不可重试的异常立即走 `_handle_failure`（不重抛原始异常，这点与 ToolRetryMiddleware 不同）**；可重试且还有余量则 sleep 后重试；耗尽后同样走 `_handle_failure`。

**使用示例**：

```python
from langchain_core.exceptions import APITimeoutError, APIConnectionError

agent = create_agent(model, tools, middleware=[
    ModelRetryMiddleware(
        max_retries=3,
        retry_on=(APITimeoutError, APIConnectionError),
        on_failure="error",
        initial_delay=0.5, backoff_factor=2, max_delay=10,
    ),
])
```

**配合关系**：本项目 nl2sql 后端的 `ModelTimeoutMiddleware`（自研，位于 P2-11 治理项）就是仿照此模式实现的超时+并发闸；实践中 `retry_on` 应**先判超时再判连接错误**，避免把余额耗尽（402）这类不可恢复错误也重试。与 `ModelFallbackMiddleware` 的内外层关系见上节。

### 3.8 ToolRetryMiddleware

**一句话用途**：工具执行抛异常时按指数退避重试，耗尽后注入错误 ToolMessage 或抛错。

**源码位置**：`langchain/agents/middleware/tool_retry.py`

**关键签名**：

```python
class ToolRetryMiddleware(AgentMiddleware):
    def __init__(self, *,
                 max_retries: int = 2,
                 tools: list[str | BaseTool] | None = None,   # None = 所有工具
                 retry_on: tuple[type[Exception], ...] | Callable = (Exception,),
                 on_failure: Literal["error", "continue"] | Callable = "continue",
                 backoff_factor: float = 2.0,
                 initial_delay: float = 1.0,
                 max_delay: float = 60.0,
                 jitter: bool = True): ...
```

**构造参数详解**：`on_failure` 旧值 `"raise"` → `"error"`、`"return_message"` → `"continue"`（触发 `DeprecationWarning`）。`tools` 过滤不命中时直接透传 `handler(request)`。

**工作原理**（`wrap_tool_call`）：与 ModelRetry 相同的循环，但有两处关键差异：

1. `GraphBubbleUp` 无条件 re-raise（保住 HITL 中断）；
2. **不可重试的异常立即原样重抛**（而不是走 on_failure）——这样外层的 `ToolErrorMiddleware` 才能接住它做统一转换。

耗尽后 `_handle_failure`：`"error"` 抛最后异常；callable 返回内容；`"continue"` 注入 `ToolMessage(status="error", content="Tool 'X' failed after N attempt(s) with ExcType: msg. Please try again.")`——文案带 "Please try again"，鼓励模型换参数重试。

**使用示例**：

```python
agent = create_agent(model, tools, middleware=[
    ToolRetryMiddleware(max_retries=3, tools=["web_search"],
                        retry_on=(TimeoutError,), on_failure="continue"),
])
```

**配合关系**：官方文档推荐的组合是 **ToolRetry 在内层（列表靠后）、ToolError 在外层**，且 ToolRetry 设 `on_failure="error"`——重试耗尽后异常继续向外冒，由 ToolError 统一转成对模型友好的错误消息。

### 3.9 ToolErrorMiddleware

**一句话用途**：把工具执行抛出的任意异常转换成自定义的错误 ToolMessage，让模型有机会自我纠正而不是整个 run 崩掉。

**源码位置**：`langchain/agents/middleware/tool_error.py`

**关键签名**：

```python
class ToolErrorMiddleware(AgentMiddleware):
    def __init__(self,
                 on_error: Callable[[Exception, ToolCallRequest], str | list | None] | None = None,
                 *,
                 aon_error: Callable[..., Awaitable[...]] | None = None,
                 tools: list[str | BaseTool] | None = None): ...
```

**构造参数详解**：`on_error` 与 `aon_error` 至少提供一个；`tools` 按名字过滤。回调返回值语义：返回 `str` 或 content blocks → 转成 `ToolMessage(status="error")`；返回 `None` → `raise`（原样传播）。只配了 `aon_error` 却走同步路径时抛 `RuntimeError`。

**工作原理**（`wrap_tool_call`）：`GraphBubbleUp` 永远先放行；其余异常交给 `on_error(exc, request)`。**它只能看到工具执行期异常**——参数绑定/校验错误在上游 ToolNode 已被处理，不会到这里。

**使用示例**：

```python
def handle(exc: Exception, request) -> str | None:
    if isinstance(exc, PermissionError):
        return "权限不足：该操作需要管理员身份。"   # 点名异常类型，不回显原始敏感信息
    return None                                    # 其他异常照常抛出

agent = create_agent(model, tools, middleware=[
    ToolErrorMiddleware(handle),
    ToolRetryMiddleware(max_retries=2, on_failure="error"),  # 内层
])
```

**配合关系**：docstring 明确指出与 `ToolRetryMiddleware` 的标准搭配——**retry 放内层且 `on_failure="error"`**，异常穿透到外层由本中间件转换。编写 `on_error` 时应**优先按异常类型分支而不是回显异常消息**，避免把连接串、密钥等敏感细节泄漏进模型上下文。

### 3.10 PIIMiddleware

**一句话用途**：对输入消息、工具结果、模型输出中的敏感信息（邮箱/信用卡/IP/MAC/URL 或自定义正则）执行 block/redact/mask/hash 四种脱敏策略，且支持流式输出线路级脱敏。

**源码位置**：`langchain/agents/middleware/pii.py`（检测与规则引擎在 `_redaction.py`）

**关键签名**：

```python
class PIIMiddleware(AgentMiddleware):
    def __init__(self, pii_type: str, *,
                 strategy: Literal["block", "redact", "mask", "hash"] = "redact",
                 detector: str | Callable | None = None,   # 正则串或函数；None = 内置检测器
                 apply_to_input: bool = True,
                 apply_to_output: bool = False,
                 apply_to_tool_results: bool = False): ...
    @property
    def name(self): return f"PIIMiddleware[{self.pii_type}]"
```

**构造参数详解**：

| 参数 | 说明 |
|---|---|
| `pii_type` | 内置类型：`email`、`credit_card`（Luhn 校验，13–19 位）、`ip`、`mac_address`、`url`；也可以是自定义类型名（此时必须给 `detector`） |
| `strategy` | `redact` → `[REDACTED_EMAIL]`；`mask` → 保形掩码（邮箱 `user@****.tld`、卡号 `****-****-****-1234` 保留分隔符、IP `*.*.*.last`、MAC `**:**:**:**:**:xx`、URL `[MASKED_URL]`、通用 `****last4`）；`hash` → `<{type}_hash:{sha256前8位}>`（可关联同一实体）；`block` → 抛 `PIIDetectionError(pii_type, matches)` 直接阻断 |
| `detector` | `None` 用内置；字符串编译为正则；可调用对象接受 `"text"` 键别名并归一化为 `PIIMatch` 列表 |
| 三个 apply_to | 分别控制：用户输入（最后一条 HumanMessage）、模型输出（最后一条 AIMessage 的 content，**tool_calls 保留**）、工具结果（最后一条 AIMessage 之后的所有 ToolMessage） |

**工作原理**：

- `before_model`：按开关重建消息列表——脱敏最后一条 HumanMessage 与其后的 ToolMessage。
- `after_model`：脱敏最后一条 AIMessage 的文本内容。
- **流式线路级脱敏**：只要开了输出侧，`transformers` 会注册一个 `_PIIStreamTransformer`（`before_builtins=True`，订阅 `("messages", "tools", "values")` 三个流模式）。它维护 128 字符回看缓冲（按 `(run_id, block_index)` 键控），对 text-delta / reasoning-delta 做"扣留-回看"式检测，防止敏感串被逐 token 切碎后漏检；tool_call_chunk 的累积 args 同样处理；tools 通道覆盖 tool-started 输入、tool-output-delta、tool-finished 输出、tool-error 消息；values 通道对 state 快照的副本脱敏；`block` 策略在流中直接抛 `PIIDetectionError`；缓冲在 content-block-finish / message-finish / error / finalize 时清理。

**使用示例**：

```python
agent = create_agent(model, tools, middleware=[
    PIIMiddleware("email", strategy="mask", apply_to_input=True),
    PIIMiddleware("credit_card", strategy="block"),
    PIIMiddleware("employee_id", detector=r"EMP\d{6}", strategy="hash",
                  apply_to_input=True, apply_to_tool_results=True),
])
```

**配合关系**：`name` 带类型后缀 ⇒ **多个实例可共存**，各管一种 PII。与 `ShellToolMiddleware` 的 `redaction_rules` 是两套独立机制（后者作用于 shell 输出）。`block` 策略抛出的 `PIIDetectionError` 会被外层 `ToolErrorMiddleware` / 重试中间件当作普通异常处理，设计时注意别让重试把 block 又跑一遍。

### 3.11 TodoListMiddleware

**一句话用途**：给 Agent 注册 `write_todos` 工具并在系统提示词中注入规划纪律，让模型对多步任务显式维护一张任务清单。

**源码位置**：`langchain/agents/middleware/todo.py`

**关键签名**：

```python
class Todo(BaseModel):
    content: str
    status: Literal["pending", "in_progress", "completed"]

class PlanningState(AgentState):
    todos: Annotated[list[Todo], OmitFromInput]

class TodoListMiddleware(AgentMiddleware[PlanningState]):
    def __init__(self, *, system_prompt: str = WRITE_TODOS_SYSTEM_PROMPT,
                 tool_description: str = WRITE_TODOS_TOOL_DESCRIPTION): ...
```

**工作原理**：

- 注册工具：`write_todos = StructuredTool.from_function(func=_write_todos, coroutine=_awrite_todos, args_schema=WriteTodosInput, infer_schema=False)`；实现返回 `Command(update={"todos": todos, "messages": [ToolMessage(f"Updated todo list to {todos}", tool_call_id=runtime.tool_call_id)]})`——**直接写 state 的 todos 通道**。
- `wrap_model_call`：把 `system_prompt` 作为新的 text content block **追加**到系统消息（不覆盖）。
- `after_model`：检测到同一条 AIMessage 里**并行调用多个 write_todos** 时，为每个调用注入错误 ToolMessage（"should never be called multiple times in parallel"）。
- 提示词纪律：≥3 步的任务必须用；开工立即标 `in_progress`；完成前始终至少一条 `in_progress`；被阻塞时不许标 `completed`；**最终回答必须是最后一次 write_todos 之后的独立消息**。

**使用示例**：

```python
agent = create_agent(model, tools, middleware=[TodoListMiddleware()])
# 前端可从 state["todos"] 渲染进度条
```

**配合关系**：

- 与 `ContextEditingMiddleware` 组合时把 `write_todos` 加入 `exclude_tools`（清单更新消息不该被清掉）。
- 本项目 nl2sql 的实践（见 MEMORY「每个 skill 边界都 write_todos」）：配合自研 `ProgressBoundaryMiddleware` 强制子任务边界写 todos；子 agent 不可靠时的根因是提示词注入被中间件顺序盖掉——**TodoList 的 wrap_model_call 位置决定提示词注入次序**。
- `state_schema = PlanningState` 自动并入 Agent State，其他中间件与前端都能读 `todos`。

### 3.12 ShellToolMiddleware

**一句话用途**：为 Agent 提供一个带持久会话的 `shell` 工具（bash 进程常驻、支持 startup/shutdown 命令、资源限制、超时重启、输出截断与脱敏）。

**源码位置**：`langchain/agents/middleware/shell_tool.py`（进程管理策略在 `_execution.py`）

**关键签名**：

```python
class ShellToolState(AgentState):
    shell_session_resources: Annotated[Any, UntrackedValue, Private]  # weakref.finalize 兜底清理

class ShellToolMiddleware(AgentMiddleware[ShellToolState]):
    def __init__(self, workspace_root: str | Path | None = None, *,
                 startup_commands: list[str] | None = None,
                 shutdown_commands: list[str] | None = None,
                 execution_policy: BaseExecutionPolicy | None = None,  # 默认 HostExecutionPolicy()
                 redaction_rules: list[RedactionRule] | None = None,
                 tool_description: str | None = None,
                 tool_name: str = "shell",
                 shell_command: tuple[str, ...] | None = None,        # 默认 ("/bin/bash",)
                 env: dict[str, str] | None = None): ...
```

**工作原理**：

1. `before_agent`：创建资源（无 `workspace_root` 时用前缀 `langchain-shell-` 的临时目录；有则 `mkdir -p`），通过 policy `spawn()` 启动 `ShellSession`（Popen 三管道 + 守护读线程 → queue），依次执行 `startup_commands`——**任一失败/超时即 RuntimeError 并清理**。
2. 工具入参 `_ShellToolInput{command XOR restart}`（model_validator 强制二选一）。
3. 执行：向 stdin 写命令 + `printf '__LC_SHELL_DONE__{uuid} %s\n' $?` 哨兵标记，从 queue 收集输出直到标记或超时；按 `max_output_lines` / `max_output_bytes` 截断并打 flag。
4. 超时 → **重启会话**，返回 `ToolMessage(status="error", content="Command timed out after X seconds", artifact={"timed_out": True, ...})`。
5. 输出脱敏：命中 `redaction_rules` 且策略为 block 时返回 `"Output blocked: detected {type}"` + matches artifact。
6. 非零退出码 → 追加 `"Exit code: N"`、`status="error"`；artifact 携带 total_lines/bytes、截断标志、脱敏命中。
7. `after_agent`：best-effort 执行 `shutdown_commands`（失败仅警告）+ 触发 finalizer。会话资源存 state（`UntrackedValue`），支持从 state 恢复（`_get_or_create_resources`）。

**使用示例**：

```python
from langchain.agents.middleware import ShellToolMiddleware, DockerExecutionPolicy

agent = create_agent(model, middleware=[
    ShellToolMiddleware(
        workspace_root="/data/project",
        startup_commands=["source .venv/bin/activate"],
        execution_policy=DockerExecutionPolicy(image="python:3.12-alpine3.19",
                                               network_enabled=False, memory_bytes=512*1024*1024),
    ),
])
```

**配合关系**：三种执行策略（详见 [4.4](#44-_executionpy)）决定隔离级别；`redaction_rules` 与 `PIIMiddleware` 共用 `_redaction.py` 引擎但作用面不同（shell 输出 vs 消息流）。工具名默认 `shell`，可用 `tool_name` 改名避免与其他工具冲突。

### 3.13 FilesystemFileSearchMiddleware

**一句话用途**：注册只读的 `glob_search` / `grep_search` 两个文件搜索工具，把搜索范围钉死在指定根目录内。

**源码位置**：`langchain/agents/middleware/file_search.py`

**关键签名**：

```python
class FilesystemFileSearchMiddleware(AgentMiddleware):
    def __init__(self, *, root_path: str | Path, use_ripgrep: bool = True,
                 max_file_size_mb: int = 10): ...
```

**工作原理**：

- `glob_search(pattern, path="/")`：pathlib glob；拒绝绝对路径与含 `..` 的 pattern；每个命中结果做 `_is_within_root`（resolve 后前缀校验）双保险；按 mtime 排序返回虚拟路径，无命中返回 `"No files found"`。
- `grep_search(pattern, path="/", include=None, output_mode="files_with_matches"|"content"|"count")`：正则先验证；`use_ripgrep=True` 时走 `rg --json --glob include -- pattern base`（30s 超时 + 结果逐条 root 校验，纵深防御）；否则 Python fallback：`os.walk(followlinks=False)`，跳过 >`max_file_size_mb` 与无法解码的文件；`content` 模式输出 `file:line:text`。
- `_validate_and_resolve_path` 统一拒绝 `..` / `~` 并强制根目录内。

**使用示例**：

```python
agent = create_agent(model, middleware=[
    FilesystemFileSearchMiddleware(root_path="/srv/docs", max_file_size_mb=5),
])
```

**配合关系**：与 DeepAgents `FilesystemMiddleware` 的区别——后者是**虚拟文件系统**（可读写、可换 backend、带权限），本中间件是**纯只读物理目录搜索**，轻量且无 state 侵入，适合"让 agent 查资料"场景。

### 3.14 LLMToolSelectorMiddleware

**一句话用途**：在每次模型调用前，用一个小模型从全量工具中挑出与当前用户问题最相关的子集，缓解工具过多导致的选错/上下文膨胀。

**源码位置**：`langchain/agents/middleware/tool_selection.py`

**关键签名**：

```python
class LLMToolSelectorMiddleware(AgentMiddleware):
    def __init__(self, *,
                 model: BaseChatModel | None = None,     # 默认复用 Agent 主模型
                 system_prompt: str = "Your goal is to select the most relevant tools for answering the user's query.",
                 max_tools: int | None = None,
                 always_include: list[str] | None = None): ...
```

**工作原理**（`wrap_model_call`）：

1. 无工具或无可选工具时直接透传；`always_include` 里的名字必须存在，否则 `ValueError`；消息里没有 HumanMessage 则 `AssertionError`。
2. **动态构造结构化输出 schema**：`ToolSelectionResponse{tools: list[Union[Annotated[Literal[name], Field(description=desc)], ...]]}`——每个候选工具变成一个带描述的字面量选项。
3. `model.with_structured_output(schema).invoke([system, 最后一条用户消息])`；选了不存在的工具 → `ValueError`。
4. `max_tools` 按相关度顺序截断；`always_include` 追加（不占额度）；provider 原生 dict 工具原样保留。
5. `handler(request.override(tools=[*selected, *always, *provider_dicts]))`。

**使用示例**：

```python
agent = create_agent(model, tools=fifty_tools, middleware=[
    LLMToolSelectorMiddleware(model="openai:gpt-4o-mini", max_tools=8,
                              always_include=["write_todos"]),
])
```

**配合关系**：

- 与 `ProviderToolSearchMiddleware` 是**同一问题的两种解法**：本中间件用自家 LLM 客户端筛选（provider 无关），后者用提供商服务端原生 tool search（见下节）。二者不要同时启用。
- 每次模型调用都会先打一次筛选模型 ⇒ 增加延迟与成本；`max_tools` 与 `always_include` 是控制这两项的旋钮。
- 筛选发生在 wrap_model_call 层，因此**只影响模型看到的工具面**，tools 节点仍能执行历史消息里引用过的工具。

### 3.15 ProviderToolSearchMiddleware

**一句话用途**：利用 Anthropic / OpenAI 服务端的原生"工具搜索"能力，把大工具集标记为 defer_loading，由提供商在服务端按需检索，本地不预筛。

**源码位置**：`langchain/agents/middleware/provider_tool_search.py`

**关键签名**：

```python
class ProviderToolSearchMiddleware(AgentMiddleware):
    def __init__(self, *, searchable_tools: list[str | BaseTool] | None = None):  # None = 全部
```

**工作原理**（`wrap_model_call` → `_prepare_request`）：

1. `searchable_tools` 里的名字必须已绑定，否则 `ValueError`；没有可 defer 的工具则透传。
2. 推断 provider：依次查 `_model_params(config)`、`_default_config`、`_get_ls_params().ls_provider`、类名（`ChatAnthropic` / `ChatOpenAI`）；不支持或无法识别且确有 deferred 工具 → `ValueError`。
3. deferred 判定：名字命中，或工具 `extras["defer_loading"] is True`。
4. `request.override(tools=[*deferred标记后的工具, provider_search_spec])`——server tool spec：Anthropic 为 `tool_search_tool_bm25_20251119`，OpenAI 为 `tool_search`。

**使用示例**：

```python
agent = create_agent("anthropic:claude-sonnet-4-5", tools=big_toolset, middleware=[
    ProviderToolSearchMiddleware(),   # 全部工具交给服务端 BM25 检索
])
```

**配合关系**：只支持 Anthropic / OpenAI；`defer_loading` extras 标记允许与手动指定混用。与 `LLMToolSelectorMiddleware` 二选一。

### 3.16 LLMToolEmulator

**一句话用途**：用 LLM 模拟指定工具的执行结果（真工具完全不被调用），用于测试、演示或在工具不可用时兜底。

**源码位置**：`langchain/agents/middleware/tool_emulator.py`

**关键签名**：

```python
class LLMToolEmulator(AgentMiddleware):
    def __init__(self, *,
                 tools: list[str | BaseTool] | None = None,   # None = 模拟所有工具
                 model: BaseChatModel | None = None):          # 默认 init_chat_model("anthropic:claude-sonnet-4-5-20250929", temperature=1)
```

**工作原理**（`wrap_tool_call`）：不在名单内的工具直接 `handler(request)`；命中的则构造提示词（工具名/描述/args，要求"Generate a realistic response... Return ONLY the tool's output... Introduce variation"），`model.invoke([HumanMessage(prompt)])`，把结果包成 ToolMessage **短路返回——真工具永不执行**。异步路径用 `ainvoke`。

**使用示例**：

```python
# 集成测试：模拟掉有副作用的写库工具
agent = create_agent(model, tools=[query_db, write_db], middleware=[
    LLMToolEmulator(tools=["write_db"]),
])
```

**配合关系**：短路意味着外层的 `ToolRetryMiddleware` / `ToolErrorMiddleware` 只能看到模拟器自身的异常；模拟器返回的 ToolMessage 不带真实 `status`/artifact，评估链路（如本项目 Langfuse judge）应注意区分模拟与真实执行。

## 四、LangChain 中间件基础设施

### 4.1 types.py

除 [1.1–1.5](#一中间件机制基础) 已述内容外，值得记住的实现细节：

- 装饰器合成类的真身：`type(name, (AgentMiddleware,), {"state_schema": ..., "tools": ..., "before_model": wrapped})()`——所以装饰器产物与手写类在 Pipeline 中完全等价。

### 4.4 _execution.py

`ShellToolMiddleware` 的进程执行策略族：

```python
class BaseExecutionPolicy(ABC):
    def __init__(self, *, command_timeout=30.0, startup_timeout=30.0,
                 termination_timeout=10.0, max_output_lines=100, max_output_bytes=None): ...
    @abstractmethod
    def spawn(self, *, workspace, env, command) -> Popen[str]: ...

class HostExecutionPolicy(BaseExecutionPolicy):
    # cpu_time_seconds / memory_bytes：Linux 用 prlimit（spawn 后设置），macOS 用 preexec_fn；
    # 需要 POSIX resource 模块；create_process_group=True 便于整组清理
class CodexSandboxExecutionPolicy(BaseExecutionPolicy):
    # binary="codex", platform="auto", config_overrides={}
    # 组装 `codex sandbox <platform> [-c k=json]... -- cmd`（Seatbelt/Landlock 沙箱）
class DockerExecutionPolicy(BaseExecutionPolicy):
    # binary="docker", image="python:3.12-alpine3.19", remove_container_on_exit=True,
    # network_enabled=False（默认 --network none）, memory_bytes, cpus, read_only_rootfs, user
    # cpu_time_seconds 参数会 RuntimeError（请用 cpus）；
    # workspace 仅在非临时目录（前缀 langchain-shell-）时 bind-mount（-v path:path -w path）
```

选择建议：本机受信脚本 → Host；需要真沙箱且装了 codex → CodexSandbox；生产/不受信代码 → Docker（默认断网）。

## 五、DeepAgents 中间件详解

`deepagents/middleware/__init__.py` 的模块文档说明了 DeepAgents 为什么把能力做成**中间件**而非普通工具：中间件能通过 `wrap_model_call` 拦截每次模型调用，实现**动态工具过滤、系统提示词注入、消息变换、跨轮状态维护**——这些是纯工具做不到的。`create_deep_agent()` 会把内部中间件与用户传入的 tools/middleware 合并装配。

导出面：`AsyncSubAgentMiddleware` / `SubAgentMiddleware`（子智能体）、`FilesystemMiddleware` + `FilesystemPermission`、`MemoryMiddleware`、`SkillsMiddleware`、deepagents 版 `SummarizationMiddleware` / `SummarizationToolMiddleware` / `create_summarization_tool_middleware` + `DEEPAGENTS_DEFAULT_SUMMARY_PROMPT`、`RubricMiddleware` 及配套类型。本文重点讲解任务指定的 filesystem / permissions / patch_tool_calls / rubric / _tool_exclusion / _fs_interrupt / _utils 七个模块。

### 5.1 FilesystemMiddleware

**一句话用途**：给 Agent 装一套虚拟文件系统工具（`ls` / `read_file` / `write_file` / `edit_file` / `glob` / `grep`，backend 支持时加 `execute`），并自动把超大工具结果/超大用户消息"驱逐"到文件系统，防止上下文爆炸。

**源码位置**：`deepagents/middleware/filesystem.py`

**关键签名**：

```python
class FilesystemState(AgentState):
    files: Annotated[NotRequired[dict[str, FileData]],
                     DeltaChannel(_file_data_delta_reducer, snapshot_frequency=50)]

class FilesystemMiddleware(AgentMiddleware[FilesystemState, ContextT, ResponseT]):
    def __init__(self, *,
                 backend: BACKEND_TYPES | None = None,            # 默认 StateBackend()
                 system_prompt: str | None = None,
                 custom_tool_descriptions: Mapping[str, str] | None = None,
                 tool_token_limit_before_evict: int | None = 20000,
                 human_message_token_limit_before_evict: int | None = 50000,
                 max_execute_timeout: int = 3600,
                 _permissions: list[FilesystemPermission] | None = None): ...
```

**构造参数详解**：

| 参数 | 说明 |
|---|---|
| `backend` | 文件存储后端：`StateBackend`（默认，存在图 state 里，随 checkpoint 持久化）、`FilesystemBackend`（真实磁盘）、`StoreBackend`（langgraph Store）、`CompositeBackend`（路由混合，如 `{"/memories/": StoreBackend()}`）、或实现 `SandboxBackendProtocol` 的沙箱（此时才有 `execute` 工具）。传 callable 工厂已弃用（0.7.0 移除） |
| `tool_token_limit_before_evict` | 工具结果超过该 token 数（按 4 字符/token 估算）即写入 `{artifacts_root}/large_tool_results/<tool_call_id>` 并替换为"头尾预览 + 文件引用"；`ls/glob/grep/read_file/edit_file/write_file` 六个工具**豁免**（自带截断或不可能超限） |
| `human_message_token_limit_before_evict` | 最后一条 HumanMessage 超限（默认 50k token）→ 内容写入 `{artifacts_root}/conversation_history/<uuid>.md`，消息打上 `additional_kwargs["lc_evicted_to"]` 标记，模型看到的是截断预览；state 里的原文通过标记仍完整 |
| `max_execute_timeout` | execute 工具单命令超时上限（默认 3600s），超出即拒绝 |
| `_permissions` | 文件权限规则（见 5.2）；**与可执行 backend 不兼容**——除非所有规则路径都限定在 CompositeBackend 的路由前缀内，否则 `NotImplementedError` |

**工作原理**：

1. **工具注册**：七个工具全部 `StructuredTool.from_function(func=同步, coroutine=异步, infer_schema=False, args_schema=Pydantic模型)`，同步/异步路径成对实现。`read_file` 支持 `offset/limit` 分页、超 5000 字符长行折行（`5.1`、`5.2` 续行标记）、空文件统一警告、图片/音视频/PDF 按 backend 声明的 `encoding=="base64"` 或扩展名返回**多模态 content blocks**（带 mime_type）。`glob` 有 20s 超时（`GLOB_TIMEOUT`）：同步路径用共享 `ThreadPoolExecutor(4)` + `BoundedSemaphore`（满载直接拒绝而非排队），异步路径用 `asyncio.wait` 超时后 cancel；等待超时与 backend 内部抛的 `TimeoutError` 严格区分。`execute` 运行时检查 `supports_execution(backend)`，不支持则优雅报错。
2. **wrap_model_call**：① 若 `execute` 在工具面但 backend 不支持 → 从 `request.tools` 过滤掉；② 动态系统提示词（带缓存，按 `include_execution` 键控最多算两次）：文件工具说明 + 大结果驱逐说明 + （可选）execute 说明 + （可选）CompositeBackend 的**虚拟路径 ↔ 宿主 shell 路径映射表**（`_route_host_path_prompt`：只有 default 是 `LocalShellBackend` 时本地路由才有宿主映射；virtual 模式映射到 backend 的 cwd，非 virtual 剥前缀映射到 `/`；store 路由无映射，只能用文件工具访问）；用 `append_to_system_message` 追加；③ **大 HumanMessage 驱逐**：已带 `lc_evicted_to` 标记的消息替换为截断预览（仅本次请求），新命中的写盘并返回 `ExtendedModelResponse(command=Command(update={"messages": [tagged]}))` 把标记写回 state——**刻意不用 `REMOVE_ALL_MESSAGES` 哨兵**，靠消息 id 让 DeltaChannel reducer 原位去重，避免同超步内模型节点写入的 AIMessage 被误清。
3. **wrap_tool_call**：工具执行后检查结果大小，超限的 ToolMessage（含 Command 包裹的多消息，注意保留 `REMOVE_ALL_MESSAGES` 哨兵）驱逐到 `/large_tool_results/<tool_call_id>`。**工具执行异常刻意不拦截**，原样穿透给外层重试/错误中间件。
4. **state 设计**：`files` 用 `DeltaChannel`（每 ~50 个 pregel step 打一次快照）限制读深度；reducer 支持 `None` 值删除文件。

**使用示例**：

```python
from deepagents.middleware import FilesystemMiddleware
from deepagents.backends import StateBackend, CompositeBackend, StoreBackend
from langchain.agents import create_agent

# 混合存储：临时文件在 state，/memories/ 持久到 Store
backend = CompositeBackend(default=StateBackend(), routes={"/memories/": StoreBackend()})
agent = create_agent(model, middleware=[FilesystemMiddleware(backend=backend)])
```

**配合关系**：

- 与 `_ToolExclusionMiddleware`：harness profile 可把 `execute` 等工具标记排除，剔除中间件必须放在 FilesystemMiddleware **之后**（更内层）才能滤掉它注入的工具。
- 与 `HumanInTheLoopMiddleware`：`mode="interrupt"` 的权限规则经 `_fs_interrupt.py` 转成 HITL 配置（见 5.3）。
- 与 langchain `SummarizationMiddleware`：驱逐（eviction）是"内容搬进文件系统、可 read_file 找回"，摘要是"内容压成文字、不可逆"；deepagents 的设计是**先驱逐后摘要**，摘要提示词可引导模型去 `/large_tool_results/` grep 找细节。
- 本项目 nl2sql 实践：`CompositeBackend.default` 是否为 `SandboxBackendProtocol` 决定 deepagents 是否给该 agent `execute` 工具（MEMORY「deepagents 是否给某 agent execute 工具」的判定式 `supports_execution(CompositeBackend.default)` 就出自本文件）。

### 5.2 FilesystemPermission 与 permissions.py

**一句话用途**：一条文件系统访问规则（操作 × 路径模式 × 效果），是 deepagents 文件权限体系的数据单元；`permissions.py` 只是它的向后兼容再导出（5 行）。

```python
@dataclass
class FilesystemPermission:
    operations: list[Literal["read", "write"]]
    paths: list[str]                                  # 必须以 "/" 开头；禁 ".."；"~" 抛 NotImplementedError
    mode: Literal["allow", "deny", "interrupt"] = "allow"
```

**语义**：

- `allow`：放行（默认）。
- `deny`：工具直接返回 permission-denied 错误；**批量工具（ls/glob/grep）的结果也会逐条过滤掉 deny 路径**。
- `interrupt`：调用在 HITL 阶段暂停等人批（见 5.3）。interrupt 模式的路径**不在结果过滤中剔除**——因为中断发生在工具执行前，用户批准后再滤掉会让刚批准的列表变空。

**匹配规则**（`_check_fs_permission`）：按规则列表顺序**首条命中即生效**（first-match wins），路径匹配用 `wcmatch.glob`（`BRACE | GLOBSTAR` 标志，支持 `{a,b}` 与 `**`）。因此 deny 要放在 allow 前面。

**工具 → 操作映射**：`ls/read_file/glob/grep → read`；`write_file/edit_file → write`。

**使用示例**：

```python
rules = [
    FilesystemPermission(operations=["read", "write"], paths=["/secrets/**"], mode="deny"),
    FilesystemPermission(operations=["write"], paths=["/projects/*/deploy/**"], mode="interrupt"),
    FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="allow"),
]
```

**配合关系**：`mode="interrupt"` 的规则要求装配层同时挂 `HumanInTheLoopMiddleware`；`mode="deny"` 由 FilesystemMiddleware 的工具实现直接执行（工具内 `_check_fs_permission` + 结果过滤双保险）。带执行能力的 backend 目前不支持 permissions（工具级 execute 权限未实现），构造时直接 `NotImplementedError`——这正是本项目「语义库表/字段级权限方案」选择 MDL 投影而非 execute 侧拦截的原因之一。

### 5.3 _fs_interrupt.py

**一句话用途**：把 `FilesystemPermission(mode="interrupt")` 规则翻译成 `HumanInTheLoopMiddleware` 的 `interrupt_on` 配置——FilesystemMiddleware 本身不认识 HITL，这层胶水由 `deepagents.graph` 装配时调用。

**核心函数**：

```python
def _build_interrupt_on_from_permissions(
    rules: list[FilesystemPermission],
) -> dict[str, InterruptOnConfig]:
    # 没有任何 interrupt 规则 → 返回 {}
    # 对每个"其操作可能触发 interrupt 规则"的文件工具生成一条 InterruptOnConfig：
    #   allowed_decisions = 全部四种（approve/edit/reject/respond）
    #   when = 按工具 scope 定制的谓词
```

**工具 scope 模型**（`_FS_TOOL_PATH_ARGS`）：

- `"exact"`（read_file / write_file / edit_file）：谓词 = 路径参数命中 interrupt 规则才触发；**前置 deny 规则优先**（deny 时不触发中断，工具直接报权限错误）。
- `"bulk"`（ls / glob / grep）：路径参数是搜索根，可能带出任何后代——只要**搜索子树与 interrupt 规则的锚点前缀可能相交**（`_paths_overlap`）就触发；路径缺省（`grep(path=None)`）时**无条件触发**（无法定位的批量调用可能碰到任何东西）；`path="."` 之类当前目录别名归一为 `/`，堵住绕行。
- `glob` 额外多一层 `pattern` 门控：绝对 pattern（`/secrets/**`）会无视 `path` 重定向搜索根，含 `..` 的相对 pattern 可能爬出 `path`——两种都按锚点相交判定触发。

**安全设计要点**：interrupt 规则的模式应以**字面前缀锚定**（如 `/secrets/**`）；完全无锚的模式（`/**/secrets`）锚点退化为 `/`，会对所有批量调用保守地过度触发。四种决策全开放——即使人工 `edit` 改了参数，调用仍会重新进入工具的 deny 前置检查，人是授权闸门而非绕过通道。

### 5.4 PatchToolCallsMiddleware

**一句话用途**：Agent 启动时扫描消息历史，为所有"有调用无结果"的悬空 tool_call 补一条合成 ToolMessage，避免下一次模型调用因消息序列不合法而被 API 拒绝。

**源码位置**：`deepagents/middleware/patch_tool_calls.py`

**工作原理**（`before_agent`，全文件仅 47 行）：

1. 收集所有 ToolMessage 的 `tool_call_id` 为 `answered_ids`。
2. 遍历所有 AIMessage 的 `tool_calls` **和 `invalid_tool_calls`**，若无悬空调用直接返回 `None`（零开销快路径）。
3. 有悬空则重建消息列表，在每个悬空 AIMessage 后插入合成 ToolMessage：
   - invalid_tool_call → `"Tool call {name} with id {id} could not be executed - arguments were malformed or truncated."`
   - 正常 tool_call → `"Tool call {name} with id {id} was cancelled - another message came in before it could be completed."`
4. 返回 `{"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), *patched_messages]}` 整体替换。

**产生悬空的典型场景**：run 被取消/前端切会话打死 run（本项目 MEMORY「切会话会把在跑的 run 打死」）、invalid tool_call 400 链（langchain_openai 把 `invalid_tool_calls` 并入 `tool_calls`）、进程重启截断。

**配合关系**：必须放在 `before_agent` 链的**最前面**（middleware 列表首位附近），否则 HITL/子 agent 中间件可能先读到非法序列。它与 langchain `ToolCallLimitMiddleware(exit_behavior="end")` 的收尾消息互补——后者是主动终止，前者是被动修复历史。

### 5.5 RubricMiddleware

**一句话用途**（`@beta`）：每轮回答结束后，用一个独立的"评分员"子 agent 按 rubric（评分标准）打分；不合格且有预算时把评语注入对话并让主模型**当场返工**，形成自动质量闭环。

**源码位置**：`deepagents/middleware/rubric.py`

**关键签名**：

```python
class RubricMiddleware(AgentMiddleware[RubricState, ContextT, ResponseT]):
    def __init__(self, *,
                 model: str | BaseChatModel,             # 必填：评分员模型
                 system_prompt: str | None = None,        # 默认 GRADER_SYSTEM_PROMPT
                 tools: list[BaseTool] | None = None,     # 评分员可用工具
                 max_iterations: int = 3,                 # [1, 20]
                 on_evaluation: Callable[[RubricEvaluation], None] | None = None): ...
```

**State**（`RubricState`）：公开通道 `rubric`（用户在输入里给出的评分标准文本）；私有通道 `_rubric_status`、`_rubric_iterations`、`_rubric_evaluations`、`_current_grading_run_id`、`_active_rubric`。

**判定词汇**：

- `GraderVerdict`：`satisfied` / `needs_revision` / `failed`（终态）。
- `RubricResult` 额外增加：`max_iterations_reached`、`grader_error`（均终态，`_TERMINAL_RESULTS` frozenset）。
- `GraderResponse{result, explanation, criteria: list[CriterionEval]}`；`CriterionEval` 按 `passed` 字段做 discriminated union（fail 必须给 `gap`）；model_validator 拒绝自相矛盾的组合（satisfied 却含 fail 项 / needs_revision 却全过）。

**工作原理**：

1. `before_agent`：state 无 `rubric` → 完全 no-op（零成本）；出现新 rubric、或同一 rubric 但上一状态已终态 → 重置迭代计数/状态并铸造新 `_current_grading_run_id`。
2. `after_agent`（`@hook_config(can_jump_to=["model"])`）：
   - 发 `rubric_evaluation_start` 自定义流事件。
   - **懒构建**评分员：`create_agent(model=resolve_model, system_prompt, tools, name="rubric_grader", response_format=GraderResponse)`。
   - 组装 payload：随机 8 位 hex nonce，把 rubric 包进 `<rubric-{nonce}>...</rubric-{nonce}>`、对话记录包进 `<transcript-{nonce}>...</transcript-{nonce}>`；`_sanitize_for_payload` 转义正文里的字面 `</rubric`/`</transcript`，**防止提示词注入伪造闭合标签**。
   - transcript 取法：第一条真实 HumanMessage（跳过 `lc_source=rubric_grader` 的注入消息）+ 最近 30 条消息；每条 ≤4000 字符（超出加 `...(truncated)`）；角色标签 user/assistant/tool:name；content blocks 渲染——tool_call 渲染成 `<tool_call name=... args=.../>`，其他块渲染 `(type)`。
   - 按评分结果分支：
     - `satisfied` / `failed` → 终态，正常结束；
     - `needs_revision` 且迭代 < `max_iterations` → 注入一条 HumanMessage 返工提示（评分员 explanation + 未过 criteria 清单，`name/lc_source="rubric_grader"`）并返回 `{"jump_to": "model"}` **让主 agent 立刻重答**；
     - 预算耗尽 → `_rubric_status = max_iterations_reached` + `logger.warning`；
     - 评分员抛异常 → `grader_error`（`KeyboardInterrupt` / `CancelledError` 照常传播）。
   - 无论如何都发 `rubric_evaluation_end` 事件并调用 `on_evaluation` 回调（回调异常仅记日志吞掉）。

**使用示例**：

```python
from deepagents.middleware import RubricMiddleware

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-5",
    middleware=[RubricMiddleware(model="openai:gpt-4o-mini", max_iterations=2)],
)
# 运行时在 state 里给 rubric：
agent.invoke({"messages": [...], "rubric": "1. SQL 必须可执行；2. 结论必须有数据支撑"})
```

**配合关系**：`jump_to: "model"` 依赖 `after_agent` 钩子的条件边；返工循环会**成倍放大模型调用数**，务必与 `ModelCallLimitMiddleware` 同用兜底。评分注入的 HumanMessage 带 `lc_source` 标记，`SummarizationMiddleware`/transcript 组装都会识别并跳过，避免"评分提示词被当成用户话"的递归污染。本项目 nl2sql 的 Langfuse LLM-judge 属于**事后离线评估**，RubricMiddleware 是**在线返工闭环**，两者定位不同、可并存。

### 5.6 _ToolExclusionMiddleware

**一句话用途**：按名字黑名单从模型请求中剔除工具（私有实现，供 harness profile 使用）。

```python
class _ToolExclusionMiddleware(AgentMiddleware):
    def __init__(self, *, excluded: frozenset[str]): ...
    def wrap_model_call(self, request, handler):
        if self._excluded:
            filtered = [t for t in request.tools
                        if _tool_name(t) not in self._excluded]   # BaseTool.name 或 dict["name"]
            request = request.override(tools=filtered)
        return handler(request)
```

**关键约定**（docstring 明说）：必须放在 middleware 栈的**末尾附近**——即所有会注入工具的中间件（filesystem、subagent 等）之后，才能把它们注入的工具也剔掉。`wrap_model_call` 洋葱模型中"列表第一个 = 最外层"，因此"放得靠后"= 更贴近模型 = 最后一道工具面过滤。

**配合关系**：与 `LLMToolSelectorMiddleware` 都是工具面收窄，但语义相反——exclusion 是静态黑名单（配置驱动、零成本），selector 是动态白名单（每次调 LLM）。本项目 MEMORY「已建模库不绑 dbmcp」的工具过滤思想与此同源。

## 七、完整组合示例

下面组合 9 个中间件，展示一个生产级 Agent 的典型装配（顺序即 Pipeline 位置，注释说明为什么放在这）：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import (
    ModelFallbackMiddleware, ModelRetryMiddleware, ModelCallLimitMiddleware,
    ToolCallLimitMiddleware, ToolRetryMiddleware, ToolErrorMiddleware,
    HumanInTheLoopMiddleware, InterruptOnConfig,
    SummarizationMiddleware, ContextEditingMiddleware, ClearToolUsesEdit,
    PIIMiddleware, TodoListMiddleware, LLMToolSelectorMiddleware,
)
from deepagents.middleware import FilesystemMiddleware, PatchToolCallsMiddleware
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend

def on_tool_error(exc: Exception, request) -> str | None:
    """按异常类型转换，不回显原始消息（防泄漏连接串等敏感细节）。"""
    if isinstance(exc, PermissionError):
        return "权限不足：该操作需要更高授权。"
    if isinstance(exc, TimeoutError):
        return "工具执行超时，请缩小查询范围后重试。"
    return None  # 其余照常抛出

agent = create_agent(
    model="anthropic:claude-sonnet-4-5",
    tools=business_tools,               # 40+ 业务工具
    middleware=[
        # ── before_agent 层：先修历史，再谈其他 ──
        PatchToolCallsMiddleware(),     # 悬空 tool_call 修补，必须最早

        # ── 模型调用可靠性：外层 fallback，内层 retry ──
        ModelFallbackMiddleware(        # 主模型挂了换备胎（自动清 Anthropic 缓存标记）
            "anthropic:claude-sonnet-4-5", "openai:gpt-4o"),
        ModelRetryMiddleware(max_retries=2, on_failure="error"),
        # ↑ on_failure="error" 让耗尽后的异常继续向外冒给 fallback

        # ── 资源闸：模型次数 + 工具次数 ──
        ModelCallLimitMiddleware(thread_limit=200, run_limit=25, exit_behavior="end"),
        ToolCallLimitMiddleware(tool_name="expensive_sql", thread_limit=20),
        ToolCallLimitMiddleware(run_limit=80, exit_behavior="continue"),

        # ── 上下文管理：先清工具结果（80k），再摘要（140k）──
        ContextEditingMiddleware(edits=[
            ClearToolUsesEdit(trigger=80_000, keep=5, exclude_tools=("write_todos",)),
        ]),
        SummarizationMiddleware(model="openai:gpt-4o-mini",
                                trigger={"tokens": 140_000}, keep=("messages", 20)),

        # ── 能力扩展：虚拟文件系统 + 任务清单 ──
        FilesystemMiddleware(backend=CompositeBackend(
            default=StateBackend(), routes={"/memories/": StoreBackend()})),
        TodoListMiddleware(),

        # ── 工具面收窄：40+ 工具只给模型看 8 个 ──
        LLMToolSelectorMiddleware(model="openai:gpt-4o-mini", max_tools=8,
                                  always_include=["write_todos"]),

        # ── 人机协同：高危操作审批（放在模型侧钩子的最后）──
        HumanInTheLoopMiddleware(interrupt_on={
            "delete_record": True,
            "run_ddl": InterruptOnConfig(allowed_decisions=["approve", "reject"]),
        }),

        # ── 工具执行可靠性：外层 error 转换，内层 retry ──
        ToolErrorMiddleware(on_tool_error),
        ToolRetryMiddleware(max_retries=2, on_failure="error"),
        # ↑ retry 在 error 内层且耗尽后抛错，异常恰好被 ToolErrorMiddleware 接住转文案

        # ── 安全：PII 脱敏（最内层，贴近真实输入输出）──
        PIIMiddleware("email", strategy="mask"),
        PIIMiddleware("id_card", detector=r"\d{17}[\dXx]", strategy="redact",
                      apply_to_input=True, apply_to_tool_results=True),
    ],
)
```

**这个装配里的顺序要点复盘**：

1. `PatchToolCallsMiddleware` 第一位——历史不合法时任何后续中间件都可能崩。
2. `ModelFallback` 在 `ModelRetry` 外层（列表更靠前）：每个模型先各自重试，都失败才换模型；且 retry 设 `on_failure="error"` 保证异常能冒到 fallback。
3. `ToolError` 在 `ToolRetry` 外层，同理：重试耗尽的异常向外冒，被 error 转成模型能理解的 ToolMessage。
4. `ContextEditing`（80k）阈值低于 `Summarization`（140k）：便宜的清理先行，昂贵的摘要兜底。
5. `LLMToolSelector` 在 `TodoListMiddleware` 之后：`write_todos` 由 always_include 保住，不会因筛选丢失。
6. `PIIMiddleware` 放最后（最贴近模型/工具的真实 I/O 边界）：无论前面哪层改写了消息，进出模型的最后一道都过脱敏。
7. `HumanInTheLoopMiddleware` 依赖 checkpointer（`interrupt()` 的暂停/恢复），部署时务必配置；恢复用 `Command(resume={"decisions": [...]})`。

## 附：快速选型指南

- **上下文爆了** → `SummarizationMiddleware`（不可逆压缩）或 `ContextEditingMiddleware`（可逆、只清工具结果）；deepagents 栈里 `FilesystemMiddleware` 的驱逐是第三条路（内容可找回）。
- **模型/工具不稳** → `ModelRetry` + `ModelFallback` / `ToolRetry` + `ToolError`，牢记"重试在内、转换/降级在外"。
- **怕烧钱死循环** → `ModelCallLimit` + `ToolCallLimit` 双闸。
- **高危操作** → `HumanInTheLoopMiddleware`；文件系统细粒度管控用 `FilesystemPermission`（deny 硬拦 / interrupt 送审）。
- **工具太多模型选花眼** → 自家模型筛选用 `LLMToolSelector`，Anthropic/OpenAI 服务端筛选用 `ProviderToolSearch`，静态黑名单用 `_ToolExclusion`。
- **合规脱敏** → `PIIMiddleware` 多实例（每种 PII 一个），流式输出也在线路级覆盖。
- **回答质量闭环** → deepagents `RubricMiddleware`（在线返工）；离线评估另走 Langfuse judge。
