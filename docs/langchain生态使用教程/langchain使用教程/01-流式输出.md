## 1. 概述：流式输出的架构设计

### 1.1 为什么流式是 LangGraph 的「一等公民」

一次 agent 问答往往要跑几十秒到几分钟：模型思考、调工具、写文件、再思考。如果只在结束时返回一个最终结果，用户体验是「白屏转圈 90 秒」；对服务端来说，一个长时间不吐字节的 HTTP 连接还很容易被 nginx / 网关按 `proxy_read_timeout` 掐断。

所以 LangGraph 把「边算边吐」做成了运行时的核心能力，而不是外挂的日志功能。它需要同时满足四件事：

1. **多种粒度**：既要「每步之后的完整状态」（`values`），也要「每个节点返回了什么」（`updates`），还要「模型的每一个 token」（`messages`）、「工具的每一次生命周期」（`tools`）、「业务自定义进度」（`custom`）、「调试细节」（`debug` / `checkpoints` / `tasks`）。
2. **可组合**：一次运行可以同时订阅多种模式，输出交错在同一个流里，且**顺序正确**。
3. **穿透层级**：主图 → 子图 → 子子图 → 工具内 LLM 调用，任何深度产生的事件都要能带「命名空间」冒泡上来。
4. **背压（backpressure）**：消费者慢的时候，生产者不能无限堆内存。

### 1.2 三代 API：v1 / v2 / v3

`langgraph 1.2.9` 里同时存在三套流式形态，理解它们的差别是读懂全部源码的前提。

| 代际 | 入口 | 产出物 | 定位 |
|------|------|--------|------|
| **v1** | `graph.stream(...)` / `graph.astream(...)`（`version="v1"`，默认） | 裸 payload，或 `(mode, payload)`、`(ns, payload)`、`(ns, mode, payload)` 元组 | 传统形态，形状随参数组合变化，**类型不友好** |
| **v2** | 同上，`version="v2"` | `StreamPart` TypedDict：`{"type": mode, "ns": ns, "data": payload, ...}` | 形状统一、可静态检查，是 **v3 的地基** |
| **v3** | `graph.stream_events(..., version="v3")` / `graph.astream_events(..., version="v3")` | `GraphRunStream` / `AsyncGraphRunStream` 对象，带**类型化投影**（`run.values` / `run.messages` / `run.subgraphs` / `run.tool_calls` …） | 实验性（`@beta`），面向「人写业务代码」的符合直觉的 API |

v3 的实现方式很关键——它**没有另起一套引擎**，而是**在 v2 之上架了一层「转换器管线」**。看 `pregel/main.py:3560`：

```python
@beta(message="The v3 streaming protocol on Pregel is experimental.")
async def _apregel_stream_v3(self, input, config=None, *, interrupt_before=None,
                             interrupt_after=None, control=None, transformers=None, **kwargs):
    parent_ns = _resolve_parent_ns(self.config, config)          # ① 当前调用点所在的 checkpoint 命名空间
    compiled_factories = _normalize_stream_transformer_factories(self.stream_transformers)
    extra_factories = _normalize_stream_transformer_factories(transformers)
    mux = StreamMux(
        factories=[                                              # ② 4 个内置 transformer + 编译期 + 调用点
            ValuesTransformer, MessagesTransformer,
            LifecycleTransformer, SubgraphTransformer,
            *compiled_factories, *extra_factories,
        ],
        scope=parent_ns, is_async=True,
    )
    graph_aiter = self.astream(                                  # ③ 底层仍然是 v2 astream！
        input,
        patch_configurable(config, {CONFIG_KEY_STREAM_MESSAGES_V2: True}),
        stream_mode=_collect_stream_modes(mux),                  # ④ 需要哪些模式由 transformer 反推
        subgraphs=True,                                          # ⑤ 强制打开子图穿透
        version="v2",
        interrupt_before=interrupt_before, interrupt_after=interrupt_after,
        control=control, **kwargs,
    ).__aiter__()
    return AsyncGraphRunStream(graph_aiter, mux)                  # ⑥ 用 mux 包住底层迭代器
```

四个设计要点值得记住：

- **`stream_mode` 不是硬编码的**，而是 `_collect_stream_modes(mux)` —— 把所有已注册 transformer 的 `required_stream_modes` 求并集（`pregel/main.py:398`）。没人在意的模式，图根本不发，省 CPU。
- **`subgraphs=True` 恒开**，v3 靠 namespace + 分级 mini-mux 来区分「本层」和「子层」，所以调用方**不允许**再传 `stream_mode` / `subgraphs`，传了直接 `TypeError`（`_reject_v3_invariant_kwargs`，`pregel/main.py:387`）。
- **`CONFIG_KEY_STREAM_MESSAGES_V2`** 这个 configurable 开关会让 Pregel 挂 `StreamMessagesHandlerV2` 而不是 v1 版，从而把模型输出切成 content-block 协议事件（第 5 章详述）。
- v3 是**纯消费者侧的重组**：图跑的还是同一个 Pregel 循环。

### 1.3 端到端数据流（v3 异步路径）

```
┌──────────────────────── Pregel 循环（生产者） ────────────────────────┐
│ loop.tick() → PregelRunner.tick(tasks)                               │
│   ├─ 节点返回 → loop 写 channel → StreamProtocol 发 "values"/"updates" │
│   ├─ 模型 token → StreamMessagesHandlerV2.on_stream_event → "messages"│
│   ├─ 工具生命周期 → StreamToolCallHandler.on_tool_* → "tools"         │
│   ├─ 节点内 get_stream_writer()(...) → stream_writer → "custom"       │
│   └─ checkpoint / task 起止 → "checkpoints" / "tasks" / "debug"       │
│                       ↓ 全部塞进 AsyncQueue                           │
└──────────────────────────────────────────────────────────────────────┘
                        ↓ astream(version="v2") 整形为 StreamPart
        {"type": "messages", "ns": ("agent:abc",), "data": (event, meta)}
                        ↓ convert_to_protocol_event()          ← _convert.py
        {"type":"event","method":"messages","seq":42,
         "params":{"namespace":["agent:abc"],"timestamp":1728...,"data":(...)}}
                        ↓ AsyncGraphRunStream._apump_next()    ← run_stream.py
                        ↓ StreamMux.apush(event)               ← _mux.py
   ┌────────────── transformer 管线（按注册顺序 aprocess） ──────────────┐
   │ ValuesTransformer   → run.values      (StreamChannel[dict])        │
   │ MessagesTransformer → run.messages    (StreamChannel[ChatModelStream])│
   │ LifecycleTransformer→ run.lifecycle   (具名 channel → 上 wire)      │
   │ SubgraphTransformer → run.subgraphs   (StreamChannel[SubgraphRunStream])│
   │ 你注册的 transformer → run.extensions["custom:xxx"]                 │
   └────────────────────────────────────────────────────────────────────┘
                        ↓ 未被 suppress 的事件追加进主日志 mux._events
                        ↓
              消费者：async for x in run.messages / run.values / run
```

### 1.4 两个贯穿全局的设计原则

**原则一：调用方驱动的泵（caller-driven pump），没有后台线程/任务。**

`GraphRunStream` 的类注释（`run_stream.py:31`）写得很直白：

```python
class GraphRunStream:
    """Sync run stream with caller-driven pumping.

    The caller's iteration on any projection (`values`, `messages`,
    raw events, or `output`) drives the graph forward. No background
    thread is used — the caller's `for` loop is the pump.
    """
```

意思是：**你 `for` 循环不转，图就不往前跑**。`StreamChannel._sync_cursor` 的逻辑（`stream_channel.py:182`）：

```python
def _sync_cursor(self) -> Iterator[T]:
    while True:
        if self._items:                       # ① 缓冲区有货 → 直接吐
            _stamp, item = self._items.popleft()
            yield item
        elif self._closed:                    # ② 流已结束 → 抛错或收工
            if self._error is not None:
                raise self._error
            return
        elif self._request_more is not None:  # ③ 缓冲区空 → 拉一次泵（推进一步图）
            if not self._request_more():
                if not self._items and not self._closed:
                    return
        else:
            return
```

由此推出两个必须遵守的约束：

- **背压天然成立**：内存占用由消费节奏决定，`StreamChannel` 的 `maxlen` 参数甚至「accepted for forward compatibility; currently unused」（`stream_channel.py:60`）。
- **懒订阅陷阱**：拿到 `run` 之后**必须马上开始迭代某个投影**。你如果先 `await asyncio.sleep(60)` 再回来迭代，这 60 秒里图**一步都没跑**。（异步侧略有不同：多个并发消费者共享 single-flight 泵，见 4.4。）

**原则二：投影是单消费者的（single-consumer）。**

`StreamChannel.__aiter__` 里：

```python
if self._subscribed:
    raise RuntimeError(
        "StreamChannel already has a subscriber; use .atee(n) for fan-out."
    )
self._subscribed = True
```

同一个 `run.values` 迭代第二次会直接抛 `RuntimeError`。真要一分为二，用 `tee(n)` / `atee(n)`（`stream_channel.py:245` / `288`）。另外 `push()` 有个「懒订阅」优化：**没有订阅者时根本不进本地缓冲**（但具名 channel 的 wire 自动转发照常触发）：

```python
def push(self, item: T) -> None:
    if self._subscribed:                      # ← 没人订阅就不占内存
        if self._closed:
            raise RuntimeError("Cannot push to a closed StreamChannel")
        stamp = self._mux._next_push_seq() if self._mux is not None else 0
        self._items.append((stamp, item))      # ← 存 (单调序号, item)，供 interleave 排序
    if self._wire_fn is not None:
        self._wire_fn(item)                    # ← 具名 channel：额外注入主日志，始终执行
```

## 2. StreamMode 枚举详解

### 2.1 图层的 7 个模式（`langgraph/types.py:120`）

```python
StreamMode = Literal[
    "values", "updates", "checkpoints", "tasks", "debug", "messages", "custom"
]
"""How the stream method should emit outputs.

- `"values"`: Emit all values in the state after each step, including interrupts.
    When used with functional API, values are emitted once at the end of the workflow.
- `"updates"`: Emit only the node or task names and updates returned by the nodes or tasks after each step.
    If multiple updates are made in the same step (e.g. multiple nodes are run) then those updates are emitted separately.
- `"custom"`: Emit custom data using from inside nodes or tasks using `StreamWriter`.
- `"messages"`: Emit LLM messages token-by-token together with metadata for any LLM invocations inside nodes or tasks.
- `"checkpoints"`: Emit an event when a checkpoint is created, in the same format as returned by `get_state()`.
- `"tasks"`: Emit events when tasks start and finish, including their results and errors.
- `"debug"`: Emit `"checkpoints"` and `"tasks"` events for debugging purposes.
"""
```

逐个拆解，**并给出 v2 载荷的确切类型**（`types.py:262-351`）：

#### `"values"` —— 每步之后的完整状态快照

```python
class ValuesStreamPart(TypedDict, Generic[OutputT]):
    type: Literal["values"]
    ns: tuple[str, ...]
    data: OutputT                      # read_channels() 读出的完整 state
    interrupts: tuple[Interrupt, ...]  # ← 唯一带 interrupts 字段的模式
```

用途：需要「随时能拿到当前全量状态」的场景，比如前端整屏刷新、HITL 恢复前看现场。注意它**很贵**：每一步都把整个 state（含全部历史消息）序列化一遍。本项目里 `state.next` / `update_state` 相关的坑（幽灵 next、快照盖写）都发生在这一层。

`interrupts` 字段是 v3 `run.interrupted` / `run.interrupts` 的数据源，见 `run_stream.py:94`：

```python
def _observe_event(self, event: ProtocolEvent) -> None:
    """Track values-event state for output/interrupted/interrupts."""
    if event["method"] != "values":
        return
    params = event["params"]
    if params["namespace"] != self._scope_list:   # ← 只认本层，子图快照不算
        return
    self._latest = params["data"]
    interrupts = params.get("interrupts", ())
    if interrupts:
        self._interrupted = True
        self._interrupts.extend(interrupts)
```

#### `"updates"` —— 每个节点/任务返回的增量

```python
class UpdatesStreamPart(TypedDict):
    type: Literal["updates"]
    ns: tuple[str, ...]
    data: dict[str, Any]     # {节点名: 该节点返回的更新}；可能含 __interrupt__ / __metadata__
```

同一步里跑了 3 个节点 ⇒ 发 3 条，各自单独。这是**最常用**的模式：体积小、语义清楚（「谁改了什么」）。`__interrupt__` 键承载 HITL 中断（服务端 `langgraph_api/stream.py:598` 专门有分支处理它）。

#### `"messages"` —— 模型 token 流

```python
class MessagesStreamPart(TypedDict):
    type: Literal["messages"]
    ns: tuple[str, ...]
    data: tuple[AnyMessage, dict[str, Any]]   # (消息块, 元数据)
```

**`data` 是二元组**，第二个元素是元数据字典（`langgraph_step` / `langgraph_node` / `langgraph_triggers` / `langgraph_checkpoint_ns` / `ls_model_name` …）。第一个元素的**具体形状取决于是 v1 还是 v2 handler**：

- v1（`StreamMessagesHandler`）：`AIMessageChunk`（token 级增量）或节点输出里的完整 `BaseMessage`；
- v2（`StreamMessagesHandlerV2`，v3 专用）：一个 content-block 协议事件 dict（`{"event": "message-start", ...}`），元数据里额外带 `run_id`。

详见第 5 章。

#### `"custom"` —— 业务自定义数据

```python
class CustomStreamPart(TypedDict):
    type: Literal["custom"]
    ns: tuple[str, ...]
    data: Any        # 你在节点里传给 StreamWriter 的任意值
```

节点里怎么拿到 writer？两种写法：

```python
# 写法 A：声明 writer 形参，LangGraph 自动注入
from langgraph.types import StreamWriter
def node(state: State, writer: StreamWriter) -> dict:
    writer({"stage": "解析语义层", "progress": 0.3})   # ← 只有 custom 在 stream_mode 里才真发出去
    return {...}

# 写法 B：运行时取（工具内部、深层函数里更方便，不用改函数签名）
from langgraph.config import get_stream_writer
def some_deep_helper():
    get_stream_writer()({"stage": "执行 SQL"})
```

`get_stream_writer()` 的官方 docstring（`langgraph/config.py:126`）带一条**版本警告**：

```
!!! warning "Async with Python < 3.11"
    If you are using Python < 3.11 and are running LangGraph asynchronously,
    `get_stream_writer()` won't work since it uses contextvar propagation
    (only available in Python >= 3.11).
```

即：它靠 ContextVar 传播，**Python < 3.11 的异步场景下拿不到 writer**（静默失效）。本项目跑 Python 3.13，不受影响。同理，`_tool_call_writer`（第 6 章）也是 ContextVar，受同样的版本约束。

`StreamWriter` 的定义（`types.py:136`）明确说明「**不用 `stream_mode="custom"` 时它是 no-op**」：

```python
StreamWriter = Callable[[Any], None]
"""`Callable` that accepts a single argument and writes it to the output stream.
Always injected into nodes if requested as a keyword argument, but it's a no-op
when not using `stream_mode="custom"`."""
```

对应 `pregel/main.py:2841` 的三分支装配：

```python
if "custom" in stream_modes:
    def stream_writer(c: Any) -> None:
        stream.put((
            tuple(get_config()[CONF][CONFIG_KEY_CHECKPOINT_NS].split(NS_SEP)[:-1]),  # ← 自动打上当前 ns
            "custom", c,
        ))
elif CONFIG_KEY_STREAM in config[CONF]:
    stream_writer = config[CONF][CONFIG_KEY_RUNTIME].stream_writer   # 继承父图的（子图场景）
else:
    def stream_writer(c: Any) -> None:
        pass                                                          # ← no-op
```

> ⚠️ 本项目的 `main_agent.py` **没有**任何 `get_stream_writer` 调用（`grep` 全 `src/` 零命中）。进度是通过 `write_todos` 写 state + `sync_launcher` 同步子 agent todos 实现的，走的是 `values`/`updates` 而非 `custom`。这是一个有意的架构选择，第 11 章展开。

#### `"checkpoints"` —— 每次落盘

```python
class CheckpointStreamPart(TypedDict, Generic[StateT]):
    type: Literal["checkpoints"]
    ns: tuple[str, ...]
    data: CheckpointPayload[StateT]    # config / metadata / values / next / parent_config / tasks
```

形状与 `get_state()` 一致（`CheckpointsTransformer` 注释原文）。**没配 checkpointer 时这个模式一条都不发**，但投影仍然存在（`transformers.py:933`）。这是排查「重启后状态丢失」类问题的最佳观测点。

#### `"tasks"` —— 任务起止

```python
class TasksStreamPart(TypedDict):
    type: Literal["tasks"]
    ns: tuple[str, ...]
    data: TaskPayload | TaskResultPayload
```

两种载荷靠「有没有 `result` 键」区分（`transformers.py:464`）：

```python
class TaskPayload(TypedDict):        # 任务开始
    id: str; name: str; input: Any; triggers: list[str]
    metadata: NotRequired[dict[str, Any]]   # 含 lc_agent_name / langgraph_node / langgraph_step

class TaskResultPayload(TypedDict):  # 任务结束
    id: str; name: str
    error: str | None
    interrupts: list[dict]
    result: dict[str, Any]           # {channel 名: 本任务写入的值}
```

`tasks` 是 v3 **子图发现与生命周期推断的唯一信号源**——`LifecycleTransformer` 和 `SubgraphTransformer` 都只吃它。

#### `"debug"` —— 前两者的带步骤号包装

```python
DebugPayload = _DebugCheckpointPayload | _DebugTaskPayload | _DebugTaskResultPayload
# 每个都长这样：{"step": int, "timestamp": ISO8601, "type": "checkpoint"|"task"|"task_result", "payload": ...}
```

即 `"debug"` ≈ `"checkpoints"` + `"tasks"` 再套一层 `step` / `timestamp`。人肉排障用；生产别常开（体积翻倍）。

### 2.2 图层没有、但服务端有的 4 个模式

`langgraph_api/schema.py:18` 定义了 **HTTP API 层**的模式枚举，比图层多 4 个：

```python
StreamMode = Literal[
    "values", "messages", "updates", "events", "debug", "tasks",
    "checkpoints", "custom",
    "messages-tuple",   # ← 服务端专有
    "tools",            # ← 图层运行时支持但不在 Literal 里
    "lifecycle",        # ← v3 transformer 合成

```

- **`"messages-tuple"`**：**不是**图的模式，是服务端的「兼容别名」。`langgraph_api/stream.py:238` 把它翻译成 `messages`：
  ```python
  if "messages-tuple" in stream_modes_set and not is_remote_pregel:
      stream_modes_set.remove("messages-tuple")
      stream_modes_set.add("messages")
  ```
  再在 `:543` 决定 wire 形状：请求 `messages-tuple` 的客户端拿到**原始二元组** `(message, metadata)`；请求 `messages` 的客户端拿到服务端重建的 `messages/partial`、`messages/complete`、`messages/metadata` 三种事件。`consume()`（`:644`）里还有一句 `if "messages-tuple" in stream_modes: stream_modes.add("messages")` 用于断线重连的可恢复判定。
  > 📌 这正是本项目「前端 getter 隐式请求 messages-tuple + 后端归一化」那条链路的机制来源。
- **`"tools"`**：图层**运行时认**（`pregel/main.py:2830` `if "tools" in stream_modes:`），但**没写进 `langgraph.types.StreamMode` 这个 Literal**，所以直接传给 `graph.astream(stream_mode=["tools"])` 会有类型检查告警（运行时正常）。服务端在 Protocol v2 run 上会自动加它（`event_streaming/capabilities.py` 第 2 条明确说「Missing ⇒ `graph.astream(stream_mode=["tools", ...])` raises」）。
- **`"lifecycle"`**：v3 `LifecycleTransformer` 合成的通道，不是图原生模式。
- **`"events"`**：请求「原始 `astream_events(version="v2")` 事件」，服务端走完全不同的分支（`stream.py:306`）。

### 2.3 v1 vs v2 的输出形状：`_output()` 一张表说清

所有形状差异都收敛在 `pregel/main.py:4184` 的 `_output()`：

```python
def _output(stream_mode, print_mode, stream_subgraphs, getter, empty_exc,
            version="v1", output_mapper=None, state_mapper=None) -> Iterator:
    while True:
        try:
            ns, mode, payload = getter()          # 队列里恒为三元组 (ns, mode, payload)
        except empty_exc:
            break
        if mode in print_mode:                     # print_mode 只打印，不影响产出
            print(" ".join((get_bolded_text(f"[{mode}]"), repr(payload))))
        if mode in stream_mode:
            if version == "v2":
                if mode == "values":
                    ints: tuple[Interrupt, ...] = ()
                    if isinstance(payload, dict):
                        ints = payload.pop(INTERRUPT, ())       # ← __interrupt__ 提成独立字段
                        if output_mapper:
                            payload = output_mapper(payload)     # ← state schema 归一
                    yield {"type": mode, "ns": ns, "data": payload, "interrupts": ints}
                elif mode in ("checkpoints", "debug"):
                    if state_mapper:
                        _coerce_checkpoint_values(payload, state_mapper)
                    yield {"type": mode, "ns": ns, "data": payload}
                else:
                    yield {"type": mode, "ns": ns, "data": payload}
            elif stream_subgraphs and isinstance(stream_mode, list):
                yield (ns, mode, payload)          # v1 四种组合 ↓
            elif isinstance(stream_mode, list):
                yield (mode, payload)
            elif stream_subgraphs:
                yield (ns, payload)
            else:
                yield payload
```

| `stream_mode` | `subgraphs` | `version` | 每次 yield 的形状 |
|---|---|---|---|
| `"updates"`（单模式） | `False` | v1 | `payload`（裸值） |
| `"updates"` | `True` | v1 | `(ns, payload)` |
| `["updates","messages"]` | `False` | v1 | `(mode, payload)` |
| `["updates","messages"]` | `True` | v1 | `(ns, mode, payload)` |
| 任意 | 任意 | **v2** | `{"type": mode, "ns": ns, "data": payload}`（`values` 多一个 `interrupts`） |

> 💡 **实战建议**：新代码一律用 `version="v2"`。v1 的四种形状意味着你的 `for` 循环体必须写四套解包逻辑，而 v2 永远是一个 dict。v3 内部也只用 v2。

| StreamMode | 内置 transformer | `required_stream_modes` | v3 投影 | 投影元素类型 | 是否默认注册 |
|---|---|---|---|---|---|
| `values` | `ValuesTransformer` | `("values",)` | `run.values` | `dict[str, Any]` | ✅ |

### 3.2 内部机制：队列 + 回调 + 泵

```python
stream = AsyncQueue()
aioloop = asyncio.get_running_loop()
stream_put = cast(
    Callable[[StreamChunk], None],
    partial(aioloop.call_soon_threadsafe, stream.put_nowait),   # ← 关键：线程安全的入队
)
```

为什么要 `call_soon_threadsafe`？因为节点可能跑在 executor 线程里（同步工具、`run_in_executor` 的 LLM 调用），而队列属于事件循环线程。所有生产者（loop 本身、各 callback handler、`stream_writer`）拿到的都是这个 `stream.put`，事件则统一在循环里被消费。

接着按模式**装配回调 handler**（`main.py:2811-2838`，异步侧对称）：


注意是 **`inheritable_handlers`** —— 会被子 runnable 继承，所以节点里嵌套的模型调用、工具调用都能被观察到。

然后是**并发流式**的关键开关（`main.py:2936`）：

```python
get_waiter: Callable[[], concurrent.futures.Future[None]] | None = None
if (self.stream_eager or subgraphs
        or "messages" in stream_modes or "custom" in stream_modes):
    waiter: concurrent.futures.Future | None = None
    loop.stack.callback(stream._count.release)     # 退出时释放信号量（sync future 不可取消）

    def get_waiter() -> concurrent.futures.Future[None]:
        nonlocal waiter
        if waiter is None or waiter.done():
            waiter = loop.submit(stream.wait)
            return waiter
        else:
            return waiter
```

这段是「**为什么 token 能在节点还没返回时就冒出来**」的答案：`PregelRunner.tick(..., get_waiter=get_waiter)` 在执行任务的同时等待「队列里有新东西」这个 future，一有就把控制权交回生成器去 `yield`。没有它，`messages`/`custom` 只能等整个节点跑完才批量吐出。判定条件也说明了：**只要你订了 `messages` 或 `custom`，或开了 `subgraphs`，并发流式就自动打开**，无需额外配置。

主循环（`main.py:2964`）：

```python
while loop.tick():                                   # BSP：一步 = 一个 superstep
    for task in loop.match_cached_writes():
        loop.output_writes(task.id, task.writes, cached=True)
    for _ in runner.tick(
        [t for t in loop.tasks.values() if not t.writes],
        timeout=self.step_timeout,
        get_waiter=get_waiter,                       # ← 并发流式
        schedule_task=loop.accept_push,
    ):
        yield from _output(stream_mode, print_mode, subgraphs,
                           stream.get, queue.Empty, version,
                           _output_mapper, _state_mapper)
    loop.after_tick()
    emit_graph_lifecycle_events(loop)
    if durability_ == "sync":
        loop._put_checkpoint_fut.result()            # 同步落盘：阻塞等 checkpoint 写完
```

收尾时还要处理三种退出状态：`out_of_steps` → `GraphRecursionError`（提示里直接给出「调大 `recursion_limit`」的建议）、`draining` → `GraphDrained`、正常 → `run_manager.on_chain_end(loop.output)`。异常路径统一 `on_chain_error(e)` 后 re-raise。

> 📌 本项目 `main_agent.py:281` 设了 `"recursion_limit": 500`。这个值直接决定 `out_of_steps` 什么时候触发；deep agent 的多轮工具循环很容易吃掉几十步。

### 3.3 子图穿透是怎么接上的

## 4. `astream_events()` 方法详解

### 4.1 一个方法，两套完全不同的语义

```python
def astream_events(self, input, config=None, *, version="v2",
                   interrupt_before=None, interrupt_after=None,
                   control=None, transformers=None, **kwargs):
    if version == "v3":
        _reject_v3_invariant_kwargs(kwargs)
        return self._apregel_stream_v3(input, config, interrupt_before=..., transformers=transformers, **kwargs)
    return super().astream_events(input, config, version=version, **kwargs)
```

- **`version="v1"` / `"v2"`**：委托给 `Runnable.astream_events`，产出 `StreamEvent` dict（`on_chat_model_start` / `on_chat_model_stream` / `on_tool_end` / `on_chain_stream` …）。这是 LangChain 通用的、**基于回调**的事件流，粒度到每个 runnable，但没有图结构语义。
- **`version="v3"`**：返回 `Awaitable[AsyncGraphRunStream]`，是 LangGraph 专属的**协议事件 + 类型化投影**体系。

两者的返回类型不同（`AsyncIterator[StreamEvent]` vs `Awaitable[Any]`），调用方式也不同：

```python
# v2
async for ev in graph.astream_events(inp, config, version="v2"):
    if ev["event"] == "on_chat_model_stream":
        print(ev["data"]["chunk"].content, end="")

# v3 —— 注意必须先 await 拿到 run，再 async with
async with await graph.astream_events(inp, config, version="v3") as run:
    async for msg_stream in run.messages:
        async for delta in msg_stream.text:
            print(delta, end="")
```

`async with` 不是可选的装饰：`AsyncGraphRunStream.__aexit__` 调 `abort()`，保证提前 break 时把图**真正取消**（见 4.5）。

### 4.2 v3 的调用点参数

| 参数 | 说明 |
|---|---|
| `version="v3"` | 必填，选择协议 |
| `interrupt_before` / `interrupt_after` | 静态断点，透传给底层 `astream` |
| `control: RunControl` | 协作式排空请求（蓝绿发布时优雅停机用） |
| `transformers` | **额外的 transformer 工厂序列**，追加在编译期 `stream_transformers` 之后。必须是 `factory(scope)` 形状的可调用对象；**传预构建实例会 `TypeError`**（见 `_normalize_stream_transformer_factories`，`main.py:417`） |
| `**kwargs` | 透传给底层 `astream`：`context`、`durability`、`output_keys`、`print_mode`、`debug` 都可以。**`stream_mode` 和 `subgraphs` 不行**，传了抛 `TypeError` |

```python
_V3_INVARIANT_KWARGS: tuple[str, ...] = ("stream_mode", "subgraphs")

def _reject_v3_invariant_kwargs(kwargs: dict[str, Any]) -> None:
    collisions = [k for k in _V3_INVARIANT_KWARGS if k in kwargs]
    if collisions:
        raise TypeError(
            "stream_events(version='v3') / astream_events(version='v3') do "
            f"not accept {', '.join(collisions)}; v3 owns these "
            "(stream_mode is built from the transformer mux, subgraphs is "
            "forced True so nested namespaces flow through scoped muxes)."
        )
```

`transformers` 的工厂约束值得单独强调（`main.py:430`）：

```python
for spec in specs or ():
    if isinstance(spec, StreamTransformer):
        raise TypeError(
            "stream_events(version='v3') transformers must be scope-aware callables, "
            f"got pre-built instance {type(spec).__name__}. Pass the "
            "transformer class or a factory like "
            "`lambda scope: MyTransformer(scope, ...)`."
        )
```

原因：**子图需要克隆一份新的 transformer 实例**（`StreamMux._make_child`），预构建实例无法克隆。所以要么传类本身（构造函数签名恰好是 `(scope)`），要么传 `lambda scope: MyTransformer(scope, foo=bar)`。

编译期注册的写法：

```python
graph = builder.compile(transformers=[ToolCallTransformer, UpdatesTransformer])
# 或带配置：
graph = builder.compile(transformers=[lambda scope: PiiRedactor(scope, patterns=PATTERNS)])
```

`Pregel.__init__` 把它存成 tuple（`main.py:831`）：`self.stream_transformers = tuple(stream_transformers or ())`。

### 4.3 `AsyncGraphRunStream` 的完整表面

```python
class AsyncGraphRunStream:
    def __init__(self, graph_aiter, mux, *, wire_pump=True):
        self._graph_aiter = graph_aiter
        self._mux = mux
        self.extensions: Mapping[str, Any] = MappingProxyType(mux.extensions)  # 只读投影注册表
        self._exhausted = False
        self._latest: dict[str, Any] | None = None      # 最新 values 快照
        self._interrupted = False
        self._interrupts: list[Any] = []
        self._scope_list: list[str] = list(mux.scope)
        self._pump_cond = asyncio.Condition()           # take-a-number 泵用
        self._pumping = False
        self._anext_task: asyncio.Future[Any] | None = None
        self._aborting = False
        for key in mux.native_keys:                     # ← _native=True 的投影挂成直接属性
            setattr(self, key, mux.extensions[key])
        if wire_pump:
            self._wire_arequest_more(mux)               # ← mux.bind_apump(self._apump_next)
```

可用的成员：

| 成员 | 类型 | 语义 |
|---|---|---|
| `run.values` | `StreamChannel[dict]` | 本层状态快照流（需 `ValuesTransformer`） |
| `run.messages` | `StreamChannel[AsyncChatModelStream]` | 本层每次 LLM 调用一个 handle |
| `run.lifecycle` | `StreamChannel[LifecyclePayload]` | 子图/子 agent 生命周期（**具名 channel，也上 wire**） |
| `run.subgraphs` | `StreamChannel[AsyncSubgraphRunStream]` | 直接子图句柄 |
| `run.updates` / `.custom` / `.tasks` / `.checkpoints` / `.debug` / `.tool_calls` | `StreamChannel[...]` | 注册了对应 transformer 才有 |
| `run.extensions` | `MappingProxyType(dict)` | **所有**投影的只读注册表，含 `custom:<name>` 形式的用户 channel |
| `await run.output()` | `dict \| None` | 驱动到结束，返回最终 state；出错则抛 |
| `await run.interrupted()` | `bool` | 驱动到结束，返回是否被中断 |
| `await run.interrupts()` | `list[Any]` | 驱动到结束，返回中断载荷列表 |
| `async for ev in run` | `ProtocolEvent` | 订阅**主事件日志**（原始协议事件，含被 transformer 保留的一切） |
| `await run.abort()` | — | 提前终止并取消在跑的节点/子图 |

三个「驱动到结束」的方法都是**方法而非属性**，注释解释了原因（`run_stream.py:511`）：

```python
async def output(self) -> dict[str, Any] | None:
    """Drive the run to completion and return the final state.

    Methods (not properties) on the async lane so `run.output`
    without `await` raises at type-check time instead of silently
    yielding a coroutine object.
    """
    await _adrive_until_done(self._apump_next)
    if (err := self._mux._events._error) is not None:
        raise err
    return self._latest
```

（同步侧 `GraphRunStream.output` 则是 `@property`，因为它不需要 await，写 `run.output` 就能用。这是两条 lane 有意为之的不对称。）

### 4.4 take-a-number 泵：多个并发消费者如何共享一个图

`AsyncGraphRunStream._apump_next`（`run_stream.py:391`）是 v3 异步侧最精巧的一段：

```python
async def _apump_next(self) -> bool:
    """Drive one pump step, or wait for the active pumper to drive one.

    "Take-a-number" semantics: at most one task at a time calls
    `graph_aiter.__anext__()` (asyncio iterators can't be advanced
    concurrently). Other callers wait on a Condition that the
    active pumper notifies after each step. This lets a "passive"
    consumer — one whose projection's buffer is being filled by the
    active pumper's push — wake up as soon as its data lands,
    instead of queueing on the pump and only observing its data one
    graph event late.
    """
    async with self._pump_cond:
        if self._exhausted or self._graph_aiter is None:
            return False
        if self._pumping:
            await self._pump_cond.wait()      # ① 别人在泵 → 等它这一步的通知
            return not self._exhausted
        self._pumping = True                  # ② 我抢到号了

    try:
        try:
            # ③ 把 __anext__ 包成子任务，abort() 才能中途取消它
            self._anext_task = asyncio.ensure_future(self._graph_aiter.__anext__())
            try:
                part = await self._anext_task
            except asyncio.CancelledError:
                if self._aborting:
                    self._exhausted = True    # abort 发起的取消 → 优雅停止
                    return False
                self._anext_task.cancel()     # 外部真取消 → 连带停在跑的拉取
                raise
            finally:
                self._anext_task = None
            event = convert_to_protocol_event(part)
            self._observe_event(event)
            await self._mux.apush(event)      # ④ 过 transformer 管线
            return True
        except StopAsyncIteration:
            self._exhausted = True
            await self._mux.aclose()
            return False
        except Exception as e:                # ← 故意不接 BaseException
            self._exhausted = True
            await self._mux.afail(e)
            return False
    finally:
        async with self._pump_cond:
            self._pumping = False
            self._pump_cond.notify_all()      # ⑤ 通知所有等号的消费者
```

这套语义带来一个非常实用的性质：**你可以用 `asyncio.gather` 并发消费多个投影**，它们会各自驱动同一个图，事件被正确分发到各自的 channel，且每个消费者在自己数据落地的那一刻就醒，不用等下一轮。

```python
async with await graph.astream_events(inp, config, version="v3") as run:
    async def watch_messages():
        async for ms in run.messages:
            async for d in ms.text:
                print(d, end="", flush=True)

    async def watch_lifecycle():
        async for ev in run.lifecycle:
            print(f"\n[{ev['event']}] {ev['namespace']} {ev.get('graph_name','')}")

    await asyncio.gather(watch_messages(), watch_lifecycle())
```

背压从哪来？类注释：「Backpressure comes from the logs: when a subscribed log's buffer reaches `maxlen`, `apush` awaits the subscriber to drain, which holds back the pump and paces the graph.」——消费者不取，泵就不推进，图自然慢下来。

### 4.5 `abort()`：真正能取消在跑的节点

```python
async def abort(self) -> None:
    async with self._pump_cond:
        if self._exhausted:
            return
        self._exhausted = True
        self._aborting = True
        graph_aiter = self._graph_aiter
        self._graph_aiter = None
        anext_task = self._anext_task
        self._pump_cond.notify_all()          # ① 唤醒所有等号的
    # ② 若正卡在 __anext__，取消它 —— CancelledError 会传进图生成器帧 → Pregel 循环 → 嵌套子图节点
    if anext_task is not None and not anext_task.done():
        anext_task.cancel()
        try:
            await anext_task
        except (asyncio.CancelledError, Exception):
            pass
    # ③ 此时生成器已不在运行，aclose() 才是安全的收尾（也覆盖「没在拉取」的情况）
    if graph_aiter is not None and (aclose := getattr(graph_aiter, "aclose", None)) is not None:
        try:
            await aclose()
        except Exception:
            pass
    try:
        await self._mux.aclose()
    except Exception:
        pass
```

注释里点明了为什么必须先 cancel 再 aclose：裸 `aclose()` 在生成器正在运行时会抛 `asynchronous generator is already running`，**取消不了正在跑的节点**。这也是「前端点『停止』但后端还在烧 token」这类 bug 的正解路径。`abort()` 幂等。

### 4.6 `interleave()`：按到达顺序交织多个投影（仅同步侧）

`GraphRunStream.interleave(*names)`（`run_stream.py:205`）解决「我想在一个 `for` 循环里同时看 messages 和 values，并且**顺序正确**」：

```python
for name, item in run.interleave("messages", "values"):
    if name == "messages":
        print("msg:", item)
    else:
        print("val:", item)
```

排序依据是 `StreamChannel.push()` 时打上的单调戳（`_next_push_seq()`），所以是**严格到达序**，不是轮询（round-robin）。它会：
- 校验每个 name 都是 `StreamChannel`（不是则 `TypeError`）、已绑定、绑定到同步 lane、且未被订阅；
- 迭代期间**独占**这些 channel，生成器结束/关闭/抛错时在 `finally` 里释放 `_subscribed = False`；
- 所有 channel 都排空且泵返回 False 时收尾。

异步侧**故意不提供** `interleave`，`_remote_run_stream.py:370` 的注释说明了理由：

```python
# Note: deliberately no `interleave()` on the async adapter. Local
# `AsyncGraphRunStream` doesn't have one either (async callers compose
# with `asyncio.gather` / `asyncio.as_completed`). The sync adapter
# provides `interleave()` because sync callers have no comparable
# primitive for iterating multiple iterators concurrently.
```

### 4.7 主事件日志：`async for ev in run`

`run.__aiter__` 返回 `self._mux._events.__aiter__()`，即 `StreamMux` 自己持有的那个**无名单消费者 channel**。里面流的是 `ProtocolEvent`：

```python
class ProtocolEvent(TypedDict):
    """A protocol event emitted by the streaming infrastructure.

    Wraps a raw stream part (values, messages, custom, etc.) in a uniform
    envelope with a monotonic sequence number assigned by the root StreamMux.
    Consumers that need a total order across root events should use `seq`, not
    `params.timestamp` (which is wall-clock and not monotonic).
    """
    type: Literal["event"]
    event_id: NotRequired[str]
    seq: NotRequired[int]
    method: str          # StreamMode 值："values" / "messages" / "custom" / "custom:xxx" / "lifecycle" …
    params: _ProtocolEventParams   # {namespace: list[str], timestamp: int(ms), data: Any, interrupts?: tuple}
```

> ⚠️ **排序请用 `seq`，不要用 `timestamp`**。`_ProtocolEventParams` 的注释明确写了：`timestamp` 是 wall-clock 毫秒，**NTP 校时时会倒退**。`seq` 只在**根 mux** 上分配（子 mux `_assign_seq=False`），所以只有根日志有全序。

被 transformer `process()` 返回 `False` 的事件**不会进主日志**——目前只有 `tasks` 事件被 `_TasksLifecycleBase.process` 抑制（`transformers.py:473`，理由：「consumers iterating the raw protocol stream see the higher-level view」，避免同一信息以两种形状被看到两遍）。所以想看原始 task 载荷，得注册 `TasksTransformer` 读 `run.tasks`。

## 5. 逐 token 流式输出

### 5.1 最小实现：`StreamingStdOutCallbackHandler`

`langchain_core/callbacks/streaming_stdout.py` 全文只有 154 行，但它把「token 流」的本质暴露得最干净——**流式输出 = 一个 `on_llm_new_token` 回调**：

```python
class StreamingStdOutCallbackHandler(BaseCallbackHandler):
    """Callback handler for streaming.

    !!! warning "Only works with LLMs that support streaming."
    """

    def on_llm_start(self, serialized, prompts, **kwargs) -> None: ...   # 空实现：占位
    def on_chat_model_start(self, serialized, messages, **kwargs) -> None: ...

    @override
    def on_llm_new_token(
        self, token: str | list[str | dict[str, Any]], **kwargs: Any
    ) -> None:
        """Run on new LLM token. Only available when streaming is enabled."""
        sys.stdout.write(str(token))     # ← 拿到一个 token 就立刻写出去
        sys.stdout.flush()               # ← 必须 flush，否则被 stdio 缓冲攒着
```

用法：

```python
from langchain_core.callbacks import StreamingStdOutCallbackHandler

# 方式一：模型级 streaming=True + 回调
model = ChatOpenAI(model="deepseek-chat", streaming=True,
                   callbacks=[StreamingStdOutCallbackHandler()])
model.invoke("讲个笑话")           # 边生成边打印

# 方式二：直接 .stream()（推荐，不需要回调）
for chunk in model.stream("讲个笑话"):
    print(chunk.content, end="", flush=True)
```

> ⚠️ `str(token)` 而不是 `token`：因为新版模型可能把 token 传成 **content-block 列表**（`list[str | dict]`），直接 `write` 会 `TypeError`。这个细节说明「token」这个概念在 content-block 协议下已经泛化了。

**LangGraph 的做法就是把这类回调 handler 挂到运行时的 inheritable handlers 上**，让「节点内部的模型调用」产生的 token 也能冒泡到图的输出流。

### 5.2 v1 路径：`StreamMessagesHandler`（`pregel/_messages.py:49`）


**第一步：模型启动时登记命名空间**（`:130`）


**第二步：每个 token 发出**（`:151`）


```python
def _emit(self, meta: Meta, message: BaseMessage, *, dedupe: bool = False) -> None:
    if dedupe and message.id in self.seen:
        return
    else:
        if message.id is None:
            message.id = str(uuid4())          # ← 补 id，前端靠它做增量拼接
        self.seen.add(message.id)
        self.stream((meta[0], "messages", (message, meta[1])))   # ← (ns, mode, payload)
```

**第三步：结束时补发完整消息并去重**（`:166`、`:223`）

`on_llm_end` 把 `response.generations[0][0].message` 以 `dedupe=True` 再发一次；`on_chain_end` 处理**节点返回值里的消息**（包括 `Command(update=...)` 形式），同样 `dedupe=True`。`dedupe` 靠消息 `id` 去重，避免「token 流已经发过、节点结束又发一遍完整消息」造成前端重复渲染。

另外 `on_chain_start`（`:191`）会把**输入 state 里已有的消息 id 全部预先塞进 `self.seen`**：

```python

```

这就是「`stream_mode="messages"` 不会把对话历史重放一遍」的机制。

核心转发逻辑（`:373`）：

```python
def on_stream_event(self, event: dict[str, Any], *, run_id, parent_run_id=None, tags=None, **kwargs):
    """Forward a protocol event from stream_events(version="v3") as a messages stream part."""
    if meta := self.metadata.get(run_id):
        if event.get("event") == "message-start":
            self._streamed_run_ids.add(run_id)          # ① 标记这个 run 走了流式
            msg_id = event.get("message_id")
            if msg_id:
                self.seen.add(msg_id)                   # ② 让 on_chain_end 的去重跳过它
        v2_meta = {**meta[1], "run_id": str(run_id)}    # ③ 关键：注入 run_id
        self.stream((meta[0], "messages", (event, v2_meta)))
```

③ 是 transformer 层能把散落的事件**重新聚合成一条消息**的唯一线索。② 解决一个很隐蔽的双计数问题（源码注释原文）：

> Record message_id on message-start so on_chain_end's dedupe skips the finalized AIMessage the node returns (otherwise the messages projection double-counts: once from streaming, once from the chain output).

配套的 `on_llm_end` 覆写（`:336`）也据此分叉：流式过的 run 只补 id 入 `seen` 不再 emit；没流式过的（比如节点里直接 `model.invoke()`）才 emit 完整消息。

还有一处 v2 专属的过滤（`:307`）：

#### content-block 协议事件长什么样

`MessagesData`（`langchain_protocol/protocol.py`）是一个 union，事件类型有：

| `event` 值 | 含义 | 关键字段 |
|---|---|---|
| `message-start` | 一条消息开始 | `message_id`、`role`（`"ai"` / `"tool"` …） |
| `content-block-start` | 一个内容块开始 | `index`、`content_block`（`{"type": "text"}` / `{"type": "reasoning"}` / `{"type": "tool_call", ...}`） |
| `content-block-delta` | 块的增量 | `index`、`delta`（`{"type": "text_delta", "text": "你"}`） |
| `content-block-finish` | 块结束 | `index` |
| `message-finish` | 消息结束 | `message_id`、`usage`（`UsageInfo`）、`response_metadata` |
| `error` | 出错 | `message` |

**一条消息可以有多个块、块可以交错**。这正是 v1 `AIMessageChunk` 表达不了的东西（v1 只有 `content` + `tool_call_chunks`），也是「reasoning 模型」能同时流式输出思考过程和正文的基础。

### 5.4 `MessagesTransformer`：把散落事件重组成 `ChatModelStream`

`stream/transformers.py:155` 的类注释把两种输入形状说得很清楚：

```
Two input shapes are handled (via params["data"] = (payload, metadata)):

1. Protocol event (dict with "event" key) — emitted by stream_events(version="v3")
   via the `on_stream_event` callback. Routed to an existing `ChatModelStream` by

   message. Replayed as a synthetic protocol event lifecycle via `message_to_events`,
   then the already-complete stream is pushed to the log.

V1 `AIMessageChunk` tuples (from `on_llm_new_token`) are not streamed into this
```

分发实现（`:265`）：

```python
def process(self, event: ProtocolEvent) -> bool:
    if event["method"] != "messages":
        return True
    params = event["params"]
    if params["namespace"] != self._scope_list:      # ① 只投影本层
        return True

    payload, metadata = params["data"]
    node: str | None = metadata.get("langgraph_node")
    run_id = str(metadata.get("run_id", "")) if metadata else ""

    if isinstance(payload, dict) and "event" in payload:
        self._route_protocol_event(cast("MessagesData", payload), run_id=run_id, node=node)
    elif (isinstance(payload, BaseMessage)
          and not isinstance(payload, AIMessageChunk)     # ② v1 chunk 直接忽略
          and not isinstance(payload, ToolMessage)):      # ③ 工具消息不属于消息投影
        self._route_whole_message(payload, node=node)

```

```python
def _route_protocol_event(self, event: MessagesData, *, run_id: str, node: str | None) -> None:
    event_type = event.get("event")
    if event_type == "message-start":
        if event.get("role") == "tool":
            self._ignored_runs.add(run_id)               # 工具 run 整条忽略
            return
        message_id = event.get("message_id")
        stream = self._make_stream(namespace=[], node=node,
                                   message_id=str(message_id) if message_id is not None else None)
        self._by_run[run_id] = stream                    # ← run_id 建索引
        self._log.push(stream)                           # ← 立刻推给消费者（此时消息还是空的！）
        stream.dispatch(event)
    elif run_id in self._ignored_runs:
        if event_type == "message-finish":
            self._ignored_runs.discard(run_id)
    elif run_id in self._by_run:
        stream = self._by_run[run_id]
        stream.dispatch(event)                           # ← 后续事件灌进同一个 handle
        if event_type == "message-finish":
            del self._by_run[run_id]                     # ← 关闭
```

注意 `self._log.push(stream)` 发生在 **`message-start` 那一刻**，此时 `stream` 里还一个字符都没有。消费者拿到的是一个**活的句柄**，后续 `dispatch` 会持续喂它。这就是为什么必须「拿到就迭代」——如果你在循环体里做别的事而不消费 `stream.text`，事件会在句柄内部缓冲堆积。

`_make_stream`（`:229`）决定造同步还是异步版本：

### 5.5 `ChatModelStream` 的类型化投影

```python

    - `.reasoning` — same as `.text` for reasoning content
    - `.tool_calls` — iterable of `ToolCallChunk` deltas; `.get()` returns `list[ToolCall]`
    - `.output` — blocking property, returns assembled `AIMessage`

    !!! note "Output shape is always v1 content blocks"
        `.output.content` is always a list of v1 protocol blocks (text, reasoning,
        tool_call, image, …), regardless of the underlying model's `output_version`
        setting.
    """
```

```python
@property
def text(self) -> SyncTextProjection: ...        # 可迭代 str 增量；str() 得全文
@property
def reasoning(self) -> SyncTextProjection: ...   # 思考过程
@property
def tool_calls(self) -> SyncProjection: ...      # ToolCallChunk 增量；.get() 得 list[ToolCall]
@property
def output(self) -> AIMessage:                   # 阻塞直到流结束
    self._drain()
    if self._error is not None:
        raise self._error
    if self._output_message is None:
        raise RuntimeError("Stream finished without producing a message")
    return self._output_message
```

`AsyncChatModelStream`（`:1198`）对称，差别是 `.output` 是 **awaitable**，并且整个对象支持 `await stream`（`__await__` 直接给 `AIMessage`）：

```python
@property
def output(self) -> AsyncProjection: ...
def __await__(self) -> Generator[Any, None, AIMessage]: ...
```

原始事件迭代有**回放缓冲**语义（`:1155`）：即使你已经消费过一部分 `.text`，`for event in stream` 仍会从头吐出所有 `MessagesData` dict（`self._events` 是全量列表 + cursor）。

> 💡 **usage 从哪拿**：`.output.usage_metadata`（流结束后）。这是本项目 `TokenMeterMiddleware` 之外另一条统计口径——不过本项目走的是中间件路线，不依赖 v3。

### 5.6 服务端如何把 token 变成 SSE

生产环境里前端看到的是 `langgraph_api/stream.py` 加工后的三种事件（`:543` 附近）：

| SSE 事件名 | 载荷 | 请求哪个 mode 才有 |
|---|---|---|
| `messages/partial` | `{"content": "...", "type": "AIMessageChunk", "id": ...}` 累积到当前的消息 | `messages` |
| `messages/complete` | 完整消息 | `messages` |
| `messages/metadata` | 元数据 | `messages` |
| `messages` | **原始二元组** `[message, metadata]` | `messages-tuple` |

也就是说：**同样一份底层 token 流，请求 `messages` 得到「服务端替你拼好的累积消息」，请求 `messages-tuple` 得到「原始增量」**。本项目前端用的是后者（getter 隐式请求 `messages-tuple`），然后在 SDK/前端侧累积。

## 6. 工具调用流式输出

工具调用流式有两个层面，别混：**① 模型正在生成 tool_call 的参数（增量 JSON）**，这属于 `messages` 通道（`ChatModelStream.tool_calls`）；**② 工具正在执行、往外吐中间结果**，这属于 `tools` 通道。本章讲第二个。

### 6.1 `StreamToolCallHandler`（`pregel/_tools.py:35`）

```python
class StreamToolCallHandler(BaseCallbackHandler, _StreamingCallbackHandler):
    """Callback handler that emits tool-call lifecycle events on the stream.

    Fires on LangChain's `on_tool_*` callbacks and pushes to the `tools`
    stream mode. Emits `tool-started` / `tool-output-delta` /
    `tool-finished` / `tool-error` payloads keyed by `tool_call_id`.

    While a tool is executing, this handler sets `_tool_call_writer` to a
    closure bound to that call's namespace and `tool_call_id`.
    `ToolRuntime.emit_output_delta` reads that ContextVar so tool bodies
    can stream partial output without threading the writer through their
    own signature.

    Attached by `Pregel.stream` / `astream` when `"tools"` is in
    `stream_modes`. `run_inline = True` keeps event ordering deterministic.
    """
    run_inline = True
```

`_start`（`:121`）里最妙的是这个闭包 + ContextVar：

```python
def _start(self, serialized, input_str, *, run_id, metadata, tags, inputs, kwargs) -> None:
    ns = self._ns_for_emit(metadata, tags)
    if ns is None:
        return
    tool_call_id = cast("str | None", kwargs.get("tool_call_id")) or str(run_id)
    tool_name = ((serialized or {}).get("name") or cast("str | None", kwargs.get("name")) or "")

    def writer(delta: Any) -> None:                     # ① 造一个绑定了 ns + tool_call_id 的 writer
        self.stream((ns, "tools", {
            "event": "tool-output-delta",
            "tool_call_id": tool_call_id,
            "delta": delta,
        }))

    token = _tool_call_writer.set(writer)                # ② 塞进 ContextVar，记下 token 以便复位
    self._run_to_call[run_id] = (ns, tool_call_id, token)

    payload: dict[str, Any] = {
        "event": "tool-started",
        "tool_call_id": tool_call_id,
        "tool_name": tool_name,
    }
    if inputs is not None:
        payload["input"] = inputs
    self.stream((ns, "tools", payload))                  # ③ 起始事件
```

ContextVar 的定义（`:25`）：

```python
_tool_call_writer: ContextVar[ToolCallWriter | None] = ContextVar(
    "langgraph_tool_call_writer", default=None
)
"""ContextVar holding the writer for the currently-executing tool call.

Set by `StreamToolCallHandler.on_tool_start` and reset on end/error.
Read by `ToolRuntime.emit_output_delta` (in `langgraph.prebuilt`).
"""
```

为什么用 ContextVar 而不是把 writer 作为参数传进工具？因为工具签名是**模型可见的 schema**，塞个 writer 进去会污染模型的工具定义。ContextVar 让「深层工具函数」无需改签名就能拿到当前调用的 writer。

`_ns_for_emit`（`:87`）复用了消息 handler 的三条抑制规则：无 metadata / 带 `TAG_NOSTREAM` / 子图但 `subgraphs=False` 且 ns ≠ parent_ns。

`_end` / `_error`（`:167` / `:185`）都先从 `self._run_to_call.pop(run_id)` 拿回 `(ns, tool_call_id, token)`，**复位 ContextVar**（`self._reset_writer(token)`）再发终态事件。复位是必须的，否则嵌套工具调用会把 delta 发到错误的外层 tool_call_id 上。

> 📌 注释里点明了一个实现细节：`on_tool_end` 的 kwargs **不带** `tool_call_id`，所以只能用每个回调都有的 `run_id` 做关联。

### 6.2 工具内部怎么发增量：`ToolRuntime.emit_output_delta`

`prebuilt/tool_node.py:1732`：

```python
def emit_output_delta(self, delta: Any) -> None:
    """Stream a partial output chunk on the `tools` stream channel.

    Reads the per-tool-call writer that `StreamToolCallHandler`
    installs on a ContextVar at `on_tool_start` and forwards `delta`
    through it. Silent no-op when the graph was not run with
    `"tools"` in `stream_mode` (no writer is set), so tool authors
    can leave `emit_output_delta` calls in place without gating
    them on stream mode.

    Args:
        delta: Partial output chunk. Any JSON-serializable value;
            surfaced as-is on the `tools` channel's
            `tool-output-delta` payload under `"delta"`.
    """
    writer = _tool_call_writer.get()
    if writer is None:
        return          # ← 没开 tools 模式就是 no-op，工具代码不用写 if 判断
    writer(delta)
```

「**静默 no-op**」这个设计非常重要：工具作者可以无条件写 `runtime.emit_output_delta(...)`，不必关心调用方有没有订阅 `tools`。

### 6.3 `ToolCallTransformer` + `ToolCallStream`：v3 的类型化视图

`tools` 通道的原始载荷是四种 dict。v3 把它们聚合成一个句柄（`prebuilt/_tool_call_stream.py`）：

```python
class ToolCallStream:
    """Scoped view of a single tool call's lifecycle.

    Yielded on `run.tool_calls` once per `tool-started` event. Fields
    are populated as events arrive:

    - `tool_call_id`, `tool_name`, `input`: stable from the start event.
    - `output_deltas`: a `StreamChannel` of delta chunks. Iterate (sync or
      async) to consume partial output in arrival order.
    - `output`: terminal payload from `tool-finished`, or `None` if the
      call failed or is still in flight.
    - `error`: terminal error string from `tool-error`, or `None` if the
      call succeeded or is still in flight.
    - `completed`: True once a terminal event has been observed.
    """
    def __init__(self, tool_call_id, tool_name, input=None):
        self.tool_call_id = tool_call_id
        self.tool_name = tool_name
        self.input = input
        self._output_deltas: StreamChannel[Any] = StreamChannel()
        self.output: Any = None
        self.error: str | None = None
        self.completed = False

    def _finish(self, output: Any) -> None:
        self.output = output; self.completed = True; self._output_deltas.close()

    def _fail(self, message: str) -> None:
        self.error = message; self.completed = True; self._output_deltas.close()

    def __iter__(self): return iter(self._output_deltas)         # 直接迭代 = 迭代 delta
    def __aiter__(self): return self._output_deltas.__aiter__()
```

`ToolCallTransformer`（`prebuilt/_tool_call_transformer.py`）的注释说明了它**为什么不是内置默认**：

```python
class ToolCallTransformer(StreamTransformer):
    """...
    A nameless `StreamChannel[ToolCallStream]` is used (no protocol
    auto-forwarding) because the live handles are not serializable and
    should not be injected into the main event log. Wire consumers
    subscribe to the `tools` channel instead, where the raw protocol
    events flow through untouched by this transformer (`process`
    returns `True`).

    Registered explicitly by users at compile time via
    `builder.compile(transformers=[ToolCallTransformer])` — not a
    default built-in, so the `tools` channel is user-opt-in.
    """
    _native = True
    required_stream_modes = ("tools",)
```

两个关键点：

1. **`process` 返回 `True`（pass-through）**：`tools` 事件仍然进主日志上 wire，因为远程客户端要靠原始事件自己重建句柄（`ToolCallStream` 是活对象，不可序列化）。对比 `_TasksLifecycleBase.process` 返回 `False`——`tasks` 被彻底折叠进 lifecycle/subgraphs 投影。
2. **匿名 channel**：`StreamChannel()` 不带名字 ⇒ 不触发 wire 自动转发 ⇒ `run.tool_calls` 是纯进程内投影。

`process` 的状态机（`:79`）：

```python
def process(self, event: ProtocolEvent) -> bool:
    if event["method"] != "tools":
        return True
    if tuple(event["params"]["namespace"]) != self.scope:    # 只投影本层；子图的归子 mini-mux
        return True
    data = event["params"]["data"]
    tool_call_id = data.get("tool_call_id")
    if tool_call_id is None:
        return True
    event_type = data.get("event")
    if event_type == "tool-started":
        stream = self._new_stream(tool_call_id, data.get("tool_name", ""), data.get("input"))
        self._active[tool_call_id] = stream
        self._log.push(stream)
    elif event_type == "tool-output-delta":
        stream = self._active.get(tool_call_id)
        if stream is not None:
            stream._push_delta(data.get("delta"))
    elif event_type == "tool-finished":
        stream = self._active.pop(tool_call_id, None)
        if stream is not None:
            stream._finish(data.get("output"))
    elif event_type == "tool-error":
        stream = self._active.pop(tool_call_id, None)
        if stream is not None:
            stream._fail(data.get("message", ""))
    return True
```

`finalize` / `fail` 兜底：run 结束时仍 `active` 的调用统一 `_finish(None)` / `_fail(str(err))`，保证消费者的 `async for` 能正常收工而不是永久挂起。

### 6.4 用法

```python
from langgraph.prebuilt._tool_call_transformer import ToolCallTransformer

graph = builder.compile(transformers=[ToolCallTransformer])     # ← 必须显式注册

async with await graph.astream_events(inp, config, version="v3") as run:
    async for call in run.tool_calls:                           # 每个 tool-started 一个句柄
        print(f"[{call.tool_name}] 入参={call.input}")
        async for delta in call:                                # 等价于 call.output_deltas
            print("  进度:", delta)
        print("  结果:", call.output, "错误:", call.error)
```

> ⚠️ 上面的写法有**懒订阅陷阱**：`async for call in run.tool_calls` 每拿到一个句柄就在循环体里把它消费完，才会回到外层拉下一个事件。若两个工具并发执行，第二个的 delta 会在句柄内缓冲。要真正并行消费，用 `asyncio.gather` 或把句柄收集起来后再并发迭代（4.4 的 take-a-number 泵支持这么做）。

### 7.1 v1/v2：`subgraphs=True` 与命名空间

传统方式只有一个开关：

```python
async for ns, mode, payload in graph.astream(
    inp, config, stream_mode=["updates", "messages"], subgraphs=True, version="v2"

# ns=()                       → 主图
# ns=("nl2sql:1ef3...",)      → 一层子图（node_name:task_id）
# ns=("nl2sql:1ef3", "wren:x")→ 两层
```

机制见 3.3：父图把自己的 `stream` 对象通过 `CONFIG_KEY_STREAM` 传给子图，子图**复用同一队列**，只是打上更深的 ns。所以「穿透」在 v1/v2 是**免费的**，代价是你得自己按 ns 字符串做分流。

### 7.2 v3：`LifecycleTransformer` 与 `SubgraphTransformer`

v3 把 ns 字符串升级成了**结构化对象**。两个 transformer 都继承 `_TasksLifecycleBase`（`transformers.py:373`），共用同一套「从 `tasks` 事件推断生命周期」的逻辑：

```python
class _TasksLifecycleBase(StreamTransformer):
    """Shared bookkeeping for `tasks`-event-driven lifecycle inference.

    Both `LifecycleTransformer` (wire-serializable channel) and
    `SubgraphTransformer` (in-process navigation handles) discover
    subgraphs by watching the same `tasks` stream — `started` on the
    first event at a tracked namespace, terminal status when the
    parent's `TaskResultPayload` arrives. Centralizing the dispatch
    + open-set bookkeeping here keeps the inference rules from
    drifting between the two surfaces.
    """
    required_stream_modes = ("tasks",)
```

三个模板方法：

| 钩子 | 职责 |
|---|---|
| `_should_track(ns)` | 作用域过滤（多深 vs 仅直接子级） |
| `_on_started(ns, graph_name, trigger_call_id)` | 首次见到某 ns 时触发（推 payload / 建句柄） |
| `_on_terminal(ns, status, error)` | 父任务的 `TaskResultPayload` 到达时触发 |

`process` 的分派（`:459`）：

```python
def process(self, event: ProtocolEvent) -> bool:
    if event["method"] != "tasks":
        return True
    ns = tuple(event["params"]["namespace"])
    data = event["params"]["data"]
    if "result" in data:                    # ← 有 result 键 ⇒ TaskResultPayload（任务结束）
        self._handle_task_result(ns, data)
    else:                                    # ← 否则 TaskPayload（任务开始）
        self._record_identity(ns, data)
        self._record_pending_tool_calls(data)
        self._handle_task_start(ns, data)
    # Tasks events are folded into the synthesized projections;
    # suppress from the main event log so iterators don't double-see
    # the same information in two shapes.
    return False                             # ← 抑制 tasks 事件
```

**子 agent 识别**（`:518`）——这段是理解「deepagents 的 subagent 为什么会出现在 `run.lifecycle` 里」的关键：

```python
def _handle_task_start(self, ns, data) -> None:
    if not self._should_track(ns) or ns in self._seen:
        return
    self._seen.add(ns)
    parsed_name, trigger_call_id = _parse_ns_segment(ns[-1])     # "node:task_id" → (node, task_id)
    metadata = data.get("metadata") or {}
    child_lc = metadata.get("lc_agent_name")
    # A subagent boundary is any nested run carrying an lc_agent_name (set by create_agent).
    is_subagent = child_lc is not None
    graph_name = child_lc if is_subagent else (parsed_name or None)
    cause: LifecycleCause | None = None
    if is_subagent and trigger_call_id is not None:
        tool_call_id = self._pending_tool_calls.get(trigger_call_id)
        if tool_call_id:
            cause = {"type": "toolCall", "tool_call_id": str(tool_call_id)}   # ← 哪个工具调用引发了它
    self._pending_cause = cause
    self._on_started(ns, graph_name, trigger_call_id)
    if trigger_call_id is not None:
        self._open[ns] = trigger_call_id       # ← 记下「哪个父任务的结果会关掉我」
```

`_record_pending_tool_calls`（`:488`）从任务 `input` 里挖出触发的 `tool_call_id`，兼容两种形状（当前 Pregel 的 `tool_call_with_context` dict / 旧版 list）。这样 `cause` 就能告诉你「这个子 agent 是 `task` 工具调用产生的」。`LifecycleCause` 是个 union：`{"type": "toolCall", "tool_call_id": ...}` / `{"type": "send", ...}` / `{"type": "edge", ...}`。

**终态判定**（`:591`）：

```python
def _terminal_from_result(payload: dict[str, Any]) -> tuple[SubgraphStatus, str | None]:
    """Map a `TaskResultPayload` to a `(status, error)` pair.

    Order matters: a result with both `error` and `interrupts` prefers
    the interrupt classification, since `GraphInterrupt` manifests as
    a populated `interrupts` list, not as `error`.
    """
    if payload.get("interrupts"):
        return "interrupted", None
    error = payload.get("error")
    if error:
        return "failed", str(error)
    return "completed", None

SubgraphStatus = Literal["started", "completed", "failed", "interrupted", "drained"]
```

`drained` 来自 `_status_from_exception`：`GraphDrained → "drained"`、`GraphInterrupt → "interrupted"`、其他 → `"failed"`。这是**协作式排空（蓝绿发布）**在流式层的可见信号。

### 7.3 两个 transformer 的作用域差异

```python
# LifecycleTransformer：跟踪 scope 之下**所有深度**，输出扁平流
def _should_track(self, ns): 
    depth = len(self.scope)
    return len(ns) > depth and ns[:depth] == self.scope

# SubgraphTransformer：**只跟踪直接子级**，孙子由子 mux 自己的 SubgraphTransformer 发现
def _should_track(self, ns):
    depth = len(self.scope)
    return len(ns) == depth + 1 and ns[:depth] == self.scope
```

`LifecycleTransformer` 用**具名 channel**（`StreamChannel("lifecycle")`），所以 payload 会被 mux 自动转发进主日志、以 `method="lifecycle"` 上 wire（`_native=True` ⇒ 不加 `custom:` 前缀）。远程 SDK 客户端因此能收到同一份数据。

`SubgraphTransformer` 则建**活的导航句柄**：

```python
def _on_started(self, ns, graph_name, trigger_call_id) -> None:
    if self._mux is None:
        return
    try:
        child_mux = self._mux._make_child(ns)              # ① 建子作用域 mini-mux
    except RuntimeError:
        return                                              # 无 factories ⇒ 建不了，静默跳过
    handle_cls = AsyncSubgraphRunStream if child_mux.is_async else SubgraphRunStream
    handle = handle_cls(mux=child_mux, path=ns,
                        graph_name=graph_name, trigger_call_id=trigger_call_id)
    self._handles[ns] = handle
    self._log.push(handle)                                  # ② 推给消费者
```

事件转发（`:813`）——**顺序很重要**：

```python
def process(self, event: ProtocolEvent) -> bool:
    # Run tasks bookkeeping first so a `started` handle exists
    # by the time we forward the event to the child mini-mux.
    keep = super().process(event)                  # ① 先做 tasks 记账（可能建出句柄）
    handle = self._handle_for_event(event)          # ② 再找该事件属于哪个子句柄
    if handle is not None:
        handle._observe_event(event)                # ③ 更新句柄的 output/interrupted 状态
        handle._mux.push(event)                     # ④ 灌进子 mux 的 transformer 管线
    return keep
```

`_handle_for_event` 用 `ns[: depth + 1]` 做前缀匹配，所以孙子的 events 也会被转发到儿子句柄的 mini-mux，再由儿子自己的 `SubgraphTransformer` 发现孙子。递归结构就是这样搭起来的。

### 7.4 子图句柄的表面

`SubgraphRunStream` / `AsyncSubgraphRunStream` **继承自 `GraphRunStream` / `AsyncGraphRunStream`**（`run_stream.py:587` / `:630`），所以拥有完全相同的投影表面（`values` / `messages` / `lifecycle` / `subgraphs` / `output` / …），外加：

| 属性 | 类型 | 含义 |
|---|---|---|
| `path` | `tuple[str, ...]` | 完整命名空间路径 |
| `graph_name` | `str \| None` | 子 agent 名（有 `lc_agent_name` 时）或节点名 |
| `trigger_call_id` | `str \| None` | 父图里那个任务的 id |
| `status` | `SubgraphStatus` | 由 `SubgraphTransformer` **就地更新** |
| `error` | `str \| None` | 失败原因 |

构造时传 `graph_iter=None, wire_pump=False`，泵委托给父级（`:613`）：

```python
def _pump_next(self) -> bool:
    """Delegate to the parent's pump.

    Cursors on this handle's projections call here when their
    buffers empty. Driving the parent fans events into our
    mini-mux, transparently advancing the whole run.
    """
    if (self._exhausted or self._seen_terminal
            or self._mux._events._closed or self._parent_pump_fn is None):
        return False
    return self._parent_pump_fn()
```

所以「迭代子句柄的 `values`」实际上在驱动**整个根 run**——这就是 `_SubgraphRunStreamMixin` 注释说的：

> Pump-driving methods delegate to the parent pump so `handle.output` and friends drive the root run.

### 7.5 用法

```python

        async for snap in sub.values:               # ← 这会驱动整个根 run
```

## 8. 远程图流式输出

`RemoteGraph` 是「把远程 LangGraph Server 上的一个 assistant 当成本地图用」的代理。它的流式实现分两层：**v1/v2 走 SSE 手工解析**，**v3 直接复用 SDK 的 thread stream 适配器**。

### 8.1 `RemoteGraph.astream`：SSE → StreamPart（`pregel/remote.py:912`）

```python
async def astream(self, input, config=None, *, context=None, stream_mode=None,
                  interrupt_before=None, interrupt_after=None, subgraphs=False,
                  headers=None, params=None, version="v1", **kwargs):
    """Create a run and stream the results.

    This method calls `POST /threads/{thread_id}/runs/stream` if a `thread_id`
    is specified in the `configurable` field of the config or
    `POST /runs/stream` otherwise.
    """
    client = self._validate_client()
    merged_config = merge_configs(self.config, config)
    sanitized_config = self._sanitize_config(merged_config)
    stream_modes, requested, req_single, stream = self._get_stream_modes(stream_mode, config)
    if isinstance(input, Command):
        command = cast(CommandSDK, asdict(input)); input = None       # ① Command 走 command 参数
    else:
        command = None
    thread_id = sanitized_config.get("configurable", {}).pop("thread_id", None)

    async for chunk in client.runs.stream(                            # ② SDK 的 SSE 流
        thread_id=thread_id, assistant_id=self.assistant_id,
        input=input, command=command, config=sanitized_config, context=context,
        stream_mode=stream_modes, interrupt_before=interrupt_before,
        interrupt_after=interrupt_after,
        stream_subgraphs=subgraphs or stream is not None,
        if_not_exists="create",                                       # ③ 线程不存在就建
        headers=(_merge_tracing_headers(headers) if self.distributed_tracing else headers),
        params=params, **kwargs,
    ):
        # ④ SSE 事件名形如 "updates|node:x|sub:y" —— 用 NS_SEP 拆出 mode 和 ns
        if NS_SEP in chunk.event:
            mode, ns_ = chunk.event.split(NS_SEP, 1)
            ns = tuple(ns_.split(NS_SEP))
        else:
            mode, ns = chunk.event, ()
        # ⑤ 父图命令：直接抛异常让父图处理
        if mode == "command" and chunk.data.get("graph") == Command.PARENT:
            raise ParentCommand(Command(**chunk.data))
        # ⑥ 补上调用方自己的 ns（远程不知道调用方在哪一层）
        if caller_ns := (config or {}).get(CONF, {}).get(CONFIG_KEY_CHECKPOINT_NS):
            caller_ns = tuple(caller_ns.split(NS_SEP))
            ns = caller_ns + ns
        # ⑦ 如果 RemoteGraph 是作为父图的节点在跑，把事件转发进父图的流
        if stream is not None and mode in stream.modes:
            stream((ns, mode, chunk.data))
        # ⑧ 中断 / 错误还原成本地异常
        if chunk.event.startswith("updates"):
            if isinstance(chunk.data, dict) and INTERRUPT in chunk.data:
                if caller_ns:
                    raise GraphInterrupt([Interrupt(**i) for i in chunk.data[INTERRUPT]])
        elif chunk.event.startswith("error"):
            raise RemoteException(chunk.data)
        # ⑨ 过滤掉调用方没请求的模式
        if mode not in requested:
            continue
        if chunk.event.startswith("messages"):
            chunk = chunk._replace(data=tuple(chunk.data))            # JSON 数组 → 二元组
        # ⑩ 按 version / subgraphs / req_single 决定 yield 形状
        if version == "v2":
            ints = ()
            if mode == "values" and isinstance(chunk.data, dict):
                ints = tuple(Interrupt(**i) if isinstance(i, dict) else i
                             for i in chunk.data.pop(INTERRUPT, ()))
            yield {"type": mode, "ns": ns, "data": chunk.data, "interrupts": ints}
        elif subgraphs:
            ...
```

⑦ 是**「RemoteGraph 作为节点嵌进父图」时子图穿透的实现**：远程事件被重新打上「调用方 ns + 远程 ns」后塞进父图的同一个流。所以从父图看，远程子图和本地子图**行为一致**。

④⑩ 说明 **wire 上的模式编码方式**：SSE 的 `event:` 字段是 `mode|ns1|ns2`，服务端 `langgraph_api/stream.py` 那边正是用 `f"{mode}|{'|'.join(ns)}"` 生成的——两端严格对称。

### 8.2 `RemoteGraph.astream_events(version="v3")`：适配器

适配器把 SDK 的 `AsyncThreadStream` 伪装成本地 `AsyncGraphRunStream` 的表面（`_remote_run_stream.py:244`）：

### 8.3 三个「本地/远程不一致」的坑

**坑 1：`interrupted` / `interrupts` 是非阻塞快照。** 远程侧的 docstring 明确点出这个差异（`:300`）：

```python
async def interrupted(self) -> bool:
    """Whether the remote run is currently paused at an interrupt.

    Reads the SDK's current value without blocking. This differs from
    local `AsyncGraphRunStream.interrupted()`, which drives the run to
    terminal before returning the flag. Callers that need a
    wait-for-interrupt pattern should drain a projection (e.g.,
    `async for snap in stream._sdk.values`) until the SDK's paused
    sentinel fires, then call this method.
    """
    return self._sdk.interrupted
```

也就是说本地 `await run.interrupted()` 会**驱动到结束**，远程不会。想在远程等中断，得先自己 drain 一个投影。

**坑 2：`lifecycle` 和 `debug` 在远程 `extensions` 里查不到。** `_ProjectionRegistry` 的注释（`:80`）：

```
`lifecycle` is intentionally absent: local derives a status payload from it
rather than yielding `params.data`, and the SDK consumes it as control-plane
(driving `output` / `interrupted`), so its shape can't be matched — it
remains reachable via the raw `events` iterator. `debug` is absent too: it
is not a v3 wire channel.
```

```python
_TYPED = ("values", "messages", "tool_calls", "subgraphs")      # SDK 原生解码
_DECODED = ("updates", "checkpoints", "tasks", "custom")        # 本地用 _ChannelProjection 解码
```

`_ChannelProjection` 复用 SDK 自己的 `DataDecoder`，保证「远程 `run.extensions["updates"]` 迭代出来的 item 形状」与「本地 `UpdatesTransformer` push 的形状」一致。

**坑 3：`Command` 只支持 `resume`。** `_translate_command_input`（`:21`）：

```python
def _translate_command_input(input: Any) -> Any:
    """Translate a local `Command` into the v3 wire `input`, else passthrough.

    The v3 server decides start-vs-resume from thread state (an interrupted
    run or pending interrupts) and, on resume, wraps the whole `input` as
    `{"resume": input}` itself. So a resume `Command` must surface its raw
    `resume` value as the wire `input` (not the serialized dataclass, which
    the server would double-wrap). The v3 `run.start` path has no `goto` /
    `update` channel, so those are rejected.
    """
    if isinstance(input, Command):
        if input.goto or input.update:
            raise NotImplementedError(
                "RemoteGraph v3 streaming supports `Command(resume=...)` only; "
                "`goto` / `update` are not supported by the v3 `run.start` path."
            )
        return input.resume
    return input
```

**服务端会自己包一层 `{"resume": ...}`**，所以客户端必须把 `Command.resume` 的裸值发过去，否则双重包装。

## 9. 流式转换器 StreamTransformer

`StreamTransformer` 是 v3 唯一的官方扩展点。它的定位（`stream/_types.py:44`）：

```python
class StreamTransformer(ABC):
    """Extension point for custom stream projections.

    Transformers observe protocol events flowing through the StreamMux and
    build typed derived projections (StreamChannels, promises, etc.).

    Set `_native = True` on a transformer to have its projection keys
    exposed as direct attributes on the run stream (in addition to
    appearing in `run.extensions`).

    Subclasses must implement `init` and override at least one of
    `process` / `aprocess`. The `finalize` / `afinalize` and `fail` /
    `afail` hooks are optional — the default implementations are no-ops.
    StreamChannel instances in the projection dict are auto-closed /
    auto-failed by the mux, so most transformers don't need `finalize`
    or `fail` at all.
    """
```

### 9.1 四个类变量：声明式配置

```python
requires_async: ClassVar[bool] = False           # 显式声明「我只能在 astream 下跑」
supports_sync: ClassVar[bool] = False            # 我覆写了异步钩子但同时支持同步 lane
required_stream_modes: ClassVar[tuple[str, ...]] = ()   # 我需要图发哪些模式
before_builtins: ClassVar[bool] = False          # 我要在内置 transformer 之前跑
```

`required_stream_modes` 会被 `_collect_stream_modes(mux)` 求并集，直接决定底层 `astream` 的 `stream_mode`。**这是 v3 的性能优化点**：没声明的模式图压根不发。

`before_builtins` 是给**内容改写型** transformer 的钩子（PII 脱敏、敏感词过滤），因为 `MessagesTransformer` 会**急切地**把文本快照进自己的投影。它的 docstring 里有一段非常重要的 **foot-gun 警告**：

> **Foot-gun:** transformers in this lane see `tasks` events before `LifecycleTransformer` and `SubgraphTransformer` consume them — mutating `event["params"]["namespace"]` or the data dict's `id` / `result` / `error` / `interrupts` fields will desync their bookkeeping. Observe freely; mutate only fields no built-in reads (e.g. `delta.text` on `messages` events).

翻译成人话：**你可以随便看，但只能改内置 transformer 不读的字段**（比如 `messages` 事件里的 `delta.text`）。改 namespace 或 tasks 的 `id`/`result`/`error`/`interrupts` 会让子图生命周期记账彻底错乱。

### 9.2 生命周期钩子

| 钩子 | 何时调用 | 返回 |
|---|---|---|
| `init()` | 注册时一次（**抽象方法，必须实现**） | `dict[str, Any]` 投影字典 |
| `_on_register(mux)` | `init()` 之后 | — （需要建子 mux 时捕获 mux 引用） |
| `process(event)` | 同步 lane，每个事件 | `bool`：`True` 保留进主日志，`False` 抑制 |
| `aprocess(event)` | 异步 lane，每个事件 | 同上；**默认委托给 `process`** |
| `finalize()` / `afinalize()` | 正常收尾 | — |
| `fail(err)` / `afail(err)` | 出错收尾 | — |
| `schedule(coro, on_error=)` | 任意时刻 | `asyncio.Task` |

`process` 的默认实现是**抛异常**而不是放行，注释说明了理由：

```python
def process(self, event: ProtocolEvent) -> bool:
    """...The default raises so a missing override fails loudly rather
    than silently passing every event through."""
    raise NotImplementedError(
        f"{type(self).__name__} must override process() or aprocess()"
    )
```

### 9.3 两种异步姿势：`aprocess` vs `schedule`

类注释给出了明确的选型标准：

> Use `aprocess` when the pump must wait for async work before the next transformer sees the event (e.g. PII redaction that mutates `event` in place). Use `schedule()` for decoupled async work whose result lands on an independent projection (e.g. async moderation scoring, cost lookup, external tracing).

即：
- **`aprocess`** = 串行阻塞管线。慢的 `aprocess` 会拖慢整条流水线（「The mux awaits this before dispatching to the next transformer, so a slow `aprocess` serializes the pipeline」）。只在「后续 transformer 或消费者必须看到改写结果」时用。
- **`schedule()`** = fire-and-forget，结果落到独立投影。**不阻塞泵**。

`schedule` 的实现（`:233`）把任务生命周期托管给了 mux：

```python
def schedule(self, coro, *, on_error: Literal["log", "raise"] = "log") -> asyncio.Task[Any]:
    """Schedule a coroutine tied to this transformer's lifecycle.

    The mux holds the task reference, awaits all scheduled tasks
    during `aclose()` before calling `afinalize()`, and cancels
    them on `afail()`. Authors don't need to track tasks or
    implement the last-task-closes-the-log dance.
    """
    try:
        asyncio.get_running_loop()
    except RuntimeError:
        raise RuntimeError(
            f"{type(self).__name__}.schedule() requires a running "
            "event loop; this transformer must run under astream(), "
            "not stream(). Set requires_async=True on the class so "
            "this fails at registration rather than at first event."
        ) from None
    wrapped = self._wrap_scheduled(coro) if on_error == "log" else coro
    task = asyncio.create_task(wrapped)
    tasks = self._scheduled_task_set()
    tasks.add(task)
    task.add_done_callback(tasks.discard)
    return task
```

`on_error="log"`（默认）会把协程异常吃掉只打日志——**一个辅助任务失败不该掀翻整个 run**。

### 9.4 lane 检测：`transformer_requires_async`

```python
def transformer_requires_async(transformer: StreamTransformer) -> bool:
    """Return True if the transformer needs a running event loop."""
    if transformer.requires_async:
        return True
    if transformer.supports_sync:
        return False
    cls = type(transformer)
    for name in ("aprocess", "afinalize", "afail"):
        if getattr(cls, name) is not getattr(StreamTransformer, name):   # ← 反射比较函数对象
            return True
    return False
```

**只要覆写了任一个异步钩子就自动判定为异步 lane**，无需手动声明。`StreamMux._register` 据此在同步 run 下 fail-fast：

```python
if transformer_requires_async(transformer) and not self.is_async:
    raise RuntimeError(
        f"{type(transformer).__name__} requires an async run — "
        "it overrides aprocess/afinalize/afail or sets "
        "requires_async=True. Use astream(), not stream()."
    )
```

注意 `SubgraphTransformer` 同时覆写了 `aprocess`/`afinalize`/`afail` **又**设了 `supports_sync = True`——因为它两条 lane 都实现了，必须在同步 `stream()` 下也能用。这是 `supports_sync` 的教科书用例。

### 9.5 `StreamMux`：管线怎么组装

`_register`（`_mux.py:227`）做四件事：

```python
projection = transformer.init()
if not isinstance(projection, dict):
    raise TypeError(f"StreamTransformer.init() must return a dict, got {type(projection).__name__}")
conflicts = set(projection) & set(self.extensions)
if conflicts:
    attributions = ", ".join(f"{key!r} (owned by {self._projection_owners[key]})" for key in sorted(conflicts))
    raise ValueError(f"Transformer {type(transformer).__name__} returned projection keys that "
                     f"conflict with already-registered keys: {attributions}")     # ← 冲突带归属方
is_native = bool(getattr(transformer, "_native", False))
self._transformers.append(transformer)
self._bind_and_wire(projection, native=is_native)
self.extensions.update(projection)
```

**投影键冲突会报错并告诉你被谁占了**——这个错误信息设计得很友好，避免「我的 `run.values` 怎么没数据」这种盲查。

`_bind_and_wire`（`:464`）决定了 **wire 上的 method 名**：

```python
for value in projection.values():
    if isinstance(value, StreamChannel):
        value._bind(is_async=self.is_async)
        value._bind_mux(self)
        self._channels.append(value)
        if value.name is not None:                                    # ← 具名才上 wire
            method = value.name if native else f"custom:{value.name}" # ← 内置不加前缀，用户加
            value._wire(_make_forward(method))
```

三条规则：
1. **匿名 channel（`StreamChannel()`）= 纯进程内投影**，不上 wire。`MessagesTransformer` / `ValuesTransformer` / `SubgraphTransformer` / `ToolCallTransformer` 都是匿名的——因为它们推的是**活对象**（`ChatModelStream`、`SubgraphRunStream`、`ToolCallStream`），不可序列化。
2. **具名 channel = 自动转发进主日志**，远程客户端也能收到。`LifecycleTransformer` 用 `StreamChannel("lifecycle")` + `_native=True` ⇒ wire method 就叫 `lifecycle`。
3. **用户自定义具名 channel 一律加 `custom:` 前缀** ⇒ 你写 `StreamChannel("progress")`，wire 上是 `custom:progress`，进程内可通过 `run.extensions["progress"]` 拿到（`extensions` 里存的是原始键）。

`_forward`（`:496`）特意**绕过 transformer 管线**：

```python
def _forward(self, method: str, item: Any) -> None:
    """Inject a ProtocolEvent for a StreamChannel push.

    Forwarded events bypass the transformer pipeline to avoid
    infinite recursion (a transformer that pushes to a channel
    during `process()` would re-trigger itself).
    """
```

`push` 里还有一个容易被忽略的顺序细节（`:269`）：

> On the root mux, `seq` is assigned right before an event enters the main log, **not** before the transformer pipeline runs. This ensures that events auto-forwarded from StreamChannels during `process()` get **earlier** seq numbers than the original event, preserving monotonic ordering in the root log.

即：transformer 在 `process()` 里推 channel 产生的转发事件，`seq` 比触发它的原始事件**更小**。这保证了「派生事件排在其因之前」的直觉顺序。

### 9.6 自己写一个 transformer

```python
from langgraph.stream import StreamChannel, StreamTransformer
from langgraph.stream._types import ProtocolEvent


class KeywordAlarmTransformer(StreamTransformer):
    """监听 messages 通道，命中敏感词就往 alarms 投影推一条。

    - 匿名 channel：alarms 只在进程内可见（不上 wire）。
      若要上 wire，改成 StreamChannel("alarms")，method 会变成 "custom:alarms"。
    - required_stream_modes=("messages",)：告诉 mux「让图发 messages 模式」。
      注意 messages 本来就在默认集合里（MessagesTransformer 也声明了），
      这里重复声明是无害的（求并集）。
    - 只覆写 process（同步），所以同步 stream() 和异步 astream() 都能用
      （aprocess 默认委托给 process）。
    """

    _native = True                                  # ← 暴露成 run.alarms 直接属性
    required_stream_modes = ("messages",)

    KEYWORDS = ("口令", "身份证", "银行卡")

    def __init__(self, scope: tuple[str, ...] = ()) -> None:
        super().__init__(scope)                     # ← 必须调，self.scope 由它设置
        self._log: StreamChannel[dict] = StreamChannel()   # 匿名 ⇒ 不上 wire
        self._scope_list = list(scope)

    def init(self) -> dict:
        return {"alarms": self._log}                # 键名 = run.alarms / extensions["alarms"]

    def process(self, event: ProtocolEvent) -> bool:
        if event["method"] != "messages":
            return True                             # 不关我事，放行
        if event["params"]["namespace"] != self._scope_list:
            return True                             # 只看本层（子图的交给子 mux 的同名实例）
        payload, metadata = event["params"]["data"]
        # v3 下 payload 是协议事件 dict；v1 下是 AIMessageChunk —— 两种都兜住
        text = ""
        if isinstance(payload, dict):
            delta = payload.get("delta") or {}
            text = delta.get("text") or ""
        else:
            text = getattr(payload, "content", "") or ""
        for kw in self.KEYWORDS:
            if kw in text:
                self._log.push({
                    "keyword": kw,
                    "node": metadata.get("langgraph_node"),
                    "text": text,
                })
                break
        return True                                 # ← 只观察不改写，原样保留进主日志
```

注册并使用：

```python
# 编译期注册（对所有 run 生效）
graph = builder.compile(transformers=[KeywordAlarmTransformer])

# 或调用点注册（只对本次生效）—— 注意必须传「工厂」，不能传实例
async with await graph.astream_events(
    inp, config, version="v3", transformers=[KeywordAlarmTransformer],
) as run:
    async for alarm in run.alarms:
        print("⚠️ 命中敏感词:", alarm)
```

带参数的工厂写法：

```python
transformers=[lambda scope: KeywordAlarmTransformer(scope)]        # ← scope 由 mux 传入
```

>     )
> ```

> 这两个导入路径都带「内部 API」气味，跨版本升级时可能变动——生产代码里最好包一层 try/except 或在自己的适配模块里集中导入。

## 10. 完整代码示例

以下四个示例都是**可直接运行**的完整脚本。示例 1–3 只需 `langgraph` + 一个可用的 chat model（用 `FakeListChatModel` 可完全离线跑通结构）；示例 4 需要一个跑起来的 LangGraph Server（本项目 `langgraph dev --port 2026` 即可）。

### 示例 1：v2 多模式 + 子图穿透（推荐的生产写法）

```python
"""示例 1：一次运行同时订阅 updates / messages / custom，并穿透子图。

演示要点：
- version="v2" 让输出形状恒为 dict，不用写四套解包逻辑
- subgraphs=True 让子图事件带 ns 冒泡上来
- StreamWriter 发自定义进度
- 子图内部的 LLM token 也会出现在 messages 模式里
"""
from typing import Annotated, TypedDict

from langchain_core.messages import AIMessage, HumanMessage
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langgraph.config import get_stream_writer          # 运行时取 writer（工具/深层函数里最方便）
from langgraph.graph import StateGraph, START, END
from langgraph.types import StreamWriter


# ── 1. 状态定义：messages 用 add_messages reducer 累积 ──────────────
from langgraph.graph.message import add_messages


class State(TypedDict):
    messages: Annotated[list, add_messages]
    result: str


# ── 2. 模型：离线可跑（换成 ChatOpenAI 即为真实流式）───────────────
model = FakeListChatModel(responses=["你好，我是助手。", "子图里的回答。"])


# ── 3. 子图：内部调模型 + 发 custom 进度 ──────────────────────────
def sub_node(state: State, writer: StreamWriter) -> dict:
    """子图节点。writer 形参会被 LangGraph 自动注入。"""
    writer({"stage": "子图开始", "ns": "sub"})       # ← custom 事件（ns 由运行时自动打上）
    answer = model.invoke(state["messages"])          # ← 触发 messages 事件
    writer({"stage": "子图结束", "ns": "sub"})
    return {"messages": [answer], "result": "sub done"}


sub_builder = StateGraph(State)
sub_builder.add_node("sub_node", sub_node)
sub_builder.add_edge(START, "sub_node")
sub_builder.add_edge("sub_node", END)
sub_graph = sub_builder.compile()


# ── 4. 主图：一个节点调用子图（作为节点嵌入 ⇒ 会被穿透）────────────
def main_node(state: State) -> dict:
    # 子图作为节点直接 invoke：主图 stream 时若 subgraphs=True，
    # 子图内部的 messages/custom 事件会带上 ns=("main_node:<task_id>",) 冒泡上来
    out = sub_graph.invoke(state)
    return {"messages": out["messages"], "result": out["result"]}


def progress_node(state: State) -> dict:
    """演示 get_stream_writer()：不靠形参注入也能拿到 writer。"""
    get_stream_writer()({"stage": "主图进度", "pct": 50})
    return {"result": state.get("result", "")}


builder = StateGraph(State)
builder.add_node("main_node", main_node)
builder.add_node("progress_node", progress_node)
builder.add_edge(START, "main_node")
builder.add_edge("main_node", "progress_node")
builder.add_edge("progress_node", END)
graph = builder.compile()


# ── 5. 消费流 ────────────────────────────────────────────────────
async def main() -> None:
    config = {"configurable": {"thread_id": "demo-1"}}
    inp = {"messages": [HumanMessage(content="你好")]}

    # stream_mode 传 list ⇒ 多模式；version="v2" ⇒ 每个 part 都是 dict
    async for part in graph.astream(
        inp,
        config,
        stream_mode=["updates", "messages", "custom"],
        subgraphs=True,          # ← 穿透子图
        version="v2",            # ← 形状恒为 {"type","ns","data"}
    ):
        mode = part["type"]
        ns = part["ns"]           # () 是主图；("main_node:xxx",) 是子图
        depth = "  " * len(ns)    # 用缩进直观表现层级

        if mode == "custom":
            # custom 的 data 就是你传给 writer 的原值
            print(f"{depth}[custom] {part['data']}")

        elif mode == "messages":
            # messages 的 data 恒为二元组 (消息, 元数据)
            msg, meta = part["data"]
            # meta["langgraph_node"] 告诉你这个 token 出自哪个节点
            content = msg.content if isinstance(msg.content, str) else str(msg.content)
            print(f"{depth}[msg:{meta.get('langgraph_node')}] {content!r}")

        elif mode == "updates":
            # updates 的 data 是 {节点名: 该节点返回的更新}
            for node_name, update in part["data"].items():
                print(f"{depth}[update] {node_name} -> {list(update.keys())}")

        # values 模式没订，所以不会收到全量 state 快照（省带宽）

    # 跑完后取最终状态（需要 checkpointer 才有意义）
    print("done")


if __name__ == "__main__":
    import asyncio
    asyncio.run(main())
```

### 示例 2：v3 逐 token + 工具调用 + 子图生命周期（并发消费）

```python
"""示例 2：v3 协议 —— 类型化投影 + take-a-number 泵并发消费。

演示要点：
- async with await graph.astream_events(..., version="v3") as run
- run.messages 拿 ChatModelStream，再 .text / .reasoning / .tool_calls 分投影消费
- ToolCallTransformer 需编译期显式注册，才有 run.tool_calls
- run.lifecycle 是子 agent 生命周期的扁平流
- 用 asyncio.gather 并发消费多个投影（take-a-number 泵支持）
"""
import asyncio
from typing import Annotated, TypedDict

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.tools import tool
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.prebuilt._tool_call_transformer import ToolCallTransformer
from langchain.tools import ToolRuntime          # ← 工具运行时，带 emit_output_delta


class State(TypedDict):
    messages: Annotated[list, add_messages]


# ── 1. 一个会发中间进度的工具 ─────────────────────────────────────
@tool
def slow_lookup(query: str, runtime: ToolRuntime) -> str:
    """查询很慢的东西，过程中会流式吐出进度。"""
    for i in range(3):
        # emit_output_delta 在没订 tools 模式时是静默 no-op，可以无条件写
        runtime.emit_output_delta({"progress": (i + 1) / 3, "msg": f"第{i+1}批"})
    return f"{query} 的结果"


# ── 2. 图：agent 节点 + 工具节点 ──────────────────────────────────
model = FakeListChatModel(responses=["我来查一下。", "查完了，答案是 42。"])


def agent_node(state: State) -> dict:
    return {"messages": [model.invoke(state["messages"])]}


def should_continue(state: State) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END


builder = StateGraph(State)
builder.add_node("agent", agent_node)
builder.add_node("tools", ToolNode([slow_lookup]))
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", should_continue, ["tools", END])
builder.add_edge("tools", "agent")

# ★ 关键：ToolCallTransformer 不是内置默认，必须显式注册才有 run.tool_calls
graph = builder.compile(transformers=[ToolCallTransformer])


# ── 3. 并发消费多个投影 ───────────────────────────────────────────
async def main() -> None:
    config = {"configurable": {"thread_id": "demo-2"}}
    inp = {"messages": [("user", "帮我查一下")]}
    # 注：FakeListChatModel 是结构演示用的假模型，既不会产出 tool_calls，
    #     也不保证实现 content-block 事件生成器（v3 的 run.messages 依赖它）。
    #     真跑请换成 ChatOpenAI / ChatDeepSeek 等真实模型，并：
    #       model = model.bind_tools([slow_lookup])
    #     这样模型发出 tool_call → ToolNode 执行 → tool-started /
    #     tool-output-delta / tool-finished 三类事件才会流进 run.tool_calls。

    # v3 必须先 await 拿到 run，再 async with（__aexit__ 会 abort() 兜底取消）
    async with await graph.astream_events(inp, config, version="v3") as run:

        async def watch_messages() -> None:
            """逐 token 打印模型输出。每次 LLM 调用产生一个 ChatModelStream。"""
            async for stream in run.messages:
                # .text 是 str 增量投影；还有 .reasoning / .tool_calls
                async for delta in stream.text:
                    print(delta, end="", flush=True)
                # 想要完整 AIMessage：await stream.output（会阻塞到该消息结束）
                print()

        async def watch_tools() -> None:
            """工具执行进度。ToolCallStream 直接可迭代 = 迭代 output_deltas。"""
            async for call in run.tool_calls:
                print(f"\n🔧 {call.tool_name}({call.input}) 启动")
                async for delta in call:
                    print(f"   …{delta}")
                print(f"   ✅ output={call.output} error={call.error}")

        async def watch_lifecycle() -> None:
            """子图/子 agent 生命周期（本例没有子图，通常为空）。"""
            async for ev in run.lifecycle:
                print(f"\n🧬 {ev['event']} {ev.get('graph_name')} {ev['namespace']}")

        # take-a-number 泵：多个消费者共享同一个图，各自在自己数据落地时醒
        await asyncio.gather(watch_messages(), watch_tools(), watch_lifecycle())

        # 三个投影都耗尽后，run 已经跑完；取最终状态
        final = await run.output()
        print("\n最终消息数:", len(final["messages"]) if final else None)


if __name__ == "__main__":
    asyncio.run(main())
```

### 示例 3：自定义 transformer + `custom` 模式做业务进度总线

```python
"""示例 3：把散落的 custom 事件聚合成「阶段进度」投影。

场景：本项目式的长任务（解析语义层 → 生成 SQL → 执行 → 出图 → 写报告），
每个阶段由不同节点/工具发 custom 事件，前端只想看「当前阶段 + 百分比」。

演示要点：
- 自定义 StreamTransformer：init() 返回投影、process() 观察 custom 事件
- 具名 channel（"progress"）⇒ 自动转发上 wire，method = "custom:progress"
  （因为 _native=False；设 _native=True 则 method 直接叫 "progress"）
- required_stream_modes=("custom",) ⇒ mux 会自动让图发 custom 模式
- 用 schedule() 做不阻塞泵的异步旁路工作
"""
import asyncio
import time
from typing import Annotated, TypedDict

from langgraph.graph import StateGraph, START, END
# 这些都是 langgraph.stream 的公开导出（见 langgraph/stream/__init__.py 的 __all__）
from langgraph.stream import (
    CustomTransformer,        # 提供 run.custom 原始流；custom 模式不是 v3 默认注册的
    StreamChannel,
    StreamTransformer,
    ProtocolEvent,
)
from langgraph.types import StreamWriter


class State(TypedDict):
    stage: str


class ProgressAggregator(StreamTransformer):
    """把 {"stage": ..., "pct": ...} 形状的 custom 事件聚合成进度快照。"""

    _native = True                             # ⇒ run.progress 直接可访问
    required_stream_modes = ("custom",)        # ⇒ 图会发 custom 模式
    # before_builtins = True                   # 若要改写内容再打开

    def __init__(self, scope: tuple[str, ...] = ()) -> None:
        super().__init__(scope)
        # 具名 channel ⇒ mux 自动转发进主日志（wire method = "custom:progress"）
        self._log: StreamChannel[dict] = StreamChannel("progress")
        self._scope_list = list(scope)
        self._started_at = time.monotonic()

    def init(self) -> dict:
        return {"progress": self._log, "raw_custom": StreamChannel()}  # 匿名 = 纯进程内

    def process(self, event: ProtocolEvent) -> bool:
        if event["method"] != "custom":
            return True
        if event["params"]["namespace"] != self._scope_list:
            return True                        # 只处理本层；子层的由子 mux 处理
        data = event["params"]["data"]
        if not isinstance(data, dict) or "stage" not in data:
            return True                        # 不是我们约定的形状，放行不处理
        snapshot = {
            "stage": data["stage"],
            "pct": data.get("pct"),
            "elapsed_ms": int((time.monotonic() - self._started_at) * 1000),
        }
        self._log.push(snapshot)               # ← 具名 channel：既进投影也上 wire
        return True                            # 原始 custom 事件仍保留在主日志

    def finalize(self) -> None:
        """收尾：推一条终态，让消费者知道进度流结束了。"""
        self._log.push({"stage": "__done__", "pct": 100,
                        "elapsed_ms": int((time.monotonic() - self._started_at) * 1000)})


# ── 业务节点：用 StreamWriter 报进度 ─────────────────────────────
def parse_semantic(state: State, writer: StreamWriter) -> dict:
    writer({"stage": "解析语义层", "pct": 20})
    return {"stage": "parsed"}


def gen_sql(state: State, writer: StreamWriter) -> dict:
    writer({"stage": "生成 SQL", "pct": 50})
    return {"stage": "sql"}


def execute(state: State, writer: StreamWriter) -> dict:
    writer({"stage": "执行查询", "pct": 80})
    return {"stage": "executed"}


builder = StateGraph(State)
builder.add_node("parse_semantic", parse_semantic)
builder.add_node("gen_sql", gen_sql)
builder.add_node("execute", execute)
builder.add_edge(START, "parse_semantic")
builder.add_edge("parse_semantic", "gen_sql")
builder.add_edge("gen_sql", "execute")
builder.add_edge("execute", END)

# 编译期注册：CustomTransformer（拿原始 custom）+ 我们的聚合器
graph = builder.compile(transformers=[CustomTransformer, ProgressAggregator])


async def main() -> None:
    config = {"configurable": {"thread_id": "demo-3"}}

    async with await graph.astream_events({}, config, version="v3") as run:

        async def watch_progress() -> None:
            async for snap in run.progress:
                bar = "█" * int((snap.get("pct") or 0) // 10)
                print(f"\r{bar:<10} {snap['pct']:>3}% {snap['stage']:<12} "
                      f"{snap['elapsed_ms']}ms", end="", flush=True)

        async def watch_raw() -> None:
            # run.custom 是 CustomTransformer 提供的原始流（Any）
            async for item in run.custom:
                pass  # 这里只是演示「原始事件也能同时消费」

        await asyncio.gather(watch_progress(), watch_raw())
        print("\n最终:", await run.output())


if __name__ == "__main__":
    asyncio.run(main())
```

### 示例 4：客户端消费 LangGraph Server 的 SSE 流（本项目生产链路）

```python
"""示例 4：用 langgraph_sdk 直连服务端，复现本项目前端的取流方式。

关键点：
- stream_mode 用 "messages-tuple" 拿**原始增量二元组**（本项目前端走这条）
  用 "messages" 则拿服务端拼好的 messages/partial、messages/complete
- subgraphs=True 才有 ns 信息
- join() 会把 SSE 解析成 (mode, chunk) 元组流
"""
import asyncio

from langgraph_sdk import get_client


async def main() -> None:
    # 本项目：langgraph dev --port 2026（生产是 nginx 入口）
    client = get_client(url="http://localhost:2026")

    # 1) 建线程（或用已有的 thread_id 续聊）
    thread = await client.threads.create()
    thread_id = thread["thread_id"]

    # 2) 发起流式 run
    #    ⚠️ runs.stream() 产出的是 StreamPart(NamedTuple)，字段为
    #       (event: str, data: dict, id: str | None) —— 不是 (mode, chunk) 二元组，
    #       直接 `async for mode, chunk in ...` 会因为字段数不匹配而 ValueError。
    #       默认 version="v1"（原始 SSE 形状）；version="v2" 则产出
    #       StreamPartV2（{"type","ns","data"} 形状），与图层 v2 对齐。
    async for part in client.runs.stream(
        thread_id=thread_id,
        assistant_id="chat_agent",          # ← langgraph.json 里注册的图 id
        input={"messages": [{"role": "user", "content": "各部门人数是多少？"}]},
        config={
            "configurable": {
                "db_name": "wit",           # ← 本项目：前端选库透传（dynamic_prompt 会读它）
                # "user_id": "...",         # ← 多用户隔离需要的身份字段
            }
        },
        # messages-tuple = 原始 (message, metadata) 二元组，前端自己累积
        # 若写 "messages"，服务端会改发 messages/partial（累积态）
        stream_mode=["messages-tuple", "updates", "values", "custom"],
        stream_subgraphs=True,              # ← 让子图事件带 ns 冒泡
        stream_resumable=True,              # ← 断线可重放整条流（长任务强烈建议开）
        on_disconnect="continue",           # ← 默认 cancel：前端切会话会打死 run（项目已知坑）
        version="v1",
    ):
        mode, chunk = part.event, part.data
        # mode 形如 "messages"、"updates"、"values"、"messages|node:task_id"
        if mode == "metadata":
            print("run 元数据:", chunk)      # {"run_id": ..., "attempt": 1}

        elif mode.startswith("messages"):
            # messages-tuple 的 chunk 是 [message_dict, metadata_dict]
            msg, meta = chunk
            content = msg.get("content", "")
            # 增量拼接：同 id 的消息不断累加
            print(f"[{meta.get('langgraph_node')}] +{content!r}", end="", flush=True)

        elif mode == "updates":
            # chunk = {节点名: 更新}；__interrupt__ 键承载 HITL 中断
            if "__interrupt__" in chunk:
                print("\n⏸ 中断:", chunk["__interrupt__"])
            else:
                print("\n📦 节点更新:", list(chunk.keys()))

        elif mode == "values":
            # 全量 state 快照 —— 本项目的进度卡字段就在这里
            for key in ("todos", "query_headers", "subagent_steps_map", "active_queries"):
                if key in chunk:
                    print(f"\n📊 {key} = {chunk[key]}")

        elif mode == "custom":
            print("\n🔔 自定义:", chunk)

        elif mode == "error":
            print("\n❌", chunk)

    # 3) 事后读最终状态（不依赖流）
    state = await client.threads.get_state(thread_id=thread_id)
    print("\n最终消息数:", len(state["values"].get("messages", [])))


if __name__ == "__main__":
    asyncio.run(main())
```

## 11. 项目实战分析：`main_agent.py` 的流式实现

### 11.1 第一个结论：**项目里一行流式代码都没有**

对 `src/` 全量搜索的结果：

```bash
$ grep -rn "stream_mode\|astream(\|get_stream_writer\|StreamWriter" src/
# （零命中）
```

`src/agent/main_agent.py` 全文 286 行，从 `_build_system_prompt()` 到 `create_deep_agent(...)`，**没有任何一处提到 stream**。这不是遗漏，而是**架构决策**：

> 本项目以 `langgraph.json` 注册图、由 **LangGraph Server（`langgraph_api`）托管运行**。流式能力是**服务端运行时**提供的，业务代码只负责「产出一个可被流的图」。

`langgraph.json`：

```json
{
  "graphs": {
    "chat_agent":   { "path": "./src/agent/main_agent.py:agent" },
    "nl2sql_agent": { "path": "./src/agent/graphs/nl2sql_agent.py:agent" }
  },
  "checkpointer": {
    "backend": "custom",
    "path": "./src/agent/checkpoint/checkpointer_factory.py:checkpointer"
  },
  "env": ".env"
}
```

服务端拿到 `agent` 这个 `Runnable` 后，在 `langgraph_api/stream.py:509` 这样调用它：

```python
async with (
    stack,
    aclosing(
        graph.astream(
            input,
            config,
            stream_mode=list(stream_modes_set),     # ← 由 HTTP 请求参数决定，不是业务代码
            output_keys=output_keys,
            **kwargs
        )
    ) as stream,
):
```

`aclosing(...)` 保证客户端断连时**生成器被正确关闭**——这正是第 4.5 节 `abort()` 语义在服务端的对应物（本项目记忆里「切会话会把在跑的 run 打死」`on_disconnect=cancel` 就作用在这一层）。

### 11.2 服务端替项目做了哪些模式决策

`stream.py:206-245` 的归一化逻辑（**每个 run 都会走**）：

```python
stream_mode: list[StreamMode] = kwargs.pop("stream_mode")
# Go 侧会把无法识别的 StreamMode 映射成 unknown，往返后变 None，这里滤掉
stream_mode = [mode for mode in stream_mode if mode is not None]
stream_modes_set: set[StreamMode] = set(stream_mode) - {"events"}
event_streaming_v2_run = bool(configurable.get("__event_streaming_v2"))
is_remote_pregel = isinstance(graph, BaseRemotePregel)
if is_remote_pregel:
    stream_modes_set.discard("tools")        # 远程 pregel 不支持这两个
    stream_modes_set.discard("lifecycle")
if "debug" not in stream_modes_set:
    stream_modes_set.add("debug")            # ★ 总是加 debug（服务端自己要 checkpoint/task_result）
if "messages-tuple" in stream_modes_set and not is_remote_pregel:
    stream_modes_set.remove("messages-tuple")
    stream_modes_set.add("messages")          # ★ messages-tuple 是别名，底层就是 messages
if "updates" not in stream_modes_set and UPDATES_NEEDED_FOR_INTERRUPTS:
    stream_modes_set.add("updates")
    only_interrupt_updates = True             # ★ 加 updates 只为捕获 __interrupt__
else:
    only_interrupt_updates = False
```

三条对理解本项目行为至关重要：

1. **`debug` 永远开着**。服务端要靠 `debug` 里的 `checkpoint` / `task_result` 事件维护线程状态（`:529`）。所以即使前端只请求 `values`，图也会跑 `debug` 模式——这是 2.1 节说的「开 debug 会顺带产出 updates/values」在生产里的实际体现。
2. **`messages-tuple` 就是 `messages`**。前端请求哪个只影响 **wire 形状**，不影响图。`:543` 的分叉：
   ```python
   elif not event_streaming_v2_run and "messages-tuple" in stream_mode:
       if subgraphs and ns:
           yield f"messages|{'|'.join(ns)}", chunk      # ← 带 ns 后缀的事件名
       else:
           yield "messages", chunk                       # ← 原始二元组直发
   elif not event_streaming_v2_run:
       # 请求 "messages" 的客户端：服务端替你累积
       msg_, meta = chunk
       if msg.id in messages:
           messages[msg.id] += msg                       # ← 服务端做 chunk 累加
       else:
           messages[msg.id] = msg
           yield "messages/metadata", {msg.id: {"metadata": meta}}
       yield ("messages/partial" if isinstance(msg, BaseMessageChunk) else "messages/complete"), [...]
   ```
   本项目前端走的是 **`messages-tuple` + SDK 侧累积**（记忆条目「主 agent token 流式链路已通：前端 getter 隐式请求 messages-tuple + 后端归一化 + SDK 逐 token 累积」）。
3. **`updates` 被强制加进来只为中断**。`:598` 那个分支专门把带 `__interrupt__` 的 updates **改名为 `values` 事件**发出去：
   ```python
   elif (mode == "updates" and isinstance(chunk, dict)
         and "__interrupt__" in chunk and len(chunk["__interrupt__"]) > 0
         and only_interrupt_updates):
       yield "values", chunk          # ← 注意：事件名是 values 不是 updates
   ```
   这解释了「前端明明没订 updates，却能收到 HITL 中断」的现象。

另外，`event_streaming_v2_run`（`__event_streaming_v2` configurable）是**新一代 Protocol v2 事件流**的开关。打开后 `messages` 的 wire 形状变成 content-block 事件（第 5.3 节那套），与 v1 完全不兼容——所以源码注释强调「the protocol contract is fixed for the lifetime of the run」，且**故意不在这里重查 feature flag**，避免排队中的 run 被中途降级搞坏正在解析的消费者。本项目当前跑的是 v1 形状。

### 11.3 项目通过哪些「非流式」手段影响流的内容

既然不改流式代码，项目对流的干预全部落在**中间件**上。这里有一个必须搞清的区分：

| 层 | 数据来源 | 受中间件影响吗 |
|---|---|---|
| `messages`（token 流） | 模型 callback 直发（`StreamMessagesHandler.on_llm_new_token`） | ❌ **不受 `wrap_model_call` 后处理影响** |
| `values` / `updates`（state 流） | 节点返回 → channel → checkpoint | ✅ 中间件改的就是这里 |

因为 token 流是**模型输出直接经 callback 冒出**的，而 `wrap_model_call` 类中间件是在模型调用**返回之后**才拿到 `result` 做改写。改写结果进 state，**不会回头改已经吐出去的 token**。

这直接解释了两个项目已知现象：

**① `VfsPathResolverMiddleware`：流里是 VFS 路径，state 里是真实路径。**

该中间件（`src/agent/middlewares/vfs_path_resolver.py`）在 `wrap_model_call` / `awrap_model_call` 里把最终 `AIMessage` 文本中的 `/workspace/report/x.html` 改写成 `D:/workspace1/report/x.html`，且**只改 AIMessage、不碰 ToolMessage 和 tool_call args**、fail-open、幂等。

后果：前端**逐 token 渲染的瞬间**看到的是 `/workspace/...`（token 流已发出），**消息定格后**（从 state / `values` 读）才变成真实路径。`main_agent.py:273` 的注释也点明了它的层次位置：

```python
# vfs_path_resolver 放列表末尾（最内层、紧贴模型）：后处理在 langfuse_span /
# trace_recorder 等外层记录之前完成，保证 trace、checkpoint、前端看到同一份真实路径。
```

「trace、checkpoint、前端看到同一份」——但**流式 token 这一路不在其中**。这是设计上的已知取舍，不是 bug。

**② `MessageSlimmerMiddleware`：截断发生在 state 侧。**

大工具结果（默认 `LARGE_RESULT_TRUNCATE_CHARS=8000`）被截断 + 落盘，图表 iframe 有豁免（`CHART_IFRAME_EXEMPT_MAX_CHARS` 默认 60000，正则 `r"<iframe[^>]*>.*?</iframe>"`）。它改的是**进 checkpoint 的 ToolMessage**，所以影响 `values`/`updates` 流和前端历史回放，**不影响工具执行当时的 token 流**。项目记忆里「大图表被 MessageSlimmer 静默截掉 ⇒ `</iframe>` 消失 ⇒ 聊天里图表全白」正是这条 state 侧链路的故障。

**③ `recursion_limit: 500` 直接决定流何时因 `GraphRecursionError` 断掉。**

```python
agent = create_deep_agent(...).with_config({
    "recursion_limit": 500,
    "callbacks": get_langfuse_callbacks(),
})
```

`astream` 主循环 `while loop.tick()` 耗尽步数时抛 `GraphRecursionError`，服务端把它变成 SSE `error` 事件。deep agent 的「主 agent → 子 agent → 工具 → 再思考」循环很容易吃掉几十上百步，500 是刻意放宽的。

**④ Langfuse callbacks 与流式 handler 共存。**

`get_langfuse_callbacks()` 注入的 handler 和 `StreamMessagesHandler` 一起挂在 `run_manager.inheritable_handlers` 上。两者都设 `run_inline = True` 时按注册顺序就地执行——所以**Langfuse 埋点慢会直接拖慢 token 流**。这是「模型响应正常但前端 token 一顿一顿」的一个可能排查方向。

### 11.4 子 agent 为什么「不流式」——以及项目的补偿方案

`main_agent.py:203`：

```python
nl2sql_async = AsyncSubAgent(
    name="nl2sql",
    description="NL2SQL查询专家",
    graph_id="nl2sql_agent",     # ← 指向 langgraph.json 里注册的另一个图
)
```

`deepagents/middleware/async_subagents.py:286` 的 `start_async_task` 实现：

```python
thread = client.threads.create()                     # ① 新建一个**独立 thread**
run = client.runs.create(                            # ② 新建一个**独立 run**（不是 stream！）
    thread_id=thread["thread_id"],
    assistant_id=spec["graph_id"],                   #    "nl2sql_agent"
    # input=..., config=...（此处省略）
)
task_id = thread["thread_id"]                        # ③ task_id 就是子 thread_id
```

**这三个事实决定了子 agent 的 token 不可能出现在主 run 的流里**：

| 机制 | 是否覆盖 AsyncSubAgent | 原因 |
|---|---|---|
| `subgraphs=True`（v1/v2 穿透） | ❌ | 只穿透**进程内 namespace 嵌套**的子图；这里是另一个 thread + 另一个 run |
| v3 `SubgraphTransformer` | ❌ | 靠 `tasks` 事件发现子图；跨 run 没有对应 tasks 事件 |
| v3 `LifecycleTransformer` | ❌ | 同上，`lc_agent_name` 也无从采集 |
| `RemoteGraph` 转发（8.1 ⑦） | ❌ | 项目用的是 `client.runs.create`，不是把远程图当节点嵌进来 |

所以子 agent 的进度必须**另辟通道**。项目的做法（`src/agent/subagents/sync_launcher.py` + `sync_subagent_todos.py`）：

```
start_async_task 返回
   ↓ sync_launcher monkey-patch 拦到 result（Command.update.async_tasks）
   ↓ launch_sync(main_thread_id, sub_thread_id, agent_name, task_info)
后台守护线程/协程循环：
   client.threads.get_state(thread_id=sub_thread_id)    ← 轮询子 thread 的 state
   ↓ 提取 todos / steps / query_header / 终态
   _sync_update_state(main_thread_id, {"subagent_steps_map": {sub_thread_id: steps}})
   ↓ 内部：client.threads.update_state(..., as_node="__start__")
主 thread 产生新 checkpoint
   ↓
前端 /state 轮询 or values 流读到 → 进度卡刷新
```

这条链路有三个必须知道的性质：

1. **它是「轮询 + 状态回写」，不是流。** 进度刷新频率取决于 sync 循环的轮询间隔，与 token 流式无关。前端看到的「任务卡」是 `MainAgentState` 里那几个按 `task_id` 键控的字段：
   ```python
   query_headers:      Annotated[NotRequired[dict[str, dict]],  _merge_dict_by_key]
   subagent_steps_map: Annotated[NotRequired[dict[str, list]],  _merge_dict_by_key]
   active_queries:     Annotated[NotRequired[dict[str, bool]], _merge_dict_by_key]
   ```
   `_merge_dict_by_key` reducer 是**并发多查询**的关键：各 sync 线程只写自己 `task_id` 的 key，reducer 做合并而非整值替换，避免互相覆盖。
2. **主 run in-flight 期间 `update_state` 会被拒（硬 409）。** 项目记忆里的「async_tasks 写入丢失竞态」正是这个：in-flight run 拒绝 `update_state` 且无重试。所以子 agent 的终态回写有丢失风险，代码里有专门的 P2-4「放手 ≠ 不写了」补偿分支。
3. **`as_node="__start__"` 有幽灵 next 副作用（P2-12）。** `update_state(as_node="__start__")` 会把 `next` 写回入口节点，导致 `state.next` 非空却并不代表真有下一步。别把它当「丢步」查。

### 11.5 主 agent 自己的 token 流式为什么「已通」

主 agent 的模型调用是**进程内**的（`create_deep_agent` 造出来的图直接在服务端进程里跑），所以第 5 章那套 callback 机制完整生效：

```
主 agent 模型 token
  → StreamMessagesHandler.on_llm_new_token
  → stream.put((ns, "messages", (AIMessageChunk, meta)))
  → astream 产出 {"type":"messages","ns":ns,"data":(chunk,meta)}
  → langgraph_api/stream.py:543 分支（前端请求 messages-tuple）
  → yield "messages", chunk
  → SSE: event: messages / data: [...]
  → langgraph_sdk joinStream 解析
  → 前端 useChat 逐 token 累积渲染
```

其中 `subgraphs=True` 时事件名会带 ns 后缀（`f"messages|{'|'.join(ns)}"`）。本项目记忆里「子 agent 不流式」说的就是 11.4 那条独立 run 的路径，与主 agent 这条链路互不相干。

### 11.6 如果要给项目加流式能力，三条可选路径

| 方案 | 改动量 | 收益 | 代价 / 风险 |
|---|---|---|---|
| **A. 加 `custom` 模式进度总线** | 小：在关键节点/工具里 `get_stream_writer()({...})` | 阶段级进度实时推给前端，不必等 sync 轮询 | 前端要新订 `custom` 模式并处理新事件；`get_stream_writer()` 在没订 custom 时是 no-op，**灰度安全** |
| **B. 把 nl2sql 改成进程内子图** | 大：换掉 `AsyncSubAgent`，改用同步 subagent / 直接 `add_node(sub_graph)` | 子 agent token 真正流式；v3 `subgraphs` / `lifecycle` 全部可用 | **失去「可取消的长任务」能力**（`AsyncSubAgent` 的初衷就是支持取消）；主 run 的 `recursion_limit` 压力上升；与现有 `sync_launcher` / `check_progress` / 任务卡机制全部冲突 |
| **C. 用 `RemoteGraph` 包 nl2sql_agent** | 中：`RemoteGraph(graph_id="nl2sql_agent", url=..., assistant_id=...)` 作为节点 | 保留独立 thread/run 的可取消性，同时靠 8.1 ⑦ 的转发让子 agent 事件带 ns 冒泡进主流 | 多一跳 HTTP；`RemoteGraph` 的 `interrupted` 语义与本地不一致（8.3 坑 1）；v3 远程不支持 `transformers` |

**推荐 A**：与项目现有架构（服务端托管、前端订 `values`/`messages-tuple`、进度走 state 回写）**正交**，不触碰已验证的蓝绿发布与任务卡链路，且 `get_stream_writer()` 的 no-op 特性让「先埋点、后开启」成为可能。

| 症状 | 优先排查 | 对应章节 |
|---|---|---|

## 附录：版本与兼容性备忘

- 本文所有源码摘录取自本项目 `.venv` 实际安装版本。**v3（`stream_events(version="v3")`）标注为 `@beta`**，API 可能变动；生产关键路径建议先用 v2（形状稳定、类型完整）。
- v3 的四个内置 transformer（`Values` / `Messages` / `Lifecycle` / `Subgraph`）是硬编码在 `_pregel_stream_v3` / `_apregel_stream_v3` 里的，**无法移除**，只能通过 `before_builtins` 抢在它们之前观察/改写。
- `langgraph.types.StreamMode` 这个 Literal **不含** `tools` / `lifecycle` / `messages-tuple`，但运行时认 `tools`，服务端认全部三个。写类型标注时用 `langgraph_api.schema.StreamMode` 或自己放宽。
- `StreamChannel(maxlen=...)` 参数当前**未实现**（"accepted for forward compatibility; currently unused"），不要指望它做限流。
- 排序永远用 `ProtocolEvent.seq`，不要用 `params.timestamp`（NTP 校时会倒退）。
