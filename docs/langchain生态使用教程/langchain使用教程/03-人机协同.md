## 1. 概述：人机协同的设计理念和适用场景

### 1.1 为什么需要 Human-in-the-Loop（HITL）

Agent 的本质是「模型自主决策 → 调用工具 → 观察结果 → 再决策」的循环。但完全自主的循环在两类场景下不可接受：

1. **高风险操作**：删库、发邮件、转账、执行写 SQL——一旦执行无法回滚，必须有人在执行前把关；
2. **信息缺口**：模型的决策依赖只有人类知道的信息（选哪个主题、发给谁、口径怎么定），需要暂停下来向人提问。

HITL 的核心设计理念是：**把「人的决策」建模为图执行中的一个可持久化暂停点（interrupt），而不是一次同步阻塞调用**。这样：

- 暂停可以持续任意久（几分钟到几天），进程重启也不丢状态（依赖 checkpointer）；
- 人可以做四种决策：**批准（approve）、拒绝（reject）、编辑后执行（edit）、代人回答（respond）**；
- 恢复执行时图从断点继续，而不是从头重跑。

### 1.2 LangChain/LangGraph 生态中的三层实现

| 层次 | 组件 | 角色 |
|------|------|------|
| 底层原语 | `langgraph.types.interrupt()` + `Command(resume=...)` | 在任意节点内暂停图、向客户端抛出载荷、接收恢复值 |
| 预置件 | `ToolNode`（`GraphBubbleUp` 透传）、`create_react_agent`（`interrupt_before/after`） | 让工具执行层与 agent 骨架天然兼容 interrupt |
| 应用层 | `langchain.agents.middleware.HumanInTheLoopMiddleware` | 声明式配置「哪些工具需要审批、允许哪些决策」，封装全部 interrupt 协议细节 |

### 1.3 典型适用场景

- **工具调用审批**：模型要执行 `delete_file` / `run_sql(UPDATE ...)`，先弹卡片让人确认；
- **参数编辑**：模型草拟的邮件收件人不对，人直接改参数后放行；
- **询问用户类工具**：`ask_user` 工具的「真实实现」就是人的回答，工具本身不执行；
- **多步审批流**：一个任务里多个敏感步骤逐一过闸；
- **护栏与合规**：所有出站写操作强制留人工审计痕迹。

## 2. LangGraph interrupt 机制详解

### 2.1 `interrupt()` 函数：可恢复的「抛异常」

`langgraph/types.py` 中的 `interrupt()` 是整个 HITL 体系的基石。先看源码（节选）：

```python
def interrupt(value: Any) -> Any:
    """Interrupt the graph with a resumable exception from within a node.

    在给定节点中，第一次调用该函数会抛出 GraphInterrupt 异常、终止执行，
    传入的 value 会随异常一起浮出给客户端。
    客户端必须用 Command(resume=...) 指定恢复值才能继续执行。
    图会「从节点开头重新执行」——节点内所有逻辑会被重跑！
    如果一个节点里有多个 interrupt 调用，LangGraph 按它们在节点内出现的
    顺序匹配 resume 值（按 task 隔离，不跨 task 共享）。
    使用 interrupt 必须启用 checkpointer。
    """
    conf = get_config()["configurable"]
    scratchpad = conf[CONFIG_KEY_SCRATCHPAD]
    # ① 每个 task 有一个 interrupt 计数器：本节点内第几次 interrupt
    idx = scratchpad.interrupt_counter()
    # ② 已有历史 resume 值（重放场景）→ 直接返回对应位置的值，不再抛异常
    if scratchpad.resume:
        if idx < len(scratchpad.resume):
            conf[CONFIG_KEY_SEND]([(RESUME, scratchpad.resume)])
            return scratchpad.resume[idx]
    # ③ 本次恢复带来的新 resume 值 → 追加进列表并返回
    v = scratchpad.get_null_resume(True)
    if v is not None:
        assert len(scratchpad.resume) == idx, (scratchpad.resume, idx)
        scratchpad.resume.append(v)
        conf[CONFIG_KEY_SEND]([(RESUME, scratchpad.resume)])
        return v
    # ④ 没有 resume 值 → 抛 GraphInterrupt，图暂停，value 浮出给客户端
    raise GraphInterrupt(
        (Interrupt.from_ns(value=value, ns=conf[CONFIG_KEY_CHECKPOINT_NS]),)
    )
```

**逐段解析这套「重放式恢复」语义：**

1. **第一次执行到 `interrupt()`**：scratchpad 里没有 resume 值 → 走分支④抛 `GraphInterrupt`。这是一个特殊控制流异常（`GraphBubbleUp` 家族），LangGraph 运行时捕获它、把当前状态写进 checkpointer、把 `Interrupt(value=..., id=...)` 通过 `__interrupt__` 通道浮出给客户端。
2. **客户端用 `Command(resume=X)` 恢复**：图**从该节点的开头重新执行**。前面已恢复过的 `interrupt()` 调用走分支②直接返回历史 resume 值（这就是「重放」）；执行到本次待恢复的那个 `interrupt()` 时走分支③，返回 `X`。
3. **推论（重要！）**：`interrupt()` 之前的节点代码会被执行两遍（甚至 N 遍）。因此 **interrupt 之前不要放有副作用的操作**（写库、发请求）；副作用应放在 interrupt 之后，或者依赖节点内幂等。

### 2.2 `Interrupt` 类型

```python
@final
@dataclass(init=False, slots=True)
class Interrupt:
    value: Any   # interrupt() 传入的载荷（审批卡内容、问题文本等）
    id: str      # interrupt 的 ID，可用于定向恢复（xxh3_128(命名空间) 生成）
```

`id` 由 checkpoint 命名空间哈希而来，同一暂停点的 id 稳定，支持 `Command(resume={id: value})` 形式的**按 id 定向恢复**（多个并行 interrupt 时有用）。

### 2.3 `Command`：恢复与状态更新的统一原语

```python
@dataclass
class Command(Generic[N], ToolOutputMixin):
    graph: str | None = None      # None=当前图；Command.PARENT=最近的父图
    update: Any | None = None     # 对图状态的更新（配合 update_state 语义）
    resume: dict[str, Any] | Any | None = None
    # resume 两种形态：
    #   - {interrupt_id: value, ...}  按 id 定向恢复多个 interrupt
    #   - 单个值                       恢复「下一个」interrupt
    goto: Send | Sequence[Send | N] | N = ()   # 跳转到指定节点
```

恢复一个暂停的图：`graph.invoke(Command(resume=值), config)` 或 `graph.stream(Command(resume=值), config)`，config 里必须带同一个 `thread_id`。

### 2.4 客户端如何感知 interrupt

- `graph.invoke(...)` 的返回值里带 `__interrupt__` 键（tuple of `Interrupt`）；新版 `invoke(..., version="v2")` 返回的 `GraphOutput` 对象直接有 `.interrupts` 属性；
- `graph.stream(...)` 会产出 `{'__interrupt__': (Interrupt(...),)}` chunk；
- **通过 LangGraph Server（HTTP API）时**：`GET /threads/{tid}/state` 的 `tasks[].interrupts` 里能看到待处理 interrupt——注意顶层图可能把子图的 interrupt「吞掉」不在 `__interrupt__` 顶层展示，**可靠做法是遍历 `state.tasks[].interrupts`**（本项目就踩过这个坑，见第 12 章）。

`StateSnapshot` 中的相关字段（`types.py`）：

```python
class StateSnapshot(NamedTuple):
    values: dict[str, Any] | Any    # 当前通道值
    next: tuple[str, ...]           # 下一步要执行的节点
    tasks: tuple[PregelTask, ...]   # 每个 task 携带 interrupts
    interrupts: tuple[Interrupt, ...]  # 本步待解决的 interrupt
```

### 2.5 旧版 `langgraph/prebuilt/interrupt.py`：已废弃的通用 HITL 协议

该文件定义了一套**与工具无关**的通用人工介入协议，现已全部标记 `@deprecated`，迁移到 `langchain.agents.interrupt`：

```python
class HumanInterruptConfig(TypedDict):
    allow_ignore: bool    # 允许忽略/跳过本步
    allow_respond: bool   # 允许文本反馈
    allow_edit: bool      # 允许编辑内容/状态
    allow_accept: bool    # 允许直接接受

class HumanInterrupt(TypedDict):
    action_request: ActionRequest          # {action: "run_command", args: {...}}
    config: HumanInterruptConfig           # 允许哪些交互
    description: str | None                # 给人看的说明

class HumanResponse(TypedDict):
    type: Literal["accept", "ignore", "response", "edit"]
    args: None | str | ActionRequest       # accept/ignore→None；response→str；edit→新 ActionRequest
```

用法是 `response = interrupt([request])[0]`，恢复时传 `Command(resume=[{"type": "accept", "args": None}])`。它和 langchain 1.x 的 `HumanInTheLoopMiddleware` 是两代协议：**旧协议按「交互能力开关」（allow_*）描述，新协议按「决策类型」（approve/edit/reject/respond）描述**。新项目应直接用 `HumanInTheLoopMiddleware`。

### 2.6 `interrupt_before` / `interrupt_after`：静态断点

除了动态 `interrupt()`，编译期还能声明静态断点：

```python
graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["tools"],   # 执行 tools 节点「前」暂停
    interrupt_after=["agent"],    # 执行 agent 节点「后」暂停
)
```

静态断点**不需要** resume 值——用 `graph.invoke(None, config)` 就能继续。适合「每次进工具节点前都停一下」的粗粒度控制；缺点是停在哪、为什么停、载荷是什么都不如 `interrupt()` 灵活。

## 3. HumanInTheLoopMiddleware 详解

`langchain/agents/middleware/human_in_the_loop.py` 是 langchain 1.x `create_agent` 体系下的官方 HITL 中间件，把第 2 章的底层原语封装成声明式配置。

### 3.1 核心数据结构

```python
class ActionRequest(TypedDict):
    name: str                     # 待审批的工具名，如 "send_email_tool"
    args: dict[str, Any]          # 工具参数
    description: NotRequired[str] # 给人看的描述（审批卡片文案）

class ReviewConfig(TypedDict):
    action_name: str
    allowed_decisions: list[DecisionType]   # 本工具允许的决策集合
    args_schema: NotRequired[dict[str, Any]] # 允许 edit 时的参数 JSON Schema

# 一次 interrupt 抛给客户端的完整载荷
class HITLRequest(TypedDict):
    action_requests: list[ActionRequest]    # 可能一次多个工具调用
    review_configs: list[ReviewConfig]

DecisionType = Literal["approve", "edit", "reject", "respond"]

class HITLResponse(TypedDict):
    decisions: list[Decision]     # 恢复值的结构：{"decisions": [...]}
```

四种决策的载荷：

```python
class ApproveDecision(TypedDict):
    type: Literal["approve"]                      # 原样执行

class EditDecision(TypedDict):
    type: Literal["edit"]
    edited_action: Action                         # {"name": ..., "args": {...}} 改后执行

class RejectDecision(TypedDict):
    type: Literal["reject"]
    message: NotRequired[str]                     # 拒绝理由 → 反馈给模型

class RespondDecision(TypedDict):
    type: Literal["respond"]
    message: str                                  # 人代替工具回答 → 直接成为 ToolMessage
```

### 3.2 配置：`interrupt_on`

```python
class InterruptOnConfig(TypedDict):
    allowed_decisions: list[DecisionType]
    description: NotRequired[str | _DescriptionFactory]  # 静态文案或动态生成函数
    args_schema: NotRequired[dict[str, Any]]
    when: NotRequired[Callable[[ToolCallRequest], bool]] # 条件断言：True 才 interrupt
```

`__init__` 的归一化逻辑（源码摘录）：

```python
def __init__(self, interrupt_on: dict[str, bool | InterruptOnConfig], *,
             description_prefix: str = "Tool execution requires approval") -> None:
    resolved_configs: dict[str, InterruptOnConfig] = {}
    for tool_name, tool_config in interrupt_on.items():
        if isinstance(tool_config, bool):
            if tool_config is True:   # True = 放开全部四种决策
                resolved_configs[tool_name] = InterruptOnConfig(
                    allowed_decisions=["approve", "edit", "reject", "respond"])
            # False = 自动放行，不进 resolved_configs
        elif tool_config.get("allowed_decisions"):
            resolved_configs[tool_name] = tool_config
```

要点：
- **没有出现在 `interrupt_on` 里的工具默认自动放行**（白名单式审批）；
- `True` 是「四种决策全允许」的语法糖；
- `when` 谓词支持按参数动态决定是否拦截（例如只拦 `path` 以 `/etc` 开头的 `delete_file`）。注意 `when` 在 batch 模式下拿到的 `request.tool` 是 `None`，不能依赖它。

### 3.3 主流程：`after_model` 钩子

中间件挂在 **`after_model`** 阶段——模型产出 `AIMessage`（含 tool_calls）之后、工具真正执行之前：

```python
def after_model(self, state, runtime):
    # ① 找最后一条 AIMessage，没有 tool_calls 就直接返回
    last_ai_msg = next((m for m in reversed(state["messages"])
                        if isinstance(m, AIMessage)), None)
    if not last_ai_msg or not last_ai_msg.tool_calls:
        return None

    # ② 遍历 tool_calls，挑出命中 interrupt_on 且 when 谓词放行的
    for idx, tool_call in enumerate(last_ai_msg.tool_calls):
        if (config := self.interrupt_on.get(tool_call["name"])) is not None:
            if not self._should_interrupt(tool_call, config, state, runtime):
                continue
            action_request, review_config = self._create_action_and_config(...)
            ...
    if not action_requests:
        return None                       # 全被自动放行 → 不打断

    # ③ 关键一步：一次 interrupt 打包「本轮全部待审批工具」
    hitl_request = HITLRequest(action_requests=..., review_configs=...)
    decisions = interrupt(hitl_request)["decisions"]   # ← 图在这里暂停！

    # ④ 校验决策数与待审批工具数一致（顺序一一对应）
    if len(decisions) != len(interrupt_indices):
        raise ValueError(...)

    # ⑤ 逐个应用决策，按原顺序重建 tool_calls
    for idx, tool_call in enumerate(last_ai_msg.tool_calls):
        if idx in interrupt_indices:
            revised_tool_call, tool_message = self._process_decision(
                decisions[decision_idx], tool_call, config)
            ...
        else:
            revised_tool_calls.append(tool_call)   # 自动放行的原样保留

    # ⑥ 就地改写 AIMessage 的 tool_calls，并可能追加人造 ToolMessage
    last_ai_msg.tool_calls = revised_tool_calls
    return {"messages": [last_ai_msg, *artificial_tool_messages]}
```

### 3.4 决策落地：`_process_decision`

```python
if decision["type"] == "approve" and "approve" in allowed_decisions:
    return tool_call, None                    # 原 tool_call 保留，正常执行

if decision["type"] == "edit" and "edit" in allowed_decisions:
    edited_action = decision["edited_action"]
    return (ToolCall(type="tool_call",
                     name=edited_action["name"],     # 甚至可以改成别的工具！
                     args=edited_action["args"],
                     id=tool_call["id"]),            # id 保持不变
            None)

if decision["type"] == "reject" and "reject" in allowed_decisions:
    content = decision.get("message") or (
        f"User rejected the tool call for `{tool_call['name']}` ... "
        "Do not retry this tool call unless the user explicitly requests it.")
    tool_message = ToolMessage(content=content, name=..., tool_call_id=...,
                               status="error")       # ← 错误态 ToolMessage
    return tool_call, tool_message

if decision["type"] == "respond" and "respond" in allowed_decisions:
    tool_message = ToolMessage(content=decision["message"], ...,
                               status="success")     # ← 成功态、人代答
    return tool_call, tool_message                   # 工具本身不执行
```

三种「不执行原调用」的处理方式对比：

| 决策 | 工具是否执行 | 模型看到什么 |
|------|------------|-------------|
| approve | ✅ 原参数执行 | 真实工具结果 |
| edit | ✅ **改后参数**执行 | 改后调用的工具结果 |
| reject | ❌ | `status="error"` 的 ToolMessage（默认文案明确告诉模型「别重试」） |
| respond | ❌ | `status="success"` 的 ToolMessage，内容就是人写的 `message` |

注意 reject/respond 场景下 `revised_tool_call` 仍保留在 `AIMessage.tool_calls` 里——因为每个 tool_call **必须**有配对的 ToolMessage，否则下一次调模型会 400（OpenAI 协议约束）。中间件用「人造 ToolMessage」补上配对。

## 4. ToolNode 中的 interrupt 集成

`langgraph/prebuilt/tool_node.py` 本身不发起审批 interrupt（那是中间件的事），但它必须**保证 interrupt 异常能穿透工具执行层**，否则 HITL 会被错误处理逻辑吞掉。

### 4.1 `GraphBubbleUp` 永远透传

`_execute_tool_sync`（异步版同理）的错误处理里有一段关键注释与代码：

```python
try:
    response = tool.invoke(call_args, config)
    ...
# GraphInterrupt 是一种永远会被重新抛出的特殊异常。触发场景：
# (1) 工具函数内部直接调用了 interrupt()
# (2) 「图被当作工具调用」时，图内节点抛出了 GraphInterrupt
# (3) 子图在作为工具的图内被 interrupt
# （2、3 常见于 supervisor-with-tools 多 agent 架构）
except GraphBubbleUp:
    raise                       # ← 不进错误处理，原样上抛
except Exception as e:
    # 其余异常按 handle_tool_errors 配置转成 status="error" 的 ToolMessage
    ...
```

**解析**：`GraphInterrupt` 继承自 `GraphBubbleUp`。如果没有这条 `except GraphBubbleUp: raise`，工具内/子图内的 `interrupt()` 会被 `handle_tool_errors=True` 的默认兜底转成一条错误 ToolMessage——图不会暂停，人会永远等不到审批卡。这是把「图当工具」嵌套时 HITL 失效的最常见根因。

### 4.2 v2 的 Send 分发与长时间暂停

```python
class ToolCallWithContext(TypedDict):
    """内部数据结构：让 ToolNode 接受用 Send API 分发、带额外上下文的 tool call。

    create_agent 用 Send API 把多个 tool call 分发成并行的 ToolNode 实例，
    以支持「图执行可能被无限期暂停」的 human-in-the-loop 工作流。
    """
    tool_call: ToolCall
    __type: Literal["tool_call_with_context"]
    state: Any
```

`create_react_agent(version="v2")` / `create_agent` 中，**每个 tool call 是一个独立 task**（Send 分发）。配合第 2 章「resume 值按 task 隔离」的语义，好处是：某个工具在函数体内 `interrupt()` 时，只有那个 task 暂停重放，其它并行工具的 task 结果已经 checkpoint，不会被重跑。

### 4.3 `wrap_tool_call`：工具边界的确定性拦截

`ToolNode._run_one` 中，如果配置了 wrapper，会先构造 `ToolCallRequest` 交给 wrapper：

```python
tool_request = ToolCallRequest(tool_call=call, tool=tool,
                               state=tool_runtime.state, runtime=tool_runtime)
if self._wrap_tool_call is None:
    return self._execute_tool_sync(tool_request, input_type, config)
def execute(req):
    return self._execute_tool_sync(req, input_type, config)
# wrapper 可以：直接执行 execute(request)、改 request 再执行、
# 或完全短路——不调 execute，直接返回自己的 ToolMessage
```

「短路返回」正是本项目 `SqlReadOnlyMiddleware` 的用法（第 12 章）：**不需要人参与的确定性策略，用 `wrap_tool_call` 拦截比 interrupt 审批更合适**——不暂停、不等人、无 checkpointer 依赖。

### 4.4 `ValidationNode`（tool_validator.py）：审批前的「机器预审」

`langgraph/prebuilt/tool_validator.py` 的 `ValidationNode` 已标记废弃（推荐 `create_agent` + 自定义工具错误处理），但其思想值得借鉴：它**不执行工具**，只把 `AIMessage.tool_calls` 的参数用 pydantic schema 校验一遍，合法则回放序列化结果、非法则返回带 `is_error` 的 ToolMessage 让模型修正。

在 HITL 流程里，这类「机器可判」的校验应该放在 interrupt **之前**：先用 schema/规则把明显非法的调用打回给模型，只把「机器判不了、需要人拍板」的调用送到审批卡——减少人的审批负担，也避免人被无效请求打扰。

### 4.5 `langgraph/graph/ui.py`：把审批卡渲染成生成式 UI

interrupt 的 `value` 只是数据；前端如何呈现可以用 `push_ui_message` 推送生成式 UI 组件：

```python
from langgraph.graph.ui import push_ui_message

def approval_node(state):
    # 推一个前端组件（如 <tool-approval-card>），props 是组件入参
    push_ui_message(
        name="tool-approval-card",
        props={"tool": "run_sql", "sql": state["pending_sql"]},
        state_key="ui",      # 同时写进图状态的 "ui" 通道（配 ui_message_reducer）
    )
    decision = interrupt({"question": "是否执行该 SQL？"})
    ...
```

`push_ui_message` 做两件事：① 通过 `get_stream_writer()` 把 `{"type":"ui", id, name, props, metadata}` 事件写进 custom 流（前端 `stream_mode="custom"` 实时收到）；② 通过 `CONFIG_KEY_SEND` 把同一事件写进图状态的 `ui` 键（用 `ui_message_reducer` 归并，支持按 id 更新/删除、`merge=True` 增量合并 props）。这样**刷新页面后审批卡仍能从状态里恢复渲染**——对可能暂停数天的 HITL 场景很重要。

## 5. create_react_agent 中的 checkpointer 与 interrupt 配合

`langgraph/prebuilt/chat_agent_executor.py` 的 `create_react_agent`（现已废弃，等价物是 `langchain.agents.create_agent`）签名中与 HITL 直接相关的参数：

```python
def create_react_agent(
    model, tools, *,
    checkpointer: Checkpointer | None = None,
    # ↑ 持久化图状态（单线程=单会话）。interrupt 能跨进程恢复全靠它。
    interrupt_before: list[str] | None = None,
    # ↑ 可选节点名："agent" 或 "tools"。在节点执行「前」暂停。
    #   文档原话：适合在采取行动前加用户确认。
    interrupt_after: list[str] | None = None,
    # ↑ 在节点执行「后」暂停。适合直接返回或做后处理。
    post_model_hook: RunnableLike | None = None,
    # ↑ agent 节点（调 LLM）之后的钩子，文档原话：
    #   "Useful for implementing human-in-the-loop, guardrails, validation"
    ...
)
```

三者最终都传给 `builder.compile(checkpointer=..., interrupt_before=..., interrupt_after=...)`。

**硬性约束：`interrupt()` 必须搭配 checkpointer。** 原因见第 2 章的重放语义——暂停时整个图状态（含 scratchpad 里的 resume 列表）要落盘；恢复时按 `thread_id` 取回、从节点头重放。没有 checkpointer，`interrupt()` 抛出的 `GraphInterrupt` 无人善后，直接变成运行错误。

选择建议：
- 开发/测试：`InMemorySaver`（进程内，重启即丢）；
- 生产：`PostgresSaver` / `AsyncPostgresSaver` / `SqliteSaver` 等持久实现。本项目生产环境即使用平台库持久化 run 状态，配合 LangGraph Server 的 `/threads/{tid}/state` 观测断点。

`post_model_hook` 与 `HumanInTheLoopMiddleware` 的关系：中间件的 `after_model` 本质上就是被编排进图的 post-model 阶段节点。用 `create_agent` + 中间件是声明式做法；用 `post_model_hook` 手写一个调 `interrupt()` 的节点是命令式做法，二者选一即可。

## 6. 审批模式（Approve / Reject）实现

最小可用的审批闭环分四步：**配置 → 触发 → 读取 → 恢复**。

```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

# ── 第 1 步：声明哪些工具需要审批 ─────────────────────────
agent = create_agent(
    model="openai:gpt-4o",
    tools=[dangerous_delete_tool, safe_read_tool],
    checkpointer=InMemorySaver(),          # interrupt 的前提条件！
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                # 只允许 approve / reject 两种决策（不给编辑权）
                "dangerous_delete_tool": {
                    "allowed_decisions": ["approve", "reject"],
                    "description": "模型请求删除数据，请人工确认",
                },
                # safe_read_tool 不配置 = 自动放行
            },
        ),
    ],
)

config = {"configurable": {"thread_id": "demo-thread"}}

# ── 第 2 步：正常调用；命中审批工具时图会暂停 ─────────────
result = agent.invoke(
    {"messages": [{"role": "user", "content": "把过期的订单删掉"}]},
    config=config,
)
# result["__interrupt__"] = (Interrupt(value={
#     "action_requests": [{"name": "dangerous_delete_tool",
#                          "args": {...}, "description": "..."}],
#     "review_configs": [{"action_name": "dangerous_delete_tool",
#                         "allowed_decisions": ["approve", "reject"]}],
# }),)

# ── 第 3 步：把 interrupt 载荷渲染给人（此处从简） ────────
intr = result["__interrupt__"][0]
print("待审批:", intr.value["action_requests"])

# ── 第 4 步：按人的决定恢复 ───────────────────────────────
# 批准 → 工具按原参数执行，循环继续
agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), config)

# 或拒绝 → 工具不执行；模型收到 status="error" 的 ToolMessage
# message 是给人写的拒绝理由，会原样进入模型上下文引导它改道
agent.invoke(
    Command(resume={"decisions": [
        {"type": "reject", "message": "生产库禁止删单，请改为打归档标记"}
    ]}),
    config,
)
```

**Reject 的默认文案值得注意**（源码）：不传 `message` 时，模型收到的是——

> "User rejected the tool call for `X` with id Y. The tool was not executed. Do not retry this tool call unless the user explicitly requests it."

明确指示「不要重试」，防止模型把 reject 当瞬时错误反复撞墙。如果你的业务希望模型换条路走，**一定要传自定义 `message` 说明替代方案**。

## 7. 编辑模式（Edit tool arguments）实现

编辑模式让人在不打断任务的前提下修正模型的参数错误：

```python
# 配置时放开 edit 决策
HumanInTheLoopMiddleware(
    interrupt_on={
        "send_email_tool": {
            "allowed_decisions": ["approve", "edit", "reject"],
            # args_schema 可选：给前端渲染参数编辑表单用（JSON Schema）
        },
    },
)

# 模型想发：send_email_tool(to="all@company.com", subject="裁员名单")
# 人审查后觉得收件人太广、主题不妥 → edit 改参放行：
agent.invoke(
    Command(resume={"decisions": [
        {
            "type": "edit",
            "edited_action": {
                "name": "send_email_tool",        # 通常与原工具同名
                "args": {                          # ← 完整的新参数集
                    "to": "hr-lead@company.com",
                    "subject": "组织架构调整通知（草稿）",
                },
            },
        }
    ]}),
    config,
)
```

源码行为（`_process_decision`）：中间件用 `edited_action` 的 `name`/`args` **重建 ToolCall，但保留原 `id`**——消息配对关系不断裂；随后工具以新参数执行，模型看到的是改后调用的结果，它并不知道参数被人动过（如需让模型知情，可结合 reject+message 或在 description 里约定）。

两个易错点：
1. `edited_action.args` 是**整体替换**，不是增量 patch——必须给出完整参数集；
2. resume 结构里编辑内容放在 `edited_action` 子对象，**不是**平铺在 decision 顶层。

## 8. 输入模式（Request human input / respond）实现

`respond` 决策面向「ask user 型工具」：工具的存在只是为了让模型有个合法的提问出口，**真实实现就是人的回答**。

```python
from langchain_core.tools import tool

@tool
def ask_user(question: str) -> str:
    """当缺少关键业务信息时，用这个工具向用户提问。"""
    # 函数体永远不会被执行——respond 决策直接短路它
    raise NotImplementedError("由人类回答")

HumanInTheLoopMiddleware(
    interrupt_on={
        "ask_user": {"allowed_decisions": ["respond"]},  # 只允许代答
    },
)

# 模型调用 ask_user(question="报表用蓝色还是红色主题？") → 图暂停
# 人在输入框里写下答案，以 respond 恢复：
agent.invoke(
    Command(resume={"decisions": [
        {"type": "respond", "message": "用蓝色主题，标题加粗"}
    ]}),
    config,
)
# 效果：工具「没有执行」，但模型收到一条
#   ToolMessage(content="用蓝色主题，标题加粗", status="success")
# 对模型而言与工具正常返回无异，循环无缝继续。
```

与 reject 的区别：reject 产生 `status="error"`（模型理解为「此路不通」），respond 产生 `status="success"`（模型理解为「工具给出了答案」）。

如果不想定义假工具，也可以**在任意自定义节点里直接 `interrupt("请补充XX信息")`**——这就是第 2 章的原语用法，恢复值就是 `interrupt()` 的返回值：

```python
def collect_requirements(state):
    # 载荷可以是任意可序列化对象；这里直接用一个问题字符串
    answer = interrupt("请提供报表的统计口径（自然月还是财务月）？")
    return {"caliber": answer}

graph.invoke(Command(resume="财务月"), config)   # collect_requirements 里 answer = "财务月"
```

## 9. update_state() 与 resume 机制

恢复一个暂停的图有**两条路径**，语义不同：

### 9.1 `Command(resume=...)`：沿着断点继续（推荐）

```python
graph.invoke(Command(resume=值), config)
```

- 图**从被 interrupt 的节点开头重放**，`interrupt()` 返回「值」；
- 节点内 interrupt 之前的代码会再次执行（副作用警告见 2.1）；
- 这是 HITL 审批的标准恢复方式，中间件的决策协议完全建立在它之上。

`Command` 还可以同时携带状态更新与跳转：

```python
Command(
    resume={"decisions": [...]},       # 恢复 interrupt
    # update=... 与 goto=... 在恢复场景一般不用，
    # 但 Command 作为工具返回值时可以更新状态/跳转节点
)
```

### 9.2 `graph.update_state(...)`：改写历史再分叉

```python
graph.update_state(
    config,
    {"messages": [HumanMessage(content="算了，别删了")]},  # 状态增量
    as_node="human",     # 假装这次更新是 "human" 节点写出来的
)
graph.invoke(None, config)   # 传 None 表示「不带新输入，从当前状态继续」
```

- `update_state` 会在 checkpoint 历史上**追加一个新分叉**，然后 `invoke(None, ...)` 让图从该分叉继续；
- 经典用法是「静态断点 + 人工改状态」：`interrupt_before=["tools"]` 暂停后，人用 `update_state` 直接改写 `messages` 里最后一条 AIMessage 的 tool_calls（改参数、删调用），再继续；
- ⚠️ 已知陷阱：`update_state(as_node="__start__")` 会把 `next` 写回入口节点，造成「幽灵 next」；对 in-flight 的 run 调 `update_state` 会被拒绝且无重试（写入丢失竞态）。**审批恢复优先用 `Command(resume=...)`，不要混用 update_state。**

### 9.3 二者对比

| | `Command(resume=...)` | `update_state()` + `invoke(None)` |
|---|---|---|
| 配合 | 动态 `interrupt()` | 静态 `interrupt_before/after` 或任意改写 |
| 语义 | 提供 interrupt 的返回值，重放节点 | 伪造一次状态写入，产生新分叉 |
| 典型场景 | 审批/编辑/代答 | 人工纠正消息历史、时间旅行调试 |
| 风险 | 节点前段代码重复执行 | as_node 用错产生幽灵 next；in-flight 写入竞态 |

## 10. 多步审批流程设计

一次任务里多个环节都要过人时，有三种设计：

### 10.1 单节点打包审批（HumanInTheLoopMiddleware 默认行为）

模型一轮产出 N 个待审批 tool_calls → **一次 interrupt 打包全部**（`HITLRequest.action_requests` 是列表）→ 人一次给 N 个 decisions（顺序必须与 action_requests 一一对应，数量不符直接 `ValueError`）。适合「一轮并行工具调用一起批」。

### 10.2 串行多断点：一个节点多个 interrupt

```python
def deploy_pipeline(state):
    # 断点 1：批配置变更
    d1 = interrupt({"step": "config", "diff": state["config_diff"]})
    if d1["type"] != "approve":
        return {"deploy_result": "cancelled at config"}
    apply_config(state["config_diff"])          # 副作用放在 interrupt 之后！

    # 断点 2：批数据库迁移
    d2 = interrupt({"step": "migrate", "sql": state["migrations"]})
    if d2["type"] != "approve":
        return {"deploy_result": "cancelled at migrate"}
    run_migrations(state["migrations"])

    return {"deploy_result": "ok"}
```

恢复时按顺序逐个来：第一次 `Command(resume={"type":"approve"})` 过断点 1（重放时断点 1 直接返回历史值、走到断点 2 再次暂停），第二次 resume 过断点 2。**匹配规则是「按节点内出现顺序」**（2.1 的 scratchpad 计数器），所以不要在 interrupt 前放条件分支改变 interrupt 的调用次序，否则重放时 resume 值会错位。

### 10.3 每步一个审批节点：显式状态机

审批环节多、且每步之间有独立的业务逻辑时，把每个审批建成图节点更清晰：

```
START → plan → approve_plan → execute_step → approve_step → … → finalize → END
                    │(reject)                      │(reject)
                    └────────→ replan ←────────────┘
```

每个 `approve_*` 节点内部一次 `interrupt()`，reject 分支用条件边路由回 `replan`。好处：checkpoint 粒度细、每步可独立观测/重试、前端可按节点名渲染不同审批卡。

### 10.4 设计守则

1. **能机器判的不要给人判**：schema 校验、只读/写分类、黑白名单放 `wrap_tool_call` / `ValidationNode` 式预审，人只处理真正需要裁量的请求；
2. **interrupt 前零副作用**：重放语义决定了一切写操作必须在 interrupt 返回之后；
3. **决策协议要校验数量与顺序**：decisions 与 action_requests 一一对应；
4. **给 reject 附理由**：引导模型改道而非重试；
5. **审批卡要可恢复渲染**：结合 `push_ui_message` 写入状态，前端刷新/换设备后仍能看到待办。

## 11. 完整代码示例

### 场景一：工具调用审批（approve / reject 闭环）

```python
"""场景一：删除文件工具的审批闭环。"""
import uuid
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langchain_core.tools import tool
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

@tool
def delete_file(path: str) -> str:
    """删除指定路径的文件（危险操作）。"""
    return f"deleted {path}"

@tool
def list_files(directory: str) -> str:
    """列出目录内容（安全操作，无需审批）。"""
    return "a.txt, b.log, secret.env"

agent = create_agent(
    model="openai:gpt-4o",
    tools=[delete_file, list_files],
    checkpointer=InMemorySaver(),               # 没有它 interrupt 直接报错
    middleware=[HumanInTheLoopMiddleware(
        interrupt_on={
            "delete_file": {
                "allowed_decisions": ["approve", "reject"],
                # 动态描述：把参数渲染进审批卡文案
                "description": lambda tc, state, runtime:
                    f"⚠️ 模型请求删除文件：{tc['args'].get('path')}",
                # 条件拦截：只拦 .env 文件，其它自动放行
                "when": lambda req: req.tool_call["args"].get("path", "").endswith(".env"),
            },
        },
    )],
)

config = {"configurable": {"thread_id": str(uuid.uuid4())}}
out = agent.invoke(
    {"messages": [{"role": "user", "content": "清理一下目录，把 secret.env 删了"}]},
    config,
)

# 检查是否暂停在审批上
if interrupts := out.get("__interrupt__"):
    req = interrupts[0].value["action_requests"][0]
    print("审批卡:", req["description"])        # ⚠️ 模型请求删除文件：secret.env
    human_says_no = True
    if human_says_no:
        final = agent.invoke(
            Command(resume={"decisions": [
                {"type": "reject", "message": ".env 是配置文件不允许删除，请跳过它"}
            ]}),
            config,
        )
    else:
        final = agent.invoke(
            Command(resume={"decisions": [{"type": "approve"}]}), config)
    print(final["messages"][-1].content)
```

### 场景二：多步审批（发布流水线，串行两断点）

```python
"""场景二：手写 StateGraph，一次发布要过「配置审批」「SQL 审批」两道闸。"""
from typing import TypedDict, Optional
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class DeployState(TypedDict):
    config_diff: str
    migration_sql: str
    log: list[str]

def approve_config(state: DeployState):
    # 第一道闸：载荷带上足够让人判断的上下文
    decision = interrupt({
        "step": "1/2 配置变更",
        "payload": state["config_diff"],
        "allowed": ["approve", "reject"],
    })
    if decision["type"] != "approve":
        # reject 的理由写进日志，走条件边终止
        return {"log": state.get("log", []) + [f"配置被拒: {decision.get('reason')}"]}
    return {"log": state.get("log", []) + ["配置已批"]}

def approve_sql(state: DeployState):
    # 第二道闸：恢复本节点时，approve_config 不会重跑（它是上一个节点，
    # 其结果已 checkpoint）；但本节点内 interrupt 之前的代码会重放。
    decision = interrupt({
        "step": "2/2 数据库迁移",
        "payload": state["migration_sql"],
        "allowed": ["approve", "edit", "reject"],
    })
    if decision["type"] == "edit":
        # 人可以改 SQL 后放行
        sql = decision["edited_sql"]
    elif decision["type"] == "approve":
        sql = state["migration_sql"]
    else:
        return {"log": state["log"] + ["迁移被拒"]}
    # 副作用（真正执行迁移）放在 interrupt 之后，避免重放导致重复执行
    return {"log": state["log"] + [f"已执行迁移: {sql[:50]}..."]}

def route_after_config(state: DeployState):
    return END if any("被拒" in x for x in state["log"]) else "approve_sql"

builder = StateGraph(DeployState)
builder.add_node("approve_config", approve_config)
builder.add_node("approve_sql", approve_sql)
builder.add_edge(START, "approve_config")
builder.add_conditional_edges("approve_config", route_after_config)
builder.add_edge("approve_sql", END)
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "deploy-001"}}
out = graph.invoke(
    {"config_diff": "timeout: 30→60", "migration_sql": "ALTER TABLE t ADD c INT", "log": []},
    config,
)
print("暂停于:", out["__interrupt__"][0].value["step"])     # 1/2 配置变更

out = graph.invoke(Command(resume={"type": "approve"}), config)  # 过第一道闸
print("暂停于:", out["__interrupt__"][0].value["step"])     # 2/2 数据库迁移

# 第二道闸：人把 INT 改成 BIGINT 后放行
out = graph.invoke(
    Command(resume={"type": "edit", "edited_sql": "ALTER TABLE t ADD c BIGINT"}),
    config,
)
print(out["log"])
# ['配置已批', '已执行迁移: ALTER TABLE t ADD c BIGINT...']
```

### 场景三：带编辑的审批（HumanInTheLoopMiddleware edit 决策）

```python
"""场景三：SQL 执行工具，人可以改 SQL 后放行（edit），也可以代答（respond）。"""
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langchain_core.tools import tool
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

@tool
def run_sql(sql: str) -> str:
    """在业务库执行 SQL 并返回结果。"""
    return f"[mock] rows for: {sql}"

@tool
def ask_user(question: str) -> str:
    """缺少信息时向用户提问（由人代答，工具体不执行）。"""
    raise NotImplementedError

agent = create_agent(
    model="openai:gpt-4o",
    tools=[run_sql, ask_user],
    checkpointer=InMemorySaver(),
    middleware=[HumanInTheLoopMiddleware(
        interrupt_on={
            "run_sql": {"allowed_decisions": ["approve", "edit", "reject"]},
            "ask_user": {"allowed_decisions": ["respond"]},
        },
        description_prefix="SQL 执行需要人工审批",
    )],
)

config = {"configurable": {"thread_id": "sql-demo"}}
out = agent.invoke(
    {"messages": [{"role": "user", "content": "查一下用户表最近 10 条"}]}, config)

# 模型生成了 SELECT * FROM users ORDER BY id DESC LIMIT 10，
# DBA 审查后要求加上脱敏 → edit 改参放行：
intr = out["__interrupt__"][0].value
original_sql = intr["action_requests"][0]["args"]["sql"]
safer_sql = original_sql.replace("SELECT *", "SELECT id, name, phone_masked")

out = agent.invoke(
    Command(resume={"decisions": [
        {
            "type": "edit",
            "edited_action": {
                "name": "run_sql",              # 工具名保持
                "args": {"sql": safer_sql},      # ← 完整新参数（整体替换）
            },
        }
    ]}),
    config,
)
# run_sql 以 safer_sql 执行；模型基于脱敏结果继续回答用户。

# 若模型接着调 ask_user("结果要导出成 CSV 还是 Excel？") → 再次暂停，
# 这次用 respond 代答：
out = agent.invoke(
    Command(resume={"decisions": [{"type": "respond", "message": "CSV，UTF-8 编码"}]}),
    config,
)
print(out["messages"][-1].content)
```

## 12. 项目实战分析：nl2sql 的 SQL 闸门演进

本项目（`src/agent/middlewares/sql_approval.py`）是 HITL 设计理念的一个真实演化案例：**从「人工审批」退到「确定性硬拦截」**，恰好说明了什么时候该用 interrupt、什么时候不该。

### 12.1 v1（历史）：HumanInTheLoopMiddleware 人工审批

模块 docstring 记载：v1 曾用 langchain 1.x `HumanInTheLoopMiddleware`（after_model 阶段 interrupt）对写/DDL SQL 做人工审批，配套：

- 前端 `ToolApprovalInterrupt` 审批卡组件；
- 后端恢复端点 `POST /api/threads/{tid}/sql-approval`（`src/api/sql_approval.py`）。

恢复端点的协议完全遵循第 3 章的决策格式：

```python
# body: {
#   "main_thread_id": "...",
#   "decisions": [{"type": "approve"} | {"type":"reject","message":...}
#                 | {"type":"edit","edited_action":{"name","args"}}],
# }
# 端点内部：把决策以 Command(resume={"decisions": [...]}) 注回子线程，
# 子 run 从断点继续（approve 执行 / reject 返回拒绝 ToolMessage /
# edit 用修改后的 SQL 执行）。
```

其中有两个值得记下的工程细节：

1. **待审批 interrupt 的发现方式**——不是读顶层 `__interrupt__`，而是遍历线程 state 的 `tasks[].interrupts`：

```python
async def _find_pending_interrupt(http, base, thread_id):
    resp = await http.get(f"{base}/threads/{thread_id}/state")
    state = resp.json()
    for task in state.get("tasks") or []:          # ← 逐 task 找
        for intr in task.get("interrupts") or []:  # ← task 级 interrupts
            value = intr.get("value")
            if isinstance(value, dict) and value.get("action_requests"):
                return value                        # 命中 HITL 审批载荷
    return None
```

原因：本项目的主 agent 是 top-level graph，子 agent 的 HITL interrupt 会被顶层图**抑制**、不出现在顶层输出——审批检测必须读 `state.tasks[].interrupts`（这条已沉淀为项目记忆）。恢复前先 `_find_pending_interrupt` 确认子线程确实停在审批上（否则 409「没有待审批的 SQL」），也避免了重复恢复。

2. **决策结构服务端校验**（`_validate_decisions`）：decisions 必须是非空数组、每个元素是对象、`type` 在白名单内、reject 的 message 必须是字符串——把第 3 章「数量与结构一一对应」的约束前移到 HTTP 边界，防止脏 payload 把恢复打成 `ValueError`。

### 12.2 v2（现状）：`SqlReadOnlyMiddleware` 只读硬拦截

2026-08-28 产品要求「执行的 SQL 只允许查询操作，其余一律禁止」——写/DDL 不再有审批通道，v1 的 interrupt 审批被替换为 `wrap_tool_call` 层的**确定性拦截**：

```python
class SqlReadOnlyMiddleware(AgentMiddleware):
    def wrap_tool_call(self, request, handler):
        if _is_run_sql_tool(self._tool_name(request)):
            sql = self._sql(request)
            if sql:
                verdict, detail = classify_sql(sql)
                if verdict == "write":
                    return self._deny(request, detail)  # 短路：不调 handler，
                                                        # 直接返回 status="error"
            self._normalize_wrenai_limit(request)       # 放行前的参数归一
            return handler(request)                     # 真正执行工具
        ...
```

`classify_sql` 的判定策略（保守拦截）：

- 首关键词在 `_WRITE_LEADING`（INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/TRUNCATE/GRANT/…）→ `("write", 关键词)`，直接拒绝；
- `WITH ...` CTE 里再搜 INSERT/UPDATE/DELETE（防 `WITH ... INSERT INTO`）；
- **无法识别的语句一律按写操作处理**（fail-closed）；
- SELECT 无 WHERE/LIMIT/GROUP BY/聚合 → 标记 `full_dump`（放行但可展示提示）。

拒绝时返回的 ToolMessage 与第 3 章 reject 决策同构（`status="error"` + 给模型的改道指引）：

```python
return ToolMessage(
    content=("Error: 系统为只读查询系统，仅允许执行 SELECT（含 WITH...SELECT）只读查询。"
             f"检测到 {detail or '非查询'} 操作，已禁止执行。"
             "请改用 SELECT 查询，或向用户说明无法执行数据修改。"),
    name=..., tool_call_id=..., status="error",
)
```

旧 API 端点 `api/sql_approval.py` 保留不删（避免破坏旧协议），但不再被触发；`configurable.sql_approval_policy` 前端开关对写/DDL 失效；`classify_sql` 保留供 eval 与前端只读展示复用。

### 12.3 为什么从 interrupt 退回硬拦截？——选型启示

| 维度 | HITL interrupt 审批（v1） | wrap_tool_call 硬拦截（v2） |
|------|--------------------------|---------------------------|
| 决策者 | 人（每次写操作都要等人） | 规则（分类器一次写死） |
| 时延 | 暂停直到人回复，可能数小时 | 零暂停、微秒级 |
| 依赖 | checkpointer + 恢复端点 + 前端审批卡 + 子线程 interrupt 探测 | 无额外依赖 |
| 复杂度 | 高（本项目实测：顶层图抑制子 interrupt、需读 tasks[].interrupts） | 低（一个中间件） |
| 适用 | 决策需要人的裁量（该不该发这封邮件） | 决策可由规则完全确定（只读系统禁写） |

结论与第 10.4 节守则一致：**「能机器判的不要给人判」**。当产品语义是「一律禁止」而非「个案裁量」时，interrupt 审批是过度设计——它引入了 checkpointer、恢复协议、前端组件、子线程 interrupt 探测等一整套复杂度，换来的却是一个本可以用 20 行分类器表达的确定规则。反过来，若需求是「写操作需 DBA 个案批准」，则 v1 的架构（中间件 interrupt + `Command(resume={"decisions": [...]})` 恢复端点 + `tasks[].interrupts` 探测）就是标准答案，其协议设计可直接复用。

另外，`SqlReadOnlyMiddleware` 还展示了 `wrap_tool_call` 的第三种用法——**参数归一**：放行前就地改写 `request.tool_call["args"]`（剥 SQL 尾部 LIMIT 防 Wren 双重 LIMIT 语法错、剥 Cube limit/offset 改平台侧截窗），以及结果后处理（`_apply_cube_window` 对 ToolMessage 内容截窗，异常一律 fail-open 返回原结果）。拦截、改写、后处理都在工具边界一个钩子里完成，不惊动模型、不打断图执行——这正是「不需要人参与的策略」的最佳落点。
