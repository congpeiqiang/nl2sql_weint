## 1. 中间件架构概述：两套体系

本项目涉及**两套中间件体系**，二者是「基类同一、职责分层」的关系：

### 1.1 LangChain agents 中间件（`langchain.agents.middleware`）

这是**协议层**。核心是 `AgentMiddleware` 基类（`.venv/.../langchain/agents/middleware/types.py`），
它定义了 agent 主循环中所有可拦截的位点（模型调用前后、工具调用前后、run 起止）。
`create_agent(model, tools, middleware=[...])` 把中间件列表编译进 LangGraph 图：
节点型钩子成为图节点，wrap 型钩子成为洋葱式调用链。

官方同时提供了一批开箱即用的中间件（`middleware/__init__.py` 的导出清单）：

```python
# .venv/.../langchain/agents/middleware/__init__.py（节选）
from langchain.agents.middleware.summarization import SummarizationMiddleware
from langchain.agents.middleware.human_in_the_loop import HumanInTheLoopMiddleware
from langchain.agents.middleware.model_call_limit import ModelCallLimitMiddleware
from langchain.agents.middleware.tool_call_limit import ToolCallLimitMiddleware
from langchain.agents.middleware.pii import PIIMiddleware
from langchain.agents.middleware.todo import TodoListMiddleware
from langchain.agents.middleware.model_fallback import ModelFallbackMiddleware
from langchain.agents.middleware.tool_retry import ToolRetryMiddleware
# ...
```

### 1.2 deepagents 中间件（`deepagents.middleware`）

这是**能力层**。deepagents 的中间件同样继承 `AgentMiddleware`，但每个中间件自带一组
工具 + 系统提示词注入 + 请求拦截，构成「深度智能体」的核心能力。
`deepagents/middleware/__init__.py` 的模块 docstring 把「为什么用中间件而不是普通工具」
讲得非常清楚（源码摘录）：

```text
Middleware subclasses `AgentMiddleware`, overriding its `wrap_model_call()`
hook that intercepts every LLM request before it is sent. This lets middleware:

* Filter tools dynamically      —— 动态过滤工具（如 FilesystemMiddleware 按后端能力摘除 execute）
* Inject system-prompt context  —— 注入系统提示（MemoryMiddleware / SkillsMiddleware）
* Transform messages            —— 改写消息（SummarizationMiddleware 上下文压缩）
* Maintain cross-turn state     —— 维护跨轮状态（类型化 state dict）

A plain tool function in a `tools=[]` list cannot do any of this -- it is
only invoked *by* the LLM, not *before* the LLM call.
```

deepagents 提供的主要中间件：`FilesystemMiddleware`（VFS 文件工具）、`MemoryMiddleware`、
`SkillsMiddleware`（渐进披露技能）、`SubAgentMiddleware` / `AsyncSubAgentMiddleware`（子代理）、
`SummarizationMiddleware`、`RubricMiddleware` 等。

`deepagents/middleware/_utils.py` 只有一个函数，但极其常用——所有「往系统提示词追加一段」
的中间件都用它（保持 content-block 结构而非字符串拼接）：

```python
# .venv/.../deepagents/middleware/_utils.py
def append_to_system_message(
    system_message: SystemMessage | None,
    text: str,
) -> SystemMessage:
    """Append text to a system message."""
    new_content: list[ContentBlock] = list(system_message.content_blocks) if system_message else []
    if new_content:
        text = f"\n\n{text}"
    new_content.append({"type": "text", "text": text})
    return SystemMessage(content_blocks=new_content)
```

### 1.3 本项目的选择

本项目 **20+ 个自研中间件全部直接继承 `langchain.agents.middleware.AgentMiddleware`**，
通过 `create_deep_agent(..., middleware=[...])` 注入，与 deepagents 内置中间件同栈混排。
判据很简单：

| 需求 | 用什么 |
|---|---|
| 拦截/改写模型请求、工具调用、消息、state | 自研中间件（继承 `AgentMiddleware`） |
| 无状态、只被 LLM 主动调用的功能 | 普通工具函数（`tools=[...]`） |
| 文件系统/子代理/技能/记忆等通用能力 | deepagents 内置中间件 |

## 2. 中间件基类详解

### 2.1 `AgentMiddleware` 接口全貌

源码摘录（`.venv/.../langchain/agents/middleware/types.py:383`，签名有精简）：

```python
class AgentMiddleware(Generic[StateT, ContextT, ResponseT]):
    """Base middleware class for an agent."""

    state_schema: type[StateT] = _DefaultAgentState
    """中间件节点可见的 state schema（可扩展自定义字段）"""

    tools: Sequence[BaseTool]
    """中间件自带的额外工具（随中间件注册进 agent）"""

    @property
    def name(self) -> str:
        return self.__class__.__name__   # 图节点名默认 = 类名

    # ── 节点型钩子：返回 state 更新 dict（或 None / Command）──
    def before_agent(self, state, runtime) -> dict | None: ...
    async def abefore_agent(self, state, runtime) -> dict | None: ...
    def before_model(self, state, runtime) -> dict | None: ...
    async def abefore_model(self, state, runtime) -> dict | None: ...
    def after_model(self, state, runtime) -> dict | None: ...
    async def aafter_model(self, state, runtime) -> dict | None: ...
    def after_agent(self, state, runtime) -> dict | None: ...
    async def aafter_agent(self, state, runtime) -> dict | None: ...

    # ── wrap 型钩子：拿到 handler 回调，可重试/短路/改写 ──
    def wrap_model_call(self, request: ModelRequest, handler) -> ModelResponse | AIMessage | ExtendedModelResponse: ...
    async def awrap_model_call(self, request, handler) -> ...: ...
    def wrap_tool_call(self, request: ToolCallRequest, handler) -> ToolMessage | Command: ...
    async def awrap_tool_call(self, request, handler) -> ...: ...
```

**两类钩子的本质区别**（选型第一问）：

| | 节点型钩子（before/after_*） | wrap 型钩子（wrap_*_call） |
|---|---|---|
| 图形态 | 独立 graph 节点 | 洋葱式调用链（不进图） |
| 返回值 | state 更新 dict / `Command` / `None` | `ModelResponse` / `ToolMessage` / `Command` |
| 能否重试/短路真实调用 | 否（只能用 `jump_to` 改流向） | 能（handler 可调 0 次、1 次、多次） |
| 改动是否落 state/checkpoint | **是** | 否（除非用 `ExtendedModelResponse.command`） |
| 典型用途 | 补消息、改流向、run 收尾 | 过滤工具、换模型、改写结果、计时、拦截 |

基类对未实现的 wrap 钩子**主动抛 `NotImplementedError`**，报错文案会提示你「只实现了
async 版却在同步上下文调用」这类问题——这是设计好的诊断路径，不是 bug。

### 2.2 `ModelRequest`：模型请求的不可变快照

```python
# types.py:85（节选）
@dataclass(init=False)
class ModelRequest(Generic[ContextT]):
    model: BaseChatModel                 # 本次调用用的模型实例
    messages: list[AnyMessage]           # 消息列表（不含 system）
    system_message: SystemMessage | None # 系统消息
    tool_choice: Any | None
    tools: list[BaseTool | dict]         # 本次调用绑定给模型的工具
    response_format: ResponseFormat | None
    state: AgentState                    # 完整 agent state
    runtime: Runtime[ContextT]
    model_settings: dict[str, Any]

    def override(self, **overrides) -> ModelRequest:
        """不可变模式：返回替换了指定字段的新实例，原对象不动。"""
        return replace(self, **overrides)
```

**关键纪律：改写请求一律用 `request.override(...)`，不要直接赋值属性。**
`__setattr__` 被重写为发 `DeprecationWarning`（types.py:167），官方明说直接赋值已废弃。
`override` 支持的键：`model` / `system_message` / `messages` / `tool_choice` / `tools` /
`response_format` / `model_settings` / `state`。

⚠️ 项目实证（多处中间件 docstring 反复标注）：**`request.runtime.config` 恒为空 dict**，
读 `configurable`（db_name、user_id、thread_id…）必须走 `langgraph.config.get_config()`。
见 `tool_filter.py:122`、`current_db_context.py:31`、`model_required.py:60` 等。

### 2.3 `ModelResponse` / `ExtendedModelResponse`：两种返回形态

```python
# types.py:270（节选）
@dataclass
class ModelResponse(Generic[ResponseT]):
    result: list[BaseMessage]            # 通常一条 AIMessage
    structured_response: ResponseT | None = None

@dataclass
class ExtendedModelResponse(Generic[ResponseT]):
    model_response: ModelResponse[ResponseT]
    command: Command[Any] | None = None  # 额外的 state 更新，走图的 reducer 归并
```

- 返回 `ModelResponse`（或直接 `AIMessage`，会自动转换）→ 只影响本次模型输出；
- 返回 `ExtendedModelResponse` → **模型输出之外再追加一条 `Command(update={...})`
  写 state**，这是 wrap 型钩子往 checkpoint 里持久化自定义字段的唯一正规通道
  （项目实例：`token_meter.py` 写 `state["token_stats"]`）。

### 2.4 `ToolCallRequest`：工具调用请求

来自 `langgraph.prebuilt.tool_node`，四个关键字段：

- `request.tool_call`：**dict**（TypedDict），含 `name` / `args` / `id`——注意是 dict，
  `getattr(tc, "args")` 拿不到，必须 `tc.get("args")`（项目里 `_tool_args` 帮助函数
  对两种形态都做了兼容，见 `query_gate.py:120`）；
- `request.tool`：`BaseTool` 实例（可用 `override(tool=...)` 换执行实例——
  `dynamic_mcp_tools.py` 的「改道」就靠它）；
- `request.state`：当前 state（dict 或 BaseModel 皆有可能，取 messages 要防御式写，
  见 `failure_circuit._state_messages`）；
- `request.runtime`：含 `tool_call_id`、`execution_info.thread_id` 等。

`wrap_tool_call` 的 handler 返回 `ToolMessage | Command`。**改写工具结果时的铁律**
（`failure_circuit.py:362` 注释原文）：

```python
# 保留 tool_call_id / name / status —— LangGraph 的 tool 配对与
# langfuse_span 的「exec 失败」判定都靠它们。
return result.model_copy(update={"content": new_text})
```

### 2.5 `hook_config(can_jump_to=[...])`：流向控制

节点型钩子可以返回 `{"jump_to": "model" | "tools" | "end"}` 改变图的流向，但**必须**
先用 `@hook_config(can_jump_to=[...])` 声明，否则 langchain 建的是普通平边，
`jump_to` 会被**静默丢弃**（详见 §5.9 CaliberGate 与 §9 陷阱清单）。

### 2.6 函数式快捷装饰器

不想写类时，`types.py` 提供了 7 个装饰器，把裸函数包装成中间件实例：
`@before_agent` / `@before_model` / `@after_model` / `@after_agent` /
`@dynamic_prompt` / `@wrap_model_call` / `@wrap_tool_call`。例如：

```python
from langchain.agents.middleware import before_model, AgentState
from langgraph.runtime import Runtime

@before_model(can_jump_to=["end"])           # 声明可以跳到 end
def guard(state: AgentState, runtime: Runtime) -> dict | None:
    if too_many_messages(state):
        return {"jump_to": "end"}            # 提前收尾
    return None                              # 什么都不改

agent = create_agent(model, tools, middleware=[guard])  # 装饰器产物直接进列表
```

`@dynamic_prompt` 是 `wrap_model_call` 的特化：函数收 `ModelRequest`、返回字符串或
`SystemMessage`，装饰器替你完成 `request.override(system_message=...)`。
本项目 `nl2sql_agent.py` 的 `dynamic_prompt`（按库注入「查询通道路由」段）即此形态。

## 3. 中间件注册与执行顺序

### 3.1 注册方式

两条路，本项目两条都在用：

```python
# ① langchain 原生
from langchain.agents import create_agent
agent = create_agent(model, tools=[...], middleware=[mw1, mw2, ...])

# ② deepagents（本项目主/子 agent 均走这条，见 main_agent.py:268、nl2sql_agent.py:345）
from deepagents import create_deep_agent
agent = create_deep_agent(
    model=..., tools=[...], subagents=[...],
    middleware=_middleware,          # ← 自研中间件列表
    backend=composite_backend,
    permissions=FILE_PERMISSIONS,
    state_schema=MainAgentState,     # ← 扩展 state 字段在这里声明
)
```

`create_deep_agent` 会**先放自己的内置中间件**（`TodoListMiddleware` 恒在栈首、
`PatchToolCallsMiddleware`、`FilesystemMiddleware` 等），再把用户列表 extend 进去
（`deepagents/graph.py:773-775` / `:812`，`caliber_gate.py` docstring 有引用）。
所以**你的中间件永远不是列表第 0 个**——这个事实直接决定了 §9 里 `jump_to` 装饰器
是硬要求而非可选。

### 3.2 执行顺序（本教程最重要的一张表）

langchain 的组装规则（`factory.py`，多处项目注释交叉验证过）：

| 钩子 | 顺序 |
|---|---|
| `before_agent` / `before_model` | **列表序**（index 0 → 末尾），每个是独立图节点 |
| `after_model` / `after_agent` | **逆列表序**（index 大者先跑） |
| `wrap_model_call` / `wrap_tool_call` | **first = outermost（洋葱）**：请求流 `[0]→[1]→…→真实调用`，响应流反向 |

洋葱模型推论（项目注释原话，`query_result_offload.py:24`）：

```text
Request 流  first → last → tool
Response 流 tool → last → first
⇒ 外层中间件在 handler(request) 返回**之后**做后处理
⇒ 内层的后处理**先**跑，外层看到的已是内层改写后的结果
```

### 3.3 实战：nl2sql 子 agent 的完整中间件栈

`src/agent/graphs/nl2sql_agent.py:247-343`，顺序经过精心设计（每条都有注释说明理由）：

```python
_middleware = [
    DynamicMCPToolsMiddleware(),        # 最外层：先并入运行期新库工具，再交给内层裁剪
    TraceRecorderMiddleware(...),       # 事件采集（本地 SQLite 追踪）
    skills_middleware,                  # deepagents SkillsMiddleware
    ProgressTrackerMiddleware(),
    CaliberGateMiddleware(),            # after_model 口径闸（index 小 = 跑得晚 = 等 ProgressBoundary 先推进 todos）
    ProgressBoundaryMiddleware(),
    DanglingToolCallsMiddleware(),      # before_model：补 orphan tool_call
    ThinkingToggleMiddleware(),         # wrap_model_call：按 configurable 换模型
    ToolFilterMiddleware(),             # wrap_model_call：按库过滤工具
    FilesystemThreadGuardMiddleware(),  # wrap_tool_call：跨线程 process_data 读写护栏
    MessageSlimmerMiddleware(...),      # 通用大结果截断（在 QueryResultOffload 外层）
    KnowledgeTrimMiddleware(),          # 知识料裁剪（在 MessageSlimmer 内层：Slimmer 按裁剪后文本去重）
    QueryResultOffloadMiddleware(),     # run_sql/query_cube 大结果落盘+瘦身
    FailureCircuitMiddleware(),         # 失败熔断（LangfuseSpan 外层 ⇒ span 吃原始报错）
    LangfuseSpanMiddleware(),           # skill 级 span + 打分 + process_data dump
    dynamic_prompt,                     # @dynamic_prompt 函数式中间件
]
_middleware.append(QueryGateMiddleware())       # 授权/通道/顺序三规则闸
_middleware.append(CubeRouteGateMiddleware())   # cube 车道软闸
_middleware.append(sql_approval_middleware)     # HITL SQL 审批
_middleware.append(WriteTodosProtocolMiddleware())
_middleware.insert(0, QuotaErrorMiddleware())   # 额度耗尽 → 友好提示（须包住所有内层）
_middleware.insert(0, ModelTimeoutMiddleware()) # 超时 → 友好提示 + 重试 + 并发闸

```

三个教科书级的顺序决策，都值得抄走：

1. **`DynamicMCPTools` 必须在 `ToolFilter` 外层**——先并入新库工具，再按当前库裁剪；
   挂反了新库工具会绕过过滤（`dynamic_mcp_tools.py:34`）。
2. **`FailureCircuit` 夹在 `MessageSlimmer`（外）与 `LangfuseSpan`（内）之间**——
   内层后处理先跑 ⇒ ① span / process_data dump 吃到的是**原始**报错（观测面不撒谎）；
   ② Slimmer 的体积判据与 md5 去重作用在**改写后**进 state 的文本上（不出现两套账）。
3. **`vfs_path_resolver` 放 main_agent 列表末尾（最内层、紧贴模型）**——后处理最先完成，
   外层 langfuse_span / trace_recorder / checkpoint / 前端看到的是同一份真实路径
   （`main_agent.py:273`）。

## 4. 自定义中间件开发步骤（Step by Step）

以「我要写一个 XX 中间件」为例，走七步：

**Step 1 — 选钩子。** 问三个问题：
- 要拦截/改写**模型调用**还是**工具调用**？→ 决定 `wrap_model_call` / `wrap_tool_call`；
- 需要**重试、短路、换模型、改结果**吗？→ 必须 wrap 型；
- 需要把数据**持久化进 state / 改图流向**吗？→ 节点型（`before_model` 返回 dict /
  `after_model` + `jump_to`），或 wrap 型 + `ExtendedModelResponse.command`。

**Step 2 — 建文件。** 放 `src/agent/middlewares/<snake_name>.py`，模块 docstring 写清
「背景 trace / 为什么既有护栏不够 / 设计口径 / 挂载位置 / 开关」——这是本仓的强约定，
每个中间件文件头都是一份事故复盘（见 `failure_circuit.py:1-82`）。

**Step 3 — 写类骨架。** 继承 `AgentMiddleware`，同时实现 sync 与 async 两个版本
（生产走 `ainvoke`/`astream`，async 版才是主路径；sync 版留给脚本与单测）。
async 版的标准兼容写法（全仓统一模式）：

```python
async def awrap_tool_call(self, request, handler):
    result = handler(request)
    if hasattr(result, "__await__"):   # handler 可能返回协程也可能返回裸值
        result = await result
    return self._after(request, result)  # 公共后处理与 sync 版共用
```

**Step 4 — 定失败语义。** 二选一并在 docstring 写明：
- **fail-open**（护栏/观测/瘦身类）：自身任何异常只记日志、透传原结果，
  「护栏本身绝不能弄坏工具调用」（`failure_circuit.py:395`）；
- **fail-closed**（授权/配额类）：判据读不到就拦（`model_required.is_blocked_for`：
  「读配置炸了：宁可挡住也不能回落别人的模型」）。

**Step 5 — 加开关与阈值。** 环境变量一键回退（`NL2SQL_FAIL_CIRCUIT=off`、
`NL2SQL_CUBE_ROUTE_GATE=off`、`EXECUTE_GUARD_STRICT=0`…），非法值一律回落默认
（`failure_circuit._env_int`）。生产中间件没有开关 = 出事只能回滚发版。

**Step 6 — 挂载并写清位置理由。** 在 `nl2sql_agent._middleware` / `main_agent.middleware`
插入，注释说明「为什么在这个位置」（参照 §3.3 三条）。

**Step 7 — 验证。** 纯函数抽出来单测（§6），再跑 E2E 脚本，最后按 MEMORY 的纪律
在生产 `docker exec md5sum` 确认发版生效。

### 5.1 `failure_circuit.py` — 失败熔断（三阈值设计）

**问题**（trace `ec484c693f`）：语义库删掉 model `do_bug` 后，模型拿到
`table 'wren.public.do_bug' not found` 不收手，在 `dry_run`/`run_sql`/`query_cube`/`dry_plan`
之间来回撞**同一个对象 18 次**，烧掉 406.7s（整个 turn 才 433.9s），最终以 402 余额耗尽收场。

**签名设计（本案例最值钱的一条）**：

```python
# failure_circuit.py:30-36（docstring 摘录）
# 签名 = (错误族, 归一化对象名)，**不含工具名**。
# 不带工具名是刻意的：同一根因会被 dry_run / run_sql / query_cube / dry_plan
# 四种工具各撞一次。若把工具名并入签名，每种工具各自计数 ⇒ 熔断形同虚设，
# 18 次只会变成 8 次。
# 对象名取最后一段（wren.public.do_bug → do_bug），跨工具对齐。
```

**无进程内账本**：计数从 state 推导——只扫「最后一条 HumanMessage 之后」的 ToolMessage
（`_current_turn_messages`），因此子 agent 线程复用不误伤、重启/多 worker 不错乱、
同批并行扇出天然不算重复。改写后的消息内嵌机读标记 `【fail-circuit:<族>:<对象>】`，
下一轮解析不依赖自由文本（模型可能转述）。

**三阈值升级**：

```python
# failure_circuit.py（docstring 表格）
# | 第几次      | 行为                                              |
# | 1          | 放行原错误，改写为「可收手的信息」（去 list_models 核实/如实告知用户）|
# | ≥ WARN(2)  | 改写为「本 run 第 N 次撞同一对象，停止重试」          |
# | ≥ STOP(3)  | 终态措辞 + 进硬闸：args 再出现该对象名 → 直接拒绝执行   |
# 另有失败预算 TOTAL(6)：本轮跨对象「不存在」类失败总量封顶（只加措辞、不硬拦）
```

硬闸判定用词边界正则在 args 文本里找对象名（`_blocked_sig`）；已知裂口：**视图/Cube
间接引用绕过**（args 文本里不出现对象名）——MEMORY 有记录，教程如实标注。

**改写时保形状**：

```python
# failure_circuit.py:362
# 保留 tool_call_id / name / status —— LangGraph 的 tool 配对与
# langfuse_span 的「exec 失败」判定都靠它们。
return result.model_copy(update={"content": new_text})
```

### 5.2 `model_timeout.py` — 模型超时处理

**问题**：模型 API 超时后，原始异常被 LangGraph 序列化进 run stream 的 error 事件，
而前端 SDK **不渲染 stream.error** → 界面永久转圈（trace `ef83792`：4×60s 重试后空白）。

**解法**：`wrap_model_call` 捕获超时 → **不抛异常**，返回一条友好中文 `AIMessage`。
agent 正常结束、消息进 checkpoint，用户直接看到提示。这是「返回而非抛出」范式的样板
（同构：`quota_error.py`、`model_required.py`）。

**异常分类的顺序纪律**（`_classify_failure`，源码摘录）：

```python
# model_timeout.py:107
def _classify_failure(exc, *, attempt, attempts, started) -> tuple[str, float]:
    """给出下一步动作：("friendly"|"retry"|"raise", 退避秒)。

    判定顺序**必须是超时优先**：openai.APITimeoutError 是 APIConnectionError 的
    子类，反过来判会把「对端慢」当「连接断」去重试，用户白等几个 60s。
    """
    if is_timeout_error(exc):
        return "friendly", 0.0            # 超时 → 友好消息，不重试
    retryable = is_connection_error(exc)
    if retryable and attempt < attempts:
        return "retry", backoff_seconds(attempt)   # 连接类 → 带抖动退避
    return "raise", 0.0                   # 其他原样上抛，且先 ERROR 记异常链
```

**收口点长出的三件事**：这里是全系统模型调用的唯一收口点（主/子 agent 都注册），
所以顺手挂了 ① prometheus 计时计数（`note_llm_call`，覆盖同步与 await 两段——
「异步 handler 的真耗时在 await 里，只量 `handler(request)` 会量成 0」）；
② 连接类错误退避重试（SDK `max_retries=3` 用尽后的第二道）；③ 并发闸 + 按用户配额
（`model_call_slot`，排队超预算 **fail-open**：闸不能自己变成故障）。
退避睡眠在闸**外**（槽已释放），否则退避中的调用白占额度堵别人。

**失败戳**：友好消息同时 `mark_failed(...)`（`agent/utils/failure_signal.py`）——
「不抛异常」的代价是这条消息与正常回答数据上无法区分，曾导致 CaliberGate 把超时当
终稿打回、`check_async_task` 报 success。戳是附加信息，**文案一字符不改**（用户可见契约）。

### 5.3 `token_meter.py` — Token 用量计量

**核心机制**：`wrap_model_call` 计时 + 从 `AIMessage.usage_metadata` 提取用量，然后
**用 `ExtendedModelResponse.command` 把统计写进 state**——这是 wrap 钩子持久化自定义
state 字段的标准姿势：

```python
# token_meter.py:98
return ExtendedModelResponse(
    model_response=response,
    command=Command(update={"token_stats": step_stat}),  # 走图的 reducer
)
```

累积不是中间件自己做的，而是**自定义 reducer**（`_accumulate_token_stats`：数值字段累加、
`step_count` 递增、`steps` 追加且只留最近 50 步防 state 膨胀），字段声明在
`main_agent.MainAgentState`：

```python
# main_agent.py:233
token_stats: Annotated[NotRequired[dict], _accumulate_token_stats]
```

**职责单一的反面教材就在隔壁**：`trace_recorder.py` 头注明写「本中间件只记事件、
不写 state.token_stats，避免两处同时 update 同一字段导致 reducer 累加重复
（**实测双中间件时 token 统计翻倍**）」。

细节：`_current_round` 用「state 里 human 消息数」推当前轮号——又是「从 state 推导、
不落进程内账本」的口径。

### 5.4 `query_gate.py` — 查询准入闸门（三规则）

**背景**：`dynamic_prompt` 的「查询通道路由」只是文本指引，**模型不遵守**
（trace `bbb0eda0`：已建模库上仍直连 `dbmcp_run_sql` ×21）。文本指引失效 ⇒ 程序化兜底。

三条规则，软硬分明：

| 规则 | 性质 | 内容 |
|---|---|---|
| 零：库授权（P1-16） | **硬闸，每次必拦** | 调用者对目标库无授权 → `status="error"` 拒绝并列出可用库。补 `tool_filter` 的残留口：「看不见 ≠ 调不到」——`dbmcp_*` 的目标库是**参数**（出站前不知道填哪个库），`wrenai_<slug>_*` 的库名在**工具名**里而执行侧注册表只按名字取实例不看身份 |
| 一：通道硬闸 | **硬闸，每次必拦** | 当前库已在 Wren 语义层建模 → `dbmcp_*` 一律不执行，错误文案指到 `wrenai_<库>_run_sql` |
| 二：顺序软提醒 | **软门，每线程一次** | `run_sql/dry_run/dry_plan` 前若本轮从未调过任何「获取工具」→ 提醒先走 wren-retrieve 四路取料 |

软门的防打扰设计（`_mark_reminded` + 进程内 `_REMINDED` set + 上限清空）值得注意的
是它的**已知缺陷**：进程内计数重启即失忆——所以后来的 `caliber_gate` 改成了从 state
推导重试次数（§5.9）。这是一个「同一问题两代解法」的活教材。

所有拒绝消息统一 `status="error"` + `Error:` 前缀——让 `langfuse_span._maybe_score`
的 `looks_like_exec_error` 把它记成 exec 失败而非 `sql_exec_success=1`（观测口径联动）。
目标库解析优先级：工具参数 `db_name` → state 系统提示里的路由标记
（正则 `_ACTIVE_DB_RE`，注意注释里那个 `\*{0,2}` 的血泪史：真实注入文本带 Markdown
加粗，早先的正则一条都匹配不上，兜底成了死代码）。取不到线程 id / 库名 → fail-open。

### 5.5 `tool_filter.py` — 动态工具过滤

**机制**：`wrap_model_call` 里 `request.override(tools=filtered)`——只改**出站 payload**，
不动图注册的工具（原理注释在文件头：「LangGraph 在后续模型调用中只传递新列表」）。

过滤规则：

```python
# tool_filter.py:8-12（docstring 摘录）
# - wrenai_<当前库名>_* → 保留（当前库的语义层工具）
# - wrenai_<其他库名>_* → 过滤（其他库的语义层工具，LLM 不需要）
# - dbmcp_* → 当前库**有**语义层工具时移除（语义层独占），否则保留
# - 非 wrenai/dbmcp 的工具 → 保留（如图表工具等）
```

两个精妙点：

1. **「语义层独占」的判定用实际存在的工具而非配置**：
   「判定用 `name.startswith(prefix)` 而非 `is_modeled()`：后者查的是 db_config 配置，
   wrenai server 加载失败时（2026-09-08 预检事故）配置仍显示已建模，据此移除 dbmcp
   会让模型一个查询工具都没有——必须 fail-open 保留。」
2. **未选库不是后门**（`_filter_unselected`，P1-2）：`db_name` 为空时不再「返回全部工具」，
   改为按调用者可见库裁剪 wrenai 工具；授权读取本身失败 → fail-open（一次 sqlite 读故障
   不能让所有人查不了数），账号查不到 → 空可见库 → **fail-closed**。

`_resolve_db_name` 再次实证 `request.runtime.config` 恒空、必须走
`langgraph.config.get_config()`。开关：`NL2SQL_SEMANTIC_EXCLUSIVE_TOOLS=0` 秒回退。

### 5.6 `langfuse_span.py` — 可观测性追踪

规模最大的中间件（1189 行），三件事：

1. **skill 级 span**（`wrap_tool_call`）：工具名后缀 → 启发式 skill 分类
   （`TOOL_SKILL_MAP`），`client.start_observation(name=f"skill:{skill}:{tool}", ...)`；
   展示名另有一套 `_resolve_display_skill` 解析**真实编排 skill**（read_file 命中
   SKILL.md 是权威信号 + `_TOOL_OWNER_SKILLS` 唯一归属表覆盖过期活动 skill）。
2. **在线评分**（`_maybe_score`）：`sql_valid_score` / `sql_exec_success` /
   `schema_match_score` 确定性分 + 抽样调度 LLM-judge；执行失败不再调 judge（省成本）。
3. **process_data 落盘**（`_dump_process_data`）：工具边界直接把 input/output 代写为
   `{workspace}/nl2sql_process_data/{thread}/{skill}/{tool}-{seq}.json`——
   「走磁盘写不走模型，0 额外 LLM 往返」。

跨线程 trace 归巢是重头戏：deepagents 异步工作线程丢 OTel context ⇒ skill span 成孤儿。
解法是从 `config.metadata.langfuse_parent_trace_id`（主线程注入）构造
`trace_context={"trace_id":..., "parent_span_id":...}` 显式嵌套，并补
`langfuse.trace.name` / `session.id` 属性防 v4 误判 root（M-T2/T3b/T6/T8b 一串修复，
docstring 全程标注）。

**监控旁路纪律**：所有 Langfuse 调用兜 try/except，「异常不影响工具执行」；
`after_agent` 恒返回 `None`（本中间件不做状态更新）。截断阈值与 MessageSlimmer
**读同一个环境变量** `LARGE_RESULT_TRUNCATE_CHARS`——「若小于 MessageSlimmer 的落盘
阈值，占位符里写的具体文件名就是假的，故两处必须同源对齐」。

### 5.7 `message_slimmer.py` — 消息瘦身

**问题**：LangGraph 每个 checkpoint 存「截至当前的完整消息列表」（O(n²) 膨胀），
大头是超大 tool 结果（单条 73.4KB read_file 占 24%）与完全重复结果。

两个动作都在 `wrap_tool_call`（结果进 state **之前**）：

1. **截断超大**：文本 > `LARGE_RESULT_TRUNCATE_CHARS`（默认 8000）→ 完整内容落盘
   `large_tool_results/<tool_call_id>`（复用 deepagents `_offload_tool_message_content`），
   消息里只留 head+tail 预览 + 路径指针；
2. **去重**：文本 md5 与线程内历史某条同名工具结果完全相同 → 替换为小占位
   （引用首次 tool_call_id），**保留 tool_call_id / name / id**，配对与前端步骤关联不破坏。

**三张免截断白名单，每张背后都是一次生产事故**：

| 白名单 | 事故 |
|---|---|
| 完整交互式图表 iframe（`data:text/html;base64,`） | 预览按行截断，图表结果基本只有一行 → `</iframe>` 被砍掉，**聊天与报告同时静默丢图** |
| 知识类工具（`get_instructions` 等，按**后缀**匹配兼容 `wrenai_<库>_` 前缀） | trace `2f98ed67`：20.9k 口径原文被落盘成 head5/tail5 预览，正文在被砍掉的中间 → 模型拿文件工具去 VFS 找不存在的 knowledge 路径 9 次，全被权限拒，随后 LLM 超时子任务报废 |
| 归因结果（`attribution_analyze`） | 嵌套 JSON 截断后是半个 JSON，模型照着被砍断的对象读错数字（这张是预防性的，docstring 如实区分了性质） |

每张白名单都有**体积上限**（默认 60000，超限仍落盘 + warning）：「不能让上下文被
无上限的巨型结果撑爆」。工具名判据一律按后缀、`ToolMessage.name` 缺失时**不豁免**
（退回落盘，方向安全）。

返回值拆包也值得学：结果可能是 `ToolMessage` 也可能是带消息的 `Command`
（`_unwrap_command_messages` 还要处理 `REMOVE_ALL_MESSAGES` 哨兵再原样还原）。

### 5.8 `vfs_path_resolver.py` — 路径解析

**问题**：agent 全程在 VFS 命名空间（`/workspace/...`），聊天里回显的「最终结果 →
/workspace/report/x.html」对用户是误导（不知道是哪个工作区、不可直接打开）。

**解法**：`wrap_model_call` **后处理**——模型返回后，把 AIMessage 文本里的 VFS 路径
改写为真实磁盘路径（`_VFS_PREFIXES` 三前缀 → WorkspaceManager 属性；统一正斜杠，
Windows 可直接导航）：

```python
# vfs_path_resolver.py:97
def _postprocess(self, response):
    """改写 response.result 里所有 AIMessage 文本中的 VFS 路径。"""
    try:
        wm = get_workspace_manager()
        for i, msg in enumerate(response.result or []):
            if not isinstance(msg, AIMessage):
                continue                       # ⚠️ 只改 AIMessage
            ...
            messages[i] = msg.model_copy(update={"content": new_text})
    except Exception:
        _logger.warning("[vfs_path] 后处理失败，返回原响应", exc_info=True)
    return response                            # fail-open
```

安全边界写得很清楚：**绝不碰 ToolMessage 与 tool_call 参数**——`write_file` 的 path
必须保持 VFS 形态（后端 `_resolve_path` 只按 `/` 前缀解析）；正则用负向后顾
`(?<![A-Za-z0-9_:/\\])` 排除已是真实磁盘路径的 `D:/workspace/...`，避免二次改写；
改写幂等。挂载在 main_agent 列表**末尾**（最内层），理由见 §3.3 第 3 条。

**补充案例 A：`caliber_gate.py` — `after_model` + `jump_to` 的正确姿势。**
它的 docstring 是一份 langchain factory 源码考证：`after_model` 每轮必跑（终态轮也跑），
但只注入消息不会让模型重答（见 `tool_calls` 为空直接退循环）；重答的正规通道是
`jump_to="model"`，而 `jump_to` 是 `EphemeralValue`（每个 superstep 自动清空 ⇒ 不会死循环）。
**必须显式 `@hook_config(can_jump_to=["model"])`**，因为 deepagents 把 TodoListMiddleware
恒放栈首 ⇒ 我们永远不是 `loop_exit_node` ⇒ 那条「不写装饰器也能跳」的无条件边与我们无关。
四组合实测表（`[0]`/`[1]` × 有/无装饰器）直接写在 docstring 里。重试计数
`_retries_in_turn` **由 state 推导**（数本轮注入过几条 `[系统自动通知]` HumanMessage），
天然跨重启——对 `query_gate._REMINDED` 进程内方案的代际升级。

**补充案例 B：`dangling_tool_calls.py` — 为什么选 `before_model` 而非 `wrap_model_call`。**
「后者只改出站 payload（override 不落 state）；要落 state 得走 ExtendedModelResponse +
Command，会排到 model 回复之后（乱序）。before_model 是唯一『补进 state 正确位置 +
同一轮被 model 读到』的挂点。」——节点型 vs wrap 型选型的最清晰论证。
核心扫描逻辑 `_collect_dangling_tool_messages` 是**纯函数，供单测**。

**补充案例 C：`knowledge_trim.py` — 自验证安全闸。** 裁剪 `get_instructions` 前先按
wren `load_rules` 的口径重建分片，拼接结果与收到的原文**不逐字相等就放弃裁剪**：
「这条闸把『同构』变成自验证的——顺序或 strip 差一点只会静默不裁，绝不会裁错内容」。
另有地板（保留 ≥3 文件且 ≥ 原文×0.4 字符，按**原序**补足——口径有先后依赖不许重排）、
裁完反而更长则不裁、追加说明段措辞必须是「与当前问题无关」而非「读不到」
（后者会诱发模型去 VFS 找路径，同 §5.7 知识料事故）。

**补充案例 D：`trace_recorder.py` — 单例中间件的并发纪律。** docstring 原话：
「曾经的做法是在 wrap_model_call 里把结果存到 `self._cached_thread_id`，再由
wrap_tool_call 读回来。**那是并发下必错的写法**：中间件实例是进程内单例，而写入到读取
之间隔着整个 LLM 推理时长，期间别的 run 会覆盖这个属性 → 工具事件系统性挂错会话
（生产 10 个 run 共用 1 个实例，必有此现象）。现取（contextvar / request 携带）才与
并发数无关。」

## 7. 中间件组合使用的最佳实践

从本仓 20+ 个中间件的共存经验里提炼：

**7.1 顺序即语义，写下来。** 每条挂载位置都要有注释论证（参照 §3.3）。经验法则：

```text
wrap 链（first = outermost）：
  最外层：门禁类（ModelRequired → ModelTimeout → QuotaError——「须包住所有内层模型调用」）
  ↓      工具面装配（DynamicMCPTools 并入 → ToolFilter 裁剪：先加后裁）
  ↓      观测类放中间偏内（LangfuseSpan 要吃**原始**结果，所以瘦身/改写类在它外层）
  最内层：紧贴模型的输出改写（vfs_path_resolver 放列表末尾）
```

**7.2 同源阈值，一处定义。** 两处读同一环境变量（`LARGE_RESULT_TRUNCATE_CHARS` 被
message_slimmer 与 langfuse_span 共读）；工具名判据抽到公共模块
（`agent/utils/query_tools.DATA_TOOL_SUFFIXES` 三处共用；`cube_route_gate` 直接
`from agent.middlewares.query_gate import _thread_id, _tool_args`——「各自维护一份必然
漂移，而漂移的后果是软门静默失效」）。

**7.3 纵深防御，不搞二选一。** `tool_filter`（看不见）+ `query_gate` 规则零（拦得住）
是明确设计的两道：「看不见 + 拦得住是纵深，非二选一」——出站裁剪管不了参数里的库名、
历史消息里的存量工具名、模型幻觉的工具名。

**7.4 一个 state 字段只允许一个写入者。** TraceRecorder 与 TokenMeter 的分工注释
（§5.3）是血的教训：双写 `token_stats` → reducer 累加重复 → 统计翻倍。

**7.5 软门统一范式。** 每线程至多提醒一次 + 独立命名空间（cube_route_gate **不与**
query_gate 共用 `_REMINDED`——「共用会让两个软门互相吃掉提醒机会」）+ 文案里写清
**逃生口**（「原样重发一次即可，本线程不会再拦」）+ 一键 env 回退。

**7.6 错误文案是给模型的指令，不是给人的日志。** 被拦消息要同时做到：
`status="error"` + `Error:` 前缀（观测口径联动）、说明**为什么**被拦、给出**下一步
该调什么**（具体工具名与参数形态）、只陈述可证事实（`dynamic_mcp_tools._REMOVED_HINT`
的血案：文案断言「库已被删除」，真因是上游 wren 压根没这个工具，模型把谎言转述给了用户）。

**7.7 失败信号跨中间件接力。** 「返回友好消息」类中间件（timeout/quota/model_required）
必须盖 `failure_signal` 失败戳，下游（caliber_gate 放行失败终局、run-status 端点、
check_async_task）读戳分流——否则每个下游各自猜，各猜各错。

**7.8 观测类永远旁路。** langfuse_span / trace_recorder / prom 埋点全部 try/except 吞掉
自身异常：「监控坏了不能让问答跟着挂」。

## 8. 完整代码示例（从零开始）

### 8.1 示例一：`SlowToolAlarmMiddleware` — 工具计时 + 慢结果告警

覆盖知识点：`wrap_tool_call` 双版本、fail-open、env 开关、改写时保形状、日志纪律。

```python
"""SlowToolAlarmMiddleware — 工具调用计时；超过阈值在结果尾部追加告警标记。

教学示例：演示 wrap_tool_call 的标准骨架——
- sync/async 双实现，公共后处理抽 _after（全仓统一模式）；
- fail-open：自身异常绝不影响工具结果；
- env 一键关闭 + 阈值可配；
- 改写 ToolMessage 用 model_copy(update=...)，保留 tool_call_id/name/status。
"""
from __future__ import annotations

import logging
import os
import time
from typing import Any, Callable

from langchain.agents.middleware import AgentMiddleware
from langchain_core.messages import ToolMessage
from langgraph.prebuilt.tool_node import ToolCallRequest

_logger = logging.getLogger(__name__)

# 阈值与开关都走环境变量，非法值回落默认（照抄 failure_circuit._env_int 的口径）
_DEFAULT_SLOW_MS = 10_000


def _enabled() -> bool:
    """NL2SQL_SLOW_TOOL_ALARM=off 一键回退（生产中间件的标配）。"""
    return (os.getenv("NL2SQL_SLOW_TOOL_ALARM") or "").strip().lower() not in {
        "off", "0", "false", "no",
    }


def _tool_name(request: ToolCallRequest) -> str:
    """tool_call 是 dict（TypedDict），必须 .get 而不能 getattr。"""
    tc = getattr(request, "tool_call", None) or {}
    if isinstance(tc, dict):
        return str(tc.get("name", "") or "")
    return str(getattr(tc, "name", "") or "")


class SlowToolAlarmMiddleware(AgentMiddleware):
    """工具执行超过 slow_ms 时，在结果文本尾部追加一行机读告警标记。"""

    def __init__(self, *, slow_ms: int | None = None) -> None:
        # 构造参数优先（供单测注入），缺省读 env
        self._slow_ms = slow_ms if slow_ms is not None else int(
            os.getenv("NL2SQL_SLOW_TOOL_MS", "") or _DEFAULT_SLOW_MS
        )

    def _after(self, request: ToolCallRequest, result: Any, elapsed_ms: int) -> Any:
        """公共后处理（sync/async 共用）。任何异常都透传原结果。"""
        try:
            if elapsed_ms < self._slow_ms:
                return result
            if not isinstance(result, ToolMessage):
                return result                     # Command 等形态不动
            name = _tool_name(request) or "?"
            _logger.warning(
                "[slow_tool] %s 耗时 %dms（阈值 %dms）", name, elapsed_ms, self._slow_ms,
            )
            # 只动 content；tool_call_id/name/status 原样保留（配对与观测口径不破）
            content = result.content if isinstance(result.content, str) else str(result.content)
            return result.model_copy(update={
                "content": f"{content}\n\n【slow-tool:{name}:{elapsed_ms}ms】",
            })
        except Exception:                          # noqa: BLE001
            _logger.warning("[slow_tool] 后处理异常，透传原结果", exc_info=True)
            return result

    # ── 同步版（脚本/单测路径）──────────────────────────────
    def wrap_tool_call(
        self,
        request: ToolCallRequest,
        handler: Callable[[ToolCallRequest], ToolMessage],
    ) -> ToolMessage:
        if not _enabled():
            return handler(request)                # 关闭时零动作直通
        t0 = time.perf_counter()
        result = handler(request)                  # handler 的异常照常上抛（不吞业务错）
        return self._after(request, result, int((time.perf_counter() - t0) * 1000))

    # ── 异步版（生产路径）───────────────────────────────────
    async def awrap_tool_call(
        self,
        request: ToolCallRequest,
        handler: Callable[[ToolCallRequest], Any],
    ) -> ToolMessage:
        if not _enabled():
            result = handler(request)
            if hasattr(result, "__await__"):       # 全仓统一的 awaitable 兼容写法
                result = await result
            return result
        t0 = time.perf_counter()
        result = handler(request)
        if hasattr(result, "__await__"):
            result = await result                  # ⚠️ 真耗时在 await 里（model_timeout 同款教训）
        return self._after(request, result, int((time.perf_counter() - t0) * 1000))
```

挂载：追加到 `_middleware` 中 `LangfuseSpanMiddleware` **之前**（外层），
这样告警标记不会污染 span 里的原始 output。

### 8.2 示例二：`TurnBudgetMiddleware` — 每轮工具预算（节点型钩子 + jump_to + 自定义 state）

覆盖知识点：`before_model` 节点钩子、`hook_config(can_jump_to=["end"])`、
自定义 `state_schema` + reducer、从 state 推导计数（不落进程内账本）。

```python
"""TurnBudgetMiddleware — 本轮（最后一条 HumanMessage 之后）工具调用数超预算时提前收尾。

教学示例：演示节点型钩子的完整套路——
- before_model 每轮模型调用前必触发（START 与 tools 回环都先进它）；
- 计数从 state 推导（数本轮 ToolMessage 条数），重启/多 worker 天然正确
  （caliber_gate._retries_in_turn 同款口径，不用 query_gate._REMINDED 那种进程内 set）；
- jump_to="end" 必须配 @hook_config(can_jump_to=["end"])，否则被静默丢弃；
- state_schema 扩展自定义字段（budget_warned），PrivateStateAttr 语义 = 不进输入输出 schema。
"""
from __future__ import annotations

import logging
import os
from typing import Any, NotRequired, TypedDict

from langchain.agents.middleware import AgentMiddleware, AgentState, hook_config
from langchain_core.messages import HumanMessage, ToolMessage

_logger = logging.getLogger(__name__)

_DEFAULT_BUDGET = 60


class BudgetState(AgentState):
    """扩展 state：本中间件私有的标记字段。"""
    budget_warned: NotRequired[bool]     # 是否已经警告过（避免每轮重复注入）


def _budget() -> int:
    """env 读预算，非法值回落默认（不因配置写错改变行为）。"""
    try:
        v = int((os.getenv("NL2SQL_TURN_TOOL_BUDGET") or "").strip() or _DEFAULT_BUDGET)
        return v if v >= 1 else _DEFAULT_BUDGET
    except ValueError:
        return _DEFAULT_BUDGET


def count_turn_tool_calls(messages: list[Any]) -> int:
    """本轮工具调用数 = 最后一条 HumanMessage 之后的 ToolMessage 条数。

    纯函数，供单测（dangling_tool_calls._collect_dangling_tool_messages 同款设计）。
    """
    start = 0
    for i in range(len(messages) - 1, -1, -1):
        if isinstance(messages[i], HumanMessage):
            start = i + 1
            break
    return sum(1 for m in messages[start:] if isinstance(m, ToolMessage))


class TurnBudgetMiddleware(AgentMiddleware[BudgetState, Any, Any]):
    """超预算 → 注入一条系统通知并 jump_to end，让 agent 用现有信息收尾。"""

    state_schema = BudgetState           # ← 声明扩展 schema，字段才会进图 state

    def _check(self, state: BudgetState, runtime: Any) -> dict | None:
        try:
            msgs = list((state or {}).get("messages") or [])
            n = count_turn_tool_calls(msgs)
            budget = _budget()
            if n < budget:
                return None                              # 未超预算：零动作
            if state.get("budget_warned"):
                return {"jump_to": "end"}                # 警告过了还超 → 直接收尾
            _logger.warning("[turn_budget] 本轮工具调用 %d 次 ≥ 预算 %d，注入收尾指令", n, budget)
            return {
                "jump_to": "end",
                "budget_warned": True,
                "messages": [HumanMessage(content=(
                    f"[系统自动通知] 本轮工具调用已达 {n} 次（预算 {budget}）。"
                    "请立即停止调用工具，基于已有信息向用户如实收尾；"
                    "查不到的部分明确说明，不要继续试探。"
                ))],
            }
        except Exception:                                # noqa: BLE001  fail-open
            _logger.warning("[turn_budget] 判定异常，放行", exc_info=True)
            return None

    # ⚠️ 硬要求：没有这行装饰器，jump_to 会被静默丢弃、注入的消息污染尾部
    #   （caliber_gate docstring 的四组合实测；deepagents 栈首恒是 TodoListMiddleware，
    #    我们永远不是 loop_exit_node，享受不到那条无条件读 jump_to 的边）。
    @hook_config(can_jump_to=["end"])
    def before_model(self, state: BudgetState, runtime: Any) -> dict | None:
        return self._check(state, runtime)

    # ⚠️ 第二个参数必须叫 runtime —— langchain 按参数名注入，改叫 r 会运行期抛
    #   "missing 1 required positional argument"（caliber_gate 记录的静默坑）。
    @hook_config(can_jump_to=["end"])
    async def abefore_model(self, state: BudgetState, runtime: Any) -> dict | None:
        return self._check(state, runtime)
```

挂载与配套：`before_model` 是节点型钩子，按**列表序**执行——放在
`DanglingToolCallsMiddleware` 之后（先补 orphan 再数数）；若 agent 用了自定义
`state_schema`（如 `MainAgentState`），需把 `budget_warned` 字段并进去或确认
schema 合并策略。注入消息用仓内既有的 `[系统自动通知]` 前缀——**四处过滤器认它**
（前端标题/评测/报告锚点/trace 归并，见 `caliber_gate._RETRY_TAG` 注释），自造前缀会踩副作用。

## 9. 常见陷阱与调试技巧

每一条都在本仓留下过生产事故或实测记录，按「杀伤力」排序：

### 9.1 `jump_to` 被静默丢弃（最阴的坑）

**症状**：`after_model` 返回了 `{"jump_to": "model", "messages": [...]}`，模型却不重答，
注入的消息变成末条污染尾部。
**根因**：`jump_to` 只在本节点出边是**条件边**时才被读；条件边只在
`@hook_config(can_jump_to=[...])` 非空时才建。唯一的例外是 `loop_exit_node`
（= 列表里第一条带 after_model 的中间件），而 deepagents 把 `TodoListMiddleware`
恒放栈首 ⇒ **你永远不是它** ⇒ 装饰器是硬要求。
**调试**：数「模型被调了几次」（§6.3 图级脚本）；`caliber_gate.py:69-77` 的四组合
实测表可直接对照。

### 9.2 `request.runtime.config` 恒为空

**症状**：中间件里读 `request.runtime.config["configurable"]["db_name"]` 永远拿空串，
按库过滤/注入全部失效。
**根因**：langchain 官方明确 `Runtime` 不含 config；实证 2026-08-11（`db_name=''`）。
**定式**：

```python
from langgraph.config import get_config
cfg = get_config() or {}
db_name = (cfg.get("configurable") or {}).get("db_name", "")
meta = cfg.get("metadata") or {}      # langfuse_session_id / user_question / workspace 等
```

全仓至少 6 个中间件（tool_filter / query_keywords / thinking_toggle / model_required /
current_db_context / cube_route_gate）都带着这条实证注释。

### 9.3 只实现 sync 版，生产是 async 路径

**症状**：本地 `invoke()` 好好的，线上 `astream()` 抛
`NotImplementedError: Asynchronous implementation of awrap_model_call is not available`。
**根因**：基类对未实现的那一半**主动抛错**（types.py:574/626/732/801 的长文案就是诊断书）。
**定式**：sync/async 成对实现；async 版里 handler 的返回值先
`hasattr(result, "__await__")` 判断再 await（全仓统一模式）；**计时要覆盖 await 段**
（「只量 `handler(request)` 会量成 0」——model_timeout.py:26）。

### 9.4 在 `self` 上缓存请求级状态（单例并发必错）

**症状**：工具事件系统性挂到「最后一个发起模型调用的会话」上；低并发测不出来，
上量必现。
**根因**：中间件实例是**进程内单例**，10 个并发 run 共用一个 `self`；
模型调用与工具调用之间隔着整个 LLM 推理时长。
**定式**：请求级数据现取（`request.runtime.execution_info.thread_id` /
`langgraph.config.get_config()`），跨轮数据进 state 或从 state 推导。
必须用进程内结构时（软门 `_REMINDED`、模型缓存）要：加锁 + 容量上限 + 想清楚
重启失忆的后果（`trace_recorder.py:66-73` 有完整论证）。

### 9.5 改写 ToolMessage 丢形状

**症状**：改写内容后 LangGraph 报 tool 配对错误、前端步骤卡片错乱、
Langfuse `sql_exec_success` 记错。
**定式**：`result.model_copy(update={"content": ...})` 只动 content，
**`tool_call_id` / `name` / `status` 一个都不能丢**；自己构造拒绝消息时三件套齐全 +
`status="error"` + `Error:` 前缀（与 `looks_like_exec_error` 观测口径联动）。
另注意 `content` 可能是 str 也可能是 content-block 列表（`failure_circuit._extract_text`
的兼容写法照抄即可）。

### 9.6 wrap 钩子的 override 不落 state

**症状**：在 `wrap_model_call` 里 `request.override(messages=...)` 补了消息，
下一轮消息不见了。
**根因**：override 只改**本次出站 payload**。要持久化：节点型钩子返回 dict
（`before_model` 是「补进 state 正确位置 + 同一轮被 model 读到」的唯一挂点，
dangling_tool_calls 的选型论证），或 `ExtendedModelResponse(command=Command(update=...))`
（会排到模型回复之后，注意乱序）。

### 9.7 钩子参数名必须叫 `state` / `runtime`

langchain 按**参数名**注入。把 `runtime` 改叫 `r` → 运行期
`missing 1 required positional argument`（caliber_gate docstring 记录的静默坑）。

### 9.8 双写同一 state 字段 → reducer 重复累加

两个中间件都 `Command(update={"token_stats": ...})` ⇒ 统计翻倍（实测）。
**一个字段一个写入者**，其余只读（trace_recorder 头注就是这条纪律的成文）。

### 9.9 「护栏文案」会被模型逐字转述给用户

拒绝/改写文案里**只许陈述可证事实**。血案（dynamic_mcp_tools.py:73-79）：文案断言
「库已被删除或重新关联」，真因是上游 wren 版本压根没有该工具 ⇒ 用户以为语义库被人删了。
同理，裁剪说明写「与当前问题无关」而非「读不到」（后者诱发模型去 VFS 找不存在的路径）。

### 9.10 截断/瘦身会静默毁掉结构化内容

按行截断毁 iframe（图表全白）、按字符截断毁嵌套 JSON（归因读错数）、
落盘知识料毁口径来源（模型满 VFS 找路径）。**给每一类「不可截断的内容」建白名单 +
体积上限 + 超限 warning**（message_slimmer 三张白名单的完整事故链见 §5.7）。

### 9.11 路径归一必须与工具侧同构

`filesystem_thread_guard` 的教训：护栏拿到的是**未归一化原始入参**，工具侧却先
`validate_path()`（补前导斜杠、折叠 `.`/`//`）——不同构就有实测绕过
（`workspace/x`、`/workspace/./x`、POSIX 恰好双前导斜杠特例）。
写路径类护栏前先读工具侧的归一函数，逐条对齐。

### 9.12 调试技巧速查

- **日志前缀统一** `[模块名]`（`[fail_circuit]` / `[query_gate]` / `[ToolFilter]`…），
  生产 grep 一把捞；拦截类必记 warning（谁、什么参数、为什么拦）。
- **env 开关做 A/B**：怀疑某中间件引起回归时，先 `NL2SQL_XXX=off` 一键摘除对比，
  再决定回滚与否——这是「每个生产中间件必须有开关」的真正价值。
- **看 Langfuse span / traces.sqlite**：观测类中间件的产物就是调试现场
  （span output 是原始 payload，process_data dump 是逐工具 JSON）。
- **判线上代码版本**：`docker exec md5sum`（MEMORY 铁律：打 tag ≠ 部署，
  「未发版」标记不可信）。
- **给验收脚本留后门**：像 `model_required.is_blocked()` 那样暴露「不必搭
  ModelRequest 就能直调」的方法，E2E 脚本会感谢你的。
- 另注意本仓环境坑：bash 重定向落盘的输出会被 DLP 加密 ⇒
  `cmd > /tmp/x; grep FAIL /tmp/x` 是静默假通过（rc 真、grep 假），校验脚本慎用重定向。
