## 1. 概述：子智能体架构设计

### 1.1 为什么需要子智能体

主智能体（Orchestrator）的上下文窗口是稀缺资源。当一个任务需要几十次工具调用、产生大量中间结果时，如果全部堆在主线程里，会导致：

- **上下文膨胀**：token 消耗剧增，模型注意力被中间噪音稀释；
- **无法并行**：主线程是串行的对话循环，多个独立任务只能排队；
- **职责混杂**：不同领域（如 NL2SQL、报告生成）的工具和提示词互相干扰。

子智能体（Subagent）的核心价值是：**在隔离的上下文窗口里完成一段多步工作，只把浓缩后的最终结果交还主智能体**。deepagents 的 `TASK_TOOL_DESCRIPTION` 里写得很直白（源码摘录）：

```text
Launch an ephemeral subagent to handle complex, multi-step independent tasks
with isolated context windows.
...
Each agent invocation is stateless. You will not be able to send additional
messages to the agent, nor will the agent be able to communicate with you
outside of its final report.
```

### 1.2 两种子智能体：同步 vs 异步

deepagents 提供了两套完全独立的子智能体机制，`create_deep_agent` 会根据 spec 的字段自动分流（`graph.py`）：

```python
# graph.py — create_deep_agent 内部的分流逻辑
for spec in subagents or []:
    if "graph_id" in spec:
        # 有 graph_id 字段 → 异步子智能体（远程 Agent Protocol 服务器）
        async_subagents.append(cast("AsyncSubAgent", spec))
        continue
    if "runnable" in spec:
        # 有 runnable 字段 → 预编译同步子智能体（CompiledSubAgent）
        inline_subagents.append(spec)
    else:
        # 声明式同步子智能体（SubAgent）→ 填默认值、装配中间件栈
        ...
```

| 维度 | 同步子智能体（`SubAgentMiddleware`） | 异步子智能体（`AsyncSubAgentMiddleware`） |
|---|---|---|
| 暴露的工具 | 1 个：`task` | 5 个：`start/check/update/cancel/list_async_task(s)` |
| 执行位置 | **进程内**，作为 `task` 工具调用的嵌套子图 | **远程服务器**（Agent Protocol / LangGraph Platform / 自托管） |
| 阻塞语义 | 工具调用阻塞到子智能体跑完才返回 | `start_async_task` 立即返回 task_id，后台执行 |
| 结果形态 | 单条 `ToolMessage`（最终 AIMessage 文本或结构化 JSON） | 通过 `check_async_task` 主动拉取；可中途 `update` 追加指令 |
| 生命周期 | 一次性（ephemeral）、无状态 | 任务登记在 state 的 `async_tasks` 字典里，跨轮次可追踪 |
| 通信方向 | 单向：主 → 子（一次任务描述），子 → 主（一次最终报告） | 双向：可多次向运行中的子任务发消息 |
| 典型场景 | 隔离式研究、并行分析、结构化抽取 | 长耗时任务（NL2SQL 查询）、需要用户中途干预的任务 |

### 1.3 选择标准

- **任务能在一次工具调用的时长内完成、且主智能体需要立刻用结果做下一步** → 同步。
- **任务耗时长（分钟级）、用户可能想中途查进度/改指令/取消、或者要同时跑很多个** → 异步。
- 同步子智能体也可以并行——只要主智能体在**同一条 AI 消息里发出多个 `task` 工具调用**，ToolNode 会并发执行它们（`TASK_TOOL_DESCRIPTION` 第 1 条 usage note 就是教模型这么做）。但这种并行仍受"整轮工具调用必须全部结束才能回到模型"的约束；异步则完全解耦。

本项目（nl2sql）的选择是：**主智能体用异步子智能体跑 NL2SQL 查询**（`main_agent.py`），因为一次问数动辄几十秒到几分钟，且前端需要实时进度条、用户需要"停止"按钮——这些都必须要有 task_id 可追踪的后台任务模型。

## 2. SubAgentMiddleware（同步）详解

### 2.1 子智能体的三种规格

`subagents.py` 定义了两种 spec，加上运行时自动补齐的 general-purpose，共三种形态：

**（1）`SubAgent` —— 声明式规格（TypedDict）**

```python
# subagents.py 源码摘录（字段有删减，注释为原文翻译）
class SubAgent(TypedDict):
    name: str                # 唯一标识，主智能体调 task() 时用它选择
    description: str         # 干什么的——主智能体据此决定何时委派
    system_prompt: str       # 子智能体的系统提示词

    tools: NotRequired[...]          # 不填则继承主智能体的工具
    model: NotRequired[str | BaseChatModel]  # 'provider:model-name' 或模型实例
    middleware: NotRequired[list[AgentMiddleware]]  # 追加在默认栈之后
    interrupt_on: NotRequired[dict]  # 子智能体专属 HITL 配置（需 checkpointer）
    skills: NotRequired[list[str]]   # SkillsMiddleware 的技能目录
    permissions: NotRequired[list[FilesystemPermission]]  # 文件权限；给了就整体替换父级规则
    response_format: NotRequired[...]  # 结构化输出 schema（Pydantic/dataclass/JSON Schema）
```

**（2）`CompiledSubAgent` —— 预编译规格**

```python
class CompiledSubAgent(TypedDict):
    name: str
    description: str
    runnable: Runnable   # 任意 state schema 含 'messages' 键的 Runnable
```

注意两条硬性约束（源码 docstring）：

- `runnable` 的状态 schema **必须包含 `messages` 键**——这是子智能体向主智能体回传结果的唯一通道；
- `CompiledSubAgent` **不继承** `create_deep_agent(state_schema=...)`，也不继承顶层 `interrupt_on`——调用方自己负责。

**（3）general-purpose 默认子智能体**

```python
# subagents.py
GENERAL_PURPOSE_SUBAGENT: SubAgent = {
    "name": "general-purpose",
    "description": DEFAULT_GENERAL_PURPOSE_DESCRIPTION,
    "system_prompt": DEFAULT_SUBAGENT_PROMPT,
}
```

若调用方没有提供名为 `general-purpose` 的子智能体，`graph.py` 会自动补一个（继承主智能体的 model 和全部 tools），除非 harness profile 显式禁用。这意味着**即使你只配了异步子智能体，`task` 工具通常仍然存在**，挂着一个"和主智能体能力相同"的通用同步子智能体。

### 2.2 创建：从 spec 到 Runnable

`create_sub_agent` 是声明式 spec 的编译入口：

```python
# subagents.py 源码摘录
def create_sub_agent(spec, *, state_schema=None, response_format=None) -> Runnable:
    if "model" not in spec:
        raise ValueError(f"SubAgent '{spec['name']}' must specify 'model'")
    if "tools" not in spec:
        raise ValueError(f"SubAgent '{spec['name']}' must specify 'tools'")

    model = resolve_model(spec["model"])           # 字符串 → init_chat_model；实例 → 原样
    middleware = list(spec.get("middleware", []))

    interrupt_on = spec.get("interrupt_on")
    if interrupt_on:
        middleware.append(HumanInTheLoopMiddleware(interrupt_on=interrupt_on))

    selected_response_format = response_format if response_format is not None \
        else spec.get("response_format")
    create_agent_kwargs = {
        "system_prompt": spec["system_prompt"],
        "tools": spec["tools"],
        "middleware": middleware,
        "name": spec["name"],                       # ← 关键：绑定 lc_agent_name
        "response_format": selected_response_format,
    }
    if state_schema is not None:
        create_agent_kwargs["state_schema"] = state_schema
    return create_agent(model, **create_agent_kwargs)
```

解析要点：

1. **每个子智能体就是一个完整的 `create_agent` 图**——有自己的 model/tools/middleware 循环，与主智能体同构；
2. `name=spec["name"]` 会被 `create_agent` 写进 run config 的 `metadata.lc_agent_name`，这是第 7 节 `SubagentTransformer` 识别子智能体边界的依据；
3. `model`/`tools` 缺失直接抛 `ValueError`——但走 `create_deep_agent` 时这两项已在图组装阶段补齐（见 2.6），所以只有绕过它直接调 `create_sub_agent` 才会踩到；
4. `resolve_model`（`_models.py`）对字符串走 `init_chat_model(model, **apply_provider_profile(model))`，支持 `'openai:gpt-5.5'` 这类 `provider:model` 写法，并叠加 provider profile（如 OpenAI Responses API 默认值）。

### 2.3 调度：`task` 工具的执行路径

`_build_task_tool` 把所有子智能体 spec 编译进一个闭包，产出唯一的 `task` 工具：

```python
# subagents.py 源码摘录（核心路径，有删减）
def task(description: str, subagent_type: str, runtime: ToolRuntime) -> str | Command:
    if subagent_type not in subagent_graphs:
        # 未知类型不抛异常，而是返回错误文本让模型自纠
        return f"We cannot invoke subagent {subagent_type} because it does not exist, ..."
    if not runtime.tool_call_id:
        raise ValueError("Tool call ID is required for subagent invocation")

    subagent, subagent_state = _validate_and_prepare_state(subagent_type, description, runtime)

    # 父级的 callbacks/tags/configurable 会自动透传到子图：
    # langgraph 的 ensure_config 从环境父 config 播种并按 key 合并（langgraph#7926），
    # 子智能体自己绑定的 config（lc_agent_name、recursion_limit）在冲突时获胜。
    subagent_config: RunnableConfig = {"configurable": {"ls_agent_type": "subagent"}}

    with _subagent_tracing_context():          # LangSmith 追踪打 subagent 标签
        result = subagent.invoke(subagent_state, subagent_config)   # ← 同步阻塞点
    return _return_command_with_state_update(result, runtime.tool_call_id)
```

`atask` 是它的 async 孪生版本，唯一区别是 `await subagent.ainvoke(...)`。两者通过 `StructuredTool.from_function(name="task", func=task, coroutine=atask, args_schema=TaskToolSchema)` 注册为同一个工具——**同步/异步执行路径由外层图的调用方式决定，工具定义只写一次**。

调度流程四步（对应 `TASK_SYSTEM_PROMPT` 里的 lifecycle）：

```text
Spawn（模型发出 task 调用，带 description + subagent_type）
  → Run（工具内部 subagent.invoke，独立上下文里自主多步执行）
  → Return（提取最终消息，打包成 Command）
  → Reconcile（ToolMessage 回到主线程，主智能体综合结果）
```

### 2.4 通信：状态如何进、结果如何出

**入向**（`_validate_and_prepare_state`）：

```python
# 复制父 state，剔除三类 key，再用任务描述替换整个消息历史
subagent_state = {k: v for k, v in runtime.state.items() if k not in _EXCLUDED_STATE_KEYS}
subagent_state = {k: v for k, v in subagent_state.items() if k not in private_state_keys}
subagent_state["messages"] = [HumanMessage(content=description)]
```

其中：

```python
_EXCLUDED_STATE_KEYS = {"messages", "todos", "structured_response"}
```

- `messages` 被显式替换为**只含一条 HumanMessage**——子智能体看不到主线程的对话历史，一切上下文必须由 `description` 携带（这就是"隔离上下文窗口"的实现）；
- `todos`、`structured_response` 没有跨 agent 传递的语义；
- `private_state_keys` 是各中间件 state schema 里标了 `PrivateStateAttr` 的字段（见第 4 节），属于"中间件私产"，不外泄给子智能体。

**出向**（`_return_command_with_state_update`）：

```python
# subagents.py 源码摘录
def _return_command_with_state_update(result: dict, tool_call_id: str) -> Command:
    if "messages" not in result:
        raise ValueError("CompiledSubAgent must return a state containing a 'messages' key...")

    # 除三个排除键外，子智能体 state 的其余字段会合并回父 state
    state_update = {k: v for k, v in result.items() if k not in _EXCLUDED_STATE_KEYS}

    structured = result.get("structured_response")
    if structured is not None:
        # 优先返回结构化输出（Pydantic → model_dump_json；dataclass → asdict）
        content = structured.model_dump_json() if hasattr(structured, "model_dump_json") else ...
    else:
        # 否则回溯到最后一条非空 AIMessage 文本。
        # （Anthropic 偶尔在成功的工具调用后追加一条空的 end_turn AIMessage，
        #   倒序找非空文本可以避免把空串当成结果。）
        content = ""
        for msg in reversed(result["messages"]):
            if isinstance(msg, AIMessage):
                text = msg.text.rstrip() if msg.text else ""
                if text:
                    content = text
                    break

    return Command(update={
        **state_update,
        "messages": [ToolMessage(content, tool_call_id=tool_call_id)],
    })
```

解析要点：

1. 返回的是 langgraph 的 `Command`，不是普通字符串——这让工具可以**同时更新 state 的任意字段**（例如子智能体写的文件状态、自定义 state 字段）并追加 ToolMessage；
2. 主智能体默认只能看到 `content` 一条文本。`DEFAULT_SUBAGENT_PROMPT` 因此专门叮嘱子智能体："The calling agent only sees your final assistant message... Ensure your final response contains the complete answer."
3. **动态 response_format**：调用方可以在 config 里塞 `configurable["__deepagents_subagent_response_format"]`，`_select_subagent` 检测到后会用该 schema 现场重编译子智能体——同一个子智能体可以在不同调用点返回不同结构。

### 2.5 SubAgentMiddleware 本体

```python
# subagents.py 源码摘录（有删减）
class SubAgentMiddleware(AgentMiddleware[Any, ContextT, ResponseT]):
    def __init__(self, *, backend, subagents, system_prompt=TASK_SYSTEM_PROMPT,
                 task_description=None, private_state_keys=None, state_schema=None):
        if not subagents:
            raise ValueError("At least one subagent must be specified")
        self.subagent_names = frozenset(spec["name"] for spec in subagents)
        task_tool = _build_task_tool(subagents, task_description,
                                     private_state_keys=..., state_schema=...)
        # 系统提示词追加"可用子智能体清单"
        agents_desc = "\n".join(f"- {s['name']}: {s['description']}" for s in subagents)
        self.system_prompt = system_prompt + "\n\nAvailable subagent types:\n\n" + agents_desc
        self.tools = [task_tool]     # ← 中间件通过 tools 属性向图注入 task 工具

    def wrap_model_call(self, request, handler):
        # 每次调模型前把子智能体使用说明拼进 system message
        new_system_message = append_to_system_message(request.system_message, self.system_prompt)
        return handler(request.override(system_message=new_system_message))
```

中间件对图的全部贡献就两件事：**注入 `task` 工具**（`self.tools`，由 `create_agent` 收集进 ToolNode）+ **注入系统提示词**（`wrap_model_call` 钩子）。`private_state_keys` 还提供了 setter——设置后会重建 task 工具（因为剔除逻辑被闭包捕获了）。

### 2.6 图组装：create_deep_agent 为子智能体做了什么

`graph.py` 对每个声明式 `SubAgent` 做的"补齐"（源码要点归纳）：

```python
# graph.py — create_deep_agent 内部（节选归纳）
raw_subagent_model = spec.get("model", model)        # 模型默认继承主智能体
subagent_permissions = spec.get("permissions", permissions)  # 权限默认继承主智能体

subagent_middleware = [
    TodoListMiddleware(),                            # 子智能体也有 write_todos
    FilesystemMiddleware(backend=backend, _permissions=subagent_permissions),
    create_summarization_middleware(subagent_model, backend),  # 子智能体也做上下文压缩
    PatchToolCallsMiddleware(),
]
if spec.get("skills"):
    subagent_middleware.append(SkillsMiddleware(backend=backend, sources=...))
subagent_middleware.extend(spec.get("middleware", []))   # 用户自定义中间件排后面
_append_prompt_caching_middleware(subagent_middleware)

subagent_interrupt_on = spec.get("interrupt_on", interrupt_on)  # HITL 默认继承顶层
raw_subagent_tools = spec.get("tools") if "tools" in spec else tools  # 工具默认继承

processed_spec = {**spec, "model": subagent_model,
                  "tools": subagent_tools or [], "middleware": subagent_middleware}
```

即：**声明式子智能体自动获得一套与主智能体同规格的默认中间件栈**（todos、文件系统、摘要、工具调用修补、提示词缓存），用户只需声明差异部分。主智能体的中间件栈顺序则为：

```text
TodoList → Skills(可选) → Filesystem → SubAgent(有同步子智能体时)
→ Summarization → PatchToolCalls → AsyncSubAgent(有异步子智能体时)
→ 用户 middleware → profile extra → 工具排除 → PromptCaching
→ Memory(可选) → HumanInTheLoop(可选)
```

`FilesystemMiddleware` 与 `SubAgentMiddleware` 被列入 `_REQUIRED_MIDDLEWARE`，**任何 harness profile 都不允许把它们排除掉**（排除会直接抛 `ValueError`），因为前者承担权限安全闸、后者承担 `task` 工具。

## 3. AsyncSubAgentMiddleware（异步）详解

### 3.1 设计定位

`async_subagents.py` 文件头注释：

```text
Async subagents use the LangGraph SDK to launch background runs on remote
Agent Protocol servers. Unlike synchronous subagents (which block until
completion), async subagents return a task ID immediately, allowing the main
agent to monitor progress and send updates while the subagent works.
```

关键词是 **remote**。异步子智能体不在本进程内执行——它是一个部署在别处（LangGraph Platform 托管或自托管 langgraph server）的图，主智能体通过 `langgraph_sdk` 的 HTTP 客户端对它做 thread/run 级别的操作。规格定义：

```python
class AsyncSubAgent(TypedDict):
    name: str           # 唯一标识
    description: str    # 供主智能体决定何时委派
    graph_id: str       # 远程服务器上的图名或 assistant ID
    url: NotRequired[str]              # Agent Protocol 服务器地址；缺省走 SDK 默认端点；
                                       # 传 None 可用 ASGI 进程内传输（仅异步调用支持）
    headers: NotRequired[dict[str, str]]  # 自托管服务器的自定义认证头
```

`_resolve_headers` 会默认补 `x-auth-scheme: langsmith`（LangGraph Platform 需要，自托管服务器通常忽略）。

### 3.2 任务台账：AsyncTask 与状态扩展

```python
# async_subagents.py 源码摘录
class AsyncTask(TypedDict):
    task_id: str        # 唯一标识（= thread_id）
    agent_name: str     # 哪类异步子智能体在跑
    thread_id: str      # 远程服务器上的会话线程 ID
    run_id: str         # 当前这次执行的 run ID（update 后会换）
    status: str         # 'running' / 'success' / 'error' / 'cancelled' ...
    created_at: str          # ISO-8601 UTC
    last_checked_at: str     # 上次通过 SDK 查状态的时间
    last_updated_at: str     # 状态变化或发送 update 的时间

def _tasks_reducer(existing, update):
    """把任务更新合并进现有 tasks 字典（按 key 合并而非整体替换）。"""
    merged = dict(existing or {})
    merged.update(update)
    return merged

class AsyncSubAgentState(AgentState):
    async_tasks: Annotated[NotRequired[dict[str, AsyncTask]], _tasks_reducer]
```

`AsyncSubAgentMiddleware.state_schema = AsyncSubAgentState`，`create_agent` 会把它合并进图的总 state schema。这个设计有两层意义：

1. **task_id 持久化在 checkpoint 里**，跨轮次、跨上下文压缩都活着（源码注释："Task IDs are persisted in the agent state under `async_tasks` so they survive context compaction/offloading"）；
2. `_tasks_reducer` 按 key 合并，**多个并发任务各写各的 key，互不覆盖**——本项目把这个模式推广到了 `query_headers`/`subagent_steps_map` 等字段（见第 11 节）。

### 3.3 五个工具的实现

**（1）`start_async_task` —— 异步创建**

```python
# async_subagents.py 源码摘录（同步版，异步版同构）
def start_async_task(description, subagent_type, runtime) -> str | Command:
    error = _validate_agent_type(agent_map, subagent_type)
    if error:
        return error                       # 未知类型 → 错误文本，不抛异常
    spec = agent_map[subagent_type]
    try:
        client = clients.get_sync(subagent_type)
        thread = client.threads.create()   # ① 在远程服务器开一个新会话线程
        run = client.runs.create(          # ② 在该线程上创建一个后台 run
            thread_id=thread["thread_id"],
            assistant_id=spec["graph_id"],
            input={"messages": [{"role": "user", "content": description}]},
        )                                  #    runs.create 不等待执行，立即返回 run 元数据
    except Exception as e:
        return f"Failed to launch async subagent '{subagent_type}': {e}"

    task_id = thread["thread_id"]          # task_id 就是 thread_id
    task: AsyncTask = {"task_id": task_id, "agent_name": subagent_type,
                       "thread_id": task_id, "run_id": run["run_id"],
                       "status": "running", ...}
    return Command(update={
        "messages": [ToolMessage(f"Launched async subagent. task_id: {task_id}",
                                tool_call_id=runtime.tool_call_id)],
        "async_tasks": {task_id: task},    # 经 _tasks_reducer 合并进 state
    })
```

要点：`client.runs.create`（不带 `wait`）是**投递语义**——远程服务器把 run 排进队列后立刻应答，真正的执行发生在服务器侧的后台。`_ClientCache` 按 `(url, headers)` 惰性创建并缓存 SDK 客户端；同步客户端必须有 `url`（`url=None` 的 ASGI 传输只支持异步调用，`get_sync` 会抛 `ValueError`）。

**（2）`check_async_task` —— 结果回调（拉取式）**

```python
def check_async_task(task_id, runtime) -> str | Command:
    task = _resolve_tracked_task(task_id, runtime)   # 从 state.async_tasks 找台账
    if isinstance(task, str):
        return task                                   # "No tracked task found..."
    client = clients.get_sync(task["agent_name"])
    run = client.runs.get(thread_id=..., run_id=...)  # 查 run 状态
    thread_values = {}
    if run["status"] == "success":
        thread = client.threads.get(thread_id=...)    # 成功才拉全量线程 state
        thread_values = thread.get("values") or {}
    result = _build_check_result(run, task["thread_id"], thread_values)
    return _build_check_command(result, task, runtime.tool_call_id)
```

`_build_check_result` 在 success 时取 `thread_values["messages"][-1]` 的 content 作为 result；error 时带上 `run["error"]`。`_build_check_command` 则把最新状态写回 `async_tasks`（只有状态真的变了才刷新 `last_updated_at`）。

注意：**没有推送回调，一切靠拉取**。系统提示词为此定了严格纪律（`ASYNC_TASK_SYSTEM_PROMPT` 摘录）：

```text
- After launching, ALWAYS return control to the user immediately.
  Never auto-check after launching.
- Never poll `check_async_task` in a loop. Check once per user request, then stop.
- Task statuses in conversation history are ALWAYS stale — ... ALWAYS call a
  tool to get the current status.
```

**（3）`update_async_task` —— 向运行中的子任务追加指令**

核心一行：

```python
run = client.runs.create(
    thread_id=tracked["thread_id"],        # 同一个线程 → 子智能体能看到全部历史
    assistant_id=spec["graph_id"],
```

`task_id` 不变、`run_id` 换新。这是异步相对同步的最大能力差异：**同步子智能体是一次性的（stateless, one-shot），异步子智能体的线程是有记忆的、可多轮交互的**。

**（4）`cancel_async_task`**：`client.runs.cancel(thread_id, run_id)`，然后把台账状态置 `cancelled`。

**（5）`list_async_tasks`**：对 state 里的所有任务批量刷活状态。有一个精细的优化：

## 4. 子智能体状态管理（_state.py）

`_state.py` 只有一个函数，但它是同步子智能体状态隔离的守门员：

```python
# deepagents/middleware/_state.py 全文核心
def private_state_field_names(*state_schemas: type[object]) -> frozenset[str]:
    """返回所有 state schema 中标注了 PrivateStateAttr 的字段名。"""
    names: set[str] = set()
    for state_schema in state_schemas:
        with contextlib.suppress(Exception):
            hints = get_type_hints(state_schema, include_extras=True)  # 保留 Annotated 元数据
            for name, annotation in hints.items():
                if _has_marker(annotation, PrivateStateAttr):
                    names.add(name)
    return frozenset(names)

def _has_marker(annotation: object, marker: object) -> bool:
    origin = get_origin(annotation)
    if origin is Annotated:
        args = get_args(annotation)
        return any(meta is marker for meta in args[1:])   # Annotated[T, PrivateStateAttr]
    if origin is not None:
        return any(_has_marker(arg, marker) for arg in get_args(annotation))  # 递归剥泛型
    return False
```

**工作机制**：langchain 的中间件可以用 `Annotated[T, PrivateStateAttr]` 声明"这个 state 字段是我私有的"。`graph.py` 在组装完主智能体中间件栈后统一收集：

```python
# graph.py
private_state_keys = private_state_field_names(
    *(mw.state_schema for mw in deepagent_middleware if getattr(mw, "state_schema", None) is not None)
)
if sub_agent_middleware is not None:
    sub_agent_middleware.private_state_keys = private_state_keys   # setter 会重建 task 工具
```

此后每次 `task` 调用，`_validate_and_prepare_state` 都会把这些 key 从传给子智能体的 state 副本里剔除（出向的 `state_update` 同样受 `_EXCLUDED_STATE_KEYS` 约束）。

**状态传递全景图**（同步子智能体）：

```text
父 state ──┬── 剔除 messages/todos/structured_response（固定排除）
           ├── 剔除 PrivateStateAttr 字段（中间件私有）
           ├── 其余字段原样拷贝（files、自定义 state 字段…）
           └── messages := [HumanMessage(description)]   ← 唯一"新鲜"输入
                          │
                          ▼  subagent.invoke(...)
子 state（独立演化：自己的 messages/todos/中间件私有字段）
                          │
                          ▼  返回 Command
父 state ←── state_update（剔除三键后的子 state 差量）
         ←── ToolMessage(最终 AIMessage 文本 或 structured_response JSON)
```

**异步子智能体的状态则是"两套账"**：主智能体 state 里只有 `async_tasks` 台账（元数据），业务 state 全在远程线程里，`check_async_task` 成功时才通过 `threads.get` 拉一份快照回来。两者之间没有自动同步——这正是本项目要自建 sync watcher 线程的原因（第 11 节）。

## 5. LangGraph 子图（Subgraph）机制

### 5.1 同步子智能体 = 工具调用里嵌套的独立图

deepagents 的同步子智能体**不是**通过 LangGraph 的"子图节点"（`graph.add_node("sub", compiled_subgraph)`）挂载的，而是把编译好的子图 runnable **藏进 `task` 工具的执行体**里：

```python
result = subagent.invoke(subagent_state, subagent_config)
```

这样做的取舍：

- ✅ 子智能体的调用完全由**模型**决定（发不发 task、发给谁、带什么描述），不需要在图拓扑里预先连边；
- ✅ 天然支持一条 AI 消息里多个 task 并发（ToolNode 并发执行工具调用）；
- ✅ 父子 state 边界清晰（进出都经过显式的过滤/合并代码）；
- ⚠️ 子图的执行对父图而言是"一次工具调用"的黑盒，父图的 checkpoint 不会为子图内部的每一步单独存档（子智能体 invoke 时不带父 checkpointer，中间状态不持久化——所以同步子智能体是 ephemeral 的）。

不过父子仍处在同一个 langgraph 运行时上下文里：`ensure_config` 会把环境 config（callbacks、tags、configurable）播种给子 run，并按 key 合并（langgraph#7926），所以 LangSmith/Langfuse 追踪、`thread_id` 等 configurable 都能透传，而子智能体自己 `with_config` 绑定的 `lc_agent_name`、`recursion_limit` 在冲突时获胜。`subagents.py` 里的注释专门解释了为什么只额外打一个 tracing 标签而不手工转发 config（重复转发会在 merge 语义下重复计数，如 duplicate tags）。

### 5.2 传统子图节点方式（对照）

`create_agent(name=...)` 的 docstring 指出了另一条路：

```text
name: An optional name for the `CompiledStateGraph`.
      This name will be automatically used when adding the agent graph to
      another graph as a subgraph node - particularly useful for building
      multi-agent systems.
```

即：任何编译好的 agent 图都可以直接 `parent_graph.add_node("researcher", researcher_agent)` 作为子图节点。两种方式对比：

| | 工具内嵌（deepagents task） | 子图节点（LangGraph 原生） |
|---|---|---|
| 触发者 | 模型运行时决策 | 图拓扑/条件边预先决定 |
| state 边界 | 显式过滤 + Command 合并 | 共享 schema 的 key 自动流通 |
| checkpoint | 子图内部不落父 checkpoint | 子图节点作为父图 super-step 的一部分存档 |
| 流事件命名空间 | 有独立 namespace（`ns` 深度 +1） | 同样有 namespace |

无论哪种方式，运行时的流事件都带命名空间（namespace tuple），`SubagentTransformer` 就是靠命名空间深度 + `lc_agent_name` 来识别"这是一次子智能体执行"的（第 7 节）。

### 5.3 异步子智能体 = 跨进程的"远程子图"

异步子智能体把嵌套层级从"进程内的图"提升到"服务器上的图"：主智能体与子智能体之间只有 HTTP（Agent Protocol）边界，各自有独立的 checkpoint、独立的 state schema、独立的部署周期。代价是所有状态交互都必须显式建模（task_id 台账、拉取式 check、watcher 同步线程）。

## 6. create_react_agent 与子智能体的关系

`langgraph/prebuilt/chat_agent_executor.py` 里的 `create_react_agent` 是 LangGraph v0 时代的经典 ReAct 构造器，**现已整体废弃**：

```python
# chat_agent_executor.py 源码摘录
@deprecated(
    "create_react_agent has been moved to `langchain.agents`. Please update your "
    "import to `from langchain.agents import create_agent`.",
    category=LangGraphDeprecatedSinceV10,
)
def create_react_agent(model, tools, *, prompt=None, response_format=None,
                       pre_model_hook=None, post_model_hook=None,
                       state_schema=None, ..., version: Literal["v1", "v2"] = "v2",
                       name=None, **deprecated_kwargs) -> CompiledStateGraph:
```

它的图结构是固定的两节点循环：

```text
START → [pre_model_hook?] → agent(model) → 有 tool_calls？
                                 ↑               │ 是
                                 │               ▼
                                 └──────────── tools(ToolNode)
                                                 │ 否 → END
```

- `version="v1"`：ToolNode 一次处理整条消息，消息内多个 tool call 在节点内部并行；
- `version="v2"`：每个 tool call 用 `Send` API 分发到独立的 ToolNode 实例；
- `remaining_steps`（≈ recursion_limit − 已走步数）不足 2 且还有 tool_calls 时，直接返回 "Sorry, need more steps..."，避免撞 `GraphRecursionError`；
- `pre_model_hook`/`post_model_hook` 是仅有的两个扩展点（消息裁剪、护栏等），表达能力远不如中间件体系。

**与子智能体的关系**有三层：

1. **血缘**：`langchain.agents.create_agent`（factory.py）就是它的继任者——把 pre/post hook 泛化成了完整的 `AgentMiddleware` 体系（before_agent / wrap_model_call / wrap_tool_call / after_model / state_schema / tools ...）。deepagents 的 `create_sub_agent` 和 `create_deep_agent` 底层全部走 `create_agent`。
2. **可组合性**：`create_react_agent` 的产物是 `CompiledStateGraph`（一个 Runnable），因此**可以**被塞进 `CompiledSubAgent.runnable` 当同步子智能体用——只要 state 里有 `messages` 键（它默认的 `AgentState` 满足）。这是老代码接入 deepagents 子智能体体系的最低成本路径。
3. **识别机制**：它同样支持 `name=` 参数并写入 run 元数据，所以经它创建的嵌套 agent 也能被 `SubagentTransformer` 识别为子智能体流。

新项目不应再用 `create_react_agent`；读它的价值在于理解"model↔tools 循环"这个所有 agent 框架的原子结构——中间件体系只是在这个循环的各个切面上挂了钩子。

## 7. SubagentTransformer：流事件变换与工具注入

先澄清一个容易混淆的分工：

- **工具注入**（让模型"看得见" task 工具）发生在 `SubAgentMiddleware.tools` → `create_agent` 收集 `middleware_tools` → 建 `ToolNode`；系统提示词注入发生在 `wrap_model_call`。这些在 factory.py 里完成。
- **`SubagentTransformer`**（`langchain/agents/_subagent_transformer.py`）负责的是另一件事：**流式输出（stream）层面的子智能体事件识别与分流**——让消费者能独立订阅某个子智能体的执行流。

### 7.1 注册位置

```python
# factory.py — create_agent 尾部
return graph.compile(
    checkpointer=checkpointer, store=store, ..., name=name,
    transformers=[
        ToolCallTransformer,
        SubagentTransformer,        # ← 默认注册，所有 create_agent 图都有
        *middleware_transformers,   # 中间件通过 AgentMiddleware.transformers 声明的
        *(transformers or ()),      # 调用方显式传入的
    ],
).with_config(config)   # config.metadata["lc_agent_name"] = name
```

### 7.2 子智能体边界的判定

文件头注释把判定规则讲得很清楚：

```text
A subagent boundary is a nested run whose `lc_agent_name` is set *and* differs
from its parent namespace's `lc_agent_name`. Plain subgraphs inherit the
parent's name (so they compare equal and are excluded); unnamed agents have
`lc_agent_name == None` (also excluded).
```

即三条件：**嵌套 run**（namespace 深度 = 父深度 + 1，见 `_should_track`）+ **带 `lc_agent_name`**（由 `create_agent(name=...)` 绑定）+ **与父命名空间的 name 不同**。基类 `_TasksLifecycleBase` 按 namespace 记录每个任务启动时的 `lc_agent_name`（first-write-wins），并从父任务的 pending tool calls 里恢复出触发这次子智能体执行的那个 tool call，作为 `cause`（`{"type": "toolCall", "tool_call_id": ...}`）。

### 7.3 事件分流

```python
# _subagent_transformer.py 源码摘录（有删减）
def _on_started(self, ns, graph_name, trigger_call_id) -> None:
    cause = self._pending_cause            # 触发的 tool call（因果边）
    child_lc = self._lc_by_ns.get(ns)
    if child_lc is None:                   # 无名 run → 不是子智能体，跳过
        return
    if self._mux is None or ns in self._handles:
        return
    child_mux = self._mux._make_child(ns)  # 为该子智能体建独立的流通道
    handle_cls = AsyncSubagentRunStream if child_mux.is_async else SubagentRunStream
    handle = handle_cls(mux=child_mux, path=ns, graph_name=graph_name,
                        trigger_call_id=trigger_call_id, cause=cause)
    self._handles[ns] = handle
    self._log.push(handle)                 # 句柄出现在 run.subagents 频道上

def process(self, event) -> bool:
    keep = super().process(event)          # 先做任务生命周期簿记
    handle = self._handle_for_event(event) # 按 namespace 前缀路由
    if handle is not None:
        handle._observe_event(event)
        handle._mux.push(event)            # 子作用域事件转发进子智能体自己的 mux
    return keep
```

效果：消费者在 `run.subagents` 上拿到一个 `SubagentRunStream`/`AsyncSubagentRunStream` 句柄（带 `.name` 和 `.cause` 属性），可以**独立消费该子智能体的消息流**——这对前端展示"子任务卡片"、对可观测性平台按 agent 拆 span 都是基础设施。终态处理上，`_on_terminal` 依据 status 对子 mux 做 close（成功）或 fail（失败），且 `_mark_terminal` 保证只转换一次。

`aprocess` 是异步孪生实现，注释特别说明它"重复做一遍 tasks 簿记"是为了让异步 lane 在判别子智能体边界前也观察到父身份与 pending tool calls——同步/异步两条 lane 各自完整，不交叉驱动。

## 8. 同步阻塞模型 vs 异步并发模型

### 8.1 同步：阻塞在工具槽位里

同步子智能体的时序：

```text
主图: model 节点 → AI 发出 task 调用 → tools 节点执行 task()
                                          │
                                          │ subagent.invoke(...)   ← 主图在这里停住
                                          │   子图: model→tools→model→…→最终 AIMessage
                                          ▼
      ToolMessage 写回 state ← Command(update=...)
主图: model 节点（带着子智能体的最终报告继续推理）
```

关键性质：

1. **占住一个工具执行槽**。主图的这一步 super-step 不结束，就不能回到模型节点。子智能体跑 5 分钟，主线程就"卡"5 分钟（用户视角没有任何中间反馈——子智能体不流式透出到主线程消息里，只能通过 stream 的 subagents 句柄旁路订阅）。
2. **同批并行**。一条 AI 消息里的多个 task 调用由 ToolNode 并发执行（async 路径 `asyncio.gather`），所以"3 个研究员并行调研"是同步模型支持的——但木桶效应仍在：整批必须全部完成才继续。
3. **本项目实测的容量约束**：同步工具池有满员语义（满了返回"繁忙"而非假超时），且全局并发天花板 = 10 个 run 槽，一次问数约消耗 3 个 run ⇒ 实际约 3~4 个并发查询。同步子智能体的每次 invoke 都在消耗这些真实资源。

### 8.2 异步：投递-台账-拉取

异步子智能体的时序：

```text
主图: model → start_async_task()
                │ threads.create + runs.create（HTTP，毫秒级）
                ▼
      Command: ToolMessage("task_id: xxx") + async_tasks[xxx]={status: running}
主图: model → "已启动后台任务 xxx" → END（本轮结束，控制权还给用户）

      ……远程服务器后台执行子图（分钟级）……

用户: "进度如何？"
主图: model → check_async_task(xxx)
                │ runs.get → status；success 则 threads.get → values.messages[-1]
                ▼
      ToolMessage(JSON: status/result) + async_tasks[xxx] 状态刷新
主图: model → 向用户汇报结果 → END
```

关键性质：

1. **主线程零阻塞**：`start_async_task` 的耗时是一次 HTTP 往返，主智能体立刻可以继续对话、启动更多任务。多个异步任务在远程服务器上真并发。
2. **拉取式结果收集**：没有回调/事件推送，结果靠 `check_async_task` 主动拉。这带来"历史状态永远过期"问题（提示词里的 "Task statuses in conversation history are ALWAYS stale"），必须每次现查。
3. **可中断可续写**：`update_async_task` 用 `multitask_strategy="interrupt"` 打断当前 run、在同一线程上起新 run——子智能体带着完整历史继续干活。同步子智能体绝无此能力。
4. **台账即状态机**：`async_tasks` 里每个任务的 status/时间戳三元组（created/checked/updated）构成了跨轮次的任务生命周期记录，前端与运维脚本都可以直接读它。

### 8.3 一句话总结

> 同步模型把"等待"内化为主图的一次工具调用（简单、强一致、无追踪负担，但阻塞且有木桶效应）；异步模型把"等待"外化为一个可寻址的后台任务（不阻塞、可干预、真并发，但需要台账、轮询纪律和一整套进度同步基础设施——这正是本项目 3000+ 行 watcher 代码的由来）。

## 9. 子智能体的工具隔离与共享

### 9.1 同步子智能体：默认共享、显式隔离

**共享（默认）**：`graph.py` 中 `raw_subagent_tools = spec.get("tools") if "tools" in spec else tools`——不声明 `tools` 就**整体继承主智能体的工具列表**。general-purpose 子智能体就是这样获得"与主智能体相同能力"的。`_tools.py` 的 `_apply_tool_description_overrides` 会对继承的工具做描述改写（harness profile 的措辞定制），且**不改动调用方原对象**（dict 用 copy、BaseTool 用 `model_copy`），纯 callable 原样透传。

**隔离（显式声明）**：给 spec 填 `tools=[...]` 即完全替换——子智能体只看得见清单内的工具。这是"领域专家"型子智能体的标准做法：更窄的工具面 = 更少的误用可能 + 更短的 tool schema token。

**中间件注入的工具**：子智能体的默认中间件栈（TodoList/Filesystem/Skills…）各自带工具（`write_todos`、`ls/read_file/write_file/edit_file/glob/grep`、`execute` 等），这些是子智能体**自有**的，与主智能体的同名工具互不干扰（各图各建 ToolNode）。

**权限隔离**：`permissions` 字段的语义是"给了就整体替换"（不是合并）：

```text
If omitted, inherits the parent agent's permissions. If provided, replaces
the parent agent's rules entirely for this subagent.
```

规则按声明顺序评估、首个命中生效，由 `FilesystemMiddleware` 在工具层执行（注意：直接调 backend 不经过权限层）。本项目的 `nl2sql_agent.py` 就为独立部署的子图单独配了 `NL2SQL_FILE_PERMISSIONS`（读收窄、写仅限 workspace）。

**state 隔离**：见第 4 节——`_EXCLUDED_STATE_KEYS` + `PrivateStateAttr` 双闸门。

### 9.2 异步子智能体：物理隔离

异步子智能体的工具**完全由远程图的部署决定**，主智能体侧的 spec 里根本没有 `tools` 字段。想改子智能体的工具面，得改远程那个图的代码并重新部署。这是最强的隔离，也意味着主子两侧的演进解耦（各自的发版节奏互不牵制）。

### 9.3 本项目的工具解析层

`loader.py` 的 `resolve_subagent_tools` 展示了一种 YAML 驱动的工具装配方式：配置里写工具名**子串**，运行时在可用工具池里做 `pattern in tool_name` 匹配 + 去重：

```python
# loader.py 源码摘录
for pattern in config.get("tools", []):
    matched = False
    for tool_name, tool_obj in tool_index.items():
        if pattern in tool_name:          # 子串匹配（注意误伤风险）
            resolved.append(tool_obj)
            matched = True
    if not matched:
        print(f"[WARNING] {config['name']}: 工具 '{pattern}' 未匹配")  # 静默降级
```

优点是非技术人员可以维护子智能体配置；代价是子串匹配可能误伤（如 `sql` 会匹配到所有含 sql 的工具），且未匹配只打 WARNING 不失败——工具面悄悄变窄时要有告警意识。

## 10. 错误处理与超时

### 10.1 同步子智能体

| 故障 | 行为 | 源码依据 |
|---|---|---|
| `subagent_type` 不存在 | **返回错误字符串**（不抛），模型可自纠改派 | `task()` 首行检查 |
| 缺 `tool_call_id` | 抛 `ValueError`（宿主环境 bug，不该静默） | `task()` |
| spec 缺 model/tools | 编译期抛 `ValueError` | `create_sub_agent` |
| 子智能体 state 无 `messages` | 抛 `ValueError`（CompiledSubAgent 契约违反） | `_return_command_with_state_update` |
| 子智能体内部工具报错 | 由子图自己的 ToolNode 转成 ToolMessage，子智能体自行决定重试/绕路——**不外溢到主图** | create_agent 通用行为 |
| 子智能体内部抛未捕获异常 | 沿 `invoke` 传播到父图 tools 节点，本次 run 失败 | langgraph 通用行为 |
| 步数失控 | 父图 `recursion_limit=9999`（deepagents 放宽）；子图自身默认限额；`remaining_steps` 兜底话术 | `graph.py` with_config |
| 最终消息为空 | 倒序找非空 AIMessage；全空则 ToolMessage 内容为空串 | `_return_command_with_state_update` |

超时方面，**deepagents 本身没有给同步子智能体内置时长上限**——子智能体跑多久，主图的工具调用就等多久。生产上需要在中间件层自行加模型超时/预算护栏（本项目子图挂了 `ModelTimeoutMiddleware`、失败熔断中间件等）。

### 10.2 异步子智能体

SDK 层的原则是"**所有异常转文本**"（因为 LangGraph SDK 抛无类型错误）：

```python
except Exception as e:  # noqa: BLE001  # LangGraph SDK raises untyped errors
    logger.warning("Failed to launch async subagent '%s': %s", subagent_type, e)
    return f"Failed to launch async subagent '{subagent_type}': {e}"
```

launch/check/update/cancel 全部如此——错误作为工具结果回到模型，让模型决定重试还是告知用户，而不是炸掉主图。状态机层面，run 的终态包含 `error` 与 `timeout`，`check_async_task` 在 error 时返回 `run["error"]` 详情；`_fetch_live_status` 在查询失败时**回退缓存状态**（fail-soft）。

`_TERMINAL_STATUSES` 的存在让终态任务免于反复网络查询，也隐含一个契约：**终态不可逆**。但注意本项目发现的例外——`interrupted` 在 deepagents 语义里是终态，在 nl2sql 场景却可能是"上下文压缩的瞬时暂停"，会被后续机制自动恢复，所以项目侧把它从终态集里摘了出来，单独用 120s 卡死超时兜底（见 11.3）。

### 10.3 项目加装的三层护栏（check_progress.py）

远程 run 报 `success` ≠ 业务成功。项目在 `_enhanced_build_check_result` 里做了**终态改判**：

```python
# check_progress.py 源码摘录
if result["status"] == "success":
    _mark = last_failed_mark(messages)     # 扫描消息里的失败戳（nl2sql_failure）
    if _mark:
        # 超时/额度耗尽/未配模型被中间件吞成友好文案后，图照常 END ⇒ run 报 success。
        # 不读戳的话，主 agent 会拿到 status:"success" + 一段超时文案——契约错。
        run = {**run, "status": _st, "error": _detail or run.get("error")}
        result["status"] = _st
        result["error_kind"] = _mark["kind"]
```

且**只在 run 已 success 时读戳**——running 时绝不降级（戳可能是上一轮遗留的）。这层"失败信号机读化"配合 `STALE_RUN_TIMEOUT`（600s 运行上限）、`INTERRUPTED_STUCK_TIMEOUT`（120s）等 watcher 侧超时，构成了从 SDK 状态到业务语义的完整纠错链。

## 11. 项目实战分析

本项目的子智能体架构一句话概括：**主智能体（chat_agent）通过 deepagents 异步子智能体机制把 NL2SQL 查询委派给独立部署的 `nl2sql_agent` 图，再用三个 monkey-patch + 一个 watcher 线程体系补齐 deepagents 缺失的进度可视化与状态同步能力**。

### 11.1 接线总览（main_agent.py）

```python
# src/agent/main_agent.py 源码摘录
nl2sql_async = AsyncSubAgent(
    name="nl2sql",
    description="NL2SQL查询专家",
    graph_id="nl2sql_agent",       # ← 远程 langgraph server 上注册的图名
)

agent = create_deep_agent(
    model=_agent_model,
    tools=[*mcp_tools, build_report_tool, attribution_analyze_tool],
    subagents=[nl2sql_async],      # 只有异步子智能体（task 工具仍会带 general-purpose）
    state_schema=MainAgentState,   # 自定义 state：并发多查询的键控字段
    ...
)
```

远程侧 `graphs/nl2sql_agent.py` 用同一个 `create_deep_agent` 构建独立图（自己的工具面、自己的文件权限 `NL2SQL_FILE_PERMISSIONS`、自己的中间件栈），部署为 `nl2sql_agent`。**主子两侧是两次独立发版**——这是异步架构的解耦红利，也是"打 tag ≠ 部署、判线上版本必须进容器 md5sum"这类运维纪律的根源。

`MainAgentState` 把 deepagents 的 `_tasks_reducer` 模式推广到所有并发写入字段：

```python
class MainAgentState(DeepAgentState):
    query_headers:      Annotated[NotRequired[dict[str, dict]],  _merge_dict_by_key]  # task_id → 卡片头
    subagent_steps_map: Annotated[NotRequired[dict[str, list]],  _merge_dict_by_key]  # task_id → 步骤列表
    active_queries:     Annotated[NotRequired[dict[str, bool]], _merge_dict_by_key]   # task_id → 是否运行中
```

**每个并发查询一个 task_id 键，各 watcher 线程只写自己的键，reducer 按 key 合并**——这是多子智能体并发时避免互相覆盖的核心手法（但仍需 11.3 的进程锁兜底 `as_node="__start__"` 的读-改-写竞态）。

### 11.2 sync_launcher.py：给 start_async_task 挂钩子

deepagents 的 `start_async_task` 只登记台账，不管进度同步。项目通过 monkey-patch `_build_start_tool`，在工具返回的 `Command` 里"顺手"把 watcher 线程拉起来：

```python
# src/agent/subagents/sync_launcher.py 源码摘录
def _maybe_launch_sync(result, runtime):
    if not isinstance(result, Command):
        return
    async_tasks = (getattr(result, "update", None) or {}).get("async_tasks", {})
    main_thread_id = (getattr(runtime, "config", None) or {}) \
        .get("configurable", {}).get("thread_id")     # 主智能体的 thread_id
    for task_id, task_info in async_tasks.items():
        launch_sync(main_thread_id, task_info.get("thread_id", task_id),
                    task_info.get("agent_name", "unknown"), task_info)  # 后台起 watcher

def _wrap_sync(description, subagent_type, runtime):
    result = _orig_sync(description, subagent_type, runtime)  # 原工具逻辑不动
    _maybe_launch_sync(result, runtime)                       # 追加：非阻塞启动同步
    return result

tool.func = _wrap_sync          # 同步/异步两条执行路径都要包
tool.coroutine = _wrap_async
```

设计要点：**包装而非替换**（原工具的 Command 原样返回，模型视角零感知）；**非阻塞**（launch_sync 只起线程）；**幂等的 apply_patch**（模块级 `_PATCHED` 标志，且必须在 `create_deep_agent` 之前 import——补丁改的是工厂函数，图建完再补就晚了）。

### 11.3 sync_subagent_todos.py：watcher 线程体系

每个子任务一个守护线程，0.5s 一轮轮询子线程、把进度合并写回主线程 state，前端 TasksFilesSidebar 零改动即可显示子任务步骤与耗时。核心循环骨架：

```python
# src/agent/subagents/sync_subagent_todos.py 源码摘录（大幅精简）
async def _async_sync_loop(main_thread_id, sub_thread_id, agent_name, task=None, ...):
    # 用 HTTP client 而非 ASGI in-process：watcher 是独立守护线程，
    # 没有主进程的 ASGI 应用上下文（get_client(url=None) 会炸）
    client = get_client(url=os.getenv("LANGGRAPH_API_URL", "http://localhost:2026"))
    await asyncio.sleep(3)          # 等子智能体的 run 创建完成

    while True:
        await asyncio.sleep(0.5)    # 加快同步频率，减少 write_todos 覆盖窗口
        run_status = await _get_run_status(client, sub_thread_id, ...)
        # 1) running：拉子线程 todos → _merge_steps_monotonic（已完成步骤永不回退）
        #    → 写 subagent_steps_map[task_id] / query_headers[task_id] / active_queries[task_id]=True
        # 2) 终态（success/error/cancelled/timeout）：写最终 steps + async_tasks 终态
        #    + active_queries=False + 通知主 agent 续跑（只触发一次）
        # 3) 各类兜底：STALE_RUN_TIMEOUT=600s 强制收尾；INTERRUPTED_STUCK_TIMEOUT=120s；
        #    COMPLETE_WRITE_MAX_SECONDS=300s 写不进去就登记 pending_terminal 由补写器接手
```

这个文件浓缩了大量生产事故换来的不变量，挑五个最有教学价值的：

1. **进程级写锁**：`as_node="__start__"` 的 `update_state` 在并发下有读-改-写竞态（后写者基于旧值覆盖，reducer 合并失效），所以所有 keyed 字段写入经 `_SYNC_WRITE_LOCK` 串行化，且持锁期间不 await（锁内用同步 HTTP client，避免死锁）。
2. **单调步骤基线**：`update_async_task` 重派发后子线程 todos 从 pending 重来，照抄会把已完成步骤降级、前端进度条回退（trace a6f86bbd）。`_seen_completed` 按内容记账，**已完成的步骤永不回退**。
3. **幽灵 next**：`update_state(as_node="__start__")` 会把主线程 head checkpoint 的 `next` 写成图入口节点——若补丁落在主 run 终态之后且不再有新 run，就留下一个无人推进的"幽灵 next"。它**不是丢步**，但读 `state.next` 的新代码必须同时看 `last_message_is_final`。
4. **终态回退守护（P3）**：主线程 auto-continue run 若从旧 checkpoint 分叉，会在每个节点边界重写整份 state 快照，把 watcher 刚写好的终态打回（卡片"跑完又回到执行中"）。守护逻辑按"status + active_queries + steps 三要素"识别回退并重写，上限 900s / 200 次（防病态刷写变僵尸线程）。
5. **watcher 注册表 + 存活检查**：`_ACTIVE_LOOPS[sub_thread_id] → Thread`，`is_sync_alive()` 供恢复端点在续跑子 run 前检查 watcher 是否还活着，死了就重新 launch——保证"重启中段"的子任务终态同步不丢（前端任务卡冻结的根治）。

另有 EventStore 追踪集成（SUBAGENT_SPAWN 等事件落统一轨迹库）和失败汇报去重（`failure_reported_local` + state 标记双层）。

### 11.4 check_progress.py：把 check_async_task 从"状态机"升级成"业务语义层"

deepagents 原版 `check_async_task` 在 running 时只回 `{"status": "running"}`，success 时机械取 `messages[-1]`。项目的增强补丁（同样是 monkey-patch `_build_check_result` + 换输入 schema）加了六层能力：

1. **running 中间态**：拉子线程 values，提取整体进度（completed/total）、每步状态+耗时（数据源 = `ProgressTrackerMiddleware` 的本地 step_history + message metadata 时间戳估算 fallback）、当前步骤、最近工具调用、AI 最新想法；
2. **结果锚点**：不再取 `messages[-1]`（子 agent 以工具调用收尾时末条必是短收尾语），改取**最后一条有实质内容的 AI 消息**（`_pick_result_message`），并回传下标供排查；
3. **结果摘要 + 逃逸通道**：默认 2000 字符/20 行上限防撑爆主 agent 上下文；摘要按"逻辑表"分段计数、逐张点名行数（修"78 个部门"幻觉与"39 行变 53 行"跨表求和两个事故）；`full=true` 时预算放大到 60000 字符/500 行——这个参数是"结果定格后主 agent 拿不到完整原文 → 只能 update_async_task 重派发制造新消息 → 4 次重派发空转 6.5 分钟"（trace 72e222c0）的直接解药：**摘要截断必须配显式逃逸通道，否则模型会自创邪路**；
4. **增量读取**：`since` 游标只回之后的新消息（每条截断 800 字符、单次最多 20 条）；
5. **SQL 取证链**：提取最后一次 run_sql、判 SQL 来源四态（cube_metric / llm_from_schema / …）、进程内复算物理 SQL（`plan_run_sql`/`plan_cube_sql`）、口径护栏告警（`caliber_sql_warning`）、大结果落盘文件指针——报告与审计全靠这层；
6. **终态改判**：success 但消息里有失败戳 → 改判 error（见 10.3）。

### 11.5 track_progress.py：进度数据的生产端

`ProgressTrackerMiddleware.awrap_model_call` 在每次模型调用后，从消息历史里倒序找最后一次 `write_todos` 的 ToolMessage，正则解析出 todos 列表，调用 `record_todos_progress` 写入 `%TEMP%/nl2sql_progress/{thread_id}.json`：

```python
# track_progress.py 源码摘录
# 检测状态变化，记录转换时间（step_history 是每步耗时的数据源）
for t in todos_list:
    prev_status = prev_todos.get(t["content"])
    if prev_status != t["status"]:
        step_history.append({"step": t["content"], "from": prev_status,
                             "to": t["status"], "ts": now})
```

`read_progress(thread_id)` 供 check_progress 消费。注意这是**文件总线**而非 state 通道——因为进度快照的写入方（子图中间件）与读取方（主图工具补丁）分属两个进程/图，state 互不相通，只能借宿主机临时目录中转（同机部署前提）。

### 11.6 loader.py：YAML 声明式子智能体

面向同步子智能体（SubAgent dict）的配置化装配：扫描 `configs/*.yaml`，支持 `system_prompt_file` 外置提示词、必填字段校验（name/description/system_prompt/tools）、工具名子串解析（见 9.3）。产出可直接喂给 `create_deep_agent(subagents=...)` 的 dict 列表。它体现的思路是：**子智能体的"人格"（提示词）与"能力"（工具面）都应可配置、可审查、可版本化**，而不是散落在代码里。

## 12. 完整代码示例

### 场景一：同步子智能体调用（并行研究 + 结构化返回）

```python
"""场景一：同步子智能体 —— 三个研究员并行调研，结构化结果汇总。

演示要点：
1. SubAgent 声明式 spec（tools 显式收窄 = 领域专家）
2. response_format 结构化输出（JSON 直接回到主智能体）
3. 主智能体在一条消息里发多个 task 调用 → ToolNode 并发执行
"""
from pydantic import BaseModel, Field
from deepagents import create_deep_agent

# ── 1. 定义结构化返回 schema ─────────────────────────────
# 子智能体的最终产物会被 JSON 序列化后作为 ToolMessage 内容，
# 主智能体拿到的是严格结构化的数据而非自由文本。
class ResearchFindings(BaseModel):
    topic: str = Field(description="调研主题")
    findings: str = Field(description="核心发现摘要")
    confidence: float = Field(description="置信度 0~1")

        {

    ],
```

### 场景三：多子智能体协作（异步扇出 + watcher 进度同步，项目模式）

```python
"""场景三：并发多查询 + 进度同步 —— 复刻本项目 main_agent 的协作骨架。

架构：
  主智能体 ──start_async_task──▶ 远程子图 A（nl2sql 查询 1）
            ──start_async_task──▶ 远程子图 B（nl2sql 查询 2）   ← 真并发
  每个任务一个 watcher 守护线程，把子线程 todos 进度写回主线程
  state 的键控字段（task_id → 步骤列表），前端按 key 渲染多张进度卡片。
"""
import threading
from typing import Annotated, NotRequired
from deepagents import create_deep_agent, AsyncSubAgent, DeepAgentState

# ── 1. 键控合并 reducer：并发写入互不覆盖的地基 ───────────
def _merge_dict_by_key(existing: dict | None, update: dict) -> dict:
    """与 deepagents._tasks_reducer 同语义：按 key 合并而非整值替换。
    每个 watcher 只写自己 task_id 的 key，reducer 保证并发安全。"""
    merged = dict(existing or {})
    merged.update(update)
    return merged

class MainAgentState(DeepAgentState):
    # task_id → {标题、状态...}；task_id → [步骤]；task_id → 是否运行中
    query_headers:      Annotated[NotRequired[dict[str, dict]], _merge_dict_by_key]
    subagent_steps_map: Annotated[NotRequired[dict[str, list]], _merge_dict_by_key]
    active_queries:     Annotated[NotRequired[dict[str, bool]],_merge_dict_by_key]

# ── 2. 给 start_async_task 挂 watcher 钩子（包装而非替换）──
def patch_start_tool_with_watcher():
    """monkey-patch deepagents._build_start_tool：
    启动子任务后，顺带拉起该任务的进度同步线程。
    ⚠️ 必须在 create_deep_agent 之前执行（补丁改的是工厂函数）。"""
    from deepagents.middleware import async_subagents as mod
    orig = mod._build_start_tool

    def patched(agent_map, clients, tool_description):
        tool = orig(agent_map, clients, tool_description)
        orig_sync, orig_async = tool.func, tool.coroutine

        def launch_watchers(result, runtime):
            from langgraph.types import Command
            if not isinstance(result, Command):
                return result
            tasks = (result.update or {}).get("async_tasks", {})
            main_tid = (runtime.config or {}).get("configurable", {}).get("thread_id")
            for tid, info in tasks.items():
                # 幂等保护：先查注册表，活着就不重复起线程
                if not is_sync_alive(tid):
                    launch_sync(main_tid, info["thread_id"], info["agent_name"], info)
            return result

        def wrapped(desc, subtype, runtime):
            return launch_watchers(orig_sync(desc, subtype, runtime), runtime)
        tool.func = wrapped          # coroutine 同理包装（略）
        return tool

    mod._build_start_tool = patched

# ── 3. watcher 骨架：轮询子线程 → 写回主线程键控字段 ──────
def launch_sync(main_tid: str, sub_tid: str, agent_name: str, task: dict):
    """每个子任务一个守护线程（线程内新建事件循环跑异步逻辑）。"""
    def _loop():
        import asyncio
        from langgraph_sdk import get_client
        client = get_client(url="http://localhost:2026")  # watcher 线程无 ASGI 上下文，必须走 HTTP

        async def _poll():
            seen_completed: set[str] = set()      # 单调基线：已完成步骤永不回退
            while True:
                await asyncio.sleep(0.5)
                run = await _get_run(client, sub_tid)          # runs.get
                if run and run["status"] in ("success", "error", "cancelled", "timeout"):
                    _write_state(main_tid, {                   # 终态收尾（三个写入）
                        "active_queries": {sub_tid: False},
                        "async_tasks": {sub_tid: {**task, "status": run["status"]}},
                    })
                    break
                values = await _get_values(client, sub_tid)    # threads.get → todos
                steps = _merge_steps_monotonic(values, seen_completed)
                _write_state(main_tid, {                       # 只写自己的 key！
                    "subagent_steps_map": {sub_tid: steps},
                    "active_queries": {sub_tid: True},
                })

        # 进程级锁串行化 update_state（as_node="__start__" 并发下有读-改-写竞态）
        asyncio.run(_poll())

    t = threading.Thread(target=_loop, daemon=True, name=f"sync-{sub_tid[:8]}")
    register_sync_thread(sub_tid, t)   # 注册表：供存活检查/重启恢复
    t.start()

# ── 4. 组装主智能体 ──────────────────────────────────────
patch_start_tool_with_watcher()        # 先打补丁
agent = create_deep_agent(
    model=my_model,
    tools=[build_report_tool],
    subagents=[AsyncSubAgent(name="nl2sql", description="NL2SQL查询专家",
                             graph_id="nl2sql_agent")],
    state_schema=MainAgentState,
    checkpointer=my_checkpointer,
)

# ── 5. 一次提问扇出两个并发查询 ──────────────────────────
agent.invoke({"messages": [{"role": "user",
    "content": "对比 A 部门和 B 部门去年的工时与产出，分别查"}]}, cfg)
# 模型发出 2 个 start_async_task → 2 个远程 run 真并发执行
# → 2 个 watcher 线程各自把进度写进 subagent_steps_map 的不同 key
# → 前端渲染两张独立进度卡片；check_async_task 分别取两份结果后汇总对比
```

## 13. 最佳实践：何时用同步、何时用异步

### 13.1 决策表

| 判断维度 | 倾向同步（task） | 倾向异步（start_async_task） |
|---|---|---|
| 任务时长 | 秒级~1 分钟内 | 分钟级以上 |
| 主智能体是否立刻需要结果 | 是（下一步推理依赖它） | 否（可先答复用户，稍后收集） |
| 用户是否需要中途干预 | 不需要（一次描述说清） | 需要（补充口径/改指令/取消） |
| 并发规模 | 少量（受同批工具调用与 run 槽约束） | 大量（远程服务器各自排队） |
| 进度可视化需求 | 无（黑盒到最终报告） | 有（需要台账 + watcher + 前端卡片） |
| 子智能体是否需要独立部署/发版 | 不需要（同进程同版本） | 需要（解耦演进） |
| 失败恢复 | 重新发一次 task 即可 | task_id 台账 + 终态改写 + 补写器 |
| 上下文成本 | 子智能体最终报告进主线程 | 结果经摘要层压缩后才进主线程 |

### 13.2 通用守则（两种机制都适用）

1. **任务描述自包含**。子智能体看不到主线程历史（同步是显式剔除，异步是远程隔离），`description` 必须携带全部上下文并明确"要创建内容、做分析还是只调研"、明确期望的返回格式。
2. **能并行就并行**。独立子任务在同一批里发出（同步：一条 AI 消息多个 task；异步：连续多次 start），这是 `TASK_TOOL_DESCRIPTION` 的第一条 usage note。
3. **简单任务不要委派**。几个工具调用能解决的事直接做——拆子智能体只增加延迟与失真环节（源码示例里"点三个外卖"就是反例）。
4. **子智能体的输出默认可信，但要给它"说清失败"的通道**。结构化 response_format / 失败戳（本项目的 `nl2sql_failure`）让失败机读化，防止"假成功"污染主线程。
5. **结果只回最终报告**。需要中间步骤可见时，不要改用同步，而是像本项目一样加旁路（watcher 写键控 state 字段 + 前端订阅），主线程消息流保持干净。

### 13.3 异步特有的纪律

1. **启动后立即交还控制权**，绝不自动 check；用户问一次才查一次，**永不轮询**（`ASYNC_TASK_SYSTEM_PROMPT` 的 Critical rules，也是省 token 的硬约束）。
2. **历史状态永远过期**：对话里出现过的 "running" 不作数，汇报状态前必须现查（单任务 `check_async_task`，多任务 `list_async_tasks`）。
3. **task_id 完整展示**，不截断不缩写——它是用户与运维定位后台任务的唯一凭据。
4. **摘要截断必须配逃逸通道**：结果被截断时给模型一个"要原文"的正当出口（本项目 `full=true`），否则模型会自创邪路（重派发子任务"制造新消息"，实测空转 6.5 分钟）。
5. **台账写入按 key 合并 + 串行化**：并发多任务时依赖 reducer 的键控合并，`update_state(as_node="__start__")` 的读-改-写竞态要加锁；读 `state.next` 必须同时看 `last_message_is_final`（幽灵 next）。
6. **watcher 不幂等就要有注册表**：起线程前查 `is_sync_alive`，重启后对"中段任务"补拉 watcher，终态写入失败登记待补写——否则前端卡片永久转圈。
7. **run 报 success ≠ 业务成功**：在结果提取层读失败戳做终态改判，且只对 success 改判、running 绝不降级。

### 13.4 同步特有的注意点

1. **子智能体默认继承主智能体的工具与权限**——领域专家型子智能体应显式收窄 `tools` 与 `permissions`（`permissions` 是整体替换不是合并，写的时候要把放行规则带全）。
2. **`CompiledSubAgent` 是三不管地带**：不继承 state_schema、不继承 interrupt_on、不继承默认中间件栈，一切自理；唯一硬约束是 state 含 `messages` 键。
3. **子智能体的中间步骤对主线程不可见**是特性不是缺陷——需要旁路观测时用 stream 的 `run.subagents` 句柄（`SubagentTransformer` 提供）或 LangSmith 的 `ls_agent_type=subagent` 标签过滤，不要试图把它们塞回主线程消息。
4. **同批并行的木桶效应**：一批 task 里最慢的决定整批时长，把长任务混进同步批次会拖死所有短任务——这种混合负载正是改用异步的信号。
