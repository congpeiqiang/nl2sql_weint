## 二、可扩展性评估

### 2.1 🔴 中间件链的深度耦合与顺序依赖

**现状：** 主 Agent 17 层中间件，子 Agent 23 层中间件。每一层的插入位置都有严格的注释说明顺序约束。

```python
# nl2sql_agent.py 中间件链（23 层，顺序敏感）
_middleware = [
    DynamicMCPToolsMiddleware(),    # 最外层：先并入工具
    TraceRecorderMiddleware(),
    skills_middleware,
    ProgressTrackerMiddleware(),
    CaliberGateMiddleware(),        # 必须在 ProgressBoundary 之前
    ProgressBoundaryMiddleware(),
    DanglingToolCallsMiddleware(),
    ThinkingToggleMiddleware(),
    ToolFilterMiddleware(),
    FilesystemThreadGuardMiddleware(),
    MessageSlimmerMiddleware(),     # 必须在 QueryResultOffload 之外层
    KnowledgeTrimMiddleware(),      # 必须在 MessageSlimmer 内层
    QueryResultOffloadMiddleware(), # 必须在 LangfuseSpan 之前
    FailureCircuitMiddleware(),     # 必须在 MessageSlimmer 内层、LangfuseSpan 外层
    LangfuseSpanMiddleware(),
    dynamic_prompt,
    QueryGateMiddleware(),          # append — 必须在 LangfuseSpan 内层
    CubeRouteGateMiddleware(),      # append — 与 QueryGate 同层
    sql_approval_middleware,         # conditional append
    WriteTodosProtocolMiddleware(), # 必须最后
    QuotaErrorMiddleware(),         # insert(0) — 最外层
    ModelTimeoutMiddleware(),       # insert(0) — 次外层
    ModelRequiredMiddleware(),      # insert(0) — 最最外层
]
```

**问题：**
- 23 层中间件的**插入顺序是全系统的隐性契约**，靠注释维护。任何新增中间件都需要理解整个链的拓扑。
- 存在**循环依赖风险**：MessageSlimmer 必须在 QueryResultOffload 外层、KnowledgeTrim 必须在 MessageSlimmer 内层、FailureCircuit 必须在 MessageSlimmer 内层且 LangfuseSpan 外层——这已经是部分序约束，不是简单的线性顺序。
- **新人不可能在不阅读 500+ 行注释的情况下正确添加中间件**。

**优化方案：**

```python
# 方案 A：声明式中间件管道（推荐）
from dataclasses import dataclass
from enum import Enum, auto

class Layer(Enum):
    """中间件执行阶段——从外到内"""
    GUARD = auto()        # 门禁类：ModelRequired, QuotaError, ModelTimeout
    TOOL_REGISTRY = auto()  # 工具注入：DynamicMCPTools, ToolFilter
    OBSERVABILITY = auto()  # 观测：TraceRecorder, LangfuseSpan, TokenMeter
    PROGRESS = auto()      # 进度：ProgressTracker, ProgressBoundary, WriteTodos
    CONTEXT = auto()       # 上下文：ThinkingToggle, DbContext, QueryKeywords
    SAFETY = auto()        # 安全：FilesystemThreadGuard, ExecuteGuard, SQLApproval
    OPTIMIZATION = auto()  # 优化：MessageSlimmer, KnowledgeTrim, QueryResultOffload
    GATE = auto()          # 业务门控：CaliberGate, QueryGate, CubeRouteGate, FailureCircuit
    PROMPT = auto()        # 提示词注入：dynamic_prompt, SkillsMiddleware

@dataclass
class MiddlewareSpec:
    layer: Layer
    middleware: Any
    after: list[str] = field(default_factory=list)  # 同层内的顺序约束
    before: list[str] = field(default_factory=list)

PIPELINE: list[MiddlewareSpec] = [
    MiddlewareSpec(Layer.GUARD, ModelRequiredMiddleware()),
    MiddlewareSpec(Layer.GUARD, QuotaErrorMiddleware()),
    MiddlewareSpec(Layer.GUARD, ModelTimeoutMiddleware()),
    MiddlewareSpec(Layer.TOOL_REGISTRY, DynamicMCPToolsMiddleware()),
    # ... 声明式
]

def build_middleware_chain(specs: list[MiddlewareSpec]) -> list:
    """拓扑排序 → 平坦列表。新增中间件只需声明 layer + 依赖。"""
    ...
```

**收益：**
- 新增中间件只需声明层级和依赖，不需要理解 23 层的完整顺序
- 自动检测循环依赖（拓扑排序会报错）
- 单元测试可验证管道拓扑的正确性

### 2.2 🔴 单进程天花板：所有 Agent 共享同一事件循环

**现状：** Main Agent + NL2SQL SubAgent + 所有 API 路由 + MCP 子进程管理 全部运行在**同一个 Python 进程**中。

```
一个进程承担的角色：
├── HTTP 服务器（Starlette + uvicorn）
├── LangGraph 运行时（agent 执行引擎）
├── MCP 客户端（管理 N 个 wren 子进程）
├── MCP 服务端（db_mcp_server，stdio 传输）
├── 后台任务（metrics sampler, retention, embedder warmer, eval queue）
├── 守护线程池（per-subagent sync threads）
└── Git 操作（subprocess.run，阻塞式）
```

**可扩展性上限：**
- 当前 `docker-compose.yml` 内存限制 **1200MB**
- 并发天花板 = **10 个 run 槽**（全局共享，memory 记录）
- 每个 run ≈ 3 个子 run ⇒ 实际并发 ≈ **3-4 个用户同时查询**
- 超过此值：APIConnectionError（6 并发失败的全是连接错误）

**优化方案：**

| 方案 | 描述 | 复杂度 | 收益 |
|------|------|--------|------|
| **A. 水平扩展（推荐短期）** | 蓝绿部署已实现，扩展到 N 色 | 低 | 线性扩展 |
| **B. 读写分离** | API 路由进程与 Agent 执行进程分离 | 中 | API 响应不受 agent 阻塞 |
| **C. Agent Worker Pool** | Agent 执行抽到独立 worker 进程池 | 高 | Agent 可独立扩缩容 |

方案 B 的具体架构：

```
                    ┌──────────────┐
                    │   nginx:80   │
                    └──────┬───────┘
                           │
              ┌────────────▼────────────┐
              │    API Gateway 进程     │  ← 纯 ASGI，无 agent 逻辑
              │    (Starlette 路由)     │
              └────────────┬────────────┘
                           │ Redis/消息队列
              ┌────────────▼────────────┐
              │    Agent Worker Pool    │  ← 独立进程，可 N 实例
              │    (LangGraph Runtime)  │
              │    ┌───┐ ┌───┐ ┌───┐   │
              │    │ W1│ │ W2│ │ W3│   │
              │    └───┘ └───┘ └───┘   │
              └────────────┬────────────┘
                           │
              ┌────────────▼────────────┐
              │    PostgreSQL           │  ← 共享 checkpoint
              └─────────────────────────┘
```

### 2.3 🟠 数据库数量的线性扩展问题

**现状：** 每个建模数据库需要：
- 1 个 `wrenai_*` MCP 子进程（stdio 传输）
- 1 个 Wren engine 实例（~0.9s 冷启动）
- MCP 连接建立 3-60s

**4 个数据库的启动时间** ≈ 4 × 0.9s = 3.6s（engine）+ 4 × 3-60s（MCP 连接）

**扩展到 20 个数据库时：**
- 20 个 MCP 子进程 × 3-60s = **1-20 分钟启动**
- 20 个 engine 实例的内存开销
- 工具列表膨胀：每库 ~18 个工具 × 20 库 = **360 个工具**

**优化方案：**

```python
# 方案：MCP 连接池 + 懒加载 + 按需淘汰
class MCPConnectionPool:
    """per-db MCP 连接池，支持 LRU 淘汰"""

    def __init__(self, max_active: int = 5):
        self._active: OrderedDict[str, MCPSession] = OrderedDict()
        self._max_active = max_active

    async def acquire(self, db_name: str) -> MCPSession:
        if db_name in self._active:
            self._active.move_to_end(db_name)  # LRU
            return self._active[db_name]

        if len(self._active) >= self._max_active:
            evicted_name, session = self._active.popitem(last=False)
            await session.close()  # 淘汰最久未用

        session = await self._connect(db_name)
        self._active[db_name] = session
        return session
```

### 2.4 🟡 工具数量膨胀对 LLM 的影响

**现状：** 子 Agent 的工具列表包含所有建模库的全部工具。模型每次调用都需要理解完整的工具 schema。

```
单库工具数 ≈ 18 (run_sql, dry_run, dry_plan, query_cube, get_mdl, ...)
N 库工具数 ≈ 18 × N + 2 (dbmcp_run_sql, dbmcp_get_db_info)
```

当 N=10 时，模型面对 **182 个工具**，每次 LLM 调用的 token 开销和选择正确率都会下降。

**已有缓解：** `ToolFilterMiddleware` 按 `db_name` 过滤工具。
**进一步优化：** 只在 `DynamicMCPToolsMiddleware` 层加载当前库的工具，而不是加载全部再过滤。减少工具 schema 的 token 消耗。

## 四、可靠性评估

### 4.1 🔴 守护线程 sync 机制的脆弱性

**现状：** 子 Agent 的进度同步依赖**守护线程轮询**（`sync_subagent_todos.py`）：

```
守护线程每 500ms:
1. HTTP 调用 LangGraph API 获取子 run 状态
2. 解析 todos + steps
3. 全局锁内写主 Agent state (update_state)
4. 终态检测 → 通知主 Agent 继续
```

**脆弱点：**

| 风险 | 触发条件 | 后果 |
|------|----------|------|
| **全局写锁串行化** | 多并发查询 | 进度更新延迟叠加 |
| **守护线程随主进程死** | 进程崩溃 | 进度丢失（checkpoint 不存 sync 线程状态） |
| **竞态：update_state 覆盖** | 两个 sync 线程同时写 | 已用 `_SYNC_WRITE_LOCK` 缓解，但锁内有 HTTP 调用 |
| **HTTP 自调用失败** | LangGraph API 繁忙 | 静默跳过一轮（500ms 延迟） |
| **stale run 检测** | 子 run 卡死 | `STALE_RUN_TIMEOUT=600s` 才兜底 |

**优化方案：**

```python
# 方案：事件驱动替代轮询（长期）
# LangGraph 支持 stream_mode="updates"，可推送状态变更
# 替代每 500ms 的 HTTP 轮询

# 方案：短期 — 批量写入 + per-task 锁
class SyncBatchWriter:
    """聚合多个 sync 线程的写入，定期批量 flush"""

    def __init__(self, flush_interval: float = 1.0):
        self._pending: dict[str, dict] = {}  # task_id -> latest state
        self._lock = asyncio.Lock()
        self._flush_interval = flush_interval

    async def submit(self, task_id: str, state_update: dict):
        async with self._lock:
            self._pending[task_id] = state_update  # 最新覆盖旧值

    async def _flush_loop(self):
        while True:
            await asyncio.sleep(self._flush_interval)
            async with self._lock:
                batch, self._pending = self._pending, {}
            if batch:
                # 单次 update_state 合并所有 task 的更新
                merged = {}
                for task_id, update in batch.items():
                    merged = _merge_dict_by_key(merged, update)
                await _update_main_state(merged)
```

### 4.3 🟠 Checkpoint 膨胀与 O(n²) 增长

**现状：** LangGraph checkpoint 存储**完整消息历史**。每次 tool call 的输入/输出都作为 `ToolMessage` 进入 state。

**缓解措施（已有）：**
- `MessageSlimmerMiddleware`：截断 > 8000 字符的结果
- 去重：相同内容 → stub 引用
- 豁免：图表、知识工具不截断

**仍然存在的问题：**
- 长会话（50+ 轮对话）的 checkpoint 可达 **数十 MB**
- Postgres checkpoint 查询变慢
- 没有 checkpoint 压缩或归档机制
- `recursion_limit=500` 意味着单 turn 最多 500 步，每步都进 state

**优化方案：**
1. **增量 checkpoint**：只存 delta（新增的消息），不存全量历史
2. **checkpoint 归档**：超过 N 天的 checkpoint 移到冷存储
3. **消息摘要**：对早期消息生成摘要替代原文

### 4.4 🟠 SQLite 共享连接的并发风险

**现状：** Auth 数据库使用**单连接 + 全局锁**：

```python
# auth/grants.py
_conn = sqlite3.connect(db_path, check_same_thread=False)
_lock = metered_rlock()  # 所有读写都要进锁
```

**风险：**
- 每次认证请求都进锁（`register_user` 有 60s TTL 缓存缓解）
- 并发读同一 `SELECT` 在 sqlite3 下会互踩（memory 记录）
- 锁获取超时 = 请求超时

**已有缓解：** 60s TTL 缓存 + WAL 模式 + `busy_timeout=15000ms`。
**进一步优化：** 读操作使用连接池（多连接），写操作仍单连接。

### 4.5 🟡 故障恢复的不完整性

**当前故障恢复矩阵：**

| 故障类型 | 恢复机制 | 覆盖度 |
|----------|----------|--------|
| LLM API 超时 | `ModelTimeoutMiddleware` | ✅ 友好提示 |
| LLM 配额耗尽 | `QuotaErrorMiddleware` | ✅ 友好提示 |
| MCP 服务器崩溃 | 启动预检 + 后台 reconciliation | ⚠️ 运行期不自动重连 |
| 子 Agent run 卡死 | `STALE_RUN_TIMEOUT=600s` | ⚠️ 10 分钟才发现 |
| Postgres 连接断开 | `_SelfHealingPostgresSaver` | ✅ 自动重连 |
| 进程重启 | 守护线程丢失 → 进度丢失 | ❌ sync 状态不持久化 |
| Wren engine 崩溃 | engine cache 有 LRU 淘汰 | ⚠️ 首次查询失败需重试 |

## 五、性能评估

### 5.1 🔴 首次查询冷启动延迟

```
用户首次查询的时间分解：
├── 认证 token 验证          ~5ms
├── LangGraph run 创建       ~50ms
├── 主 Agent 模型调用 #1     ~2-5s (LLM 响应)
├── 子 Agent 创建            ~100ms
├── MCP 工具连接（如冷）      ~3-60s  ← 最大瓶颈
├── Wren engine 构建（如冷）  ~0.9s/库
├── 语义检索                  ~0.5-4s (GPU 冷加载 13-17s)
├── SQL 生成 + 执行           ~1-3s
└── 结果返回                  ~100ms

最坏情况首次查询 ≈ 70-90s
正常情况首次查询 ≈ 5-15s
```

**优化方案：**
1. **Startup 预热**（已有 embedder 预热，应扩展到 MCP 连接 + engine 构建）
2. **MCP 连接池**（见 §2.3）
3. **Engine 预构建**（startup 时为所有建模库预构建 engine）

### 5.2 🟠 内部 HTTP 自调用的开销

**现状：** API handler 大量通过 `httpx.AsyncClient` 调用同进程的 LangGraph API：

```python
# thread_fork.py — 一次 fork = 4 次内部 HTTP 调用
await client.threads.create(...)        # 1. 创建新线程
await client.threads.get_history(...)   # 2. 读历史
await client.threads.get_state(...)     # 3. 读状态
await client.threads.update_state(...)  # 4. 写状态
```

**问题：**
- 每次 HTTP 调用都经过完整的中间件链（CORS → RequestContext → DrainGate → Auth → Langfuse）
- 序列化/反序列化开销（JSON/msgpack）
- 内部 IP 判断逻辑脆弱（Docker 网络 IP + 无 Cookie + 无 X-Forwarded-For）

**优化方案：** 内部调用走**直连函数**而非 HTTP：

```python
# 方案：内部调用绕过 HTTP
class InternalLangGraphClient:
    """直接调用 LangGraph 运行时函数，跳过 HTTP + 中间件链"""

    async def get_state(self, thread_id: str) -> dict:
        # 直接调用 checkpointer.get() 而非 HTTP GET /threads/{id}/state
        return await self._checkpointer.aget(config)

    async def update_state(self, thread_id: str, values: dict, **kwargs):
        # 直接调用 checkpointer.aput()
        return await self._checkpointer.aput(config, values)
```

### 5.3 🟠 Sync 线程轮询频率与延迟

**现状：** 500ms 轮询间隔 → 进度更新最大延迟 500ms。

**权衡：**
- 降到 100ms → 5× API 调用量，LangGraph API 压力增大
- 升到 2s → 前端进度条明显卡顿

**优化方案：** 自适应轮询：

```python
async def _adaptive_poll(self):
    """初始快轮询，稳定后降频，终态附近再加速"""
    interval = 0.2  # 初始 200ms
    stable_count = 0

    while not self._done:
        state = await self._fetch_state()
        if state_changed(state):
            interval = 0.2  # 变化时恢复快轮询
            stable_count = 0
        else:
            stable_count += 1
            interval = min(0.2 + stable_count * 0.1, 2.0)  # 逐步降频到 2s

        await asyncio.sleep(interval)
```

### 5.4 🟡 Wren Engine 串行构建

**现状：** 多库同时到达时 engine 构建是串行的：

```python
# wren_plan.py — 每个库串行构建 engine
eng = _build_engine_for(mdl_path, conn)  # ~0.9s/库
```

4 库并发 → 3.6s 等待。

**优化方案：** `asyncio.gather` 并行构建 + engine 预热。

> 以下为审查代理对代码库独立验证后发现的**初始评估遗漏项**。

### 6.1 🔴 异常处理反模式（757 处 `except Exception:`）

**grep 实查确认：127 个文件中共 757 处 `except Exception:`，另有 2 处裸 `except:`。**

**重灾区 TOP 5：**

| 文件 | `except Exception:` 次数 |
|------|--------------------------|
| `sync_subagent_todos.py` | 43 |
| `langfuse_span.py` | 42 |
| `langfuse_client.py` | 36 |
| `feedback_annotation.py` | 31 |
| `check_progress.py` | 26 |

**问题：**
- 宽泛异常捕获隐藏了真实错误，使调试极其困难
- 在 23 层中间件链 + 守护线程架构下，静默吞异常可能导致**级联故障且几乎无法诊断**
- 裸 `except:` 会连 `KeyboardInterrupt` 和 `SystemExit` 都吞掉

**裸 `except:` 位置：**
- `src/agent/utils/path_resolver.py:1`
- `src/agent/retrieval/adapters.py:1`

**优化方案：**

```python
# ❌ 当前模式（757 处）
except Exception:  # noqa: BLE001
    _logger.warning("xxx 失败: %s", e)

# ✅ 目标模式：分层捕获 + 结构化日志
except (ConnectionError, TimeoutError) as e:
    _logger.warning("[module] 网络异常: %s", e)
except ValueError as e:
    _logger.error("[module] 数据解析异常: %s", e)
except Exception as e:  # noqa: BLE001  最后兜底
    _logger.exception("[module] 未预期异常")  # exception() 含 traceback
```

### 6.2 🔴 全局状态泛滥（62 把锁 / 32 个文件）

**grep 实查确认：32 个文件中共 62 处 `threading.Lock()`/`threading.RLock()` 实例。**

**问题：**
- 评估提到 sync 线程的全局写锁，但遗漏了更广泛的**全局状态管理问题**
- 20+ 模块级全局变量配合锁使用：`_users_cache`, `_secret_cache`, `_db_conn`, `_default_store`, `_CACHE_LOCK`, `_STORE`, `_RUNNER`, `_WORKER`, `_path_cache` 等
- 这使得评估中"蓝绿部署扩展到 N 色"的水平扩展方案比预期更困难——**全局缓存和单例假设了单进程**
- 进程分离方案（§2.2 方案 B/C）需要序列化或复制所有这些全局状态

**优化方案：**
1. **审计全局状态**：列出所有模块级全局变量及其生命周期
2. **分类处理**：
   - 纯配置型 → 冻结为不可变（startup 后只读）
   - 缓存型 → 考虑外部缓存（Redis）替代进程内缓存
   - 连接型 → 连接池（已有部分实现）
3. **依赖注入**：替代模块级单例，使测试和进程分离更可行

### 6.3 🟠 守护线程复杂度（超出 sync 线程）

**除 `sync_subagent_todos.py` 外，至少还有以下守护线程：**

| 文件 | 守护线程用途 | 生命周期 |
|------|-------------|----------|
| `eval/eval_queue.py` | 评估任务 worker | `_WORKER` 单例 |
| `message_feedback.py` | Langfuse 回调 | 3+ 守护线程 |
| `feedback_annotation.py` | 标注统计 | `_stats_lock` |
| `utils/caliber_evidence.py` | 业务口径语料 | `_CORPUS_LOCK` |
| `utils/wren_plan.py` | Engine 缓存 | `_CACHE_LOCK` |

**问题：** 多个守护线程 + 不同的生命周期 + 复杂的停机语义，且**没有线程生命周期的文档化**。

### 6.4 🟠 配置管理脆弱性

**环境变量大量使用但缺少集中校验：**
- `LANGGRAPH_API_URL`（13 个文件各自读取）
- `NL2SQL_DRAIN_SECS`, `NL2SQL_FAIL_CIRCUIT`, `NL2SQL_CUBE_ROUTE_GATE`, `NL2SQL_RETRIEVAL` 等功能开关
- 拼写错误或遗漏的环境变量导致**静默失败**而非启动期报错

**已有缓解：** `setting.py` 使用 Pydantic `BaseSettings`，但只覆盖了核心配置。功能开关类环境变量散落在各模块中 `os.getenv()` 直接读取。
