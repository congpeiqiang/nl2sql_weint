# WIT 运营管理平台 · WrenAI 语义库查询问题集

> 用途：NL2SQL 语义层（WrenAI）的**验证 / 回归问题集**。每题给出「业务问法 + 期望口径 + 首选对象 + 陷阱」，
> 用于检查系统是否选对 cube/视图、口径是否正确、是否越界访问未建模表。
> 数据基准：**2026-09-15**（平台数据实时变化，数量会漂移，允许 ±1% 误差）。

## 0. 语义库对象总览（48 张表 + 5 个视图 + 6 个立方体）

| 域 | 立方体（cube） | 视图 | 主要表 |
|---|---|---|---|
| 需求交付 | `story_delivery` | `v_story` | `do_story`、`do_story_project`、`do_story_rel` |
| 缺陷质量 | `bug_quality` | `v_bug` | `do_bug` |
| 迭代燃尽 | `iteration_burndown_cube` | `v_iteration_burndown` | `do_iteration_burndown`、`do_iteration`、`do_iteration_detail`、`do_iteration_project` |
| 工时投入 | `workhour_analysis` | `v_workhour` | `do_work_hour`、`do_work_hour_detail_extend`、`do_work_hour_examine`、`do_table_user` |
| 任务时效 | `task_timeliness` | — | `do_task_report`、`do_task`、`do_task_log` |
| 项目组合 | `project_portfolio` | `v_project` | `do_project`、`do_project_module`、`do_user_link` 等 |

**判定约定**
1. **口径正确**优先于回答漂亮：分母是否排除「已取消/关闭」、时间窗口是否精确、样本覆盖度是否说明。
2. **不越界**：只能查上面 48 张表 + 5 个视图；查已移除/未建模对象应明确说明并给替代方案（见 §H）。
3. **不臆造**：字典未收录的编码（需求类别、需求来源、缺陷解决结果、迭代状态码等）只给码值，不编中文名。
4. **样本要说明**：凡是覆盖率不足 100% 的指标（需求及时率、迭代燃尽、缺陷漏测等）必须注明样本口径。
5. **只读**：任何修改数据的请求（UPDATE/DELETE/DROP/INSERT）一律拒绝。
6. **时间窗口**：SQL 的 `BETWEEN` 是闭区间；cube 时间维度的 `dateRange` 是**左闭右开**（`start,end`），
   两者混用会少算一天的数据（详见 D1）。

## A. 需求交付域（`story_delivery` / `v_story`）

**A1. 目前各项目还有多少未完成需求？按数量从多到少排前 20。** ★
- 口径：未完成 = `status NOT IN (14, 6, 99)`；项目用 `project_name`（来自 `do_story.project_id → do_project`）
- 首选：cube `story_delivery`（`open_count` × `project_name`）
- 陷阱：不排除已取消（6）/关闭（99）会把 3964 条不算"在做"的需求算进来

**A2. 2026 年每个月提出了多少需求、完成了多少？** ★
- 口径：按 `mention_time` 分月（覆盖 24880/24901 ≈ 99.9%）；完成用 `status = 14`
- 首选：cube `story_delivery`，时间维度 `mention_time:month`
- 陷阱：1~9 月实测 411/203/660/569/414/443/575/601/232（提出数）

**A3. 需求完成率是多少？按项目看哪些项目完成率最低（有效需求 ≥20 条）？** ★★
- 口径：**完成率 = 已完成 /（有效需求 − 已取消）**，分母必须排除 `status = 6`
- 首选：cube `story_delivery`（`done_rate`），或 `v_story` 自行聚合
- 陷阱：用总数当分母会低估完成率（已取消 2512 条）

**A4. 需求按时交付率是多少？** ★★★
- 口径：`status = 14` 且 `true_test_complete ≤ expect_test_complete` 视为按时；
  分母 = **已完成且两端时间齐全**的需求（实测 7001/16264 ≈ 43%）
- 首选：cube `story_delivery`（`test_ontime_rate`、`avg_test_deviation_days`）
- 陷阱：① 不能拿全部有效需求当分母；② 必须说明覆盖率约 43%；③ 旧的宽表字段 `verify_status` 已停用，
  不存在"平台已内置判定"这回事

**A5. 有多少需求已经超期但还没完成？** ★★
- 口径：`status NOT IN (14,6,99)` 且 `expect_test_complete < CURRENT_DATE`（实测约 1364 条）
- 首选：cube `story_delivery`（`overdue_open_count`）
- 陷阱：用 `expect_complete_time` 判定会只剩 210 条（该字段只有 4933/24901 有值）

**A6. 哪些需求应用在了多个项目上？分别涉及几个项目？** ★★
- 口径：`v_story.app_project_count > 1`（实测 208 条），明细来自 `do_story_project`（有效 12066 行 / 11741 个需求）
- 首选：视图 `v_story`（`project_scope = '多项目'`）或直接查 `do_story_project`
- 陷阱：直接 JOIN `do_story_project` 会放大行数，按需求计数必须 `COUNT(DISTINCT story_id)`

**A7. 需求之间的依赖关系有多少？哪些需求依赖最多？** ★★★
- 口径：`do_story_rel`（有效 204 行，`node_task_type` **全部 = 3 需求**）；`story_id` = 依赖方，`business_id` = 被依赖需求
- 首选：视图 `v_story.dep_story_count` / `depended_by_count`；要名单就 JOIN `do_story_rel`
- 陷阱：① 依赖项名称无法用拼接串拿到（引擎无 `group_concat`）；② 目标需求可能已被软删（3 条）

**A8. 需求的工作量合计是多少？** ★★
- 口径：`SUM(workload)`；但实测只有 **3167/24901** 条填了工作量、2202 条填了预计工时
- 陷阱：直接报"总工作量 22955"而不说明填报率会误导；必须注明"仅按已填报需求统计"

**A9. 按优先级 / 需求类型看需求分布。** ★
- 口径：优先级 `1=P0 … 4=P3`，**约半数记录为空串**（`v_story` 里显示「未设置」）；类型 0=常规、1=紧急、2=口头
- 陷阱：把空串当 P0 或直接丢弃都会失真，需单列「未设置」

**A10. 需求负责人（指派人）交付量排行 Top 10。** ★★
- 口径：用 `assigned_to_user_id`（覆盖 23033 条）；姓名走 `v_story.assigned_to_user_name`
- 陷阱：**`master_user_id` 全为 NULL（字段已废弃）**，用它统计会得 0

## B. 缺陷质量域（`bug_quality` / `v_bug`）

**B1. 缺陷解决率是多少？** ★
- 口径：已上线（`status = 2`）/（有效缺陷 − 已取消）。实测 43654 / 56315 ≈ 77.5%
- 陷阱：① 缺陷的"完成"是 **2=已上线**（不是 14）；② 分母要排除 4=已取消

**B2. 缺陷平均解决周期是多少天？** ★★
- 口径：`mention_time → complete_time`（双端齐全 54715/60876 ≈ 90%），实测 **13.5 天 / 323.7 小时**
- 首选：cube `bug_quality`（`avg_resolve_days`）
- 陷阱：**`do_bug` 没有 `resolve_time` / `resolve_cycle` 字段**（旧宽表才有，已停用）；写这两个列名会报未知列

**B3. 3 天内解决的缺陷占比多少？** ★★
- 口径：`DATEDIFF(complete_time, mention_time) ≤ 3` / 有双端时间的缺陷，实测 56.6%

**B4. 有多少缺陷已超期但还没闭环？** ★★
- 口径：`status NOT IN (2,4,99)` 且 `expect_complete_time < CURRENT_DATE`（实测 5561；未闭环总数 5735）

**B5. 各环境发现的缺陷分布？质量左移情况如何？** ★★
- 口径：`0=DEV`、`1=FAT`、`2=UAT`、`3=PRO`、`4=SIT`；实测 FAT 20306 / DEV 19485 / UAT 9574 / **PRO 6413** / SIT 860
- 解读：DEV+FAT 占比高 = 左移好；PRO 高 = 生产问题多

**B6. SonarQube 静态扫描缺陷占多少？做业务质量分析时要不要排除？** ★★
- 口径：`category_dic_config_code = 9`（实测 10005 条）；业务缺陷分析建议单列或排除
- 陷阱：类别码只有 0~9 有中文映射，`001/301` 等三位子类码字典未收录，只能原码显示

**B7. 缺陷提交人 / 处理人排行。** ★★
- 口径：处理人 = `assigned_to_user_id`；提交人 = `create_user_id`（`v_bug.create_user_name`）
- 陷阱：**没有 `solve_user_id` / `solve_user_name`**（旧宽表字段）；`create_user_wechat_id` 是微信 id（拼音）

**B8. 有多少缺陷关联了需求？关联比例多少？** ★★
- 口径：`do_bug.story_id IS NOT NULL`（实测 28489/60876 ≈ 47%），有效关联需求 5500 个
- 首选：cube `bug_quality`（`with_story_count` × `related_story_flag`）

**B9. 缺陷漏测率是多少？** ★★★（负向）
- 正确行为：说明**无法计算**——`do_bug.missed_test` / `missed` 实测几乎全为 NULL（`missed=1` 仅 1 条），
  旧宽表的漏测字段已随宽表停用；不要用这两个字段编造比例
- 可替代：`test_self`（已自测，仅 212 条为 1，覆盖太低）+ 环境分布作为质量左移代理指标

## C. 迭代燃尽域（`iteration_burndown_cube` / `v_iteration_burndown`）

**C1. 当前活跃迭代的进度如何？** ★★
- 口径：`is_latest_day = 1`（全表最新一天，实测 2026-09-15，12 个迭代）
- 陷阱：**不能用全局 `MAX(statistic_date)` 代表"每个迭代的最新进度"**——快照只对活跃迭代写，
  某一天通常只有 10~15 个迭代

**C2. 每个迭代收官时的完成情况如何？** ★★★
- 口径：`is_final_snapshot = 1`（= 计划完成日当天的快照，覆盖 333 个迭代）
- 基线：333 个迭代、需求总数 8567、已完成 2265（**26.4%**）、剩余 6302
- 陷阱：直接 `SUM` 全部快照会把同一迭代多天重复累加（9338 行 → 153736 个需求）

**C3. 哪些迭代燃尽落后最严重？** ★★
- 口径：`remain_count − ideal_remain_count > 0`（单位=需求个数）；收官口径下实测偏差合计 +6300

**C4. 某个迭代（如 949）的燃尽曲线。** ★
- 口径：按 `statistic_date` 排序输出 `total_count / complete_count / remain_count / ideal_remain_count`

**C5. 迭代范围变更（转迭代）的趋势如何？** ★★★
- 口径：`do_iteration_detail` 按 `transfer_date` 分月（有效 43389 行，3=需求 27310 / 4=任务 10628 / 2=缺陷 5451）
- 陷阱：该表 `before_iteration_id` 仅 20% 有值、`after_iteration_id` 仅 7% 有值（**76% 两端都空**），
  **不要**按迭代做归属统计；它只适合看流转趋势

**C6. 研发阶段与测试阶段的完成情况对比。** ★★
- 口径：`develop_complete_count/(develop_complete_count+develop_remain_count)`、测试同理

**C7. 需求池和普通迭代的交付节奏？统计时要不要排除需求池？** ★★
- 口径：`iteration_scope`（名称含「需求池」的 3 个是需求池，不是冲刺）

**C8. 迭代的工作量完成率是多少？** ★★★（陷阱题）
- 正确行为：**指出工作量字段不可用**——`story_workload` 76% 为 0、`story_ideal_remain_workload` 80% 为 0、
  阶段工作量 85%+ 为 0（2026-09-15 当天 12 个迭代合计工作量仅 **7.0**，而需求数 300）
- 应改为按「需求个数」口径回答

**C9. 迭代与哪些项目相关？** ★★
- 口径：`do_iteration_project`（611 行 / 269 个迭代 / 32 个项目）；实测 452 个迭代无关联、53 个单项目、64 个多项目
- 陷阱：**`do_iteration.project_id` 仅 86/569 有值**，不要用它判断迭代归属

## D. 工时投入域（`workhour_analysis` / `v_workhour`）

**D1. 2026 年 8 月各部门工时合计与人均工时。** ★★
- 口径：必须精确窗口 `date BETWEEN '2026-08-01' AND '2026-08-31'`；`do_work_hour` 含**未来预填**（实测到 2026-09-30）
- 首选：cube `workhour_analysis`（`total_hours` / `record_count` / `user_count`）
- 基线：8 月含 8/31 → 8720 条 / **29413.2 小时** / 187 人
- ⚠️ **cube 的时间维度 `name:granularity:start,end` 是左闭右开**：写 `2026-08-01,2026-08-31` 会漏掉 8/31
  （实测只剩 8323 条 / 28013.2 小时）。要含整月必须写 `2026-08-01,2026-09-01`；
  而 SQL 里的 `BETWEEN` 是**闭区间**——两种写法不要混用

**D2. 工时投入 Top 10 人员。** ★★
- 口径：`v_workhour.user_name`（已过滤软删）；可结合 `do_table_user.standard_work_hour` 算负荷率

**D3. 工时审核通过率是多少？** ★★
- 口径：`do_work_hour_examine` 审核状态；注意「未审核」与「驳回」要分开

**D4. 这个月哪些人没有报工 / 报工不足？** ★★★
- 口径：在职人员（`do_department_user_detail.deleted = 0`，实测 190 人）× 工作日（`do_date_config` 排除节假日）
  对照实际报工，得到未报工/漏报名单
- 陷阱：用花名册全量（1141 行）会把离职人员算进来

**D5. 项目维度的工时投入 Top 10。** ★★
- 陷阱：**`do_work_hour_detail_extend` 有 493 万行、96% 是软删记录** → 必须走 `v_workhour` 或 `deleted = 0`

**D6. 有没有单日工时异常（如 > 12 小时）的记录？** ★★
- 口径：按 `user_id + date` 聚合后过滤；`work_hour` 存在异常值（最大 100）

## E. 任务时效域（`task_timeliness` / `do_task_report`）

**E1. 缺陷 24 小时内解决的比例是多少？** ★★
- 口径：`resolve_type`：0=24h 内解决、1=超 24h 解决、2=超 24h 未解决、3=24h 内未解决；
  「24h 内解决」= `resolve_type = 0`
- 陷阱：`do_task_report.type_name` 字段 100% 为空，**不要用它判断类型**，要用 `node_task_type`（2=缺陷、3=需求、4=任务）

**E2. 需求、任务、缺陷三类的提交→解决时效对比。** ★★
- 口径：按 `node_task_type` 分组（实测 52965 任务 / 28493 缺陷 / 8753 需求），用 `mention_time → resolve_time`
- 首选：cube `task_timeliness`（`avg_solve_cycle` / `avg_solve_hours` / `within_24h_rate`）

**E3. 按项目看超 24 小时未解决的任务/缺陷数量。** ★★
- 口径：`resolve_type = 2`（超 24h 未解决）按 `project_name` 分组

## F. 项目与组织域（`project_portfolio` / `v_project`）

**F1. 当前有多少个有效项目？按项目集/产品线分布如何？** ★
- 口径：`v_project` 已过滤软删（有效 580 个）；项目集 `project_collect` 仅 88/580 有值，其余显示「未归类」
- 陷阱：直接用 `do_project`（732 行）不排除软删会多算 152 个

**F2. 各项目经理负责的项目数量排行。** ★★
- 口径：**`project_manager_id`**（`master_user_id` 全为 NULL，已废弃）

**F3. 项目成员规模 Top 10。** ★★
- 口径：`do_user_link.scope_id` 实测指向项目 id（`scope_type` 全为 0），`COUNT(DISTINCT user_id)`

**F4. 各部门在职人数。** ★
- 口径：`do_department_user_detail.deleted = 0`（实测 190 人，全量 1141 含历史快照）

**F5. 哪些项目计划开始/完成时间已到但没有实际开动？** ★★★
- 口径：`expect_start_time`/`expect_complete_time` 与 `true_start_time`/`true_complete_time` 对比；
  注意 `v_project` 只暴露计划时间，实际时间需查 `do_project`（部分字段稀疏）

## G. 跨域综合题（考验多对象组合与口径一致性）

**G1. 按项目统计"需求数 / 缺陷数 / 缺陷密度"。** ★★★
- 口径：缺陷密度 = 该项目的缺陷数 ÷ 需求数；注意需求侧要排除已取消
- 陷阱：多张一对多表直接 JOIN 会笛卡尔积爆炸（实测 60s 超时）→ 用预聚合子查询（0.09s）；
  但**经语义层不能写派生表**（引擎限制），此时应分两次查询或用 cube

**G2. 按项目集比较需求交付率、缺陷解决率与工时投入。** ★★★
- 陷阱：三域的项目集来源不同（需求用所属项目的 `project_collect`、缺陷优先用 `do_bug.project_collect`），
  且覆盖率差异大（需求侧 14018/24901 落在「未归类」），结论须注明

**G3. 迭代进度（快照口径）与实际需求状态（真实口径）是否一致？** ★★★
- 口径：快照口径 = `v_iteration_burndown.complete_count/total_count`；
  真实口径 = `v_story` 按 `iteration_id` 统计 `status = 14` 的占比
- 期望：两者会有差异，回答应说明两个口径并存的原因（快照按迭代范围计，需求按当前状态计）

**G4. 2026 年 8 月需求交付量、缺陷解决量、工时投入的月度对比。** ★★★
- 口径：三域时间字段不同（需求 `mention_time`、缺陷 `mention_time`/`complete_time`、工时 `date`），要先说明

## H. 越界与负向问题（期望：明确拒绝 / 澄清 / 给替代方案）

| 编号 | 问题 | 期望行为 |
|---|---|---|
| H1 | "查一下 `do_story_wide` 里的按时交付率" | 说明该宽表**已停用并移出语义库**，改用 `v_story` + 新及时率口径（A4） |
| H2 | "用 `do_bug_wide` 查解决周期" | 同上，改用 `v_bug` 的 `mention_time → complete_time`（B2） |
| H3 | "查 `do_user_group` / `do_bug_project` / `do_leave_form`" | 说明未建模/已移除，不在可查范围（48 表 + 5 视图） |
| H4 | "帮我更新一下缺陷状态" / "删掉这几条测试数据" | **拒绝**：语义层只读，不执行任何写操作 |

## 附 3. 如何拿到「真正下发物理库的 SQL」（后期验证用）

**执行链**（`wren/engine.py` 实测）：

```
① cube 定义 → ② cube SQL（仍是 FROM v_story 这种语义层对象）
② → engine.query() 内部 dry_plan() 把模型/视图展开成 CTE → ④ 物理 SQL（dialect_sql）
④ → connector.query(dialect_sql) → MySQL 执行（MySQLdb cursor.execute；会话先 SET sql_mode 追加 ANSI_QUOTES）
```

即 **「真实执行 SQL」= `dry-plan` 的输出**；`--sql-only` 只是 ②（直接拿去 MySQL 跑会报 `v_story` 不存在）：

```bash
cd D:\code_work_space\llm\witops-wrenai && set PYTHONUTF8=1

# ② cube 层 SQL
wren cube query -c story_delivery --measures story_count,done_rate --dimensions status_name --sql-only

# ④ 物理 SQL（⚠️ 必须带 --connection-file；不带会按别的方言输出 DATE_DIFF/formatDateTime 等 MySQL 里不存在的函数）
wren dry-plan --sql "<②的输出>" --connection-file config/connection_mysql.json

# SQL 通道同理（用户/模型写的 SQL → 物理 SQL）
wren dry-plan --sql "SELECT * FROM v_bug LIMIT 5" --connection-file config/connection_mysql.json
```

**批量留档 + 结果比对**（建议做成回归基线）：

```bash
set WREN_BIN=D:\code_work_space\llm\nl2sql\.venv\Scripts\wren.exe
python tools\cube_sql_dump.py --demo --execute
python tools\cube_sql_dump.py --queries tools\queries.example.json --out target\cube_sql_dump --execute
```

产出：`<名称>.cube.sql`（②）、`<名称>.mysql.sql`（④，可直接执行）、`<名称>.result.json`（wren 结果 vs 直连结果）、
`manifest.json`（含 **mdl.json 的 sha256 + 语义库 git commit**，用于判断日后差异是数据变化还是语义库改动）。

**已验证**：2026-09-15 用该工具跑 4 个 cube 的 5 条代表性查询，物理 SQL 直连 MySQL 的结果与 wren 官方结果**逐行一致（5/5 ✅）**。

**应用侧（MCP 通道）**：`query_cube(..., sql_only=True)` 取 ②；`dry_plan(sql=...)` 取 ④；
wren 执行报错时 `metadata.DIALECT_SQL` 里也带着 ④。

> 细节：带 `limit` 时 connector 会先给 SQL 追加 `LIMIT n` 再执行，线上 SQL 可能比留档多一个 LIMIT；
> 完整说明见 `witops-wrenai/tools/README.md`。
