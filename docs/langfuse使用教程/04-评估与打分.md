# 04 · 评估与打分

> Langfuse 的 Score 系统是评估 LLM 应用质量的核心。  
> 本章覆盖：评估体系设计、四种评估方式、五维评估实战、评估单元、rubric 工程化、校准回路。  
> 参考：[Langfuse Evaluation Overview](https://langfuse.com/docs/evaluation/overview)、[LLM-as-a-Judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)、[Scores](https://langfuse.com/docs/evaluation/scores/overview)

## 1. Score 数据模型

Score 是 Langfuse 中存储评估结果的统一数据对象：

| 属性 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `name` | str | 评分名称（低基数标识） | `"sql_biz_correct_score"` |
| `value` | float | 数值（通常 0~1） | `0.85` |
| `comment` | str | 说明文字 / reasoning | `"SQL 正确回答了用户问题"` |
| `data_type` | enum | `NUMERIC` / `BOOLEAN` / `CATEGORICAL` | `NUMERIC` |
| `trace_id` | str | 关联的 trace | `"9e0ad442..."` |
| `observation_id` | str | 关联的 observation（可选） | `"aebfebd4..."` |
| `dataset_run_id` | str | 关联的实验 run（可选） | `"run-123..."` |
| `source` | enum | `API` / `ANNOTATION` / `EVALUATOR` | `API` |

### Score 关联层级

```
Dataset Run Score（实验运行级）
    └── 整个实验的聚合评分
Trace Score（追踪级）
    └── 一次完整任务的评分
Observation Score（步骤级）
    └── 某个具体步骤的评分
```

## 2. 评估体系设计（三明治评分）

本项目采用的「三明治评分」架构，将评估分为三层：

```
                    ┌─────────────────────────────┐
                    │  ① 确定性规则（全量、零成本）   │
                    │  sql_valid / schema / exec   │
                    │  → 每条查询必出分，同步执行     │
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │  ② LLM-Judge（采样、异步）     │
                    │  sql_biz_correct / report    │
                    │  → 按采样率触发，daemon 线程    │
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │  ③ 用户反馈（权威、被动）      │
                    │  user-feedback (👍/👎)       │
                    │  → 用户触发，100% 权威信号     │
                    └─────────────────────────────┘
```

### 2.1 为什么需要分层

| 层级 | 优势 | 局限 |
|------|------|------|
| 确定性规则 | 零成本、全量、即时 | 只能判确定性维度（语法/执行/安全） |
| LLM-Judge | 能判语义正确性、幻觉 | 有成本、有延迟、可能不准 |
| 用户反馈 | 最权威、零成本 | 被动、稀疏、信噪比低 |

三层互补：**确定性规则兜底安全，LLM-Judge 覆盖语义，用户反馈是最终判据**。

## 3. 方式一：确定性规则评估

### 3.1 三个确定性维度

| 维度 | Score 名 | 计算逻辑 | 值域 | 触发条件 |
|------|----------|----------|------|----------|
| Schema 匹配 | `schema_match_score` | 表和字段是否被发现 | 1.0 / 0.3 | schema-linking span 结束 |
| SQL 安全 | `sql_valid_score` | `classify_sql()` 分类 | 0.0~1.0 | sql-execution span 结束 |
| 执行成功 | `sql_exec_success` | SQL 是否执行成功 | 1.0 / 0.0 | sql-execution span 结束 |

### 3.2 SQL 安全性分类

```python
def classify_sql(sql: str) -> tuple[str, str]:
    """SQL 安全性分类
    
    Returns:
        (category, detail): 
        - ("read", "") → 只读 SELECT
        - ("full_dump", "") → 无 LIMIT 的全表扫描
        - ("write", "DELETE") → 写操作
        - ("ddl", "DROP") → DDL 操作
    """
    normalized = sql.strip().upper()
    
    # DDL 检测
    if any(normalized.startswith(kw) for kw in ["CREATE", "DROP", "ALTER", "TRUNCATE"]):
        return ("ddl", normalized.split()[0])
    
    # 写操作检测
    if any(normalized.startswith(kw) for kw in ["INSERT", "UPDATE", "DELETE", "MERGE"]):
        return ("write", normalized.split()[0])
    
    # 全表扫描检测
    if "LIMIT" not in normalized and "WHERE" not in normalized:
        return ("full_dump", "")
    
    return ("read", "")
```

### 3.3 打分时机

确定性评估在 **span 结束时同步打分**，零 LLM 成本：

```python
# LangfuseSpanMiddleware._maybe_score 中
def score_deterministic(span_name, tool_result):
    if "schema-linking" in span_name:
        score = 1.0 if schema_found else 0.3
        langfuse.score_current_trace(name="schema_match_score", value=score)
    
    elif "sql-execution" in span_name:
        # SQL 安全
        category, detail = classify_sql(sql)
        safety_map = {"read": 1.0, "full_dump": 0.4, "write": 0.0, "ddl": 0.0}
        langfuse.score_current_trace(name="sql_valid_score", value=safety_map[category])
        
        # 执行成功
        exec_score = 1.0 if tool_result.get("error") is None else 0.0
        langfuse.score_current_trace(name="sql_exec_success", value=exec_score)
```

## 4. 方式二：LLM-as-Judge 评估

### 4.1 三个语义维度

| 维度 | Score 名 | 评估内容 | 采样率 |
|------|----------|----------|--------|
| SQL 业务正确性 | `sql_biz_correct_score` | SQL 结果是否回答了用户问题 | 30% |
| 报表准确性 | `report_table_score` | 报表/表格数据的准确度 | 30% |
| 分析报告质量 | `analysis_report_score` | 分析质量 + 幻觉检测 | 30% |

### 4.2 评估单元（Evaluation Subject）

**核心设计**：LLM-Judge 的输入必须是干净、完整、无歧义的结构化数据，而非原始 span 数据。

```json
{
    "subject_id": "<trace_id>",
    "ts": "2026-10-14T03:02:31Z",
    "question": "有多少员工",
    "db_name": "WIT运营管理平台数据库",
    "final_sql": "SELECT COUNT(*) FROM employee WHERE status = 'active'",
    "exec_status": { "ok": true, "error": "" },
    "result_summary": {
        "row_count": 1,
        "head_rows": [["employee_count", "190"]],
        "note": "head-10/truncated-at-8000"
    },
    "final_answer": "当前数据库中共有 190 名在职员工。",
    "report": null,
    "task_type": "sync",
    "skill_tags": ["nl2sql-sql-of-thought"]
}
```

**为什么需要评估单元**（解决 5 个失真源）：

| 失真源 | 问题 | 评估单元如何解决 |
|--------|------|-----------------|
| F1: judge 拿探路 SQL 当最终答案 | 一次查询多次 `run_sql`，span 无 final 标记 | `final_sql` 字段明确标识最终 SQL |
| F2: 大结果只留 VFS 占位符 | >8KB 的 span output 被替换为路径 | `result_summary` 始终携带 head_rows |
| F3: 报告被压缩到 2KB | `write_file` input 被 `_compact` 截断 | `report.text_head` 保留关键部分 |
| F4: 问题文本解析错误 | 深 agents 场景取到系统通知 | `question` 字段直取 `metadata.user_question` |
| F5: rubric 笼统 | 无分档锚点、无 few-shot | rubric 托管在 Langfuse Prompt 中 |

### 4.3 LLM-Judge 评估流程

```
1. 查询完成 → 组装评估单元
2. 按采样率决定是否评估（NL2SQL_EVAL_JUDGE_SAMPLE=0.3）
3. 命中 → 投入持久化 SQLite 队列（eval_queue.sqlite）
4. 单例 daemon worker 消费队列
5. 从 Langfuse 拉取 rubric prompt
6. 调用 LLM 评估
7. 写入 Score + reasoning
8. 失败 → 留在队列待补评（不丢）
```

### 4.4 Rubric 工程化

评估标准（rubric）不在代码中硬编码，而是作为 Langfuse Prompt 管理：

```text
你是一个 SQL 查询评估专家。请评估以下 SQL 查询是否正确回答了用户的问题。

## 用户问题
{{question}}

## 数据库
{{db_name}}

## 最终 SQL
{{final_sql}}

## 执行结果
{{result_summary}}

## Agent 回答
{{final_answer}}

## 评分标准

| 分数 | 含义 | 锚点示例 |
|------|------|----------|
| 1.0 | 完全正确 | SQL 精确回答了问题，结果完全匹配 |
| 0.75 | 基本正确 | SQL 回答了主要问题，但有轻微遗漏 |
| 0.5 | 部分正确 | SQL 回答了部分问题，有重要遗漏 |
| 0.25 | 基本错误 | SQL 有明显错误（JOIN 错、条件遗漏） |
| 0.0 | 完全错误 | SQL 与问题无关或完全答非所问 |

## 输出格式（严格 JSON）

{
    "score": 0.x,
    "reasoning": "一句话说明评分理由",
    "issues": ["发现的具体问题（如有）"]
}
```

### 4.5 通过 UI 配置 LLM-as-Judge

1. **Settings → Models**：配置评估模型的 API Key（如 OpenAI、DeepSeek）
2. **Evaluations → New Evaluator**：
   - **Name**：`nl2sql-sql-correctness`
   - **Target**：所有名为 `chat-turn` 的 trace
   - **Model**：选择评估模型
   - **Prompt**：粘贴上述 rubric
   - **Sampling**：30%（避免全量评估的高成本）
   - **Filter**：`environment = production`

### 4.6 内置评估模板

Langfuse 提供多个开箱即用的评估模板：

| 模板 | 用途 | 适用场景 |
|------|------|----------|
| **Hallucination** | 检测幻觉 | 回答是否与上下文一致 |
| **Helpfulness** | 有用性评估 | 回答是否有帮助 |
| **Toxicity** | 毒性检测 | 有害/不当内容 |
| **Context Relevance** | 上下文相关性 | 检索结果与问题相关 |
| **Context Faithfulness** | 忠实度 | 回答是否基于检索到的上下文 |
| **Answer Relevance** | 回答相关性 | 回答是否切题 |

## 5. 方式三：用户反馈

### 5.1 反馈类型判别

本项目区分「查询反馈」和「闲聊反馈」，使差评信号更精准：

| 信号 | 来源 | 可靠度 | 说明 |
|------|------|--------|------|
| 确定性评分存在 | trace 上有 `schema_match_score` 等 | ★★★ | 闲聊 trace 恒无，查询 trace 恒有 |
| run_sql 族 observation | trace 有 `skill:sql-execution:*` | ★★★ | 查询铁证 |
| SQL 快照 | FeedbackStore.sql 非空 | ★★☆ | 零成本本地检查 |

```python
def classify_feedback_type(thread_id, message_id, sql_snapshot=""):
    """'query' | 'chat' | ''（未判定）"""
    # 快路径
    if sql_snapshot:
        return "query"
    # 慢路径：查 Langfuse trace
    trace_id = find_message_trace_id(thread_id, message_id)
    if trace_id and has_query_scores(trace_id):
        return "query"
    return "chat"
```

### 5.2 反馈写入

```python
# 前端 👍/👎 → 后端 API
@app.put("/api/threads/{tid}/messages/{mid}/feedback")
async def submit_feedback(tid, mid, body):
    rating = body["rating"]  # "positive" | "negative"
    comment = body.get("comment", "")
    
    # 1. 写入本地 SQLite（唯一真相）
    feedback_store.upsert(tid, mid, rating, comment)
    
    # 2. 判别反馈类型
    fb_type = classify_feedback_type(tid, mid, sql_snapshot=feedback_store.get_sql(tid, mid))
    
    # 3. 写入 Langfuse Score
    score_value = {"positive": 1.0, "negative": 0.0}.get(rating, 0.5)
    langfuse.create_score(
        name="user-feedback",
        value=score_value,
        trace_id=find_trace_id(tid, mid),
        comment=comment,
        metadata={"feedback_type": fb_type},
    )
```

## 7. 校准回路

### 7.1 为什么需要校准

LLM-Judge 本身可能不准确。校准回路让分数的含义「可测量、可回归、可持续」：

```
┌────────────────────────────────────────────────┐
│  ① 回归集（人工标注的好/坏样本）                   │
│  ② 定期重跑 Judge → 一致率（Judge 与人工的一致度）  │
│  ③ 一致率 < 阈值 → 调整 rubric / 模型 / 埋点      │
│  ④ 变更先过门禁再上线                             │
└────────────────────────────────────────────────┘
```

### 7.2 一致率计算

```python
def calculate_agreement(judge_scores, human_labels):
    """二值一致率：Judge 与人工标注的好/坏是否一致"""
    threshold = 0.5
    correct = 0
    for j_score, h_label in zip(judge_scores, human_labels):
        j_label = "good" if j_score >= threshold else "bad"
        if j_label == h_label:
            correct += 1
    return correct / len(human_labels)

# 目标：一致率 ≥ 80%
```

### 7.3 评估精准化七个失真源

本项目识别的 Judge 失真源及解决方案：

| # | 失真源 | 后果 | 解决方案 |
|---|--------|------|----------|
| F1 | judge 拿探路 SQL 当最终答案 | 对错颠倒 | 评估单元的 `final_sql` 标记 |
| F2 | 大结果只留 VFS 占位符 | judge 读不到数据 | `result_summary` 始终携带 |
| F3 | 报告正文被压缩到 2KB | 报告评审只看开头 | `report.text_head` |
| F4 | 问题文本解析错误 | 取到系统通知 | `question` 直取 metadata |
| F5 | rubric 是一句笼统话 | judge 靠猜 | rubric 托管 + 分档锚点 |
| F6 | 采样失败即丢 | 该评没评 | 持久化队列 + 补评通道 |
| F7 | 进程被杀前未 flush | 分数丢失 | 停机 flush 钩子 |

## 8. 评估最佳实践

### 8.1 多维度评估矩阵

| 维度 | 类型 | 成本 | 频率 | 适用场景 |
|------|------|------|------|----------|
| Schema 匹配 | 确定性代码 | 零 | 每条 | 基础质量 |
| SQL 安全性 | 确定性代码 | 零 | 每条 | 安全底线 |
| 执行成功 | 确定性代码 | 零 | 每条 | 可用性 |
| 业务正确性 | LLM Judge | 中 | 采样 30% | 深度质量 |
| 报表准确性 | LLM Judge | 中 | 采样 30% | 报表场景 |
| 分析质量 | LLM Judge | 中 | 采样 30% | 分析场景 |
| 用户满意度 | 真实反馈 | 零 | 用户触发 | 最终判据 |

### 8.2 分数解读与行动

| 分数范围 | 含义 | 行动 |
|----------|------|------|
| 0.8 ~ 1.0 | 优秀 | 保持 |
| 0.5 ~ 0.8 | 一般 | 关注改进 |
| 0.0 ~ 0.5 | 较差 | 优先修复，自动采集为 BadCase |
| N/A | 未评估 | 检查采样配置 |
