# 07 · 反馈闭环

## 1. 闭环全景

```
                         ┌─────────────────────────────────────────┐
   用户提问 ──→ Agent 执行 ──→ ① SQL 只读硬拦截（运行时安全闸门）    │
                     │              │                               │
                     │   五维评分     │  差评/低分/异常                │
                     ▼              ▼                               │
           Langfuse Traces     ④ collect_badcase                    │
           + Scores             ──→ Dataset:badcase                 │
                     │              │                               │
               前端 👍/👎           ▼                               │
                     │        ⑤ BadCase 状态机                      │
                     │         (pending → reviewed)                 │
                     │              │                               │
                     │              ▼                               │
                     │    ⑤ 人工复审 + 标注                         │
                     │    (补正确 SQL / 定 bad_type)                 │
                     │              │                               │
                     │              ▼                               │
                     │    ⑥ 修复 prompt → staging                   │
                     │              │                               │
                     │              ▼                               │
                     │    ② run_experiment 离线门禁                  │
                     │    (A/B 回归测试)                             │
                     │              │                               │
                     │              ▼                               │
                     │    ⑦ canary 灰度发布                         │
                     │              │                               │
                     │              ▼                               │
                     │    ③ feedback_gate 在线门禁                   │
                     │    (真实用户 👍/👎 对比)                      │
                     │              │                               │
                     │              ▼                               │
                     │    production 全量发布                        │
                     │              │                               │
                     └──────────────┘                               │
                               闭环完成                              │
```

### 1.1 三道闸门

| 闸门 | 时机 | 工具 | 判据 | 作用 |
|------|------|------|------|------|
| ① SQL 只读硬拦截 | 每条查询执行前 | `classify_sql` | 写/DDL → 直接拒绝 | **运行时安全** |
| ② 离线 A/B 回归门禁 | 发版前预检 | `run_experiment` | 核心维均值退化 > 阈值 | **离线质量** |
| ③ 在线真实反馈门禁 | 放量后/灰度 | `feedback_gate` | 好评率退化 > 阈值 | **在线口碑** |

## 2. 用户反馈采集

### 2.1 反馈入口

```
用户消息: "统计 artist 表有多少艺术家"
Agent 回复: "共 275 位艺术家"
          [👍] [👎] [评论]  ← 用户交互
```

### 2.2 反馈写入链路

```
前端 PUT /api/threads/{tid}/messages/{mid}/feedback
  ├─► 本地 FeedbackStore（SQLite：rating/note/question/sql/context/feedback_type）
  └─► 后台线程写 Langfuse user-feedback score
      （好评 1.0 / 差评 0.0 / 撤销 -1.0 哨兵分）
```

### 2.3 反馈类型判别

```python
def classify_feedback_type(thread_id, message_id, sql_snapshot=""):
    """区分「查询反馈」和「闲聊反馈」
    
    查询类反馈参与 BadCase 采集和门禁统计
    闲聊类反馈仅计入总数和信噪比看板
    """
    # 快路径：有 SQL 快照 → 查询
    if sql_snapshot:
        return "query"
    
    # 慢路径：查 Langfuse trace
    trace_id = find_message_trace_id(thread_id, message_id)
    if not trace_id:
        return ""  # 未判定
    
    # 有确定性评分 → 查询（闲聊 trace 恒无评分）
    if has_query_scores(trace_id):
        return "query"
    
    # 有 run_sql 族 observation → 查询
    if has_sql_tools(trace_id):
        return "query"
    
    return "chat"
```

## 3. BadCase 自动采集

### 3.1 采集规则

每天 02:13 cron 自动扫描最近 1 天的 trace：

| 条件 | 阈值 | 命中含义 |
|------|------|----------|
| 用户差评 | `user-feedback = 0` | 用户明确不满 |
| 业务正确性低 | `sql_biz_correct < 0.6` | LLM Judge 判定不正确 |
| 执行失败 | `sql_exec_success = 0` | SQL 执行报错 |
| 只收集查询类 | `feedback_type = "query"` | 排除闲聊差评 |

### 3.2 采集命令

```bash
# 生产环境 cron 脚本
docker exec nl2sql-app_langgraph-api_1 bash -c \
  "cd /app && PYTHONPATH=/app/src /app/.venv/bin/python \
   -m agent.eval.collect_badcase --days 1"
```

### 3.3 采集产物

**Dataset Item**（写入 Langfuse Dataset:badcase）：

```json
{
    "datasetName": "badcase",
    "input": "查 1990 年后上映、按评分倒序的前 10 部电影",
    "expectedOutput": "",
    "metadata": {
        "source_trace_id": "9e0ad442-c830-...",
        "reasons": ["sql_biz_correct_score=0.25", "user_feedback=0"],
```

## 4. 人工复审与标注

### 4.1 复审流程

```bash
# 查看待审列表
python -m agent.eval.badcase_status list --status pending

# 交互式复审（自动打开 Langfuse trace 页面）
python -m agent.eval.badcase_status review
```

复审交互：

```
[1/3] pending
  问题   : 查 1990 年后上映、按评分倒序的前 10 部电影
  命中原因: sql_biz_correct_score=0.25, user_feedback=0
  数据库 : imdb
  > 按 f/i/r/s/q 操作：
    f = fixed（真问题，已修复）
    i = invalid（误报，非模型问题）
    r = reviewed（确认真问题，待修）
    s = skip（跳过）
    q = quit（退出）
```

### 4.2 标注页面（前端 UI）

前端提供专门的标注页面，功能比 CLI 更丰富：

1. **查看 trace**：直接展示 Langfuse trace 详情
2. **判断有效性**：真问题 vs 误报
3. **补正确 SQL**：人工输入标准答案 SQL
4. **执行验证**：在目标数据库上执行人工输入的 SQL
5. **定错误类型**：`bad_type` 分类（JOIN 错误 / 条件遗漏 / 聚合错误 / ...）
6. **确认入库**：写入 Dataset:badcase + 更新 badcase_status

### 4.3 状态机

```
pending ──review──▶ reviewed ──mark fixed──▶ fixed（离开回归集）
    │                    │
    │                    └──mark invalid──▶ invalid（离开回归集）
    │
    └──直接 mark──▶ fixed / invalid
```

| 状态 | 含义 | 是否在回归集中 |
|------|------|---------------|
| `pending` | 新采集，待复审 | ✅ 参与回归 |
| `reviewed` | 确认真问题，待修 | ✅ 参与回归 |
| `fixed` | 已修复 | ❌ 离开回归集 |
| `invalid` | 误报 | ❌ 离开回归集 |

### 4.4 标注命令

```bash
# 标记为已修复
python -m agent.eval.badcase_status mark 9e0ad442 fixed \
    --note "修复了 JOIN 逻辑，name 应连 person 表"

# 标记为误报
python -m agent.eval.badcase_status mark a3d9e021 invalid \
    --note "用户测试差评，非模型问题"

# 查看统计
python -m agent.eval.badcase_status summary
```

## 5. 修复与回归验证

### 5.1 修改 Prompt

```bash
# 在 Langfuse UI 编辑 prompt → 同步到 staging
DC -m agent.prompt.sync_prompts --all --label staging --commit "修复缺年份过滤"
```

### 5.2 离线门禁（闸门②）

```bash
# 用回归集（pending + reviewed）做 A/B 回归
DC -m agent.eval.run_experiment --from-badcase --labels production staging
```

结果示例：

```

production   0.61              0.95        1.00

```

### 5.3 标记修复

```bash
# 门禁通过后标记 fixed
DC -m agent.eval.badcase_status mark 9e0ad442 fixed --note "SQL 生成要求带年份过滤"
```

## 6. 灰度发布

### 6.1 Canary 灰度

```bash
# 修改容器 .env.prod
LANGFUSE_CANARY_LABEL=staging
LANGFUSE_CANARY_RATIO=0.1    # 10% 流量走新版本

# 重启服务生效
```

### 6.2 在线门禁（闸门③）

灰度期间持续监控真实用户反馈：

```bash
# 对比新旧版本的用户好评率
python -m agent.eval.feedback_gate \
    --reference production \
    --candidate canary \
    --threshold 0.1
```

## 7. 完整时间线走读

一个差评从产生到闭环的完整过程（以 imdb 库为例）：

| 步骤 | 时间 | 动作 | 角色 | 对应章节 |
|------|------|------|------|----------|
| 1 | Day 1 15:12 | 闸门① SQL 只读硬拦截 → 放行 | 自动 | §1 闸门① |
| 2 | Day 1 15:13 | 五维评分：`sql_biz_correct=0.25` | 自动 | §2 五维评分 |
| 3 | Day 1 15:14 | 用户点 👎 + 评论 | 用户 | §2 用户反馈 |
| 4 | Day 2 02:13 | `collect_badcase` 自动采集 → pending | cron | §3 自动采集 |
| 5 | Day 2 09:00 | 人工复审 → 确认真问题（按 r） | 工程师 | §4 人工复审 |
| 6 | Day 2 09:20 | 改 prompt → `sync_prompts --label staging` | 工程师 | §5 修复 |
| 7 | Day 2 09:30 | 闸门② `run_experiment` → exit 0 | 工程师 | §5 门禁② |
| 8 | Day 2 14:00 | canary 灰度 10% | 工程师 | §6 灰度 |
| 9 | Day 5 09:00 | 闸门③ `feedback_gate` → exit 0 | cron | §6 门禁③ |
| 10 | Day 5 09:10 | `production` 标签全量发布 | 工程师 | §6 全量 |
| 11 | Day 6 02:13 | 次日采集确认不再复现 → 闭环 | cron | 验证 |
