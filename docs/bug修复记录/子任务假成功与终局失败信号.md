**类型**：中间件把失败伪装成正常回答（缺机读信号）⇒ 三个读取方各自猜错
**严重程度**：高（用户看到「答完了」但**一 SQL 未执行**；卡片进度与模型拿到的事实互相矛盾；单轮 620.8s）

**触发**：生产 trace `3dcc9a66f3b5734b8df7fc6941478b1d`，thread `01a0e694` / 子 run `01a0e695`，问题「丛培强 本月工时分析」

## 二、三个用户可见症状 → 根因

| # | 现象 | 根因 |
|---|---|---|
| 1 | 主 agent 调 `check_async_task` 拿到 **`status:"success"` + 超时文案**，只能自己推理「marked as success, but the result is actually a timeout error」 | 终态判据只看 `run.status`，不看内容（**3 处独立判据**都这样：watcher / `check_async_task` / `run-status`） |
| 2 | 卡片停在第 2 步「Schema 提取与裁剪」计时涨到 8m14s，而模型被告知 `0/6 (0%)` / `current_step=第 1 步` | 进度有两个源：卡片读 `state.todos`（`ProgressBoundaryMiddleware` 确定性推进，权威），`check_async_task` 只反扫 messages 里的 `write_todos`（旧、停在第 1 步） |
| 3 | 234s 白等（06:01:45 → 06:05:38），整轮 620.8s，**一 SQL 未执行** | 超时后回合没结束：CaliberGate 见「无口径块」把回合打回模型 |

**症状 3 的机制细节**：`_no_block` 的两条逃生口对超时文案**都不成立**——本轮确实取过知识料（`_used_evidence_tool` 为真），而超时文案里没有「本次未依据知识库口径」字样。于是必然 `jump_to="model"`。

另外 watcher 侧还有一个 **时钟口径**错误：卡死预算从 watcher 自己的 `loop_start` 起算，而 run 的 `created_at` 更早 ⇒ 620.8s 的 run 撞上 600s 预算，watcher 的强制 `timeout` 写入与 run 自己的 `success` 收尾**相差 17 秒**，两套账都落了盘。

## 三、修法：失败信号机读化，终态与进度各收敛到一个权威源

### 核心原则

1. **失败信号必须机器可读**——文案是给用户看的，不能当协议（本仓已有两次「纯 prompt 契约被证伪」的先例）。
2. **无标记 = 今天的行为**（逐字不变），由负对照锁住；历史 checkpoint 不受影响。

### 新增契约 `src/agent/utils/failure_signal.py`

`AIMessage.additional_kwargs["nl2sql_failure"] = {"kind","detail","at"}`，kind ∈ `model_timeout` / `quota_exhausted` / `model_required`。只由代码写（模型/工具伪造不了），过 checkpoint 序列化往返并一路到前端。`run_status_for(kind)` 单点产出 run 状态：`model_timeout → "timeout"`，其余 → `"error"`——**只许产出 `error`/`timeout`**（都在 `_RUN_DONE_STATUSES` 里，写错的串会让卡片永不结束）。

### 五个消费点

| 消费点 | 改动 |
|---|---|
| `model_timeout` / `quota_error` / `model_required` 三个中间件 | 写友好文案的**同一条消息**上打戳；**文案一字符未改** |
| `CaliberGateMiddleware._after` | 紧跟 `isinstance(last, AIMessage)` 后：见戳 → 记日志并 `return None`（放行），消灭 234s 空窗 |
| `check_progress._enhanced_build_check_result` | **只在 `run["status"]=="success"` 时**读戳 → 降级为 `timeout`/`error`、填 `error_kind`/`error`，借道既有失败分支。running 时绝不降级（戳可能是上一轮遗留） |
| `sync_subagent_todos` 终态入口 + `_terminal_error` | success + 有戳 ⇒ 改判；改判后**零额外代码**自动修好四件事：不再发「已完成」续跑、发带原因的 `[系统自动通知]` 失败汇报、终态写入正确、trace `SUBAGENT_COMPLETE` 带真实终态。`_terminal_error` 兜底用戳的 detail（本环境 `run.error` 恒为 None） |
| `api/thread_run_status.classify` | 判据 5 扩成「`last_run.status` 是失败终态 **或** 末条 AI 带戳」；`last_error` 回落 `detail_of(mark)` ⇒ 主图 `turn_failed` ⇒ 前端「上一轮执行失败（未完成）」+ 重试按钮 |

### 顺手修的两处

- **`async_tasks` 是整条替换 reducer**：`check_async_task` 重建的 `updated_task` 只带固定 8 键，会**抹掉** watcher 刚写的 `error`/`failure_reported` ⇒ 显式保留这三个键。
- **watcher 卡死预算改口径**：起点从 `loop_start` 换成**当前 run 的 `created_at`**（取不到退回 `loop_start`）。必须取当前 run 的、**不能用 `task["created_at"]`**——`update_async_task` 重派发时原样保留它，用 task 字典会让重派发任务一开局就被误杀。

### 进度权威源

`check_async_task` 改为 `_todos_from_state(thread_values)` **优先**、messages 反扫降级为 fallback（卡片读的就是同一个 `values["todos"]`）。

## 四、故意不改

1. **`_last_message_is_final` 不动**：它判的是「末条是不是终稿文本」，失败消息确实是终稿；前端 settle 依赖它。改了会新造「未完成」态、把「执行失败」横幅换成「已中断」。两者因此天然互斥，不会同时出两个横幅。
2. **不给超时加额外重试**：SDK 侧 `timeout=60, max_retries=3` 已是四连击 ≈240s，再加会撞工具超时 300s。超时的正确出路是快速失败 + 明确失败态 + 用户可见的重试按钮。
3. **前端一行不动**（`async_tasks.status` 值域已含 `error`/`timeout`，`turn_failed` 分支已存在）。
4. 不动 `progress_boundary` 的分桶/推进、`_merge_steps_monotonic`、任何用户可见文案。
