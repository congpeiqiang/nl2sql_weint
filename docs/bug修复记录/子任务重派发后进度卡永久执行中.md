# 子任务被 update_async_task 重派发后，进度卡永久停在「执行中」

**日期**：2026-09-14
**类型**：状态机缺陷（重派发不重建进度同步器）+ 结果摘要行数口径错误（诱发误派发）
**严重程度**：高（子任务早已结束，前端进度卡永久转圈、状态残留 running，用户以为还在查询）

---

## 一、问题描述

会话 `01a09e22-3384-7c01-b93d-b6e50635bc40`（trace `a6f86bbdb6fe32d693ed8c9fdf84b909`）：

> 「前 1 分钟进度条执行完了查询阶段，进度条又重新查询执行 (1m11s...)」

现象完整复述：

1. `04:19:31` 查询阶段进度条走完（卡片一度**离开**「执行中」分组）——用户看到的「执行完了」；
2. 紧接着**同一个任务卡又回到「执行中」**，`└ 查询执行 (1m11s...)` 一直转；
3. 直到会话结束（`GET /threads/{tid}/state`）卡片内容仍冻结在 `🔍 nl2sql 执行进度 (6/8)`，`async_tasks[task].status = "running"`、`active_queries[task] = true`，state 停在 checkpoint `2026-09-14T04:20:03.846` 再没动过。

### 复现条件

- 子 agent 正常跑完一轮查询（run #1 `success`），终态 `async_tasks` / `final steps` / `active_queries=false` 全部落地（sync watcher 随后在 ~10s 宽限期结束、`break` 退出）；
- 主 agent 在 `check_async_task` 看到**结果摘要的行数与正文自相矛盾**（见根因 2），判定「数据缺失」；
- 主 agent 用 `update_async_task` 对**同一个 task_id** 补发指令 → deepagents 用 `runs.create(multitask_strategy="interrupt")` 换 run（`status` 改回 `running`，`created_at` 保留）→ 卡片重新出现在执行中分组，elapsed 从原始起点继续涨；
- `update_async_task` **不拉任何进度同步器**，而旧 watcher 已经退出 → 进度/终态再也没人写。

---

## 二、根因分析

### 根因 1（直接原因）：重派发不重建进度同步器

进度同步器（`src/agent/subagents/sync_subagent_todos.py`）的**唯一**拉起路径是 `sync_launcher.py` 对 deepagents `_build_start_tool` 的包装，即只覆盖 `start_async_task`：

- `update_async_task` 换 run 后没有 watcher → `subagent_steps_map[task]` 不再更新；
- 旧 watcher 在写入终态后只多活 `POST_COMPLETE_MAX_CYCLES = 20`（20 × 0.5s = 10s）就 `break`，其「终态回退自愈」（每 4 周期比对一次 `async_tasks`）也随线程一起消失；
- 于是 `status="running"` + `active_queries=true` + 冻结的 `subagent_steps_map` 形成**永久残留**，前端每 1s 轮询拿到的都是同一份死数据。

### 根因 2（诱发原因）：`_summarize_result` 跨表求和，行数与正文自相矛盾

`check_progress.py::_summarize_result` 的旧实现：

```python
total_data = sum(len(r["data"]) for r in table_runs)   # 把「所有表格」的行数加在一起
...
table_part = first["header"] + "\n" + first["sep"] + "\n" + "\n".join(kept) + suffix
```

子 agent 的最终答复里是**两张表**（39 行明细 + 14 行「各人员合计」），正文写「已查询到 39 行明细」；摘要因此写成 **「数据表共 53 行」**（39+14），且只渲染第一张表的前 20 行。主 agent 读到这个既无法归因、又与正文冲突的数字，判定明细缺失，于是 `update_async_task` 补发「补取完整 39 行明细（write to file）」。

> 注意：这次重派发并**没有真的重查**。子 run #2 只做了 `write_file`(CSV) → `read_file`（被权限拒）→ `grep`（被拒）→ 直接给出答复，**零 `run_sql`**。所以「又重新查询执行」是**显示层回退**，不是真的重跑查询——排查时不要被它误导。

### 根因 3（放大器）：最终 steps 写入是一次性的，失败不重试

完成分支里（`sync_subagent_todos.py`）：

```python
if not has_notified_completion:
    has_notified_completion = True      # ← 置位在写入之前
    ...
    try:
        await asyncio.to_thread(_sync_update_state, ...)
    except Exception as e:
        _logger.warning("[sync] 写入最终 steps 失败: %s", e)   # ← 只告警，永不重试
```

与同段 `async_tasks` 的「2s 退避重试到 `COMPLETE_WRITE_MAX_SECONDS`（300s）」形成不对称：主线程 in-flight run 期间 `update_state` 被拒时，`async_tasks` 会重试成功，**最终 steps 却永久丢失** → `status=success` 而卡片内容仍是中间态（本次现象里 6/8 的 `└ 查询执行 (1m11s...)` 就是这么留下来的）。

### 根因 4（伴生）：steps 会随 todo 重写而回退

子 run 被重派发后，子线程 `todos` 从 pending 重新开始；watcher 每轮照抄，会把**已完成**的步骤降级回 `pending/in_progress` → 前端进度条回退（8/8 → 6/8 → 「查询执行」重新转圈）。

## 三、解决方案

全部在后端，前端零改动（进度卡是纯渲染器：直接打印 `todo.content`、按 `status` 出图标）。

| # | 位置 | 改动 |
|---|---|---|
| P0 | `check_progress.py::_patched_build_update_tool` 的 `_w`/`_aw` | 新增 `_relaunch_sync_after_redispatch()`：重派发成功后，若 `is_sync_alive(task_id)` 为假则 `launch_sync(..., pin_run_id=True)` 重建 watcher（复用 `sql_approval.py` / `task_cancel.py` 已有的存活检查写法，`launch_sync` 本身不幂等）。主线程 id 取自 `runtime.config["configurable"]["thread_id"]`（`runtime.state` 是图状态通道，不含 thread_id）；仅当条目 `status == "running"` 时才算重派发；任何失败都只告警，绝不让工具调用失败 |
| P0b | `sync_subagent_todos.py::_get_run_status` | 新增 `expect_run_id`：重派发路径只跟踪新 run_id，避免换 run 窗口期读到**旧 run 的终态**、开局即写终态。匹配不到返回 `None` 走等待分支；20s 仍不出现则退回「取最新 run」并 WARNING，**不退出**（退出=卡片永久卡死） |
| P1 | `sync_subagent_todos.py` 完成分支 | 最终 steps 载荷只快照一次并缓存；写失败按 2s 退避**重试到成功**（上限仍为 `COMPLETE_WRITE_MAX_SECONDS = 300`，防僵尸线程）。退出闸门由 `async_tasks_written and active_queries_cleared` 改为**并上 `final_steps_written`**，确保「完成后多活 10s 让耗时稳定」和终态回退自愈不会在最终步骤落地前就 `break`。四个时限常量提到模块级，便于离线测试压到毫秒级 |
| P2a | `check_progress.py::_summarize_result` | 行数**不再跨表求和**：先按「（续）」标记/表头相同把分段归组为**逻辑表**（保住 `8ccef016` 那次「两段 38 行 = 76 行」的语义），再逐张点名行数（`数据表 2 张（第1张 39 行、第2张 14 行，逐张统计非合计）`）；**每张表都渲染**各自表头 + 配额行数（每张至少 1 行，余量补给还有未展开行的表，总行数仍 ≤ 20）；marker 增加「未展开的行不是数据缺失…无需重新派发子任务」 |
| P2b | `sync_subagent_todos.py` 运行分支 + 启动块 | 新增 `_read_steps_snapshot()` / `_merge_steps_monotonic()`：启动时读旧 steps 建「已完成内容」基线（用 `_strip_duration_suffix` 做稳定 key），运行分支按内容合并，**已完成的步骤永不回退**；若启动时已有旧 steps（= 重派发），先写一次占位 —— 沿用旧步骤、header 改为 `🔍 nl2sql 执行进度 (6/8) · 已重新派发，继续执行` 并置 `in_progress` |

> 未做：`check_async_task` 不扩展去写 `subagent_steps_map`。deepagents 的 `_build_check_command`（`async_subagents.py:399-422`）本来就会回写 `async_tasks[task].status`，已是既有兜底；在工具调用路径里再写主 state 会与图的 reducer 抢时序，收益不抵风险。

## 五、第二轮（后续 trace 实测后的补充修复）

2026-09-14 复测 trace `72e222c0e8d5951f9c4bdcedf0623f08`（会话 `01a09e92-…`）：P0~P2b 都已生效（重派发后 watcher 确实被重建、卡片一度恢复 `7 步已完成`），但**症状依旧** —— 说明还有一层独立机制。

### 根因 5（治 A）：主 run 从**陈旧 checkpoint** 分叉，按节点边界重写整份 state 快照

- `06:22:26.219/.697/.934` watcher 三次写入全部正确（`success` / `aq=false` / `7 步已完成`）；
- **1.3 秒后** head 变成续跑 run 的 checkpoint：`source=input`，`parent_checkpoint_id = 1f1b0045-…`（`06:20:10.131`，= 子任务启动后 4 秒、任何进度产生之前的旧状态），而**当时的 head 是 `1f1b004a-…`（`06:22:26.934`，step 134）**；
- 该 run 每过一个节点边界就重写整份内存快照（`src=loop`），前端「最后写入者胜」→ 卡片被打回「执行中、无步骤」；watcher 之后的写入落在**另一条 lineage**（step 132/133/134），只在无节点写入的窗口露出。

**机制已用最小复现证实**（`D:\tmp\repro_fork_from_stale_checkpoint.py`，InMemorySaver + 2 节点图，ALL PASS）：`runs.create` **不带** `checkpoint_id` → 父=当时 head、继承 watcher 终态；**带旧 `checkpoint_id`** → 父=那个旧 cp、state 回退（running、steps 归零）。即 langgraph 会尊重显式 `checkpoint_id` 并回退到它——生产续跑 run 的 `multitask_strategy=enqueue` + 显式旧 `checkpoint_id`（turn 收尾点）正是这么把 state 打回去的。

> **根因位置在前端续跑调用处**（`useChat.ts` 为 DLP 加密文件，不可读改）。后端只能做**缓解/自愈**；根治需前端去掉那个陈旧的 `checkpoint_id` 参数（1 行）。判定依据：后端 `src/` 无该参数的生产者、`thinking_toggle.py:37` 表明续跑消息由前端发出、`src/api/thread_fork.py` 是后端唯一显式使用 `checkpoint_id` 的地方。

### 根因 6（治 B）：结果摘要的 20 行上限**没有正当逃逸通道** → 重派发风暴

- marker 承诺的「完整数据可通过 `check_async_task` 增量读取获取」在结果**已定格**时是假话：`06:22:29.096` 全量读取与 `06:22:30.788` `since=56` 返回**完全相同**内容（同 2774 chars）——没有新消息，增量通道什么都给不出；
- 只有子 agent 之后又产生新消息，`since=N` 才吐未摘要原文 → 主 agent 于是用 `update_async_task` **去制造新消息**：`06:22:44 / 06:24:09 / 06:25:46 / 06:27:37` 四次重派发，每次跟 `sleep 75/90/90/100`；子 run #2~#5 合计约 35 秒、**零 `run_sql`**，只复述文本（约 6.5 分钟空转）；
- 切片拼装还造出假矛盾（拼出的逐行加总 4,005.0 ≠ 子 agent 的 4,389.0）→ 触发第 4 次质询。最终答案自洽（14 人合计正好 4,389.0），说明 4,005 是拼装产物。

### 缺陷 7（P4 的残留逃逸口）：`check_async_task` 的「结果」取的是**最后一条** AI 消息

`full=true` 给了更大的预算，但**取内容的锚点**没变：`result` = 子线程最后一条 `AIMessage`。nl2sql 子 agent 的收尾语是一句 55 字的「以上为查询结果的全部内容…」，于是：

- 真正的 2779 字总结在消息 `[30]`，而 `check_async_task` 取出的是 `[32]`（55 字）→ `full=true` 返回了一个**没有内容**的载荷；
- 主 agent 只好自己找：`since=0` 拉回 10730 chars，再对落盘文件（`large_tool_results/…`）连读 3 页 `read_file`（多烧 4 轮）。主线程实测调用序列：`[8] check_async_task(full=true)` → `[10] check_async_task(since=0)` → `[12]/[14]/[16] read_file`；同一会话 `[22] since=33` 又踩了一次。

> 两个结论：① 第二轮写的 prompt「也不要用 `since=N` 增量读取」**过宽**——这次正是 `since=0` 把数据救回来的，该禁的是「在结果定格后指望 `since` 补新数据」，不是 `since` 本身；② 治本是让 `check_async_task` 取**最后一条带实质内容的** AI 消息，修在 P4 的同一处（`_build_check_result`）；**注意判据不能用「无 tool_calls」**——子 agent 的终稿 `[30]` 恰恰带着 `write_todos` 调用（见下）。

#### 补充核实：落盘的是原始明细，`[30]` 是子 agent 自己写的 digest

逐条读子线程 `01a09edd-7092-70b2-916b-71eb68f60857` 的 state（33 条消息）后确认，**「大内容落盘、子上下文只留摘要 + 局部」这个设计是成立的**，与本缺陷是两件独立的事：

| 子线程消息 | 角色 | 长度 | 内容 |
|---|---|---|---|
| `[5]`/`[8]`/`[15]`/`[17]` | `tool` | — | 正文提到 `large_tool_results/…` = MessageSlimmer 的落盘占位 |
| `[18]`/`[20]`/`[22]` | `ai` → `tool`(read_file) | 9817 / 6376 | **带行号的 JSON 分片**（`301 "…"`、`601 "…"`）= 子 agent 分页把自己落盘的文件读回来 |
| `[25]` | `tool`(wrenai_query_cube) | 9412 | 原始 Cube 结果（未超 16000 阈值，未落盘） |
| `[30]` | **`ai`** | **2779** | 子 agent **自己撰写的终稿汇总**（`## 📊 …工时情况汇总`），**带 `tool_calls=['write_todos']`** |
| `[32]` | `ai` | 55 | 收尾语 ← `check_async_task` 返回的就是它 |

即：落盘文件里是**逐人逐项目逐月的原始明细**，`[30]` 是子 agent 据此写的 digest —— 它从未离开子线程 state，**不是「拿不到」，是 `check_async_task` 取错了那一条**。

**这是结构性必然，不是偶发**：协议要求收尾前调 `write_todos` → 最后一轮是工具调用 → 模型随后必然再补一条「工具已执行」性质的短 AI 消息 → 终稿被顶替必然发生。凡「以工具调用收尾」的 agent 都会中招。
