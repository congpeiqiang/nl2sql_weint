# 混合模型策略指南

## 概述

SQL-of-Thought 框架支持**混合模型部署**——对推理密集型 Agent 使用推理模型（如 Claude Opus 3），对生成型 Agent 使用更便宜的非推理模型（如 GPT-4o）。

该策略可将总成本降低约 **30%**，同时在 100 样本消融实验中保持 **85% 的执行准确率**（相比之下，全 Opus 3 为 95%）。

## Agent-模型映射

### 推理密集型 Agent（使用推理模型）

| Agent | 为何需要推理模型？ | 适合的模型 |
|-------|------------------|-----------|
| **Schema Linking** | 需要深度 Schema 理解、外键推断、语义列映射 | Claude Opus 3, GPT-5, Claude Sonnet 4 |
| **查询计划** | 需要 CoT 推理来生成过程性计划、逻辑分解 | Claude Opus 3, GPT-5 |
| **纠错计划** | 需要基于分类法的诊断推理、根因分析 | Claude Opus 3, GPT-5 |

### 生成型 Agent（使用非推理模型）

| Agent | 为何非推理模型足够？ | 适合的模型 |
|-------|-------------------|-----------|
| **子问题分解** | 遵循清晰模式的结构化 JSON 分解；创造性推理需求少 | GPT-4o, Claude Haiku |
| **SQL 生成** | 计划到 SQL 的映射；遵循过程性计划的明确指令 | GPT-4o, Claude Haiku |
| **纠错 SQL** | 遵循结构化的纠错计划；引导式重新生成，非开放式推理 | GPT-4o, Claude Haiku |

## 成本分析

### 全 Spider 数据集运行（约 1034 样本）

| 配置 | 总成本 | 预估运行时间 | EA（100样本） |
|------|--------|------------|:------------:|
| 仅 Claude Opus 3 | $42.58 | ~5 小时 | 95% |
| 仅 GPT-5 | ~$44.20 | ~5 小时 | 89% |
| **混合：Opus（推理）+ GPT-4o（生成）** | **~$30** | ~5 小时 | 85% |
| 仅 GPT-4o-mini | 更低 | ~4 小时 | 87% |
| 仅 GPT-3.5 | 最低 | ~3 小时 | 67% |

### 单样本成本分解（混合方案）

```
推理模型调用（3 个 Agent × ~$0.03/百万输入 Token + ~$0.15/百万输出 Token）：
  - Schema Linking：~$0.04
  - 查询计划：~$0.06
  - 纠错计划（如需）：~$0.05

非推理模型调用（3 个 Agent × ~$0.005/百万输入 Token + ~$0.015/百万输出 Token）：
  - 子问题分解：~$0.008
  - SQL 生成：~$0.01
  - 纠错 SQL（如需）：~$0.01

单样本（首次成功）：~$0.11
单样本（含 1 次纠错）：~$0.17
```

## 模型选择指南

### 追求最高准确率
```
所有 Agent → Claude Opus 3（$15/百万 Token）
预期 EA：~95%（100样本）→ ~91.59%（全 Spider）
```

### 追求最佳成本-性能平衡
```
Schema Linking → Claude Opus 3
查询计划 → Claude Opus 3
子问题分解 → GPT-4o（$2.5/百万 Token）
SQL 生成 → GPT-4o
纠错计划 → Claude Opus 3
纠错 SQL → GPT-4o

预期 EA：~85%（100样本）
```

### 预算受限部署
```
所有 Agent → GPT-4o-mini（$0.15/百万 Token）
预期 EA：~87%（100样本）

⚠️ 注意：非推理模型更常产生"语法正确但逻辑错误的 SQL"
  - 跨表混淆列
  - 忘记 GROUP BY
  - 选择错误/多余的列
```

### ❌ 不推荐
```
所有 Agent → GPT-3.5（$0.0015/百万 Token）
预期 EA：~67%——对生产环境来说太低

所有 Agent → 开源模型（Llama 3.1 8B, Qwen 2.5 1.5B）
预期 EA：~45.3%——幻觉问题、高延迟（慢 3 倍）、缺少列
```

## Temperature 和超参数

| 参数 | 值 | 原因 |
|------|-----|------|
| Temperature | **0** | 确定性输出；更高的 temperature 会降低计划的忠实度 |
| Top_p | 默认 | temperature 为 0 时无需覆盖 |
| 其他超参数 | 默认 | 保持简单——无需复杂调优 |

## 何时切换模型

| 信号 | 操作 |
|------|------|
| 预算无限制 | → 所有 Agent 使用 Claude Opus 3 |
| 预算适中（约 $30/次） | → 使用混合方案（Opus 推理，GPT-4o 生成） |
| 预算紧张 | → 所有 Agent 使用 GPT-4o-mini（接受 87% EA） |
| 准确率必须 >90% | → 至少 Schema Linking + 查询计划必须使用推理模型 |
| 准确率必须 >85% | → 混合部署足够 |
| 实时延迟关键 | → 避免开源模型（慢 3 倍） |

## 实用实施建议

1. **从混合方案开始**：对生产环境来说最具成本效益
2. **优先升级推理 Agent**：如果准确率低，先升级 Schema Linking 和查询计划到推理模型，再升级生成 Agent
3. **监控错误模式**：如果生成 Agent 产生大量语法错误 → 升级到更好的模型。如果产生逻辑错误的 SQL → 升级查询计划 Agent
4. **缓存 MDL**：通过 `wren context build` 构建后跨查询复用——Schema Linking 成本会显著下降
5. **跟踪纠错频率**：如果超过 50% 的查询进入纠错循环 → 升级查询计划 Agent（更好的初始计划可减少纠错需求）
