# SQL-of-Thought 设计原则

## 核心原则

### 1. 分阶段推理是强制性的

**原则**：在生成 SQL 之前必须先生成查询计划——绝不能跳过此步骤。

**证据**：消融实验表明，跳过查询计划步骤会导致约 5% 的准确率下降（Claude Opus 3：95% → 90%）。

**理由**：LLM 在数学、编程和规划任务中更擅长进行推理。中间推理步骤能够：
- 显式组织相关的 Schema 元素
- 减少幻觉
- 提升自然语言意图与 SQL 输出之间的一致性

**实现**：查询计划 Agent 只生成过程性步骤，绝不生成 SQL。

### 2. 查询计划 Agent 不得生成 SQL

**原则**：计划阶段严格限定为过程性——不包含可执行的 SQL 代码。

**理由**：在规划阶段直接生成 SQL 会将推理与实现混为一谈，导致：
- 过早地锁定特定的 SQL 构造
- 降低 SQL Agent 优化实现的灵活性
- 更高的幻觉率

**实现**：在提示词中明确限制："生成逐步的过程性计划。不要生成任何 SQL 代码。"

### 3. 引导式纠错优于非引导式纠错

**原则**：分类法 + CoT 推理 > 仅靠原始执行反馈。

**证据**：95–99% 的生成查询在语法上已经是有效的。主要的失败原因是**意图不匹配**——逻辑错误但语法有效的查询。原始执行轨迹对纠正这些问题提供的指导非常有限。

**理由**：结构化的分类法能够：
- 对查询失败的原因进行分类（而不仅仅是失败的内容）
- 提供可解释的、基于语言学的诊断
- 给出具体、可操作的修复策略

**实现**：纠错计划 Agent 使用简洁的分类法编码 + CoT 推理模板。

### 4. 简洁的错误编码优于冗长的描述

**原则**：使用分类法子类编码（如 `join_missing`、`agg_no_groupby`）代替冗长的错误描述。

**理由**：冗长的描述会：
- 溢出 LLM 上下文窗口
- 增加延迟和成本
- 降低对实际修复策略的关注度

**实现**：9 个类别，31 个子类，全部使用简短编码名称。

### 5. Temperature = 0

**原则**：所有 LLM 调用使用 temperature 0，以获得确定性和可靠的输出。

**证据**：将 GPT-4o 的 temperature 提高到 0 以上增加了表面多样性，但降低了计划的忠实度——出现了更多无效的 JOIN 和子句误用。

**实现**：所有 Agent 交互设置 `temperature=0`。`top_p` 和其他超参数使用默认值。

### 6. 纠错尝试之间不共享历史

**原则**：每次纠错尝试从头开始——不保留前一次尝试的草稿或历史。

**证据**：通过共享草稿携带历史会导致：
- 上下文窗口膨胀
- 延迟和 API 成本增加
- 重复和 Schema 漂移加剧
- 准确率降低

**实现**：纠错循环每次尝试重置上下文。仅提供当前失败的 SQL + 错误 + 分类法。

### 7. 单一纠错流水线（而非多个按错误类型划分的 Agent）

**原则**：每次尝试使用一个纠错计划 Agent → 一个纠错 SQL Agent。

**证据**：一种包含多个修复 Agent（每种错误类型一个）→ 聚合 Agent 的消融设计失败，原因是：
- 独立的编辑相互冲突
- 合并过程产生不连贯的 SQL
- 协调开销增加了成本却没有带来收益

**实现**：单一统一的纠错流水线，一次性处理所有错误类型。

### 8. 不添加子句特定的硬编码规则

**原则**：不要为单个子句（JOIN、LIMIT 等）添加特定的提示词规则。

**证据**：添加子句特定规则会：
- 膨胀上下文窗口
- 用无关细节分散模型注意力
- 整体降低准确率

**实现**：保持提示词通用，聚焦于计划 → SQL 映射逻辑。

### 9. SQL 重新生成前的结构化推理步骤

**原则**：纠错计划 Agent 必须在错误检测和 SQL 修复之间起到中介作用。

**证据**：一种以自由形式应用完整错误分类法并将错误直接发送给 SQL Agent 的批评者循环表现不佳。LLM 在无引导的调试中表现困难，至少需要一个结构化的推理步骤才能受益。

**实现**：错误检测 → 纠错计划（CoT 推理）→ 纠错 SQL（引导式重新生成）。

## 失败的消融设计（请勿复现）

| ❌ 失败的方法 | 证据 | 原因 |
|-------------|------|------|
| 自由形式分类法 → 直接给 SQL Agent | 表现不如结构化纠错 | LLM 在无引导的调试中表现困难 |
| Temperature > 0 | 降低了计划的忠实度 | 更多无效 JOIN 和子句误用 |
| 子句特定的提示词规则（JOIN、LIMIT） | 降低了准确率 | 膨胀上下文，分散模型注意力 |
| 每种错误类型多个修复 Agent → 聚合 Agent | 完全失败 | 独立编辑冲突，合并不连贯 |
| 纠错尝试间共享草稿 | 降低了准确率 | 重复、Schema 漂移、成本/延迟增加 |

## 混合模型策略

### 原则：推理任务用推理模型，生成任务用更便宜的模型

| Agent | 需要推理？ | 推荐模型类别 |
|-------|:---------:|-------------|
| Schema Linking | ✅ 是 | 推理模型（Claude Opus, GPT-5） |
| 查询计划 | ✅ 是 | 推理模型 |
| 纠错计划 | ✅ 是 | 推理模型 |
| 子问题分解 | ❌ 否 | 非推理模型（GPT-4o） |
| SQL 生成 | ❌ 否 | 非推理模型 |
| 纠错 SQL | ❌ 否 | 非推理模型 |

### 成本-性能权衡

| 配置 | 成本（100样本） | EA（100样本） | 备注 |
|------|----------------|:------------:|------|
| 全 Claude Opus 3 | ~$42.58（全 Spider：~$42） | 95% | 最佳准确率 |
| 全 GPT 模型 | ~$44.20（全 Spider） | 89% | 良好准确率 |
| 混合（Opus 推理 + GPT-4o 生成） | ~$30（全 Spider） | 85% | 良好的成本-性能平衡 |
| 仅 GPT-4o-mini | 更低 | 87% | 预算选项 |
| 仅 GPT-3.5 | 最低 | 67% | 不推荐 |
| 开源（Llama 3.1 8B） | ~$0（自托管） | ~45% | 不适合 NL2SQL |

### 混合方案为何有效

- Schema Linking、查询计划制定和纠错计划需要深度推理——推理模型在此表现出色
- 子问题分解、SQL 合成和纠错 SQL 遵循结构化指导——非推理模型表现足够
- 成本节约：约 30% 的成本降低，同时保持 85% 的执行准确率
