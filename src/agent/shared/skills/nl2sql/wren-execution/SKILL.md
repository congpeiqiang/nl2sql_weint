# 查询执行（run_sql）

## 概述

六步主循环的**最后一步**：(3)(4)(5) 产出的最终 SQL 在这里真正下发。本技能只管**执行与呈现**——SQL 的对错、口径、性能都不在这里改：执行失败要回到产出该 SQL 的技能去修（见「失败处理」）。

## 输入

- 最终 SQL（来自 wren-metric-query 的编译 SQL / wren-sql-author 的手写或混合 SQL）
- 行数上限 N（top-N 由问题决定；未明说时用默认）

## 执行前检查（三条，缺一不可执行）

1. **dry_run 门已过**：该 SQL 必须已经 `dry_run` 通过。**未过 → 先回对应技能修，禁止"先跑了再说"**。
2. **改动过必复验**：SQL 在 dry_run 之后、无论是在步骤(4) 纠错改过还是步骤(5) wren-perf-optimize 优化过，**执行前必须用最终 SQL 再 dry_run 一次**，杜绝"干跑 A 执行 B"。
3. **行数走参数**：按下方行数契约准备 `limit`，**检查 SQL 正文里没有 `LIMIT` 子句**（有就删掉，交给参数）。

## 行数契约（所有 run_sql 通道通用）

- SQL 正文**一律不写 `LIMIT`**：服务端执行时会自动追加行数上限（多取一行探测截断），SQL 自带 `LIMIT` 会构成双重 LIMIT 而**语法报错**。
- **top-N 用 `ORDER BY ...` 排好序**，行数由 `run_sql(sql, limit=N)` 控制。
- `limit` 默认 **1000**，**最大 10000**；"全部/所有"这类问题给足上限，不要省略。

## 只读铁律

只允许 `SELECT` / `WITH ... SELECT`（含 CTE 只读查询）。DML/DDL（`INSERT`/`UPDATE`/`DELETE`/`DROP`/`ALTER`/`CREATE`…）与本系统的 `SET`/`USE`/`CALL` 等一律不执行；发现了就改写为 SELECT，改不了就报告。**循环内任何情况下不调用 `store_query`**（回写由 FeedbackStore 桥接在循环外异步完成）。

## 结果呈现（大结果自动落盘，必须照此办）

当结果表**超过 50 行**、或结果文本**超过 8000 字符**时，服务端已把全量数据自动落盘到
`/workspace/nl2sql_process_data/{thread_id}/query_result/*.md`，你在工具结果里只会看到结构化 JSON：
`{columns, row_count, rows: [前 20 行样例], rows_truncated: true, full_result_file: "…"}`。

此时的最终回复**必须**是：

1. 一句话结论 / 总数（**引用 `row_count`**，不要数样例行数当总数）；
2. 前 20 行样例 markdown 表（**只引用工具结果 `rows` 字段里可见的行**）；
3. 全量文件 VFS 路径（把 `full_result_file` 原样给出），说明完整数据见该文件；
4. **末尾附 `## 业务口径` 块**——逐条一行、三字段 `口径项 | 内容 | 出处`，内容取 §步骤(1) 取料到的 `rules/*.md` / `metrics/指标定义.md` **原文的逐字片段**（从取料返回里直接复制，**不要翻译/概括/合并成「人话」**；长条目可用 `…` 省略中段，最多 3 处、省掉的字数不得多于引到的字数），出处**照抄取料返回里出现的那个文件名**（裸名即可，如 `报工与工时.md`、`报工与工时.md R3`——**不必也不要自己拼 `rules/` 前缀**，返回里文件名本来就是裸的，凭印象拼的路径可能不存在）；只写本次结论真正依据的口径（3~6 条）。主 agent 生成报告时**原样抽走这一节** ⇒ 缺了报告里就没有业务口径。本节的 `出处 + 内容` 会被**程序化逐字核验**，不过的打回重写（≤2 次），最终仍不过的在报告里单列标注「不是知识库原文」。
   **什么时候才允许整节不写**：只有「纯明细列举、本次结论确实一条口径都没用到」才可以省略，并在末尾单独一行写 `本次未依据知识库口径`；**用到了下列任一项就是必写**：统计窗口/时间范围、有效记录口径（软删/状态过滤）、人员或口径池（在职/应报工）、表或视图的选择口径、比率的分母。**取料返回里带编号的规则条目（`R1`/`R6`/`R8`）就是给这节用的**——不要只写「统计口径说明」这种自述，那不算交出口径。**本轮取过知识料却没有这一节，系统会直接打回。**

**禁止**：把全量数据逐行重打回回复；用 `read_file` 读该 `query_result/*.md` 后照抄内容；把样例行数（20）误当业务统计口径——业务行数以 `row_count` 为准；凭印象补口径或编造出处。出处与内容两种具体错法（生产实测）也禁止：**① 把库对象当出处**（表名、视图名 `v_workhour`、Cube 名 `workhour_analysis（Cube）`、「语义库字段字典」、「MDL」都是**被口径约束的对象**，不是口径来源）；**② 把原文改写成自己的话**（`if_approve = 1 的 work_hour` 写成「审批通过的工时」——改写过的内容在核验里等同于编造）。重写时**只能引本次取料返回里真实出现的原文**，取不到依据的条目直接删掉，**但不要因为删条目而把整节省掉**（整节省掉＝用户彻底看不到口径，比引错一条更糟）。

## 失败处理

| 失败类型 | 动作 |
|---|---|
| 语法 / Schema / Join / 过滤 / 聚合 / 值 类 | 按九大类错误分类法诊断，输出精简错误编码（如 `join_missing`、`agg_no_groupby`）→ **回 wren-sql-author 修正**（≤3 次）→ 重 dry_run → 回本步重执行 |
| 超时 / 权限 / 连接 / 工具异常（非 SQL 问题） | **不在本技能内重试执行**（重试只会再撞同一面墙）；据实返回失败与错误文本，交由编排器判定降级或转澄清 |

- 相同 `error_code` **连续 2 次**出现 → 判定"卡住"，终止并输出最后 SQL + 全部诊断历史，不要再试。
- 每次修正不携带前次尝试的闲聊历史（只带当前失败 SQL + 错误信息 + 分类法诊断）。

## 与其他技能的分工

- **不生成/不改 SQL** → wren-sql-author；**不判路由** → wren-orchestrator；**不做性能优化** → wren-perf-optimize；**不检索** → wren-retrieve（取料包只在步骤(1) 取一次）。
- 执行成功后按编排器的 todo 纪律，把「查询执行」标 completed、下一步标 in_progress，**真正写完最终回复后**才标最后一步 completed。
