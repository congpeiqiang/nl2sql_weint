### 一、现状分析

当前项目的图表渲染链路如下：

```
主智能体 (main_agent.py)
  └── tools = mcp_tools (来自 tools/mcp_tool.py)

              ├── npx -p semiotic semiotic-mcp
              └── 提供 suggestChart / renderChart / getSchema 等图表工具

**关键点：**
- 图表工具通过 `MultiServerMCPClient` 以 **stdio** 方式加载
- 配置硬编码在 `_get_main_server_config()` 中
- 主智能体通过 `create_deep_agent(tools=mcp_tools)` 注入工具

### 三、适配方案

#### 方案 A：提示词模板化（推荐）

**思路：** 将提示词中的图表规范部分改为**动态模板**，根据 `CHART_ENGINE` 环境变量在加载时注入对应的图表规范。

**实现方式：**

```
prompt/
  ├── MAIN_AGENT_PROMPT.md          # 基础提示词（不含图表规范）
  ├── chart_specs/
  │   ├── semiotic.md               # Semiotic 图表规范（现有内容）
  │   └── echarts.md                # ECharts 图表规范（新写）
```

在 `main_agent.py` 中动态拼接：

```python
from agent.settings.setting import settings

# 读取基础提示词
base_prompt = _SYSTEM_PROMPT_PATH.read_text(encoding="utf-8")

# 根据 CHART_ENGINE 注入对应的图表规范
engine = settings.CHART_ENGINE.lower()
chart_spec_path = Path(__file__).parent / "prompt" / "chart_specs" / f"{engine}.md"
chart_spec = chart_spec_path.read_text(encoding="utf-8")

# 用占位符替换
SYSTEM_PROMPT = base_prompt.replace("{{CHART_SPEC}}", chart_spec)
```

**优点：**
- 提示词与引擎解耦，切换引擎只需改 `.env`
- 每个引擎的规范独立维护，互不影响
- 不需要在提示词中写条件判断

**缺点：**
- 需要重构现有提示词，将 Semiotic 相关内容抽离到独立文件

#### 方案 B：提示词内条件分支

**思路：** 在提示词中保留两套规范，用条件标记区分。

```markdown
### 图表渲染规范

{{#if echarts}}
使用 ECharts MCP 工具渲染图表...
{{else}}
使用 Semiotic MCP 工具渲染图表...
{{/if}}
```

**优点：**
- 单一文件，无需拆分

**缺点：**
- 提示词文件会变得臃肿
- 需要引入模板引擎（如 Jinja2）或自定义替换逻辑
- 两套规范混在一起，维护困难

#### 方案 C：运行时动态注入（最灵活）

**思路：** 不修改提示词文件，而是在 `main_agent.py` 中根据 `CHART_ENGINE` 动态生成完整的系统提示词。

```python
def _build_system_prompt() -&gt; str:
    base = _SYSTEM_PROMPT_PATH.read_text(encoding="utf-8")
    engine = settings.CHART_ENGINE.lower()
    
    if engine == "echarts":
        # 追加 ECharts 图表规范
        echarts_spec = Path(__file__).parent / "prompt" / "chart_specs" / "echarts.md"
        return base + "\n\n" + echarts_spec.read_text(encoding="utf-8")
    else:
        # 默认 Semiotic（现有提示词已包含）
        return base
```

**优点：**
- 改动最小，现有 Semiotic 提示词不动
- ECharts 规范作为追加内容注入
- 切换引擎只需改 `.env`

**缺点：**
- 如果基础提示词中已有 Semiotic 内容，ECharts 模式下会同时存在两套规范，可能造成 LLM 混淆

   156	## 九、必须遵守的九大设计原则
   157	
   158	以下原则来自论文的核心发现和失败消融教训，每一个都是经过实验验证的最佳实践，**必须严格遵守**：
   159	
   160	### 原则 1：阶段化推理不可跳过
   161	
   162	- **规则：** 永远先生成 Query Plan，再生成 SQL。**绝对不允许跳过 Query Plan 步骤。**
   163	- **原因：** 消融实验显示跳过 Query Plan 会导致约 5% 的准确率下降。中间推理步骤能显式组织 Schema 元素、减少幻觉、改善 NL 意图与 SQL 的对齐。
   164	
   165	### 原则 2：Query Plan Skill严禁生成 SQL
   166	
   167	- **规则：** Query Plan Agent 的输出必须是**纯文本的步骤式执行计划**，不包含任何 SQL 代码片段。
   168	- **原因：** 推理阶段就生成 SQL 会导致过早承诺特定 SQL 构造，降低下游 SQL Agent 的优化灵活性，增加幻觉风险。
   169	- **实施：** 如果在 Query Plan 输出中发现 SQL 代码，**必须丢弃该输出并重新生成**。
   170	
   171	### 原则 3：分类法引导 &gt; 无引导纠错
   172	
   173	- **规则：** 纠错时使用**结构化错误分类法 + CoT 推理**，而不是仅凭原始执行错误信息。
   174	- **原因：** 95-99% 的生成查询在语法上是有效的，主要失败是意图不匹配（逻辑错误但语法正确的查询）。原始执行 trace 提供的指导非常有限。结构化分类法能诊断"为什么会失败"而不只是"什么失败了"。
   175	
   176	### 原则 4：使用精简错误编码，不用冗长描述
   177	
   178	- **规则：** 在纠错诊断中使用分类法**子类编码**（如 `join_missing`、`agg_no_groupby`），而非冗长的自然语言描述。
   179	- **原因：** 冗长描述会溢出 LLM 上下文窗口、增加延迟和成本、降低对修复策略的聚焦。
   180	
   181	### 原则 5：Temperature 必须为 0
   182	
   183	- **规则：** 所有 LLM 调用必须设置 `temperature=0`。
   184	- **原因：** 升高 temperature 会降低计划忠实度，导致更多无效 JOIN 和子句误用。
   185	
   186	### 原则 6：纠错尝试间不共享历史
   187	
   188	- **规则：** 每次纠错尝试都从零开始——**不保留前一次尝试的 scratchpad 或历史**。
   189	- **原因：** 共享历史会扩展上下文窗口、增加延迟和 API 成本、放大重复和 Schema 漂移，最终降低准确率。
   190	
   191	### 原则 7：不添加子句特定的硬编码规则
   192	
   193	- **规则：** 不要在 SQL 生成的 Prompt 中添加针对特定子句（JOIN、LIMIT 等）的特殊规则。
   194	- **原因：** 子句特定规则会膨胀上下文窗口、用无关细节干扰模型、整体降低准确率。
   195	
   196	### 原则 8：结构化推理步骤必须先于 SQL 重新生成
   197	
   198	- **规则：** 在错误检测和 SQL 修复之间，必须通过 **Correction Plan Agent** 进行结构化 CoT 推理。
   199	- **原因：** 直接将错误分类法以自由格式发送给 SQL Agent 的效果明显不如通过结构化推理步骤。LLM 在无引导调试中表现不佳。
   200	
   201	### 原则 9：进度追踪（必须执行）
   202	
   203	每次收到任务后，立即用 write_todos 创建进度列表。每完成一个步骤，立即更新进度。
